# 简报、Tick 通知与回执的条数预算及优先级设计

> 状态：设计提案，未实现、未批准为现行产品合同。
> 日期：2026-11-06。
> 源码基线：远端 `main` 的 `d920c6250ac844ee5f6aed7f37af0ff700ef33ae`（PR #1019）。
> 交付范围：仅本设计文档。配置名、字段名和行为变化凡标为“建议／拟新增”，均不能用于当前版本。

## 1. 问题与成功标准

用户希望在默认五条建议中先看到值得采取行动的内容，并能分清“没有建议”“有建议但未展开”和“数据不足，无法判断”。增加上限只能缓解拥挤，不能解决顺序、重复和信息丢失问题。

本方案的成功标准是：

1. 当前有效的移仓和平仓建议先于普通观察行参与选择；增加普通 hold 或开仓候选，不能把本来能展示的持仓动作挤掉。
2. 条目选择、账户／分区／整份预算和最终渠道大小限制遵循同一选择计划；本轮变化不再隐式突破上限。
3. 在允许合并的范围内，同一动作的多个 lot、多个账户可共用展示卡；每个账户仍有独立事实、容量、通知身份和送达证据。
4. 每次省略都能说明数量、类别、约束层和查看范围。未知数量不得显示为零。
5. 回执说明历史发送了什么，不承担完整建议清单的职责；其读取保护不被误当作推送条目上限。
6. 每个有效固定报告时间都必须生成并送达该批次报告，无论与上一份相比是否有变化、是否有新候选；不得通过少发、停发、合并到下一批或延后发送来控制篇幅。正常无变化及真实空态都必须明确表达，不能伪装成扫描失败或直接静默。

### 1.1 用户提供的生产证据

以下是任务输入中的生产实测，作为设计要解决的历史问题保留；本次没有重新读取生产主机、账户、配置或券商数据：

- 某账户有 13 个持仓，按 `recommendation_state`、剩余最高年化、净兑现比例和身份排序后，五个普通观察行排在前五。两笔移仓结果为 `roll_advice.outcome=found`、`roll_notification_eligible=true`，被排在第六、七位，没有出现在简报中；输入称其 `net_income` 分别为 2040、1523。
- 无开仓候选的另一个账户能看到五条移仓，而有开仓候选的账户没有看到移仓，形成“建议更多、展示反而更少”的体验。
- 同一标的在两个账户重复展示，各占一个名额。按账户及市场独立输出时，多个账户的总信息量很快增加。
- 总条数、分区条数、账户持仓提醒条数和回执读取保护没有统一说明，用户无法判断缺失发生在哪一层。

这组证据没有绑定到本设计基线的完整运行输入，不能直接证明当前 `main` 仍由同一机制产生这些现象。尤其不把开仓候选的存在认定为持仓被挤掉的源码原因。

### 1.2 核对后的现状修正

本地任务开始时的 `main` 是 `2ff8514b3`，落后于已核验的远端 `main`。本提案使用上述远端基线，避免忽略当天已合入的修复。

| 输入中的描述 | 当前基线的实际行为及影响 |
|---|---|
| `_MAX_TOTAL_ITEMS=40` 是简报总条数 | 常量确实为 40，但候选视图和持仓视图分别新建 `_RenderBudget`。Wheel、资金、提醒等也没有共享此对象。不能将其称为整份消息最多 40 条。合成回放中，25 个变化候选与 25 个变化持仓动作可同时进入视图，共 50 条。 |
| actions=5、candidates=3、rejections=5 是分区硬上限 | 三个配置默认值属实，校验范围均为 1–20。候选和持仓采用 `max(配置值, 变化项数量)`，因此变化项可突破 3／5。`max_rejection_reasons` 只被定义、校验及归一化，当前 renderer 没有消费它；它不是实际生效的拒绝原因上限。 |
| 普通 hold 与移仓同级，争夺五个展示名额 | 原始 Close Advice 排序确实为 close → hold → 其它，随后剩余最高年化升序、`net_capture_ratio` 降序及身份。当前渲染先过滤普通 hold／not_evaluable，再对有效移仓分组，然后应用展示名额；已不是“先取五个原始持仓再过滤”。 |
| `close_advice.max_items_per_account=5` 限制所有持仓建议 | 当前 service 只用它截取合格的 CLOSE 通知行、生成平仓 action 及 `notification_eligible`。全部原始 close rows 仍进入 `positions`；移仓有独立标志及有效性检查，不受这个 CLOSE 上限直接限制。0 表示本层不限，仍受展示／渠道限制。 |
| 账户上限不按市场 | 配置键没有 market 后缀，但 Daily Brief 每次按账户和市场组装，所以运行效果是“每账户 × 每市场”。底层 CLOSE selector 自身只按 account 分组，不能把所有调用者都称为双维分组。 |
| 没有开仓候选，五个名额就全部给移仓 | 当前候选和持仓的展示预算独立，持仓选择不读取候选数量。空候选不意味着获得额外的持仓名额。 |
| 同标的重复各占名额 | 跨账户尚未合并；同账户移仓已按动作分组：方向、标的、旧到期日、旧行权价和目标合约一致的多个 lot 共用一张卡。仅目标合约相同、旧仓不同的动作仍分别保留。 |
| `_MAX_MESSAGE_CHARS=12000` 是最终唯一大小限制 | 正文截断使用 Python 字符数；飞书另有内容 UTF-8 字节和完整请求体保护，卡片与备用正文还会再次裁剪。最终限制不能只按字符判断。 |
| 回执最多 500 行／2 MB | `MAX_SOURCE_ROWS=500` 和 `MAX_SOURCE_BYTES=2*1024*1024` 是部分来源的读取保护，不是返回建议数量；并非所有来源都统一受二者限制。详见第 7 节。 |

生产输入中的 `net_income` 在此仅保留原称谓。当前移仓首位候选的净现金字段是 `net_credit`，年化是 `incremental_annualized_return`；`net_income` 也用于开仓候选，不能不核对载荷就互相改名或比较。

## 2. 方案对比与裁决

| 方案 | 规则 | 收益 | 代价及不能解决的问题 |
|---|---|---|---|
| A：保留各层独立上限，只把移仓排前或增加持仓上限 | 原账户通知保持不变，局部改排序／数字，补省略文案 | 改动小；可以验证单个入口不漏移仓 | 字符和渠道裁剪仍可能删除后面的高价值内容；无法解释不同层计数；跨账户重复仍占名额。当前 main 已做一部分过滤、分组，继续叠加局部补丁收益有限。 |
| B：统一展示选择计划，默认账户隔离，可显式合并同市场账户 | 事实完整保留；资格、聚合、优先级、配额和传输裁剪逐层执行；同一计划驱动正文、卡片、摘要及确认身份 | 明确五条含义；预算可解释；能控制重复；不再把展示条数当事实条数 | 未来实现需调整 service 提前切片、renderer 及冻结 envelope 的职责；账户合并会显式改变产品呈现合同，不能由相同收件人自动推导。 |
| C：默认跨所有账户、市场建立一个收益评分和总配额 | 汇总后按总净收入等单一分数选前五／四十 | 消息少、表面上容易比较 | 币种、资金、策略目标和授权不可互换；大账户压倒小账户；可能把条件性交股改善当现金收益。需要新估值模型，且破坏市场／账户隔离。 |

**推荐 B。** 默认仍按账户和市场独立输出。跨账户合并作为 B 的显式可选能力，仅对配置列出的同市场账户组生效，且整组接收范围必须全部获授权。默认不启用合并；因此默认变更解决排序和预算问题，生产重复问题需另行启用账户组后才消除。不能宣称默认值一改就消除了所有跨账户重复。

不采用“重复行权重减半”：两个账户各自的建议仍有效，减半不能节省展示空间，还可能使两个副本同时落选。可安全合并时合并；不能合并时保留各账户建议，接受必要的重复。

## 3. 单位、作用域与信息保留

### 3.1 四种数量必须分别命名

- **源行数**：扫描实际评估的持仓 lot、候选合约等事实行，不受展示配额裁切。
- **展示条数**：一张完整的决策卡，含执行所需的合约及账户信息。一个 lot 同时有平仓和移仓时，是一张卡中的两个备选建议；必须说明二者互斥，不暗示平仓后还能再执行同一旧仓的移仓。
- **账户占用数**：一张跨账户合并卡在每个成员账户分别占一条账户配额；在整份消息只占一条。它并不创造额外资金或让某账户绕过上限。
- **投递消息数**：同一逻辑报告在不同渠道／route 的副本数。复制不再次消耗展示条数，但必须分别记录投递结果。

标题、时间、资金汇总、缺失数据标记、省略脚注及分类数量摘要不算决策卡，但占用正文和请求体大小。不得借“摘要不计条数”塞入另一份逐条建议清单；只允许类别、数量、受影响账户和查询入口等摘要。

正常无动作时，固定报告的空态说明不占五条动作名额，实际动作计数为 0；不填充普通 hold、伪建议或其它无意义条目。若仍有与上轮相同且当前有效的动作，“无变化”仅是状态说明，这些实际动作照常进入快照、参与条数预算，不能把无变化误当作无动作。

### 3.2 预算的作用域

默认是“一个账户 × 一个市场 × 一个固定批次或增量通知”的逻辑报告。显式账户组启用后，改为“一个账户组 × 同一市场 × 同一固定批次或兼容的本次增量”的逻辑报告。

整份 40 条是该逻辑报告的硬上限，不是全天累计、整轮 Tick 所有市场累计或所有重试累计。两个市场分别生成计划；历史冻结 envelope 的精确重试复用原计划，不能因为本轮有新内容就重新分配旧消息的名额。不新增一个会压掉故障／恢复回执的 Tick 全局消息数闸门。

固定批次的发送义务先于本节所有展示预算。动作配额耗尽、业务内容无变化或没有候选，都只能影响正文中的展开方式，不能取消或推迟该批次。账户组合并只能在同一固定批次内合并展示，不能等待另一账户的新变化、跨批次攒报或降低任何账户的固定报告频率。

### 3.3 信息保留边界

展示选择不修改策略结论、原始结果、完整候选身份集合或资金容量。未来实现需要从现有封存报告／候选快照读取未切片的合格集合，然后选择展示项；不能只拿当前 service 已取前 3 的候选当作全部来源。

用户看到的状态至少区分：

| 状态 | 可使用的表述 |
|---|---|
| 来源完整且确实无合格建议 | “本轮无符合条件的移仓／平仓建议” |
| 有合格建议，但预算省略 | “有 8 条持仓动作，本次展示 5 条；另 3 条移仓未展开” |
| 仅部分来源完整 | “已确认至少 5 条建议；另有数据缺口，总数未知” |
| 历史建议现在已过有效期 | “历史移仓结果已过期，当前不可据此执行” |
| 普通观察或无法评估未逐条展示 | “普通观察 6 笔；另 2 笔无法评估，详见数据说明” |

“折叠”仅用于有真实结构化内容、确有查询途径的摘要。省略不是交互式展开控件，也不是用户已经读过该建议的证据。

## 4. 推荐的优先级与排序细则

### 4.1 资格先于排序

现行策略 owner 继续判断是否可以建议，不由展示层重做收益或风控计算。

- 移仓：`outcome=found` 只是必要条件。还需状态、旧 lot／合约身份、正净现金、现行 CC／Put 规则、`roll_notification_eligible` 和 `actionable_until_utc` 等现有门禁通过。过期、零净现金、净支出、身份不一致的结果不得靠排序进入可执行档。
- 平仓：现行 policy、完整经济指标、有效报价与证据、`recommendation_state=close` 等现有 selector 条件通过。不能只检查一个 close 字符串。
- 开仓：封存候选合格、容量至少一手、必需证据完整；资金待结算、容量未知或其它门禁阻断时不标作可立即执行。
- `planning_only` 和 `blocked` 保留现行语义：计划期内容必须标明仅供计划，不能被本设计升级为当前可执行建议。

此后说的“可执行”均指证据和策略允许用户当前考虑执行，系统仍不下单，也不保证实际成交价格。

### 4.2 档位及每档内部顺序

| 档位 | 内容 | 内部顺序与展示规则 |
|---|---|---|
| A：已有持仓的可执行动作 | 合格移仓、合格平仓；同旧仓同时成立的合为备选动作卡 | 先处理具有已证实业务截止点、且早于下次固定报告的动作，按截止点升序。其余使用下述平仓／移仓双队列规则。报价剩余有效期仅作资格与同分判断，不把报价更陈旧自动视为更有价值。 |
| B：可执行开仓机会 | 当前合格且有容量的 CSP、CC、Combo、Wheel 开仓建议 | 各策略内部严格沿用封存排名，不改业务评分。跨策略按 rank 轮转：先各策略 rank=1，再 rank=2；同 rank 的固定顺序 CSP、CC、Combo、Wheel。本轮新增／变化只在同一策略同一业务排名的同分情况下先展示。 |
| C：需知情、通常无需交易 | 来源已证实的临期、指派／交割时间临近、相关事件提醒 | 已证实事件／最后可交易截止时间升序，再按现有 owner 的严重性顺序、账户、市场、标的和事件身份。未证实的时间排后并标“时间待核实”，不按零天处理；不从 Delta 或不完整日历推断指派已发生。 |
| D：普通 hold | 没有 A／C 的有效持仓观察结论 | 默认只汇总，不占五条。用户显式查询明细时，剩余最高年化升序、净兑现比例降序，再按账户、市场、标的、旧合约／lot 身份；缺值排末。 |
| E：not_evaluable | 缺报价、日历、费用、覆盖或身份冲突等 | 默认不形成交易建议卡。先按现有 owner 判定的阻断程度，再按受影响账户、市场、标的、原因和 lot 身份展示缺口摘要；阻断当前决策的事实进入强制状态区。 |

C 档只是投影已有日历、风险、生命周期事实及 attention 标记，不新增“DTE 小于某数必须交易”的策略。本基线 renderer 并未完整展开所有此类信息；未来接入时必须绑定现有 owner 的信号和事件时间。无该事实来源时显示未知，不临时发明临期窗口。指派是 OM 接受的策略结果，不能把“接近指派时间”写成损失或强制平仓理由。

### 4.3 A 档双队列：不把异质收益相加

移仓和止盈平仓之间没有已批准、可直接比较的统一收益分数。采用确定的双队列，代价是放弃声称选出了数学意义上的全局收益最优五条：

1. 对同一个旧仓，合并平仓和移仓备选，经济字段分别保留；不重复占名额。归入移仓队列，保留“同时建议平仓”。
2. 有明确且即将发生的业务截止点的动作先选。这个集合不能由“本轮变化”或短报价 TTL 扩大；没有已证实截止点时不获得该优先。
3. 其余平仓队列按剩余最高年化升序 → `net_capture_ratio` 降序 → 旧仓最后可交易时间升序 → 稳定身份。
4. 其余移仓队列按首位合格目标的 `incremental_annualized_return` 降序 → 方向对应行权价调整比例降序 → `extension_days` 升序 → 同币种 `net_credit` 降序 → 稳定身份。只选择 producer 已排序的首位目标，不重选新合约；不使用 CC 的条件性交股改善替代净现金年化。
5. 两队列轮流取首项；没有业务截止差异时先平仓、后移仓。任一队列为空，剩余名额全部给另一队列。已合并进移仓卡的平仓不再进入平仓队列。
6. 有限数值缺失排末，必需经济字段缺失则回到资格失败，不能用 0 补齐。最终稳定身份包含市场、账户和旧仓／动作身份，排序不依赖 CSV 行序。

这里的轮流不是一组可配置权重。它使默认五条在两种动作都存在时通常包含至少一种移仓和一种平仓，避免任一同档子类永久霸占名额；有更早业务截止点时仍允许另一子类全部让位。候选排名及收益均来自原 owner；展示层不重新估值。

### 4.4 五条目标、反例及保底裁决

A 先于 B，B 先于 C 的完整卡。D／E 用摘要，不拿普通 hold 填满五条。五条是最多五张决策卡，数据不足时允许更少，不能为凑数降低资格。

不设置“每个档位固定一条”的硬保底。五条有限时，强制给 hold、not_evaluable 或每个策略留位，会重新挤掉可执行动作。C／E 中影响当前决定的提醒通过强制状态摘要保证知情，不保证独立卡片名额。

明确接受以下取舍：

- 有七条有效持仓动作和一个开仓机会时，默认先展示五条持仓动作，开仓可能只留“另有机会未展开”的摘要。B 不承诺每次有独立卡片。
- 一笔大额、低年化移仓可能排在一笔金额较小、高年化移仓之后。2040／1523 本身不足以决定名次；若业务希望净现金总额优先，属于另一个需批准的排序目标，本提案不暗改。
- 双队列可能让经济性较弱的平仓排在下一条移仓前；这是跨异质建议保留多样性的固定取舍。具备同仓备选时不占两条。
- 大量确定的即将到期动作可以占满五条，非紧急移仓仍可能未展开。此时必须写明省略，不保证“所有 found 都推送”。
- 临近交割的信息即使没有独立卡，仍在摘要中可见。它不被误读成“必须操作”，也不能被普通候选或尾部字符截断抹掉。

## 5. 统一分层预算及降级顺序

### 5.1 执行顺序

| 层 | 何时生效 | 约束／让位规则 | 超限后的行为 |
|---|---|---|---|
| L0：事实与资格 | 完整读取和规范化后 | 有效性、授权、策略门禁先于一切预算；源读取失败不能当零建议 | 保留不可用／部分状态；无依据的动作退出可执行集合，原因进入缺口摘要 |
| L1：聚合与排序 | 任何展示切片之前 | 同一展示动作聚合、保留成员身份，再形成 A–E 队列 | 不丢原始行；重复展示合并，语义不同的动作不强并 |
| L2：账户及分区 | 从队列取卡时逐张检查 | 默认每账户 5 张，所有 A／B／C 共用。各策略候选默认最多 3 张。更高档先取，较低档让位；变化项无豁免 | 整张省略，记录 `account_limit` 或 `section_limit`；未使用名额可供同账户其它未达上限的内容使用 |
| L3：整份报告 | 与 L2 同一次分配检查 | 整份最多 40 张；账户剩余额度及分区剩余额度不能突破它 | 整张省略并记 `report_limit`；不是把已排好的一大段正文直接切尾 |
| L4：正文及渠道 | 对已选卡计量、排版后 | 强制状态区、完整动作和省略摘要必须一起容纳；字符、UTF-8 内容及完整请求体均须过限 | 先紧凑表达，再从最低档／该档末尾撤掉整卡，回写选择计划及省略原因，直到满足所有渠道限制 |

L2、L3 是一次选择的联合约束，不能先把每区各自前五不可逆截掉，再拼接执行总限制。逐卡检查固定为账户 → 分区 → 整份；多个限制同时不足时，按此顺序记录第一个不满足者为首要省略原因，不扣减任何已用额度，也不在后续层重复计算同一张卡。已通过条数分配、最后因 L4 被撤掉的卡单记大小限制。

默认上限关系是“账户 5、策略 3、整份 40、长度／字节硬限”，不是把四个数相乘。把账户上限设为 0 只取消 L2 的账户约束，L3／L4 仍生效。预算只减少展开，不会扩大资格。

### 5.2 共享名额与账户公平性

同一账户内，空候选区的剩余空间可以用于 A；有候选区也必须先分配 A，不存在“开仓先渲染所以持仓拿不到名额”。普通 hold 不占份额，候选不足不额外生成持仓动作。

默认不同账户不共享配额。显式账户组合并后：

- 每账户上限仍独立。无持仓／无候选账户未用的名额不能让另一个账户超过其五条；若操作者希望放宽，修改该上限，而不是静默借用。
- 整组 40 张是共享上限。先在当前最高非空档中按账户轮流提供一张，下一轮继续，未达到上限的账户使用剩余空间；相同档中尚未获得一张的账户先于已获得多张的账户。每账户内部沿用第 4 节排序。
- 每轮使用规范化账户名的稳定顺序；前一轮合并卡已经覆盖的账户视为本轮已获得一张，避免重复领取。跨账户合并卡在整份只占一张。
- 合并卡的每个成员账户都必须有剩余额度。某成员已经达到上限时，先拆回账户动作，仅让仍有额度的成员参与选择并重新计量正文；达到上限的成员记为账户层省略，不能借另一成员的名额展示或确认。
- 高档先于低档；同档账户公平性先于跨账户经济指标比较。极端情况下 40 条不足以覆盖所有账户，仍可能有账户为零，必须列出受影响账户和数量，不宣称存在普遍保底。

这会让一个经济性较弱账户的首条先于另一个账户的第五条出现，属于明确接受的公平性代价；不能声称它按全组现金收益最大化。配置同一份上限的有候选账户，不会仅因为有开仓机会而失去本应入选的 A 档动作。

### 5.3 最终大小和信息丢失

推荐停止对交易动作使用任意字符切片。未来正文组织顺序为：状态及时间 → 强制缺口／临近事项摘要 → 已有持仓动作 → 开仓机会 → 其它知情卡 → 资金 → 展示范围说明。

强制区域提前预留实际编码长度：账户／市场／数据时间／计划期或阻断状态，影响当前判断的缺口及临近事项摘要，展示／省略的分类计数和查询说明。其它区域使用剩余空间。强制区域自身过长时按账户及原因折叠摘要，不枚举全部身份；受影响数量未知就明说未知。

降级依次为：删除重复标签和解释性长文 → 相同原因汇总 → 将低档卡转为计数摘要 → 从低档、低排名开始整卡移除。核心合约、账户、执行方向、关键现金／收益指标、有效期及影响该建议的缺口不可拆散；跨账户成员信息放不下时拆成各自独立卡并重新计数，不能只保留部分成员却确认全部。

即使 0 张动作能完整放下，也要保留“发现 N 条／至少 N 条，但正文大小限制未展开”的消息；真实零动作则明确“扫描正常，本轮无符合条件的动作”，不得混淆两者。正常无变化说明、计划批次、实际数据时间和必要的持仓／资金状态属于固定报告的受保护内容，不受五条动作配额抑制。

L4 只能压缩报告内容，不能取消固定批次。若最小状态消息仍超过渠道限制，作为 `render_unavailable` 记录可见的渲染／投递故障，该批次不得记为已送达；必须进入既有故障处理及投递恢复流程，不能把它当成正常空态、无变化或省略发送的优化。外部渠道故障不能保证物理上准时送达，但必须保留原计划时间、实际尝试／确认时间及失败证据，不能算作按时送达验收通过；正常可用条件下不得策略性延后。

L4 撤卡后不从剩余内容回填其它高长度动作，避免反复选取、结果不稳定；记录最终保留集合即可。

通用正文维持 12,000 Python 字符硬限。当前飞书的本地保护分别为 24 KiB markdown 内容、28 KiB 完整请求 JSON，后者含 recipient、UUID、结构及 escaping；它们是本项目保护值，不声称等于供应商公开最大值。飞书主卡、备用 post 以及冻结正文必须携带同一组完整动作。优先、备用均需在冻结前计量，不依赖发送时才报超大错误。

## 6. 跨账户去重的精确边界

### 6.1 推荐的合并条件

同标的不是同动作。合并限于以下条件全部成立：

1. 同一市场、交易日及逻辑批次；来源各自有效，具备可比较且仍有效的证据；不混用历史重试与本轮新建议。
2. 操作者显式配置了该账户组，接收范围中每个接收方都有组内每个账户的完整查看权限；发送前继续沿用既有账户／route 授权复核。相同聊天 ID 本身不构成合并授权。
3. 移仓的策略方向、旧完整合约、目标完整合约及币种相同；平仓的旧完整合约及动作相同；开仓的策略族及全部腿的完整合约相同。不得仅凭标的或目标合约相同合并。
4. 业务限定、缺口及动作可执行性一致。不同的备选动作组合、覆盖条件、有效期状态或风险警示导致不同决定时，保留独立卡。只存在数量、手续费、资金容量、收益数值差异时，可在完整账户子行中分别呈现。

卡片写明涉及账户及各自手数、净现金／成本、容量和有效期。跨账户收益默认不相加；跨币种和资金一律不合并。同账户多 lot 的同一动作可以沿用已有聚合并显示总手数、净现金及成员数，仍保留全部成员的来源身份。

### 6.2 对现行产品合同的影响

现行通知 PRD 要求固定报告按账户、市场分别发送。账户组是本设计有意提出的可选产品变化，后续实现必须同步修改该合同，并证明既有 route、冻结消息、逐账户确认和未知投递状态仍成立；本文件不把这些修改算成已经获批或已经完成。

不能合并时，不使用权重减半压制任一账户的有效动作。默认隔离报告中的必要重复是接受的风险。不同市场永不共享条目或资金预算；所谓“按市场统一”限于同一市场中显式获准的账户组。

## 7. Tick 通知、送达与回执的一致性

### 7.1 相同选择语义，不同内容范围

**硬约束：`fixed_report` 是每个有效固定时间必发的当前完整快照，与业务内容是否变化无关。** “完整”指覆盖当前候选、持仓、资金、状态及必要缺口，不是只发相对上轮的差异；逐条展开仍服从第 5 节预算，并明确省略范围。无变化时也按计划生成、发送及确认，不能因无新候选、内容摘要相同、动作数为 0 或已提醒身份相同而跳过、延后或降为纯心跳。固定报告中的相同动作可以每个固定批次再次出现；候选身份的同日去重只控制增量提醒，不能去重掉新的固定报告批次。相同固定批次的重试仍保持幂等，不重复发送已确认消息。

`candidate_alert` 是有符合既有通知条件的新增候选／移仓变化时才产生的附加通知，只从原生命周期判定为待提醒的集合取卡；普通排序、报价变化或原地不变都不自动触发它。它不能替代固定报告，也不能成为固定报告等待变化的理由。主动查询读取指定范围的快照，回执读取历史事件及保存的正文；四者不能统一成一个“建议条数”。

| 本轮条件 | 固定批次 | 非固定的有效增量时点 |
|---|---|---|
| 扫描正常、与上轮完全无变化，仍有有效动作 | 发送当前快照，明确“扫描正常，与上轮相比无业务变化”，照常展示当前动作及省略说明 | 不因无变化生成新的 candidate_alert；既有冻结消息重试按原规则处理 |
| 扫描正常、无变化且真实零候选／零可执行动作 | 发送正常空态报告，明确无候选／无动作及持仓、资金状态，不能什么都不发 | 不新建 candidate_alert |
| 有符合通知条件的新候选／移仓 | 发送固定快照并承载变化，不另用 candidate_alert 替代；沿用同批不额外双发的规则 | 按现有门禁生成附加 candidate_alert |
| 扫描或关键数据失败 | 按计划发送明确失败说明（既有 fixed_failure），不能写成“正常无变化”或“无候选” | 不将失败当新增机会；按原故障／恢复合同处理 |

固定空态报告至少包含计划批次、实际数据时间、正常扫描状态、变化结论、候选／动作空态，以及可用持仓和资金状态；缺数据时明确缺失，不补零。“无变化”必须以本轮成功扫描和可靠可比证据为依据，不能用上一份旧正文冒充本轮新快照。示例：“扫描正常｜与上轮相比无业务变化；本轮无符合条件的开仓候选、无可执行平仓／移仓动作；持仓继续监控，资金状态如下。” 若前轮不可比较，应明确“本轮扫描正常，变化情况无法比较”，仍发送当前快照。

增量提醒采用同一账户／整份上限和 A、B 内部排序，不再有独立的“所有开仓合计先取三个身份”的隐藏规则；每策略 3 条的配置仍有效。这是相对当前 alert 行为的明确变化，可能增加一次增量消息的开仓展开数，必须作为后续验收项。

篇幅控制只允许聚合、排序、减少展开及明确摘要，禁止通过降低固定推送频率、省略发送、等待下一轮变化或跨批合并实现。本设计不增加扫描、通知时点、自动补发批次或消息分页，也不减少现有固定报告批次；不把普通 hold、C 档观察或 E 档缺口升级为新增候选提醒。它们只作为现有合法消息中的上下文。省略内容能否在以后自然通知，仍受原通知窗口、当前有效性和既有生命周期约束；这只说明某条动作不保证以后完整展开，绝不减免下一固定时间发送快照的义务。

### 7.1.1 本次硬约束的冲突检查及影响

源码基线的通知决策在 `ran_scan=true` 的扫描分支中先检查 `fixed_due`，可靠扫描选择 fixed_report，不依赖 pending 候选是否为空；非固定时才按待提醒集合决定 candidate_alert。`ran_scan=false` 分支只允许原消息精确重试，不能据此证明漏跑的固定批次也会正常生成报告，见 [Daily Brief domain](../domain/domain/daily_decision_brief.py) 206–239 行。现行 [通知体验 PRD](OPTION_NOTIFICATION_EXPERIENCE_PRD.md) 也要求固定点无候选仍发送、展示持仓和资金。该证据支持正常扫描的发送资格与变化解耦，但不能代替调度确实执行及实际按时送达的运行验收；漏跑固定批次属于未履行发送义务，不能归为正常无变化。

原方案没有明确写“无变化不发”、用增量替代固定报告或降低推送频率；但有三处表述不足，现明确收紧：

- 第 3.2 节的“一个固定批次或增量通知”只定义预算作用域，现明确固定批次发送义务先于预算，账户组不能等待凑齐变化再发送。
- 第 5.3 节的 `render_unavailable` 是故障，不是允许为省篇幅跳过固定报告的正常降级；现补齐未送达、失败证据及恢复要求。
- 原第 7.1 节只说“固定报告展示当前可用结果”，且末尾“不承诺一定补发”可能被读成整份报告可省略；现改为每批必发完整快照，并将该不保证严格限定为单条被省略动作的以后展开。

条数、优先级和跨账户聚合规则不因此改变；新增的是固定发送不可被这些规则取消的硬门槛。无动作空态的动作数为 0，不占五条、不凑数；有相同动作的无变化快照仍按通常预算展示。固定批次必须有自己的计划身份和最终送达证据，不能以同一正文／候选集合曾在上一批确认过来抵扣本批。

### 7.2 展示与确认分开记录

当前代码的确认口径有两种，未来计划必须明确保留这一区别：

- 移仓：只有完整出现在冻结正文、渠道主内容和备用正文中的成员身份，才在 provider 确认后进入已提醒集合。合并卡完整时确认全部成员，省略／部分成员未完整出现时不能确认这些成员。
- 普通开仓：当前增量消息只展开少数代表，但 envelope 可包含全部待提醒身份，确认后全部进入当日已提醒集合；带未展开计数的摘要承担集合通知作用。本设计保留这个去重政策，避免通过预算改动悄悄引入后续重复提醒。

拟在展示计划／投递元数据中分别记 `expanded`、`summary_notified`、`not_shown`，不能把“已通知集合”对外称作“全部逐条展示”。普通开仓只有相关摘要实际保留在最终正文时才能沿用摘要承载确认；L4 若连摘要也省掉，必须撤掉这些普通开仓身份的本次确认资格，并留在原生命周期待提醒集合。摘要必须能从结构化计划核对到确切的被承载开仓身份；若沿用以整个身份集合为确认单位的生命周期，就保留该集合全部未展开身份的摘要及数量，不能无说明地只确认其中一部分。移仓摘要始终不承担完整动作确认。

发送失败或结果未知都不能因扫描成功、消息渲染成功而标记 `delivery_confirmed`。冻结计划包括账户成员、所用配额、最终内容、身份与摘要证据；重试不得按新配置重排。账户组的多渠道投递必须继续保留每账户、每 route 的独立状态，不能以另一个账户／渠道成功推导本账户成功。

### 7.3 500 行／2 MiB 的真实口径及裁决

| 当前保护／返回限制 | 实际作用域 |
|---|---|
| `MAX_SOURCE_ROWS=500` | trade inbox 查询 SQL 源行、lifecycle 查询每张表源行的读取保护；先取 501 行，超限要求缩小查询。部分账户／标的过滤及一行展开多个语义回执发生在后面，故不是 500 条匹配回执。 |
| `MAX_SOURCE_BYTES=2*1024*1024` | 使用共享 helper 的单个 JSON 文件最多 2 MiB；超限整个来源不可用，不截取半个 JSON，也无该文件的下一页。 |
| 其它源保护 | scheduled run inventory 另有 500 个目录保护；trade／lifecycle 大行另有 SQL TEXT 长度保护。fanout inventory 读取不统一使用上述 500／2 MiB 常量，不能称所有回执来源都已同限。 |
| `receipt_read` 列表 | 请求 limit 默认 10、schema 1–50；多事件页实际最多 12 项，selected rows 的 JSON 数组另限 5,000 字节。列表不带全部正文。 |
| `receipt_read` 正文 | 单正文经脱敏后每页 1,800 字符；分页及 `body_complete` 说明正文覆盖范围。|

精确保护由 [receipt helper](../src/application/receipt_query.py)、[trade inbox reader](../src/application/trades/inbox.py)、[lifecycle reader](../src/application/ledger/receipt_queries.py)、[run inventory](../domain/storage/repositories/run_repo.py) 和 [receipt_read facade](../src/application/agent_tools/receipts.py) 分别拥有。

**裁决：保持读取保护与展示配额分离，不将 500 改为 40，也不将推送提升为 500。** 读取保护控制查询成本，展示预算控制用户注意力和渠道大小。本次不修改回执查询实现、分页、cursor、来源读取或输出 schema。

建议后续产品表述统一为三组数字：“源结果 N 个动作”“本消息展开 K 个、摘要说明 M 个”“回执当前页 R 个历史事件”。源读取超限要保留 `partial`／`unavailable`、`missing_sources` 和未知总数；不能写成“还有 500 条没推送”。

### 7.4 “推送没有、回执里有”怎样解释

当前 Daily Brief 回执使用保存的 `rendered_message` 或 fanout 的冻结 message，不直接读取飞书主卡／备用内容的最终可见文本。因此“有冻结原文”“回执正文已翻完”“渠道完整显示”是三件事。后续展示元数据可帮助解释，当前版本不得假称已经有逐卡送达证据。

回执也不是所有未展示建议的检索库。完整建议应从同账户、市场、数据时间绑定的 Brief／Close Advice 查询及封存来源读取。看到历史回执有建议而最新推送没有，可能是已过期、结果变化、预算省略、通知范围不同或渠道裁剪；应先对齐时间、账户、市场、正文来源及展示摘要，不能只用行数判断漏发。

同一次逻辑报告、同一冻结版本内，未来要求渠道主内容、备用正文、回执保存正文及展示计划在完整动作集合上相符；只有其中的明确摘要可以承载未展开的普通开仓身份。旧回执保持历史原文，不能用新预算重写。

## 8. 可观测性与缺失数据规则

### 8.1 用户可见说明

每次实际触发预算，至少显示层级、范围、类别和数量。例如：

> 展示范围｜账户甲上限 5 条：已展示 3 条移仓、2 条平仓；另 3 条移仓未展开。
> 展示范围｜CSP 每策略上限 3 条，另 2 个开仓机会未展开。
> 展示范围｜同市场账户组共展示 40 条，整份上限触发；另 6 条开仓机会未展开。
> 展示范围｜正文／渠道大小限制：撤去 1 条知情卡、1 条开仓卡；完整结果可按本次账户、市场和数据时间查询。
> 数据说明｜账户乙有 2 笔缺少可用报价，无法判断是否存在更多动作；不是零建议。

层级计数按最终选择计划计算，不能让同一条先被账户上限淘汰，又被总上限、字符上限重复累计。多层都有独立省略时，各记实际首次淘汰的集合。对小消息脚注可以按类别合并，但 A 档的省略数量必须可见。

普通观察、缺口摘要、去重合并各有独立计数：“11 笔普通观察未逐条展开”不等同“省略 11 条可执行动作”；“6 个 lot 合为 3 条动作”也不等同“丢弃 3 条”。

### 8.2 拟新增的结构化展示证据

以下字段放在应用层的展示计划和冻结投递元数据中，不把展示配额写回策略事实、候选评分或业务账本：

| 字段建议 | 必需内容 |
|---|---|
| `scope`、`policy_version` | 账户／显式组、市场、批次、来源修订及预算策略版本 |
| `limits` | 账户、分区、整份条数，以及适用的字符／字节限制和配置来源 |
| `counts` | 源行、合格动作、合并卡、完整展开、摘要承载、未展示；分别注明是 lot、卡还是账户成员计数 |
| `omissions` | 首次省略层、原因、档位、类别、受影响账户、源身份引用及计数；真实缺失数量用 null |
| `coverage` | 来源 complete／partial／unavailable，已知下界和未知范围；与预算省略分开 |
| `delivery_evidence` | 各身份 expanded／summary_notified／not_shown，最终主／备用正文可见集合及冻结内容摘要 |
| `transport_sizes` | 字符数、UTF-8 内容字节、最终请求体字节、各阶段是否撤卡及原因 |

内部身份引用仅留在原有授权范围的结构化记录；用户消息不新增内部 ID、路径或未经授权的账户信息。计数应满足每层守恒，展示计划可关联到本次源结果及冻结 envelope，不另造一个跨环境审计系统。

这与“缺失数据必须明确”不冲突。来源缺失是对世界状态不知道，预算省略是已知结果少展示：两者必须同时呈现，不能相互覆盖。只要缺口影响一张建议，就在该卡或受保护摘要中保留；不能以“篇幅有限”删除后宣称完整可执行。

## 9. 配置边界、默认值与迁移影响

### 9.1 建议配置

以下均为后续实现建议，当前 validator 会拒绝尚未支持的新键。

| 配置 | 建议默认／边界 | 影响及取舍 |
|---|---|---|
| 拟新增 `notifications.daily_brief.max_items_per_account` | 5；非负整数，0 仅表示账户层不限 | 唯一的账户展示上限，统一覆盖 A／B／C，按市场独立。相对当前多个五条上限，消息会更短，持仓优先，开仓展开数可能减少。 |
| 拟新增 `notifications.daily_brief.max_total_items` | 40；整数 1–40 | 单个逻辑报告硬上限。允许降低；40 仍是固定安全 ceiling，放大需要重新评估渠道与注意力，不接受配置绕过。 |
| 保留 `notifications.daily_brief.max_candidates_per_strategy` | 3；沿用 1–20 | 单策略开仓卡上限，服从账户及整份上限，不再因变化项自动扩容。改变默认值同时影响固定／增量／查询的展示。 |
| 保留并赋予实际展示语义 `notifications.daily_brief.max_rejection_reasons` | 5；沿用 1–20 | 当前没有生效消费者；未来用于非关键原因明细的展开数，这是新增行为。关键数据缺口和阻断状态不受它静默抑制，剩余原因汇总计数。 |
| 拟新增 `notifications.daily_brief.account_groups` | 空列表；各组至少两个不同的已配置账户，同市场、组间不重叠 | 默认保持逐账户报告。只有显式组和完整接收授权都满足才合并；配置冲突报错，不自动扩大组或接收范围。 |

空组默认值避免把两个相同接收目标误当作跨账户合并授权。合并条件未满足时，不静默部分合并；保持逐账户报告并给出明确配置诊断。市场、账户、通知目标的既有配置 owner 不被此设置取代。

### 9.2 现有键的处置

- `close_advice.max_items_per_account`：建议迁移到新的账户展示上限，之后从 Close Advice 的策略／事实生产中退出条目选择职责。其当前 0 语义保留为账户层不限，整份及渠道仍限。独立 CLOSE 读取／展示入口继续说明自己的输出范围，不使用预算删掉原始评估行。
- `notifications.daily_brief.max_actions_per_priority`：建议与旧 CLOSE 上限一同迁移后退役。当前它实际影响持仓展示且允许变化扩容，名称不能准确描述统一模型；不继续增加一个同义上限。
- 旧键到新键不是严格语义等价：原来可能是“5 条平仓加若干移仓、每策略另 3 条”，新规则是所有决策卡共用账户 5 条。后续迁移预览必须列出这个变化。若多个显式旧值互相冲突或与新键冲突，要求明确选择一个新值，不能由 renderer 默默取某个值或双重限制。
- 旧键只有单一有效显式值且未设置新键时，可由配置迁移工具提出同值迁移；没有显式值则建议默认 5。0 必须在预览中解释，不能被当作缺省或“关闭提醒”。
- 本设计不改变策略启停、有效性时长、扫描节奏、收益门槛、资金规则或 receipt_read 查询保护。

分层顺序、A 优先、双队列规则、账户隔离、合并等价条件、缺口不可伪装成零、完整显示与确认的关系，以及 12,000 字符／渠道字节保护固定在版本化合同中，不做可配置权重。避免让配置变成第二套策略引擎。

默认值即使不变，统一作用域也会改变消息内容；这不是单纯的文案更新。后续实现应按固定 fixture 对比旧／新入选集合及省略解释，并在配置迁移说明中列明。现有冻结通知继续按旧计划重试；不能在中途把五条的新解释套到已准备的历史消息上。

本节定义后续实现验收，不代表本次文档交付已实现这些行为。除第 1.3 节已运行的基线检查外，以下新增断言都需未来实现及离线验证；生产表现仍需另行授权的运行读回。

| 长中文、长合约标签、JSON escaping、合并账户子行导致 L4 超限 | 正文≤12,000 字符；飞书内容≤24 KiB、请求≤28 KiB；只能撤完整卡，省略原因指向实际大小限制，主卡／备用／保存正文动作集合相同。 |
| 移仓被撤卡、部分成员显示不全、发送失败／未知、精确重试 | 被省略成员不进入移仓已提醒集合；失败／未知不伪装成功；重试 payload、计划及成员身份不随新上限改变。完整分组成功后确认全部显示成员。 |
| 五个普通开仓身份只展开三个，但摘要说明余两个；再构造摘要被大小限制移除 | 有完整摘要时保留既有集合确认；摘要消失时仅能确认完整展示者。两种情况都记录 expanded／summary_notified／not_shown，不能将摘要确认当逐条显示。 |
| 500／501 SQL 源行、2 MiB／多 1 字节 JSON、receipt 列表及正文多页 | 现有来源保护与分页行为保持；超限为缺源而非成功空集；总数未知保持 null。设计文案不称其“500 条建议”。 |
| 来源缺失同时发生配额省略；历史回执与当前建议不同 | 用户能同时看到“已知 N 条被省略”和“另有未知范围”；可按账户／市场／数据时间对齐来源，回执 body_complete 不被解释为当前建议完整。 |
| 组内一个账户失去接收授权，或来源跨市场、时间不兼容 | 不向缺少完整权限的目标发送合并卡；不跨市场合并；不以组内其它账户成功替代该账户送达。原冻结重试继续按既有授权检查处理。 |

复现应使用仓库已有 fixture builder 和匿名化 fixture，冻结时间，覆盖 assemble → normalized brief → selection plan → renderer → channel payload → persisted envelope → provider stub → receipt 的一跳到完整链路；不连接真实券商、不真实发通知、不为补齐预期改写策略事实。

## 11. 风险、未决运行事实与不做的事

- **注意力目标有取舍。** 五条无法完整承载全部机会。本提案选择持仓动作优先、公平轮转及明确省略，不能保证五条总净收益最高，也不能保证每种策略都有卡片。
- **合并会增加单卡长度。** 节省条数不等于节省字节；账户子行与缺口必须完整，必要时拆卡并重新计数，接受最终少于五条。
- **跨账户默认不合并。** 生产重复问题需要显式账户组及合同变更落地；两个账户碰巧发往同一聊天不足以开启该能力。
- **固定时间是硬约束。** 无变化、无候选和篇幅预算都不能减免固定报告；网络／渠道故障仍可能造成实际延迟，必须记录为未按时送达及失败恢复，不能将其包装为正常空态或策略性静默。此次仅补设计，未证明生产环境已满足送达时效。
- **观察可能长期不展开。** C／D／E 没有独立卡片保底，强制摘要保证知情；明细依赖主动查询及来源保留期，不承诺无限历史可查。
- **当前提前切片需要收口。** 后续实现必须在现有源 owner 处暴露完整合格集合，让展示计划只选一次；不通过另跑扫描或查询实时行情恢复已丢候选，也不另造推荐引擎。
- **当前回执不是逐卡渠道截图。** 新元数据落地前，不能声称所有历史冻结原文等于渠道实际可见内容；本设计不重写历史记录。
- **未核实运行事实。** 当前生产采用 legacy 还是 routes/channels、各账户有效配置、实际组授权及已部署渠道版本均未读取；本文不据此声称生产已修复。生产输入中的 2040／1523 也未映射到当前源码字段重新求值。
- **本次不做。** 不修改代码、测试、配置、现行合同或索引，不新增业务阈值／收益评分，不改 receipt_query 的实现或读取边界，不改通知时机、去重身份、自动下单、账本、部署和历史数据。本次只提交本文件到设计分支；推送、PR、合并、发布与后续实现均需各自授权。
