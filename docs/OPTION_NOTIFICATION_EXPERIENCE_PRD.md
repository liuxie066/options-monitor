# 期权监控通知体验升级 PRD

- **状态**：Approved for implementation
- **日期**：2026-07-21
- **产品范围**：Options Monitor 策略扫描后的主动通知与主动查询
- **适用策略**：Sell Put、Covered Call、Combo Yield
- **适用粒度**：账户 + 市场 + 市场交易日
- **文档性质**：产品需求；不规定具体代码拆分

## 1. 背景

当前通知升级以 Daily Decision Brief、revision 和 material-change lifecycle 为中心，实际体验存在三个主要问题：

1. 用户无法稳定预期什么时候会收到消息；
2. 错过一条消息后只能翻聊天历史，最后一条主动通知可能已经很久；
3. 消息缺少稳定的资金信息，尤其是现金总额和可用于期权开仓的资金。

本次需求回到更直接的使用模型：

> **保留一套权威策略扫描；扫描完成后，再根据当前计划点和扫描结果决定发不发、发什么。**

不建立第二套候选扫描器。唯一 scheduler 在固定报告点和交易时段内的有效半点执行同一套 canonical 策略扫描；现有 10 分钟定时唤醒在其他时刻不执行 pipeline，但允许对已经持久化、尚未确认的通知 envelope 做 delivery-only 重试。

## 2. 已确认的产品方向

通知模型由三部分组成：

1. **固定报告**：恢复原有计划点通知，包括开盘后、交易时段内有效整点和收盘前批次；
2. **新增候选半点通知**：权威策略扫描在交易时段内的有效半点发现新的合格候选后，当轮立即发送独立通知；固定报告点发现新增候选时，由完整报告承载，不额外发送第二条消息；
3. **随时查询**：用户随时读取最近一次成功策略扫描产生的最新快照。

系统故障、恢复和业务操作回执继续保留，不属于普通候选变化通知。

## 3. 产品目标

1. 每个固定报告点都有稳定、可预期的账户监控消息；
2. 新增合格候选在本轮扫描完成后立即送达：有效半点发送独立通知，固定报告点通过完整报告送达；
3. 固定报告和新增候选通知都来自同一次、同一套 canonical 策略扫描；
4. 用户随时可以查询最近一次成功扫描结果，不依赖聊天历史；
5. 固定报告、候选通知和查询结果都显示数据时间与新鲜度；
6. 资金区块展示现金总额、可用于期权开仓的资金和候选容量；
7. 资金区块不展示账户总资产、净资产或证券市值；
8. 扫描失败不得被描述成“监控正常，本轮无候选”；
9. 用户消息不展示 revision、digest、delivery pointer、内部 ID 或原始状态枚举。

## 4. 非目标

本次需求不包括：

- 新增第二套候选扫描、轻量扫描或独立实时扫描器；
- 新增候选专用 timer、scheduler 或可独立配置的扫描频率；
- 自动下单、自动调仓或根据通知交互推断成交；
- 逐笔、分钟级或行情事件流通知；
- 对所有 material change 主动通知；
- 主动通知普通排序、报价、收益率、Delta 或容量变化；
- 主动通知普通候选消失；
- 用账户总资产、股票市值或净资产替代现金数据；
- 为固定报告、候选通知和主动查询建立三套业务 read model；
- 修改候选过滤、排序、Close Advice、资金风控或交易账本的业务权威。

## 5. 核心架构合同

### 5.1 唯一策略扫描

系统只有一套 canonical 策略扫描流程：

```text
scheduler 触发
  -> 执行账户与市场策略扫描
  -> 生成结构化扫描结果
  -> 持久化最新快照
  -> 执行统一通知决策
```

固定报告、新增候选通知和主动查询都读取该扫描流程的结构化结果。

禁止：

- 新增候选专用扫描器；
- 通过旧通知 Markdown 反推候选；
- 在通知层重新实现候选过滤或排名；
- 为了即时通知重复请求同一轮行情与账户数据。

### 5.2 扫描频率与通知频率分离

唯一 scheduler 的实际扫描目标是两组时间点的并集：

- 固定报告点：`09:40 + 交易时段内有效整点 + 15:50`；
- 新增候选检查点：交易时段内有效 `HH:30`。

`09:30` 不执行扫描，由 `09:40` 开盘后完整报告替代，避免开盘后 10 分钟内重复扫描。港股午休、非交易日、市场 gate 和账户级去重继续生效。现有 10 分钟定时任务只负责唤醒 scheduler；不属于上述目标点时，扫描决策必须 no-op，不执行 pipeline、不请求 broker、不生成新快照或 revision。

扫描 no-op 不等于丢弃发送恢复机会：如果账户+市场已经存在持久化的 pending/ambiguous delivery envelope，且当前仍在既有发送允许窗口内，本次唤醒可以只复用原 envelope 做幂等核验或精确重试。delivery-only 重试不得生成新候选差异、不得改变 revision、candidate set、delivery key 或 message hash。

账户级调度去重必须以“已处理的 scheduled scan target”作为权威水位，不能用 pipeline 实际完成时间推断某个计划点已经执行。实际完成时间只用于运行观测。

这仍是一套 canonical 扫描频率：不新增候选专用 timer、scheduler、轻量扫描、delivery daemon 或第二套候选权威。

每次扫描完成后，通知策略独立判断：

- 当前是否为固定报告点；
- 本轮是否出现新的合格候选；
- 本轮扫描是否可靠成功；
- 是否存在发送禁用、quiet hours 或 provider 故障。

“新增候选及时通知”的含义是：

> **只要某次权威扫描已经发现并确认候选，就在该次扫描的通知阶段立即发送，不等待下一个整点。**

它不承诺在两次扫描之间发现尚未被系统扫描到的市场变化；在正常连续交易时段内，新增候选通常最晚在下一个半点或固定报告点被发现，再加 pipeline/send 延时。跨港股午休时等待到下一个有效目标点。

### 5.3 一个快照，多个投影

同一次扫描最多产生以下用户投影：

- 固定完整报告；
- 独立新增候选通知；
- 主动查询结果。

三者内容详略不同，但业务事实必须来自同一份结构化快照。

## 6. 扫描后通知决策

每次成功策略扫描后执行以下决策矩阵：

| 固定报告点 | 有新增候选 | 结果 |
|---:|---:|---|
| 否 | 否 | 只更新快照，不主动通知 |
| 是 | 否 | 发送固定完整报告 |
| 否 | 是 | 立即发送独立新增候选通知 |
| 是 | 是 | 只发送固定完整报告 |

要求：

1. 非固定报告点发现新增候选时，立即发送独立候选通知；
2. 固定报告点发现新增候选时，只发送完整报告，不额外发送候选通知；
3. 固定完整报告确认成功后，其中包含的新增候选视为已送达，并加入当日已提醒集合；
4. 固定完整报告发送失败时，不得把其中的新增候选标记为已提醒；
5. 固定报告和独立候选通知分别使用稳定幂等身份；
6. 扫描失败时不得执行正常候选差异判断。

## 7. 固定报告

### 7.1 固定报告点

恢复原有通知节奏：

- 市场开盘后 `09:40`；
- 交易时段内每个有效整点；
- 市场收盘前 `15:50`；
- 港股午休期间不发送；
- 非交易日不发送正常市场报告。

固定报告点以市场当地时间和 scheduler 的计划批次为准。延迟执行时仍显示原计划批次，并单独显示真实数据时间。

### 7.2 固定报告行为

1. 每个有效固定报告点、每个账户、每个市场分别发送一份报告；
2. 有候选时展示当前主要候选；
3. 没有候选时仍发送，但不得只保留一句心跳；
4. 没有候选时仍展示可用的持仓和资金状态；
5. pipeline 或关键数据失败时发送明确失败说明；
6. provider 确认成功前不得标记该计划点已发送；
7. 相同账户、市场、计划点的重试不得重复送达；
8. provider 未确认的完整报告必须保存稳定 envelope，并可在后续 10 分钟唤醒点做 delivery-only 精确重试，无需等待下一次策略扫描；
9. delivery-only 重试不得请求 broker、更新 successful current、生成 revision 或旋转 delivery key；
10. `15:50` 完整报告发送失败时，允许在仍属既有发送窗口的 `16:00` 唤醒点重试原 envelope。

### 7.3 固定报告结构

```text
# OM · 决策简报 · lx

状态｜14:00 批次
市场｜港股
数据｜香港 14:00 / 北京 14:00

## 当前候选

**1｜9992.HK｜Sell Put｜08-28 HK$145 Put（首选）**
指标｜年化 25.2% · Delta -0.23

## 持仓

汇总｜共 1 条，当前没有需要处理的持仓。

## 资金
现金总额｜HK$480,000
可用于期权开仓｜HK$225,000
9992.HK 08-28 HK$145 Put｜按当前现金最多 8 手

## 提醒
多个 Sell Put 候选共享同一现金额度，手数不能相加
```

飞书固定简报的紧凑卡片投影只在实际展示了逐候选手数容量时保留上述
共享现金提醒；未展示手数时应省略该提醒。单个合约无当前报价、无可用到期日或
通用 `partial_data` 不进入用户侧“提醒”；明确的行情获取失败、策略扫描失败、来源快照错误，
以及 sealed 快照已识别的期限匹配 RV 等硬证据缺失仍须具体展示。预取状态 `fetched` 按成功处理，
不生成假缺口。后台结构化简报仍保留每个真实缺口事实。

无候选示例：

```text
# OM · 决策简报 · lx

状态｜14:00 批次
市场｜港股
数据｜香港 14:00 / 北京 14:00

## 当前候选
本轮暂无符合条件的候选。

## 持仓

汇总｜共 1 条，当前没有需要处理的持仓。

## 资金
现金总额｜HK$480,000
可用于期权开仓｜HK$225,000
```

## 8. 新增普通候选半点通知

### 8.1 触发时机

1. 固定报告点或有效半点的成功 canonical 策略扫描完成后计算新增候选；
2. 有效半点确认出现新增合格候选时，在本轮通知阶段立即发送独立通知；
3. 当前是固定报告点时，只发送包含当前候选的完整报告，不额外发送候选通知；
4. 不等待后续固定报告点补发已在非固定点发现的候选；
5. 不新增第二套扫描；
6. 不要求新增候选恰好出现在整点；系统在下一个有效半点或固定报告点发现它；
7. 如果扫描本身只在某些时间运行，通知时效受该唯一扫描的实际运行时间约束。

### 8.2 合格候选条件

新增候选必须：

- 来自正式结构化、labeled candidate；
- 已通过 canonical 策略过滤；
- 当前处于可行动状态；
- 数据未过期；
- 不是 rejected、raw-only、malformed 或关键数据缺失的结果；
- 具备明确标的、策略、合约、报价和必要指标；
- Sell Put 资金容量至少支持一手；
- Covered Call 具备至少一手有效覆盖能力；
- Combo Yield 满足 canonical 组合容量与腿关系要求。

### 8.3 候选身份与去重

当前推荐的新增候选身份：

```text
账户 + 市场 + 标的 + 策略族
```

示例：

```text
lx + HK + 9992.HK + Sell Put
lx + HK + 9992.HK + Covered Call
```

规则：

1. 同一标的、同一策略下新增另一个行权价或到期日，不视为新的候选身份；
2. 同一标的出现另一策略族，视为新的候选；
3. 本轮候选集合与上一次成功扫描的候选集合比较；
4. 同一候选身份在同一交易日成功提醒后，不重复提醒；
5. 同日消失后重新出现，不重复提醒；
6. 新交易日重新建立已提醒集合；
7. provider 发送失败时不得加入已提醒集合，后续扫描仍可重试。

候选身份最终粒度见“待确认事项”。

### 8.4 多个新增候选

同一账户、市场、同一轮扫描发现多个新增候选时，合并为一条新增候选通知：

- 默认最多展开 3 个；
- 超出部分显示数量，并提示主动查询；
- 不为每个候选分别发送一条消息。

### 8.5 新增候选通知结构

```text
# OM · 决策简报 · lx

状态｜新增候选 · 13:30 发现
市场｜港股
数据｜香港 13:30 / 北京 13:30

## 新增候选

**1｜3690.HK｜Sell Put｜08-28 HK$95 Put（首选）**
指标｜年化 18.5% · Delta -0.22

## 资金
现金总额｜HK$480,000
可用于期权开仓｜HK$225,000
3690.HK 08-28 HK$95 Put｜按当前现金最多 3 手

## 提醒
多个 Sell Put 候选共享同一现金额度，手数不能相加
下单前重新确认报价、流动性和事件风险
```

## 9. 不主动通知的普通变化

以下变化只更新最新快照，不主动发送变化消息：

- 候选排序变化；
- 同一标的策略下新增行权价或到期日；
- 权利金、年化收益率、Delta、DTE 或报价变化；
- 最大可开仓手数变化；
- 普通候选消失；
- 已提醒候选同日消失后重新出现；
- 候选从备选变为首选；
- 事件风险的普通变化；
- 持仓继续观察或无法评估（不指向需要做出变化的行动，通知持仓区不逐条展示，但计入“另有 N 个持仓未展开”）；
- 非固定报告点的成功扫描没有新增候选。

系统故障、恢复、交易回执和到期维护回执不属于普通变化，仍按各自合同通知。

## 10. 随时查询

### 10.1 查询入口

用户可以使用自然语言查询，至少支持：

- `期权监控`；
- `最新期权报告`；
- `港股期权`；
- `美股期权`；
- `lx 期权`；
- `sy 期权`。

### 10.2 查询行为

1. 查询读取最近一次成功 canonical 策略扫描的最新快照；
2. 不返回“最后一次发送消息”的静态副本；
3. 查询完全只读；
4. 查询不推进固定报告、候选提醒或 provider delivery 状态；
5. 查询结果显示账户、市场、数据时间、新鲜度和最近扫描状态；
6. 可可靠计算时显示下一计划扫描时间；
7. 固定报告与查询复用同一个用户投影和 Markdown renderer；
8. 聚合查询必须按账户和市场清晰分节，不混合资金。

查询示例：

```text
# OM · 决策简报 · lx

状态｜当前查询 · 查询时间 14:36
市场｜港股
数据｜香港 14:30 / 北京 14:30
状态｜今日最新

## 当前候选
...

## 持仓
...

## 资金
现金总额｜HK$480,000
可用于期权开仓｜HK$225,000
```

过期数据示例：

```text
数据｜上一交易日 15:50
状态｜已过期，仅供计划参考
今日扫描暂不可用
```

## 11. 资金数据合同

资金区块不展示：

- 账户总资产；
- 账户净资产；
- 股票市值；
- 期权市值；
- 基金市值。

### 11.1 现金总额

- 只统计现金；
- 多币种分开显示；
- 缺少明确汇率与业务口径时不得强行折算相加。

示例：

```text
现金总额：HKD 480,000 / USD 18,000
```

### 11.2 可用于期权开仓的资金

- 使用现有账户、资金和风险约束后的 canonical 可用金额；
- 与现金总额分开显示；
- 必须显示币种；
- 不得使用总资产替代；
- 不得把多个候选容量相加后当作可用资金。

### 11.3 候选容量

- 每个候选分别显示当前最多支持的整手数；
- Sell Put 共享现金池时必须提示手数不可相加；
- Covered Call 使用可覆盖股数与 multiplier 计算；
- Combo Yield 使用 canonical 组合容量口径。

资金数据不可用时显示：

```text
资金数据暂不可用，本轮不提供可开仓手数。
```

禁止用 `0` 表示未知。

## 12. 故障与恢复

1. 固定报告点扫描失败时，发送明确的报告失败说明；
2. 非固定报告点单次扫描失败可以保持安静；
3. 连续失败达到现有告警阈值后发送系统告警；
4. 已发送故障告警后首次恢复成功时发送一次恢复提醒；
5. pipeline 失败不得生成“监控正常，本轮无候选”；
6. 故障结果不得参与新增候选比较；
7. 扫描失败不得覆盖最近一次成功快照；
8. provider 失败、pipeline 失败、OpenD 失败和数据覆盖不足必须在审计中可区分；
9. provider 发送失败不触发重复策略扫描；后续非扫描唤醒只处理已持久化 envelope。

固定报告失败示例：

```text
# OM · 决策简报 · lx

状态｜数据异常 · 14:00 批次失败
市场｜港股
结论｜本轮策略扫描未形成可靠结果，无法生成正常报告。
后续｜下一计划扫描会继续尝试。
```

## 13. 发送状态与幂等

产品需要的最小状态包括：

```text
账户 + 市场 + 交易日
- 各固定报告点是否已确认发送
- 上一次成功扫描的候选身份集合
- 当日已确认提醒的候选身份集合
- 当前待确认 delivery envelope 及其稳定 delivery key、source revision/failure artifact 和 message hash
```

要求：

1. 只有 provider 确认成功后才推进对应发送状态；
2. `--no-send`、quiet hours、本地确认失败和 provider 失败均不推进；
3. 固定报告和新增候选通知使用不同的幂等身份；
4. 同一固定报告点重试不重复；
5. 固定完整报告确认成功后，其中包含的新增候选加入当日已提醒集合；
6. 固定完整报告失败时，其中的新增候选保持未提醒状态；
7. 同一候选身份同日不重复；
8. 主动查询不写入发送状态；
9. revision 可以作为内部审计历史，但不决定普通 material-change 通知；
10. 实现复用现有 route、retry、delivery confirmation 和审计链路，不建立第二套 sender；
11. 非扫描唤醒只允许读取并处理已持久化 envelope，不运行 brief assembler，不生成新的通知内容；
12. provider definite failure 可精确重试原 envelope；ambiguous 状态必须冻结内容，只能走现有幂等核验或支持幂等键的精确重试；
13. `--no-send` 不确认状态，也不得把本次 dry-run 新准备的消息发布为后续可自动发送的 envelope；已有生产 envelope 保持不变；
14. quiet hours 不确认状态，已持久化 envelope 保留到后续允许发送的唤醒点。

## 14. 账户与市场隔离

1. 每个账户独立计算候选、资金、持仓和通知状态；
2. US/HK 独立计算交易日、市场时间和新鲜度；
3. 主动通知按账户和市场分别发送；
4. 聚合查询必须明确分节；
5. 不同账户、市场、币种的资金不得合并；
6. 港股午休和非交易时段按市场 scheduler 合同处理。

## 15. 验收场景

### 场景 A：整点正常、有候选

- canonical 扫描成功；
- 当前是有效整点；
- 没有新增候选；
- 发送一份固定完整报告；
- 包含当前候选、持仓、现金总额和可用于开仓资金。

### 场景 B：整点正常、无候选

- canonical 扫描成功；
- 当前是有效整点；
- 没有候选；
- 仍发送固定报告；
- 显示“本轮暂无符合条件的候选”；
- 仍展示可用的持仓和资金信息。

### 场景 C：半点发现新增候选

- 有效半点 canonical 扫描成功；
- 当前不是固定报告点；
- 本轮相对上一次成功扫描出现新的合格候选；
- 同一轮立即发送独立新增候选通知；
- 不等待下一整点；
- 不发送固定完整报告。

### 场景 D：固定点同时发现新增候选

- canonical 扫描成功；
- 当前是固定报告点；
- 本轮有新增候选；
- 只发送固定完整报告；
- 不额外发送独立新增候选通知；
- 完整报告确认成功后，其中的新增候选加入当日已提醒集合；
- 完整报告发送失败时不标记候选，后续扫描仍可发送或重试。

### 场景 E：同一标的新增另一合约

- 上次已有 `9992.HK + Sell Put`；
- 本轮只新增另一个到期日或行权价；
- 不发送新增候选通知；
- 固定报告或主动查询显示当前首选和备选合约。

### 场景 F：候选同日重新出现

- 候选已在当日成功提醒；
- 后续消失；
- 同日再次出现；
- 不重复发送新增候选通知。

### 场景 G：新增候选发送失败

- canonical 扫描发现新增候选；
- provider 发送失败；
- 不加入当日已提醒集合；
- 持久化原 candidate envelope；
- 后续 10 分钟唤醒点即使不执行扫描，也可对相同 delivery key、相同候选集合和相同 message hash 精确重试；
- 重试成功前不推进 alerted 状态。

### 场景 H：整点 pipeline 失败

- 当前是固定报告点；
- pipeline 失败；
- 发送明确失败说明；
- 不出现“监控正常”或“本轮无候选”；
- 不执行新增候选比较。

### 场景 I：主动查询

- 最后一条主动消息已经较早；
- 后续 canonical 扫描已更新快照但没有触发通知；
- 用户查询“港股期权”；
- 返回最近一次成功扫描快照；
- 查询不改变任何发送状态。

### 场景 J：资金缺失

- 候选数据存在但资金数据不可用；
- 消息显示“资金数据暂不可用”；
- 不显示 `0`；
- 不使用总资产代替；
- 不提供伪造容量。

### 场景 K：同一扫描只执行一次策略计算

- 本轮同时满足固定报告点和新增候选条件；
- 候选、持仓和资金只由一套 canonical 扫描计算；
- 只生成一条固定完整报告；
- 不为新增候选重复执行策略扫描或 broker 数据请求。

### 场景 L：收盘前报告发送失败后精确重试

- `15:50` canonical 扫描成功并持久化完整报告 envelope；
- provider definite failure，固定批次未确认；
- `16:00` timer 唤醒但不是新的 scan target；
- 系统不运行 pipeline、不请求 broker、不生成新 revision；
- 系统使用原 revision、原 delivery key 和原 message hash 精确重试；
- 只有 provider confirmed 后才确认 `15:50` 固定批次。

## 16. 发布与观察要求

1. 先使用 `--no-send` 验证四种输入组合：静默、仅固定报告、仅新增候选、固定点同时有新增候选；
2. 使用单账户、单市场进行真实发送 canary；
3. Canary 至少覆盖：
   - 整点有候选报告；
   - 整点无候选报告；
   - 有效半点新增候选通知；
   - 固定点有新增候选时只发送完整报告；
   - 同日候选不重复；
   - 主动查询最新快照；
   - pipeline 失败不误报健康；
   - provider 失败不推进状态；
   - `15:50` 失败后 `16:00` delivery-only 精确重试且不扫描；
4. 生产启用前确认 Compact 旧心跳不会与新固定报告并行发送；
5. 生产观察至少记录：
   - 固定报告成功率；
   - 新增候选通知数量；
   - 新增候选从扫描完成到发送开始的耗时；
   - 重复抑制数量；
   - delivery-only retry attempt/confirmed/ambiguous 数量；
   - 主动查询快照新鲜度；
6. 不因本需求修改交易状态、broker-facing 数据或策略过滤权威。

## 17. 待确认事项

   - 当前推荐：方案 A，并按账户、市场分节。

## 18. 决策摘要

已确认：

- 只有一套 canonical 策略扫描；
- 扫描完成后由统一通知策略决定是否发送；
- 复用现有 10 分钟定时唤醒，只有固定报告点和有效半点执行 canonical pipeline；
- 恢复 `09:40 + 有效整点 + 15:50` 固定报告；
- 新增合格候选在有效半点被发现时，本轮立即发送独立通知；
- 新增候选通知不等待下一固定报告点；
- 固定报告点发现新增候选时只发送完整报告，并在确认成功后将候选标记为已送达；
- 支持随时查询最近一次成功扫描快照；
- 不发送普通排序、指标、容量和候选消失变化；
- 资金展示现金总额、可用于期权开仓的资金和候选容量；
- 不展示账户总资产或净资产；
- 系统故障、恢复和业务操作回执继续独立通知。
