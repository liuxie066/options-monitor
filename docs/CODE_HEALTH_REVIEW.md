# 合并后增量巡检

本流程检查已经合并到 `main` 的改动，交付有证据的问题、验证缺口和漏检原因；已有问题与使用反馈统一在 GitHub issue 跟踪，按下文流程复核和处理。合并后巡检已启用每日本地调度；issue 处理的接入实现按用户授权开发，复用同一个任务及现有 PR、测试、过程报告和 [开发经验](../LESSONS.md)。本机安装结果以安装回执为准；没有成功安装回执时不能视为日程已启用 issue 处理。它不替代合并前审查，也不是新增的 GitHub 强制门禁。

## 目标与权限

成功标准：明确审过哪些提交、确认了什么、原验证为什么漏检，以及下一次如何检查。零发现也是有效结果，不以问题数量评价巡检。

巡检阶段对业务代码和外部系统保持只读；可在隔离临时目录运行无外部副作用的定向测试。用户于 2026-11-03 进一步授权：确认缺陷后，在同次调度接上独立本地修复、回归验证与独立审核。检查前阅读 [Agent Manual](../AGENTS.md)、本次相关合同和经验条目；保留无关工作区的改动。

手动报告保存在 gitignored 的 `docs/reviews/`，定时报告与修复任务位于独立状态目录，不强行纳入版本控制。提交、推送、发布 issue、创建远端 PR、合并、发布、调整权限和封禁贡献者仍需逐次明确授权；无人值守流程在本地改动、验证证据及 PR 草稿齐备后等待交付授权。疑似敏感或恶意内容仅记录必要的脱敏证据，按 [Security](../SECURITY.md) 处理。

## 每轮范围与续跑

1. 冻结本轮目标 `main` 的完整 SHA，记录源码、依赖环境和起始时间。审查期间 `main` 的新提交留到下一轮。
2. 首轮沿目标 SHA 的 first-parent 主线选择最近三个已合并 PR，按主线从旧到新审查，以最早一个 PR 的主线父提交为本轮起点。不得按 PR 编号或列表默认排序推定合并顺序。首轮起点之前的历史明确不在覆盖范围内。
3. 后续轮次先读取上一份报告，核对“已完成至”是本轮目标的祖先；续查其后的改动，每轮 first-parent 主线单元数上限由配置 `max_units` 决定（默认 10）。PR 合并和直接提交各计一个主线单元，都必须列出并检查。没有新提交时记录无增量；续跑记录缺失或主线关系不成立时，明确报告断点，不能猜测已完成位置。
4. 每个 PR 比较其合并提交与主线父提交，检查全部变更文件，并追踪相关入口及上下游一跳。再确认候选问题在本轮冻结目标是否仍然存在，避免将后续已修复的问题重新报成新缺陷。
5. 每轮以约 30 分钟为投入预算，及时记录进展。预算耗尽时保存未完成项和下一步，不能把未检查的提交记为完成；不为凑满 `max_units` 配置的上限扩大投入。

可用 `git log --first-parent <目标SHA>` 确认主线顺序，再用 `gh pr view <编号>` 核对 PR、变更和检查记录。PR 编号、完整 SHA、测试修订和证据路径都写入报告，不能只记录“最新 main”或“CI 全绿”。

“已完成至”表示从本轮起点连续完成了四项检查，不表示不存在缺陷或已经修复。确认问题可以转入后续跟踪；关键证据不足以完成某项检查时保留待审，不跨过该提交推进位置。

## 四项检查

| 检查项 | 要回答的问题 | 验证线索 |
|---|---|---|
| 实现与所有权 | 是否重复已有能力，或在下游补偿上游错误？ | 对照 [API Index](API_INDEX.md)，追踪真实入口、canonical owner 和相邻调用者。 |
| 测试判别力 | 是否删除或弱化断言、扩大 mock、增加 skip？测试能否暴露旧错误？ | 检查测试 diff；适配器、进程、持久化和时限问题保留相应真实边界，必要时做最小前后对照。 |
| 业务失败路径 | 缺失、异常、超时是否被当成成功？隔离和幂等约束是否保留？ | 按相关合同验证成功与失败，明确账户、市场、数据完整性和写入边界。 |
| 权限与执行能力 | workflow、依赖、安装、插件和版本变更是否新增外部执行或发布能力？ | 检查实际 diff 和当前生效证据；修改 `VERSION` 的 PR 另按 [Release Process](RELEASE_PROCESS.md) 核对发布边界。 |

结构变化和静态扫描只能提供线索；不得仅凭重复代码、函数长度或扫描告警断言缺陷或恶意行为。CI 完整执行当前测试集合，也不证明断言强度和业务边界已被覆盖。

## 候选问题与经验

先查关联 issue、修复 PR 和相关经验，区分新问题、重复问题及已修复的历史原因。先沿真实入口验证触发条件，检查下游是否已阻断；未实证的线索保留为待验证，不写成确认缺陷。

确认问题至少记录触发条件、预期和实际结果、源码位置、实际复现日志、稳定去重 key，以及明确的修复文件范围。没有实证日志的线索保留为验证缺口；例如首轮 V001 不自动变成当前业务故障。结构化确认记录先写入 `repairs/<问题标识>/task.json` 和本地 issue 草稿，再推进审查游标；同 key 复用任务，不重复开工。

同次调度最多继续一个待办修复：创建冻结基础的独立本地分支/worktree；在未修改业务源码时先补回归并由 runner 记录真实断言失败；启动另一个上下文修改 owning boundary，保持该回归文件不变；由 runner 对同样用例重跑，要求失败/跳过/fixture error 为零；再启动全新只读审核上下文核对整个最终 diff、未跟踪测试、上下游、门禁和实测证据。

审核通过后生成本地 `pr-draft.md`，状态为 `awaiting_delivery_authorization`；这不代表远端 PR 已创建，也不构成提交、推送、合并或发布授权。审核要求修改时，下次日跑续接实现与复审；无法复现或关键证据不足时停为待裁决/blocked。任务状态和审查游标分离，无新增 PR 时仍可继续待办；同次预算不足则保留阶段和脏分支，不删除或提交。

修复与验证共用每日约30分钟预算。生产、服务、发布边界的改动以及已验证依赖输入发生变化时，保留记录并交用户单独裁决或刷新环境，不自动安装或放宽权限。原因查明后，按 `LESSONS.md` 的触发条件、错误原因、下次检查方式和证据更新原条目；相同原因合并，不复制任务流水账。被证伪的审查判断先保留反证，只有可复用且证据充分的原因才进入经验。

## 每轮报告

建议文件名为 `docs/reviews/code-health-review-<YYYYMMDD-HHMMSS>.md`。报告至少包括：

- 范围：起始 SHA（不含）到目标 SHA（含）、有序 PR/直接提交、冻结时间、源码和测试环境。
- 检查记录：逐 PR 列出四项检查结论、所用证据，以及未运行或未覆盖的内容。
- 确认问题：触发、预期/实际、源码和复现证据；无发现时明确写零。
- 验证缺口：缺什么、影响什么结论、下一步如何补；待验证不冒充已确认。
- 漏检原因与经验：旧验证为什么没挡住，新证据覆盖了哪个边界，是否已有经验可复用。
- 后续动作：已有 issue/PR，或可直接评审的 issue 草稿；没有新问题时无需制造 issue。
- 续跑：连续“已完成至”SHA、待审项、下一轮起点；如果预算耗尽，记录实际停止处。

报告同时承担续跑记录。当前报告只在本地，跨设备或换工作区前需要显式交接报告；找不到时不得宣称已延续覆盖。

## 首版验收

首次手动执行后，检查以下条件：

1. 范围冻结、PR 顺序和检查记录可追溯，未完成项可续跑，原工作区未被覆盖。
2. 每条确认问题有证据，验证缺口与未运行项明确，没有以问题数量充当完成标准。
3. 用 `LESSONS.md` 的 L001 演练真实 gateway 与推进时钟的检查要求；已修复案例不重复报题。测试可在隔离环境复核，不访问真实供应商。
4. 文档入口、链接、格式和适用 guardrails 通过，报告未被强行跟踪。

用户于 2026-11-03 在首轮通过后授权每天运行一轮，后续两轮由持久调度试运行，再复核覆盖、误报与续跑。反复出现且可确定判断的规则优先进入现有测试或 guardrails；不增加 CI、贡献者评分或黑名单。

## Issue 与使用反馈处理

GitHub issue 是已有问题与使用反馈的统一持久待办。对话或其他渠道可以提供反馈；先查重，相同故障补充到原 issue，新问题才建 issue，不另建反馈队列。普通答疑可以直接解释；需要继续复核、产品裁决或研发处理的有效反馈应留下 issue。新建、评论、关闭、修改 issue 及对外回复均需相应明确授权；缺少授权时先准备具体正文草稿，本地处理可以继续。

反馈至少记录来源、使用版本或提交、触发步骤、预期与实际、已有证据和缺失信息。用户未提供的事实保持未知；故障以“用户报告，待复核”记录，issue 的存在不代表缺陷成立。体验建议记录希望改善的行为，策略偏好记录待决事项，不强行包装成 bug。诊断附件只采集必要的脱敏内容，内部日志与完整附件不自动公开。

手动复核与每日任务按以下顺序进行，每轮共用约30分钟；预算不足时保存待续位置，不为完成数量扩大范围：

1. 冻结当前 `main` SHA 和 issue 讨论快照，先检查 assignee、最新讨论、关联开放或已合并 PR，以及本机正在处理该问题的任务。没有 assignee 不等于无人处理；范围重叠时复用已有工作或保留待办。
2. 最多复核3条 issue，读取完整讨论和关联实现，追踪真实入口及上下游一跳。在冻结版本上分别记录“仍可复现”“已修复或部分修复”“证据不足或未复现”“需要产品或策略裁决”。后续评论可以纠正原报告，不能只按标题开修。
3. 最多推进1条已确认、范围清楚且获授权的问题；明确当前剩余问题、owning boundary、文件范围和回归条件。沿现有本地复现、修复、验证与独立审核步骤处理；低影响的文档修正核对事实来源、链接和门禁即可，不为单行措辞新增镜像测试。没有合格问题时零修复有效。
4. 在 gitignored 的 `docs/reviews/` 保留本轮报告、命令退出码、必要反证和验证证据。报告按 issue 链接列出冻结版本、结论、已改与未改范围、证据位置、阻塞与下一步；它是执行证据，不作为第二套待办。issue 更新草稿区分已完成和残留，获得针对该更新的授权后再发出；关闭 issue 需另行明确授权。
5. 有符合条件的真实使用反馈时，将其整理为新 issue 或原 issue 的补充，获授权后写入，再按同一流程复核。没有新反馈就明确记录“反馈建单未验收”，不能编造故障来演示。完成本地改动与审核后准备 PR 草稿；提交、推送、创建远端 PR、合并和发布继续逐次授权。

处理进度与合并后审查游标分开。issue 中的历史问题或使用反馈不属于本轮新增提交时，不改写 `completed_commits`，也不推进定时任务的覆盖游标。用户于 2026-11-03 授权将 issue 处理接入现有每日任务：`scripts/code_health_issues.py` 负责独立取数、复核及准入，复用 `scripts/code_health_repair.py`；不改变线上 Bot 权限。

每日通过只读 GitHub API 分页读取全部开放 issue 摘要，先复核有待续修复的 issue，再按尚未复核优先、上次复核时间最早优先，最多选三条；已在同一冻结 SHA 复核、issue 元数据、开放 PR 及本地修复状态均未变化时跳过。`blocked` 保留为可重试，模型超时或未完成项不记完成。选中后分页保存完整评论、timeline、关联 PR，以及开放 PR 的文件范围；后续纠正和已合并修复必须纳入判断。需要他人输入的 `needs_decision`、`not_reproduced` 等结论在输入或 main 变化后再审，不承诺每天重复同一条。

模型返回 `confirmed`、`already_fixed`、`not_reproduced`、`needs_decision`、`blocked`、`duplicate` 或 `in_progress`。只有冻结版本上的实测证据、明确 owner 与文件范围齐备时才入修复队列；已有 assignee、关联开放 PR 或与开放 PR 文件重叠时记录 `in_progress`，不接管。稳定故障 key 在两种来源间复用同一任务；不同 key 的故障分别保留完整发现与验收范围，文件相交不能证明是同一问题。两种来源均在执行时检查本地文件冲突：与更早的待修或待交付工作重叠时暂停后来的任务，保留各自证据和待续资格，交人工解决冲突。issue 来源的待续任务需在本轮开放列表中核对每个来源：归属未变、输入指纹未变、先前复核仍为 confirmed 且验证目标相同才可恢复；输入变化时优先重新复核。一个故障关联超过三条 issue 时，可复用同版本且输入未变的先前结论，不要求所有来源同日重审。新反证、已修结论、关闭、取数失败或变化尚未复核均保留工作区并暂停。来源 issue、验证 SHA 和新增证据另记，不伪称发现来自本轮新增提交。

反馈文字准确区分“已复现”“本地修复完成”“已合并”“已发布”和“运行版本已验证”，绑定对应提交、版本与证据。合并到 `main` 不等于用户运行版本已修复；新建 issue 不代表承诺修改策略或发布。使用反馈的手动验收要求至少有一条真实反馈完成查重、建单或补充、复核与明确下一步；缺少输入时，只确认规则落地及历史 issue 处理结果。

## 每日本地调度

执行入口为 `scripts/code_health_review.py`，macOS 使用同一个用户级 launchd，每天本地时间 09:17 运行一轮。首次游标来自已完成首轮的完整 SHA；每轮先冻结远端 main，按配置 `max_units` 限制处理的 first-parent 主线单元数（默认 10，PR 合并或直接提交各计一个），并最多复核三条 issue。没有增量时仍可处理 issue 和修复待办；两种输入均无待办时不调用模型。两种发现共用一个修复队列，每轮最多推进一条修复，不增加第二个日程。

安装状态、规则副本、独立 Git mirror、游标与报告位于本机用户目录的 `Library/Application Support/options-monitor/code-health-review/`；任务工作区不作为调度运行依赖。每轮持久保存 `plan.json`、patch、报告、结构化结果及执行回执。`state.json` 保存连续已完成提交位置，`issue-state.json` 仅保存各 issue 的输入指纹、验证 SHA、结论及报告/修复任务位置，作为 GitHub 待办的本地执行进度；`last-run.json` 保存最近执行状态；runner 每次成功运行后同时刷新已有 `installation.json` 的 `next_calendar_trigger`，记录完成时刻之后的下一个系统本地时间 09:17。定时巡检报告位于 `runs/<运行编号>/report.md`，issue 的完整快照、逐条报告与评论草稿位于同轮 `issues/`。评论草稿尚未发布，仍需明确授权。

runner 先获取只读 GitHub 元数据和冻结源码，再用已有订阅登录的 Codex CLI 按主线顺序逐提交审查，每个提交使用独立上下文。Agent 不加载个人 CLI 配置或 MCP，模型网关和目录参数由本地任务配置明确指定；巡检和审核上下文只可在阶段 `work/` 写临时文件，复现/实现上下文额外只允许写独立修复树，均禁止网络和交互提权。外层 runner 负责写报告与游标。修复回归使用无网络验证沙箱与独立依赖环境，日志和 JUnit 由 runner 回读；每日总预算由 `timeout_seconds` 控制（当前安装为1800秒），提交巡检按本轮实际计划提交数分配，issue 复核仍受 `issue_timeout_seconds`（默认600秒）和实际剩余时间限制，其后修复只用每日预算剩余部分。issue 取数每次请求使用总预算剩余时间；耗尽时不记录完成。提交巡检子预算超时只保留该阶段待续，按实际剩余时间继续 issue 和修复；总预算不足的阶段留待下轮，不承诺单轮完成修复。仅在退出成功、报告非空、完成提交为计划的连续前缀且报告已持久化后推进提交游标；issue 结果不参与该游标。issue 报告及合格修复记录先持久化，再写 issue 进度；复核失败不影响已完成提交覆盖，但会单独记入回执。运行锁防止手动与定时并发更新状态。

提交巡检预算公式：`N = max(1, len(planned_commits))`，单元基准 `U = max(30, review_timeout_seconds / 3)`（默认900/3=300秒，旧配置表示三个单元的基准预算）。先取 `R = min(timeout_seconds, floor(deadline - monotonic()))`；有本轮待审 issue 时预留 `I = min(R, issue_timeout_seconds)`，否则 `I = 0`，得 `A = R - I`。启用 repair 时，巡检上限 `C = min(floor(A * N / (N + 3)), A - 30)`，为后续修复保留三个单元的份额且至少30秒；未启用时 `C = A`。最终巡检超时 `T = floor(min(U * N, C))`。若 `T < 30` 则巡检记待续，保留后续阶段预算；剩余总预算不足30秒时也不启动阶段。默认每日1800秒、repair启用且尚未消耗预算时，无 issue 的1/3/9个提交分别获得300/900/1350秒；有待审 issue 预留600秒时分别为300/600/900秒。该 `T` 是整批提交阶段的总额度；每个当前提交可以使用 `floor(min(提交阶段deadline, 每日deadline) - monotonic())` 秒，后续提交重新读取该余量。`U` 仅用于整批预算缩放，不再另设单提交硬上限，以免较大提交每轮都在相同上限处超时而永远阻塞连续游标。每个上下文只接收当前提交、冻结源码、对应 patch 和此前已持久报告，提示中写明真实硬超时，并要求在最后 `min(60秒, 本单元预算的四分之一)` 停止新探针、生成结构化结果。单元退出成功、结果合格、报告与证据持久化后立即推进连续游标，再审下一单元。单元记录位于同轮 `units/<SHA>/`；顶层报告与结果聚合已完成单元，聚合 finding 的证据复制到同轮 `work/units/<SHA>/`。后续单元超时或未完成时，已有覆盖、报告和修复任务保留，当前及之后单元待续；不会跨过未完成单元。阶段执行前重新核算实际剩余时间，预算分配不延长每日 deadline，也不承诺本轮完成全部提交。`--smoke` 继续只受总预算剩余时间限制。

发现中的 `evidence_log` 可以是阶段 `work/` 内的相对路径，或规范化后仍位于该目录内的绝对路径。绝对路径的原始组件含 `..` 或 `.git` 时拒绝；解析路径与 `work/` 的 symlink 后，必须能通过路径级 `relative_to(work)` 检查，转换结果还须满足原有相对路径校验（无 `..`、`.git`）。目录外路径、同前缀兄弟目录和通过 symlink 逃逸的路径仍拒绝。归一化后的 finding、持久化结构化结果与修复任务均保存相对 `work/` 的 `evidence_log`；入队仍要求该证据为目录内实际文件。`owner_path`、`fix_scope` 继续只允许原有规则下的相对路径。

状态与维护命令使用本机实际路径替换占位符：

```bash
<python> <状态目录>/runner.py status --state-dir <状态目录>
<python> <状态目录>/runner.py run --state-dir <状态目录> --dry-run
launchctl print gui/$(id -u)/local.options-monitor.code-health-review
launchctl kickstart gui/$(id -u)/local.options-monitor.code-health-review
```

`--dry-run` 只取数规划，包括最多三条 issue 的完整快照，不调用模型、不改两种进度。`--smoke` 仅调用模型读规则和源码验证结构化结果，不处理 issue、不审查增量、不推进游标。状态入口同时显示 issue 进度；回执中 `issues.status` 单独表示 issue 阶段的完成、待续或失败，不能用外层进程成功推断 issue 已完成。暂停任务使用 `launchctl bootout gui/$(id -u) <plist路径>`，恢复使用 `launchctl bootstrap gui/$(id -u) <plist路径>`；操作调度或删除状态仍需要相应用户授权。不要删除唯一游标及报告副本。

任务跨本次聊天会话继续，但不是云端常驻：依赖该 macOS 用户已登录、机器可运行、GitHub认证和本地模型网关可用。睡眠错过的 calendar 触发由 launchd 在唤醒后合并补跑；关机或退出登录时不运行，也不承诺补齐每天一次。失败保留回执，等下次日跑或显式手动重试；不自动修改权限、切换模型或高频重试。
