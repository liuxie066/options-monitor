## Findings

### 1-未修复-高-S4 sealed snapshot 封存位置错误，写在 symbol 级函数会导致重复封存或缺少 run 级上下文
- **位置**: plan §8 S4；§5 affected files（`combo_yield_steps.py`）；§7 decision 1
- **问题类型**: 不可直接实施 / 切片过粗 / 状态机漏洞
- **当前写法**: plan 写“`combo_yield_steps.py` 在 `run_combo_yield_scan_and_summarize` 成功/空结果后 seal snapshot”。
- **反例/失败场景**: `run_combo_yield_scan_and_summarize` 是 symbol 级函数，per-symbol pipeline 每个 symbol 调用一次。若在每个 symbol 完成后 seal 到同一 run/account，第二次调用会重复写同一个 snapshot 路径；opening snapshot 的写入是 `write_account_run_state_bytes_once_safely`（once-safely，二次写会报 AccountRunConfigError）。同时该函数签名没有 `run_id`、`account`、`physical_account`、`account_config_sha256` 等 seal 必需参数，只有 `report_dir`。
- **为什么有问题**: opening snapshot 的 seal 点在 `pipeline_watchlist.py:855`，是 run/account 级聚合所有 symbol 后一次封存；Combo 若在 symbol 级 seal 会破坏“一账户/run 一份不可变快照”的既有不变式。
- **直接证据**: `pipeline_watchlist.py:855`（唯一 seal 调用点）；`opening_candidate_snapshot.py:168-176`（once-safely 写入）；`combo_yield_steps.py:466-506`（symbol 级 facade，无 run_id/account 参数）。
- **影响**: 实施 Agent 生成错误代码（重复封存冲突）或被迫在 symbol 级凭空造 run 上下文，破坏唯一真源与 once-safely 语义。
- **建议改法和验证点**: 明确 S4 的 seal 位置在 run/account 级聚合处（`pipeline_watchlist.py` 或 Combo 专属 run 级 collector），由它收集各 symbol 的 `ranked_pairs` + reject reasons 后封存一次；`combo_yield_steps` 只产出 symbol 级 pair 结果与拒绝证据，不 seal。测试必须覆盖多 symbol run 只生成一份 snapshot。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### 2-未修复-中-删除清单不完整，`max_debit` / `max_debit_native` 会残留为死配置
- **位置**: plan §6 contract changes；§5 affected files；§8 S2
- **问题类型**: 契约缺失 / 范围漂移
- **当前写法**: 只列删除 `funding_mode` 与 `max_call_cost_to_put_credit`。
- **反例/失败场景**: `YIELD_ENHANCEMENT_ALLOWED_FIELDS` 仍含 `max_debit` / `max_debit_native`；`config_validator.py:675-684` 仍有 `funding_mode=max_debit 要求 max_debit` 校验；`sell_put_call_helper.py:371-375, 798` 仍读 `max_debit_native`。只删两个字段后这些配置键和分支变成死代码，validator 报错路径不一致，配置作者可能以为 `max_debit` 仍生效。
- **为什么有问题**: 确认文档第 4 节明确废弃 `funding_mode`（credit_or_even / max_debit）整体，不是仅删枚举字段；方案没把配套字段一起清理。
- **直接证据**: `config_validator.py:206-209, 671-684`；`yield_enhancement_config.py:51-71`；`sell_put_call_helper.py:369-375, 798-799`。
- **影响**: 死配置键残留、校验语义不一致，违反“删除/废弃”的确认结论。
- **建议改法和验证点**: 把 `max_debit`、`max_debit_native` 一并移出 allowed fields，validator 对它们按已移除字段拒绝；同步清理 `YIELD_ENHANCEMENT_DEFAULTS`、`STRUCTURE_DEFAULTS`、`configs/system.json`、示例。测试：配置含 `funding_mode` / `max_call_cost_to_put_credit` / `max_debit` / `max_debit_native` 任一项都报错。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 3-未修复-中-S3 跨标的 `put_only_period_net_return` 字段来源未定义，实施 Agent 会猜
- **位置**: plan §7 decision 2；§8 S3
- **问题类型**: 不可直接实施 / 契约缺失
- **当前写法**: “pair row 新增 `put_only_period_net_return`，由 `put_only_net_credit / (put_strike * multiplier - put_only_net_credit)` 计算”。
- **反例/失败场景**: 代码里 put universe 行已经带 `period_net_return_on_cash_basis`（来自 Sell Put 扫描，`scan_sell_put.py:83`）；plan 要求重新算一个等价字段，但没有定义与主策略字段的对齐规则，也没有定义分母非正（`put_strike*multiplier - put_only_net_credit <= 0`）时如何处理。主策略在 `candidate_engine.py:461-469` 对 `net_cash_basis <= 0` fail closed（`net_cash_basis_non_positive`），Combo 沿用这一语义才能保证 put 腿“继承 Sell Put 硬门槛”是真的。
- **为什么有问题**: 排序 key 直接消费该字段（`yield_enhancement_staggered_rank_key` / `pair_shadow_rank_key` 现在用 `put_only_annualized_net_return`），字段语义不一致会让跨标的排序和主策略收益口径漂移。
- **直接证据**: `candidate_engine.py:461-469`；`scan_sell_put.py:83`；`yield_enhancement.py:423-431, 810-816`。
- **影响**: 实施 Agent 自造公式或错误 fallback，排序与主策略不一致。
- **建议改法和验证点**: 明确字段来源 = put universe row 的 `period_net_return_on_cash_basis`（若缺失才 fallback 计算），分母非正按主策略 `net_cash_basis_non_positive` 语义 fail closed 或置为不参与排序；测试断言与主策略同行的字段值一致。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 4-未修复-中-Daily Brief 切换只写了“读快照”，未定义快照字段到 `_candidate_view` 的映射
- **位置**: plan §8 S4；§7 decision 5；§9 expected assertions
- **问题类型**: 不可直接实施 / 测试缺口
- **当前写法**: “`daily_decision_brief_service.py` 改为读取 snapshot 中的 `ranked_pairs`，不再对 CSV 调用 `select_best_yield_enhancement_per_symbol`”。
- **反例/失败场景**: `_candidate_view(row, family="combo_yield", ...)`（`daily_decision_brief_service.py:1750`）读取的字段集合来自 CSV row；snapshot 的 `ranked_pairs` 需要包含全部渲染字段，否则通知渲染缺列/缺值。plan 没有列出 snapshot payload 字段清单，也没有断言“snapshot 中字段覆盖 CSV 字段”的兼容测试。
- **为什么有问题**: 通知文本是用户可见输出，字段映射缺失会导致实施 Agent 在渲染期才发现缺字段，review 不可验收。
- **直接证据**: `daily_decision_brief_service.py:140-144, 306-311, 1750-1790`（`_load_candidate_family` glob CSV、二次排序、`_candidate_view`）。
- **影响**: 通知字段缺失或渲染回归，后续返工。
- **建议改法和验证点**: 在 plan 中列出 snapshot `ranked_pairs` 的必需字段（至少覆盖 `_candidate_view` 引用的字段），并加“snapshot 字段 ⊇ CSV 渲染字段”断言测试；删除 CSV glob 后该测试仍绿。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 5-未修复-低-Agent 端 Combo 消费范围表述不确定

## Implementation Finding 6（2026-08-08T09:20+08:00，S1 事实修正）

进入 S1 实现前核实代码事实，发现 plan 对 `min_net_income=0.0` 的归因有误：

- Sell Put 主策略 `sell_put_steps.py:92-100` 的 `run_sell_put_scan(...)` 同样传 `min_annualized_net_return=0.0`、`min_net_income=0.0`，注释明确“Underwriting applies return/income thresholds once, after CNY enrichment”；
- 真正门槛在 `enrich_and_filter_sell_put_underwriting`（`sell_put_strategy_risk.py:58`），`resolve_sell_put_underwriting_config` 从 `sell_put_cfg` 解析 `min_net_income`（默认 50.0）；
- Combo 流程 `combo_yield_steps.py:267-272` 已调用 `underwriting_filter_put_candidates_fn`（默认即上述 underwriting），传入 `sell_put_cfg=yield_sp`（继承 Sell Put 配置）；
- 因此“Combo 写死 min_net_income=0.0 绕过 Sell Put 门槛”不成立；`0.0` 是 scan 层与主策略一致的故意行为，真实继承已发生在 underwriting 层。

修复：S1 从“改 scan 层 min_net_income=0→50”改为“验证并测试 Combo put 腿经过与主策略相同的 underwriting 门槛（含 `min_net_income` 继承），scan 层保持与主策略一致”。S1 的实际实现是加继承与一致性测试，必要时才对 `combo_yield_steps.py` 的 underwriting 调用做最小修正。

状态：已修复（plan §8 S1 已同步更新）。
