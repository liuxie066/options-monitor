## Goal and boundary understood

The plan must stop duplicate option-close receipts while preserving the canonical
`trade_events -> position_lots` ledger. Broker source identity, per-lot ledger events, lifecycle
allocations and notification identity have different grains: a broker deal is accepted once, may produce
a deterministic per-lot event split set, and produces one aggregate ordinary-close notification. A
zero-price expiry close may reserve a lot as non-actionable before its final reason is known, without
prematurely changing the financial projection.

## Re-review of previous findings

1. **Projection circular prerequisite — closed**: pending evidence leaves projection at frozen remaining,
   reservation blocks further action, and `expire_close` verifies projection zero only after terminal
   write.
2. **Per-lot notification duplication — closed**: ordinary close uses the canonical broker deal key and
   one aggregate Outbox after all split events and projection readback.
3. **Voided allocation effectiveness — closed**: effective void ids are derived from canonical events and

4. **Broker deal versus terminal-event cardinality — closed**: success criteria now require one complete,
   deterministic split set; ordinary close retains per-lot events without lifecycle allocations, while
   lifecycle terminal events and allocations remain one-to-one by target lot.

## Special review lenses

### Architecture boundary review

The plan preserves domain purity for reason resolution, keeps broker queries in the application/
infrastructure boundary, and keeps financial writes in the ledger transaction owner. Reservation is a
derived overlay rather than a second lot projection. Notification aggregation is separated from per-lot
ledger event identity. No blocking boundary violation remains.

### Best-practice review

The plan uses immutable evidence, deterministic identities, transaction-local revalidation, append-only
void correction, durable Outbox states, CAS revisions, fault injection and migration dry-run/readback.
Incomplete upstream evidence and uncertain provider delivery both fail closed. The validation matrix now
tests cardinality at broker, event, allocation and notification grains.

### Optimal-solution review

Reusing existing lifecycle case/evidence/allocation and canonical event projection is safer and smaller
than introducing a provisional close event, mutable allocation status or second projection. Aggregating
only the receipt layer preserves existing per-lot accounting precision while solving the user-visible
duplicate problem.

### Overengineering review

The observation contract, lifecycle overlay and Outbox add material complexity, but each addresses a
demonstrated failure mode: uncertain cause, broad open-lot consumers and send-after-mark crashes. The plan
explicitly avoids unsupported cash settlement, new systemd ownership and a second lifecycle database.
No unjustified abstraction is a blocker.

### Overcoupling review

The shared overlay facade prevents actionability logic from being copied across consumers, while the pure
resolver remains independent of SQLite, Futu and Feishu. Broker operation identity is no longer coupled to
per-lot event identity. Implementation remains broad, but slices and ownership boundaries are explicit
enough to review incrementally before any production rollout.

## Residual risks and suggested tracking

- **Slice D identity inventory**: current `broker_deal_key_from_payload()` and
  `broker_external_event_key()` still fall back to raw `deal_id` when account binding is incomplete.
  Implementation must enforce the plan's no-fallback contract at intake and Outbox creation, and the
  missing-key tests must prove zero automatic notification.
- **Slice C overlay inventory**: the set of open-lot consumers is large. Track an explicit call-site
  checklist and require fail-closed integration tests for Position Advice, Close Advice, auto-close,
  assignment scenario, report/query surfaces and quality checks.
- **Slice B broker capability**: Futu endpoint availability and pagination/coverage proof remain empirical
  implementation checks. Do not weaken `complete=true` if the SDK cannot prove coverage.
- **Slice E provider reconciliation**: if Feishu supplies no queryable message identity, `unknown` remains
  operator-owned and must never be automatically resent.
- **Rollout handoff**: mixed old/new binary and schema compatibility must be verified before any upgrade;
  migration apply, dispatcher enablement and trade-intake restore remain separate authorization gates.

## Final conclusion

**pass-with-risks**

The frozen plan is code-generation-ready. The previous ledger-grain contradiction is resolved without
changing the architecture: one broker deal produces one deterministic per-lot split set and one aggregate
ordinary-close notification. Remaining risks are implementation capability and inventory checks already
covered by explicit fail-closed gates and tests.
