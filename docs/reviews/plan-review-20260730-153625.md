# Plan Review

## Reviewed target and scope

- Target: `docs/plans/daily-brief-local-gap-degraded-delivery-plan-20260730.md`
- Revision focus: stable gap identity、mutable state diff、position-scoped alert isolation
- Full scope: required-data classification、account projections、degraded source graph、Daily Brief persistence、delivery baseline and recovery
- Review lenses: architecture boundary、best practice、optimal solution、overengineering、overcoupling

## Assumptions tested

- stable gap identity 能逐 consumer/position 跟踪同一问题；
- reason、severity、outcome、basis 的变化不会制造 recovered + new；
- confirmed normal envelope 能作为唯一且单调的 transition baseline；
- Brief revision、rendered message 和 delivery envelope 能冻结同一份 transition；
- late confirmation/operator resolution 不会使新 revision 基于过时 baseline；
- exact retry 仍能回读原 envelope/message。

上一轮 finding 已得到实质修复：计划现在把 stable gap identity 与可变状态分开，
position gap 明确绑定 requirement/lot/consumer scope，duplicate identity fail closed，
并补齐多仓位、changed、retired 和 digest 稳定性测试。

## Findings

### 1-未修复-高-baseline 选择与 Brief revision 持久化不在同一原子边界，迟到确认会冻结错误 transition

- **位置**: Phase C baseline 步骤 1-6；Daily Brief persistence 与 delivery prepare sequencing
- **问题类型**: 并发恢复风险 / 架构边界 / 不可直接实施
- **当前写法**: 计划要求在“prepare 阶段”的 account/market delivery lock 内选择最后 confirmed
  normal envelope，并把 transition 与当前 gap state 一起冻结进“新的 Brief revision/envelope”；
  但没有定义由哪个 repository API 在同一临界区内完成 baseline selection、transition computation、
  immutable revision allocation/persistence、render 和 envelope preparation。
- **反例/失败场景**:
  1. 当前 run 先按 baseline A 生成并持久化 revision N；
  2. 上一份 ambiguous/pending normal envelope 随后被 provider callback 或 operator resolution
     确认为 baseline B；
  3. 当前 run 再进入 delivery prepare。此时 revision N 已冻结基于 A 的 transition，但最新权威
     baseline 已是 B。继续发送会重复或漏掉 changed/recovered；重新计算又必须改写 immutable
     revision 或分配额外 revision。
- **为什么有问题**: baseline 是由 delivery confirmation 状态决定的，但 transition 属于 Brief
  artifact。二者分属当前两个 repository 操作，而计划只声明“使用同一 lock”，没有收敛事务
  ownership、锁顺序和冲突重试。实施者无法同时满足 immutable revision、latest-confirmed baseline
  和 exact-envelope binding。
- **直接证据**:
  - 目标计划 `468-481` 要求 prepare 锁内选 baseline，并把 transition 冻结到新 Brief
    revision/envelope；
  - `src/application/tick_notification_flow.py:760-828` 当前先 assemble、调用
    `persist_daily_decision_brief_success()`，再决定 delivery；
  - `src/application/tick_notification_flow.py:937-984` 之后才 render 并调用
    `prepare_daily_decision_brief_delivery()`；
  - `src/application/daily_decision_brief_repository.py:48-115` Brief revision 在独立 lock
    临界区内分配并持久化；
  - `src/application/daily_decision_brief_repository.py:385-428` envelope prepare 再次独立取得
    同一 account/market lock；
  - `src/application/daily_decision_brief_repository.py:588-694` confirmation 和 operator
    resolution 也通过该 lock 改变 baseline eligibility。
- **影响**: 用户可能重复收到“首次/恢复”或漏掉状态变化；错误 transition 一旦发送并 confirmed，
  会成为下一轮 baseline。错误若通过覆盖 revision 修复会破坏 content-addressed delivery，
  若通过追加 revision 修复则可能产生 orphan revision 和错误 candidate/delivery decision。
- **建议改法和验证点**: 在计划中明确一个 repository-owned 原子 API 及锁顺序。推荐让该 API
  接收尚未分配 revision 的 normalized Brief draft 和拟发送 action，在单个 account/market
  delivery lock 内：
  1. 校验 delivery state 并选择 baseline identity；
  2. 计算并写入 transition/baseline identity；
  3. 分配和持久化唯一 immutable Brief revision；
  4. render 或校验由该 revision 确定的 exact message；
  5. prepare exact envelope；
  6. 原子发布 delivery state，失败时不留下可被 current/envelope 引用的半成品。
  如果保留分步 API，则 Brief 必须记录 baseline identity，envelope prepare 在锁内重验；
  baseline 已变化时应安全废弃未发送 revision并重新分配，禁止原地覆盖。
  测试至少注入：baseline selection 前后迟到 confirm、operator resolution、进程在 revision
  write/envelope state write 之间崩溃、两个同账户 scheduled runs 竞争，以及 exact retry
  始终引用原 revision/message。
- **修复风险（低/中/高）**: 高
- **严重程度（低/中/高/严重）**: 高

## Open Questions

- render 是否放入 repository 原子 API？可以把纯 domain renderer 作为 callback/预计算函数传入，
  但最终 message digest 必须在同一临界区内绑定到刚持久化的 revision。

## Residual Risks

- 单个原子 API 会扩大 repository 临界区；应在锁外完成 provider I/O 和 Brief draft assembly，
  锁内只做本地校验、diff、持久化和 envelope freeze。Tracking destination:
  Phase C repository API design。
- 多文件原子发布仍可能留下未被 index/envelope 引用的 orphan revision；可以容忍 append-only
  orphan，但 recovery 必须跳过或显式审计，绝不能覆盖。Tracking destination:
  Daily Brief repository crash-recovery tests。
- gap-only transition 不创建独立 delivery action，恢复提示可能延迟到下一份正常简报。
  Tracking destination: Daily Brief product acceptance notes。

## Conclusion

`fail`

第六轮已解决 stable alert identity finding，但 Brief transition 与 delivery confirmation
尚未建立可实施的原子 ownership。收敛该边界前，不建议进入实现。
