- **文件(行号)**: `src/application/candidate_scanning.py:124-198`; `src/application/sell_put_steps.py:85-132`; `src/application/sell_call_steps.py:179-233`; `src/application/symbol_monitoring.py:412-434, 474-479, 625-633`; `src/application/opening_candidate_snapshot.py:420-474, 596-637`; `src/application/agent_tools/candidate_filter_impl.py:67-124, 127-224`; `tests/test_opening_candidate_snapshot.py:246-284`
- **输入场景**: 某个 symbol 的期权链读取成功，但全部合约因计算事实缺失、年化收益、净权利金、spread、IV/RV、财报或容量门槛被拒绝，因此最终候选为零。用户随后通过唯一正式人工分析入口 Agent 查询“为什么没有候选”。
- **实际分支**: 计算失败只进入 `run_candidate_scan()` 的局部 `reject_rows`；生产调用 `output=None` 且未传 `reject_log_output`，因此这些行不会进入任何正式事实。underwriting 又只返回通过的 DataFrame，final-candidate sink 也只捕获通过行。snapshot 的 `_snapshot_decisions()` 只遍历 final candidates，并要求每行已经 accepted；空结果最后只剩 strategy scope 的通用 `opening_candidates_captured`。Agent 将除 `all_decisions_captured` 和 `candidate_accepted` 以外的所有 reason 都统计为拒绝。
- **预期行为**: Candidate Engine 的每个可定位 contract/expiry 决定，无论接受或拒绝，都应随稳定 reason code 写入 sealed snapshot；Agent 只解释这些已记录决定。strategy 级完成标记不应伪装成合约拒绝原因。
- **实际行为**: 最小复现得到 `opening_status=no_candidate`、`conclusion_status=supported`、`trace_count=1`，但 `rejection_reason_counts={"opening_candidates_captured": 1}`，并生成 `status=rejected` 的同名事件；真实拒绝规则、metric 和 threshold 全部缺失。现有 empty-snapshot 测试只断言状态和空 ranked list，没有验证拒绝证据。
- **直接证据**: `run_candidate_scan()` 在 147-176 行收集计算拒绝，却仅在 190-195 行可选写 CSV；两个 strategy step 在 128-132 / 229-233 行只上送过滤后的最终行；`_snapshot_decisions()` 在 438-470 行只为 final rows 重建 accepted decision；`_scope_results()` 在 614-637 行只能从这些 accepted decisions 生成 contract scope；Agent 在 165-169 和 201-224 行把通用完成 reason 判成 rejection。该行为与实施方案要求“scope 至少定位 contract 并带稳定 reason code”和“Agent 只解释 snapshot 已记录的 Candidate Engine decision”直接冲突。
- **影响**: Agent 是本策略明确的唯一人工分析入口，但 no-candidate 的核心解释不可用且会给出错误拒绝理由；这会使策略复盘、数据缺失诊断和阈值审计失真，也无法证明 Agent、通知和 Position Advice 对同一 run 的 reason code 一致。
- **建议改法和验证点**: 让 Candidate Engine 输出完整 accepted/rejected decision stream；计算失败、hard gate 和 underwriting 拒绝都通过显式 sink 进入 snapshot 的 contract/expiry scope。将 strategy completion reason 与 rejection reason 分型，Agent 不得把前者计入拒绝。新增 no-candidate 回归：分别覆盖计算失败、容量、收益、IV/RV、财报和 spread 拒绝，并断言 Agent 返回同一 decision hash、metric、threshold 和稳定 reason code，不读取 CSV 或重跑策略。
- **修复风险（低/中/高）**: 中

### 2-未修复-高-期权持仓上下文读取失败时 Sell Put 容量退化为全额现金，可能推荐超额担保合约

- **入口/函数**: `pipeline_runtime.run()` -> `run_watchlist_pipeline_default()` -> `build_pipeline_context()` -> `enrich_sell_put_candidates_with_cash()` -> `evaluate_opening_candidate_policy()`
- **文件(行号)**: `src/application/pipeline_context.py:129-263, 516-561`; `src/application/pipeline_watchlist.py:295-299, 361-371`; `src/application/sell_put_cash.py:55-130, 207-250, 395-465`; `domain/domain/engine/candidate_engine.py:524-548`; `src/application/pipeline_runtime.py:332-355`
- **输入场景**: 未提供 prepared option-position manifest 的公开/direct pipeline 路径中，Futu portfolio cash 正常可用，但 SQLite option-position context 因读取错误、账户校验失败或缓存/数据源异常返回 unavailable；账户实际上可能已有 short put 占用接货资金。
- **实际分支**: `load_option_positions_context()` 捕获全部异常并返回 `(None, False)`。watchlist 随后构造一个只包含 Covered Call locked-share unavailable 字段的非空 `option_ctx`，没有 `cash_secured_unavailable_by_symbol`。Sell Put enrichment 将该非空对象视为可计算上下文，把 cash-secured 占用归零，并按完整现金计算正数 `max_new_contracts`。Candidate Engine 的 Put 容量 hard gate 只检查 `max_new_contracts >= 1`，不校验 option-position authority 或 `capacity_authority_status`。
- **预期行为**: 现有 short-put 占用无法读取时，Sell Put 接货容量必须 fail closed；不得把“未知”解释为零占用。Covered Call 的 locked-share fallback 与 Sell Put 的 cash-secured fallback 必须同时表达 unavailable。
- **实际行为**: 使用与 watchlist fallback 相同的 `option_ctx`、USD 20,000 现金和 `strike=90, multiplier=100` 做最小复现，enrichment 生成 `max_new_contracts=2`、`cash_secured_unavailable_reason=null`，随后 Candidate Engine 返回 `accepted=true`。同文件的 `sell_put_opening_capacity_inputs()` 本来会在 option context 缺失时 fail closed，但它没有生产调用方，仅被测试直接调用。

- **影响**: 当账户已有未平 Put 时，direct/public pipeline 可推荐超过真实接货资金承受能力的合约数量。这违背“愿意接货但不主动追求接货”的现金担保底线，属于物理账户容量安全边界错误。受控 scheduled tick 的 prepared-context barrier 可降低生产触发概率，但共享 pipeline 和公开 direct 路径仍然存在该行为。
- **建议改法和验证点**: 在 option context owner 处建立一个统一 unavailable contract，同时填充 locked-shares 与 cash-secured 不可用原因；Sell Put enrichment 在确认账户绑定、ledger authority 和 cash-secured completeness 前保持 `max_new_contracts=0`。删除或真正复用当前未接入的 `sell_put_opening_capacity_inputs()`，避免两套容量判定。新增集成测试：让 `load_option_positions_context()` 失败且账户有现金，断言 direct 和 scheduled-adapter 两条路径都产生 `hard_capacity_put`，不产生候选。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### 3-未修复-中-封存阶段用默认阈值重新判定，和扫描阶段的已解析配置不是同一策略

- **入口/函数**: `evaluate_underwriting_candidate()` -> final-candidate sink -> `_snapshot_decisions()`
- **文件(行号)**: `domain/domain/insurance_underwriting.py:35-61, 78-104`; `src/application/opening_candidate_snapshot.py:438-451`; `src/application/config_validator.py:462-498`; `domain/domain/sell_put_config.py:27-71`; `domain/domain/sell_call_config.py:91-136`; `domain/domain/engine/candidate_engine.py:421-548`
- **输入场景**: 一份通过 config validation 的 symbol/template 配置把 Sell Put 年化门槛设为 `0.08`，候选年化净收益为 `0.09`，其他 hard gate 全部满足。相同问题也适用于净权利金、IV/RV、spread 等运行时解析阈值。
- **实际分支**: underwriting wrapper 调 Candidate Engine 时显式传入已解析的 `InsuranceUnderwritingConfig`；但 `underwriting_fields()` 只把 DTE、strike 和 max-spread 的部分政策字段投影到 row，没有序列化完整 resolved policy。snapshot 随后再次调用 `evaluate_opening_candidate_policy(normalized, mode=mode)`，未传任何 resolved thresholds，因此回到 engine 默认的年化 `0.10`、净权利金 CNY 50、IV/RV 1.10/0.05 和 spread 0.40。
- **预期行为**: 相同 normalized input 在 scan adapter、sealed snapshot 和 Agent explanation 中必须使用同一个 resolved policy，得到相同 accept/reject 和 provenance；或者，如果策略合同中的 10%/CNY 50/1.10/0.05/40% 是真正固定值，配置层就不应接受其他数值。
- **实际行为**: 最小复现中，`evaluate_underwriting_candidate(... min_annualized_return=0.08)` 返回 accepted；对同一 row 调 snapshot 使用的默认 evaluator 后，结果变为 rejected，reason 为 `return_annualized`、metric `0.09`、threshold `0.10`。实际 seal 会因此抛出 `final candidate is not accepted by opening policy`。反向使用更严格配置时虽然不会报错，但 snapshot 记录的 decision provenance 仍不是扫描时实际政策。
- **直接证据**: wrapper 在 45-60 行传入 cfg 全量阈值；其字段投影在 86-98 行没有保存 min annualized、min net premium、min IV/RV 等值；snapshot 在 447 行以默认参数重判。与此同时 validator 在 478-498 行允许这些阈值取任意合法非负/区间值，Sell Put / Covered Call resolver 也会接受 symbol/template 覆盖。该行为违反实施方案 214 行要求的 direct domain、scan adapter、Agent explanation 三方 parity。
- **影响**: 合法配置可以在扫描成功后使 snapshot sealing 整体失败，导致账户 run 从“有候选”变成数据管线失败；即使未失败，消费者看到的 policy provenance 也可能与实际过滤政策不同。当前配置若恰好等于默认值则不会触发，因此严重程度评为中。
- **建议改法和验证点**: 先在合同层确定唯一真源：若阈值固定，删除/拒绝非固定配置并由 Candidate Engine 常量唯一拥有；若仍允许账户/symbol 配置，则生成不可变 resolved-policy payload/hash，扫描与 snapshot 都引用同一 payload，snapshot 不做无参数重判。新增参数化 parity 测试，至少覆盖默认、宽松、严格三组阈值和 Put/Call 两种模式，并断言 seal、Agent reason 和 engine decision hash 一致。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 中
