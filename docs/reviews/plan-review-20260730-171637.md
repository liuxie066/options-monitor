# Plan Review

## Reviewed target and scope

- **Target**: `docs/plans/daily-brief-local-gap-degraded-delivery-plan-20260730.md`
- **Review mode**: adversarial implementation-plan review
- **Scope**: `success_empty` classification, required-data evidence, strategy/candidate propagation, Daily Brief warning projection, notification authority boundary, implementation slices, and validation gates
- **Excluded**: implementation, source edits, production execution, real notification, release, and deployment

## Goal and boundary understood

The plan intentionally narrows this work unit to one case: an OpenD/Futu request that genuinely succeeds and produces zero canonical option rows. That case should remain a complete non-actionable decision source, produce a degraded Daily Brief warning, and continue through normal delivery. Provider, parse, not-attempted, partial, and integrity failures remain fail-closed and continue through the existing fixed-failure path.

This is the right product boundary. The review therefore tests whether the proposed evidence chain can actually prove “successful empty” without admitting an acquisition failure, and whether the user-visible warning remains tied to that proof.

## Assumptions tested

1. The fetch owner can distinguish a successfully empty expiration/chain response from an expiration-discovery failure.
2. Every expected expiration request can be shown to have completed before aggregate `success_empty` is emitted.
3. A zero-row quote snapshot can retain the existing receipt and manifest authority without changing candidate source schemas.
4. A completed-zero strategy status can produce a user-visible warning without granting action authority.
5. The Brief assembler can confirm, rather than merely trust, the quote binding named by the strategy status.
6. Existing candidate capture/source v1 permits zero decisions when quote dependencies are present.
7. The focused test list exercises the actual owners of empty discovery, zero-decision capture, source publication, and Brief projection.
8. The strict boundary does not require provider peers, a new coverage model, candidate source v2, a notification type, or a new persistence state machine.

## Special review lenses

### Architecture boundary review

The plan generally keeps classification at the fetch owner, evidence sealing in required-data ownership, strategy completion in strategy status, and presentation in the Brief assembler/renderer. However, the actual expiration-discovery owner is omitted from Slice A and currently destroys the distinction the plan relies on.

### Best-practice review

Positive success should be proven by explicit stage outcomes, while exceptions and skipped stages remain distinct terminal failures. The current plan states that principle but does not specify the existing discovery-stage exception collapse or test it. The Brief warning should likewise be derived from a validated evidence binding, not only from self-consistent display metadata.

### Optimal-solution review

The narrow `success_empty` slice is more practical than introducing provider-peer health, account coverage proofs, candidate source v2, or a new notification workflow. No broader model is required. The smallest safe correction is to preserve typed expiration-discovery evidence and validate the already-planned manifest/status binding.

### Overengineering review

No material overengineering finding. The deferred list is appropriately strict, existing v1 source and delivery contracts are retained, and the plan avoids new services, databases, alert identities, or retry state machines.

### Overcoupling review

The strategy status is a reasonable family-scoped projection of symbol-scoped quote evidence. It becomes unsafe only if the Brief trusts duplicated binding fields without checking them against the run-scoped manifest. A narrow equality/validation check avoids coupling the renderer to raw OpenD payloads or candidate-source internals.

## Findings

### PR-01-未修复-高-expiration discovery 失败仍可被压成空结果，`success_empty` 的正向证明不闭合

- **位置**: Typed outcome §4.1-4.2；Option-chain fetch result §5.1；Slice A；测试与质量门 §8
- **问题类型**: 状态机漏洞 / 架构边界 / 不可直接实施 / 测试缺口
- **当前写法**: 计划要求 provider 调用实际发生、成功码与 response contract 有效、全部 expiration scope 完成，且异常或未执行不得进入 `success_empty`。Slice A 只列出 `option_chain_fetching.py`、`opend_symbol_fetching.py`、outputs 和 snapshot，并笼统要求 conversion/validation exception 不再被吞。
- **反例/失败场景**: `get_option_expiration_dates()` 在重试后抛出 timeout、permission、rate-limit 或 response-shape 异常。现有 `fetch_symbol_option_chain()` 捕获任意异常并把 `expirations_all` 设为 `[]`。随后 `fetch_option_chains()` 把空 targets 改成 `[None]`，执行一次无 expiration 的 option-chain 请求。若该请求成功返回空表，实现 Agent仅按“最终 canonical rows 为 0”落地计划，就会产出 `success_empty/no_expirations`，把 discovery 获取失败伪装为可靠空数据。
- **为什么有问题**: 这正好违反计划的核心不变量“错误不伪装成空数据”，并且会重现用户要消除的歧义，只是把歧义从 `EMPTY_CHAIN` 字符串转移到新的 typed outcome。计划没有为 expiration discovery 定义独立 terminal outcome，也没有说明空 discovery 后是否允许 `[None]` 兜底请求，因此实现 Agent仍需现场重新设计最关键的状态机。
- **直接证据**:
  - 计划第 115-143 行要求 provider 成功、scope 完成，异常和未执行不能产生成功 receipt。
  - `src/application/opend_symbol_chain_fetching.py:197-214` 用 `except Exception: expirations_all = []` 吞掉 expiration discovery 的所有失败。
  - `src/application/option_chain_fetching.py:339-341` 把空 expiration targets 自动变为 `[None]`。
  - `src/application/option_chain_fetching.py:403-471` 只记录后续 chain 调用的 error/empty，无法恢复前一步 discovery 是成功空还是异常。
  - Slice A 第 330-343 行没有列出 `src/application/opend_symbol_chain_fetching.py`，测试门也没有包含该 owner 的 discovery failure/empty 分支。
- **影响**: provider/auth/timeout/parse failure 可能错误获得合法零行 quote receipt、completed-zero strategy status 和 normal degraded delivery；报告会向用户声称“获取成功但无合约”，而真实情况是获取失败。
- **建议改法和验证点**:
  - 把 `src/application/opend_symbol_chain_fetching.py` 明确加入 Slice A 的 owning boundary。
  - 为 expiration discovery 保留最小的 typed stage result：至少区分 `success_rows`、`success_empty`、`provider_error`、`parse_error`；不得再用空 list 同时表达成功空和异常。
  - 明确规则：discovery `success_empty` 可以直接形成 symbol `success_empty/no_expirations`，不得再隐式执行 `[None]` chain fallback；discovery failure 直接向上保留 failure outcome。
  - 只有 discovery 有目标时，才逐 expiration 聚合 chain outcomes；任何 expected expiration 未完成或失败均整体 fail-closed。
  - 增加直接 owner 测试：成功空 DataFrame、provider exception、invalid response、DTE 投影后无目标、一个 expiration empty、多个 expiration 全 empty、empty+error、以及 discovery failure 后断言不会调用无 expiration chain。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR-02-未修复-中-Brief 只检查 quote binding 非空，不能确认告警引用的是本 run 已封存的成功空证据

- **位置**: 不变量 §3.4/§3.8；Required-data outputs §5.2；Strategy status §5.3；Daily Brief §5.5；Slice B；验收矩阵 §7
- **问题类型**: 契约缺失 / 最佳实践偏离 / 测试缺口
- **当前写法**: manifest 和 strategy status 都携带 `source_outcome`、reason、snapshot id 与 receipt path；assembler 的交叉检查仅要求 outcome、allowlist reason、candidate count=0、snapshot id/receipt path 非空以及同 scope 无 decision。
- **反例/失败场景**: completed-zero strategy status 写入了同 run 中另一 symbol 的 snapshot id、错误 receipt path，或与 run-scoped required-data manifest 不一致的绑定。现有 status index 会验证 status artifact 本身的身份和 hash，但不会解析或验证它引用的 quote receipt。按计划的“非空”检查，Brief 仍会展示指定 symbol/family 的 `success_empty` 告警，即使该绑定没有证明这个 scope 的成功空结果。
- **为什么有问题**: 告警虽不授予行动 authority，但它是本 work unit 的核心用户可见事实。计划的不变量要求 assembler 只展示“已确认的成功空事实”，非空字符串不构成确认。与此同时，计划已经让 run-scoped manifest 保存同一 snapshot/receipt/outcome，因此无需引入新 schema 或跨到 raw provider payload，只缺少明确的一致性验证。
- **直接证据**:
  - 计划第 87-94 行要求 quote evidence 完整且 renderer 不重新分类。
  - 计划第 192-200 行规定 manifest entry 保存 snapshot/receipt 以及 `source_outcome/reason_code`。
  - 计划第 218-225 行又把这些字段投影到 strategy status。
  - 计划第 254-260 行仅检查 snapshot id 和 receipt path “非空”，没有要求等于 manifest 中该 symbol 的已验证 binding。
  - `src/application/strategy_scan_status.py:83-116` 只 hash strategy artifacts，并原样写入可选 snapshot/receipt 字符串。
  - `src/application/strategy_scan_status.py:155-190` 构建 index 时验证 status 身份与 canonical strategy artifacts，但不验证 quote receipt。
  - `src/application/daily_decision_brief_service.py:2316-2361` 当前只校验 index/run/account/market 与 terminal status，后续新增投影若照计划实现将没有 quote authority 校验。
- **影响**: normal authority 未必被放宽，但 Brief 可产生错误或串 scope 的降级告警；`lx`/`sy`、symbol 或 run 的显示事实可能不可信，且验收用自洽假数据即可通过。
- **建议改法和验证点**:
  - 在 Slice B 明确：assembler 读取并验证当前 account run 的 `state/required_data_snapshot_manifest.json`，要求 strategy status 的 snapshot id、receipt path、`source_outcome` 和 reason 与 manifest 中同 symbol 的 ready entry逐项一致。
  - 复用 `required_data_snapshot.py` 的 manifest/receipt validator；不要让 renderer 读取 raw OpenD payload，也不要新增 candidate source schema。
  - mismatch、manifest 缺失或 receipt validation failure 不得形成 success-empty warning，并继续走既有 source-integrity/failure authority。
  - 增加负向测试：空 binding、错 symbol binding、错 receipt path、snapshot mismatch、reason mismatch、manifest hash/bytes failure；同时验证正确 binding 才产生非行动型 warning。
  - 将 `tests/test_position_advice_candidate_capture_runtime.py` 加入 Slice B focused gate，并新增“completed + zero decisions + valid quote binding => capture complete”的直接用例；现有该文件只证明一条 decision 的 complete 和缺少 status 的 incomplete。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

## Open Questions

- 无。两个 finding 都可在现有严格边界内收敛，不需要引入 provider peer、coverage proof、source v2 或 notification 改造。

## Residual risks and tracking

- `success_empty` 仍只证明该请求时点和请求 scope 的可靠零结果，不证明产品永久不适用、退市或未来仍为空；继续由现有非行动型文案约束，建议在本 work unit 的验收用例中保留。
- Header-only CSV 不满足通用 `required_data_frame_covers_fetch_plan()`，因此非冻结缓存路径可能重新拉取；scheduled frozen path 可依赖当前 run manifest。此行为不阻断本计划，但应在实现 diff review 中确认没有为了缓存复用而放宽 coverage predicate。
- Open-position Close Advice 仍可能独立阻断最终 normal delivery。计划已明确不承诺该场景成功，建议作为既有 Close Advice authority 的回归项，而不是扩展本 work unit。
- 建议跟踪位置：本 plan 的 Slice A/Slice B 验收矩阵；不需要新建独立架构项目。

## Final conclusion

**fail**

严格边界本身合理，也没有明显过度设计；但计划尚未封住 expiration discovery exception 被压成空列表这一条直接反例，因此核心 `success_empty` 仍可能误分类获取失败。修复 PR-01 后，再补齐 PR-02 的 manifest/status evidence binding，计划才达到可安全交给 implementation agent 的程度。
