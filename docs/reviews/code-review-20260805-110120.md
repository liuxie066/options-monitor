### DR5-01-未修复-高-缺失 option contract code 时整账户持仓进入语义指纹

- **入口/函数**: `settlement_observation_semantic()` -> `_relevant_source_rows()` -> `_normalize_position()`
- **文件(行号)**: `src/application/ledger/lifecycle_settlement_semantics.py:65-72,123-145,401-407`; `src/application/trades/settlement_observation.py:486-494,1229-1255`
- **输入场景**: 生命周期 anchor 无法提取 `option_contract_code`，collector 正确把 observation 标记为 `option_contract_code_missing`；同账户随后新增或改变一条与目标期权无关的股票/期权持仓。
- **实际分支**: 语义投影只把 `option_contract_code` 传给 source-row relevance。该值为空时，`fresh_positions` 分支不执行任何过滤，整份账户持仓都进入 `relevant_rows_hash`。collector 的实际判定在 code 缺失时还会用 option type、expiration、strike 做 case-bound fallback，两条路径不一致。
- **预期行为**: source semantic 必须复用同一 case-bound predicate；无关持仓只能留在 audit receipt，不能改变 settlement semantic fingerprint。无法匹配的行应被排除，case 输入缺失本身由 contract identity 与 incomplete reason 表达。
- **实际行为**: 无关账户活动会生成新 fingerprint，绕过 latest-semantic admission，并按每次“新语义”重置 no-progress cadence；这重新打开持续 evidence/revision/outbox 放大的核心故障链。
- **直接证据**: `_relevant_source_rows()` 在 `option_contract_code` 为空时保留每一条 normalized position。只给同一 incomplete observation 增加 `{"code":"US.AAPL","qty":10}`，当前代码计算出的 fingerprint 已发生变化；而 `settlement_observation.py` 的决策 predicate 明确还有 type/expiration/strike fallback。
- **影响**: 正好在 case 数据不完整、最需要 fail-closed 去重的场景，账户持仓噪声会被误认为业务状态变化，无法保证 canonical writer 吸收重复 observation。
- **建议改法和验证点**: 让语义 normalizer 接收完整 contract identity，并用 canonical code 优先、type/expiration/strike fallback 的同一 predicate 过滤 `fresh_positions`；新增 code 缺失 + 无关 position 不变、匹配 position 改变的双向测试。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### DR5-02-未修复-高-无 typed metadata 的 query 失败被当成 observed business fact

- **入口/函数**: `_query_receipt()` -> `build_settlement_source_receipt()` -> `classify_observation_outcome()`
- **文件(行号)**: `src/application/trades/settlement_observation.py:708-780`; `src/application/trades/settlement_attempts.py:182-277`; `src/application/trades/close_reason_evidence.py:157-207`
- **输入场景**: gateway 返回结构合法的 receipt dict，但 `retcode` 非成功或带 `error`，同时旧 adapter/测试 double 没有提供 `error_class` 和 `provider_code`。
- **实际分支**: `_query_receipt()` 原样保留空 typed metadata。`classify_observation_outcome()` 只把同时带 `error_class/provider_code` 的 incomplete receipt 认作 failure；其余直接落到 `observed_incomplete`，携带 observation 进入 canonical writer。
- **预期行为**: transport/query failure 必须是 `retryable_error` 或 `unknown_error`，不产生 business evidence；缺少可信 provider classification 时至少应保守归一为 `unknown_error`，不能靠 raw error text决定永久状态。
- **实际行为**: query failure masquerades as an observed business state，首次失败会写 settlement evidence，并参与 resolution/revision/outbox；与计划 invariant 126 直接相反。
- **直接证据**: 对 `{"status":"incomplete","retcode":-1,"error":"query failed"}` 且 typed fields 为空的 receipt，当前 `classify_observation_outcome()` 返回 `observed_incomplete`。生产 Futu wrapper通常抛 typed exception，但 contract 接受 receipt dict，版本偏差和 adapter 回归仍会进入该分支。
- **影响**: provider failure 可污染 canonical ledger，并把 transport 波动转成业务状态变化；这既破坏证据语义，也可能重新放大通知/修订和历史读取成本。
- **建议改法和验证点**: 在 receipt ownership 处基于非成功 retcode或非空 error补 `error_class=unknown`，保留 raw text仅作诊断；覆盖 retcode/error 无 typed metadata、coverage-only incomplete、malformed response 与已有 typed code，证明只有真正 observation 进入 writer。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### DR5-03-未修复-高-post-write claim 生命周期和 terminal control failure 未闭环

- **入口/函数**: `reconcile_due_lifecycle_cases_for_source()` -> `_SettlementClaimLeaseGuard.stop()` -> compact post-write read -> `complete_settlement_attempt()` / `settlement_attempt_summary()`
- **文件(行号)**: `src/application/trades/lifecycle_runtime.py:1085-1207,1230-1241`; `src/application/trades/inbox.py:571-659`
- **输入场景**: canonical ledger transaction 已提交后，compact candidate read或 control DB等待使 completion 延迟到 lease 过期；另一个 worker取得 claim。或者最后的 status summary 遇到独立 control-table `OperationalError`。
- **实际分支**: lease guard在 canonical reconciliation 返回后立即停止，post-write candidate refresh和 control completion不再续租。stale owner completion抛普通 `ValueError`，但 control wrapper只接住 `sqlite3.OperationalError`，因此 listener记录一个未分类 due error而不是 `claim_ownership_lost`。最终 `settlement_attempt_summary()` 甚至完全绕过 wrapper。
- **预期行为**: active attempt 的 claim 应覆盖 ledger result到 control completion的整个状态机；若 ownership仍在最后窗口丢失，应返回 typed `claim_ownership_lost`，绝不能由普通异常逃逸。非关键 summary失败也应走同一 fail-closed control status。
- **实际行为**: 旧 worker可能在仍处理 post-write bookkeeping 时被第二 worker合法抢占，后者再做一次 provider call；旧 worker无法写回 bounded outcome，且调用方只看到 generic error。summary故障会让已经完成的 tick整轮报错。
- **直接证据**: runtime 在 `finally` 中先 `stop()` guard，之后才执行 `list_trade_lifecycle_due_candidates()` 和 completion；inbox定义了 `SettlementAttemptClaimOwnershipLost`，但 completion 两处 ownership mismatch都抛 `ValueError`；wrapper的 except 类型只有 `sqlite3.OperationalError`；summary直接调用。
- **影响**: claim 独占和 typed status 在最关键的 crash-after-commit窗口仍不完整，慢库/锁竞争时会制造额外 provider I/O和不可解释的 listener error，削弱本迭代的止血保证。
- **建议改法和验证点**: 让 guard持续覆盖 post-write compact refresh，完成前做最后一次 renew；completion ownership mismatch统一抛 typed exception并由 control wrapper映射；summary也通过 wrapper。新增“writer已提交后 claim 被偷”和 summary OperationalError测试，证明 canonical business state不重复、runtime返回 typed status且不抛出。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### DR5-04-未修复-中-2,100-row 验收测试没有覆盖计划要求的双 case 和 business no-op

- **入口/函数**: `test_blocked_ticks_do_not_rematerialize_large_account_evidence()`
- **文件(行号)**: `tests/test_settlement_observation.py:1658-1757`; `docs/plans/trade-intake-settlement-collector-resilience-plan-20260805.md:332-339`
- **输入场景**: 同一账户有两个 provider-required case，历史存在大量重复 settlement observations，首次分类后连续十个 blocked ticks。
- **实际分支**: 当前测试只有一个 case，插入的是 2,100 条 `legacy_diagnostic` 而非等价 settlement observations；只断言一次 account read、无 latest settlement evidence和 notifications不变，没有快照对比两 case 的 resolution revision、allocations、全量 settlement evidence/outbox，也没有证明 multi-case classification只 materialize一次账户。
- **预期行为**: 按 required test 334，两个 provider case在同一 inflated account snapshot内一次完成初始分类，后续十 tick的 provider、semantic write、revision、allocation、outbox和 account-wide reads都严格为零。
- **实际行为**: 单 case测试可以在 multi-case routing重复 materialize或只保护第一个 case时仍然通过；也无法捕获 blocked path误改 revision/allocation的回归。
- **直接证据**: fixture唯一 `case_id`来自 `_repo_with_pending_case()`，所有 2,100 rows绑定该 case且 `source_type=legacy_diagnostic`；断言集中在一个 `account_reads`计数和一个 case的 notification/latest-evidence。
- **影响**: 核心资源验收尚未建立，当前 4,452-test green不能证明用户要求的同账户多 case止血边界。
- **建议改法和验证点**: 构造同账户两个独立 pending case，为二者合计至少 2,100 条等价 legacy settlement observations；在首次 tick前后和十个 blocked ticks后快照 evidence、revision、allocations、outbox与 provider/account-read counters，逐项断言。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 中
