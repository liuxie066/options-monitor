### DR-S1-RR-01-未修复-高-合法的 empty child 会被执行为未限定 provider 请求，且错误 child 行仍可通过聚合 authority 校验

- **入口/函数**: `_fetch_one_inprocess()` ->
  `fetch_symbol_request()` -> `fetch_symbol_option_chain()` ->
  `bind_required_data_child_request_evidence()` ->
  `_validate_expected_child_request_evidence()` ->
  `required_data_frame_covers_fetch_plan_debug()`
- **文件(行号)**:
  `tests/test_required_data_expected_contract_integrity.py:76-120`;
  `src/application/multi_tick/required_data_prefetch.py:773-828`;
  `src/application/opend_symbol_fetching.py:321-325,360-372`;
  `src/application/opend_symbol_chain_fetching.py:352-378`;
  `src/application/required_data_fetching.py:225-271`;
  `src/application/opend_symbol_outputs.py:461-560`;
  `src/application/required_data_coverage.py:310-345`
- **输入场景**: 一个已被 expected-contract 测试声明为合法的 mixed plan：put child
  的 `explicit_expirations=[]`，call child 请求 `2026-09-18`。provider 对空 put child
  实际返回 `2026-08-21` put rows，对 active call child 返回正确 rows；两个 child
  都带自洽 provider snapshot completeness metadata。
- **实际分支**: in-process coordinator 对每个 spec 都调用 provider。空列表先被规范化为
  `[]`，随后 `fetch_symbol_option_chain()` 以 truthiness 判断，将其解释成“没有显式限制”，
  重新发现并抓取到期日，而不是 exact empty request。coordinator 只把 planned request hash、
  index、symbol、underlier 绑定到已返回 payload；receipt validator 只核这些身份、通用 raw
  binding、status/outcome/timestamp，不证明 child 的实际 code/rows 满足该 planned request。
  聚合 coverage 又明确跳过空 child 的 row-level demand。
- **预期行为**: planning evidence 中可以保留某 side 的 empty projection，但不能把 empty
  executable request 传给把空值解释成 unspecified 的 provider API。每个 active child 的
  实际 code set 和 aggregate rows 必须独立证明满足该 child 的 option type、expiration、
  strike window，之后才可合并并获得 receipt/seal authority。
- **实际行为**: 离线反例得到：empty child 计划到期日 `[]`，实际 child rows 到期日
  `['2026-08-21']`，`validate_required_data_payload_candidate=True`、
  `required_data_frame_covers_fetch_plan_debug=True`、aggregate status=`ok`。因此错误 child
  响应已通过 receipt 前全部 child/aggregate 语义守卫；raw/CSV exact bytes 校验只会忠实
  固化同一批错误 rows，不能补回 child-request 对应关系。
- **直接证据**: `opend_symbol_chain_fetching.py:352-355` 把空 explicit list 送入 expiration
  discovery；`required_data_fetching.py:258-267` 添加的 child evidence 不含实际请求/返回
  row 语义；`opend_symbol_outputs.py:502-559` 不检查 child code set 对 planned side/expiry/
  window；`required_data_coverage.py:329-333` 对 empty child 直接 `continue`。反例使用真实
  binding、merge、candidate validator 和 debug coverage owner，无文件或外部写入。
- **影响**: 多账户会共享一份其 child provenance 与实际 provider rows 不对应的“完整”
  数据；swapped/wrong child rows 可被签成 durable receipt/seal，且空 child 还会产生计划外
  provider 调用和数据。
- **建议改法和验证点**: 两层同时修复。第一层，planner/execution 只生成 non-empty
  executable `merged_requests`；empty top-side projection仅作为 planning evidence 保留，
  其 `include_realized_volatility` demand 必须 OR 传播到 active spec，contract 明确拒绝
  empty executable request。第二层，durable validator 对每个 active child 要求
  `requested_code_set` 非空、requested==returned、missing/unexpected 均空；用该 code set
  从 aggregate rows 精确投影并要求 code set 全等，再逐行验证 option type、expiration
  属于该 child、strike 落在该 side window。跨 child overlap 若允许，只能是同 code 的
  canonical row 完全一致，且每个 child 都独立通过。新增 real mixed active/empty 测试，
  断言只有一次 provider 调用、RV demand 保留、一次 finalize/receipt；empty child 带 rows、
  swapped active child、wrong side/expiry/window、code-set 漂移均须零 receipt。
- **修复风险**: 高
- **严重程度**: 高

### DR-S1-RR-02-未修复-高-单侧无界策略与 exact position 的合法 plan 会被自身 contract validator 拒绝

- **入口/函数**: `build_required_data_fetch_plan()` ->
  `_merge_same_side_plans()` ->
  `build_required_data_expected_fetch_contract()` ->
  `_validate_required_exact_strikes()`
- **文件(行号)**: `src/application/required_data_planning.py:601-674`;
  `src/application/required_data_plan_identity.py:760-797`;
  `tests/test_required_data_fetch_planning.py:975-1014,1017-1054`
- **输入场景**: spot 不可用，call strategy 只配置 `max_strike=100`，同时存在
  `2026-08-21 call 120` active position；对称场景是 put strategy 只配置
  `min_strike=100`，同时存在 `2026-08-21 put 80` position。
- **实际分支**: planner 按 union 语义正确生成 call window
  `(min=None,max=120)` / put window `(min=80,max=None)`，并保留 expiry-local exact strike。
  contract validator 在 exact map 非空时无条件要求 `min_strike` 和 `max_strike` 同时存在，
  因此在任何 provider/cache 读取之前抛出
  `ValueError: required-data expected exact strikes are invalid`。
- **预期行为**: one-sided unbounded 是合法 fetch window；exact strike 只需分别满足存在的
  lower/upper bound。缺失的一侧表示无界，不表示 contract invalid。
- **实际行为**: 两个对称离线复现分别输出
  `call None 120.0 {'2026-08-21': [120.0]}` 和
  `put 80.0 None {'2026-08-21': [80.0]}`，随后均被 expected-contract builder 拒绝。
  现有 planning tests 只断言 plan，没有把这两个合法 plan 继续送入 contract/coverage。
- **直接证据**: planner 在 `required_data_planning.py:628-640` 遇任一 child 无界时保留
  `None`，并在 `:645-674` 保留 exact map；validator 在
  `required_data_plan_identity.py:784-795` 将 `min_strike is None or max_strike is None`
  直接归为 invalid。两者的公开语义相互矛盾。
- **影响**: 在 quote right/spot 不可用或用户只提供单侧策略边界时，active Close Advice
  持仓的 exact quote demand 无法进入 fetch，导致 required-data/候选与平仓建议链路
  fail closed、无数据。
- **建议改法和验证点**: exact strike validator 只对存在的 bound 分别校验：lower 存在则
  `strike >= lower`，upper 存在则 `strike <= upper`；仍拒绝非正、非有限、bool、无序、
  重复和真正越界。新增 call max-only 与 put min-only 两条 full
  plan -> contract -> provider/cached coverage 回归，并保留双界与完全无界正反例。
- **修复风险**: 低
- **严重程度**: 高

### DR-S1-RR-03-未修复-中-Expiration discovery 与 DTE filter/执行层使用不同交易日时钟

- **入口/函数**: `build_required_data_fetch_plan()` ->
  `_filter_expirations_by_dte()` ->
  `build_required_data_expected_fetch_contract()`；执行侧
  `fetch_symbol_request()` -> `fetch_symbol_option_chain()`
- **文件(行号)**: `src/application/required_data_planning.py:240-262,932-983`;
  `src/application/required_data_plan_identity.py:400-421,570-592`;
  `src/application/opend_symbol_fetching.py:360-369`
- **输入场景**: expiration discovery 在 immutable evidence 中记录
  `trading_date=2026-07-27`，返回 `2026-08-07`；在 strategy DTE filter 执行前当前交易日
  翻到 `2026-07-28`，strategy 要求恰好 10 DTE。
- **实际分支**: planner 保存 discovery identity，却由 `_filter_expirations_by_dte()` 再次
  调用 `get_trading_date()`；因此按 7 月 28 日算 10 DTE 并纳入 expiry。contract validator
  以 discovery 的 7 月 27 日重算为 11 DTE，立即拒绝自己刚生成的 plan。若边界未触发
  contract 拒绝，provider execution 又在 `fetch_symbol_request()` 重读一次当前交易日，
  row DTE 仍可能与签名 anchor 不同。
- **预期行为**: 一次 bundle 的 discovery `request_identity.trading_date` 是唯一、不可变的
  DTE authority；strategy filter、position DTE、request contract、provider row DTE、
  coverage 都必须使用同一 anchor。
- **实际行为**: 离线日期翻转反例生成
  `planned ['2026-08-07'] min_dte=10 max_dte=10`，随后得到
  `ValueError: required-data expected side plan DTE range does not cover explicit expirations`。
- **直接证据**: `required_data_planning.py:246` 独立读取当前交易日，调用点
  `:965-983` 没有传 discovery anchor；contract 在
  `required_data_plan_identity.py:413-421,584-592` 按 contract trading date 重算；执行在
  `opend_symbol_fetching.py:360-369` 再取当前日。三个阶段没有共享 immutable 日期参数。
- **影响**: 市场日/午夜边界附近会出现确定性的 plan-self-rejection 或 row-DTE mismatch，
  中断该轮所有共享账户的 required-data completion；重试时结果还可能因时钟变化而不同。
- **建议改法和验证点**: discovery 完成后提取并严格验证一个 bundle trading-date anchor，
  显式传给所有 strategy/yield filter、position plan、fetch request 和 provider row-DTE
  计算；禁止这些路径再次隐式读当前交易日。增加 discovery 后时钟翻转的离线回归，证明
  plan、contract、provider rows、typed/debug coverage 均使用同一天；缓存 discovery re-entry
  也必须保留原 anchor。
- **修复风险**: 中
- **严重程度**: 中
