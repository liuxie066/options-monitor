## Adversarial failure pass

- **Entry/feature gate**: `multi_account_tick.main()` is the sole production constructor and passes scheduler market/decision plus authoritative pipeline completion. `notifications.daily_brief.enabled is True` is required; false/missing configuration uses the unchanged legacy preparation path.
- **Normal single-market send**: assembler -> immutable revision/diff -> renderer -> existing route/quiet/decision -> existing retry sender -> provider confirmation -> exact transport-key verification -> repository pointer confirmation -> scheduler notified state.
- **No material**: renderer is not invoked for outbound, no route/credential is resolved, and the run finalizes as no account notification.
- **No-send / quiet hours**: the canonical revision is persisted for audit, provider execution is skipped, and no delivery pointer advances.
- **Provider failure**: `execution.sent_accounts` excludes the account; pointer confirmation is not attempted; existing account-isolated failure handling remains active.
- **Provider success / local pointer failure**: account is removed from final sent accounts, failure code is `DAILY_BRIEF_CONFIRM_FAILED`, ambiguity/duplicate-risk metrics are incremented, and scheduler notified state does not advance for that account.
- **Retry/crash identity**: the logical S2 key remains content/diff stable; the notification boundary hashes it into the existing compact `om-<32hex>` provider form, and all outer retries reuse it.
- **Multi-market**: US/HK immutable artifacts are persisted independently, outbound is suppressed, route selection is skipped and neither market pointer advances.
- **Per-account isolation**: lifecycle, message and key dictionaries are keyed by normalized account; one account confirmation failure does not advance or suppress another account.
- **Renderer bounds**: per-section limits, a total item budget and the 12,000-character cap bound external messages while retaining the full structured local artifact.
- **Architecture/ownership**: ranking and material-diff policy remain in domain/S2 services; S3 only renders and integrates existing notification/persistence boundaries. No scheduler, queue, DB, alternate sender or production config was added.
