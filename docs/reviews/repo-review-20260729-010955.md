## Findings

### 1-未修复-高-通用账本写入会提交带 error diagnostic 的事件与部分投影

- **入口/函数**: `persist_trade_event()` / common event persistence → `project_events()` → `replace_position_lots()`
- **文件(行号)**: `src/application/ledger/writer.py:104-157,917-1007`; `src/application/ledger/preflight.py:429-561`
- **输入场景**: 两个并发或顺序 lifecycle/close 事件都以同一 open lot 为目标；第二个事件进入事务时目标 lot 已关闭。
- **实际分支**: preflight 在事务外检查；事务内插入事件、重放投影并替换 lots，但不以 `projection.has_errors` 阻断提交。
- **预期行为**: 在同一个 `BEGIN IMMEDIATE` 内基于最新状态重新验证；任何 error diagnostic 都应回滚事件和投影。
- **实际行为**: 第二个事件即使得到 `target_lot_already_closed`，仍成为 canonical `trade_events`，调用结果仍可标记 created。
- **直接证据**: failure reproduction 证明第二个 one-contract `expire_close` 返回 error diagnostic 后仍能从 repository 读到；writer 的 common path 没有 lifecycle atomic writer 所具备的 error gate。
- **影响**: 权威事件流包含业务上被拒绝的事实；后续 rebuild、performance、audit 会继续消费该事件，且 preflight 的 TOCTOU 使并发时更容易触发。
- **建议改法和验证点**: 把最终合法性检查移入写事务；`projection.has_errors` 时抛错并回滚。新增 same-lot 双 close、并发 close、失效 target 与事务回滚测试。
- **修复风险（低/中/高）**: 高
- **严重程度（低/中/高/严重）**: 高

### 2-未修复-高-publisher 会重新应用已 void 或领域投影拒绝的策略调整

- **入口/函数**: `publish_projection()` → `_apply_adjust_strategy_patch_fields()`
- **文件(行号)**: `domain/domain/ledger/projection.py:87-110,130-132,377-422`; `src/application/ledger/publisher.py:45-65,69-84,234-263`
- **输入场景**: 对 open lot 写入 strategy/leg role adjust，随后 void 该 adjust；或 adjust 本身被领域投影拒绝。
- **实际分支**: 领域投影正确排除 void/rejected adjust；publisher 随后又遍历完整原始 adjust 事件流，按 target 重写策略字段，不检查事件是否仍 active/applied。
- **预期行为**: 发布结果只能来自领域投影已确认有效的事件集合。
- **实际行为**: 被 void 的 `strategy`、`leg_role` patch 重新出现在发布的 position lot 中。
- **直接证据**: 直接复现显示 void 后领域结果不含 patch，而 publisher 的 raw replay 又将其写回；现有测试只覆盖 core field void，没有覆盖策略字段。
- **影响**: read model 与 canonical event semantics 分裂，Position Advice、组合归属和绩效分组会读取已撤销的策略事实。
- **建议改法和验证点**: 将策略 patch 纳入领域投影的单一输出，或显式使用投影确认的 active adjust set；增加 adjust→void、invalid adjust、rebuild/publish 一致性测试。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### 3-未修复-高-rebuild/startup 在投影有错误时仍删除并发布部分 lots，CLI 报告成功

- **入口/函数**: `rebuild_projection()` / startup bootstrap / `option-positions rebuild`
- **文件(行号)**: `src/application/ledger/writer.py:84-101`; `src/application/ledger/repository.py:496-530`; `src/application/ledger/bootstrap.py:279-285`; `src/interfaces/cli/option_positions.py:840-872`
- **输入场景**: canonical event stream 含 malformed、dangling 或冲突事件，重建得到 error diagnostics。
- **实际分支**: repository 先删除全部 `position_lots`，writer 无条件写入部分投影；bootstrap 不阻断；CLI 固定输出 `[DONE]`、`write_applied=True` 并 exit 0。
- **预期行为**: error diagnostic 时保留上一份可用投影并失败退出；受控强制重建必须显式授权且可恢复。
- **实际行为**: 一个诊断/恢复命令能以成功状态替换权威 read model 为不完整结果。
- **直接证据**: `replace_position_lots()` 是 delete-all/insert；rebuild path 没有 `has_errors` gate，CLI 也没有按 diagnostics 调整退出状态。
- **影响**: 服务启动或人工修复可静默丢失开放持仓，随后风险、Close Advice、Position Advice 和报告全部建立在部分视图上。
- **建议改法和验证点**: 先在内存或 staging table 验证零 error，再原子 swap；CLI 对 error 非零退出。测试 malformed stream 下旧投影不变、bootstrap fail closed、override 带备份和明确 receipt。
- **修复风险（低/中/高）**: 高
- **严重程度（低/中/高/严重）**: 高

### 4-未修复-高-投影验证 checkpoint 未绑定投影实现版本，部署后可复用旧绿灯

- **入口/函数**: `verify_projection()` → `_build_checkpoint()` / checkpoint fast path
- **文件(行号)**: `src/application/ledger/projection_verify.py:175-187,198-246`
- **输入场景**: event/position 数据未变化，但新版本修改了 projection、codec、normalization 或 invariant 逻辑。
- **实际分支**: checkpoint 只记录 schema 和 event/position fingerprints；命中相同数据指纹便跳过 replay。
- **预期行为**: 任何可能改变投影语义的代码/contract 版本都应使旧 checkpoint 失效。
- **实际行为**: 新部署可继续返回旧版本生成的 green checkpoint，直到数据发生变化。
- **直接证据**: `_build_checkpoint()` 没有 projector/code version；reuse 条件只比较 event 与 position fingerprints。
- **影响**: 发布后的投影回归无法被 readiness/verify 及时发现，生产仍被标记 healthy。
- **建议改法和验证点**: 引入稳定 `projection_contract_version` 或实现哈希并纳入 checkpoint；版本变化强制 full replay。测试同数据、不同 projector version 不复用。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### 5-未修复-高-canonical event 校验弱于 position-lot 合同，合法入流的 malformed open 可使发布/验证崩溃

- **入口/函数**: event identity/codec validation → projection → position field serialization
- **文件(行号)**: `domain/domain/ledger/identity.py:18-22,35-69`; `domain/domain/ledger/events.py:53-66,104-155`; `src/application/ledger/event_codec.py:28-43,120-164`; `domain/domain/ledger/position_fields.py:101-117,427-500`; `src/application/ledger/publisher.py:87-124`; `src/application/ledger/projection_verify.py:240-246`
- **输入场景**: open event 带零/负/NaN price、multiplier、strike，非法时间/币种/source，或其它 downstream lot contract 不接受的值。
- **实际分支**: encoder/domain event 接受；projection 形成 lot；publisher/verify 在更严格的 position serialization 中抛异常或产生不合法 lot。
- **预期行为**: canonical event 写入边界至少应满足所有下游持仓投影不变量。
- **实际行为**: “可写事件”与“可发布持仓”不是闭合合同。
- **直接证据**: event validator 只覆盖有限 identity/type 字段，而 `position_fields` 后置要求更严格；异常没有在 canonical insert 前被统一拦截。
- **影响**: 单条坏事件可阻断 rebuild/verify/publish，并叠加 Finding 3 造成部分投影替换。
- **建议改法和验证点**: 定义 open/close/adjust 各事件的完整输入 contract，在写前做 finite/positive/enum/time validation；用 property tests 验证所有 accepted events 均可 codec round-trip、project、publish。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### 6-未修复-中-phantom/self/void-to-void target 可通过验证并被健康地静默 no-op

- **入口/函数**: void/adjust event validation → `project_events()` → verify

- **输入场景**: void 指向不存在 event、指向自身，或 void 另一条 void；adjust 指向不适用 target。
- **实际分支**: 只验证 target 字符串存在；projection 将其变成 no-op，verify 可仍返回健康。

- **实际行为**: 审计流记录了看似成功但没有任何业务效果的修复事实。

### 8-未修复-高-auto-expire 先提交终结事件再单独更新 case，失败后无法自愈

- **入口/函数**: lifecycle maintenance auto-expire persistence
- **文件(行号)**: `src/application/ledger/maintenance.py:785-823,899-907`; `src/application/ledger/writer.py:285-424`
- **输入场景**: 自动过期关闭事件和 lot 已提交后，case status/allocation upsert 失败或进程崩溃。

- **严重程度（低/中/高/严重）**: 高
