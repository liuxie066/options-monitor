### DR-01-未修复-高-healthcheck 在 quote 失败时仍把 legacy aggregate 和 summary 判为成功

- **入口/函数**: `healthcheck` -> `run_healthcheck_tool()` -> typed quote probe -> legacy `opend_readiness`/`summary`
- **文件(行号)**: `src/application/agent_tools/healthcheck_impl.py:624-675, 752-777, 798-830`; `tests/test_agent_plugin_smoke.py:267-289`
- **输入场景**: account broker endpoint/identity readiness 成功，但 canonical quote endpoint 登录失败、不可达或 route conflict。
- **实际分支**: legacy per-endpoint 和 aggregate checks 在 quote probe 之前仅由 broker readiness 构造；后续 quote failure 只生成 `summary_excluded=True` 的 typed child，summary 过滤该 error。新增测试明确固化 `critical_count == 0`。
- **预期行为**: account primary 只依赖 broker readiness，但既有 `opend_readiness_<endpoint>`、`opend_readiness` 和 `summary` 必须是当前 scope 所需 quote/broker typed results 的 conjunction，避免旧消费者把整体健康误判为成功。
- **实际行为**: `opend_quote_readiness` 为 `error` 时，`opend_readiness` 仍可为 `ok`，`summary.ok` 仍为 true、`critical_count` 为 0；仅查看既有 aggregate/summary 的监控无法发现 quote plane 已失效。
- **直接证据**: lines 624-675 在 quote probe 之前完成 legacy aggregate；lines 752-777 将 quote check 标为 `summary_excluded`；lines 798-830 排除所有此类 error；测试 lines 267-289 断言这一错误投影为预期。计划 §8.5 明确要求 legacy aggregate 为所有 required typed capability 的 conjunction，同时 typed child 只是不重复计数。
- **影响**: 生产健康与告警产生 false green；行情不可用时旧监控、升级验证和 operator 可能继续放行，且 public compatibility contract 与实现相反。
- **建议改法和验证点**: 先建立同一份 typed quote/broker evidence inventory，再从它投影 per-endpoint legacy checks、account aggregate 和 summary；typed children 可 `summary_excluded`，但对应 legacy parent 必须失败。补测试：quote-only failure => account primary broker 仍 ok、legacy aggregate/summary error 且只计一次；同物理 endpoint 双角色也只计一次。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### DR-02-未修复-高-settlement 仍把 quote 当硬依赖且丢失已验证的交易环境

- **入口/函数**: source-loop periodic reconciliation / `lifecycle reconcile-due` -> `reconcile_due_lifecycle_cases_for_source()` -> `build_settlement_observation_collector()` -> `collect_broker_settlement_observation()`
- **文件(行号)**: `src/application/trades/lifecycle_runtime.py:157-187`; `src/application/trades/settlement_observation.py:27-45, 204-218, 229-295, 534-568`; `src/interfaces/cli/option_positions.py:1626-1667`
- **输入场景**: (a) listener 的 canonical quote route 缺失/冲突，因此 `quote_gateway=None`，但 broker gateway 可用；或 (b) explicit reconcile 的 validated broker binding 使用非 `REAL` 环境。
- **实际分支**: collector 在任何 broker query 之前要求 broker/quote 两者都非空并抛 `SettlementObservationDataError`；positions 和 cash-flow query/input 又把 `trd_env` 固定写成 `REAL`，调用链没有接收 binding 的 `trd_env`。
- **预期行为**: quote 缺失只产生现有 receipt shape 的 incomplete calendar receipt，broker deals/orders/positions/cash receipts 仍应被采集；所有 broker queries 使用 resolver 已验证并由 caller 传入的 environment。
- **实际行为**: quote route 静态失败会把整个 case 归为 `settlement_observation_data_invalid`，不产生任何 broker observation；SIMULATE binding 虽能通过 CLI broker readiness preflight，随后却查询 REAL 账户事实。
- **直接证据**: settlement lines 40-45 是 query 前硬失败；lines 207-215、241-249 固定 `REAL`；calendar query 直到 lines 281-295 才发生；collector lines 534-568 没有 `quote_dependency_error` 或 `trd_env` 参数；lifecycle runtime 也未从 source 传 environment。计划 §8.4 明确要求 incomplete calendar receipt 和 validated `trd_env` 贯穿。
- **影响**: quote plane 故障扩大为 account-evidence 全失，due cases 无法按既有 settlement facts 收敛；非 REAL 的合法 broker binding 会查询错误环境，造成错误空结果或 provider failure。
- **建议改法和验证点**: 允许 `quote_gateway=None` 并在 calendar query owner 内构造 typed incomplete receipt；为 collector/runtime 显式增加并验证 `trd_env`，所有 broker query/input 共用该值。补 deterministic tests：quote missing 时 broker receipts 仍执行且 calendar incomplete；SIMULATE preflight 后所有 broker methods 收到 SIMULATE；case-local ID dispatch 保持不变。
- **修复风险（低/中/高）**: 高
- **严重程度（低/中/高/严重）**: 高

### DR-03-未修复-高-tick 的 quote watchdog 仍要求 trade login，核心 capability availability boundary 没有生效

- **入口/函数**: unified tick -> `run_multi_tick_watchdog()` -> `run_opend_watchdog()` -> `run_watchdog_check()`
- **文件(行号)**: `src/application/multi_tick_watchdog.py:31-104`; `src/infrastructure/external_services.py:147-173`; `src/infrastructure/opend_watchdog.py:225-296`; `src/application/futu_doctor.py:169-212`
- **输入场景**: tick 所需 Futu quote endpoint 已 READY 且 `qot_logined=true`，但该 endpoint 没有 trade login 或 `trd_logined=false`（合法的 quote-only plane）。
- **实际分支**: tick 调用没有传 capability；watchdog 仍用 OpenQuoteContext 读取 global state，并在 `ready and qot and trd` 时才成功。doctor 同样没有 `required_capability` 参数且总是复用 coupled watchdog。
- **预期行为**: tick 对 fetch route 请求 `required_capability="quote"`，只验证 READY + quote login；broker login 不得阻塞 generic market-data flow。compatibility callers 才保留 `both` 默认。
- **实际行为**: quote plane 的 trade logout 被分类为 `OPEND_TRD_NOT_LOGINED`，tick watchdog 失败并进入既有 OpenD failure/alert path，即使所有 quote calls 都可成功。
- **直接证据**: watchdog lines 271-284 同时读取并 conjunction `qot`/`trd`；tick call site没有 capability 参数；doctor signature/call lines 169-184 也没有 capability。计划 §7.3 和 §8.1 明确列出这些迁移点，但本 diff 未修改对应实现或 tests。
- **影响**: “quote failure cannot be caused by broker capability”这一 work unit 的主可用性目标未完成；部署 quote-only OpenD 或 broker session 暂时掉线仍会阻断行情 tick，并可能触发错误运维告警/恢复动作。
- **建议改法和验证点**: 给 watchdog/doctor 增加 `required_capability`，保持 `both` compatibility default；tick 明确传 `quote`，broker health 传 expected-ID set/environment。测试 quote mode 忽略 trade logout、broker mode 忽略 quote logout、both 保持旧行为，并验证 tick 的真实 composition root 传参。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### DR-04-未修复-高-broker readiness 把缺失的 READY/login 事实默认成成功

- **入口/函数**: any broker-ready builder -> `FutuGateway.ensure_broker_ready()`
- **文件(行号)**: `src/infrastructure/futu_gateway.py:382-433`; `tests/test_futu_gateway_minimal.py:253-350`
- **输入场景**: OpenD/version-skew/test adapter 返回成功的 `get_global_state()` dict，但缺少 `program_status_type` 或 `trd_logined`；`get_acc_list()` 仍包含 expected ID。
- **实际分支**: missing/empty status 被列入允许值，missing `trd_logined` 通过 `state.get(..., True)` 被当成 true；identity subset 随后通过，builder 返回 ready。
- **预期行为**: broker readiness 必须观察到明确的 `program_status_type == READY` 和 `trd_logined is True`，缺失或畸形字段应 fail closed。
- **实际行为**: readiness payload 可返回 `program_status_type=None`、`trd_logined=True` 并放行 balance/position/history/account queries。
- **直接证据**: lines 401-404 接受 `(None, "", "READY")` 并为 login 提供 true default；lines 425-426 又把缺失 login 序列化成 true。新增 tests 只覆盖完整 READY/true、ID/environment mismatch，没有 missing-field adversarial case。
- **影响**: malformed/version-skew protocol response 会伪造 broker readiness，削弱所有新 broker builder、health 和 explicit reconcile preflight 的 fail-closed 保证。
- **建议改法和验证点**: 使用严格相等/身份检查，不对 readiness fields 提供成功默认；对 missing、null、empty、wrong-type status/login 均测试失败，并保留 account ID masking。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### DR-06-未修复-高-detail enrichment 的 readiness 异常越过原有 failure containment，完整 trade payload 也会进入 inbox retry

- **入口/函数**: push/inbox retry/backfill -> `_process_payload()` -> `process_trade_payload()` -> `enrich_trade_push_payload_with_account_id()`
- **文件(行号)**: `src/application/trades/auto_intake.py:145-187`; `src/application/trades/intake.py:488-518`; `src/application/trades/futu_detail_lookup.py:192-237, 246-349`
- **输入场景**: payload 已含可用的 `futu_account_id` 和足够 normalizer 消费的字段，同时含 order/deal ID；OpenD readiness 临时失败或 configured candidate union 中一个 ID 暂时不可见。
- **实际分支**: enrichment 在 method-level `try/finally` 之前调用 ready builder；builder exception 直接越过原本 `_query_rows()` 的 error-to-diagnostics containment，也发生在 `process_trade_payload()` 的 normalize exception boundary之前。
- **预期行为**: broker readiness 必须先于实际 lookup，但 enrichment failure 仍保持既有 fail-closed contract：返回原 payload + query/readiness diagnostics，让 authoritative normalizer/resolver 判断 payload 是否已足够；只有真正缺失身份/事实时才按现有 intake 语义失败。
- **实际行为**: transient readiness exception 直接冒泡到 `_process_inbox_payload()`，payload 被标为 retryable；即使外部 lookup 只是辅助 enrichment，已完整 trade event 也不进入 normalize/resolve。
- **直接证据**: detail lookup lines 230-236 在 `try` 外构造 ready gateway；后续只有 individual query calls 经 `_query_rows()` 转成 diagnostics；intake lines 499-518 在 normalize `try` 之前直接调用 enrichment。新增 detail tests 全部 monkeypatch builder 成成功 gateway，没有 readiness-failure regression。
- **影响**: broker/OpenD 短暂抖动扩大为 durable trade-intake delay，可能造成 push、retry 和 backfill backlog；这是本 work unit 声称不改变 listener/inbox/retry availability boundary 的回归。
- **建议改法和验证点**: 在 enrichment owner 内捕获/分类 readiness failure，关闭已构造资源并返回 fallback payload + typed diagnostic；或仅在 payload 真的缺少 lookup-owned事实时调用 builder。补完整 payload + readiness failure 仍进入 normalize/resolve、缺失身份 payload 仍 fail closed、gateway close/ID masking tests。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高
