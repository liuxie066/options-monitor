# Plan Review

## Reviewed target and scope

- Target: `docs/plans/daily-brief-local-gap-degraded-delivery-plan-20260730.md`
- Scope: opening eligibility、run-scoped required-data coverage、Position Advice degraded source graph、Daily Brief normal/fixed-failure routing、内嵌告警状态机与兼容策略
- Review lenses: architecture boundary、best practice、optimal solution、overengineering、overcoupling

## Assumptions tested

- opening eligibility 不会覆盖 open-position required data；
- `success_empty` 可以在无 peer 的单标的运行中被正向证明；
- required-data coverage 是 provider outcome 的唯一权威；
- zero-quote candidate source 仍具有完整、不可变的依赖与时间语义；
- v1/v2 artifact 可以在发布和回滚期间安全共存；
- P0 position gap 不需要 renderer 平行读取 ledger；
- alert transition 只基于 provider 已确认发送的 normal Brief。

上一轮发现的 opening/position conflation、singleton peer 矛盾、zero-quote evidence、
`not_applicable` authority 混用和 work-unit 过粗问题已在目标计划中得到实质修复。

## Findings

### 1-未修复-高-strategy status 增加终态但没有确定 schema 与文件版本迁移

- **位置**: Phase B `strategy scan status 增加 terminal not_applicable`；兼容章节
- **问题类型**: 契约缺失 / version skew / 不可直接实施
- **当前写法**: 增加 `not_applicable`、`applicability_basis`、`coverage_scope_ref` 和 evidence digest，但只明确 candidate capture 升级为 v2；没有说明 strategy status 和 index 是原地扩展 v1 还是升级 v2，也没有规定文件名和 reader 选择。
- **反例/失败场景**: writer 在 `strategy_scan_status.v1` 中写入 `not_applicable`，而当前 index/Brief reader 仍只接受 v1 的三个 terminal 与固定 counts；或者 writer 改写 v2 文件名，但 Brief 继续读取 `strategy_scan_status_index.v1.json`。
- **为什么有问题**: 新 terminal 和强制字段是非兼容契约变化。当前代码把 schema 常量、terminal allowlist、index counts、文件名和 Daily Brief reader 都硬编码为 v1。
- **直接证据**:
  - `src/application/strategy_scan_status.py:12-14,55-75,193-207`
  - `src/application/daily_decision_brief_service.py:2318-2331`
  - 目标计划 `234-240,294-296`
- **影响**: implementation Agent 必须自行决定 public artifact 版本策略；容易产生 mixed-schema 被误判失败、旧 reader 静默漏掉 not-applicable count，或回滚后无法读取当前 run。
- **建议改法和验证点**: 计划中锁定 `strategy_scan_status.v2` 与 `strategy_scan_status_index.v2` 的 schema、文件名、counts 和 reader routing；规定新版本整条 run 链路原子选择 v2，旧版本只消费 v1，禁止同 run 混用。增加 v1-only、v2-only、mixed、rollback 四类 contract tests。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### 2-未修复-高-P0 position gap 没有定义进入 Position Advice/Close Advice 的权威接口

- **位置**: Phase B Daily Brief 第 249-251 行
- **问题类型**: 架构边界 / 契约缺失 / 实施切片欠规格
- **当前写法**: P0 由 Position Advice/Close Advice 已绑定的 ledger 与 lifecycle authority 计算，renderer 不直接读取账本。
- **反例/失败场景**: `required_data_coverage.v2` 记录某个 position requirement 为 `coverage_incomplete`，candidate source 只保留 scope reference；Position Advice input/source manifest 没有 position-gap projection，runner 无法把 coverage scope 映射到具体 position/lot。实现者只能让 Daily Brief renderer 读取 coverage + ledger 并自行 join，或只按 symbol 输出无 position identity 的告警。
- **为什么有问题**: 计划正确禁止 renderer 重建账本事实，却没有指定哪个 owner、以什么输入输出把 coverage scope 与 ledger position identity 连接起来；这使关键安全行为不可直接实现。
- **直接证据**:
  - 目标计划 `72-99,221-232,242-252`
  - `src/application/position_advice_input_builder.py:348-375` 当前 current manifest 只绑定 source manifest、advice/input artifact 和 observation time，没有 coverage-to-position projection 契约。
- **影响**: implementation Agent 可能跨层读取 ledger、产生无法审计的 symbol-only P0，或完全漏掉存量仓位局部失败。
- **建议改法和验证点**: 明确由 Close Advice input preparation 在冻结 position requirements 时生成稳定 `requirement_id -> position_id/lot_id/symbol/contract` 映射；Position Advice/Close Advice runner 消费 coverage outcome 后输出 authoritative `position_data_gaps[]`，Daily Brief 只投影该输出。测试一标的多仓位、同 symbol 不同 expiry、position closed during run、requirement identity mismatch 和 coverage receipt tamper。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### 3-未修复-高-告警状态机要求 confirmed baseline，但没有定义确认后推进的持久化边界

- **位置**: Phase C；兼容与观测
- **问题类型**: 状态机漏洞 / 并发恢复风险 / 契约缺失
- **当前写法**: 比较基线只使用上一份 provider 已确认发送的 normal Brief；失败、dry-run 和 ambiguous 不推进；exact retry 冻结。
- **反例/失败场景**: 当前 normal Brief 在发送前就通过 `persist_daily_decision_brief_success()` 推进 current revision；provider 之后失败或 ambiguous。下一次 run 如果从 current Brief 取 baseline，会把未送达的 gap 当作“已告警”；如果另建状态但不与 delivery confirmation 同锁/CAS，重试和并发确认可能重复或跳过 transition。
- **为什么有问题**: 目标状态机的语义与当前“生成成功 revision”和“provider confirmed delivery pointer”两个不同持久化边界不一致。计划没有锁定 baseline 的存储位置、读取 API、confirm-time 更新以及 delivery digest 绑定。
- **直接证据**:
  - `src/application/tick_notification_flow.py:806-827` 在发送前持久化 Brief 并计算 previous/diff；
  - `src/application/tick_notification_flow.py:1344-1350` 在发送后才确认；
  - `src/application/daily_decision_brief_repository.py:48-80,1120-1210` successful current 与 confirmed delivery pointer 是两个独立状态。
- **影响**: 局部告警可能漏报、重复、错误恢复，或在 ambiguous/exact retry 后推进到与用户实际看到内容不同的 baseline。
- **建议改法和验证点**: 计划中指定 confirmed alert baseline 归 Daily Brief repository 所有，并绑定 `delivery_key + brief_digest + normalized_gap_set`；prepare 阶段只读取最后 confirmed baseline，confirm 阶段在现有 account/market delivery lock 内 CAS 推进，exact retry 不重新计算。覆盖 send definite failure、ambiguous、重复 confirmation、stale completion、同账户并发 run、跨日和 scope_retired。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

## Open Questions

- v2 strategy status 是与 v1 双写一个 release，还是由新代码原子切换且依靠旧版本回滚读取 v1 fallback？计划必须选择一种，不应留给实现阶段。
- `position_data_gaps[]` 是否作为 Position Advice summary v2 的正式字段，还是 Close Advice 独立 sidecar？建议复用 Position Advice summary，避免 Daily Brief 多源 join。

## Residual Risks

- release-controlled catalog 的权威来源仍依赖人工 review；应在实现 PR 和 Release Notes 中记录 entry 来源、有效期和复核责任。
- provider “成功但零行”只能证明调用完成和响应有效，不能证明交易所确实没有产品；产品文案应保持“本轮未取得合约数据”，除非有 catalog authority。
- 三个 Phase 已显著降低过度耦合，但 Phase B 仍跨 Position Advice 与 notification authority；建议保持独立提交和 focused gate。

## Conclusion

`fail`

修订版已经解决上一轮全部 findings，但仍有 3 个高风险、会迫使 implementation Agent 重新设计的契约/状态机缺口。
在 strategy status versioning、position gap projection 和 confirmed alert baseline 三项收敛前，不建议进入实现。
