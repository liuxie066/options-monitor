## Findings

### 1-未修复-高-candidate source 与 Position Advice source manifest 的 v2 契约仍未定义

- **位置**: Phase B candidate source publisher；版本选择与兼容章节
- **问题类型**: 契约缺失 / version skew / 不可直接实施
- **当前写法**: candidate capture 升级 v2；candidate source 始终依赖 `required_data_coverage`，并在零候选时允许零 quote dependency；但没有升级 candidate source payload、source receipt dependency policy 或 Position Advice source manifest contract。
- **反例/失败场景**: 实现者让现有 `position_advice_candidate_all_decisions.v1` receipt 依赖 `required_data_coverage`。当前 validator 要求 candidate decisions 的 required dependency 精确包含 `quotes`，且 source-kind/freshness allowlist 不认识 `required_data_coverage`；零 quote source 会在 publisher 或 source-manifest validation 阶段失败。若直接原地放宽 v1，旧 reader 会在同一 schema 下遇到新的 dependency 和 nullable market observation 语义。
- **为什么有问题**: capture v2 不是 Position Advice adopted source。真正进入 Position Advice runner 的是 `candidate_decisions` source payload/receipt/source manifest；其 public contract仍是 v1/v2 manifest 的旧组合。
- **直接证据**:
  - `src/application/position_advice_source_producers.py:14,123-190`：candidate payload 是 `position_advice_candidate_all_decisions.v1`，并强制至少一个 quote snapshot；
  - `src/application/position_advice_source_receipts.py:19-45`：source allowlist 不含 `required_data_coverage`，candidate required dependencies 固定为 `quotes`；
  - 目标计划 `252-272,381-384` 只明确 capture/status 的 v2 选择。
- **影响**: Phase B 无法生成计划承诺的 degraded source graph；或实现者被迫在 v1 下做隐式语义扩展，造成旧 reader、promotion checks、freshness/skew policy 和 rollback 行为不一致。
- **建议改法和验证点**: 明确新增 `position_advice_candidate_all_decisions.v2`，其 receipt 必须依赖一个 adopted `required_data_coverage` source；有 decisions 时再要求对应 quotes，零 decisions 时只在 coverage 证明所有 opening scopes 不产生决策时允许零 quotes。同步锁定 source-kind allowlist、freshness、account/global scope、source manifest required-for-actions、runner reader 和 mixed v1/v2 规则。测试 catalog-only、success-empty、带候选、缺 coverage、额外/错误 dependency、manifest 未采用 dependency、v1/v2 mixed 和 rollback 新 run。
- **修复风险（低/中/高）**: 高
- **严重程度（低/中/高/严重）**: 高

### 2-未修复-高-按确认时间选择 baseline 会被迟到确认的旧交易日倒退

- **位置**: Phase C baseline 选择第 1 步
- **问题类型**: 状态机漏洞 / 并发恢复风险
- **当前写法**: 从各 trading day 中“按 confirmation time/revision”找到最后一份 confirmed normal envelope。
- **反例/失败场景**: D 日发送结果 ambiguous；D+1 日 normal Brief 已确认并成为实际最新内容；随后 operator 把 D 日 envelope 解决为 delivered。D 日的 `confirmed_at` 更新得更晚。D+2 若按 confirmation time 选 baseline，会回退到 D 日 gaps，重复产生 new/recovered 告警。
- **为什么有问题**: confirmation time 是 transport finality 时间，不是报告事实的逻辑顺序；revision 又只在单个 trading day 内有序，不能跨日单独比较。
- **直接证据**:
  - 目标计划 `360-373` 明确按 confirmation time/revision；
  - `src/application/daily_decision_brief_repository.py:636-709` 允许 ambiguous delivery 后续被人工解决为 delivered，并在解决时写新的 confirmation time；
  - delivery state 以 trading day 分组，revision 为 day 内身份。
- **影响**: baseline 可能倒退，造成局部告警重复、错误恢复或 scope-retired 判断错误；用户看到的状态序列与系统审计不一致。
- **建议改法和验证点**: confirmed normal baseline 必须按逻辑报告身份最大值选择：`(market_trading_date, revision)`，`confirmed_at` 只作审计和确认存在性校验。若同一逻辑身份出现冲突 digest/delivery key 则 fail closed。增加旧日迟到确认、新日先确认、同日 stale completion、跨日 revision 重置和 operator resolution 测试。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

## Open Questions

- `required_data_coverage` 应作为 global/run source 还是每账户 adopted source？建议 run producer + account consumer adoption，receipt 绑定 producer run，manifest adoption 绑定 consumer account run。
- candidate source v2 是否需要升级整个 source manifest schema？如果现有 manifest v2 能在显式扩展 source-kind/freshness policy 后安全表达，可保持 manifest v2；必须由 contract tests 证明，不能默认。

## Residual Risks

- `required_data_coverage` 加入 Position Advice freshness/skew 后，catalog-only observation 与市场 quote observation 的时钟语义不同；应只让真实 market observation 进入 market skew，coverage evaluation time 不得伪装为 quote time。
- Close Advice CSV 仍是 Daily Brief 的直接输入；实现时必须验证 requirement/lot/scope 字段属于当前 frozen run，不能只因字段存在就接受。
- 新代码按 Account Run 原子切 v2 已避免 runtime feature flag，但正式发布后仍需 no-send canary 证明所有账户走同一 contract generation。

## Conclusion

`fail`

第三轮计划已经解决上一轮 3 项 findings，但仍有 2 个高风险问题：
Position Advice adopted source 的 v2 契约没有闭合，且跨日 baseline 的排序依据会在迟到确认时倒退。
两项收敛前不建议进入实现。
