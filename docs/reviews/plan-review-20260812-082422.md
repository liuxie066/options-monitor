# Plan Review — Candidate Compatibility CSV Retirement

- Reviewed target: `docs/gateflow/candidate-csv-retirement/plan.md`
- Review scope: authority model, Combo snapshot schema, historical compatibility, slice sequencing, config/version skew,
  and verification sufficiency
- Review timestamp: 2026-08-12 08:24:22 local system time
- Conclusion: `fail`
- Artifact path: `docs/reviews/plan-review-20260812-082422.md`

## Assumptions tested

1. Discovering snapshot files is sufficient to prove that every configured candidate owner published terminal state.
2. An accepted Combo pair evaluation is equivalent to a final ranked pair.
3. The current opening-snapshot seal can always provide the dependency boundary needed by Combo.
4. Removing and rejecting `output_mode` is safe for both authored YAML and already-generated runtime JSON.
5. Historical Combo v1 snapshots fit one of the four declared compatibility states.
6. Full pair diagnostics and rank-shadow evidence can be normalized into a bounded terminal payload without carrying
   pandas/NaN serialization behavior or duplicate full pair rows into the authority contract.

## Findings

### PR-01-未修复-高-仅发现已有 snapshot 无法证明缺失的 configured owner
- **位置**: Historical compatibility classification lines 66-78; Slice S3 items 1-3
- **问题类型**: 状态机漏洞 / 契约缺失
- **当前写法**: `supported` 被定义为“all configured candidate owners have valid sealed snapshots”，但实施步骤只写
  discover/validate opening、Combo、CC+LP snapshot，没有指定从哪里取得完整的 configured-owner 集合。
- **反例/失败场景**: 一个账户配置了 Sell Put 和 Combo；opening snapshot 成功，进程在 Combo seal 前退出。基于
  已存在 snapshot 文件的发现只能看到 opening，容易把该账户当作 supported，或根本不知道 Combo 应该存在。
- **为什么有问题**: 缺失文件不能自证它本来应存在。这样会把本计划最关键的 fail-closed 语义重新变成静默
  缺 scope，并允许不完整窗口取得回测完整性。
- **直接证据**: `publish_strategy_scan_status_index()` 已接收完整 `expected` 集合并把每个 symbol/family 写入
  `strategy_scan_status_index.v1.json` (`src/application/strategy_scan_status.py:145-227`)；plan 没有把这个现有
  expected-scope authority 纳入支持性判定。
- **影响**: Strategy Lab/Shadow Replay 可能在漏掉 Combo 或 CC+LP 的情况下错误宣称样本完整，影响研究结论和
  promotion gate。
- **建议改法和验证点**: 明确以 hash-valid strategy status index（或由它派生的窄 candidate-owner manifest）作为
  expected owner/scope 真源；逐 scope 验证应有 snapshot、schema 和 terminal status。增加“opening 已封存但 Combo
  seal 前中断”“一个账户多 symbol/variant 仅缺一个 owner”的回归，必须得到
  `unsupported_snapshot_missing` 且 strict authority 为 false。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR-02-未修复-高-Combo v2 把 eligibility acceptance 与最终 selection 错写成相等关系
- **位置**: Combo Yield v2 contract lines 49-64; Slice S1 exit tests lines 122-129
- **问题类型**: 契约缺失 / 不可直接实施
- **当前写法**: validator 要求 “equality between accepted terminal pairs and the ranked pair projection”。
- **反例/失败场景**: 同一 Funding Put 有多个合法 Call 时，pair diagnostics 会有多个 `accepted=true`；当前
  `select_best_yield_enhancement_pairs()` 先为每个 Put 选一个 Call，再跨 Put/标的选最终 pair。合法但未被最终选中的
  pair 因而 accepted，却不在 `ranked_pairs`。
- **为什么有问题**: 当前计划没有建模 `eligible`、`ranked_below`、`selected` 三种不同状态。照字面实现会拒绝合法
  snapshot；为让校验通过而丢弃未选中合法 pair，则会丢失 rank shadow 和“为什么没推荐”的证据。
- **直接证据**: pair builder 为所有通过结构/门槛的组合追加 accepted diagnostic
  (`src/application/sell_put_call_helper.py:915-925`)；随后 selector 分两层缩减
  (`src/application/sell_put_call_helper.py:996-1010`)；rank shadow 又对全部 raw pairs 建 baseline/shadow selection
  (`src/application/sell_put_call_helper.py:1013-1072`)。
- **影响**: 合法多候选运行无法封存，或研究诊断/排序证据被错误删除，直接违背“先承接证据再删 CSV”。
- **建议改法和验证点**: 在计划中固定三个状态和稳定 pair id：pair evaluation 只声明 eligibility；compact rank
  record 声明 baseline/shadow rank 与 selected；`ranked_pairs` 声明最终 terminal selection。validator 应验证最终
  pair 是 eligible 集合子集、rank/selected 标记自洽、无未知 pair id，而不是集合相等。增加同 Put 多 Call、同标的
  多 Put、跨标的多 pair 三类反例。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR-03-未修复-高-计划未覆盖 Combo-only 配置下现有 opening seal 的必然失败
- **位置**: Authority model；Slice S1 dependency binding lines 98-106
- **问题类型**: 架构边界 / 测试缺口
- **当前写法**: Combo v2 复用 opening seal 边界已经 assembled 的 dependencies，但没有说明 opening owner 为空时
  如何封存。
- **反例/失败场景**: 一个账户只启用 Combo Yield，未启用独立 Sell Put/CC。当前 pipeline 无条件先调用
  `seal_opening_candidate_snapshot()`；opening snapshot 在没有 strategy modes 时直接报错，后续 Combo snapshot 永远
  不会写出。CSV 删除后该配置没有任何候选终态权威。
- **为什么有问题**: Combo 已被计划声明为独立 owner，不能依赖另一个未配置 owner 的成功 seal。当前 plan 的测试
  也没有明确 Combo-only/CC+LP-only 配置。
- **直接证据**: opening seal 对空 modes 报错 (`src/application/opening_candidate_snapshot.py:117-120`)；pipeline
  在检查任何 Combo scope 前无条件调用它 (`src/application/pipeline_watchlist.py:1032-1046`)。
- **影响**: 合法独立 Combo 配置在实施后 fail closed 到完全不可用；研究端随后只看到 missing snapshot。
- **建议改法和验证点**: 明确各 owner 独立封存：只有存在 opening expected scopes 时才 seal opening；Combo/CC+LP
  直接绑定共用 run dependencies，不借 opening snapshot 作为必需前置。增加 SP+LC-only、CC+LP-only、opening-only、
  混合 owner 四种 pipeline capture 测试。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR-04-未修复-中-历史 Combo v1 在声明的兼容状态机中无归属
- **位置**: Combo v2 contract line 64; Historical compatibility classification lines 66-78; Slice S3 tests
  lines 216-224
- **问题类型**: 状态机漏洞 / open question 未收敛
- **当前写法**: 文本说 v1 可被识别但不具备 v2 完整诊断证据；状态机只有 supported、CSV-only、snapshot
  missing、not scanned；测试又要求 old Combo v1 “return explicit classification”。
- **反例/失败场景**: 历史运行有 hash-valid Combo v1 和 ranked pairs，也可能有 opening v1。它既不是 CSV-only，
  也不是 snapshot missing；若归 supported，会误称具有 v2 diagnostics；若归 unsupported_snapshot_missing，则事实不符。
- **为什么有问题**: 实施者必须临场决定 v1 是否可用于 accepted-candidate research、是否阻断 strict replay，以及稳定
  reason code，计划并未锁定。
- **直接证据**: plan lines 62-74 与 lines 218-220 的集合不闭合。
- **影响**: 不同 consumer 可能对同一历史运行给出不同可用性，造成 Strategy Lab/readiness 漂移。
- **建议改法和验证点**: 新增明确状态 `supported_limited_legacy_snapshot`（可读 sealed ranked pairs，但缺失诊断时
  strict promotion=false），或明确将 v1 归 `unsupported_schema_version`。用户只批准 CSV-only 退出自动兼容，因此优先
  保留 v1 sealed accepted-pair 事实并披露 limitation。为 research、archive、dataset build、run-window coverage 各加
  同一 reason/status 断言。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### PR-05-未修复-中-`output_mode` 的 authored/runtime 版本偏移没有迁移契约
- **位置**: Slice S2 item 5 and exit tests
- **问题类型**: 版本偏移 / migration hazard
- **当前写法**: 从 defaults/build output 删除该键，并对 authored use 显式报错，但没有规定已经生成的旧 runtime
  JSON 在新代码下如何处理。
- **反例/失败场景**: 已部署的 `config.us.json`/`config.hk.json` 由旧 `configs/system.json` 生成并包含
  `output_mode=separate`。源码升级后若先验证现有 runtime JSON，新 validator 会把该键当未知/removed 而阻断整个 tick，
  即使业务语义本来就等同新默认。
- **为什么有问题**: “完整移除运行分支”不等于可以忽略 source/config version skew。发布和升级虽不在当前授权范围，
  但源码计划必须给后续受控升级留下可执行迁移边界。
- **直接证据**: 当前 system defaults 写入该键 (`configs/system.json`)；resolver 把它物化到 effective config
  (`src/application/yield_enhancement_config.py:233-240`)；runtime validator 当前显式接受并校验
  (`src/application/config_validator.py:681-684`)。
- **影响**: 后续升级可能在任何候选计算前造成生产配置整体不可用。
- **建议改法和验证点**: 区分 YAML authoring 与 generated runtime snapshot：authoring 立即拒绝退休键；config build
  不再生成；对上一 schema 生成的 runtime JSON 采用一个有版本边界、只删除该无效键的加载迁移或在受控 upgrade
  preflight 中强制重建后再启用新代码。计划必须选择一种并增加 old-runtime/new-runtime/authoring 三组测试；不要保留
  任何会改变输出行为的 compatibility branch。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 中

## Open Questions

- Pair diagnostics 是 Funding Put × Call 的组合级证据，rank shadow 又复制 raw pair fields。v2 应明确存 compact
  normalized records，或把大体量逐 pair 证据写入一个由 snapshot hash 绑定的 JSONL audit artifact；不能直接把任意
  DataFrame `to_dict()` 结果（含 pandas/NumPy scalar、NaN）塞进 `allow_nan=False` 的 canonical JSON。
- 如果采用独立 JSONL audit artifact，需要定义 write-once publication、content hash、相对路径和 snapshot-before/
  audit-before 的提交顺序，避免 terminal snapshot 指向可追加或半写文件。

## Residual Risks and tracking

- 即使计划修复，历史 CSV-only 运行只能冷存档，不能恢复其当时缺失的 seal；此限制应持续记录在
  `docs/SHADOW_REPLAY_RUNBOOK.md` 和 Strategy Lab readiness reason codes。
- 全量 pair evidence 可能显著增加 JSON 体积；实施时记录最大 fixture/representative run 的 bytes 和 row counts，作为
  slice S1 review artifact 的观测项，而不是在本 work unit 引入压缩或数据库。
- 旧 CSV 文件的物理删除仍是独立 destructive operations work unit，不属于本计划。

## Final conclusion

`fail`。方向正确，但 expected-owner 真源、Combo selection state、Combo-only seal、v1 历史分类和 runtime config
版本偏移尚未达到 code-generation-ready。修复这些计划问题后再进入 implementation。
