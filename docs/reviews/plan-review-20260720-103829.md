## Summary

第三轮的五项 finding 已经在方案中得到明确修复：未知三级分类不再静默忽略，digest绑定remote alias和endpoint fingerprint，response-loss有 `already_at_target` no-op，staging-only变化不再制造无意义stale，Tool data/warnings/error层级也已统一。方案比上一版更接近可实施状态。

第四轮仍发现 2 个高严重度和 3 个中严重度问题。两个 blocker分别是：严格Changelog grammar仍允许未知二级标题提前终止 `Unreleased`，从而绕过未知内容检查并产生under-bump；apply在完整local recommendation之后执行remote查询，再直接写VERSION，没有最终local evidence recheck或single-writer/CAS保护，因此工作区可以在网络窗口内变化而仍被写入。

其余问题是条件输入要求没有映射到当前Tool schema/validator能力、remote Git命令缺少timeout和non-interactive契约、以及stable tag正则仍接受leading-zero版本并产生非确定性latest选择。

这些问题仍可局部修正，不需要改变advisory-only、复用 `version_update`、只写VERSION或remote-tag baseline的核心方向。

## Goal and boundary reconstructed

方案目标仍是：preview基于remote最高稳定tag和严格 `Unreleased` 声明产生确定性建议；用户确认后重新验证evidence，只原子更新VERSION；手动路径保持兼容，不自动修改Changelog、Git refs、release或生产。

新增边界包括：remote endpoint fingerprint、strict line grammar、expected base/target、`already_at_target` recovery、mode-sensitive output contract和staging-placement非freshness。

## Assumptions tested

1. “Unreleased到下一个任意 `##` 结束”不会让未知release intent逃离严格grammar。
2. apply的“完整recommendation + remote recheck + atomic replace”足以保证本地workspace freshness直到写入时刻。
3. 当前Tool input JSON schema能表达“仅当 bump=auto 且 apply=true 时 required”的字段。
4. `git remote get-url` / `git ls-remote` 默认不会无限等待、弹出credential prompt或进入无法取消的交互。
5. `v[0-9]+.[0-9]+.[0-9]+` 等价于canonical SemVer stable tag。
6. `already_at_target` 作为无写入结果不需要证明上一请求执行成功；当前文案已明确这一点。
7. static union output contract加payload resolver能保留manual shape并让spec发现auto variant。

## Findings

### PR4-01-未修复-高-未知二级标题可以终止 Unreleased 并绕过 fail-closed grammar
- **位置**: 4.3 Release intent、5.1 Deterministic precedence、12 Classification and strict grammar
- **问题类型**: 状态机漏洞 / 契约缺失 / fail-open parsing
- **当前写法**: `Unreleased` section从标题下一行开始，到“下一个 `## ` 标题或EOF”结束；strict grammar只验证section内部的三级标题和内容。
- **反例/失败场景**:
  ```markdown
  ## Unreleased

  ### Fixed
  - Fixed a typo.

  ## Removed
  - Removed the legacy CLI command used by automation.

  ## 1.3.0 - 2026-07-19
  ```
  parser在 `## Removed` 前结束Unreleased，只看到 `Fixed`，因此推荐patch。`Removed` 既不会作为未知三级标题被拒绝，也不会进入当前section evidence。
- **为什么有问题**: 第三轮修复的目标是“任何未知或无法归属的非空release intent都不能被静默丢弃”。允许任意H2作为section terminator重新打开了同类under-bump路径。维护者把三级标题误写成二级标题是可信的Markdown authoring错误，且当前release metadata校验不会拒绝这种额外顶级section。
- **直接证据**: plan `:174-188` 明确把任意下一个 `##` 作为终点，并只验证区段内部内容；test matrix `:715-725` 覆盖未知heading、heading外bullet、duplicate Unreleased和code fence，但没有“受支持bullet + 未知H2”场景。当前 `scripts/release_check.py:27-42` 同样在任意H2处停止版本section，且只检查目标版本section存在，不能替recommendation parser阻止该逃逸。
- **影响**: breaking/removed/security内容被遗漏，工具给出patch/minor under-bump；用户看到的evidence不完整；strict grammar的核心安全承诺不成立。
- **建议改法和验证点**:
  1. 对 `## Unreleased` 后遇到的第一个H2做结构验证：它必须是符合仓库release heading格式的版本标题；其它H2返回 `needs_input / UNSUPPORTED_UNRELEASED_CONTENT`。
  2. 若需要允许其它顶级文档section，必须显式白名单并证明它不包含release intent；v1更安全的方案是直接拒绝。
  3. 扫描整个Changelog结构，确保Unreleased与首个版本section之间没有被parser跳过的非空 sibling section。
  4. 增加 `Fixed + ## Removed`、`Added + ## Security`、unknown H2 only和合法下一个version H2测试。
- **修复风险（低）**: 只是收紧line parser boundary，不需要Markdown AST。
- **严重程度（高）**: 当前存在静默丢失声明并推荐过低版本的真实路径。

### PR4-02-未修复-高-apply在remote查询窗口后没有最终本地freshness recheck或CAS
- **位置**: 1 Success criteria、7.2 Apply recommendation、11 S2、12 Freshness tests
- **问题类型**: TOCTOU / 并发恢复风险 / 状态机漏洞
- **当前写法**: apply第5步重新计算全部local/remote recommendation，第7步比较digest，第8-9步再次执行remote endpoint/tag查询，然后第10步直接原子replace VERSION。没有在remote网络操作后再次验证HEAD、Changelog、tracked/untracked content或current VERSION，也没有single-writer lock或expected-current compare-and-swap。
- **反例/失败场景**:
  1. 第5-7步完成，digest与preview一致。
  2. 第8步 `git ls-remote` 等待网络时，另一个终端修改 `CHANGELOG.md`，新增Breaking Changes；或者把VERSION从expected base改成另一个值。
  3. remote recheck成功，第10步仍写入旧推荐target。若VERSION被并发修改，atomic replace只保证文件不撕裂，并不防止覆盖新值。
- **为什么有问题**: 成功标准声称工作区、Changelog或基线变化就拒绝写入，但当前sequencing只证明它们在第5步时未变化。atomic rename是原子写，不是compare-and-swap，也不是workspace snapshot。remote race被列为residual risk，本地可控race却没有被定义或缩小。
- **直接证据**: plan `:17-19` 声称变更会拒绝写入；`:402-414` 在local recompute之后安排remote查询并直接写入；`:748-759` freshness tests没有“apply remote recheck期间local mutation”。当前 `update_local_version()` 在 `src/application/version_check.py:68-72` 直接write temp + replace，不接受expected-current VERSION，也不检查其它evidence。
- **影响**: 用户确认后仍可能基于过期Changelog/worktree写入版本；并发VERSION更新被覆盖；审计digest与真正写入时workspace不一致。
- **建议改法和验证点**:
  1. 明确auto apply的single-writer模型。推荐使用repo-scoped advisory lock覆盖“final local recompute -> remote recheck -> final local recheck -> VERSION CAS/write”；手动编辑不遵守锁时仍由final recheck捕获。
  2. remote recheck后、写前重新计算local-only evidence digest，并与第5步结果比较；至少再次检查HEAD、Changelog、tracked/untracked content和current VERSION。
  3. auto write必须执行expected-current VERSION CAS：写前current VERSION仍须等于expected base，否则stale；不要复用一个会重新推导target但不接受expected current的宽写函数。
  4. 增加注入hook测试：在remote recheck期间修改Changelog、HEAD、untracked file和VERSION，全部必须零写入。
  5. 将无法完全消除的remote最后一瞬race继续列为residual risk，但不要把本地可检测race混在其中。
- **修复风险（中）**: 需要窄锁/CAS seam和测试注入点，但不需要持久化状态或数据库。
- **严重程度（高）**: 直接违反方案最核心的freshness写入承诺。

### PR4-03-未修复-中-条件 required 输入没有映射到现有 Tool schema/validator
- **位置**: 8.1 Input additions、10 Ownership、12 Compatibility tests
- **问题类型**: public contract / 不可直接实施 / compatibility risk
- **当前写法**: `recommendation_digest`、`expected_base_version`、`expected_target_version` 仅在 `apply=true,bump=auto` 时required；方案要求static spec可发现variants，但没有指定谁实现conditional validation。
- **反例/失败场景**: 若在 `input_schema` 把三个字段标成普通 `required=true`，现有manual patch preview/apply全部被schema validator拒绝，破坏兼容性。若全部保持optional，只在handler里偶然读取，spec无法表达条件，且遗漏字段可能落入不同错误路径。
- **为什么有问题**: 当前schema builder只支持字段级required和有限JSON schema keys，不支持 `if/then`、`oneOf`、`allOf` 等条件结构。仓库已有明确的 `AgentTool.input_validator` seam，但plan的runtime/adapter ownership没有把条件验证放到该边界。
- **直接证据**: `src/application/tool_input_schema.py:10-31` 的允许key不包含条件schema；`:74-96` 只从每个field的 `required=true` 生成全局required列表。`src/application/agent_tools/base.py:33,59-68,147-150` 已提供input_validator。plan `:438-447` 只写自然语言required，`:604-616` 未指定validator ownership。
- **影响**: implementation agent必须临场决定验证层；可能破坏manual路径，或让spec、runtime error和tests不一致。
- **建议改法和验证点**:
  1. 在plan中明确新增 `_validate_version_update_input(payload)` 并挂到 `VERSION_UPDATE_TOOL.input_validator`。
  2. validator负责mutual exclusion和条件要求：`target_version` vs any bump、auto apply三字段、auto-only expected字段、manual路径对auto字段的处理。
  3. static input descriptions明确条件，但不要把auto apply字段设为全局required。
  4. 测试需注意write gate先于input validation：要验证missing-field INPUT_ERROR，必须开启write tools并传confirm；同时锁定PERMISSION_DENIED/CONFIRMATION_REQUIRED优先级。
- **修复风险（低）**: 使用现有seam即可。
- **严重程度（中）**: 不修会导致兼容性或公开契约漂移。

### PR4-04-未修复-中-remote Git命令没有超时和non-interactive执行契约
- **位置**: 4.1 Remote authority、7.2 Apply、12 Offline/remote tests、15 Residual risks
- **问题类型**: timeout/cancellation gap / degraded dependency handling
- **当前写法**: 规定运行 `git remote get-url` 和 `git ls-remote --tags`，网络失败时fail closed，但没有timeout、credential prompt、SSH host-key prompt、process cancellation或对应reason code。
- **反例/失败场景**: origin改为不可达SSH endpoint，或credential helper要求交互。`git ls-remote` 可以长时间等待网络或终端输入，preview不返回；apply在用户已经confirm并通过write gate后卡住，调用方无法区分“仍在验证”与“未知是否写入”。
- **为什么有问题**: fail closed只有在命令最终返回时才成立。自动化Tool必须把外部依赖等待设为bounded，并禁止交互prompt。当前repo的旧 `check_version_update()` 正好没有timeout，说明不能假定复用现有代码自然获得该保护；`release_target` 的其它命令已经展示了显式timeout惯例。
- **直接证据**: plan `:82-93` 和 `:402-416` 没有timeout/env要求；`src/application/version_check.py:120-128` 的现有ls-remote无timeout；`src/application/release_target.py:158-163,348-357` 已有显式timeout helper先例。
- **影响**: Tool调用无限挂起、取消语义不清、用户可能重复apply、CI/Agent会话资源耗尽。
- **建议改法和验证点**:
  1. 所有remote Git命令使用统一bounded runner，明确timeout值和 `GIT_TERMINAL_PROMPT=0`；按平台需要设置credential helper non-interactive环境。
  2. `TimeoutExpired` 映射到稳定reason code，例如 `REMOTE_TAG_LOOKUP_TIMEOUT`；get-url和ls-remote区分错误阶段。
  3. timeout发生在写前必须保证VERSION未变化、temp file未创建。
  4. 增加slow runner、credential prompt simulation、timeout后重试测试。
- **修复风险（低）**: 可复用项目已有bounded subprocess模式。
- **严重程度（中）**: 不损坏数据，但会破坏Tool可用性和确定性失败语义。

### PR4-05-未修复-中-stable tag正则接受leading-zero版本并造成latest选择非确定
- **位置**: 4.1 Stable tag parsing、10 release_target ownership、12 Baseline tests
- **问题类型**: version skew / deterministic ordering gap / SemVer contract
- **当前写法**: stable raw ref正则是 `v[0-9]+.[0-9]+.[0-9]+`；方案称其为SemVer stable tag，但没有禁止numeric component leading zero，也没有定义两个文本版本SemVer precedence相等时如何处理。
- **反例/失败场景**: remote同时存在 `v1.2.3` 和 `v1.02.3`。当前parse/compare把两者解析为相同 `(1,2,3)`；stable sort保持输入顺序，因此 `ls-remote` 行顺序不同会让“latest”分别成为不同tag。一个可能通过VERSION equality，另一个可能触发mismatch；结果不确定。
- **为什么有问题**: SemVer numeric identifiers不允许leading zero。更重要的是，计划的deterministic recommendation依赖唯一最高baseline，当前accepted namespace允许两个不同tag具有相同precedence。
- **直接证据**: plan `:95-119` 接受任意数字串；当前 `src/application/release_target.py:12-13,29-39` 也接受leading zero并转成int。实测 `compare_versions("1.2.3", "1.02.3") == 0`，且反转两条tag输入顺序会改变 `select_latest_release()` 的结果。
- **影响**: baseline选择依赖remote输出顺序；不同机器/调用可能blocked或选择不同tag；digest和identity不稳定。
- **建议改法和验证点**:
  1. auto stable tag使用canonical regex：每个numeric component只能是 `0` 或 `[1-9][0-9]*`。
  2. 对非canonical tag明确选择：忽略并返回warning，或只要与canonical tag产生等价precedence就blocked；不要悄悄参与排序。
  3. richer identity parser应检测任何equal-precedence/different-text collision并fail closed。
  4. 保持现有manual/prerelease parser facade兼容可作为独立决定；至少auto baseline必须canonical。
  5. 增加leading-zero only、canonical+leading-zero collision、不同input order测试。
- **修复风险（低）**: 限定auto parser即可，不必全局迁移VERSION_RE。
- **严重程度（中）**: 当前determinism承诺存在可复现反例。

## Architecture boundary review

主要边界仍正确：recommendation engine只读，Tool adapter负责公开shape，VERSION write由application边界拥有，domain不参与。第三轮新增static union contract与resolver也顺着现有AgentTool能力设计。

PR4-03说明条件input validation应明确归属 `VERSION_UPDATE_TOOL.input_validator`，而不是散落在handler和recommendation engine。PR4-02则要求auto-specific write boundary支持expected-current CAS；不要为了复用现有宽 `update_local_version()` 而把freshness责任泄漏或削弱。

`release_target.py` 的新stable identity parser继续应与现有prerelease tuple parser并存；canonical stable tag限制可以只施加于新auto parser，避免无关service-upgrade API churn。

## Best-practice review

- **Parser closure**: strict section grammar不仅要验证section内部，也要验证section termination是否合法。
- **TOCTOU**: atomic replace不等于compare-and-swap；外部查询之后必须重新确认本地前置条件。
- **Schema contract**: 条件required使用现有validator seam，不应伪装成全局JSON schema required。
- **External commands**: 网络Git必须bounded且non-interactive。
- **SemVer**: canonical numeric forms和equal-precedence collisions必须明确。

## Optimal-solution review

总体方案仍是较优路径：Changelog声明优于源码语义猜测，endpoint fingerprint优于引入GitHub API，`already_at_target` no-op优于持久化receipt，复用Tool优于新增Tool。

本轮修复也不需要扩大范围：

- H2 boundary只需多一个release-heading check；
- concurrency只需窄lock/final recheck/CAS seam；
- conditional input使用现有validator；
- remote execution复用bounded runner；
- canonical stable regex只影响auto parser。

## Overengineering review

未发现新的主要过度设计。strict line grammar、endpoint fingerprint、bounded untracked hashing和no-op recovery都有明确风险依据。

repo lock如果只为auto apply、生命周期覆盖最终验证到write且不演化成通用transaction framework，不属于过度设计。不要为解决PR4-02引入数据库、长期receipt或全仓库snapshot系统。

## Overcoupling review

方案已经避免修改service upgrade和release workflow。需继续避免：

- 把auto canonical stable规则强加给所有现有prerelease consumers；
- 让operations adapter承担conditional business validation；该验证应在Tool input_validator；
- 让generic `update_local_version()` 知道Changelog/remote，只需提供窄expected-current write primitive或auto wrapper。

## Open Questions

1. 合法的下一个release H2精确格式是什么：仅stable `## X.Y.Z - date`，还是也允许prerelease历史段？应复用一个明确parser而非宽 `startswith`。
2. auto apply采用repo-scoped lock还是声明single-writer并做两次local digest？本review建议lock + final recheck + VERSION CAS。
3. remote timeout取值和runner owner是什么？建议在recommendation module使用统一小型Git runner，而不是复用无timeout的旧version check路径。
4. 非canonical stable tags是忽略并warning，还是任何equal-precedence collision都blocked？至少collision必须blocked。
5. write gate优先于conditional input validation是否是希望保留的公开错误优先级？tests需要固定。

## Residual risks and tracking

- 用户声明的SemVer影响仍可能错误；继续由manual review和release docs承担。
- final remote query之后仍存在不可消除的极小remote race；由GitHub workflow tag collision兜底。
- 不遵守repo advisory lock的外部进程仍可能在最终check与replace之间竞争；VERSION CAS必须作为最后保护，并在residual risk记录。
- endpoint fingerprint对URL spelling/credential变化敏感；这是保守stale策略。
- `already_at_target` 仍只证明当前值，不证明历史调用；当前方案已正确保留该限定。

## Final conclusion

**fail**。

第三轮finding已闭环，但在进入implementation前仍需：

1. 阻止未知H2逃离Unreleased strict grammar；
2. 为apply增加final local freshness recheck和VERSION CAS/single-writer契约；
3. 明确使用Tool input_validator实现conditional required；
4. 为remote Git增加bounded non-interactive execution；
5. canonicalize auto stable tags并拒绝equal-precedence ambiguity。

这些都是局部方案修正，不要求改变当前产品方向或增加新的持久化系统。
