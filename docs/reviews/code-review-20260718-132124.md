## Findings

### DR-1-未修复-[高]-in-process prefetch still discards the diagonal Call DTE window
- **入口/函数**: `strategy_prefetch_kwargs()`, used by the in-process required-data prefetch path before the detailed fetch plan runs.
- **文件(行号)**: `src/application/required_data_prefetch_planning.py:268-276`
- **输入场景**: A valid diagonal config has Sell Put DTE `20-60` and Combo Yield Call DTE `61-90`.
- **实际分支**: Because Combo Yield is enabled, the function enters `if want_yield_call`, then unconditionally removes `call.min_dte/max_dte` and replaces them with Sell Put values.
- **预期行为**: Diagonal mode must preserve the explicitly configured Call horizon so the prefetch envelope reaches the later Call expirations; same-expiry mode should continue deriving the Call window from Sell Put.
- **实际行为**: The prefetch payload reports a maximum DTE of 60, so an in-process fetch can omit every valid later Call even though `required_data_planning.py` now understands the 61-90 window. Candidate generation then sees no valid Call universe and silently cannot open a true diagonal pair.
- **直接证据**: `src/application/required_data_prefetch_planning.py:270-275` pops both Call DTE fields and copies `sp` values without checking `expiry_structure`; the sibling detailed planner added that check at `src/application/required_data_planning.py:374-388`. Existing tests only assert same-expiry behavior in `tests/test_required_data_prefetch_inprocess.py:231-275`.
- **影响**: True diagonal opening fails in the normal prefetch execution path despite passing config validation and unit tests for the lower-level planner; this is a silent feature failure.
- **建议改法和验证点**: Apply the same expiry-structure branch in `strategy_prefetch_kwargs()`: preserve explicit Call DTEs for diagonal and derive from Sell Put only for same-expiry. Add an in-process prefetch test asserting a 20-60 Put plus 61-90 Call produces a 20-90 fetch envelope and retains Call strike bounds.
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高
