## Goal and boundary understood

The plan must stop duplicate expiry and ordinary-close receipts without weakening the canonical
`trade_events -> position_lots` ledger. A zero-price close may establish that the option leg is closed
before its cause is known, while the canonical lot remains at its pre-terminal quantity and is blocked
from further action. Push and Poll must converge on one broker identity; terminal reason, projection,
allocation and notification intent must be auditable and idempotent.

## Re-review of previous findings

1. **Pending close versus projection-zero circularity — addressed**: the plan now keeps canonical lots at
   pre-terminal remaining, derives a non-actionable reservation, requires the no-settlement precondition
   to match frozen remaining, and verifies projection zero only after the terminal event.
2. **Per-lot ordinary-close notification identity — addressed**: the plan now uses
   `close:<canonical broker deal key>`, freezes all ordered split events/lots/quantities, and creates one
   Outbox intent only after the complete split set and projection succeed.
3. **Voided terminal allocation still effective — addressed**: the plan now derives authoritative void
   ids from canonical events, propagates them to all allocation consumers, retains old allocation rows,
   and defines an atomic correction/readback path.

## Assumptions tested

1. Pending zero-price evidence can block action without changing the financial projection.
2. The same ledger snapshot can supply allocations, effective void ids and reservation overlay.
3. No-settlement observation can prove the absence of settlement without requiring its own terminal
   postcondition in advance.
4. A single broker deal can close multiple target lots.
5. Ledger event grain and notification subject grain remain intentionally different.
6. Lifecycle evidence may require one terminal event/allocation per target lot.
7. Void effectiveness is append-only and derived from valid canonical events.
8. Correction never exposes a reopened lot as actionable.
9. Missing broker identity cannot silently fall back to raw or per-event notification keys.
10. Migration suppression precedes dispatcher activation.
11. Inbox completion after evidence acceptance is recoverable and does not own later cause progress.
12. Unknown delivery remains frozen from automatic resend.

## Special review lenses

### Architecture boundary review

The revised plan keeps financial authority in the ledger, makes reservation a read overlay rather than a
second projection, and places evidence assembly, pure resolution, transactional writing and delivery in
separate owners. The three previously blocking architecture defects are closed.

### Best-practice review

The fail-closed evidence contract, append-only void correction, CAS revisions, transactional Outbox and
crash-boundary tests are appropriate. One top-level acceptance invariant still contradicts the explicit
per-lot event model and therefore is not safe to hand directly to an implementation agent.

### Optimal-solution review

Reusing the existing per-lot ledger event/allocation grain and aggregating only at the notification layer
is the minimal correct design. Collapsing a multi-lot broker operation into one terminal event would make
target-lot projection and allocation less precise and is not an acceptable way to satisfy the current
success criterion.

### Overengineering review

No new second ledger, provisional close event or mutable allocation status was introduced. The lifecycle
overlay facade is justified because many action surfaces must apply the same reservation and void facts.
No material overengineering finding remains.

### Overcoupling review

The notification identity is now correctly decoupled from per-lot event ids. The remaining issue is a
document-level coupling in the success criteria: broker-source uniqueness is incorrectly expressed as
single-event cardinality.

## Findings

### 1-未修复-高-成功标准仍要求每笔 Futu deal 至多一个 terminal event，与已冻结的多 lot 拆分模型冲突

- **位置**: 第 17 节 Success criteria 第 1 项；对照第 11.2 节普通平仓聚合与第 10.5/14 节
  per-lot allocation/writer
- **问题类型**: 验收契约矛盾 / ledger grain 错误 / implementation handoff blocker
- **当前写法**: 对“同一 Futu deal 经 Push、Poll、Inbox retry”要求
  `terminal ledger event 至多一条`、`lifecycle allocation 唯一`。同一方案又明确一个 broker deal
  可以拆成多个 canonical close events，并冻结全部 ordered event ids、target lots 和 quantities。
- **反例/失败场景**: 一笔 Futu close deal 关闭两个 FIFO target lots。正确写入是两个确定性的
  per-lot close events；通知层按一个 canonical broker deal key 聚合成一条 Outbox。若实现者按
  Success criteria 强制“至多一个 event”，就必须丢失一个 target-lot binding、把两个 lot 合并进
  非既有粒度的 event，或错误地让验收失败。
- **为什么有问题**: Broker source identity、ledger event identity、lifecycle allocation identity
  和 notification identity 是四个不同粒度。此次修订已经正确分离 ledger 与通知，但顶层成功标准
  又把 source 去重写成 event/allocation 单例，直接否定了该设计。成功标准是实施与验收的最终依据，
  不能依赖实现者自行判断应忽略哪一条。
- **直接证据**:
  - 计划第 679-689 行明确一个 broker deal 可以产生多个 split close events，最终只创建一个
    aggregate Outbox。
  - 计划第 1246-1250 行却要求同一 deal 的 terminal event 至多一条、allocation 唯一。
  - `src/application/ledger/commands.py:386-440` 按每个 match 构造并原子写入 split events，同时保存
    `split_count/split_index/allocated_contracts`。
  - `src/application/ledger/writer.py:779-790` 明确 lifecycle terminal plan 是“一 allocation 对应一
    terminal event”，所以多 target lot 也合法产生多个 event/allocation。
- **影响**: 实施者可能为通过验收而破坏 canonical per-lot projection，或保留正确拆分后被错误判定
  失败；测试也无法同时满足“2/3 lots 多 event + 单通知”和“每 deal 至多一 event”。这会把资金账本
  粒度重新与通知粒度耦合。
- **建议改法和验证点**:
  - 将成功标准改为：每个 canonical broker deal 只接受一次，产生一个完整且确定性的 terminal
    split set；每个 `(broker deal key, target lot id)` 至多一个 effective terminal event/allocation，
    split set 不重复、不缺失、总 contracts 等于 source deal。
  - 通知成功标准单独保持：每个 broker deal 只有一个 aggregate final intent；lifecycle case 的
    interim/final transition 上限仍按一条或两条计算。
  - 增加验收断言：一笔 deal 关闭 2/3 lots 时分别得到 2/3 个 per-lot events、同数量 allocations、
    一个 aggregate Outbox；Push/Poll/replay 后 event set 与 Outbox 都不增长。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高
