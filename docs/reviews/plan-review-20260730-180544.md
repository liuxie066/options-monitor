## Special review lenses

### Architecture boundary review

Discovery ownership, plan identity, output sealing, source adoption, Brief assembly, and rendering are now separated at the correct owners. Compatibility callers retain the list-returning facade, while scheduled planning uses an internal typed surface. One adjacent owner remains omitted: prefetch budget planning derives option-chain call counts from the same fetch plan.

### Best-practice review

The revised plan follows positive-evidence and single-observation practice: no empty-list inference, no TOCTOU rediscovery, exact target propagation, frozen timestamps, and fail-closed identity mismatch. The authority split also follows least-authority: display projection cannot suppress a complete adopted source graph.

### Optimal-solution review

Using the existing plan-time discovery is the smallest practical solution because scheduled planning already calls the provider and needs exact expirations. It is preferable to a second fetch-time observation, provider peer model, new source schema, or notification workflow.

### Overengineering review

No overengineering finding. The internal typed discovery result and additive fetch-plan evidence are necessary to preserve the result of an existing provider call. Public facades and v1 source/delivery contracts remain stable.

### Overcoupling review

The plan avoids coupling the renderer to raw provider payloads and avoids coupling local warning validity to global delivery authority. Manifest/status equality is limited to the same sealed quote fact. The remaining budget-count mismatch is an adjacent derived-view consistency issue, not a reason to broaden public contracts.

## Findings

### PR-01-未修复-中-prefetch budget 仍会把 discovery-empty 计算为至少一次 option-chain call

- **位置**: Scheduled aggregation §5.1；Slice A owner boundary；验收矩阵 §7.1/§7.4；Slice A tests
- **问题类型**: 架构边界 / 最佳实践偏离 / 测试缺口 / observability inconsistency
- **当前写法**: 计划明确 discovery `success_empty` 直接发布零行 evidence，不调用 symbol fetch、CLI 或 option chain，并要求 global plan/receipt 绑定 frozen outcome。Slice A 纳入 `multi_tick/required_data_prefetch.py`，但未纳入 prefetch budget owner 或其测试。
- **反例/失败场景**: discovery 成功返回零 expirations，typed fetch plan 正确 short-circuit 为零 chain calls。现有 `estimate_prefetch_option_chain_calls()` 只看到 side plans 存在、explicit expirations 为空，返回 `max(1, 0)=1`；`_global_required_data_plan_summary()` 也使用同样的至少一次规则。多个 success-empty symbols 会被错误拆成多个 budget waves，summary/metrics 声称计划了 chain calls，甚至可能被标记 oversized，虽然执行路径明确不允许任何 chain call。
- **为什么有问题**: 这不会直接放宽报告 authority，但会让调度、容量计划和审计事实与 sealed fetch plan 冲突。实现 Agent若只修改计划列出的 owners，核心功能可能通过，而运行指标仍无法证明“没有调用 chain”，并可能增加不必要的 wave latency。
- **直接证据**:
  - 计划第 224-235、529-535、601-613 行要求 discovery-empty 不调用 fetch/CLI/chain，且测试唯一 provider observation。
  - `src/application/required_data_prefetch_planning.py:578-598` 在 fetch plan 有 side plans、explicit expirations 为空时返回 `max(1, len(expirations))`。
  - `src/application/multi_tick/required_data_prefetch.py:328-356` 同样把有 strategy requirements 的零 expiration 估算为至少一次 chain call。
  - `src/application/required_data_prefetch_planning.py:509-575` 使用该估算拆分 waves、计算 totals 和 oversized symbols。
  - Slice A 第 461-481 行没有包含 `src/application/required_data_prefetch_planning.py`；focused tests 没有包含 `tests/test_required_data_prefetch_budget.py`。
- **影响**: budget/summary/observability 与真实执行不一致；大量成功空 symbol 可能产生不必要的串行 waves 和运行时延；review 无法用 budget evidence证明 chain call 确实为 0。
- **建议改法和验证点**:
  - 将 `src/application/required_data_prefetch_planning.py` 加入 Slice A。
  - 让 `estimate_prefetch_option_chain_calls()` 和 `_global_required_data_plan_summary()` 读取 typed discovery outcome：
    - `success_empty`、`projection_empty`、discovery error -> 0 chain calls；
    - `success_rows` -> exact projected target count；
    - 缺少 typed evidence -> fail closed，不使用 `max(1, 0)` 猜测 scheduled call count。
  - 将 `tests/test_required_data_prefetch_budget.py` 加入 focused gate；断言 discovery-empty 的 symbol/wave/global totals 均为 0，多个 zero-call symbols 不被错误 oversized，success-rows 仍按 exact targets 计数。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
