# Plan Review

## Reviewed target and scope

- **Target**: `docs/plans/run-scoped-required-data-snapshot-fix-plan-20260728.md`
- **Purpose**: 第二轮 adversarial review，判断修订后的 run-scoped required-data snapshot 方案是否已经 code-generation-ready。
- **Primary scope**: prepared portfolio context、cross-account plan union、manifest/receipt seal、account future barrier、partial/full failure、Daily Brief diff/notification 和兼容性。
- **Evidence scope**: 当前 plan、`tick_account_execution.py`、`pipeline_context.py`、`futu_portfolio_context.py`、`daily_decision_brief_service.py`、`tick_notification_flow.py`、`domain/domain/daily_decision_brief.py` 及现有测试。
- **Excluded actions**: 未实施代码、未修改 plan、未运行生产流程、未提交或推送。

## Assumptions tested

1. **prepared portfolio context 可安全移到 market prefetch 之前**：方向可行，但当前 plan 没有定义并发、deadline 或 cancellation；现有 loader 的 `portfolio_timeout_sec` 参数并未约束实际 I/O。
2. **partial manifest 一定投影为 degraded 而非 blocked**：被当前 blocker 聚合反例推翻。只要有 strategy failure 且所有成功 symbol 恰好没有候选，现有服务会把整个账户 blocked。
3. **保留现有 diff policy 仍能避免把证据缺失说成候选失效**：被直接推翻。现有 diff 对当前 brief 中缺失的前序 P0/P1 action 无条件生成 `candidate_invalidated`。
4. **failed manifest 不启动 pipeline，也能由现有 notification flow 自动形成 blocked outcome**：未成立。当前 flow 只遍历 account results，并依赖 `ran_scan`、scan target 或 `ran_pipeline_accounts` 进入 assembler；plan 未定义该分支的 result/artifact contract。
5. **manifest + exact receipt 是最小充分的 immutable market boundary**：成立。方案复用既有 quote receipt，没有复制另一份 payload，也没有扩大 domain/import 边界。

## Special review lenses

- **Architecture boundary**: market planning/fetch ownership已正确上移到 tick barrier；但 broker portfolio I/O 也被移入同一 barrier，必须有独立的时间与失败边界，不能让 planning dependency 无限阻塞 market acquisition。
- **Best-practice**: payload-first、receipt、terminal manifest commit marker 和只读 consumer 符合不可变快照惯例；partial/full failure 仍需显式状态表，而不能依赖现有聚合逻辑“自然得到”目标结果。
- **Optimal solution**: 复用 `merge_prefetch_symbol_configs()`、quote receipts 和 run state 是实际且低重复的路径；无需引入数据库或通用 snapshot framework。
- **Overengineering**: prepared portfolio manifest 是为了覆盖 direct Sell Call `avg_cost` 动态上界，有当前正确性依据；继续冻结 option context/FX 将超出需要，plan 已正确排除。
- **Overcoupling**: 保留普通 `--shared-required-data` 行为并用显式 frozen manifest 是合理解耦；剩余耦合风险集中在“context barrier 延迟 market barrier”和“数据缺口影响 diff/notification”两处，见 findings。

## Findings

### PR2-01-未修复-高-前置portfolio-context阶段没有受控deadline会把行情快照和整点消息一起阻塞
- **位置**: §5.1 Account planning context、§7 Account execution barrier、§11.3 Concurrency and retry
- **问题类型**: 并发恢复风险 / 契约缺失 / 最佳实践偏离
- **当前写法**: plan 要求对所有 scanning accounts 先调用 `load_portfolio_context()`，完成 prepared context 后才构造/fetch market snapshot；只测试 account workers、account order 和 prefetch 次数。
- **反例/失败场景**: 一个账户的 Futu account balance/position query 卡住，另一个账户 context 已完成。由于 context preparation 是 prefetch 前硬屏障，market prefetch、两个账户 scan 和整点通知全部等待；如果按账户串行准备，两个账户还会累加等待。原本只影响一个账户 Covered Call 的依赖，扩大为整个 run 的可用性故障。
- **为什么有问题**: 该 work unit 本身源自“整点消息未送达/延迟”的运营问题。将无明确超时的 broker I/O 放到全局 critical path，会用一致性修复重新引入更大的通知缺失风险。plan 没有规定并行度、共享绝对 deadline、超时后的 `unavailable` 产物或迟到 future 的处理，implementation agent 必须自行设计。
- **直接证据**: plan `:64-85,192-201` 把 context preparation 放在 prefetch barrier 之前；`src/application/pipeline_context.py:379-422` 虽接收 `portfolio_timeout_sec`，但该值没有传入 `load_portfolio_context()`；`src/application/futu_portfolio_context.py:457-491` 的 balance/position gateway 查询没有该 application deadline；现有 `src/application/tick_account_execution.py:53-72` 只对账户 pipeline 提供 executor，不覆盖新增的 planning-context 阶段。
- **影响**: 整个 run 卡住 / 整点通知延迟或缺失 / 一个账户故障扩散到全部账户 / 后续返工
- **建议改法和验证点**:
  - 在 plan 中为 context preparation 定义独立 executor 和一个 run-scoped absolute deadline；每个账户只能消费剩余预算，不得按账户重新获得完整 timeout。
  - deadline 到达后，未完成账户原子发布 `status=unavailable, reason=portfolio_context_deadline_exceeded`；已完成账户结果保留，market prefetch 立即继续。
  - 明确取消/忽略迟到 future，迟到结果不得覆盖 terminal prepared-context manifest。
  - 增加测试：一个账户永久阻塞、另一个立即成功；断言 wall-clock 有界、成功 context 被保留、失败账户 call disabled、Sell Put prefetch 仍只执行一次且 account order 不影响结果。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR2-02-未修复-高-partial失败加零候选会被现有聚合规则误判为整账户blocked
- **位置**: §8.2 Symbol-level failure handling、§9.2 Decision policy、§11.5 Failure semantics
- **问题类型**: 状态机漏洞 / 不可直接实施 / 测试缺口
- **当前写法**: plan 要求每个 failed symbol 写 `strategy_scan_failure`，同时规定 partial manifest 只产生 degraded gap、其它 ready symbols 继续，单 symbol failure 不阻断账户。
- **反例/失败场景**: 9898.HK snapshot failed，另外四个 ready symbols 都成功扫描但在当前阈值下合法得到 0 candidates。failed symbol 按 plan 写入 strategy failure；整个账户的 put/call/combo rows 都为空。现有 Daily Brief blocker 因“存在 strategy failure 且没有任一 candidate row”把账户设为 blocked，尽管结构化扫描来源并非全部不可用。
- **为什么有问题**: “成功执行但没有候选”和“策略执行失败”被当前 account-level predicate 混在一起。仅物化 empty artifacts 和 prefetch gap 不能实现 plan 声称的 partial/degraded 语义；如果不明确修改可用性聚合，验收场景会直接失败。
- **直接证据**: plan `:247-256,280-285,447-453` 同时要求写 strategy failure 和 partial degraded；`src/application/daily_decision_brief_service.py:409-431` 计算 `all_decision_sources_unavailable` 后，又以 `strategy_failures and not (put_rows or call_rows or combo_rows)` 独立追加 `candidate_strategy_execution_failed` blocker；`:442-452` 只要有任一 blocker 就设为 `blocked`。
- **影响**: 单 symbol 数据缺口扩大为账户级阻断 / 用户丢失其它可信零候选或 Close Advice 结论 / 验收不可通过
- **建议改法和验证点**:
  - 在 plan 中增加明确的 availability aggregation：按 `symbol + strategy_family` 记录 `completed | unavailable | failed`，block 只在所有相关结构化 decision sources 都不可用，不能用“是否有候选行”代理执行可用性。
  - `candidate_count=0` 的成功扫描必须算 available；frozen snapshot unavailable 只影响对应 symbol/family。
  - 指定需要修改 `daily_decision_brief_service.py` 的 blocker predicate 和输入 artifact，而不仅是 `_append_prefetch_gaps()`。
  - 新增回归：一个 failed symbol + 多个成功但 0 candidate symbols + 可读 account context，断言 `status=degraded`、非 blocked、gap 唯一且没有虚构候选。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR2-03-未修复-高-禁止虚假候选失效与保留现有diff-policy互相矛盾
- **位置**: §9.2 Decision policy、§10 S4、§3 Non-goals
- **问题类型**: 契约缺失 / open question 未收敛 / 状态机漏洞
- **当前写法**: plan 规定行情证据不可用时不得断言上一轮 candidate 已失效，同时又规定继续使用现有 diff policy、不得修改 material-change policy。
- **反例/失败场景**: 上一轮 3690.HK 有 P1 Sell Put action；本轮该 symbol snapshot failed，partial brief 抑制这条 action。当前 diff 看到 previous action 在 current actions 中缺失，会无条件产生 material `candidate_invalidated`，renderer/notification 因而把“未知”表达成“失效”。
- **为什么有问题**: 这是同一份计划中的直接契约冲突。数据缺失只能支持 `unknown/unavailable`，不能支持 invalidation；现有 diff 没有读取 `data_gaps` 来区分二者。S4 只列 service/renderer 周边文件，没有把 domain diff contract 纳入修改和测试。
- **直接证据**: plan `:29,282-285,376-386` 同时声明“不改 material-change policy”“不得断言失效”和“防止 invalidated”；`domain/domain/daily_decision_brief.py:674-688` 对任何从 current actions 消失的前序 active P0/P1 action生成 `candidate_invalidated`/`action_invalidated`，未检查 data gaps。
- **影响**: 向用户发送错误状态变化 / 错误清除或替换上一轮建议 / public diff contract 被实施 Agent 临时改写 / review 不可验收
- **建议改法和验证点**:
  - 在 plan 中二选一并冻结契约：
    1. 推荐：让 diff 对 `required_data_snapshot_unavailable` 覆盖的 `symbol + strategy_family` 抑制 `candidate_invalidated`，并生成明确的 material `candidate_evidence_unavailable`；或
    2. 在 current brief 中保留同 action identity 的 `observe/blocked` evidence-unavailable action，并同步定义 diff/renderer 语义。
  - 将 `domain/domain/daily_decision_brief.py`、renderer 和 domain tests 加入 S4 files。
  - 明确这不是阈值调整，而是 invalidation evidence contract 修正。
  - 测试上一轮有 candidate、本轮同 symbol gap：消息只能说证据不可用；恢复后再按真实条件决定 recovered/invalidated。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR2-04-未修复-中-full-failure分支没有定义可被现有notification-flow消费的账户结果契约
- **位置**: §7 Account execution barrier、§9.2 Decision policy、§11.5 Failure semantics
- **问题类型**: 契约缺失 / 不可直接实施
- **当前写法**: manifest `failed` 时不启动 account pipeline，返回 typed run/account failure，并“交给现有 notification flow”形成 blocked/operational outcome。
- **反例/失败场景**: 所有 symbols failed，account futures 完全不提交。如果 outcome 中没有每账户 result，notification flow 没有对象可遍历；如果 result 的 `ran_scan=false` 且没有 scheduled scan target，它会直接跳过 brief assembly。反之若为了进入 assembler 伪造 `ran_scan=true`，又会与“pipeline 未启动”语义冲突。
- **为什么有问题**: 当前 `TickAccountExecutionOutcome`、scheduler target 和 Daily Brief assembler 对 pipeline success/ran_scan 有明确但不同的信号。plan 没有定义 failed-manifest 时必须写哪些 account artifacts、`results`/`ran_pipeline_accounts`/`scheduled_scan_targets_by_account` 各是什么，以及最终返回码/通知动作；“existing flow”不能自动补出这些状态。
- **直接证据**: plan `:200-201,282-284,454-458` 只描述结果意图；`src/application/tick_account_execution.py:107-115,160-195` 的 outcome 只从实际 account outcomes 聚合 results 和 targets；`src/application/tick_notification_flow.py:699-731` 只遍历 results，并要求 scan target、ran pipeline 或 `ran_scan=true` 才组装 brief；`:741-786` 再以 `ran_pipeline_accounts` 决定 reliable/failure artifact。
- **影响**: full failure 静默跳过 / 错误返回成功 / fixed failure 与 normal brief 混淆 / 实施 Agent 生成互相矛盾的状态
- **建议改法和验证点**:
  - 为 manifest `failed` / manifest publish failure 分别给出状态表：per-account `AccountResult`、`account_metrics`、scheduled scan target、`ran_pipeline_accounts`、failure artifact、tick return code 和是否允许 fixed failure notification。
  - 不复用 `ran_scan=true` 表示“计划过但未执行”；若现有 DTO 不够，增加明确的 `scan_attempt_status` 或专用 failure preparation path。
  - 测试 scheduled fixed-due、non-fixed、manual、`--no-send` 四种触发，断言 normal actionable brief 永不发送、审计和 idempotency status 一致。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 中

## Open Questions

1. context preparation 的 absolute deadline 应复用哪个现有 runtime budget？如果沿用 `portfolio_timeout_sec`，必须把它从当前未生效的参数变成真实 deadline，并定义多账户共享方式。
2. evidence-unavailable 是否需要新的 public diff `change_type`，还是只抑制 invalidation 并依赖 data-gap materiality？两种方案会影响 renderer、repository candidate lifecycle 和通知触发。
3. full manifest failure 是否应该发送 existing `fixed_failure`，还是只产生运营告警并以非零退出？需要与“整点消息没有”的用户预期明确对齐。
4. prepared context 的迟到 I/O 能否被底层 gateway 真正取消？若不能，必须保证其结果被隔离且不会在 terminal manifest 后写入 run account state。

## Residual risks and suggested tracking

- receipt freshness窗口可能在超长 account pipeline 中过期；应记录 seal-to-consume latency，并在实现中验证预计上界。
- 两个账户的 portfolio context 观察时间不完全相同是允许的账户事实差异，但必须在 manifest/audit 中保留各自 source time。
- run workspace 仍可能留下未 sealed 的 raw/CSV；consumer 以 terminal manifest 为唯一 commit marker可以隔离该残留，运维清理另行跟踪。
- 计划引用的 `tests/test_position_advice_candidate_capture.py` 当前不存在；实施时应按计划要求解析为现有 `tests/test_position_advice_candidate_capture_runtime.py` 或提供同等覆盖。
- 建议将 PR2-01 至 PR2-04 全部回写同一 plan artifact，并再次 planreview；前三项是进入实现前 blockers。

## Final conclusion

**fail**

修订版已经正确解决上一轮的 market-plan union、planning facts 冻结、typed symbol failure 和公共 CLI 兼容边界，整体方向明显收敛。但新增的前置 context barrier 尚无真实 deadline，partial failure 与现有 blocker/diff 状态机仍存在可复现冲突，full-failure handoff 也未形成可执行契约。当前仍不应交给 implementation agent。
