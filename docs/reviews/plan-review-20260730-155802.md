# Plan Review

## Reviewed target and scope

- Target: `docs/plans/daily-brief-local-gap-degraded-delivery-plan-20260730.md`
- Revision focus: complete end-to-end chain from provider outcome through confirmed baseline
- Full scope: coverage identity/classification、account isolation、source dependencies/freshness、strategy terminals、Brief gap state、revision/envelope atomicity、retry/recovery
- Review lenses: architecture boundary、best practice、optimal solution、overengineering、overcoupling

## Assumptions tested

- physical outcome 与 account projection 能隔离不同账户/需求；
- success-empty、provider failure、not-attempted 和 integrity failure 不会互相伪装；
- v1/v2 source dependency validation 可并存且 fail closed；
- portfolio prefilter 不会绕过 ready quote provenance；
- strategy status terminal 能无歧义承载 coverage outcome；
- consumer/gap identity 不会因无关 plan/catalog 变化旋转；
- Brief revision、message、envelope 和 confirmed baseline 在同一原子 ownership 下冻结；
- crash、late confirmation、concurrent scheduled run 和 exact retry 有确定恢复路径。

本轮没有在首个问题处停止。此前 findings 已得到实质修复：

- physical fetch 与 account consumer projection 已分层；
- consumer identity 已与整份 account plan 解耦；
- `not_attempted` 与成功空/失败明确区分；
- v1/v2 dependency validation 和 account-relevant freshness 已有版本化方向；
- stable gap identity 与可变状态已分离；
- scheduled successful Brief 已定义 repository-owned 单锁 prepare/commit boundary。

## Findings

### 1-未修复-高-portfolio prefilter 与 ready-scope quote dependency/freshness 规则互相冲突

- **位置**: Phase B candidate capture/source dependencies；portfolio prefilter；zero-quote exception
- **问题类型**: 契约缺失 / 过度耦合 / 不可直接实施
- **当前写法**: 计划一方面要求 Account Run adopt 自身所有 `ready` opening scopes 的 quote
  snapshots，candidate source quote dependencies 必须与其精确相等；另一方面又允许只要账户
  `portfolio_prefilter` 为 not-applicable 就使用零 quote dependencies。`source_observed_at`
  只定义了 coverage projections/product-catalog-only 的取值，没有定义 prefilter-only 来源。
- **反例/失败场景**: 某 Covered Call scope 的 run-global provider coverage 已为 `ready`，
  但 `sy` 因当前账户没有可覆盖股票而被 portfolio prefilter 判 not-applicable。
  按 ready-scope 规则必须 adopt quote；按 prefilter exception 又允许零 quote。选择前者会让一个
  不可行动 scope 因无关 quote freshness 阻断，选择后者则违反 exact dependency set，且无法为
  candidate receipt 提供合法 `source_observed_at`。
- **为什么有问题**: provider coverage 与账户 action relevance 是两个边界。计划正确地把
  portfolio prefilter 留在 Account Run，但没有定义它如何从“account-relevant ready scopes”
  中排除 scope、如何绑定 portfolio evidence，以及 quote dependency/freshness 如何随之重算。
- **直接证据**:
  - 目标计划 `327-330` 声明 portfolio prefilter 由 Account Run/portfolio receipt 所有；
  - 目标计划 `363-368` 要求所有 ready opening scopes 的 exact quote dependencies；
  - 目标计划 `369-374` 又允许 portfolio-prefilter not-applicable 时零 quotes，但只定义
    projection/catalog observation time；
  - `src/application/position_advice_account_sources.py:139-176` 当前 candidate source
    无条件加载 quote dependencies，并从 quote receipts 计算 observation；
  - `src/application/position_advice_account_sources.py:527-535` 当前 capture 没有 quote receipts
    会直接失败。
- **影响**: 实施者可能选择互斥规则之一，导致不必要的 fixed_failure，或发布缺少必要 quote/
  freshness provenance 的 candidate source；核心“正常或降级继续发送”行为无法稳定验收。
- **建议改法和验证点**: 明确定义 `action_relevant_scope_results[]`：
  provider coverage projection 先保持原 outcome；Account Run 再用当前 portfolio receipt
  产生独立 prefilter decision。被合法 prefilter 的 scope 必须：
  1. 从 action-relevant ready quote set 中排除；
  2. 在 capture/source 中保存 consumer scope id、`applicability_basis=portfolio_prefilter`、
     portfolio snapshot/digest；
  3. candidate receipt dependencies 包含 coverage + portfolio（以及其余全局 source graph
     既有依赖），但不包含该 scope quote；
  4. prefilter-only source observation 使用 portfolio receipt observation，expiry 取所有
     adopted dependencies 的最早值。
  测试 ready coverage + no-shares prefilter、同一 physical fetch 下另一账户仍 adopt quote、
  prefilter portfolio receipt stale/tampered、mixed prefiltered/non-prefiltered ready scopes 和
  zero-quote freshness。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### 2-未修复-高-coverage outcome 到 strategy terminal 没有确定映射，success-empty 可被写成 completed 或 unavailable

- **位置**: Phase B `strategy_scan_status.v2` terminal contract、capture reliability、Daily Brief gap projection
- **问题类型**: 契约缺失 / 状态机漏洞 / 不可直接实施
- **当前写法**: 计划定义了 `completed|unavailable|failed|not_applicable` 四类 terminal，
  只说明 `unavailable` 引用 coverage outcome、`failed` 表示扫描程序失败；没有逐项规定
  `ready`、`success_empty`、`coverage_incomplete`、local `provider_error`、product/portfolio
  not-applicable 以及 global blockers 应映射到哪个 terminal、是否必须生成 canonical empty artifacts。
- **反例/失败场景**: OpenD 成功返回合法零行。一个实现把它写成
  `completed(candidate_count=0)`，另一个实现写成 `unavailable(reason=success_empty)`。
  前者可能被 Daily Brief 当作正常零候选而不告警；后者产生 degraded gap。两者都能从当前文字找到
  支持，却只有后者符合本计划的用户目标。
- **为什么有问题**: strategy status 是 coverage 与 Daily Brief data gap 之间的公共状态机。
  terminal mapping 不唯一会让同一 provider evidence 在 capture、index counts、source reliability
  和 renderer 中产生不同语义，迫使下游重新解释原始 outcome。
- **直接证据**:
  - 目标计划 `297-307` 只列 terminal 和部分字段约束；
  - 目标计划 `318-330` 要求 capture 引用 coverage，但未给 terminal mapping table；
  - 目标计划 `605-623` 验收 success-empty degraded 和四类 counts，却未锁定中间状态；
  - `src/application/strategy_scan_status.py:12-75` 当前 v1 terminal validator 只区分
    completed 与 non-completed；
  - `src/application/strategy_scan_status.py:126-205` index 对缺失/无效状态合成 failed 并计数；
  - `src/application/daily_decision_brief_service.py:2332-2360` 当前 reader 把 completed 以外的
    status 全部投影为 data gap，说明 terminal 选择直接改变用户可见行为。
- **影响**: success-empty 可能静默成普通零候选，局部 provider error 可能误写 failed 并升级为
  全局失败，或 product/prefilter not-applicable 被错误渲染为告警；测试也无法形成唯一 oracle。
- **建议改法和验证点**: 在计划中加入唯一映射表：
  - action-relevant `ready` 且 scanner 成功 → `completed`；
  - `success_empty|coverage_incomplete|allowlisted local provider_error` → `unavailable`
    并强制 coverage scope/outcome/reason binding；
  - product catalog 或已验证 portfolio prefilter → `not_applicable`，分别绑定 catalog 或
    portfolio evidence；
  - scanner 自身 exception/timeout/artifact publication failure → `failed`；
  - `not_attempted|parse_error|integrity_error|provider-global error` 不发布可接受的 successful
    v2 capture/index，Account Run 直接 blocked。
  同时规定每类是否需要 canonical empty artifacts、candidate_count 字段和 index count，
  并逐行测试 mapping、非法组合和 Daily Brief renderer outcome。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

## Open Questions

- portfolio-prefiltered scope 是否仍需要生成 canonical empty candidate artifacts？建议生成并绑定
  status/capture digest，便于保持现有 artifact completeness，但不得伪装成 provider scan completed。

## Residual Risks

- 新原子 prepare API 的临界区扩大，应保持 provider I/O 与 source adoption 在锁外。
  Tracking destination: Phase C repository concurrency tests。
- delivery state、account current 和 shared index 是多文件发布；当前计划已指定 commit marker，
  但实现必须验证所有 crash injection points。Tracking destination:
  Daily Brief repository crash-recovery tests。
- failure-budget `not_attempted` 选择 global blocked 是保守策略，可能增加 fixed_failure；
  上线后应记录 stop reason/count，再决定是否需要独立受控降级政策。Tracking destination:
  runtime metrics and a separate policy review。

## Conclusion

`fail`

本轮完整审查共发现 2 个高风险问题，均已一次列全。Phase A identity/freshness 与 Phase C
atomic baseline 方向已经收敛；在 Phase B prefilter dependency 和 terminal mapping 明确前，
计划仍不适合交给 implementation agent。
