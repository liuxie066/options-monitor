## Findings

### 1-未修复-中-fixed report 的 selector 使用 diff 重排候选而 renderer 不使用，confirmed envelope 可证明用户看到了另一条 Combo

- **入口/函数**: `tick_notification_flow` -> `select_rendered_combo_candidate_rows()` -> `render_fixed_report()` / `render_fixed_report_card_markdown()` -> `prepare_daily_decision_brief_delivery()` -> `read_combo_candidate_exposures()`
- **文件(行号)**: `src/application/tick_notification_flow.py:943-977`; `src/application/daily_decision_brief_renderer.py:95-140, 195-222, 271-294, 720-740`; `src/application/daily_decision_brief_repository.py:1945-1975`
- **输入场景**: fixed report 中有两条同策略 Combo（原始顺序 NVDA、AMD），`max_candidates_per_strategy=1`，本轮 diff 把第二条 AMD 标记为 changed candidate。
- **实际分支**: tick 把 `diff` 传给 evidence selector；selector 的 `_candidate_views()` 先放 changed rows，因此选择 AMD 并把 AMD occurrence/exposure 写入 render context。随后文本和卡片 renderer 都没有 `diff` 参数，调用 `build_daily_brief_user_view()` 时 `normalized_diff={}`，按原始顺序选择 NVDA。delivery repository 只能验证 render-context IDs 可从 frozen Brief 重算，无法发现它们与实际 message/card 的候选不同。
- **预期行为**: 同一个 fixed-report projection 必须唯一决定文本、卡片和 envelope evidence；message digest 所绑定的实际候选集合应与 `candidate_occurrence_ids` / `candidate_exposure_ids` 一一相等。
- **实际行为**: provider confirmed 后，未展示的 AMD 可被升级为 `exact_delivered_candidate`，实际展示的 NVDA 反而只有 live evidence；证据链与用户真正看到的消息相反。
- **直接证据**: 最小反例直接调用生产 projection：actual view 的 Combo symbol 为 `NVDA`，`select_rendered_combo_candidate_rows(..., diff=AMD_changed, limit=1)` 返回 `AMD`。调用链第 947 行只给 selector 传 `diff`，第 968-976 行调用两个 fixed renderer 时均未传；renderer 第 201/216 行也未把 diff 传给已有的 `build_daily_brief_user_view(diff=...)` 参数。当前测试覆盖 candidate-alert limit 一致性，但没有 fixed-report changed-row 重排的一致性断言。
- **影响**: 精确投递事实可能产生 false positive 和 false negative；全局 matcher 会把未展示 pair 当作最高等级证据，从而改变 proposal/ambiguity，用户确认界面和后续审计都可能依据错误的“已看到候选”事实。
- **建议改法和验证点**: 由一个实际 projection 结果同时驱动文本、卡片和 evidence，或至少让 fixed text/card renderer 与 selector 接收并消费同一份 canonical diff；不要独立重复选择。新增 fixed report 回归：多条 Combo、limit=1、第二条 changed，断言文本、卡片、rendered Combo identities、occurrence IDs、exposure IDs 完全对应同一合约 pair；再覆盖无 diff 与 changed 数超过 limit 的行为。
