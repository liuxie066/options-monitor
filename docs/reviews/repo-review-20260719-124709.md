## Executive Conclusion

Two material, directly reproducible production-safety defects were found. Both are high severity:

1. Every normal tick can silently and irreversibly delete run evidence older than seven days, bypassing the repository's controlled cleanup boundary.
2. A generic crash in one multi-source trade-intake worker does not cancel sibling workers, so the coordinator can remain alive indefinitely while one account is no longer being monitored.

The repository otherwise passes its current automated baseline (`2708 passed, 10 skipped`) and Ruff/compile checks. Those gates do not cover the two failure modes above.

## Findings

### DR-001-未修复-高-Tick 启动路径静默删除七天前的 output run 证据

- **入口/函数**: `multi_account_tick` → `prepare_tick_run_workspace()` → `_cleanup_old_run_dirs()`
- **文件(行号)**:
  - `src/application/multi_account_tick.py:385`
  - `src/application/tick_run_workspace.py:22-28`
  - `src/application/tick_run_workspace.py:54-71`
  - 对照的受控清理实现：`src/application/service_cleanup.py:124-190`, `src/application/service_cleanup.py:455-513`
- **输入场景**: `output_runs/` 中存在名称匹配 `YYYYMMDDTHHMMSS`、目录 mtime 早于七天的历史 run；随后执行任何正常 tick。
- **实际分支**: `prepare_tick_run_workspace()` 在创建本次 run 之前无条件调用 `_cleanup_old_run_dirs(base)`；该函数按硬编码七天 cutoff 遍历目录并调用 `shutil.rmtree(..., ignore_errors=True)`。
- **预期行为**: `output_runs` 是运行、研究和审计证据。删除应由明确的 cleanup 操作统一负责，先 dry-run/列计划，再按保留天数、保留数量、当前 pointer 等约束确认执行，并输出操作记录。
- **实际行为**:
  - 正常 tick 隐式承担了破坏性清理职责。
  - 保留期固定为七天，无法配置或审计。
  - 不保护 `output_shared/state/last_run_dir.txt` 指向的 run；而清理发生在新 pointer 写入之前，因此旧 pointer 指向的历史 run 也可能先被删除。
  - `rmtree(ignore_errors=True)` 与两层 `except Exception: pass` 让删除失败、部分删除和 pointer 不一致都不可见。
- **直接证据**:
  - `tick_run_workspace.py:28` 无条件调用清理。
  - `tick_run_workspace.py:58-67` 计算七天 cutoff 并直接递归删除。
  - `tick_run_workspace.py:68-71` 吞掉所有错误。
  - `service_cleanup.py:137-190` 已存在保留天数、保留数量和 pointer 保护的计划逻辑；`service_cleanup.py:499` 明确区分 `dry_run` 与 `cleaned`，说明受控清理边界已经存在。
  - 直接复现：创建一个 mtime 为八天前的合法 run 目录，调用 `prepare_tick_run_workspace()` 后，`old_run_exists_after_tick_workspace_prepare` 为 `False`。
- **影响**: 历史运行证据被静默、不可逆删除；会削弱回放、问题追踪、审计和生产事故取证，并违反项目对删除 `output_runs` 需要显式确认的安全边界。
- **建议改法和验证点**:
  1. 从 tick workspace preparation 中移除 `_cleanup_old_run_dirs()`，让 `service cleanup` 成为唯一清理 owner。
  2. 若业务上必须自动保留，改为显式配置、可观测、可审计的独立维护任务，并复用 `_output_run_cleanup_plan()` 的 keep-count/pointer/path-safety 逻辑；不要在正常 tick 主链路直接删除。
  3. 添加回归测试：正常 tick 不删除任何旧 run；cleanup dry-run 不删除；确认 cleanup 保护 latest count 和 `last_run_dir` pointer；删除异常必须进入 operation result/log。
- **修复风险（低/中/高）**: 中。移除隐式清理本身风险低，但需确认磁盘容量由哪个定时维护任务接管，避免重新引入磁盘耗尽风险。
- **严重程度（低/中/高/严重）**: 高

### DR-002-未修复-高-多源 trade-intake 单源异常崩溃后协调器不会停止兄弟源

- **入口/函数**: `trade-intake` listener mode → `_coordinate_listener_sources()` → `_run_listener_source_loop()`
- **文件(行号)**:
  - `src/application/trades/auto_intake.py:151-194`
  - `src/application/trades/auto_intake.py:562-630`
  - 现有测试：`tests/test_trades_auto_intake_restart_policy.py:149-166`
- **输入场景**: 多 source 监听中，一个 source 在初始化或循环外路径抛出未处理异常；另一个 source 正常持续监听。
- **实际分支**:
  - worker 捕获异常后把结果转换为退出码 `1` 并放入 queue。
  - coordinator 只有在退出码等于认证专用码 `78` 时才调用 `stop_event.set()`。
  - 普通非零退出码仅记录到 `exit_code`，不会取消兄弟 worker。
  - coordinator 的 `while completed < len(threads)` 会继续等待所有 worker，随后还会执行无 timeout 的 `thread.join()`。
- **预期行为**: 任一 source 进入 terminal failure 后，整个多源 intake 应 fail closed：发布共享停止信号、在有界时间内停止兄弟 source、记录失败 source 的终态并让主进程返回非零，以便 systemd 重启和告警。
- **实际行为**: 正常兄弟 source 可永久运行，coordinator 永不返回；systemd 仍看到服务进程 active，失败账户的 intake 却已停止，形成“部分死亡但整体看似在线”的不可恢复状态。
- **直接证据**:
  - `auto_intake.py:159-165` 把任意 worker exception 转成 `result = 1`。
  - `auto_intake.py:182-186` 仅认证码 `78` 设置 shared stop event；普通非零码不设置。
  - `auto_intake.py:176-188` 等待全部结果并无界 join。
  - `_run_listener_source_loop()` 在进入 `while` 内部的重试 `try` 之前，会直接读取必需 key、做路径/端口转换、构造 status payload 和 `OpenDTradePushListener`（`auto_intake.py:576-622`）；这些初始化异常可逃逸到 coordinator worker。
  - 直接复现：两个 source 中 `crash` source 抛 `RuntimeError`，`sibling` 等待 shared stop event；一秒后 coordinator 仍未返回（`returned_within_1s=False`），证明普通 crash 不触发兄弟取消。
  - 现有测试只覆盖认证失败触发 sibling cancellation，没有覆盖普通非零返回或未预期异常。
- **影响**: 某一账户交易推送可能停止消费，而服务仍处于 active；丢失/延迟 intake、review 和 receipt，且 systemd 无法通过进程退出触发恢复。该问题直接影响多账户生产监控的完整性。
- **建议改法和验证点**:
  1. 任一 terminal 非零 source result 都应设置 shared stop event；认证码可以保留优先级，但不应是唯一取消条件。
  2. coordinator 应采用有界 shutdown；若 sibling 未及时退出，返回明确错误并让进程边界完成强制清理，而不是无界 join。
  3. worker exception 时写入该 source 的 `crashed/terminal` status，包含异常类别和时间，避免 runtime status 继续展示旧的 `listening`。
  4. 添加测试：source 抛异常、source 返回普通非零、多个 source 近同时失败、sibling 不响应 stop event；断言退出码、停止信号、终态和有界返回。
- **修复风险（低/中/高）**: 中。fail-closed 会把单账户故障升级为服务重启，需结合 restart/backoff 策略避免 crash loop，但比长期静默部分失效更安全。
- **严重程度（低/中/高/严重）**: 高

## Overcoupling Review

- `prepare_tick_run_workspace()` 同时承担 workspace 创建和历史 retention 删除，形成不必要的生命周期耦合；DR-001 建议拆除该耦合并归还给已有 cleanup subsystem。
- multi-source coordinator 将认证失败视为唯一全局 terminal event，把通用 worker 生命周期错误与特定认证语义耦合；DR-002 建议将“任一 terminal failure 触发整体取消”设为协调器不变量，认证码只决定最终退出语义。
- 大型模块（如 `agent_tools/analysis.py`、`close_advice_runner.py`、`service_upgrade.py`、`runtime_status_impl.py`）存在维护复杂度，但本次没有仅凭体积报告 finding；需要具体错误链路才应拆分。

## Semantic Ownership Drift Review

- **已确认 drift**: output-run retention 同时存在于 tick startup 与 `service_cleanup.py`，且两套语义不同。前者硬编码、静默、无 pointer 保护；后者显式计划、保护和审计。应收敛为一个 owner。
- **已确认 drift**: trade-intake coordinator 的“全局停止”语义被认证错误码独占，而 generic source lifecycle failure 没有相同语义。全局 worker lifecycle 应由 coordinator 统一拥有。
- **未升级为 finding**: state JSON 与 audit append 的跨进程串行化仍需证明存在可并发调用同一 source 文件的公开入口；当前证据不足，不应猜测。

## State-Machine Review

### Tick run lifecycle

Expected invariant:

```text
prepare current run != destroy historical run evidence
```

Current transition:

```text
prepare -> silently delete old runs -> create current run -> best-effort pointer write
```

This allows evidence deletion and pointer inconsistency before current-run initialization completes.

### Multi-source trade-intake lifecycle

Expected invariant:

```text
any source terminal failure -> stop all sources -> persist terminal status -> process exits nonzero -> supervisor may recover
```

Current transition:

```text
auth failure(78) -> stop all
other failure/crash -> remember exit code -> keep siblings alive -> wait forever
```

The global service state therefore does not faithfully represent per-source liveness.
