## Assumptions tested

1. `OM_PYTHON` is intentionally the only explicit recovery path over a present incompatible repo venv.
2. Without `OM_PYTHON`, a present repo venv is authoritative and blocks `PYTHON`/PATH fallback, including broken or non-executable targets.
3. Bootstrap selection is distinct from repo-runtime selection and cannot select the target venv.
4. Explicit invalid overrides fail rather than silently falling through.
5. Service-upgrade cache identity remains based on interpreter implementation + major/minor + platform + dependency inputs, not an absolute release path.
6. Import guards use Python-3.9-parseable syntax and do not introduce a `domain -> src` dependency.
7. Direct arbitrary shebang execution and missing dev `.venv` for generated commands remain explicitly classified residual risks.

## Residual risks and tracking destination

- Arbitrary direct execution of internal shebang scripts can still resolve an unsupported `python3`; retained as an explicit non-goal/residual risk because broad shebang churn does not enforce interpreter identity. Installation/runtime docs should direct operators to supported launchers and `.venv/bin/python`.
- Generated release-plan commands require a prepared `.venv`; this yields an explicit missing-environment failure rather than silently selecting an old interpreter and is acceptable for repository developer workflows.
- Python 3.12 patch versions may differ while sharing a dependency cache; accepted by the user-confirmed minimum-minor contract, with implementation/platform/dependency inputs retained in the cache key.
