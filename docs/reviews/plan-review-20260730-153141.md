# Plan Review

## Reviewed target and scope

- Target: `docs/plans/daily-brief-local-gap-degraded-delivery-plan-20260730.md`
- Revision focus: run-global physical fetch 与 account consumer projection 的两层 coverage 契约
- Full scope: degraded delivery、account isolation、position-scoped gap、embedded alert state、confirmed baseline
- Review lenses: architecture boundary、best practice、optimal solution、overengineering、overcoupling

## Assumptions tested

- account plan hash 能在 union merge 前稳定绑定账户级 opening 与 position requirements；
- shared physical fetch outcome 不会把一个账户的 coverage 结论泄漏给另一个账户；
- Account Run 只采用与自身 account/plan hash 精确匹配的 consumer projections；
- position gap 在 Brief artifact 中保持逐仓位身份；
- gap transition 能基于上一份 confirmed normal Brief 区分首次、变化、持续、恢复和 retired。

上一轮的跨账户 projection 缺口已得到实质修复：计划现在明确分离
`physical_fetch_outcomes[]` 与 `consumer_scope_projections[]`，并绑定 account plan hash、
position requirement identity 和 provider health scope。

## Findings

### 1-未修复-高-告警 identity 同时包含可变原因且缺少 consumer/position scope，变化与恢复会被误判

- **位置**: Phase C 告警 identity、状态转换、`local_data_gap_state.v1`；Phase B position gap identity
- **问题类型**: 状态机漏洞 / 契约缺失 / 过度耦合
- **当前写法**: 告警 identity 定义为
  `account + market + symbol + strategy_family + purpose + reason_code`；状态机同时要求识别
  reason/severity changed。position gap 虽然在 Brief artifact 中逐仓位保留
  `position_lot_id`、requirement id 和 coverage scope ref，但这些字段没有进入 alert identity。
- **反例/失败场景**:
  1. 同一个 consumer scope 从 `success_empty` 变成 `provider_error`。因为 `reason_code`
     已变化，比较器看到的是旧 identity 消失和新 identity 首次出现，而不是
     `reason changed`；可能同时产生 recovered + new。
  2. 同一账户、symbol、strategy family 下两个不同 expiry 的 open positions 同时缺数据。
     两者 reason 相同，当前 identity 完全相同，会在 gap set/digest 或 transition 比较时被折叠；
     随后其中一个恢复时，无法判断应持续、恢复还是仍为 P0。
- **为什么有问题**: 稳定实体身份与可变状态被混在一个 key 中，同时 position-scoped
  ownership 又没有进入 key。这样既无法满足计划声明的 reason change transition，也无法保持
  “同 symbol 多仓位分别保留 position identity”的安全边界。
- **直接证据**:
  - 目标计划 `367-382` 要求 position gap 绑定 requirement/lot/scope，且 Brief artifact
    不得丢失逐仓位记录；
  - 目标计划 `419-443` 把 `reason_code` 放入 alert identity，却要求识别
    reason/severity change，并以 alert identity 构造 `gaps[]` 与 digest；
  - 目标计划 `521-526` 要求同 symbol 不同 expiry 不合并，并测试 reason changed。
- **影响**: 用户可见告警可能重复报“恢复 + 首次”、漏报仍未恢复的仓位，或错误解除 P0；
  baseline 一旦 confirmed，错误状态会成为下一轮权威比较基础，增加后续恢复难度。
- **建议改法和验证点**: 将稳定 `gap_identity` 与可变 gap state 分离。建议 identity 绑定
  `account + market + consumer_scope_id`；position gap 还必须绑定
  `requirement_id + position_lot_id`，opening gap绑定 canonical opening scope。
  `reason_code`、severity、outcome 和 basis 仅作为可比较状态字段，不进入 identity。
  明确定义 duplicate identity 为 integrity failure，并补充测试：
  同 scope reason 变化只生成 changed；同 symbol 两仓位保持两条；单仓位恢复不影响另一仓位；
  scope retirement 与普通 recovery 可区分；排序与 digest 对输入顺序稳定。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

## Open Questions

## Residual Risks

- `consumer_scope_id` 依赖 account plan hash；配置变化造成旧 scope retirement、新 scope first-seen
  是合理行为，但应在 Phase C contract tests 中固定。Tracking destination:
  Phase C `local_data_gap_state.v1` contract tests。
- coverage receipt 的字节/hash 完整性失败仍必须是 global blocker；只有 receipt 有效但某一
  account projection 语义无效时才允许 account-local blocked。Tracking destination:
  Phase A coverage validator tests。
- gap-only 变化不会创建 delivery action，因此没有其他正常发送原因时，恢复提示会延迟到下一份
  scheduled Brief；这是当前产品边界，应保留为显式验收事实。Tracking destination:
  Daily Brief product acceptance notes。

## Conclusion

`fail`

第五轮已解决上一轮的跨账户 coverage projection finding，但告警身份与可变状态尚未分离。
在 gap identity 能逐 consumer/position 稳定追踪前，不建议进入实现。
