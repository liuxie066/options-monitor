## Findings

### PRR2-01-未修复-高-生产者删除早于全部消费者迁移，S2 验收点会形成不可运行的中间状态

- **位置**: Slice S1 item 5; Slice S2 entire scope; Slice S3 items 1-5; per-slice quality/commit contract
- **问题类型**: migration ordering / independently invalid slice
- **当前写法**: S1 直接把 status index 切为 v2；S2 删除候选 CSV producer、canonical artifact 和 CLI/path 输出；直到 S3 才迁移 research、archive、Strategy Lab、Shadow Replay 的 CSV readers/fallbacks。
- **反例/失败场景**: S2 acceptance commit 存在于分支/PR 时，新运行已不再生成 candidate/reject/pair diagnostic CSV，但 research evidence 和 Shadow Replay 仍按旧路径/glob 读取。它们会把本应支持的新运行视为缺证据或生成空数据集。类似地，S1 若只发布 v2 index，尚未迁移的 research/archive 仍可能只寻找 v1。
- **直接证据**: 计划把 producer removal 放在 S2 items 1-7，把 `research/evidence.py`、`research/archive.py`、`shadow_replay/*` 和 CLI consumer migration 放在 S3 items 1-6；Gateflow 又要求每个 slice 在 DeepReview 后形成独立 acceptance commit。
- **影响**: per-slice tests 可能只能靠跳过旧消费者通过；任一中间提交不可安全测试、回滚或作为 PR review checkpoint，违反 gated work unit 的可验证性，并可能把“没有文件”重新误报为“没有候选”。
- **建议改法和验证点**: 固定 expand/migrate/contract 顺序：S1 additive 地发布 v2 status/snapshots/manifest，同时保留现有 v1 index 和 CSV writers；S2 将所有 current/historical consumers、CLI、archive、Strategy Lab、Shadow Replay 切到 manifest/snapshot/JSONL，并证明新旧输入分类正确，但仍保留旧 producers；S3 最后删除 candidate CSV writers、v1 status publication、`output_mode`、旧 flags/adapters，并加 forbidden-pattern guard。每个 slice 的 exit tests 都要证明该 checkpoint 自洽；S2 加“删除/拒绝 CSV 读取但文件仍存在也不打开”的 sentinel，S3 加“全流程不产生目标 CSV”。
- **修复风险**: 中
- **严重程度**: 高
