### S3-DR-01 — 未修复 — 高 — MTD 评测仍允许偷偷缩小账户范围或改成自然月

- **入口/函数**: `run_eval()` structural checks for `july_mtd_option_income` and
  `mtd_correction_follow_up`
- **文件(行号)**: `scripts/copilot_p1_eval.py:27-53,212-249`;
  `tests/test_copilot_p1_eval.py:10-27,57-143`
- **输入场景**: 模型先调用 `option_performance_report`，但传
  `{"period":"month","month":"2026-07","account":"lx"}`，随后回答“MTD lx 账户……”。
- **实际分支**: 结构评测只要求第一个工具名称正确，未检查关键工具输入；回答只要求包含
  “账户”，未要求“全部账户”。这种错误调用和错误范围仍可通过新增的专属检查。
- **预期行为**: 对用户未指定账户的精确 MTD 场景，首个工具必须是
  `option_performance_report`，其输入必须是 `period=mtd` 且不得包含 `account`；答案必须明确
  “全部账户”。
- **实际行为**: 工具名正确即可；自然月与单账户结果可伪装成 MTD 聚合答案。
- **直接证据**: `required_primary_tool_used` 仅比较 `tool_names[0]`；两个 case 的
  `required_response_terms` 仅包含泛化词“账户”；测试事件的 `tool_input` 为空且没有输入约束
  断言。
- **影响**: 线上原始失败中的两个核心问题——将 MTD 混为其他期间、只回答 lx 而未说明
  聚合范围——都可能在评测显示通过后复发。
- **建议改法和验证点**: 在 `EvalCase` 增加首工具必需输入与禁止字段，结构检查读取首个
  `tool_call.tool_input`；两个 MTD case 要求 `period=mtd`、禁止 `account`，答案要求
  “全部账户”。新增反例测试证明自然月 + lx 即使工具名正确也失败。
- **修复风险**: 低
- **严重程度**: 高

### S3-DR-02 — 未修复 — 中 — 正确首答后的纠正短句被强制重复读取同一报告

- **入口/函数**: `CASES` -> `mtd_correction_follow_up`
- **文件(行号)**: `scripts/copilot_p1_eval.py:46-53`
- **输入场景**: 同一 P1 会话的第一轮已成功读取并回答 MTD；下一轮用户仍说“我写的是mtd”。
- **实际分支**: 第二轮被标记为必须产生新的 read observation，并要求首工具再次为
  `option_performance_report`。
- **预期行为**: 若上一轮已有正确 canonical MTD evidence，可直接基于上下文澄清；若确实要
  重查，则只能调用同一个 canonical MTD 工具，不能退化为 generic analysis。
- **实际行为**: 即使无需刷新也必须机械重复调用，与现有“不要机械重复相同调用”和最小工具
  序列规则冲突，并增加线上延迟与 token 成本。
- **直接证据**: `mtd_correction_follow_up` 当前设置
  `requires_read_observation=True` 且 `required_primary_tool=option_performance_report`，没有
  “允许无调用、但若调用必须 canonical”的表达能力。
- **影响**: 正确行为会被误判失败，诱导模型制造重复调用；这会削弱本 work unit 同时追求的
  首次成功率与可读性/效率。
- **建议改法和验证点**: 增加“首工具可选”标志：无新调用时通过；一旦调用，首工具及其输入
  仍必须满足 MTD canonical contract。将该 follow-up 改为无需新 observation，并用测试覆盖
  缓存回答和错误 generic/错误 scope 重查。
- **修复风险**: 低
- **严重程度**: 中
