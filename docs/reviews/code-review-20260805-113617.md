## Findings

### DR6-01-未修复-高-supported multi-case 路径仍按 case 全量重建账户历史

- **入口/函数**: `reconcile_due_lifecycle_cases_for_source()` -> `lifecycle_case_read_models_for_account()` -> `lifecycle_case_coherent_facts_from_account_snapshot()` -> `_materialize_validated_anchors()`
- **文件(行号)**: `src/application/trades/lifecycle_runtime.py:823-845`; `src/application/trades/lifecycle_reconciliation.py:116-220`; `src/application/ledger/queries.py:524-617,632-701`; `tests/test_settlement_observation.py:1864-2086`
- **输入场景**: 同一账户有多个 provider-required case 同时达到 settlement deadline，collector capability 完整可用；该账户累积了大量 lifecycle evidence/source claims/allocations/position lots。
- **实际分支**: runtime 虽只调用一次 account snapshot reader，但随后对每个 `settlement_context_case_id` 单独调用 `lifecycle_case_coherent_facts_from_account_snapshot()`。该函数每次复制并扫描整份 cases/evidence/claims/allocations/timing/lots，且 `_materialize_validated_anchors()` 每次都从全部 evidence和claims重建两个全量索引。因此 CPU/分配复杂度仍为 `O(eligible_cases × account_history)`。
- **预期行为**: 一份 coherent account snapshot 应只被规范化和索引一次，再从共享索引按 case 派生 context；增加第二个同时到期 case 不应再次遍历全部账户历史。
- **实际行为**: 支持能力下的真实 provider 路径仍会随 case数和历史量乘法放大，能够重新制造本迭代要消除的持续高 CPU。当前 2,100-row测试使用缺失静态能力，classification后直接 blocked，完全没有执行 `settlement_context_case_ids` 路径，因此仍会通过。
- **直接证据**: `lifecycle_case_read_models_for_account()` 的 `for raw_resolution`循环在每个 context case调用单 case materializer；后者在 562-617 行逐项过滤账户集合，并在 639-650 行重建全 evidence/claim map。资源测试的 collector显式要求不存在的 `synthetic.missing` capability，provider context没有被构造。
- **影响**: main虽已去掉 cash-flow直接诱因，但同类型的“多 case × 大历史”CPU放大仍未解决；当静态能力恢复或另一种合法 provider collector启用时，`trade-intake`可再次长时间占用核心。
- **建议改法和验证点**: 在 coherent-query owner处增加 account snapshot batch materializer：一次构建 cases/evidence/claims/allocations/timing/lots索引，再批量返回目标 case facts；runtime只消费批量结果。新增两个 supported provider-required case + 至少 2,100 条历史 evidence的资源回归，直接计数全历史索引构建次数为 1，并证明每 case provider call有界、语义写入和状态结果正确。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### DR6-02-未修复-中-compact due query 每分钟仍扫描全部历史终态 case

- **入口/函数**: `reconcile_due_lifecycle_cases_for_source()` -> `list_trade_lifecycle_due_candidates()`
- **文件(行号)**: `src/application/trades/lifecycle_runtime.py:432-440,560-565,831-836`; `src/application/ledger/repository.py:1040-1114`; `src/application/trades/lifecycle_runtime.py:326-339`; `src/application/trades/close_reason_reconciliation.py:655-851`
- **输入场景**: 账户长期运行后积累大量 `ledger_written`和absorbing `conflict` lifecycle cases，当前只有少量或没有待 settlement case；listener仍按分钟执行 due reconciliation。
- **实际分支**: 名为 due candidates 的 SQL 只排除 `superseded`，因此每次都读取所有历史 `ledger_written`/`conflict` raw JSON，并为每行执行 evidence count和latest-evidence相关子查询；runtime单 tick最多调用该查询三次。后续 planner才根据 reason state跳过这些终态 case。
- **预期行为**: compact invalidation读取应在数据库边界排除明确不会由该定时器推进的 absorbing terminal states，只返回仍可能发生本地 deadline transition或provider collection的 active cases。
- **实际行为**: 即使没有到期工作，每分钟成本仍随账户累计终态 case和其 evidence历史线性增长；这保留了另一条与cash flow无关的常驻 CPU增长曲线。
- **直接证据**: repository SQL谓词只有 `status != 'superseded'`；`ensure_lifecycle_timing_after_intake()` 已把 `ledger_written`和`conflict`视为不再 reconcile的状态，due reconciliation也只处理 `cause_pending`、`partially_resolved`及无有效pairing时的有限 `needs_review`分支。
- **影响**: 本迭代可以减少重复provider调用，却无法把 idle tick成本约束为 active-work规模；运行时间越久，trade-intake仍会因历史 case自然增长而逐步变慢。
- **建议改法和验证点**: 把 active due-candidate状态集合定义在repository/query contract边界，至少排除 `ledger_written`、`conflict`、`superseded`，保留 `waiting_settlement_evidence`及仍需deadline处理的 `needs_review`等状态。新增repository测试，证明终态不进入compact query、active状态仍进入，并用大量终态 + 少量active的tick回归确认候选数和相关子查询工作量只随active集合增长。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
