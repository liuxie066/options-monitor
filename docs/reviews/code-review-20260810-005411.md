## Findings

### DR-S6-01-未修复-高-候选扫描失败或休市会被误报为“合法零候选”
- **入口/函数**: `run_or_reuse_ai_decision_advice()` -> `build_frozen_inputs()` -> `run_decision_advice()` -> `zero_candidate_flags()`
- **文件(行号)**: `src/application/ai_decision_advice/orchestration.py:120-172`; `src/application/ai_decision_advice/advice.py:218-278`; `src/application/ai_decision_advice/validation.py:238-242`
- **输入场景**: opening snapshot 结构和 hash 合法，但某策略的 `strategy_status=data_unavailable/not_applicable`，或整个 snapshot 的 `opening_status=market_closed`，因此没有 ranked candidate。
- **实际分支**: S6 只验证 snapshot 结构和 market，`freeze_candidates()` 丢弃 `opening_status/strategy_results`；`zero_candidate_flags()` 仅以空 list 判断零候选。
- **预期行为**: 只有 Candidate Engine 明确返回 `no_candidate` 才是合法零候选；休市、数据不可用或策略不可用应保留既有阻断/不可用语义，不创建伪 Advice。
- **实际行为**: 系统不调模型，但持久并展示 `not_applicable: zero_candidate`，S7 将把它渲染为“本轮无可供 AI 评估的策略候选”。
- **直接证据**: snapshot contract 允许 `data_unavailable/not_applicable/market_closed`；S6 新调用链在第 135 行直接进入 relevant-symbol/freeze；零候选函数只检查两个候选数组是否为空。
- **影响**: 用户无法区分“真的没有合格候选”和“根本没有完成评估”，会弱化原候选阻断的风险信号。
- **建议改法和验证点**: 在创建 frozen inputs 前同时校验每个策略的 candidate count 与 `strategy_status`；空 family 只接受 `no_candidate`，其他状态返回 candidate input unavailable。增加 `market_closed`、`data_unavailable`、一边 `no_candidate` + 一边有候选的回归。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### DR-S6-02-未修复-中-`evidence_as_of` 错用 Advice 冻结时间，把旧证据显示成当前证据
- **入口/函数**: `run_or_reuse_ai_decision_advice()` -> `build_frozen_inputs()` -> `run_decision_advice()`
- **文件(行号)**: `src/application/ai_decision_advice/orchestration.py:149-172`; `src/application/ai_decision_advice/contexts.py:277-343`; `src/application/ai_decision_advice/advice.py:214-220`; `src/application/ai_decision_advice/evidence_store.py:140-148`
- **输入场景**: Advice 在 12:00 冻结证据索引，账户相关 symbol 的最早可用 `last_success_at` 是 06:00。
- **实际分支**: `EvidenceIndex` 已正确计算 `evidence_as_of=06:00`，但 `freeze_external_evidence()` 不保存该值；`run_decision_advice()` 把 `external_evidence.frozen_at=12:00` 写入用户 view。
- **预期行为**: `evidence_as_of` 必须是相关、可用 symbol 的最早真实 `last_success_at`；无成功快照时为 `null`。
- **实际行为**: 每次 Advice 运行都显示当前时间，即使实际证据已接近 8 小时过期线。
- **直接证据**: `EvidenceIndex.evidence_as_of` 已实现 minimum success，但唯一 Advice consumer 在 `advice.py:218` 明确读取 `frozen_at`。
- **影响**: 回执会过度陈述外部资讯的新鲜度，与用户已确认的可审计 cutoff 语义相反。
- **建议改法和验证点**: 把 `EvidenceIndex.evidence_as_of` 放入 frozen external bundle 并纳入正式结果；冻结时间仍仅用于证明当轮视图。测试中使 `frozen_at` 与 `last_success_at` 明确不同，并覆盖无成功快照的 `null`。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### DR-S6-03-未修复-高-失败或未扫描 Tick 仍替换观察分区，会丢掉上一份可信持仓与候选集合
- **入口/函数**: `multi_account_tick.main()` -> `_load_advice_candidate_snapshots()` -> `_publish_ai_decision_observation_partitions()`
- **文件(行号)**: `src/application/multi_account_tick.py:714-749`; `src/application/multi_account_tick.py:143-229`
- **输入场景**: Advice 已启用，当轮因 required-data barrier、账户 pipeline 失败或其他原因没有任何 `ran_pipeline_accounts`；共享 observation 已有上一次成功 Tick 的 PM/期权/候选 symbol。
- **实际分支**: 代码只检查 `advice_enabled`，然后用空 candidate map 和可能不完整的 prepared maps 发布新分区；配置之外的旧 PM/期权/候选 symbol 被删除。
- **预期行为**: 只有当前 market 成功 Tick 在 prepared input 和 candidate seal 完成后才替换该分区；失败/未扫描轮应保留上一份有效 generation。
- **实际行为**: Collector 后续不再刷新被误删除标的，直到另一次成功 Tick 重新发现它们。
- **直接证据**: `ran_pipeline_accounts` 只用于构造 candidate load 参数，不参与 publish gate；`publish_observation_partition()` 是 replacement 语义，不会合并同 market 上一 generation。
- **影响**: 一次生产故障可以反向缩小外部风险观察面，与“失败不覆盖最后成功事实”的整体哲学不一致。
- **建议改法和验证点**: 将 observation replacement gate 收紧为至少一个账户成功完成 pipeline，且只用已接受 snapshot 的账户构建当轮集合；增加无成功账户时旧 partition generation/content 不变的回归。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高
