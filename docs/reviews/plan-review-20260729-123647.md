# Plan Review — Daily Brief Frozen Snapshot / Close Advice Fix

## Reviewed target and scope

- Target: `docs/plans/daily-brief-frozen-snapshot-close-advice-fix-plan-20260729.md`
- Review mode: adversarial implementation-plan review
- Scope: frozen required-data authority、Close Advice 持仓需求前移、manifest/receipt provenance、账户失败投影、重入语义、实施切片与验收矩阵
- Out of scope: 实施修复、修改原 plan、真实通知、生产 tick、release、upgrade

## Goal and boundary understood

该 plan 的目标是消除 account-owned Close Advice 在 required-data snapshot seal 之后补拉并改写共享行情，从而导致后续账户 snapshot integrity 失败及通知不对称的问题。主路径是：seal 前从 canonical ledger 构造 Close Advice 精确合约需求，将其合并到唯一一次跨账户 prefetch，再让 scheduled Close Advice 只消费 manifest-bound frozen bytes。

该总体方向与现有 single-prefetch / sealed-snapshot 架构一致，也比新增 account-local supplemental cache 更小、更可审计。本 review 不建议推翻该方向；以下 findings 指向 plan 尚未收敛的 contract 和状态传播。

## Assumptions tested

1. **Seal 前可以完整确定 Close Advice 行情需求**：部分成立。lot、合约键和 lifecycle 可从 canonical ledger 推导，但 plan 没有定义 watchlist 外 symbol 的 fetch source/endpoint 如何解析。
2. **Manifest-bound plan 是 frozen Close Advice 的唯一事实来源**：未完全成立。当前 runner 还独立读取 mutable quote-cache metadata，plan 未裁决两套 provenance/freshness authority 的优先级。
3. **Close Advice integrity failure 只需 position-scoped degraded evidence**：不成立。当前 account run 捕获 Close Advice 异常后仍继续写通知文本，外层仍可能把该账户视为 pipeline succeeded。
4. **Planning artifact 在同一 run 的重入路径上可恢复**：未证明。现有 `prefetch_done=true` 分支只恢复 snapshot manifest 和 prepared context，没有恢复新 requirements artifact。
5. **Lifecycle 使用单一 business date**：目标正确，但传参契约不完整。plan 冻结 `business_date`，而 proposed `run_close_advice()` 参数中没有该值，当前 runner 会在执行时重新取上海日期。
6. **S1 可以安全作为止血切片**：仅在不独立发布的前提下成立。plan 已说明 S1 不是完整修复，但 release gate 仍需在实施 handoff 中明确。

## Special review lenses

### Architecture boundary review

把 requirements 构造放在 application orchestration、把 deterministic requirement/lifecycle 语义保留为纯逻辑，并继续让 domain policy 只做 Close Advice 判定，边界总体合理。阻断点在于 symbol fetch authority 和通知可靠性 authority 尚未明确落到现有 owner；若留给实现阶段临时决定，会出现隐式默认 fetch 或另建 Close Advice 通知权威。

### Best-practice review

原子 artifact、content hash、manifest binding、typed gap、no-send 和 seal 后二次校验都符合可测试、可审计、fail-closed 的实践。缺失的是 recovery/re-entry contract、单一 freshness authority，以及 integrity failure 向 account-level success state 的显式投影。

### Optimal-solution review

“seal 前并入唯一 prefetch”是当前约束下最实际的方案。更安全且更简单的细化是：frozen mode 仅信任 sealed receipt/manifest，不再叠加 mutable quote-cache metadata；watchlist 外 symbol 若找不到 canonical runtime fetch config，则 typed fail closed，而不是引入第二套 source resolver 或默认 OpenD endpoint。

### Overengineering review

独立 requirements artifact 有跨账户去重、审计映射、重入恢复和 manifest binding 的现实需求，不属于无依据抽象。反而不应再把 mutable `.meta.json` 纳入新绑定链或新增 Close Advice 专用缓存，这会增加双重 authority 和同步成本。

### Overcoupling review

plan 正确避免了 account-local supplemental cache，但当前未收敛的完整性失败投影会把 Close Advice runner、account outcome 和 Daily Brief authority 通过隐式异常行为耦合起来。应通过已有 account pipeline success/degraded contract传递 typed result，而不是让 Close Advice 自己决定通知。

## Findings

### PR-01-未修复-高-Close Advice 完整性失败未被明确投影为账户级 frozen snapshot 失败
- **位置**: plan §8.2 第 322 行、§10.3；`src/application/account_run.py:791-911`
- **问题类型**: 状态机漏洞 / open question 未收敛 / 契约缺失
- **当前写法**: plan 规定 integrity failure 时不得发布成功 Close Advice report，并记录 account degraded evidence；但是否把整个 Daily Brief 标为 blocked，留给“现有 candidate snapshot authority”，只在 candidate consumer 对同一 symbol 也失败时“自然 blocked”。
- **反例/失败场景**: candidate scan 已在 seal 后成功读取并验证 symbol；随后外部进程或旧路径改写该 symbol CSV；Close Advice 的发布前二次校验发现 mismatch。candidate consumer 不会回溯失败，而当前 `account_run.py` 捕获 Close Advice 异常后只写 audit/runlog，仍继续写 `symbols_notification.txt`。外层因此仍可把账户纳入 `ran_pipeline_accounts`，生成普通、看似可靠的 Daily Brief envelope。
- **为什么有问题**: 同一 run 的 manifest 被 plan 声明为唯一 commit marker。任一 frozen consumer 在提交账户报告前证实该 marker 对实际消费 bytes 已失效，意味着该账户本轮共享行情 authority 已被破坏；不能依赖更早执行的 candidate consumer 是否碰巧检测到同一问题。否则执行顺序再次决定是否发正常消息，原始“不对称通知”风险没有被根除。
- **直接证据**: plan 第 292 行要求报告写入前重验，第 310、322 行定义 integrity failure，却在第 322 行保留 Daily Brief 是否 blocked 的开放语义。当前 `account_run.py:891-901` 吞掉 Close Advice 异常并仅记录日志，`account_run.py:903-911` 随后继续写账户通知文本。
- **影响**: 完整性异常时仍可能发布正常 actionable Daily Brief；账户顺序造成不同结果；success/degraded 状态与 manifest 真相不一致；验收无法证明根因闭环。
- **建议改法和验证点**:
  - 在 plan 中明确：frozen Close Advice 的 `required_data_snapshot_integrity_failed` 是 account-level snapshot-authority failure，而不只是 position gap。
  - 让 typed Close Advice result/exception 通过现有 `AccountRunOutcome` 或等价 pipeline 状态上报，使该账户 `pipeline_succeeded=false`，并由现有 Daily Brief authority 阻断 normal actionable delivery；不要在 Close Advice 内另建发送规则。
  - 保留普通 missing contract / unusable quote 为 position-scoped not-evaluable；只把 manifest/receipt/bytes integrity failure 升格为账户级 authority failure。
  - 新增确定性测试：candidate 读取成功后、Close Advice 重验前篡改一个 byte；断言无成功 Close Advice report、账户不进入 reliable pipeline、无 normal delivery envelope/provider 调用；反转账户顺序仍得到同一失败语义。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR-02-未修复-高-watchlist 外 active position 没有 canonical fetch source/endpoint 解析契约
- **位置**: plan §6、§7.1、§10.1；`src/application/required_data_prefetch_planning.py:42-120,530-538`；`src/application/multi_tick/required_data_prefetch.py:188-228`
- **问题类型**: 架构边界 / 契约缺失 / 不可直接实施
- **当前写法**: plan 要求从 canonical ledger 得到所有 active positions，并把 `_close_advice_position_requirements` 合入每个 symbol 的 planning config，但没有说明 ledger symbol 不在 base/account watchlist 时从哪里取得 `fetch.source/host/port` 及其他 runtime symbol config。
- **反例/失败场景**: 账户仍持有一个 active short option，但标的已从 watchlist 删除、只存在 alias、被当前 market filter 排除，或原 strategy config 使用非 Futu source。requirements artifact 能生成 canonical quote key，却没有可用于 `build_required_data_fetch_plan()` 的 authoritative symbol config。实现者可能丢掉该 position，或者让现有默认值隐式落到 `127.0.0.1:11111` / 默认 source。
- **为什么有问题**: ledger 是 position authority，不是 market-data routing authority。把 position requirement 合入 prefetch 必须显式连接到现有 runtime config owner；不能由 planning 层从 symbol 猜 broker/source，也不能为满足验收把持仓伪装成 strategy config。
- **直接证据**: 当前 `build_cross_account_prefetch_config()` 只遍历 `resolve_watchlist_config(base_config/account_config)` 生成 source items（`required_data_prefetch_planning.py:50-116`）。dedupe identity 包含 resolved source、host、port（`:530-538`）。单 symbol plan 从 `symbol_cfg.fetch` 取配置，并对 host/port使用默认值（`required_data_prefetch.py:195-221`）。plan 仅定义 position requirement 的合约字段，没有定义 routing 字段或 canonical resolver。
- **影响**: 真实持仓可能仍未在 seal 前预取；错误 source/endpoint 可能查询错误市场或错误 gateway；实现 Agent 必须临时重设计；原故障在 watchlist 变化后复现。
- **建议改法和验证点**:
  - 在 plan 中指定唯一 resolver：position canonical symbol 必须映射到当前 market/account runtime 中已有的 canonical symbol fetch config；明确 base 与 account override 的优先级，并复用现有 profile/source resolution。
  - 若找不到 authoritative symbol config，fail closed 为 account/position-scoped `required_data_symbol_config_missing`，不得使用隐式 localhost/source fallback，也不得 post-seal 补拉。
  - 若产品要求持仓即使不在 watchlist也必须取数，则 plan 必须明确哪个已有 broker-level config 是 routing authority；不要在 requirements artifact 复制 secrets 或创建第二套配置模型。
  - 新增测试：active position 不在 watchlist、alias-only、market-filtered、非 Futu source、base/account fetch override；验证 source/host/port 稳定、无猜测 fallback、缺 config 时 typed unavailable。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR-03-未修复-高-frozen mode 仍可能受 mutable quote-cache metadata 的第二套 freshness authority 支配
- **位置**: plan §8.1、§8.3、§10.4；`src/application/close_advice_runner.py:2584-2621`；`src/application/opend_symbol_outputs.py:128-144`；`src/application/multiplier_steps.py:17-50`
- **问题类型**: 过度耦合 / 最佳实践偏离 / 契约缺失
- **当前写法**: plan 要求 frozen mode 验证 manifest、symbol receipt 和 exact bytes，但未说明当前 `validate_quote_cache_metadata()` 是否继续执行，也未定义 sealed receipt 与 `<symbol>_required_data.meta.json` 冲突时谁是 authority。
- **反例/失败场景**: sealed manifest/receipt 对 raw 和最终 CSV bytes 均有效，但 `.meta.json` 缺失、过期，或它记录的是 multiplier enrichment 前的 CSV hash。若实现只关掉两个 fetch 函数而保留当前 freshness validation，Close Advice 会把 manifest 已验证的 quote 标为 provenance invalid；反之，若 mutable metadata 比 receipt 更新，也可能让 frozen consumer依赖未被 manifest 绑定的状态。
- **为什么有问题**: frozen snapshot 必须有单一 provenance/freshness authority。manifest/receipt 已绑定 run、observed/expiry 和 exact bytes，再叠加一个 seal 外可变 metadata 会造成双重判定、顺序依赖和难以解释的 false negative。为新 artifact 再绑定 metadata 也会扩大同步面。
- **直接证据**: 当前 runner 在加载 CSV 后独立调用 `validate_quote_cache_metadata()`（`close_advice_runner.py:2586-2621`）。`save_outputs()` 写 CSV 后立即发布 quote metadata（`opend_symbol_outputs.py:128-144`），而 multiplier helper 可随后直接重写同一 CSV且不重发 metadata（`multiplier_steps.py:30-50`）。plan 只明确 receipt/bytes 验证和 legacy freshness tests，没有裁决 frozen mode 的 metadata 读取。
- **影响**: 合法 frozen snapshot 被误判不可用；或 frozen report 依赖 manifest 外 mutable state；新旧 writer 顺序继续影响通知可靠性；provenance review 无法收敛。
- **建议改法和验证点**:
  - 在 plan 中明确 frozen mode 的 sole authority 是 sealed snapshot manifest + receipt；freshness 使用 receipt 中 manifest-bound observed/expiry facts。
  - frozen mode 不调用 mutable quote-cache metadata validator；该 validator 仅保留给未传 manifest 的 legacy/manual mode。
  - 不把 `.meta.json` 纳入新 requirements artifact，也不新增 Close Advice 专用 freshness文件。
  - 新增冲突测试：valid receipt/manifest + missing/stale/tampered `.meta.json` 仍以 sealed authority 为准；invalid receipt 即使 `.meta.json` 新鲜也必须 fail closed。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR-04-未修复-中-`prefetch_done=true` 重入路径未恢复 manifest-bound requirements artifact
- **位置**: plan §5、§6、§9 S2/S3、§10；`src/application/tick_account_execution.py:354-384`
- **问题类型**: 并发恢复风险 / 状态机漏洞 / 测试缺口
- **当前写法**: plan 规定首次 barrier 原子写 requirements plan 并把 hash 绑定到 snapshot manifest，但没有描述同一 run 已完成 prefetch 后再次进入 account execution 时如何恢复、验证和向 account runner 传递该 plan。
- **反例/失败场景**: `request.prefetch_done=true` 时，现有代码只加载 `required_data_snapshot_manifest.json` 并发现 per-account prepared context。若实现仅在 `not prefetch_done` 分支保存内存中的 plan path/hash，重入分支会把 plan 参数传为 `None`，导致所有 frozen Close Advice fail closed；更危险的实现是从当前 ledger 重建 requirements，与已 seal manifest 不一致。
- **为什么有问题**: requirements artifact 已被定义为 run-scoped durable contract，其恢复必须和 snapshot manifest 原子绑定。重入时重读 live ledger 会把 seal 后状态混入旧 snapshot，破坏 plan identity；忽略 artifact 则造成可恢复 run 的系统性降级。
- **直接证据**: 当前重入分支 `tick_account_execution.py:354-384` 仅调用 `load_required_data_snapshot_manifest()` 并恢复 `prepared_portfolio_context.v1.json` 路径，没有 requirements artifact。plan 的验收矩阵未覆盖 `prefetch_done=true`、进程内重入或 artifact 缺失/hash mismatch。
- **影响**: 重试/恢复行为与首次执行不同；全部账户 Close Advice 无故 unavailable；或旧 manifest 与新 ledger 被错误拼接；测试只证明 happy path。
- **建议改法和验证点**:
  - 在 plan 中增加 recovery contract：重入只能从 loaded snapshot manifest 的 relpath/hash 定位并验证原 requirements artifact，禁止重建或覆盖。
  - artifact 缺失、越界 relpath、run/hash mismatch 时设置 typed barrier/account failure；不得 fallback 到 post-seal planning/fetch。
  - 新增 `prefetch_done=true` 回归：正常恢复产生与首次执行相同的 plan path/hash；缺失/篡改 artifact 时 fail closed 且无 fetch/write。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### PR-05-未修复-中-冻结的 `business_date` 没有进入 consumer 参数契约
- **位置**: plan §5、§6 第 214 行、§8 proposed signature、§9 S2；`src/application/close_advice_runner.py:2531-2559`；`domain/domain/expiration_dates.py:33-37`
- **问题类型**: 状态机漏洞 / 契约缺失 / 测试缺口
- **当前写法**: requirements artifact 保存 run-scoped `business_date`，planning 用“本轮唯一 business_date”判定 active lifecycle；但 proposed `run_close_advice()` 新参数只有 manifest、run id、plan path、account，没有 business date 的来源/验证规则。
- **反例/失败场景**: barrier 在 Asia/Shanghai 23:59 构造 requirements，account future 在次日 00:00 后运行。expiration-day position 在 planning 时为 active，runner 重新计算日期后可能成为 expired；反向重试也可能得到另一分类。不同账户跨过午夜时会消费同一 plan却采用不同 lifecycle date。
- **为什么有问题**: lifecycle 决定 requirement identity 和 quote coverage。producer 与 consumer 若不共享同一日期事实，plan 无法证明“每个 runtime active position 都有 seal 前 requirement”，账户顺序又会影响结果。
- **直接证据**: plan artifact 第 154 行包含 `business_date`，第 214 行要求本轮唯一日期；第 268-275 行 proposed signature 未包含对应值。当前 runner 在每次调用时执行 `expiration_business_today()`（`close_advice_runner.py:2552-2559`），该函数读取当前时间并转换到 expiration timezone（`expiration_dates.py:33-37`）。
- **影响**: 午夜边界出现 requirement/consumer 分类漂移、假 missing 或漏评估；两个账户结果顺序相关；artifact audit 无法重放。
- **建议改法和验证点**:
  - 明确 frozen runner 从已验证 requirements artifact 读取并使用 `business_date`，不得再次读取 wall clock；legacy mode 保持当前行为。
  - 校验该日期与 run/market contract 一致，所有账户共享同一值。
  - 新增 frozen-time 测试：barrier 前后跨上海午夜，requirements bytes、active lifecycle 和两个账户输出保持一致；legacy mode 仍使用执行时日期。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

## Open Questions

1. 对于不在任何 resolved watchlist 的 active position，当前产品期望是“使用已有 broker-level market-data routing 继续覆盖”，还是“明确 typed unavailable”？必须在实施前选择一个已有 authority，不能由实现者猜测。
2. 现有 `AccountRunOutcome` / Daily Brief flow 中哪个字段是投影 frozen integrity failure 的最小合法入口？应复用现有 pipeline success authority，不应增加 Close Advice 专用通知状态。
3. S1 是否允许单独 commit 供 review？可以，但 plan 应明确禁止单独 release/upgrade；生产完整性和 Close Advice coverage 验收必须以 S1-S5 整体为门槛。

## Residual risks and tracking

- **Seal 后 ledger 变化**：plan 已选择 position-scoped `required_data_position_not_planned`，属于明确 residual risk。建议在 run metrics 中跟踪 planned/runtime active position delta，并在异常频率升高时单独评估是否需要冻结完整 position context。
- **外部 writer 不受本进程约束**：发布前重验可检测但不能防止外部改写。建议继续由 snapshot integrity metrics / audit 追踪；不要在本 work unit 引入锁或第二套缓存。
- **Rate-limit budget**：exact expirations 可能扩大一次 prefetch 的负载。plan 已保留同 invocation wave/budget 策略；实施时应把 dedup 后合约数和估算调用数写入现有 prefetch metrics。
- **Mixed-version manifest**：老 reader 忽略可选字段是合理方向；仍需在 compatibility tests 中覆盖 new writer + old candidate consumer、old manifest + new Close Advice consumer 两个方向。

## Conclusion

**fail**

总体架构方向可信，但当前 plan 尚未达到 code-generation-ready：完整性失败的账户级传播、watchlist 外持仓的 fetch routing、frozen freshness 单一 authority、重入恢复和 run-scoped business date 均未收敛。其中前三项会直接导致正常消息在不可靠 snapshot 上继续发送、持仓无法预取，或合法 snapshot 被第二套 metadata 误判。应先修订 plan 并补齐对应验收，再交给 implementation agent。
