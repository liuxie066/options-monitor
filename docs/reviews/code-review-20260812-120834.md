### 1-未修复-中-旧 AI 重试被拦截后 Tick 仍以成功跳过结束，永久阻塞被误报为无需投递

- **入口/函数**: `run_tick_notification_flow()` -> `_prepare_daily_brief_notification()` -> no-threshold terminal branch
- **文件(行号)**: `src/application/tick_notification_flow.py:227-269, 679-725, 949-1015`; `tests/test_daily_decision_brief_notification_flow.py:773-855`
- **输入场景**: scheduled delivery-only 或 post-scan Tick 读到状态为 `pending`/`ambiguous`、且冻结正文或来源仍含已退役 AI 建议的 envelope。
- **实际分支**: classifier 记录 `legacy_ai_payload_retired` 并不把消息加入 outbound map；随后 `threshold_met=False` 进入通用空消息分支，调用 `guard_mark_success()`，以 `status=skipped` 和 `no_retryable_delivery`/`no_daily_brief_delivery` 完成幂等记录并返回 0。
- **预期行为**: 不发送、不改 envelope，同时把这个确定的本地策略阻塞作为 Tick 失败/阻塞终态暴露，便于 scheduler 和运维区分“确实无消息”与“存在无法再发送的冻结消息”。
- **实际行为**: provider 未被调用虽然正确，但顶层运行结果宣称成功且无需投递；同一冻结 envelope 会在之后每次运行中永久重复该假成功。
- **直接证据**: Slice 1 新增的 lifecycle audit 使用 `status=error`，但该错误没有进入 `DailyBriefNotificationPreparation` 的终态决策；新增回归测试反而固定断言两条路径都返回 0。
- **影响**: scheduler/guard/idempotency 状态无法可靠告警，退役 guard 的主要运营信号只藏在子级 metrics 中，可能让待处理 delivery state 长期无人发现。
- **建议改法和验证点**: 让 preparation 显式携带 blocked error code；在任何普通 no-message 分支之前，以稳定错误码完成失败终态并返回非零，同时保持 delivery state 字节不变、provider 零调用。分别覆盖 pending 与 ambiguous、delivery-only 与 post-scan。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 中

### 2-未修复-中-历史摘要兼容仅覆盖 v2 source validator，overlay-era v1 pointer 仍会被当前代码判为损坏

- **入口/函数**: `prepare_daily_decision_brief()` and `_build_v2_state_from_legacy_pointer()`
- **文件(行号)**: `src/application/daily_decision_brief_repository.py:1115-1157, 2202-2272`; `domain/domain/daily_decision_brief.py:839-866`
- **输入场景**: 磁盘上存在 AI overlay 上线期间生成的合法 Brief revision 和 v1 delivery pointer；pointer 的 `brief_digest` 是包含两个 AI 字段的当时摘要。升级后再准备 Brief，或 dry-run/apply v1-to-v2 migration。
- **实际分支**: raw revision 经当前 normalizer 后移除 AI 字段；两个 v1 路径都只计算 `daily_brief_digest(normalized)`。`prepare_daily_decision_brief()` 因 pointer digest 不等于 stripped digest 直接报 mismatch；migration preview 则把合法旧摘要报告为 `legacy_brief_digest_matches_revision=False`，并以另一个摘要重建确认事实。
- **预期行为**: 只接受 `daily_brief_compatible_digests(raw)` 中由该 revision 原始字节形状严格导出的摘要；合法 overlay-era pointer 可继续读取/迁移，任意其他摘要仍 fail closed。
- **实际行为**: 新增兼容 helper 只在 v2 successful-source validation 等局部调用，未覆盖仍受支持的 v1 pointer 生命周期。
- **直接证据**: `b3f6c247` 先前已把 v2 source validation 改为 compatible-digest membership；本 Slice 改写了兼容摘要语义，却保留 v1 的两个 exact-current-digest 比较。现有测试只验证 v2 envelope，不构造 overlay-era v1 pointer。
- **影响**: 已确认历史投递可能阻塞后续 Brief 生成，或在迁移审计中被误报为不匹配，违反本 Slice 的“历史持久化产物仍可严格验证”不变量。
- **建议改法和验证点**: v1 pointer 比较使用同一次 raw revision 的 compatible digest set；内部继续以 current digest 生成新状态即可，但 preview 必须把精确旧摘要判为匹配。增加 prepare-next-revision 与 migration-preview 两个 overlay-era 回归，并保留错误摘要拒绝测试。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 中

### 3-未修复-低-classifier 检查的 raw revision 不是其随后完成摘要校验的同一次读取

- **入口/函数**: `classify_retryable_daily_decision_brief_payload()` -> `_validate_successful_revision_source()`
- **文件(行号)**: `src/application/daily_decision_brief_repository.py:548-588, 2132-2150`
- **输入场景**: classifier 执行期间 revision 文件被并发替换，或在故障恢复/人工修复中发生读取间变化。
- **实际分支**: classifier 先读一次 raw 用于 retired-field 检查，再调用 validator；validator 又独立读一次并只返回 normalized Brief。于是“摘要验证通过”的版本与“是否含 retired fields”的版本可能不是同一份对象。
- **预期行为**: 原始字段检查和 compatible digest/identity 校验必须基于同一次严格读取，避免 integrity decision 的 TOCTOU 窗口。
- **实际行为**: 可能验证版本 B，却依据版本 A 决定 clean/blocked；在极端竞态下会放行旧 AI payload 或错误阻塞干净 payload。
- **直接证据**: classifier 在 revision path 上直接 `_read_json_strict()`，随后 `_validate_successful_revision_source()` 再对相同路径执行 `_read_json_strict()`；后者不把已验证 raw 返回给调用方。
- **影响**: 风险窗口较窄，但位于明确要求 fail-closed 的持久化完整性边界。
- **建议改法和验证点**: 抽出一次读取并返回 `(normalized_brief, raw)` 的私有 validator，现有调用继续取 normalized，classifier 对返回的同一 raw 做 retired-field 检查；用 monkeypatch/序列读取回归证明仅检查被验证对象。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低
