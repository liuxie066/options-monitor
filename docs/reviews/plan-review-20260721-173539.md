# Plan Review — 期权监控通知体验升级

- Review 时间：2026-07-21 17:35:39 Asia/Shanghai
- Reviewed target：`docs/plans/option-notification-experience-implementation-plan-20260721.md`
- 产品真源：`docs/OPTION_NOTIFICATION_EXPERIENCE_PRD.md`
- Scope：半点扫描修订后的 scheduler、持久化候选身份、通知状态机、重试、迁移、测试与 rollout
- Review posture：adversarial；只 review plan，不实施运行代码、不改生产配置、不触发通知

## Goal / boundary 复核

计划目标清楚：复用现有 10 分钟 timer，仅在固定报告点与有效 `HH:30` 执行同一套 canonical pipeline；扫描成功后更新唯一快照，再选择固定完整报告、新增候选通知或静默。候选过滤、broker fetch、sender、ledger 和 Close Advice 保持现有权威。

## Assumptions tested

1. 10 分钟 timer cadence 与真实 pipeline cadence 已明确分离；非目标 tick no-op。
2. `09:30` 被 `09:40` 开盘完整报告替代，避免 10 分钟内连续扫描。
3. HK 午休过滤、US DST/gates、非交易日和账户级去重继续复用同一 scheduler 边界。
4. 最短目标间隔是 20 分钟，而不是 30 分钟；容量验证已按 `09:40 -> 10:00` 和 `15:30 -> 15:50` 收紧。
5. no-op tick 不重试普通监控消息；provider/pipeline 失败等到下一真实 scan target，示例已从 `14:10` 改为 `14:30`。
6. pipeline failure/no-op 不推进 successful current；candidate pending 跨成功快照保留。
7. fixed + new 只发完整报告，confirmed 后按 delivery plan 的整份身份集合推进 alerted。
8. v1 pointer 迁移仍为显式 dry-run 默认，不由 normal tick 隐式执行。
9. force/manual 不伪装 scheduled batch，不推进普通候选 alerted 状态。
10. 计划没有新增第二个 scanner、sender、数据库或配置频率。

## Findings

### PR-01-未修复-高-候选身份使用未定义的 hash 会破坏跨进程去重
- **位置**: 计划 9.1“身份”；delivery v2 的 `pending_candidates`、`alerted_candidates`、candidate delivery key
- **问题类型**: 契约缺失 / 状态机漏洞 / 不可直接实施
- **当前写法**: `identity = hash(account, market, canonical symbol, strategy_family)`，没有规定 canonical serialization 或 digest 算法。
- **反例/失败场景**: 实现 Agent 直接使用 Python 内置 `hash()`。Python 进程级 hash randomization 会使同一候选在相邻 cron 进程得到不同 identity。上一轮写入的 pending/alerted 无法与下一轮 current identity 匹配，同一候选会重复提醒，未送达 pending 也可能永久遗留。
- **为什么有问题**: delivery v2 是跨 tick、跨进程持久化状态，candidate identity 必须是稳定公共数据合同，不能依赖实现语言的进程内 hash。
- **直接证据**: 计划要求 identity 持久化进按交易日保存的 delivery state，并参与稳定 candidate delivery key；现有生产入口是周期性 `tick-cron` 进程，不能假设同一 Python 进程长期存活。
- **影响**: 重复通知 / pending 状态不一致 / provider 重试失效 / 迁移和审计不可复现。
- **建议改法和验证点**:
  - 使用规范化字段组成的 deterministic canonical identity；最简单可使用 canonical JSON 字符串，不使用 Python `hash()`。
  - candidate delivery key 如需短 digest，使用现有 canonical digest helper 或标准库 SHA-256 对排序后的 canonical identities 计算。
  - 增加跨进程/不同 `PYTHONHASHSEED` 结果一致测试，以及 normalization、排序和 round-trip 测试。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

## Architecture boundary review

除 PR-01 外未发现新增跨层权威：candidate filter/rank 仍在 domain；scheduler 只生成目标与 DTO；repository 拥有 immutable revision 和 delivery state；notification flow 负责编排；provider adapter 不被重写。

## Best-practice / optimal-solution review

- 使用现有 10 分钟 timer 作为唤醒、在 scheduler 内生成固定点与半点并集，比修改生产 timer 或新增候选 timer 更小、更安全。
- 将半点固定为产品合同而不增加配置键，符合当前双市场需求和 YAGNI；若未来市场需要不同节奏，再引入配置迁移。
- no-op tick 不处理普通 delivery retry 是更简单的单一状态机，代价是失败后最多等到下一真实 scan target；计划已显式记录该 residual risk。

## Overengineering / overcoupling review

未发现需要删除的新层或依赖。delivery v2、pending/alerted 和 run-scoped plan 都对应现有明确的幂等、provider ambiguity 和迁移需求，不属于无需求抽象。候选 identity 必须先修成确定性合同，否则这些状态会被不稳定 key 绑死。

## Open questions

1. 候选身份粒度是否正式采用“账户 + 市场 + 标的 + 策略族”。
2. 默认查询是否聚合全部启用账户和市场。
3. 是否接受 force/manual 扫描只更新 successful current、不发送普通报告或候选通知。

## Residual risks

- 半点检查不是实时行情；HK 午休跨段会等到下一个有效目标点。
- provider 长时间故障会形成 fixed backlog，恢复后可能连续发送延迟报告。
- 固定点 + 半点会增加 immutable revision 数量，但尚无证据要求本 work unit 同时设计 retention。
- 远端实际 pipeline P95、OpenD 限频和双账户串行容量仍需在 execute 前只读验证。

## Conclusion

**fail**

计划的半点调度方向成立，但 PR-01 会直接破坏跨进程通知去重。修复 deterministic candidate identity 契约并补充验证点后再复审。
