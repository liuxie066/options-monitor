## Intent and contract alignment

The change implements the approved presentation-only `System Notice` shell without creating a second sender, retry loop, persistence layer, provider branch, renderer registry, DTO, or fallback path.

Verified ownership boundaries:

- `render_system_notice()` owns only H1 construction, ordered flat fields, empty-section omission, and multiline flattening.
- OpenD remains the owner of the raw 1200-character detail limit, failure classification, consecutive threshold, cooldown/burst control, recovery eligibility, send decision, and confirmed-send quota recording.
- Scheduled notification remains the owner of per-account failure aggregation, retry/confirmation evidence, provider diagnostics, failure-summary dispatch, and its single-attempt policy.
- The shell neither reads provider configuration nor handles Feishu byte limits; `FEISHU_POST_TOO_LARGE` remains a caller-owned diagnostic fact.

## Adversarial path review

### OpenD failure

Entry point: `send_opend_alert()`.

- The existing consecutive-failure gate, `no_send` exit, cooldown/burst preflight, and `_send_notification()` path are unchanged.
- The old formatter truncated `detail` to 1200 raw characters before flattening. The new caller preserves the same order by applying `str(detail)[:1200]` before handing the value to the shell.
- `message_text`, `detail`, and diagnostic values are flattened without nested Markdown indentation.
- A failed or unconfirmed provider send still returns false and does not consume the rate-limit quota; only a confirmed/ok result records the send.

### OpenD recovery

Entry point: `send_opend_recovery_notice()`.

- Recovery still resets/readies the consecutive-failure state before testing the configured threshold.
- Disabled recovery, insufficient prior failures, and `no_send` still suppress delivery.
- The shell changes presentation only; no recovery state transition or provider behavior moved.

### Delivery-failure summary

Entry point: `run_tick_notification_flow()` -> `build_notify_failure_summary_message()` -> `send_account_message_with_retry(max_attempts=1)`.

- Zero confirmed accounts now render `状态｜❌ 投递失败`; partial success renders `状态｜⚠️ 部分失败`, matching the approved semantic split.
- Batch ID, confirmed accounts, failure count, account, error code, attempts, confirmation state, message ID, and provider response code are preserved.
- Multiline diagnostic values are flattened by the shell; empty failure sections are omitted.
- The caller still sends the summary through the existing adapter with the existing non-recursive single-attempt rule; no alternate renderer or provider fallback was introduced.

### P0 transport identity

- Canonical output remains Markdown.
- The real failure-summary path continues through the existing Feishu adapter and its `post` / exactly-one-`md`-node contract.
- The same canonical Markdown is passed unchanged to the WeChat adapter.
- No code in this slice reads the Feishu byte budget or performs automatic `text` fallback.

## Over-coupling and semantic ownership review

- The new module has one public helper and one private flattening helper.
- There is no registry, template DSL, inheritance hierarchy, generic notification object, protocol-aware renderer, or speculative extension hook.
- Caller-owned labels and ordered values make the shell narrow enough to share without absorbing OpenD or delivery-failure business semantics.
- No state-machine transition or side effect was moved into presentation code.
