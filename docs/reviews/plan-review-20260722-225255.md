# Plan Review — Sell Put account-asymmetric fetch visibility fix

## Reviewed target and scope

- Target: the conversation plan produced on 2026-07-22 for the production defect where `lx` had no TCOM recommendation while `sy` did in the same US 10:00 run.
- Proposed direction: remove the account-cash-derived Sell Put strike cap from `apply_prefilters()`, preserve configured market scope for required-data planning, and leave final eligibility to the existing fail-closed cash-capacity gate.
- Review scope: goal and success signals, architecture ownership, implementation slices, regression tests, multi-account execution semantics, request-volume risk, rollout, and rollback.
- Out of scope: implementation, production mutation, config changes, notification delivery, and changing the collateral policy itself.

## Assumptions tested

1. Removing the early cash cap is the smallest change that eliminates the second cash authority.
2. The account-invariant fetch window should equal the raw configured `max_strike`.
3. Existing unit tests plus two isolated `run_symbol_monitoring()` cases prove the production `lx/sy` behavior.
4. Once TCOM is fetched, the existing final cash gate will accept the production-shaped `lx` context.
5. The larger market window will remain operationally safe without a quantitative request/time budget.
6. Deleting the now-orphaned helper/module and unused prefilter FX arguments does not change a public contract.

Architecture, best-practice, optimal-solution, overengineering, and overcoupling lenses were applied explicitly. The chosen architectural direction is sound: fetch visibility belongs to market/config planning, while account eligibility belongs to the final risk-capacity boundary. No new abstraction is warranted. The findings below are specification and validation blockers, not a request for a larger redesign.

## Findings

### PR-01-未修复-高-计划把原始配置上限误写成最终取数窗口，回归断言会反对当前正确的 spot cap
- **位置**: 目标、实现分片 1、线上验收中的“两个账户保留配置中的 TCOM `max_strike`”
- **问题类型**: 契约缺失 / 测试缺口 / 不可直接实施
- **当前写法**: 计划要求 `lx`、`sy` 的 required-data plan 都保留配置中的 TCOM `max_strike`，并在 canary 中验证不再出现 `21.7748`。
- **反例/失败场景**: TCOM 配置上限为 `45`、spot 为 `43.07` 时，正确的 required-data planner 会把最终 Put 上限收敛为 `min(45, 43.07) = 43.07`，并在没有显式 `min_strike` 时派生下限 `34.456`。若实现 Agent 按计划断言最终 plan 为 `45`，测试会拒绝当前正确行为，甚至诱导其删除 spot 安全边界。
- **为什么有问题**: 修复目标是消除“账户现金影响市场取数”，不是取消“spot 影响 Put 市场窗口”。原计划混淆了输入配置契约和 resolved fetch-plan 契约。
- **直接证据**: `src/application/required_data_planning.py:229-234` 明确读取配置上限后执行 `min(configured_max_strike, spot_reference)`；线上 `20260722T140036Z-add5f4` 的 `sy/tcom_required_data_fetch_plan.json` 显示 spot `43.07`、Put 窗口 `34.456..43.07`，而 `lx` 因 cash cap 变成 `17.41984..21.7748`。
- **影响**: 实施 Agent 可能生成错误断言或破坏现有 planner，扩大到价内/高于 spot 的非目标取数；plan 无法直接交付实现。
- **建议改法和验证点**: 把 invariant 改为“传给 planner 的 `sell_put_cfg` 对两个账户完全相同且未被现金改写；resolved Put 窗口只由配置、spot、DTE 和既有 planner defaults 决定”。固定 spot `43.07` 时，两个账户都应断言 `max_strike=43.07`、派生 `min_strike=34.456`；另加无 spot fixture，才断言回退到配置 `max_strike=45`。不要把 `ensure_required_data(max_strike=45)` 的兼容参数误当成 `fetch_plan` 的实际网络窗口。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### PR-02-未修复-高-计划没有用同一份生产形状上下文贯通取数、现金富化和最终门控
- **位置**: 实现分片 1、实现分片 3、线上验证
- **问题类型**: 测试缺口 / open question 未收敛
- **当前写法**: 计划分别测试双账户 fetch plan、`cash_free_total_cny` 接受、现金不足拒绝，并把“若仍被 `base_cny_cash_insufficient` 拒绝”留到发布后再判断。
- **反例/失败场景**: 删除早期 cap 后，TCOM 35P/40P 可以进入 required data，但 portfolio context 与 option context 没有按生产形状合并、汇率方向写反、`cash_secured_total_cny` 未传入，或 final basis precedence 走到另一路径，候选仍会在最终门控消失。分离的 planner unit test 和预计算字段 risk-capacity unit test都会通过。
- **为什么有问题**: 用户要修复的是端到端账户结果，不只是 fetch-plan 结构。计划本身已经承认最终门控可能否决，但没有在发布前锁定生产 `lx` 的真实预期，因此 success signal 不闭环。
- **直接证据**: `src/application/sell_put_cash.py:133-148` 从 `cash_by_currency` 和 `option_ctx.cash_secured_total_cny` 组合出 `cash_free_total_cny`；`domain/domain/risk_capacity.py:65-83` 又按 `base_cny`、`total_cny` 顺序选择 basis。线上只读快照显示 `lx` 的 cash 为 HKD `666787.5`、USD `10177.48`，已占用 HKD `386500`、USD `8000`、合计 CNY `388092.511619`，汇率 USDCNY `6.7711`、HKDCNY `0.863968206`；其 free total 约 CNY `256903.42`，TCOM 35P/40P 的单张要求约 CNY `23698.85/27084.40`，应明确通过 `total_cny`。
- **影响**: 修复可能只把“无痕丢失”移动到另一个阶段；本地测试通过但线上 `lx` 仍无 TCOM，导致再次发布和返工。
- **建议改法和验证点**: 增加一个经过脱敏的 production-shaped fixture，把上述 `cash_by_currency`、`option_ctx` 和汇率交给真实 `_enrich_and_filter_sell_put_cash()`，候选同时包含 TCOM 35P/40P、multiplier `100`、USD；断言两行保留、basis 为 `total_cny` 或等价可观察字段正确、没有 `cash_reserve` reject trace。再用同一链路测试 insufficient 和 missing-basis 两个 fail-closed 反例。把这个 deterministic test 设为发布前 gate，而不是线上 canary 后才决定政策。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR-03-未修复-高-双账户测试没有覆盖同一 run 的共享 required-data 和账户顺序/并发语义
- **位置**: 实现分片 1、验证命令、线上验证
- **问题类型**: 并发恢复风险 / 测试缺口 / 架构边界
- **当前写法**: 计划建议在 `test_symbol_monitoring_fetch_spec_merge.py` 中构造 `lx`、`sy` 两个账户，并分别验证 plan 和 scan 调用；未要求它们共享同一 required-data workspace，也未覆盖两种账户顺序或并发。
- **反例/失败场景**: 生产 tick 的账户流水线共享 `run_dir/required_data`。如果一个账户先基于窄窗口检查/写入，另一个账户随后或并发基于宽窗口检查/写入，单账户测试均可通过，但最终结果仍受账户顺序、覆盖检查时机或共享 CSV 最后写入者影响。
- **为什么有问题**: 用户报告的现象恰好发生在同一 10:00 multi-account run；把它降级成两个隔离单账户用例没有复现真实执行边界。修复后两个账户理论上会生成相同市场 plan，但计划必须证明这个 invariant 在共享 workspace 下成立。
- **直接证据**: `src/application/tick_account_execution.py:24-33,53-72` 支持多账户线程执行；`src/application/account_run.py:352-412` 只用共享锁串行化首次 prefetch，随后账户 pipeline 继续共享 `request.shared_required`；线上同一 run 的 TCOM plan artifact 显示 `lx` 当时 Put coverage 为 0，而 `sy` 为 4，证明账户观察到的共享数据状态并非可假设静态一致。
- **影响**: 测试无法证明原始生产场景，账户顺序或 worker 数变化后可能复发；rollout canary 也可能偶然通过。
- **建议改法和验证点**: 至少增加一个 run-scoped integration fixture，让 `lx`、`sy` 使用同一临时 `required_data_dir`，分别按 `lx→sy`、`sy→lx` 执行并断言 resolved TCOM Put plan、coverage 和最终候选一致。若生产配置允许 `multi_account_max_workers>1`，再用受控并发测试证明两个账户生成相同 fetch spec，或证明共享 prefetch 在账户 pipeline 前已经覆盖该 spec。线上 canary 必须一次运行 `--accounts lx sy --symbols TCOM --no-send`，不能拆成两个单账户 canary。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR-04-未修复-中-请求放大验收只有“无报错”，没有全 watchlist 的量化预算
- **位置**: 影响面、验证、线上验证
- **问题类型**: 最佳实践偏离 / 测试缺口 / residual risk 未量化
- **当前写法**: 计划说明到期日和 option-chain 请求不增加，只会增加窗口内 snapshot 合约数；验收标准是没有 rate-limit 或 truncation 错误。
- **反例/失败场景**: 删除所有 symbol 的账户现金 cap 后，多个低原生现金账户会同时扩大 Put snapshot code 数量。即使不触发显式 rate-limit，完整 US watchlist 的 pipeline 仍可能接近 600 秒超时，或占用更多共享 snapshot budget，造成后续 symbol 退化。
- **为什么有问题**: “没有错误”不能证明定时任务预算安全，单 TCOM canary 也不能代表全 watchlist 累积成本。当前代码已经暴露 `snapshot_requested_codes`、`market_snapshot_opend_calls` 和 `pipeline_ms`，计划没有利用这些可观察数据设 gate。
- **直接证据**: `src/application/opend_symbol_fetching.py:372-445` 在 strike 过滤后按剩余 option codes 请求 snapshots；`src/application/required_data_observability.py` 汇总 requested codes/calls；线上 TCOM 的 `lx` 窗口会从 `17.41984..21.7748` 改为市场窗口 `34.456..43.07`，请求集合会实质变化。
- **影响**: 正确性修复可能引入定时任务延迟或降级，直到完整线上 run 才暴露。
- **建议改法和验证点**: 发布前用缓存 option chain 对完整 US watchlist 计算 before/after `snapshot_requested_codes` 和预期 batch call 数；把 600 秒 tick timeout、snapshot rate budget 和历史 `pipeline_ms` 写成明确 gate。线上先做 TCOM `lx sy` canary，再在不发送通知且获授权的情况下做一次 full-watchlist canary，对比 calls、wait time、pipeline duration；超预算则回滚并另开“账户无关的 market-only fetch window”优化，不恢复现金权威。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

## Open Questions

1. 生产 US runtime 的 `multi_account_max_workers` 当前是 1 还是 2？若为 1，仍需覆盖两种账户顺序；若大于 1，并发共享 required-data 验证为 release blocker。
2. `base_cny` 优先于 `total_cny` 是明确业务政策还是历史兼容？本次线上 `lx` 快照没有 CNY cash key，因此走 `total_cny` 可满足目标；不要在本 fix 中顺带改变该政策。
3. 完整 watchlist 在取消 cash cap 后，snapshot requested codes/calls 的实际增量是多少？需要在 implementation 前用缓存 chain 定量。

## Residual risks and tracking destination

- Shared required-data 的跨进程原子写入/锁语义不属于本次最小修复；如果在相同 fetch spec 下仍观察到覆盖摇摆，应单独建立 concurrency/recovery work unit，而不是把锁重构塞进本 bug。
- `apply_prefilters()` 删除无用 FX 参数和 `pipeline_steps.py` 属于直接死代码清理，但若实现 diff 因依赖注入契约变大，可保留兼容参数一版并只移除 Put 分支；不要为清理扩大 public facade。
- 实时市场条件可能让 TCOM 最终因收益率、流动性或事件风险被拒绝；线上成功信号应是“进入统一候选/可解释拒绝链”，而 deterministic fixture 才负责证明 35P/40P 的现金通过。
- Suggested tracking: findings PR-01 through PR-04 must be folded into the implementation plan before Gateflow implementation handoff; shared-write locking, if independently reproduced after equalizing plans, should be tracked as a separate bug work unit.

## Final plan review conclusion

**fail**

The architectural direction is credible and likely optimal, but the plan is not yet code-generation-ready. It contains one incorrect fetch-window assertion and does not prove the exact production-shaped cash path or the shared multi-account execution boundary. Correct PR-01 through PR-03 before implementation; PR-04 may be accepted only with an explicit quantitative rollout gate.
