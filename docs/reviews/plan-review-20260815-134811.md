## Assumptions tested

- A point ref alone contains enough information to assign the point to an authoritative Corpus trading day.
- Separate caller-provided date and hash arguments prove the maturity/calendar fact they claim to bind.
- Allowing non-40 `required_days` values cannot escape synthetic tests into a production dataset.
- The proposed public results are precise enough that implementation will not invent status/error semantics.
- Artifact-first publication remains recoverable without a second outbox.
- Two behavior slices are the minimum useful review boundaries.

## Findings

### PR-W4-01-未修复-高-点位捕获没有绑定事前 expectation，交易日归属既无法权威推导也无法阻止意外点进入分母
- **位置**: §5 `capture_recommendation_point()`、§7 capture steps、§8 `strategy_lab_corpus_points`
- **问题类型**: 契约缺失 / 状态机漏洞 / 不可直接实施
- **当前写法**: capture 只接收 `point_ref` 和 `captured_at_utc`，但 SQLite 行要求 `trading_date`，计划也没有要求验证 point ID 是否存在于该日 write-once expectation。
- **反例/失败场景**: M2 point 只保存 canonical UTC target，不保存 trading date 或 scheduler timezone。实现者只能按 UTC 日期、硬编码 market timezone、扫描历史 artifact，或直接信任 point；前两种可能跨日错配，后两种允许 expectation 之外的 point 被计入某日 Corpus。随后按天计数可能表面完整但真实 expected identity 缺失。
- **为什么有问题**: W4 的核心动机正是事前冻结分母。捕获路径若不以 expectation 为 authority，数据库中的 `trading_date` 和完整性无法证明，违背 goal confirmation 的完整 denominator 与 gap fail-closed 信号。
- **直接证据**: `recommendation_point.v1` 的 `_POINT_FIELDS` 没有 trading date/timezone；`build_recommendation_point_id()` 只 canonicalize target 到 UTC。设计文档要求 expectation 预计算全部 point IDs，且禁止从 observed points 反推分母。
- **影响**: 数据归属错误、假完整、研究窗口污染、后续 W5 返工。
- **建议改法和验证点**: capture 必须显式接收 canonical `trading_date`，读取该日已绑定的 expectation artifact，并在任何 projection/artifact/DB 写前验证 market/account/date 及 point ID 精确成员关系。缺 expectation、late/conflicting expectation、wrong date 和 unexpected point 均不得形成 captured projection row；增加四个反例测试。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### PR-W4-02-未修复-高-成熟日期与证据哈希彼此没有语义绑定，任意字符串可被封成“最新成熟窗口”
- **位置**: §5 `freeze_research_dataset()`、§9 fixed-window selection
- **问题类型**: 信任边界 / 契约缺失 / 不可直接实施
- **当前写法**: API 分别接收 `latest_mature_trading_date`、`maturity_evidence_sha256`、calendar version/hash 和日期数组，只校验格式/相等关系，没有定义哪个 canonical payload 的 hash 必须等于哪个值。
- **反例/失败场景**: 调用方传入更早或更晚的 mature date，同时传入任意合法 64 位 hash；W4 会生成看似绑定 maturity evidence 的 dataset，但 hash 并不证明该 market/account/cutoff/date 组合。calendar hash 与日期数组同样可以来自不同事实。
- **为什么有问题**: 用户确认的是“调用方提供确定性事实并由 hash 绑定”，不是“W4 信任几个互不相关的字符串”。reference-only dataset 一旦封闭，W5 无法从其中恢复或审计选择依据。
- **直接证据**: plan §6 声称 dataset 绑定 calendar/maturity evidence，但 §5 的参数和 §9 的算法没有 canonical evidence object/ref 或 recomputed hash rule。当前代码库的 immutable contracts normally validate exact keys and recompute `content_sha256`/provenance before trust。
- **影响**: 错窗、不可审计的选择、隐藏回退、后续研究结论失去证据链。
- **建议改法和验证点**: 定义一个最小 exact-key `research_window_facts.v1` 输入，至少绑定 market/account/cutoff、完整 ordered calendar dates 的内部 hash、calendar version/receipt hash、latest mature date、maturity receipt ref/hash 和 selector version；对 canonical content hash 做重算。W4 不验证 provider 真伪，但必须验证这些选择事实相互绑定。测试篡改 date/list/cutoff/ref/hash 任一字段都失败。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR-W4-03-未修复-中-公开 freezer 可生成非 40 日 dataset，与已锁定 ExperimentSpec 合同冲突
- **位置**: §5 public contract、§9 final paragraph、§12 S2 tests
- **问题类型**: 目标漂移 / 契约缺失 / 测试缺口
- **当前写法**: `required_days=40` 对调用方可配置，并明确允许用小值构造 fixture。
- **反例/失败场景**: 运行调用方传入 `20` 或 `1`，W4 仍发布 schema-valid `sealed_historical_dataset.v1`；W5/W1B 才因 `research_evaluation.required_days` 必须为 40 而拒绝。一个不可能进入正式实验的 artifact 已被长期保存并可能被误报 ready。
- **为什么有问题**: W1B `contracts.py::_validate_research_evaluation()` 已硬性要求 40，Goal Confirmation 也确认固定 40 日。测试便利不能扩大生产 public contract。
- **直接证据**: `src/application/strategy_lab/top1/contracts.py` 对 `research_evaluation.required_days` 调用 `_fixed(..., 40, ...)`；design/control 文档称固定 40 日。
- **影响**: 跨模块合同不一致、误导 readiness、存储无效 artifact。
- **建议改法和验证点**: 保留形参以匹配设计签名也可以，但 public freezer 必须拒绝任何非 40 值；测试构造真实 40 日期/轻量空候选 projections，不开放测试后门。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### PR-W4-04-未修复-中-返回状态和稳定 reason code 未冻结，implementation 仍需发明公共行为
- **位置**: §5 public contract、§7、§9、§10
- **问题类型**: 不可直接实施 / 契约缺失
- **当前写法**: 计划只说返回 `dict`、expected gaps 不抛异常，并描述 conflict/warming/coverage 优先级；没有列出 seal/capture/freeze/status 的 exact status values、必需字段和错误 reason code 集。
- **反例/失败场景**: 一个 slice 把 feature-off 作为 exception，另一个返回 blocker；partial point 可能返回 success、gap 或 conflict；dataset artifact write conflict 可能被混入 corpus evidence conflict。测试只能追随实现，W5/W7 调用方也没有稳定契约。
- **为什么有问题**: Gateflow plan 必须 code-generation-ready。这里是跨 W4/W5/W7 的 public seam，不能把状态设计推迟给 implementation。
- **直接证据**: plan §5 的四个函数都只标注 `-> dict`；现有 M2/M3 boundaries use named schema/status values and stable `reason_code` contracts。
- **影响**: 实施漂移、测试迎合实现、后续调用方返工。
- **建议改法和验证点**: 在 plan 冻结最小返回形状：seal/capture 的 `published|idempotent|not_evaluable|conflict`，freeze 的 `ready|blocked` 与 exact blocker set，status 的 exact counters/date fields；列出仅用于 invalid input/unsafe artifact/schema 的 exception reason codes。增加 exact-key tests。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
