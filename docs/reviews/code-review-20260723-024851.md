## Findings

### 1 — fixed — high — optional close analysis introduced a production import cycle

- **Path**: `shadow_replay.analysis` -> `shadow_replay.readiness` ->
  `shadow_replay.capture` -> `shadow_replay.analysis`.
- **Failure**: attaching S4 close-policy analysis to the existing candidate
  analysis module made that module both a reusable candidate primitive and a
  higher-level close-analysis orchestrator. The generated dependency guard
  detected one production module cycle after the current `origin/main` graph
  was regenerated.
- **Fix**: moved the pure candidate analysis implementation to
  `shadow_replay.candidate_analysis`; internal candidate consumers now depend
  on that lower-level module. `shadow_replay.analysis` remains the compatible
  public facade and owns only dataset-level composition, including the
  optional close facet.
- **Coverage**: production dependency graph reports zero module cycles and no
  boundary violations; candidate-only and optional close-facet analysis tests
  pass through the public facade.

### 2 — fixed — medium — moving candidate analysis invalidated the explicit legacy-reference owner path

- **Path**: candidate analysis move -> performance legacy-reference scanner ->
  explicit allowlist.
- **Failure**: the scanner correctly reported the new file as unowned and the
  old file path as stale even though the same candidate-domain calculation had
  only moved ownership.
- **Fix**: replaced the old allowlist path with the new owning module while
  preserving the existing `candidate_strategy_domain` category. No legacy
  term or additional file was allowlisted.
- **Coverage**: exact allowlist inventory and stale-entry tests pass.
