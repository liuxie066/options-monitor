## Findings

### PR109-01-未修复-[高]-同一天只能成功发送第一批半点新增候选
- **裁决**: accepted
- **入口/函数**: `run_tick_notification_flow()` 的 scheduled candidate alert 路径，经 `prepare_daily_decision_brief_delivery()` 写入 v2 delivery state。
- **文件(行号)**: `src/application/tick_notification_flow.py:800-889`; `src/application/daily_decision_brief_repository.py:375-390,1682-1707`
- **输入场景**: 10:30 首次发现 NVDA，候选通知发送并确认；11:30 新 revision 仅新增 AMD，AMD 已进入 `pending_candidates`。
- **实际分支**: 每个交易日只有一个 `candidate_delivery` 槽。第二批 prepare 读取到已 `confirmed` 的旧 NVDA envelope；`_resolve_prepared_envelope()` 对内容不同且状态为 `confirmed` 的 envelope 直接返回旧值。
- **预期行为**: `alerted_candidates` 保留 NVDA 的已确认历史，同时 `candidate_delivery` 滚动为新的 AMD envelope；本轮立即发送第二条完整候选报告。
- **实际行为**: repository 保留旧 confirmed envelope；retry reader 不返回该 envelope；AMD 继续 pending 但本轮及后续半点都没有可发送 envelope。
- **直接证据**: `prepare_daily_decision_brief_delivery()` 将所有候选通知写入 `day["candidate_delivery"]`（375-390）；`_resolve_prepared_envelope()` 在 1699-1700 对 `confirmed` 无条件返回旧 envelope；notification flow 只发送 retry reader 返回的 envelope（881-890）。
- **影响**: 静默漏报；同一交易日只有第一批新增候选能被及时通知，违反 PRD“有效半点发现新增候选后当轮立即发送”和 identity 级日内去重合同。
- **建议改法和验证点**: 仅在候选分支、旧 envelope 已 `confirmed` 且新 delivery key 不同时允许滚动；`ambiguous` 继续冻结，pending exact retry 继续保持原 envelope，fixed reports 不变。增加 repository 两批 confirm 回归测试及 notification-flow 第二个半点发送测试。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR109-02-未修复-[高]-策略步骤异常会被 fail-closed 空 CSV 掩盖为正常无候选
- **裁决**: accepted
- **入口/函数**: `run_symbol_monitoring()` 的 Sell Put / Combo Yield 扫描异常路径，经 `assemble_daily_decision_brief()` 加载候选 artifacts，再由 fixed report renderer 输出。
- **文件(行号)**: `src/application/symbol_monitoring.py:204-275`; `src/application/sell_put_steps.py:342-348`; `src/application/daily_decision_brief_service.py:31-105,422-530`; `src/application/daily_decision_brief_renderer.py:322-329`
- **输入场景**: scheduled pipeline 进程整体返回 0，但某个启用的 Sell Put 或 Combo Yield step 在单 symbol 内抛异常；其他步骤继续执行。
- **实际分支**: 异常被捕获后仅记录日志，并生成与“策略禁用/真实空结果”相同的空 CSV；assembler 将受控空 artifact 视为 `available=True`；若没有其他 blocker，renderer 输出“本轮暂无符合条件的候选”。
- **预期行为**: 保留其他策略的可靠结果，但结构化记录失败 family/symbol；对应 family 不得由失败生成的空 artifact 证明“正常可用”。若所有决策源均不可靠则 blocked/fixed failure；若仍有其他可靠来源则 degraded，并在用户消息中明确“部分策略扫描失败、结果不完整”。
- **实际行为**: 用户无法区分“扫描成功但无候选”和“策略代码异常后被清空”，存在错误决策依据。
- **直接证据**: Sell Put 与 Combo Yield catch 均在写空 artifacts 后继续返回 summary（204-275）；Sell Put empty materializer 写入只有换行的 CSV（342-348）；candidate loader 将该受控空文件标记为 available（422-530）；非 blocked 且无 candidates 时 renderer 固定输出正常空结果（322-329）。
- **影响**: 错误状态/错误报告；核心监控故障被静默降格为“正常无候选”。
- **建议改法和验证点**: 在 strategy orchestration owner 捕获异常时复用 run-scoped `candidate_filter_trace.jsonl` 写结构化 `strategy_execution / strategy_step_failed` 记录；assembler 将失败 family 加入 data gaps，并在无该 family 可靠候选时撤销其 availability；renderer 对 partial failure 使用简短明确提示。验证真实空结果仍正常、部分失败保留其他候选并 degraded、所有候选来源失败时 blocked。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高
