# Plan Review — Option Performance Refactor Gateflow Plan

- **Reviewed target**: `docs/gateflow/option-performance-refactor-plan-20260717-224048.md`
- **Scope**: architecture ownership, public contracts, valuation/FX evidence, assigned-stock boundary, capital math, implementation slices, tests and migration readiness。
- **Review posture**: constructively adversarial；判断计划是否 code-generation-ready，而不是方向是否良好。
- **Conclusion**: `fail`

## Assumptions tested

1. `instrument_key` 可由实现者无歧义推导。
2. 已有 quote/rate adapter 足以让 current/historical unrealized 和 period-total PnL 实际可用。
3. S5 可以在不改变 ledger public API 的情况下合法读取 assigned-stock facts。
4. 新 Agent/CLI contract 已足够精确，consumer migration 有明确 file ownership。
5. capital-days 公式足以处理盘中开平、partial close 和 assignment transition。
6. evidence import/schema 初始化不会让 pure-read path产生隐式写入或格式猜测。

## Findings

### PR2-01-未修复-高-Valuation instrument identity 未定义，mark 可能跨账户/方向错配或无法匹配
- **位置**: §4.7 Valuation and FX evidence；S4。
- **问题类型**: 契约缺失 / 架构边界 / 不可直接实施
- **当前写法**: 表中只有 `instrument_key`，selector 按 key 查询，但计划没有定义 option/stock key 的字段、规范化和与 `ContractKey` 的关系。
- **反例/失败场景**: 实现者直接使用 `ContractKey.position_key`，该 key 含 broker/account/position side；同一市场期权的 mark 被重复存储且另一个账户无法复用。另一实现者只用 symbol/strike/expiry，忽略 option type、multiplier 或 currency，导致 call/put 或调整后 contract 错配。
- **为什么有问题**: valuation identity 是 evidence schema 的主键语义。数据库落地后再修改会产生迁移和历史证据孤儿。
- **直接证据**: `domain/domain/ledger/identity.py` 的 `ContractKey` 面向持仓身份，包含 broker、account、position side；计划表只写 `instrument_key`，未给编码函数或唯一字段集合。
- **影响**: 错误 mark / unrealized PnL 错误 / 跨账户重复事实 / schema migration返工。
- **建议改法和验证点**:
  - 在 S1/S4 前定义 `OptionInstrumentKey` 与 `StockInstrumentKey`；option key 至少含 canonical symbol、option_type、strike Decimal、expiration_ymd、currency、multiplier，不含 account/broker/position side；stock key含 canonical symbol/currency。
  - 固定 deterministic string codec 和 round-trip tests；`ContractKey` 必须通过显式函数转换，不直接复用 `position_key`。
  - evidence table 增加结构化 identity columns 或明确 key codec version。
- **修复风险（中）**: 需要修 plan 和 schema，但未实施前成本可控。
- **严重程度（高）**: S4 blocker。

### PR2-02-未修复-严重-计划只有 evidence 存储/导入，没有 current option mark 获取与持续留存路径，核心 total PnL/bridge 会常态不可用
- **位置**: §4.7、§4.11、S4、S7、S9。
- **问题类型**: 动机未闭环 / 切片缺失 / 不可直接实施
- **当前写法**: current query “may use injected live evidence”；S4 增加 evidence repository；S7 只有文件 import CLI；历史 query 禁止 live。没有说明 public Agent/CLI 如何为所有 open option contracts 获取 current mark，也没有定义何时把 current mark/FX 显式捕获为未来 historical evidence。
- **反例/失败场景**: 用户首次运行 `option_performance_report --period ytd`，本地没有 option mark file；当前 open option 的 ending unrealized 为 null，period total null，PnL bridge unavailable。第二天回看昨天，因没有任何 capture workflow，仍无历史 mark。系统“支持”表结构但无法生产用户需要的实际数据。
- **为什么有问题**: objective 明确要求历史估值与 FX、period total PnL 和合法 PnL bridge。仅提供手工 JSON import 不足以让生产读路径闭环。
- **直接证据**:
  - 现有 `src/application/opend_market_snapshot_fetching.py` 与 `src/application/opend_symbol_fetching.py` 有 option snapshot batch fetch 能力，但计划未指定复用函数或 allowed files。
  - 现有 monthly report realtime refresh 只覆盖 assigned-stock spot（`src/application/positions/assigned_stock_quotes.py`）。
  - S7 public input没有 mark injection字段；S4不允许修改任何 quote adapter。
- **影响**: unrealized/period-total/bridge 主功能常态 null / 历史确定性无法积累 / 实现 Agent被迫临场新增 workflow。
- **建议改法和验证点**:
  - 增加明确的 `valuation evidence collection` application path：current report 在 `refresh_quotes=true` 时只读获取 open option/assigned-stock marks与 current FX，作为本次 `live_unpersisted` evidence；历史查询不获取。
  - 增加显式 `option-performance evidence capture` CLI（dry-run默认、apply需确认），复用同一 fetch adapter并把 mark/FX写入 evidence tables；报告本身仍不写。
  - 定义 open option code 构造/批量 fetch、mid选择、quote timestamp/stale/missing规则。
  - S4/S7 allowed files 和测试加入 `opend_market_snapshot_fetching` adapter seam；测试 current fetch、capture dry-run/apply、次日 historical replay。
- **修复风险（高）**: 增加一个必要 vertical slice或扩展 S4/S7，但这是目标闭环所必需。
- **严重程度（严重）**: total PnL、historical evidence和PnL bridge blocker。

### PR2-03-未修复-高-S5 未给 assigned-stock facts 合法 ledger API，计划会继续跨边界 getattr repository internals
- **位置**: §3.1 ownership；S5 allowed files。
- **问题类型**: 架构边界 / 过度耦合 / 不可直接实施
- **当前写法**: performance service 必须消费 `assigned_stock_events`，但 S5 allowed files没有 `src/application/ledger/api.py`/`queries.py`；现有代码多处通过 `getattr(repo, "list_assigned_stock_events")` 穿透 repo。
- **反例/失败场景**: implementation 在 `performance/adapters.py` 复制现有 getattr访问，以绕开 allowed files。新性能模块依赖 concrete repository method，违反“非 ledger 模块通过 ledger application boundary”的项目 contract。
- **为什么有问题**: 计划声称修复 ownership，却没有为第二条 canonical fact stream建立只读 public boundary。
- **直接证据**:
  - `src/application/ledger/api.py` 暴露 `trade_event_log`，但没有 `assigned_stock_event_log`。
  - `src/application/agent_tools/operations_impl.py:377-379`、`materialization_impl.py:349-350` 当前直接 getattr。
  - AGENTS contract要求非 ledger 模块不导入 ledger internals，ledger application boundary位于 `src/application/ledger/api.py`。
- **影响**: 新模块继续绑定 concrete SQLite repo / 测试只能用宽 mock / ownership整改不完整。
- **建议改法和验证点**:
  - S5 allowed files加入 ledger `queries.py`/`api.py`，新增 `assigned_stock_event_log(repo)` read facade与protocol validation。
  - performance、legacy report和agent operations统一通过 facade读取；逐步移除本 scope 内的 direct getattr。
  - 添加 facade contract/test double测试。
- **修复风险（低）**: 小范围边界补齐。
- **严重程度（高）**: S5 implementation blocker。

### PR2-04-未修复-高-新 Agent/CLI 输入、current quote行为和 consumer write set 未完全规格化

- **为什么有问题**: Gateflow plan必须让 implementation不再设计 public behavior或猜 file ownership。当前描述在最用户可见的入口仍留有决策。

- **建议改法和验证点**:

### PR2-05-未修复-高-capital-days 未定义时间积分单位和状态切换边界，盘中/同日交易会出现0或重复资本
- **位置**: §4.9；S6。
- **问题类型**: 契约缺失 / 状态机漏洞 / 测试缺口
- **当前写法**: 公式使用 `notional * active_days`，但没有定义 active_days是整数自然日、inclusive天数还是毫秒比例；没有定义 close/assignment instant前后option和stock capital如何衔接。
- **反例/失败场景**: 同日开平若用日期差得到0 capital-days，annualized efficiency不可用；若两端inclusive得到1天。assignment时short-put collateral和stock basis在同一自然日都计满一天，double count。partial close后剩余quantity的资本降低时点也不明确。
- **为什么有问题**: capital efficiency是本次要替代错误return rate的用户可见指标；分母不精确会重现同类问题。
- **直接证据**: 计划只写 `active_days` 和三种basis；现有 assigned-stock实现使用timestamp/day计算但未成为全局contract。
- **影响**: efficiency不稳定 / 同日交易极端值 / assignment资本重复 / 不同实现不一致。
- **建议改法和验证点**:
  - 内部统一 `capital_milliseconds = notional * overlap_ms / 86_400_000`，公共字段命名 `capital_days`但值允许Decimal小数。
  - event interval采用 `[open_at, close_at)`；assignment instant结束put capital并开始stock capital，不重叠。
  - partial close在close instant减少quantity；current open exposure截至period end exclusive。
  - 增加同日开平、盘中partial close、午夜边界、assignment transition测试。
- **修复风险（中）**: 合同明确后实现可控。
- **严重程度（高）**: S6 blocker。

### PR2-06-未修复-中-Evidence schema初始化与import/capture格式未定义，pure-read和幂等性仍需实现者猜测
- **位置**: §4.7；S4/S7。
- **问题类型**: 契约缺失 / 恢复风险 / 不可直接实施
- **当前写法**: 计划给SQL和幂等规则，但没有定义schema初始化发生在哪个gate/path、read-only DB无表时行为、import file envelope、batch原子性和correction validation。
- **反例/失败场景**: evidence repo constructor在每次report时执行DDL，pure-read tool发生隐式写；batch import前半成功后半冲突，留下部分事实；supersedes指向不存在或不同instrument的fact。
- **为什么有问题**: operations-sensitive repo要求write path显式、可dry-run、可恢复。表结构存在不等于write state machine完整。
- **直接证据**: 当前 `SQLiteOptionPositionsRepository.__init__` 会 `_init_db()`；plan另建repository却未选择是否复用该模式。S7只写“file facts.json”。
- **影响**: pure-read side effect / partial import / evidence chain损坏 / recovery困难。
- **建议改法和验证点**:
  - schema DDL由显式 idempotent migration函数管理；read path若表不存在返回empty/not_initialized且不DDL。
  - import格式固定 `schema_version + valuation_marks[] + fx_rates[]`；全batch单事务；dry-run执行完整validation但不写。
  - correction必须same identity、target存在、不能形成supersede cycle；冲突回滚整批。
  - capture/import apply复用CLI local-write safety。
- **修复风险（低）**: plan补充即可。
- **严重程度（中）**: 应在S4前修复。
