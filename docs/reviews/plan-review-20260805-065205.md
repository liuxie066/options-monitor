# Plan Review

## Reviewed target and scope

- **Target**: 当前会话中针对 `trade-intake` 持续高 CPU 的通用治理方案
- **Review mode**: adversarial minimal-correctness review
- **Scope**: 当前事故止血、永久不支持 provider capability、无进展重试、immutable evidence admission、lifecycle revision/outbox、恢复 trade intake 的最小验收门
- **Excluded**: 实现、生产服务重启、历史证据删除或压缩、数据库迁移、发布和部署

## Goal and boundary understood

当前目标不是一次完成通用任务平台重构，而是安全恢复实时 trade intake，同时确保同一类“任务永久无法完成、轮询事实不变、但时间戳让每次结果看起来都不同”的故障不再形成无界 provider 调用、无界 immutable evidence、无界 revision 和越来越昂贵的全量 read-model 重算。

生产止血已经通过停止 `options-monitor-trade-intake.service` 完成；它是正确且可逆的事故控制，但不是最终修复。最小正确修复必须让 listener 可以恢复，同时在进入 account/case 全量读取和 provider 查询之前阻断已知永久不支持的 settlement collector，并在一般的“无进展”场景下保证重复事实不进入业务状态。

## Assumptions tested

1. 当前 `cash_flow_query unavailable` 可以在 provider collection 之前稳定识别，而不是必须对每个 case、每个 clearing day 实际调用后才能知道。
2. `broker_settlement_observation` 的业务事实与“本次在什么时间尝试过”可以使用不同 fingerprint；尝试时间本身不应推进 lifecycle 业务状态。
3. 同一 incomplete semantic result 不需要重复写入 canonical lifecycle evidence。
4. 恢复 push listener 和 history backfill 不要求同时完成 scheduler/job table、服务拆分、历史压缩和 read-model 重写。
5. 只加 source capability 特判能解决当前事故，但不能覆盖 provider 存在、返回内容却长期不变的同类无进展循环。
6. 只做 evidence 去重也不够，因为当前已有的历史 evidence 会让每分钟 due scan 本身继续昂贵，provider 查询也仍会持续发生。

## Special review lenses

### Architecture boundary review

provider capability 属于 gateway/runtime source 边界；是否到期和是否需要业务 reconciliation 属于 lifecycle owner；attempt scheduling/backoff 属于运行控制；immutable evidence 和 revision 属于 ledger 业务状态。原方案的长期分层方向正确，但最小热修不需要先把这些 owner 拆成独立 systemd 服务。

### Best-practice review

重试必须同时具备 eligibility、进展判断和 admission guard。永久不支持应在昂贵读取前 fail-closed；相同业务事实必须 idempotent；attempt receipt 不得仅因当前时间变化而制造业务 revision。

### Optimal-solution review

最小闭环是两层保护：一层在 due collector 入口做 source capability/kill-switch gate，另一层在 observation admission 做 semantic no-progress fingerprint、bounded backoff 和 no-write。它直接切断当前 CPU 路径，也保留对同类故障的通用不变量。新任务表、服务拆分和历史迁移不是恢复 listener 的前置条件。

### Overengineering review

原方案同时包含 scheduler 状态机、新 attempt/evidence 模型、bounded read model、listener/backfill/reconciler/notification 服务拆分、lease、指标和历史治理。作为长期防线合理，但作为“最小正确修复”范围过大，交付路径和回滚面明显超过当前根因所需。

### Overcoupling review

继续把 due reconciliation 放在 listener 的同一 `process_lock` 下会让一个可选的 provider reconciliation 阻塞 push、inbox retry 和 backfill。最小修复不必立刻拆服务，但必须允许 due collector 被独立禁用或短路，并保证短路发生在 account/case read-model 之前。

## Findings

### PR-01-未修复-高-完整治理方案不是当前事故的最小正确修复，恢复 listener 被不必要地绑定到多项迁移

- **位置**: 原方案 P1-P3：scheduler/job state、attempt/evidence 拆分、bounded read model、服务拆分、lease、metrics 和历史治理
- **问题类型**: 过度设计 / 交付边界 / 恢复风险
- **当前写法**: 把当前事故修复描述为一套完整的通用任务执行框架，并把服务隔离、持久化状态机、数据治理和可观测性共同纳入解决方案。
- **反例/失败场景**: `trade-intake` 已停止止血。如果必须先完成新表、新服务、新 lease 和历史迁移才恢复 listener，实时 push/backfill 的离线窗口会被显著拉长；任何一个迁移错误还会扩大到原本健康的 intake 路径。
- **为什么有问题**: 当前直接触发器在 due collector 入口可确定：gateway 已明确暴露 `cash_flow_query unavailable`，但 listener 仍每 60 秒在同一主循环、同一锁内重新执行。恢复健康 intake 只需要先让该可选 collector 在昂贵读取前被独立 gate，并封住相同事实重复进入业务状态的 admission 漏洞。
- **直接证据**:
  - `src/application/trades/auto_intake.py:1544-1576` 每 60 秒在 listener 主循环和 `process_lock` 内执行 due reconciliation。
  - `src/application/trades/lifecycle_runtime.py:155-185` source wrapper 无 capability gate，直接创建 collector 并扫描 account cases。
  - `src/infrastructure/futu_gateway.py:214-222` 已能在本地通过 `hasattr(..., "cash_flow_query")` 确认 capability 不存在。
  - `src/application/trades/settlement_observation.py:211-249` 对 clearing-date range 逐日调用 cash-flow query；当前生产环境对每个 due case 都重复走该失败路径。
- **影响**: 方案可以最终提高系统韧性，却不是最短的安全恢复路径；实现周期、回滚面和 intake 离线时间都被放大。
- **建议改法和验证点**:
  - 把第一交付切成独立 hotfix：增加 `lifecycle_due_reconciliation.enabled` kill switch，并在 source 启动时做 required-capability preflight。
  - capability 不满足时记录 typed runtime status `blocked_capability`，跳过整个 account due reconciliation；不得读取 case bundle、调用 provider、写 evidence、推进 revision 或创建 outbox。
  - listener、push inbox retry 和 backfill 保持运行；不修改 case 的 `needs_review/cause_pending` 业务含义。
  - 新任务表、独立服务、lease、历史治理和完整 metrics 作为后续 hardening，不作为恢复前置门。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### PR-02-未修复-高-只做 capability 特判不是通用解；必须保留“无进展不写入、不热重试”这一最小业务不变量

- **位置**: 原方案 attempt/evidence split、semantic fingerprint、backoff/circuit breaker
- **问题类型**: 幂等性 / 状态机 / 通用性
- **当前写法**: 长期方案包含这些能力，但没有把它们压缩成 hotfix 后唯一必要的第二道 correctness gate；容易在追求最小改动时退化为仅特判 `cash_flow_query`。
- **反例/失败场景**: provider 方法存在并成功返回，但某 required source 长期为空、权限受限或 coverage incomplete。每次 payload 的业务内容完全相同，只有 attempt/observation 时间变化。如果仅修 capability，系统仍会每分钟写一条新 evidence 并推进 revision。
- **为什么有问题**: 当前问题的可迁移根因不是某个 Futu 方法名，而是“易变 attempt metadata 被纳入 immutable business identity，且 no-progress 没有 backoff/admission guard”。不保留这条不变量，同类事故会在下一个 provider/source 上重现。
- **直接证据**:
  - `src/application/trades/close_reason_evidence.py:268-326` 把 `observed_at_ms` 和包含观察时间的 source receipts 放入 payload，再对整个 payload 计算 `observation_id`。
  - `src/application/ledger/repository.py:1335-1376` 仅按 `evidence_id` 幂等；时间变化导致新 id，因此每次都会插入新的 immutable row。
  - `src/application/ledger/writer.py:2214-2244` state fingerprint 包含该 case 的全部 evidence rows，新增等价 observation 会被视为业务状态变化并增加 resolution revision。
  - `src/application/ledger/repository.py:2942-2983,3104-3125` 单 case read 实际读取并 JSON 解析整个 account 的 lifecycle evidence；即使后续停止新增，热重试仍会重复承担已有历史成本。
- **影响**: 仅修当前 capability 后，数据和 CPU 的无界增长模式仍存在，不能称为“解决此类问题”的通用最小方案。
- **建议改法和验证点**:
  - 为 observation 计算排除 `observed_at_ms`、attempt receipt timestamps 和其他易变传输字段的 `semantic_fingerprint`。
  - 相同 case generation + 相同 semantic fingerprint 的 incomplete result：不插入 lifecycle evidence、不更新 state fingerprint、不增加 resolution revision、不创建 notification outbox。
  - 将本次尝试只记录为有界 runtime attempt receipt，并设置指数 backoff；永久错误 park，generation/capability fingerprint 改变或显式 operator resume 后再 eligibility。
  - hotfix 可以复用现有 source checkpoint/status ownership，不要求先迁移全部历史 evidence；但 admission guard 必须位于 canonical writer 之前。
  - 回归测试使用 fake clock 连跑至少 10 个 due tick：相同语义、不同时间戳时 evidence count/revision/outbox 恒定，provider 调用受 backoff 上界约束；语义或 generation 改变时允许一次新 evidence。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR-03-未修复-中-历史 read-model 优化应延期，但恢复门必须证明旧膨胀数据不会重新成为热路径

- **位置**: 原方案 bounded read model、历史压缩/迁移
- **问题类型**: 范围控制 / 性能验收
- **当前写法**: 将 bounded read model 与历史治理列为完整方案的一部分，容易误解为 hotfix 必须先迁移现有数据；反过来，若完全忽略既有约 30 MB observation JSON，又可能在恢复后误入旧的全量 case read 路径。
- **反例/失败场景**: 新 admission guard 阻止后续写入，但 source gate 放在 `lifecycle_case_read_model()` 之后。两个已有膨胀 case 仍会在每分钟 tick 中重复读取、解析、分组和 hash 账户全部 evidence，CPU 问题依旧存在。
- **为什么有问题**: 是否迁移历史和是否让历史离开周期性热路径是两个不同问题。前者可延期，后者是恢复正确性的必要验收。
- **直接证据**:
  - `src/application/trades/close_reason_reconciliation.py:631-658` 对 account 中每个 case 构建 read model，再判断是否进入 observation。
  - `src/application/ledger/repository.py:2962-2983` account bundle 会加载全部 lifecycle evidence JSON。
  - 生产止血前两个 stuck cases 已累计约 2,100 条 settlement observations、约 30 MB raw JSON；服务停止后 evidence count 保持稳定，证明增长源已被切断，但历史成本仍存在。
- **影响**: hotfix 可能名义上去重成功，实际仍因 gate 顺序错误保持高 CPU。
- **建议改法和验证点**:
  - capability/kill-switch gate 必须位于 `reconcile_due_lifecycle_cases()` 和任何 account/case bundle read 之前。
  - 恢复 canary 验收：unsupported capability 下 provider calls 为 0（除一次轻量 capability probe）、lifecycle evidence/revision 不变、trade push/backfill 正常、CPU 回落。
  - 历史压缩、摘要表和 bounded resolver 作为单独 work unit；在 admission 修复前不得删除或重写 canonical evidence。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

## Open Questions

- runtime attempt/backoff checkpoint 的最小持久化 owner 需要在实现前按现有单进程/多进程约束确定；这不改变两条必要不变量，也不要求先建设完整通用 job platform。
- provider capability fingerprint 的刷新触发可以先限定为进程启动和显式 operator resume；动态热刷新不是当前恢复前置条件。

## Residual risks and tracking

- source-level capability gate 会让相关 cases 保持 `needs_review/cause_pending`；这是 fail-closed 的预期业务状态，不应伪造 settlement 结论。
- 在受控恢复前，`options-monitor-trade-intake.service` 应继续保持停止；旧 binary 一旦重启会恢复原 60 秒热循环。
- 首个 hotfix 不清理历史 evidence，因此偶发人工 case inspection 仍可能较慢；这属于后续 bounded read-model/data-governance work unit。
- 一个 systemd 服务内共享 `process_lock` 的故障域仍然偏大；独立 reconciler 服务是合理 hardening，但不是本事故的最小正确修复。

## Minimal corrected plan

1. 保持当前 service 停止，先加入独立 due-reconciliation kill switch 和 source required-capability preflight；短路必须发生在 account/case read 前。
2. 加入 semantic no-progress admission guard：相同 generation + 相同语义的 incomplete observation 不写业务 evidence、不推进 revision/outbox，并进入 bounded backoff/park。
3. 运行 deterministic tests 和本地性能回归；随后受控 canary 恢复 listener，分别验证 push/backfill、provider call count、evidence/revision/outbox、CPU 和 typed blocked status。
4. 将 bounded read model、历史治理、独立服务、lease 和完整 observability 拆为后续 hardening，不阻塞本次恢复。

## Final conclusion

**fail**

原完整方案是合理的长期防线，但不是解决当前事故的最小正确方法。最小正确闭环只有两条不可删减的运行不变量：**不具备能力或无进展时不热重试；相同业务事实不进入新的 evidence/revision/outbox**。当前恢复还要求 capability gate 位于任何膨胀 account/case read 之前。服务拆分、新 job platform、历史迁移和全面指标均可延期。
