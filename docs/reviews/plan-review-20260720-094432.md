# Plan Review: 自动 major/minor/patch 分类与确认采用

- Review timestamp: 2026-07-20 09:44:32 +0800
- Reviewed target: 本轮对话中的《自动版本分类与确认采用设计》
- Scope: `version_update` 自动推荐、Git 基线与证据采集、major/minor/patch 分类、recommendation digest、用户确认、人工 override、测试与发布流程集成
- Review posture: adversarial, implementation-readiness focused
- Conclusion: **fail**

## Goal and claimed boundary

方案目标是复用现有 `version_update`，对当前 release diff 自动推荐 `major|minor|patch`，展示证据和置信度，用户确认后只原子更新 `VERSION`；不自动修改 CHANGELOG、不 commit、不 push、不发布、不执行生产升级。方案同时声明分类应确定性运行、不依赖外部模型，并用 `recommendation_id` 阻止确认后工作区漂移。

## Assumptions tested

1. 当前代码已有足够结构化信息，可以确定性识别 Agent Tool、CLI、配置、输出 schema、运行时下限和 source-of-truth 的兼容性变化。
2. “当前 HEAD 可达的最新稳定 tag”足以作为版本推荐基线，并且不会与远端最新 release 冲突。
3. `recommendation_id + confirm=true` 等价于“用户看过推荐并明确确认”。
4. `CHANGELOG.md / Unreleased` 在推荐时通常已填充，能够成为高权重分类证据。
5. 人工 `bump` / `target_version` 路径可以在保持兼容的同时受自动推荐下限约束。
6. 当前测试清单足以证明 Git 状态、分支偏离、tag 漂移、确认过期和 override 安全。
7. 一次实现可以可靠覆盖 CLI、Agent Tool、配置、输出、Python 下限和 source-of-truth 等多个公共契约面，而不迫使实现 Agent 临场重新设计。

## Findings

### PR-01-未修复-严重-分类器缺少可执行的公共契约提取规范，无法安全交给 implementation agent
- **位置**: “分类输入”“自动分类规则”“代码边界”
- **问题类型**: 不可直接实施 / 契约缺失 / 架构边界
- **当前写法**: 方案要求自动识别删除或新增 Agent Tool、CLI 命令、配置字段、输出字段、Python 下限、数据迁移和 source-of-truth 变化，并据此产生确定性的 major/minor/patch 证据，但没有规定每类证据从什么 canonical representation 提取、如何比较 base/head、哪些变化算删除/重命名/语义改变，以及解析失败时的状态。
- **反例/失败场景**: `src/application/agent_tools/runtime.py` 内部重构把一个 Tool 定义移动到另一模块，文本 diff 同时出现删除和新增；基于 unified diff 或路径规则会误判 major。相反，输出字段保留名称但语义改变，文本规则可能只看到普通函数修改并误判 patch。CLI 参数可以通过 helper 间接注册，配置默认值可以从常量或 overlay 继承，路径匹配无法证明兼容性。
- **为什么有问题**: 当前仓库的 release planner 只根据文件路径映射测试风险，不具备语义契约比较能力。方案新增一个模块名并列出结果字段，却把最困难的 base/head contract extraction 留给实现 Agent 决定，违反 code-generation-ready 要求。若临场采用 regex/路径启发式，工具会用“确定性”外观输出不可靠结论。
- **直接证据**: `src/application/release_test_plan.py:15-24` 的现有规则模型只有 `patterns/reason/commands/risk`；`src/application/release_test_plan.py:59-72` 把整个 CLI/Agent surface 仅映射到测试命令；`src/application/agent_tools/runtime.py:167-190` 表明 Agent Tool contract 由 Python 构造，不存在已签入的 base contract snapshot 可直接比较；发布 workflow 只在构建时生成当前 `om-agent-spec.json`，见 `.github/workflows/_release-reusable.yml:36-41`，没有 previous-release spec comparison。
- **影响**: 实现 Agent 必须重新设计 extractor；分类可能稳定地误判 breaking change；用户确认建立在错误证据上；后续 review 无法证明 major/minor/patch 的 correctness。
- **建议改法和验证点**:
  1. 把 v1 支持范围缩成明确、可解析的信号：规范化 `Unreleased` impact、Git name-status、少量 hard guards（例如 `requires-python`、已签入 schema/manifest）。
  2. 对未建立 canonical snapshot 的 CLI/config/output/source-of-truth 只返回 `classification_status=needs_review`，不得伪装成 high-confidence 自动判定。
  3. 如果必须自动比较 Agent Tool contract，先定义并签入稳定 contract snapshot，明确 base artifact 获取和字段兼容规则，再进入后续 slice。
  4. 验证重命名、移动实现但契约不变、字段名不变但语义改变、helper 间接注册和解析失败场景。
- **修复风险（高）**: 需要收敛产品承诺和契约真源，而不只是补代码。
- **严重程度（严重）**: 当前计划不是 code-generation-ready。

### PR-02-未修复-高-本地可达 tag 基线可能落后远端，生成已占用或错误的目标版本
- **位置**: “分类输入”“防止确认后变更漂移”
- **问题类型**: 状态机漏洞 / version skew / 契约缺失
- **当前写法**: 默认基线是“当前 HEAD 可达的最新稳定 Release tag”；本地没有 tag 时才 fail closed。`recommendation_id` 绑定该本地基线。
- **反例/失败场景**: 分支从 `v1.3.0` 创建后，远端已经发布 `v1.3.1`，但该 tag 不可达或尚未 fetch。本地 classifier 基于 `1.3.0` 推荐 patch 目标 `1.3.1`。用户确认后 VERSION 被写为已存在的远端版本；合并到 main 后 release workflow 尝试再次发布同名 tag，或者 release metadata 指向错误变更集合。另一个反例是远端最新 tag 为 prerelease：当前 tag parser 会接受并参与排序，但方案只写“稳定 tag”，没有稳定版过滤定义。
- **为什么有问题**: 发布版本是远端全局命名空间，不是当前分支的局部状态。只绑定本地 reachable tag 可以防工作区漂移，却不能防远端版本竞争、陈旧 clone 或平行 release。
- **直接证据**: `src/application/release_target.py:12-13` 接受 prerelease tag；`src/application/release_target.py:64-84` 的 `select_latest_release` 不过滤 prerelease；只有远端升级 target resolver 会刷新 cache 后选 tag，见 `src/application/release_target.py:139-175`。而 Release-from-VERSION workflow 只读取 VERSION 生成 tag，见 `.github/workflows/release-from-version.yml:19-27`，没有 predecessor 或 tag collision preflight。
- **影响**: 版本碰撞、错误 target version、发布 workflow 失败，或者把分支变更归到错误 release baseline。
- **建议改法和验证点**:
  1. 明确 baseline authority：默认从 `origin` 查询最高稳定 release tag，并验证 tag object/commit 可用；离线时返回 degraded/needs-input，而不是使用陈旧 reachable tag冒充权威。
  2. 验证 baseline commit 与目标分支的 ancestry；分支落后时要求 rebase/merge 或显式 base override。
  3. 明确定义 prerelease 是否参与 recommendation；稳定发布默认必须排除 prerelease。
  4. 确认前再次查询远端 tag namespace，拒绝目标版本已存在或 baseline 已变化。
  5. 增加 stale clone、parallel release、unreachable latest tag、existing target tag 和 prerelease-only tag 测试。
- **修复风险（中）**: 可复用现有远端 tag 解析，但会引入明确的网络/离线行为契约。
- **严重程度（高）**: 可能直接阻断或污染发布。

### PR-03-未修复-高-recommendation_id 只能证明新鲜度，不能证明用户确认
- **位置**: “用户交互流程”“防止确认后变更漂移”“现有 Tool 契约调整”
- **问题类型**: 状态机漏洞 / 权限与确认边界 / 过度耦合
- **当前写法**: 方案把 `recommendation_id` 描述为“无状态确认凭证”，并认为 `recommendation_id + apply=true + confirm=true` 完成用户确认，不需要 pending-operation 存储。
- **反例/失败场景**: 调用 Agent 在同一轮拿到 recommendation_id 后自行再次调用 `version_update`，设置 `confirm=true`；底层工具无法区分这是用户确认还是模型自动填充。另一个调用方可以复制 recommendation_id。digest 能证明输入未变，但不包含谁确认、何时确认、用户是否看到推荐，也没有 TTL 或一次性消费语义。
- **为什么有问题**: freshness token 与 authorization receipt 是两个不同概念。当前低层 Tool Gateway 的确认门本来就只检查环境开关和布尔值，不能支撑方案声称的“两阶段用户确认”语义。仓库内真正的聊天确认流程使用持久 operation、payload hash、TTL 和 operation resolution，说明项目已有更强边界。
- **直接证据**: `src/application/agent_tools/permissions.py:18-33` 只验证写开关和 `confirm/yes` 布尔值；`src/application/agent_tools/runtime.py:167-189` 的 `version_update` 也是这个低层 contract。相比之下，`src/application/assistant/upgrade_operations.py:89-105` 会创建 previewed operation，`:108-145` 在确认时解析 operation、校验 payload hash、过期状态并标记 confirmed。
- **影响**: 系统可能在没有真实用户确认的情况下写 VERSION；不同 surface 对“确认”含义不一致；审计和恢复语义不成立。
- **建议改法和验证点**:
  1. 把 `recommendation_id` 重命名/定义为 `evidence_digest` 或 `recommendation_digest`，只承担 staleness check。
  2. 明确 v1 surface。若只支持 Codex/本地 CLI，写清调用方必须完成外部人机确认，底层只执行显式 `confirm=true`；不要声称工具自身证明了用户确认。
  3. 若支持 WeChat/Assistant 自然语言确认，必须复用 `InboundOperationStore` 的 preview/confirm/cancel/TTL/payload-hash 状态机，而不是另造无状态确认。
  4. 测试同轮自动 confirm、过期确认、重复确认、错误 operation、payload hash mismatch 和 recommendation drift。
- **修复风险（中）**: 需要先锁定产品 surface；低层 CLI 路径可保持简单，聊天路径需复用现有 operation framework。
- **严重程度（高）**: 当前方案对用户授权提供了错误安全保证。

### PR-04-未修复-高-Unreleased 被当作高权重证据，但现有发布流程不保证推荐前存在该内容
- **位置**: “分类输入”“自动分类规则”“置信度设计”
- **问题类型**: 错误假设 / sequencing / 测试缺口
- **当前写法**: `Unreleased/Breaking|Added|Fixed` 是 major/minor/patch 的核心信号；Changelog 与代码一致时可给 high confidence。方案没有规定开发阶段何时、由谁维护 Unreleased，也没有规定先推荐版本还是先生成对应 changelog。
- **反例/失败场景**: 当前项目通常在 release metadata commit 中直接新增版本段落，功能实现结束时 `Unreleased` 仍为空。此时自动推荐发生在 changelog 编写前，只能依赖未定义的静态启发式，high-confidence 主路径不可达。若要求先由人写 `Added/Breaking`，则关键语义其实已经由人分类，所谓“自动分类”只是读取人工标签。
- **为什么有问题**: 这是一个流程前置条件，却没有进入 goal、non-goal、sequencing 或 acceptance criteria。未收敛它会让实现和文档走向两套不同产品：自动推断器或 changelog-driven recommender。
- **直接证据**: 当前 `CHANGELOG.md:1-5` 的 `Unreleased` 为空，随后直接是 `1.3.0` 版本段；现有 `scripts/release_check.py` 只要求目标版本段存在，不要求开发过程维护 Unreleased。现有版本更新函数只写 VERSION，见 `src/application/version_check.py:68-72`。
- **影响**: 推荐长期低置信度、使用者绕过工具、分类规则依赖不可验证文本，或实现被迫扩大为 changelog 自动生成器。
- **建议改法和验证点**:
  1. 先做产品选择：A) 把标准化 Unreleased 设为强制 release input；或 B) 明确它只是辅助证据，自动分类不得依赖其存在。
  2. 若选 A，更新发布 sequencing：先维护 Unreleased，再推荐版本，再确认，再把 Unreleased 固化到版本段；定义谁完成固化以及失败恢复。
  3. 若选 B，删除“Changelog 一致即可 high confidence”的强承诺，给每类结构化 detector 明确 truth source。
  4. 测试空 Unreleased、只有 Changed、混合 Added/Fixed、非标准标题和 release commit 已经固化版本段的情况。
- **修复风险（中）**: 需要调整发布作者工作流或降低自动化承诺。
- **严重程度（高）**: 当前主证据在真实流程中通常缺失。

### PR-05-未修复-高-人工路径是否受推荐下限约束没有收敛，兼容性与安全性相互冲突
- **位置**: “用户覆盖推荐”“现有 Tool 契约调整”
- **问题类型**: 公共契约缺失 / 状态机漏洞 / open question 未收敛
- **当前写法**: 方案一方面承诺原有显式 `patch|minor|major` 和 `target_version` 调用兼容，另一方面要求选择低于推荐等级时必须提供 `override_reason`，并称明确 breaking evidence 不允许无理由降级。
- **反例/失败场景**: 调用方直接使用现有 `target_version=1.3.1, apply=true, confirm=true`，不携带 `recommendation_id`。如果保持兼容，它绕过推荐下限；如果每个 apply 都强制重新分类，则在无远端 tag、离线、diff 解析失败或 intentionally detached release worktree 中，原有手动路径会被新分类器阻断。`allow_downgrade` 又是另一个 escape hatch，方案没有说明它与 policy override 的优先级。
- **为什么有问题**: 这决定自动分类是“建议功能”还是“强制发布策略”，两者具有不同 public contract、失败模式和 rollout 风险。实现 Agent不能自行选择。
- **直接证据**: 当前 `update_local_version` 接受 target 或 bump，唯一策略是默认拒绝 downgrade，见 `src/application/version_check.py:41-66`；Tool schema 暴露 `target_version` 和 `allow_downgrade`，见 `src/application/agent_tools/runtime.py:173-188`。现有测试明确证明 target_version 直接写入路径，见 `tests/test_version_check.py:46-55` 和 `tests/test_agent_plugin_smoke.py:1000-1009`。
- **影响**: 可能形成可绕过的伪策略，或意外破坏现有调用；override 审计不完整；release automation 在 degraded 环境中被锁死。
- **建议改法和验证点**:
  1. 明确 v1 是 advisory 还是 enforcing。推荐 v1 先 advisory：`auto` 接受 digest，手动路径保留但输出 `policy_override=true` 和 reason warning；不要偷偷改变旧调用的可用性。
  2. 如果未来要 enforcing，单独做 public contract 变更，定义 emergency/offline escape hatch、`allow_downgrade` 交互和 CI policy gate。
  3. 对低于推荐、高于推荐、显式 target、downgrade、classifier unavailable、base override 分别建立真值表和测试。
- **修复风险（中）**: 需要产品决策，不是代码细节。
- **严重程度（高）**: 当前无法同时兑现兼容和强制约束。

### PR-06-未修复-中-实现范围一次覆盖过宽，缺少可验证切片，容易演变成启发式大杂烩
- **位置**: “自动分类规则”“代码边界”“关键测试场景”
- **问题类型**: 过度设计 / 非最优方案 / 切片过粗 / 过度耦合
- **当前写法**: 一个新模块同时承担 Git evidence、Changelog 解析、六类公共契约判断、置信度、digest 和 override policy；随后一次性修改 Tool schema、版本写入、文档和多套测试。
- **反例/失败场景**: 为了让 Agent Tool deletion 测试通过，实现在 unified diff 上加规则；CLI/config/output 又各自追加 regex，最终 confidence 依赖若干互不等价的 heuristic。任何新增公共 surface 都要修改同一个 central classifier，release policy 与仓库文件布局高度耦合。
- **为什么有问题**: 用户当前需要的是发布时给出可信推荐并确认采用，不需要第一版自动理解仓库所有语义。更小的可靠切片是：先定义 release impact 输入和基线安全，再增加少量可证明的 structural floors；contract snapshot diff 可作为后续独立 slice。
- **直接证据**: 现有 release planner 已经通过集中路径表维护测试映射，见 `src/application/release_test_plan.py:24-150`；复刻更复杂的 semantic 路径表会形成第二套与代码结构同步的维护负担。当前 workflow 只生成 current spec，不提供 previous spec，`.github/workflows/_release-reusable.yml:36-41`。
- **影响**: 误判规则不断堆积、维护成本高、单元测试贴实现而非证明语义、首个 slice 难以审查和回滚。
- **建议改法和验证点**:
  1. 拆成三片：S1 基线/摘要/preview-confirm freshness；S2 changelog-driven recommendation + explicit unknown；S3 针对有 canonical snapshots 的公共契约增加自动 floor。
  2. 第一版不要承诺自动识别 source-of-truth 语义或任意输出字段语义。
  3. 每个 detector 必须有独立 truth source、failure mode 和 fixture，不能只按路径加分。
- **修复风险（低）**: 主要是缩小 scope 和重排 sequencing。
- **严重程度（中）**: 不缩小会增加返工和错误确定性。

### PR-07-未修复-中-测试清单缺少真实 Git 拓扑和远端竞争集成场景
- **位置**: “关键测试场景”“验收标准”
- **问题类型**: 测试缺口 / version skew / 恢复风险
- **当前写法**: 已列出分类、digest 变化、override 和 Tool gate 测试，但没有要求使用临时 Git repo 构造 tags、branches、renames、远端 refs 和并行发布。
- **反例/失败场景**: 纯函数测试使用传入 changed files 可以全部通过，但真实 `git diff` 在 rename detection、merge commit、detached HEAD、浅 clone、untracked binary、submodule 或 stale remote tag 下返回不同证据；target tag 在 preview 后由另一 release 创建，workspace digest不变，确认仍会写冲突版本。
- **为什么有问题**: 该功能的主要风险来自 Git 状态机和远端版本命名空间，不是 `bump_version()` 算术。现有 `tests/test_release_test_plan.py` 的 Git discovery 测试通过 mock subprocess 验证固定命令，不能证明复杂拓扑。
- **直接证据**: `tests/test_version_check.py:26-29` 只证明 bump 算术；`:32-68` 只证明本地文件写入和 downgrade。现有 release workflow checkout 使用默认 shallow checkout，见 `.github/workflows/release-from-version.yml:19-20` 和 `_release-reusable.yml:23-24`，更需要明确 shallow/tag behavior。
- **影响**: 单元测试绿但真实 release branch 上失败；确认后版本碰撞；无法复现边界问题。
- **建议改法和验证点**:
  1. 用临时 bare origin + 两个 clones 做集成测试。
  2. 覆盖 stale clone、远端新 tag、目标 tag 竞争、branch behind、merge commit、detached HEAD、rename、prerelease、shallow clone 和 classifier unavailable。
  3. 证明确认前 remote recheck 能捕获 preview 后发布的新版本。
- **修复风险（低）**: 测试成本可控，但必须在实现前进入 plan。
- **严重程度（中）**: 当前验证无法覆盖最危险失败路径。

## Architecture boundary review

方向上把 release policy 放在 `src/application/` 而不是 `domain/domain/` 是合理的；它依赖 Git、VERSION 和发布元数据，不属于交易业务域。主要边界问题不是目录位置，而是缺少公共契约的 canonical representations：若 classifier 直接解析任意应用源码 diff，它会穿透 CLI、Agent Tool、配置、ledger 和部署多个 ownership 边界，并把实现细节变成发布策略 API。应优先消费稳定 manifest/schema/snapshot；没有稳定表示的 surface 返回 needs-review。

## Best-practice review

做对的部分：dry-run 默认、原子 VERSION 写入、最高影响等级优先、证据输出、stale digest、明确不自动 commit/push/release。

偏离最佳实践的部分：把 freshness token 描述为 authorization；使用局部 Git 可达性决定全局版本名；没有 unknown/unsupported contract；没有明确 remote race recheck；没有临时 Git 拓扑集成测试。

## Optimal-solution review

当前方案“可以做”，但不是首个版本的最优路径。更实际的顺序是：

1. 先建立 authoritative baseline 和 stateless freshness digest；
2. 使用标准化 release impact 输入产生确定性推荐，并对缺失/冲突返回 needs-review；
3. 用户确认沿用调用 surface 的现有确认边界；
4. 只对拥有 canonical manifest/snapshot 的 surface 增加自动 compatibility floor；
5. 最后再决定是否把 advisory 提升为 enforcing policy。

这保留用户要求的自动推荐，同时避免第一版声称能理解所有业务语义。

## Overengineering review

主要过度设计是第一版同时泛化到 Agent Tool、CLI、配置、输出、runtime、migration 和 source-of-truth，而这些 surface 没有统一 schema。`confidence + evidence + digest` 本身不是过度设计；它们直接支撑安全目标。需要删减的是无 truth source 的 detector breadth，而不是安全确认和证据结构。

## Overcoupling review

风险集中在 central classifier 对仓库路径和源码表达方式的依赖。一旦实现成大路径表或 diff regex，任何模块移动都会改变版本建议，release policy 与代码组织耦合。建议 detector 按 canonical artifact 注册，不能证明的 surface保持 unknown；release test planning 和 release impact classification 可共享 changed-file discovery，但不应共享同一个 risk 枚举或把测试风险等同 SemVer impact。

## Open Questions

1. 第一版面向本地 Codex/CLI，还是同时面向 WeChat/Assistant 两轮确认？
2. 自动分类是 advisory，还是所有 `VERSION` write 的强制下限？
3. `Unreleased` 是否改为开发阶段强制维护？如果不是，哪个结构化输入承载 release intent？
4. baseline authority 是远端最高稳定 tag、目标分支 VERSION，还是二者必须一致？离线模式如何处理？
5. prerelease 是否在第一版支持？如果不支持，应在哪里 fail closed？
6. 哪些公共 surface 已经有可比较的 canonical snapshot？Agent spec release artifact是否要签入或下载用于比较？
7. 当 classifier 返回 unknown/needs-review 时，用户如何选择并留下理由？

## Residual risks and tracking

- 自动 SemVer 分类永远无法仅凭源码完全证明业务语义兼容；应作为 advisory evidence system，而不是 correctness oracle。建议在 `docs/RELEASE_PROCESS.md` 长期记录这个边界。
- 平行 release 的远端 tag race 只能通过确认/发布前 remote recheck 缩小，无法靠 workspace digest消除。建议作为 release preflight invariant 跟踪。
- 如果后续加入 contract snapshots，需要独立设计 snapshot ownership、生成时机和兼容比较规则，避免 generated artifact drift。建议单独 work unit。

## Final conclusion

**fail**。

方向正确：复用 `version_update`、read-first 推荐、用户确认、stale digest 和不自动发布都值得保留。但计划当前仍缺三个 implementation blockers：

1. 没有可执行的公共契约提取规范；
2. baseline 没有远端全局版本一致性保证；
3. recommendation digest 与真实用户确认被错误合并。

先收敛上述 blockers、确定 advisory/enforcing 和交互 surface，再交给 implementation agent。
