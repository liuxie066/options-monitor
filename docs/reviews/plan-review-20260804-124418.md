## Goal and boundary understood

The amendment is intended to close the proven loss of held-contract strike provenance without inventing that provenance in the coverage layer. Its proposed expiry-local mapping on `OptionSideFetchPlan` is the correct minimal representation: option type is already owned by the side plan, expiration remains local, and duplicate lots can safely collapse to one quote demand. Adding `required_data_planning.py` is therefore an owner-correct and parsimonious scope expansion rather than a new layer.

The review nevertheless asks whether the amended S1 is code-generation-ready and can close the already accepted DR-S1-01/02 findings on the real publication path. It cannot yet do so.

## Assumptions tested

1. A real S1 fetch produces one provider child for every `merged_requests` item.
2. Existing child evidence can be reconciled to the exact planned request, not merely counted.
3. Every input marked `planning_status=ready` either survives into the expiry-local exact-strike mapping or causes a typed failure.
4. The exact-strike comparison has one deterministic economic identity rule at every coverage entry point.
5. The proposed field remains expiry-local through position-only and strategy-plus-position merges.
6. Discovery and raw payload underlier evidence can be bound at existing owners without a new abstraction.

Assumptions 1-4 are disproven or underspecified below. Assumptions 5-6 are supported: `_position_requirement_side_plans()` and `_merge_same_side_plans()` are the owning loss point, and `domain.domain.symbol_identity.futu_underlier_code()` already provides the canonical Futu identity needed by the contract/output validators.

## Findings

### PR-S1A-01-未修复-高-S1 要求多 child 证据，却把真实 per-spec 执行留到 S6，合法 multi-spec 计划无法发布

- **位置**: amendment “Exact scope addition” 的 non-goal；`plan.md` S1 Non-goals 与 S6 Exact changes
- **问题类型**: sequencing 不安全 / scope 矛盾 / 不可直接实施
- **当前写法**: S1 要求 expected contract 的 `merged_requests` 与 child evidence 闭合，但明确“不改变 S6 exact-spec execution”；S6 才逐 exact spec 执行。
- **反例/失败场景**: put 与 call 的到期集合不同时，`_merge_side_plans()` 合法地产生两个 `merged_specs`。当前 `_fetch_one_inprocess()` 经 `_prefetch_fetch_kwargs_from_plan()` 把全部 side/expiration/window 扁平化，随后只调用一次 `fetch_symbol()`。该 payload 不含两个真实 children，而 S1 publisher 在 contract 有两个 `merged_requests` 时要求 `meta.requests` 数量为 2，于是正常 provider 结果在回执前报 `child request evidence count mismatch`。
- **为什么有问题**: 这是现有生产 call path 与新增 S1 acceptance contract 的直接冲突，不是测试 fixture 缺字段。用 fixture 人工补两个 child、放宽 validator，或把问题推迟到 S6，都会让 S1 无法宣称 DR-S1-01 已闭合。
- **直接证据**: `required_data_planning.py:644-674` 按不同 expiry tuple 分组；`tests/test_required_data_fetch_planning.py:630-656` 明确证明合法计划可有两个 specs；`required_data_prefetch.py:277-342,606-697` 将它们合并为一组 kwargs 并只调用一次 `fetch_symbol()`；`opend_symbol_fetching.py:677-719` 返回单请求 meta 且没有 `requests`；`opend_symbol_outputs.py:467-483` 要求 child 数量等于 `merged_requests`。聚焦测试结果为 `2 passed`，其中 multi-spec planner 回归确认该状态可达。
- **影响**: 正常双账户共享计划只要形成不同 expiry relations 就会 fail closed，S1 focused suite 无法代表真实成功路径；若为通过测试而伪造 child metadata，则会产生没有 provider 事实支撑的完成 authority。
- **建议改法和验证点**: 在 S1 修订中先收敛一个真实、owner-correct 的 execution/evidence 方案。优先复用现有 `RequiredDataFetchSpec`/`build_fetch_request_from_spec`，按 spec 获取 typed child result、确定性聚合并只 final-save 一次；若选择不同物理表示，expected contract 必须准确声明该物理请求而不能把逻辑 request 冒充 provider child。相应扩展最小 S1 owners（包括实际需要的 in-process/subprocess adapter），并增加真实双-spec 正常发布、任一 child 失败零回执、无伪造 `meta.requests` 的端到端回归。S6 可以继续拥有 scoped-union、spot tri-state 和 CLI exact-spec public plumbing，但不能再拥有 S1 contract 成立所必需的第一份 per-spec 事实。
- **修复风险（低/中/高）**: 高
- **严重程度（低/中/高/严重）**: 高

### PR-S1A-02-未修复-高-child evidence 只验数量和时间，无法证明对应 exact request identity/hash

- **位置**: `plan.md` S1 accepted DR-S1-01 closure；amendment Validation；expected-contract/evidence contract
- **问题类型**: 契约缺失 / review 不可验收
- **当前写法**: plan 声明 exact ordered fetch specs 和 child evidence 必须闭合，但没有规定 child 的 request identity/hash wire schema；现实现只比较 child 数量，并独立检查时间。
- **反例/失败场景**: 两个 child 可以来自相同 request、另一 symbol/binding/expiration/window，或顺序互换且内容无关；只要数量和时间 aggregate 对得上就被接受。现有 positive test 构造的两个 child 只有 `source_observed_at` 与 `completed_at_utc`，仍被 validator 接受。
- **为什么有问题**: DR-S1-01 的已接受修复要求是“child evidence 数量和 request identity/hash 必须精确匹配”。数量不是 identity；在 per-spec 执行落地后，这个缺口仍可让未执行的 exact request 获得成功 authority。
- **直接证据**: `docs/reviews/code-review-20260804-120035.md:41-63` 给出原始反例和明确修复要求；`opend_symbol_outputs.py:467-483` 仅检查 list/count/mapping；`opend_symbol_outputs.py:445-464` 只绑定 aggregate timestamps；`tests/test_required_data_output_integrity.py:460-471` 的接受用例没有任何 request identity。
- **影响**: 错 side、错 expiration、错 strike window 或重复 child 可被 receipt/seal 当成 exact plan 的完成证据，双账户消费者共享错误 authority。
- **建议改法和验证点**: 在 S1 plan 中冻结 child evidence v1：每个 child 至少携带 canonical planned-request SHA-256（由对应 `merged_requests` 的 plan-owned字段计算）、symbol、binding、status/outcome 与稳定 timestamps；validator 按确定性顺序或精确 hash multiset 与 `merged_requests` 一一匹配，并拒绝 duplicate/missing/unexpected/hash drift/non-ok child。测试必须包含同数量错 hash、重复 hash、交换但带正确显式序号/集合语义、错 binding、一个失败 child，且全部零回执；不要从 aggregate plan 事后合成 provider child。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR-S1A-03-未修复-高-计划未规定 malformed ready position requirement 必须失败，当前 planner 会静默丢失 exact demand

- **位置**: amendment “Build the mapping from ready position requirements” 与 Success signal；`_position_requirement_side_plans()` input boundary
- **问题类型**: 契约缺失 / fail-open 输入处理 / 不可直接实施
- **当前写法**: amendment 严格描述输出 mapping 的 key/value，但没有明确每一条输入 `planning_status=ready` 的校验和失败语义；“malformed identity rejected”可能只被实现为 wire-map validator。
- **反例/失败场景**: ready requirement 的 option type 非法、expiration 为空/非 ISO，或 strike 为 `True`、`NaN`、`Infinity`/缺失。当前函数会跳过非法 side/expiration/strike，或通过 `_safe_float` 把 bool/非有限数当成数值；剩余 plan 可生成自洽 hash 和空/部分 exact map，从而在 contract/coverage 层再也看不到被丢失的 held-contract demand。
- **为什么有问题**: 输出 map 的严格验证不能证明输入集合完整。用户目标是保留“every ready Close Advice position requirement”；在 provenance 被删除后，后续 owner 无法补救。
- **直接证据**: `required_data_planning.py:583-631` 对非法 requirement 使用 `continue`，expiration 只过滤空字符串，strike 使用宽松 `_safe_float`；`required_data_planning.py:794-797` 随后直接合并这些部分结果。上游 plan finalizer `close_advice_required_data.py:284-367` 排序和哈希 requirements，但不逐字段重新验证被传入的 ready item。
- **影响**: 某个真实持仓 exact quote demand 可无 typed failure 地消失，最终 CSV/receipt 对错误的缩小计划显示 complete。
- **建议改法和验证点**: amendment 应明确：在任何 side-plan 合并前，对每个 ready item 严格验证 option type、ISO expiration、positive finite non-bool strike（以及与当前 symbol 的既有绑定字段，如该函数收到）；任一无效 ready item 必须返回/抛出稳定 typed planning failure并阻断该 symbol receipt，不能 skip。新增逐字段 malformed、一个合法加一个非法、重复 lots 同 contract 合法 set-union，以及 unavailable item 明确不参与的测试。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR-S1A-04-未修复-中-exact-strike 容差和两个 coverage 入口未冻结，可能出现假匹配或同一计划的相反结论

- **位置**: amendment “one small fixed numeric tolerance”；Coverage validation
- **问题类型**: 不可直接实施 / 测试缺口 / 最佳实践偏离
- **当前写法**: 只要求“小的固定容差”，未给数值、absolute/relative 规则或边界；也未说明 typed `required_data_frame_covers_fetch_plan()` 与 receipt 使用的 debug evaluator 是否都执行 exact map。
- **反例/失败场景**: implementation 若复用现有 range-edge tolerance，会随 strike spacing/窗口宽度放大并把邻近但不同合约当成 exact strike；若一处用相对容差、另一处用严格等号，同一 CSV 可在 cache precheck 与 receipt finalizer 得到相反结论。当前 `required_data_steps.py:143-166` 先调用 typed evaluator，而 `opend_symbol_outputs.py:259-271` 用 debug evaluator。
- **为什么有问题**: exact option strike 是合约身份，不是范围近似。容差必须只吸收 JSON/CSV 浮点 round-trip，且所有 authority-facing入口需要同一 helper，否则会制造冗余 refetch 或弱路径误报 coverage。
- **直接证据**: `required_data_coverage.py:69-115` typed evaluator 与 `:118-298` debug evaluator是两套循环；现有 `_strike_edge_tolerance()` (`:711-736`) 可达到窗口宽度的 25% 或单点 strike 的 0.5%，不适合 exact identity；spot 又使用相对 `1e-6` (`:593-607`)，因此“small”没有唯一的 project-local含义。
- **影响**: 过宽容差可把错误合约当成 held contract；不一致实现会导致不必要 provider calls、manual/legacy coverage 与 receipt authority 分裂，回归无法给出唯一验收标准。
- **建议改法和验证点**: 在 plan 中冻结一个专用 exact-strike helper，例如 `math.isclose(actual, expected, rel_tol=0.0, abs_tol=1e-9)`（最终常量由 plan 明确，不得复用 range-edge tolerance），并要求 typed evaluator委托同一 debug/canonical core或两者都显式调用该 helper。测试覆盖恰好在容差内/外、高价 strike 不放大容差、错误相邻 strike，以及两个入口同结果。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

## Architecture, best-practice, optimality, overengineering, and overcoupling review

- **Architecture boundary**: expiry-local exact strikes belong on `OptionSideFetchPlan`; putting them only in coverage would be architecturally wrong. The added planning owner is minimal. Underlier derivation can use the existing domain symbol identity (`futu_underlier_code`) and output validation can compare the already present raw/discovery fields; no new adapter or schema service is needed.
- **Best practice**: immutable receipt authority requires provider evidence to bind the exact request, not a child count. Strict ready-input validation must occur before lossy projection.
- **Optimal solution**: the map is preferable to a new per-lot entity because quote completeness is a set of `(side, expiry, strike)` demands. Per-lot identity correctly remains out of S1.
- **Overengineering**: no generic demand graph, Decimal migration, or new receipt version is justified. A required debug field, one strict validator, one exact comparison helper, and real child request hashes are sufficient.
- **Overcoupling**: the current S1/S6 split is overcoupled in time: S1's success contract depends on execution semantics assigned to S6. The minimum correction is to move only the evidence-critical per-spec execution/aggregation into S1, leaving spot reuse, scoped union, public/internal CLI design, and other S6 policy there.

## Open questions

1. Which production modes must publish multi-spec success in S1: in-process only, or both in-process and subprocess? The plan currently promises a common fresh/cache/subprocess finalizer, so omitting subprocess requires an explicit typed unsupported boundary and proof that canonical production does not depend on it.
2. Is child matching ordered-list identity or hash-multiset identity? The choice must be frozen with deterministic duplicate handling before implementation; count-only is not acceptable.

## Residual risks and tracking

- Provider range calls can still omit an interior contract; after the exact map fix this is safely rejected after readback. Track as S1 residual operational cost, not a correctness deferment.
- Spot observation duplication and cross-account scope minimization remain valid S6 risks only after S1 has the minimum real per-spec facts needed for its own contract.
- Runtime symbol aliases are not part of this amendment. The underlier check should derive from the already canonical persisted plan symbol and reject an unresolvable identity; any desire to accept noncanonical runtime aliases belongs to the existing symbol-identity owner, not a relaxed receipt check.

## Conclusion

**fail**

The expiry-local exact-strike schema and added planner owner are sound, but the amendment is not yet safe to hand to implementation. It must first resolve PR-S1A-01 and PR-S1A-02 so the real multi-spec path can produce exact child evidence inside S1, explicitly fail malformed ready requirements per PR-S1A-03, and freeze the exact-strike comparison/core coverage rule in PR-S1A-04. Tests or fixtures that synthesize child metadata, compare only counts, or defer these S1 success prerequisites to S6 do not satisfy the accepted Gateflow findings.
