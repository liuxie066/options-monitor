# Plan Review

## Reviewed target and scope

- **Target**: 2026-07-30 对话中已确认的“期权到期平仓原因、状态机、等待与回执改造方案”
- **Review mode**: full adversarial pre-implementation review
- **Plan source**: 当前方案尚未形成独立 implementation plan 文档，本次以对话中逐项确认的决策为审查基线
- **Scope**: Push/轮询统一身份、Inbox 收敛、平仓事实与原因两阶段状态、独立原因判断器、提前/到期后判断、Long/Short 与股票交割矩阵、等待窗口、两营业日自动结案、人工复核、回执 Outbox、存量案件迁移
- **Excluded**: 业务代码修改、测试实现、真实飞书发送、生产服务恢复、commit/push、release、生产升级

## Goal and boundary understood

本次改造要消除同一到期事件被 Push、轮询和重试重复处理、重复发送飞书回执的问题，同时把“期权腿是否已经平仓”和“为什么平仓”拆成两个可审计阶段。原因判断必须以券商证据为依据，支持 Short assignment、Long exercise、主动交易平仓和到期无交割；缺少完整证据时保持 pending 或进入人工复核，而不是猜测。通知由业务状态迁移驱动，最多发送一次平仓确认和一次最终结果，且必须具备崩溃恢复和幂等能力。

## Confirmed decisions under review

1. Push 与轮询采用同一个 durable deal identity：
   `futu:<account>:<futu_account_id>:<deal_id>`。
2. 券商事件一旦被 Inbox 接受，即结束原始消息重试；`cause_pending`
   由生命周期流程推进，不再重放 Inbox。
3. 状态概念上分为平仓事实和原因解析两个维度。
4. 原因判断集中在无 I/O、无写入、无通知副作用的独立 domain resolver。
5. 提前发生的非零正常成交判为主动平仓；零价且有唯一对应股票交割时，根据 Long/Short、
   Put/Call 和股票方向判为 assignment 或 exercise。
6. 到期截止时间之后只接受到期交割、到期未交割，或实际成交时间早于截止时间的延迟上报；
   真正的非零价截止后成交视为冲突。
7. 乱序股票腿等待 15 分钟；无交割结论最多等待至第二个券商营业日结束。
8. 只有零价到期关闭、期权仓位消失、所有券商查询成功、没有股票交割、没有现金交割且没有冲突时，
   才自动判定到期无交割。
9. v1 只自动处理实物交割期权；现金结算产品保留枚举但进入人工复核。
10. 人工复核使用 OM CLI，要求 preview/dry-run、显式确认、券商引用或说明、审计记录和最终回执。
11. 回执按业务状态迁移发送，使用
    `case_id + transition_type + resolution_revision` 去重，并由 durable Outbox 承担投递。
12. 存量平仓回执视为已经投递；升级后重新评估原因，只允许后续补发一次“到期结果确认”。

## Assumptions tested

1. 券商接口返回成功且结果为空，足以证明目标结算窗口内没有股票或现金交割。
2. “第二个券商营业日结束”对所有市场、产品和清算日都能由现有数据稳定计算。
3. 每个合约都能取得可靠的最后交易截止时间，而不仅是到期日期。
4. 新的双维状态不会与现有 `lifecycle_case.v2`、terminal event、projection 和 allocation
   形成第二套事实权威。
5. Legacy zero-close case 能无歧义地映射到 v2 target lots。
6. 同一股票交割数量不会被两个原因判断同时消费。
7. 原因 resolver 的纯函数输出能在写入时再次验证其证据仍未被其他 case 占用。
8. 生命周期状态迁移和通知意图能够在同一事务边界内提交。
9. 飞书请求超时或结果 unknown 时，有可靠的 provider reconciliation 或人工收敛办法。
10. 现有已确认回执可以稳定映射到迁移后的 case 和 transition。
11. 自动生成 `expiration_no_settlement` 后到达的迟到交割证据有明确的纠错路径。
12. v1 不会因为保留 `cash_settlement` 枚举而把现金结算产品自动写成 terminal result。

## Special review lenses

### Architecture boundary review

独立纯 resolver 的方向正确，但生命周期事实的最终权威必须继续由现有
case/evidence/allocation/ledger transaction 边界承担。当前方案没有锁定双维状态是持久化事实、
派生读模型还是兼容展示，也没有说明 legacy adapter 如何并入 v2 case owner，存在形成平行状态机
和重复 terminal writer 的风险。

### Best-practice review

正向证据、fail-closed、数量唯一分配、transactional outbox 和可回放迁移是这类资金事实系统的
最低安全要求。方案已经提出大部分意图，但尚未把“所有查询成功”“没有交割”“通知 unknown”
定义成可验证、可持久化、可恢复的契约。

### Optimal-solution review

最小且安全的方案不是新建一套平仓原因存储，而是扩展现有
`lifecycle_case.v2 -> evidence -> terminal event -> allocation -> projection` 主链：
resolver 只产出候选裁决及证据引用，现有 ledger writer 在事务内重新校验并落账；平仓事实和原因状态
优先作为派生读模型。通知 Outbox 应与生命周期账本同库、同事务，而不是跨库协调 Inbox 和 ledger。

### Overengineering review

把事实和原因拆成两个概念有助于表达等待过程，并非过度设计；但若把所有组合都持久化成新的可写状态，
会扩大迁移和一致性成本。只有不可从事件、证据和 allocation 稳定推导的最小状态才应落库。

### Overcoupling review

原因判断不应直接依赖 Futu client、SQLite、CLI 或飞书，这是当前方案的正确边界。尚未收敛的是
evidence bundle 与现有 broker adapter、market calendar、allocation writer 和 notification
delivery state 的接口；如果交给实现阶段临时拼接，resolver 会反向耦合基础设施细节。

## Findings

### 1-未修复-严重-“两营业日且所有查询成功”没有形成可审计的无交割证据契约，可能错误写入不可逆终态

- **位置**: 两营业日等待策略、`expiration_no_settlement` 自动判定条件、broker evidence bundle
- **问题类型**: 证据权威 / fail-open / 契约缺失 / 不可直接实施
- **当前写法**: 零价到期关闭且期权仓位消失后，只要所有券商查询成功、没有匹配股票或现金交割、
  没有冲突，第二个券商营业日结束即可自动判定到期无交割。
- **反例/失败场景**: 券商股票成交查询成功，但查询窗口只覆盖交易日而未覆盖清算入账日；现金流水接口
  返回成功空集，但分页、账户范围或 clearing date 不完整；持仓快照已不包含期权。系统据此写入
  `expire_close`。数小时后迟到的 assignment 股票腿到达，现有生命周期规则会把它判为
  `late_settlement_conflicts_with_expire_close`，已经发送的“到期未交割”也需要纠正。
- **为什么有问题**: “接口调用成功”只证明请求完成，不证明针对特定账户、合约和清算窗口的否定事实
  完整。当前方案没有规定必需数据源、查询窗口、分页完整性、账户身份、as-of 时间、freshness、
  clearing date、原始响应摘要和市场日历版本，implementation agent 无法区分“完整空结果”和
  “查漏了”。
- **直接证据**:
  - `docs/POSITION_ADVICE_V2_CONTRACT.md:104-114` 明确规定到期和沉默不能证明 expiry closure；
    当前策略在固定等待后仍应进入 review，而不是自动生成 expire 事实。
  - `src/application/trades/history_backfill.py:99-164` 当前只封装历史成交查询及 lookback，
    没有形成结算完整性快照。
  - `src/infrastructure/futu_gateway.py:78-109` 暴露成交、订单、持仓、资金和交易日接口，但没有
    账户现金流水 adapter，方案要求的“无现金交割”目前无法由主链证明。
  - `src/application/trades/lifecycle_reconciliation.py:351-366` 已把 expire_close 之后到达的
    assignment/exercise 视为冲突，说明错误的否定结论不能靠后续普通重算自动修复。
- **影响**: 系统可能把证据缺失误判为到期未行权/未被指派，写入 terminal ledger event、更新仓位
  projection 并发送错误回执；后续真实交割只能进入冲突或人工修复，属于资金事实错误。
- **建议改法和验证点**:
  - 在计划中定义 immutable `broker_settlement_observation.v1`：固定必需数据源、账户身份、
    contract identity、查询起止与 clearing dates、分页完成标志、provider retcode、observed-at、
    freshness、market-calendar revision、原始响应 hash 和逐源 completeness。
  - 只有完整 observation 才能产生正向的 `no_settlement_observed` evidence；任一来源
    missing/error/stale/partial 都进入 `needs_review`。
  - 明确迟到交割的 void/correction、projection replay、回执更正和审计流程。
  - 增加空分页、截断窗口、跨清算日、现金流水缺失、API 成功但字段不完整、迟到交割和纠错回放测试。
- **修复风险（低/中/高）**: 高
- **严重程度（低/中/高/严重）**: 严重

### 2-未修复-高-最后交易截止时间和第二营业日没有权威时间策略，且与 v2 不可变 deadline 冲突

- **位置**: 提前/到期后原因分支、15 分钟配对窗口、第二个券商营业日截止、存量 case 迁移
- **问题类型**: 时间语义 / schema migration / 最佳实践偏离 / 测试缺口
- **当前写法**: 先按实际平仓成交是否早于“到期交易时间”分支；乱序腿等 15 分钟；仍无结果则等到
  第二个券商营业日结束。但尚未指定最后交易日、具体 cutoff、时区、提前收市、节假日和券商营业日的
  权威来源。
- **反例/失败场景**: 美股期权周五到期，周一为券商或市场假日；另一个合约有不同的最后交易日或
  现金结算规则。若继续使用日历日期和固定小时，系统可能提前终止等待。现有 v2 case 已把固定
  `pending_until` 写入不可变 payload，直接改为新算法会让同一 case 的 immutable identity
  与数据库记录冲突。
- **为什么有问题**: 到期日期不等于最后可交易时刻，交易所营业日也不一定等于券商结算营业日。
  时间策略若没有版本化 authority，就无法重放历史判断；既有 case 的 deadline 又不能被静默改写。
- **直接证据**:
  - `domain/domain/option_lifecycle.py:16-22` 使用固定 `PENDING_ELAPSED_HOURS = 72`。
  - `domain/domain/option_lifecycle.py:43-59` 当前 observation boundary 是到期日后一个日历日的
    本地午夜，不是合约最后交易 cutoff。
  - `domain/domain/option_lifecycle.py:85-127` 在建 case 时固化 observation start 和
    pending until。
  - `src/application/ledger/repository.py:1240-1253` 把 observation/pending 时间纳入 case
    immutable payload，迁移不能原地重算覆盖。
- **影响**: 提前平仓与到期结算可能被分错支路，等待期限在周末、假日、DST 或提前收市时错误；
  存量 case 可能因不可变字段漂移无法更新，或被错误复制成新 case。
- **建议改法和验证点**:
  - 定义版本化 `lifecycle_timing_policy`，输入至少包括市场、产品/结算类型、timezone、
    last-trading cutoff、broker settlement calendar、calendar revision 和 fail-closed 状态。
  - 缺少合约级 cutoff 或日历证据时不得自动判定，进入 `needs_review`。
  - 明确采用 schema v3、兼容读取旧 deadline，或只对新 case 启用新策略；不得修改 v2
    immutable payload。
  - 覆盖 Friday/weekend、连续假日、DST、提前收市、不同最后交易日、缺失 calendar 和
    legacy deadline 回放测试。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### 3-未修复-高-双维状态与 legacy zero-close adapter 没有指定唯一事实权威，可能生成平行 case 和重复终态

- **位置**: 平仓事实/原因两阶段状态机、独立原因模块、Inbox 结束点、legacy case 兼容
- **问题类型**: 架构边界 / 过度耦合 / 单一权威缺失 / migration gap
- **当前写法**: 新增平仓事实状态和原因解析状态，由独立模块判断原因；Push/轮询进入统一 Inbox，
  原始消息在接受后结束。但没有说明这些状态是新的持久化字段、现有 lifecycle read model 的派生值，
  还是另一张 case 表，也没有锁定 legacy zero-close case 如何采用 v2 target lots。
- **反例/失败场景**: 零价 option deal 先由当前 adapter 创建一个无 schema version 的 legacy
  lifecycle case；随后 expired-lot discovery 因只识别 v2 target ownership，又为同一 lot 创建
  `lifecycle_case.v2`。新 resolver 在 legacy case 上得出 assignment，现有 reconciliation 又在
  v2 case 上分配同一 settlement evidence，两个状态机都尝试生成 terminal event 或通知。
- **为什么有问题**: 现有系统已经以 v2 case、evidence、allocation、terminal event 和 projection
  形成生命周期主链。新双维状态若没有明确映射，会把“表达更清楚”变成第二套可写事实，破坏单一写入
  权威和幂等性。
- **直接证据**:
  - `domain/domain/option_lifecycle.py:130-225` 已从 case、evidence 和 allocations 派生
    open、settlement_pending、partially_resolved、needs_review、assigned、exercised、
    expired_unassigned、resolved_mixed 和 conflict。
  - `src/application/trades/lifecycle.py:72-199` 当前零价 deal 路径仍可创建 legacy-shaped case，
    未包含 v2 target manifest 和 immutable timing contract。
  - `src/application/ledger/writer.py:434-650` 的 expired-lot discovery 只用 v2 case target
    ownership 冻结 lot，legacy case 不能阻止重复发现。
  - `src/application/ledger/writer.py:400-431` 已把 terminal event、projection、allocation 和
    case status 放在现有原子写入边界内。
- **影响**: 同一 option lot 可能有两个 case、两个原因、两次 projection 修改和两组通知；
  implementation agent 还必须自行决定哪些新状态覆盖既有 ledger 状态。
- **建议改法和验证点**:
  - 在计划中声明 versioned lifecycle case/evidence/allocation 是唯一 canonical authority；
    平仓事实和原因状态默认由其派生，除非证明某个最小字段无法派生。
  - legacy zero-close adapter 必须采用或升级到唯一 v2/v3 case，不得旁路创建第二个 owner。
  - ordinary `trade_close` 继续由现有正常成交写入边界负责；resolver 只提供候选原因及 evidence refs，
    不直接写 terminal event。
  - 增加 Push-first、poll-first、legacy-first、discovery-first、进程重启和并发创建同一 lot 的
    唯一 case/唯一 event/唯一 notification 测试。
- **修复风险（低/中/高）**: 高
- **严重程度（低/中/高/严重）**: 高

### 4-未修复-严重-Outbox 没有与生命周期状态迁移锁定同一事务和恢复协议，仍会丢消息或重复发送

- **位置**: 回执策略、`case_id + transition_type + resolution_revision` 幂等键、
  accepted/confirmed/unknown 状态
- **问题类型**: 事务边界 / 崩溃一致性 / 幂等契约 / 不可直接实施
- **当前写法**: 引入独立 durable Outbox，按业务 transition 生成最多两条消息；accepted、
  confirmed 或 unknown 不立即重发，明确的 pre-acceptance failure 才重试。但没有说明通知意图与
  case/ledger transition 是否同库同事务、worker claim/lease、唯一约束、provider receipt
  reconciliation 和 unknown 的终结流程。
- **反例/失败场景**:
  1. ledger transition 已提交，进程在插入 Outbox 前崩溃，最终结果永远没有通知。
  2. 飞书已经接受请求，进程在标记 confirmed 前崩溃；重启后再次发送则重复，冻结 unknown
     则可能永久不确定。
  3. 两个 worker 同时观察到同一 transition，在应用层检查后各自插入并发送。
- **为什么有问题**: 幂等键只有在数据库唯一约束、原子创建通知意图和可恢复 delivery state
  配合时才有效。“独立 Outbox”如果跨 Inbox DB 与 ledger DB 协调，无法用当前 SQLite transaction
  自动保证 exactly-once intent。
- **直接证据**:
  - `src/application/trades/auto_intake.py:569-587,894-932` 当前在 payload processor 内同步发送
    receipt，之后才 settle Inbox，崩溃边界正处于业务处理、投递和 Inbox 完成之间。
  - `src/application/trades/receipt.py:18-165` 当前 receipt decision 和同步发送没有 durable
    transactional outbox。
  - `src/application/ledger/repository.py:208-294` 当前生命周期 schema 没有 notification outbox。
  - `src/application/ledger/repository.py:1256-1269` 已有 ledger SQLite transaction，可作为
    lifecycle transition 与 notification intent 的单库原子边界。
- **影响**: 本次事故的核心症状——重复飞书——可能在换成新状态机后继续存在；同时还会引入
  状态已完成但最终回执永久丢失的新故障。
- **建议改法和验证点**:
  - Outbox 与 lifecycle ledger 放在同一 SQLite authority 中，状态迁移和 notification intent
    在同一 transaction 写入，并建立数据库唯一约束
    `(case_id, transition_type, resolution_revision)`。
  - 定义 `prepared -> claimed -> accepted/confirmed | explicit_failed | unknown`、lease 超时、
    worker crash recovery、重试上限和 operator reconciliation。
  - 明确飞书是否提供可查询的 message/provider id；若不能确认 unknown，必须冻结并提供人工
    reconcile/mark-delivered/compensating-send，而不是自动重发。
  - 覆盖 transition 前、事务提交后、HTTP 写出前后、provider accepted 后、标记 confirmed 前、
    并发 worker 和重启恢复的 fault-injection 测试。
- **修复风险（低/中/高）**: 高
- **严重程度（低/中/高/严重）**: 严重

### 5-未修复-高-存量案件迁移只有业务口径，没有可执行的身份映射、审计和回滚方案

- **位置**: “既有平仓回执视为已发送、升级后重新评估、只补一次最终结果”的迁移决策
- **问题类型**: 数据迁移 / 身份映射 / 回执去重 / 运维安全
- **当前写法**: 升级时继承历史平仓回执，重新评估未完成 case；未到截止时间继续 pending，
  到期后最多补发一次结果确认，不重新发送平仓消息。
- **反例/失败场景**: 一个 legacy case 没有 target lot manifest，存在多批同合约、同方向、同到期日
  的 lot；历史 receipt 只按 raw deal id 记录，而新 Outbox 按 case transition 记录。迁移若按合约
  聚合，可能把旧回执绑定到错误 case；迁移若新建 v2 case，又可能与 discovery 创建的 case 冲突。
  重跑迁移时还可能再次插入补发意图。
- **为什么有问题**: “视为已发送”是业务规则，不是可重放的数据映射。当前方案没有 inventory、
  deterministic mapping、ambiguous rejection、dry-run counts、migration marker、原子 apply、
  repeat dry-run、备份/rollback 和 projection replay，无法安全处理生产中的遗留形态。
- **直接证据**:
  - `src/application/trades/lifecycle.py:72-199` 的 legacy case 不具备 v2 target manifest。
  - `src/application/ledger/repository.py:807-864,1240-1253` 要求 v2 case immutable target
    identity，重复 case 的不可变字段冲突会被拒绝。
  - `src/application/trades/receipt.py:123-165` 当前 receipt state 以原始 deal/state 为中心，
    与拟议的 case transition key 不是同一身份域。
  - `src/application/ledger/writer.py:434-650` discovery 仍可能为未被 v2 case 占用的 lot
    建立新 case。
- **影响**: 升级后可能重新发送旧平仓消息、漏发最终结果、把结论绑定到错误 lot，或因 case
  identity 冲突使生命周期刷新失败；一旦在生产直接执行，难以证明可回滚。
- **建议改法和验证点**:
  - 单独增加 migration phase：只读 inventory，列出 legacy cases、v2 cases、target lots、
    evidence、terminal events、receipts 和无法唯一映射的记录。
  - 生成不可变 mapping manifest；只有一对一可证明的记录自动迁移，歧义记录保留并进入
    `needs_review`。
  - 使用 migration ledger 记录旧 receipt 到新 transition suppression 的映射，数据库唯一约束
    保证重跑不新增通知。
  - 流程固定为 backup -> dry-run exact counts -> atomic per-case apply -> repeat dry-run zero
    -> lifecycle/projection replay -> audit；明确 rollback 不依赖删除原记录。
  - 覆盖一合约多 lot、partial allocation、已有 v2 case、已确认 receipt、unknown receipt、
    重跑迁移和中途失败恢复。
- **修复风险（低/中/高）**: 高
- **严重程度（低/中/高/严重）**: 高

## Residual risks and suggested tracking

- 即使统一 deal identity，券商可能对同一经济事件提供多个不同 deal id；应单独跟踪经济事件去重，
  但不得用模糊匹配覆盖 broker identity。
- 15 分钟只是乱序观察窗口，不应被解释为 assignment/exercise 的最终清算截止时间。
- 股票成交方向和零价是强提示，但不能单独证明 assignment/exercise；需要唯一数量 allocation
  和结算来源身份。
- v1 对现金结算产品必须在 instrument/settlement-style gate 处显式 fail closed，保留枚举不等于
  开放自动终态。
- 生产服务仍处于止血状态；恢复服务属于独立授权边界，不能因方案或实现通过而自动启动。

**fail**

应先修订方案并再次 planreview，再进入实现。
