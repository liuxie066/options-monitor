## Goal / non-goal / success signal

目标仍是复用现有 10 分钟 timer 和一套 canonical pipeline：真实扫描只发生在固定报告点与有效半点；扫描后选择固定完整报告、新增候选通知或静默；用户查询读取最近成功快照。非 scan target 不请求 broker、不运行 pipeline，但允许对已经持久化的 exact delivery envelope 做恢复。计划继续明确排除第二 scanner、第二 scheduler、第二 sender、第二候选权威和新数据库。

成功信号现在同时覆盖：

1. 固定点完整报告和半点新增候选通知；
2. pipeline failure 不覆盖 successful current；
3. scheduled target 不被晚完成时间吞掉；
4. provider 未确认后可跨 tick 精确恢复；
5. target 字段不会在 schema/DTO/account execution 边界被静默删除；
6. no-scan retry 不生成新 revision、candidate diff 或 broker 请求。

## Assumptions tested

1. **Occurrence identity**：scheduler 幂等使用 scheduled occurrence，而不是完成时间；晚完成不会抑制尚未处理的下一 target。
2. **Write ordering**：计划不再在 account pipeline 返回后立即 mark；先持久化 successful/failure outcome 和应发送 envelope，再提交 target watermark，最后才调用 provider。
3. **Crash recovery**：watermark 提交后、send 前崩溃时，durable exact envelope 足以让下一 no-scan tick 恢复，不依赖旧 `output_runs`。
4. **Mark failure**：processed-target state write 失败时 provider 不调用，tick fail closed，pending envelope 保留并有 audit。
5. **Legacy scheduler state**：新字段缺失时有明确的 legacy seed 兼容；首个新版 scheduled target 后切到 target watermark。
6. **Account isolation**：target map 和 watermark 均按 account 保存；一个账户晚完成或失败不推进另一个账户。
7. **Boundary round-trip**：raw scheduler payload -> normalization allowlist -> scheduler view -> per-account scan decision -> account execution map 全程保留 target；force/manual 为 `None`。
8. **Top-level reachability**：no-scan 分支不再在 notification flow 之前退出；没有 envelope 时仍保持轻量 skipped。
9. **Delivery authority**：account delivery state 的 exact envelope 是跨 tick 恢复权威；run-scoped plan 只是 audit copy，避免 cleanup 破坏 retry。
10. **Retry invariants**：delivery-only 不改变 revision、source、candidate identities、delivery key、rendered message 或 message hash。
11. **Provider states**：definite failure 保持 pending；ambiguous 冻结内容，只允许幂等核验或 provider 合同明确支持的 exact retry；confirmed 才推进 fixed/candidate 状态。
12. **No-send / quiet**：no-send 不发布新的可自动发送 envelope；已有生产 envelope 不变；quiet 可保留已有 envelope 到允许窗口。
13. **Candidate recovery**：pending 从 `current_ids - alerted_ids` 推导，避免 current 已更新、delivery state 写失败或 force/manual current 抑制后续 scheduled candidate。
14. **End-of-day**：`15:50` definite failure 可在 `16:00` 恢复，但计划已把 scan-to-first-attempt 在 16:00 前完成列为 rollout capacity gate，而不是无条件假设。
15. **One authority path**：没有新增 scanner、broker fetch、sender、database、candidate ranking 或配置频率。
16. **Migration/query**：v1 pointer 仍显式 dry-run/backup/migrate；query 仍只读 successful current，不写 delivery state。

## Architecture boundary review

- scheduler 拥有 target 生成和 processed-target state；不承担候选判断。
- tool boundary / scheduler DTO 只传递 additive scheduling facts，不承载 notification business policy。
- account execution 运行 canonical pipeline 并返回 account result + target map，不提前提交 scheduler 水位。
- repository 拥有 immutable revision、successful current、candidate delivery state、exact envelope、锁和迁移。
- notification flow 负责编排 durable prepare -> watermark commit -> existing sender，以及 no-scan exact retry。
- domain pure functions继续拥有 candidate identity/eligible extraction/notification decision；candidate ranking、Close Advice、ledger 和 broker fetch 权威不变。

依赖方向符合项目约束，且三项修订没有引入跨层反向依赖或第二条业务权威。

## Best-practice review

- 使用 scheduled occurrence watermark，而不是完成时间推断任务是否执行，符合周期任务幂等与 catch-up 的基本恢复语义。
- 使用 prepare -> commit occurrence -> send 的顺序，避免消息已发送但 scheduler 水位未提交，也避免水位已提交却没有可恢复 envelope。
- exact rendered payload 与 key/hash/source 一起持久化，比跨 tick 重新 render 更能抵抗代码版本变化，也比依赖可清理 run artifact 更可靠。
- optional additive schema field 有显式 allowlist、DTO、mixed-version 和 round-trip 测试，兼容策略足够具体。
- no-send 不发布后续自动发送 envelope，避免 dry-run 在下一 production tick 意外变成真实发送。

## Optimal-solution review

当前方案是可信替代中最小的安全路径：

1. 保留现有 10 分钟 timer，不新增 delivery daemon；
2. 保留同一个 notification flow 和 sender，只增加 no-scan 窄入口；
3. 在现有 scheduler state 中拆分 target watermark 与 completion observation，不引入新状态服务；
4. 在现有 account delivery state 中保存 exact envelope，不新增数据库/outbox 框架；
5. 复用已有 per-account normalized scheduler payload，不创建平行 DTO。

没有发现更小且同样能覆盖 `09:40 catch-up`、`15:50 final retry` 和跨进程 field propagation 的方案。

## Overengineering review

没有发现无当前需求支撑的新抽象。新增内容都直接对应本轮故障模式：

- 一个 target watermark 字段；
- scheduler v1 的一个 optional field；

- 一个窄 scheduler commit callback。

计划明确拒绝第二 timer、第二 scanner、第二 sender、新数据库和独立 outbox daemon，符合 YAGNI。

## Overcoupling review

上一轮的主要耦合已经拆开：

- `last_run_utc_by_account` 不再同时承担 completion observation 和 occurrence idempotency；
- scan cadence 不再控制已持久化 delivery 的恢复机会；
- run-scoped audit plan 不再是跨 tick retry 的唯一数据依赖；
- account notify compatibility view 不被扩成新的并行业务 DTO，target 继续走已有 normalized scheduler payload。

剩余跨模块修改是现有 tick 主链的必要编排，不是双向依赖或共享新权威。

1. CEO 是否最终接受候选身份 `账户 + 市场 + 标的 + 策略族`。

这些是 execution/production gates，不是当前 implementation design blocker。

## Residual risks

- legacy scheduler state 首次切换仍只能把 completion-time 当兼容 seed；极端切换时刻可能保守跳过或重复最近一次 target，需要 rollout audit 观察首个新版 watermark。
- provider 在发送窗口结束后仍不可用时，未确认 fixed backlog 会转为 `expired_unconfirmed`，不会跨日自动补发。
- `15:50` pipeline 若太晚完成，可能没有同日 delivery-only retry slot；计划已把它升级为容量 gate，但无法由文档本身消除。
- fixed + half-hour 成功扫描会增加 immutable revisions；本 work unit 仍只监控容量，不同时设计 retention。
- v1 pointer 没有历史 fixed target，迁移只能保留可验证的 legacy confirmation/candidate evidence。
- 半点检查不是行情流实时通知；HK 午休期间延迟到下一有效 target。
