## Assumptions tested

1. **现有 US schedule 已经是 09:40 + 整点**：成立。`run_points=10/0/10` 经 `_scheduled_run_targets()` 生成 09:40、10:00、11:00…，无需配置迁移。
2. **用户的时间混乱主要来自 target、data-as-of 和 actual delivery 混淆**：成立。当前 scheduler decision 没有把 due target 作为用户可消费的 structured batch context；消息只能展示生成/数据时间。
3. **09:40 首次成功可以固定发送**：成立。没有 confirmed baseline 时 repository 产生 `delivery_kind=full`；该语义不依赖是否有新候选。
4. **后续整点 material-only 比逐小时 heartbeat 更符合决策通知**：成立。它让“收到消息”保持为需要重新关注的信号；系统是否运行由 runtime/scheduler/audit evidence 判断。
5. **批次字段可以不污染 canonical brief/delivery identity**：成立。它属于本次 run 的 notification context，可作为 optional scheduler/flow field传递，无需进入 persisted brief、digest、diff 或 delivery key。
6. **Material change 可以用业务语义而不是任意指标波动定义**：成立。Plan 将候选生命周期、持仓建议、blocked/recovered 和整手容量边界列为 material，并明确普通价格/收益率/Delta/文案/时间变化静默。

## Architecture boundary review

**通过。** Canonical brief/diff/repository lifecycle 保持不变；projection 负责用户安全字段，scheduler 提供 structured batch，notification flow 负责 A+ send policy，runtime health 继续走既有运维证据。没有把运行心跳塞进交易简报，也没有让 renderer 解析 scheduler reason 或 broker code。

## Best-practice review

**通过。** 方案采用 explicit optional context、fail-closed rendering、confirmed-delivery baseline、material-only noise control、separate operational observability、isolated no-send canary 和 production approval boundary。时间同时展示 batch 与真实 data-as-of，避免伪造准点送达。

## Optimal-solution review

**通过。** 相比每整点强制发送完整简报，A+ 保留清晰的 09:40 + 整点检查节奏，同时避免重复消息淹没真正变化；相比新增 heartbeat/cooldown/第二套 scheduler，它复用现有 lifecycle 和 schedule，改动更小。相比只显示 data-as-of，增加 structured batch 能直接解释 09:40 批次为何可能 09:43 才送达。

## Overengineering review

**通过。** 不新增配置 key、数据库、状态文件、通知时钟、heartbeat 状态机、模板 DSL 或执行 planner。新增内容限于 compact projection 和 optional run context。

## Overcoupling review

**通过。** Schedule config 不修改；batch context 不进入 brief identity；material diff 不依赖 renderer；operational health 不依赖是否产生用户消息；projection/diff/trigger-context 作为同一兼容代码单元发布，但没有绑定生产配置 rollout。

## Findings

Revision 5 已关闭上一版方案的核心方向错误：不再把 09:40 + 整点迁移为全程 `:40`，而是保留既有 schedule，通过 structured batch + localized data-as-of 解决时间认知问题，并采用用户确认的 A+ send policy。

## Residual risks and tracking

### R1 — Optional scheduler field compatibility

- **Risk**: 新增 batch 字段可能被 scheduler DTO normalizer 丢弃，或影响依赖 exact-key assertions 的 consumer。
- **Mitigation**: inventory consumers；字段 optional；缺失时 renderer 省略批次，不解析 reason；补 exact schema/compatibility tests。
- **Tracking**: Slice D implementation evidence。

### R2 — Material-only 仍可能被误解为任务未运行

- **Risk**: 用户没有收到整点消息时无法仅凭通知判断系统健康。
- **Mitigation**: 明确决策通知与运行状态分离；runtime/scheduler status 和 failure alert 保留；消息文档说明“无消息不等于未运行”。
- **Tracking**: user docs + remote runtime verification。

### R3 — 文案密度需要真实 fixture 验收

- **Risk**: 技术字段已清理，但候选、持仓、资金和变化 banner 仍可能过长。
- **Mitigation**: initial/material/blocked/recovered/manual representative snapshots；CEO visual sign-off。
- **Tracking**: renderer acceptance artifact。

### R4 — Current workspace baseline stale

- **Risk**: 当前 HEAD 为 v1.2.419，而 plan 基于 origin/main v1.3.4；实施时若直接在当前 worktree修改会遗漏最新 Daily Brief 代码并污染用户未跟踪文件。
- **Mitigation**: 基于实施时最新 origin/main 的干净 branch/worktree；保护 `paseo.json` 和现有 docs artifacts。
- **Tracking**: Gateflow preflight。
