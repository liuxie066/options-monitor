# Plan Review: Automatic Release Version Recommendation — Revised Plan

- Review timestamp: 2026-07-20 09:56:34 +0800
- Reviewed target: `docs/plans/automatic-version-recommendation-plan-20260720-094901.md`
- Scope: revised advisory-only v1, remote stable-tag baseline, Unreleased-driven classification, recommendation digest, `version_update` integration, Git topology tests
- Prior review: `docs/reviews/plan-review-20260720-094432.md`
- Conclusion: **fail**

## Summary

修订方案已经实质解决上一轮的大部分结构性问题：它删除了“自动理解任意源码语义”的承诺，明确 v1 仅 advisory，区分 freshness 与 authorization，保留手动路径，并加入真实 Git topology tests。方向已经接近可实施。

本轮仍发现 2 个高严重度和 3 个中严重度问题。最主要的 blocker 是：远端 tag 只比较名称/版本，没有定义 remote tag object/peeled commit 与本地 baseline commit 的身份一致性；另外输出的 `confidence=high` 仍会把“Changelog 声明解析成功”误表达成“SemVer 语义判断可靠”。

## Assumptions tested

1. `git ls-remote --tags --refs` 足以建立可重放的远端 baseline identity。
2. 本地同名 tag 可以直接代表远端同名 tag 的 commit。
3. `confidence=high|medium` 能准确表达本方案实际拥有的证据强度。
4. 新 recommendation module 与现有 `version_check.bump_version` 的依赖方向已经明确。
5. Tool schema 增加远端查询后，capability/requirements contract 仍完整。
6. detached HEAD 的 preview/apply 行为已收敛，implementation agent 无需自行决定。

## Findings

### PR2-01-未修复-高-远端 tag 只有名称权威，没有定义对象身份和 peeled commit 校验
- **位置**: 4.1 版本基线、4.2 本地基线可用性、6.3 recommendation digest、7.2 Apply recommendation
- **问题类型**: version skew / 状态机漏洞 / 契约缺失
- **当前写法**: 通过 `git ls-remote --tags --refs origin` 选择最高稳定 tag；本地存在同名 tag/commit object 且为 HEAD ancestor 即可。digest包含 remote tag/version 和 local baseline commit，但没有包含 remote tag object id 或 remote peeled commit，也没有规定两者如何相等。
- **反例/失败场景**: 本地 `v1.3.0` 指向 commit A，远端同名 tag 被 force-move 到 commit B。名称、版本和本地 ancestry检查仍通过，classifier基于 A 计算 diff；apply 时再次查询仍只看到同名 `v1.3.0`，不会发现 B。对于 annotated tag，`--refs` 返回 tag object id，本地 `^{commit}` 返回 commit id，不能直接按 SHA 相等比较，implementation agent必须临场决定解析方式。
- **为什么有问题**: 方案声称远端 release 是 authority，但实际上只让远端决定版本字符串，diff baseline仍由未经远端身份验证的本地 ref 决定。digest无法防同名 tag identity漂移。
- **直接证据**: plan `:76-95` 只定义 tag name查询和本地存在/ancestry；`:245-255` 的 digest没有 remote object/peeled commit；`:306-314` 的 apply recheck只写 remote tags/target不存在。当前 `release_target.parse_release_tags` 也只保留 version/tag，不保留 object id，见 `src/application/release_target.py:64-84`。本仓库当前 tag 是 lightweight commit ref，但手动补发流程允许未来出现 annotated tag，不能依赖当前偶然形态。
- **影响**: 基于错误 commit 计算 release diff，遗漏或重复变更，推荐错误版本，且用户确认后仍无法检测。
- **建议改法和验证点**:
  1. 使用 `git ls-remote --tags origin`，同时解析 `refs/tags/vX.Y.Z` 和可选的 `refs/tags/vX.Y.Z^{}`。
  2. 定义 `remote_tag_object_sha` 与 `remote_commit_sha`：lightweight tag 的 commit sha 为 raw sha；annotated tag 使用 peeled sha。
  3. 本地执行 `git rev-parse refs/tags/vX.Y.Z^{commit}`，必须等于 `remote_commit_sha`。
  4. digest同时包含 remote raw object sha、remote peeled/commit sha 和 local resolved commit sha。
  5. preview和apply都校验；增加 lightweight、annotated、force-moved same-name tag 测试。
- **修复风险（中）**: 需要扩展远端 tag parser，而不是只复用现有 `(version, tag)` 结构。
- **严重程度（高）**: baseline authority 当前没有真正成立。

### PR2-02-未修复-高-confidence 字段把声明完整性误表达成语义正确性
- **位置**: 5.2 Sensitive-path warning、8.3 Output、9 User-facing interaction、15 Residual risks
- **问题类型**: 用户可见契约 / 最佳实践偏离 / 证据语义错误
- **当前写法**: 未命中敏感路径且 Unreleased 合法时返回 `confidence=high`、`manual_review_required=false`；命中敏感路径时返回 medium。与此同时方案明确承认分类只读取维护者声明，不理解源码业务语义。
- **反例/失败场景**: 一个 breaking 的返回值语义变化发生在未列入敏感路径的模块，维护者把它写在 `Changed` 下。工具返回 patch + high confidence + 无需人工复核。路径表也漏掉了当前 repo 的多个公共 surface，例如 `src/application/agent_tool_*.py`、`src/interfaces/agent/**`、`src/application/notify_symbols.py`、`src/application/multi_tick/notify_format.py` 和顶层 runtime config 文件。
- **为什么有问题**: “high confidence”在用户界面自然表示工具相信版本等级正确，但实际只能证明 Changelog 格式完整且路径表未命中。方案第 18、32、625-626 行已经承认工具不是语义 oracle，与 `high/manual_review_required=false` 冲突。
- **直接证据**: plan `:169-210` 用路径命中决定 high/medium；`:370-384` 将 confidence放在 recommendation里；`:625-626` 承认 Changelog由人声明且路径有漏报。项目 AGENTS ownership显示公共 Tool、CLI、通知和 config surface 分散在多个位置，单一路径清单不能证明没有兼容性风险。
- **影响**: 用户可能因为“高置信度、无需复核”接受被低估的 patch；工具的可解释性反而制造错误信任。
- **建议改法和验证点**:
  1. 删除 semantic `confidence`；替换为 `declaration_status=complete` 和 `review_flags`。
  2. `manual_review_required` 对所有 recommendation 保持 true，因为用户确认本来就是产品目标；敏感路径只增加具体 review flags。
  3. UI写“按 Unreleased 声明推荐 minor”，不要写“置信度高”。
  4. 路径表只表示关注区域，不表示未命中即安全；输出契约和测试必须固定该语义。
- **修复风险（低）**: 主要是收紧输出语义和测试期望。
- **严重程度（高）**: 当前输出会过度陈述自动分类能力。

### PR2-03-未修复-中-远端依赖没有进入 Agent Tool requirements contract
- **位置**: 8 Tool contract、10 Ownership and files
- **问题类型**: 公共契约缺失 / 架构边界
- **当前写法**: 新增 `remote_name` 并要求 preview/apply 查询远端，但只写了扩展 input schema/examples，没有要求把 `VERSION_UPDATE_TOOL.requires` 从 `("local_repo",)` 更新为包含 `git_remote`，也没有更新相关 manifest/healthcheck assertion。
- **反例/失败场景**: `om-agent spec` 继续声明该 Tool只需要 local_repo；调用方在离线环境选择它，直到执行时才收到 remote lookup failure。依赖发现和 Tool实际行为不一致。
- **为什么有问题**: Agent Tool manifest是调用方选择工具和展示依赖的公共契约。新增必需网络/远端 Git依赖必须显式进入 requires，否则 output contract虽然详细，capability discovery仍错误。
- **直接证据**: 当前 `VERSION_UPDATE_TOOL` 在 `src/application/agent_tools/runtime.py:167-184` 只 requires `local_repo`；manifest会原样暴露 requires，见 `src/application/agent_tools/base.py:96-115`。plan `:318-347` 未规定 requirements变化，`:444-447` 只写 schema/examples。
- **影响**: Tool可用性报告错误、离线失败发生得太晚、contract tests无法验证新依赖。
- **建议改法和验证点**:
  1. 明确 auto mode动态依赖问题。由于手动 mode不需要 remote，优先使用 output/runtime preflight而不是把整个 Tool永久标成不可用；或者拆分 Tool。plan必须二选一。
  2. 最小方案：保留 `requires=("local_repo",)`，在 input schema/description中明确 `bump=auto requires git remote access`，并增加 mode-sensitive dependency metadata若现有框架支持；若框架不支持，则在 docs和 error contract中明确 degraded behavior。
  3. 增加 spec、healthcheck、offline auto/manual path tests。
- **修复风险（中）**: 单一 Tool同时承载离线手动模式和在线 auto模式，不能简单全局添加 `git_remote` 而不影响兼容；需要明确动态依赖表达。
- **严重程度（中）**: implementation agent仍需决定公共 manifest语义。

### PR2-04-未修复-中-版本计算 ownership 未收敛，容易产生循环依赖或重复 SemVer 逻辑
- **位置**: 5.1 Classification policy、10 Ownership and files、S1/S2
- **问题类型**: 架构边界 / 不可直接实施
- **当前写法**: 新 recommendation module负责“recommendation and digest”，输出含 target version；plan同时要求继续复用 `version_check.bump_version()`。但 `version_check.py` 又要导入/call recommendation module，未定义 bump calculation放在哪一层。
- **反例/失败场景**: recommendation module为生成 target/digest导入 `version_check.bump_version`，而 `version_check` 导入 recommendation module，形成循环。实现者为了绕开循环在新模块复制 SemVer bump，产生两个版本规则真源。
- **为什么有问题**: target version进入 digest，不能简单留到 write层再计算；plan必须指定共享纯函数ownership。
- **直接证据**: plan `:159-165` 要求复用现有 `bump_version()`；`:423-433` 让新模块拥有 recommendation/digest；`:437-442` 又让 version_check调用 recommendation。当前 `bump_version` 位于 `src/application/version_check.py:29-38`。
- **影响**: 循环 import、重复逻辑、测试分裂、未来 SemVer规则漂移。
- **建议改法和验证点**:
  1. 把纯 `bump_version` 移到 `src/application/release_target.py`，由 recommendation和version_check共同导入；
  2. `version_check.py` 保留 re-export 或 wrapper，避免现有 imports/tests破坏；
  3. 明确 recommendation module不导入 version_check；增加 architecture/import smoke test。
- **修复风险（低）**: 小范围 ownership移动，可保持 facade兼容。
- **严重程度（中）**: 当前文件计划仍会迫使实现 Agent自行设计依赖方向。

### PR2-05-未修复-中-detached HEAD 的 apply 决策仍是空白
- **位置**: 12 Test matrix 第 19 项、4.2 baseline validation
- **问题类型**: open question 未收敛 / 状态机契约缺失
- **当前写法**: 测试写“Detached HEAD with valid ancestor may preview；apply behavior explicitly tested”，但没有规定 apply 应允许还是拒绝。
- **反例/失败场景**: 实现者选择拒绝 detached apply，会破坏项目曾使用的临时 detached release worktree路径；选择允许但未在输出中标记，用户可能在无法正常推送的临时 checkout里更新 VERSION 后误以为发布分支已准备好。
- **为什么有问题**: 这是用户可见状态机分支，测试不能只写“测试它”，必须写预期结果。repo的安全发布实践会在主 checkout dirty/diverged时使用隔离 worktree，因此 detached状态并非纯理论。
- **直接证据**: plan `:550-560` 对其它 topology case都有明确 expected status，只有 detached apply未决定；`:90-97` 也未要求 branch ref。
- **影响**: 不同实现产生不同 release可用性；文档和测试无法验收。
- **建议改法和验证点**:
  1. 建议允许 detached preview和apply，只要 remote baseline identity、ancestry、VERSION、digest和target collision检查全部通过；
  2. 输出 `workspace.branch=null`、`workspace.detached=true` 和 warning，明确后续 commit/push需要调用方处理；
  3. 增加 detached valid、detached stale baseline 和 detached target collision测试。
- **修复风险（低）**: 只需锁定行为和输出字段。
- **严重程度（中）**: 当前仍不是完全 code-generation-ready。

## Architecture boundary review

新模块放在 `src/application/`、不进入 domain、只写 VERSION的边界是合理的。剩余架构问题集中在两个地方：SemVer bump纯函数ownership未抽离；单一 Tool同时包含离线手动模式和在线 auto模式，导致 requires contract不能简单静态表达。二者都应在实现前写入plan，而不是交给实现者猜。

## Best-practice review

修订方案已采用 fail-closed baseline、两次 remote recheck、bounded untracked hashing、真实 bare-origin/two-clone测试和 advisory rollout，这些都符合发布工具最佳实践。需要修正的是 tag identity而非tag name、证据完整性而非semantic confidence，以及明确 dynamic dependency contract。

## Optimal-solution review

以标准化 Unreleased作为v1 semantic input是当前最实际的方案。无需恢复上一版的广义源码推断。最优修正不是新增更多 detector，而是：完善 remote tag identity、删除误导性的 confidence、抽离共享 SemVer函数、明确 auto模式的远端依赖和detached行为。

## Overengineering review

本轮没有发现新的主要过度设计。bounded untracked digest和双重remote check与实际 stale/race风险匹配。若继续扩充 sensitive-path列表来追求“高置信度”，会重新滑向过度设计；应通过删除 semantic confidence解决，而不是扩大路径表。

## Overcoupling review

release_test_plan和recommendation可以共享Git命令模式，但不应共享risk枚举。当前plan维持了这条边界。需避免 recommendation反向导入version_check；共享SemVer纯函数应下沉到已经拥有parse/compare的release_target模块。

## Open Questions

1. auto mode的动态 `git_remote` 依赖如何在当前静态 Tool manifest中表达：描述级契约，还是扩展 framework支持 mode-sensitive requirements？
2. 是否允许 remote annotated tags；如果允许，按上述 peeled commit契约实现。如果不允许，应显式 fail closed并说明手动补发限制。
3. detached HEAD允许apply的建议是否接受？

## Residual risks and tracking

- Changelog声明仍可能错误；这是advisory工具的固有边界，必须通过用户确认和不使用semantic confidence表达。
- remote tag在最终 GitHub workflow执行前仍可能发生极小race；workflow tag collision应继续作为最终保护。
- 将来若建立contract snapshots，应作为独立work unit，不扩大本v1。

## Final conclusion

**fail**，但比上一版明显接近通过。

需要在plan中修复后再进入 implementation：

1. 定义 remote raw/peeled tag identity并与本地commit严格相等；
2. 删除或重命名误导性的semantic confidence；
3. 收敛auto模式的动态远端依赖契约；
4. 抽离共享SemVer bump ownership；
5. 明确detached HEAD apply行为。

这些都是局部plan修正，不需要推翻当前advisory-only方向。
