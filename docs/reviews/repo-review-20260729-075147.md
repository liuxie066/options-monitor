## Findings

### 1-未修复-高-账户与标的控制面写错权威层，且账户 CLI 绕过统一写门禁

- **入口/函数**：`./om accounts add|edit|remove`、`./om symbols ... --apply`、`om-agent manage_accounts|manage_symbols`、Inbound symbol add/remove。
- **文件（行号）**：`src/interfaces/cli/account_ops.py:10-35,38-87`；`src/application/account_management.py:14-105`；`src/application/agent_tool_init_local.py:236-258,324-449,457-620,628-685`；`src/interfaces/cli/symbols.py:107-170`；`src/application/agent_tools/config.py:482-508`；`src/application/agent_tools/symbols_impl.py:157-190`；`src/application/assistant/symbol_operations.py:40-68,228-319`；`src/application/runtime_config_freshness.py:371-503`。
- **触发输入**：通过任一公开控制面新增账户、修改 symbol，或执行 `./om accounts remove --market us --account-label lx`；也可显式传入 `--market us --config-path config.hk.json`。
- **实际分支**：这些路径直接修改 `config.us.json` / `config.hk.json`。human account CLI 没有 `--dry-run`、`--apply` 或 `--confirm`，application 默认 `dry_run=False`；显式 `config_path` 还会绕过 market/path identity 校验。Inbound add/remove 在 YAML authoring 存在时仍回退到 runtime JSON。
- **预期行为**：所有持久化配置 CRUD 只修改 `config.yaml`，在统一 preview/confirm/CAS/backup 边界内验证并重建对应市场 snapshot；请求市场、路径和生成元数据必须一致。
- **实际行为**：命令可以直接覆盖 runtime snapshot 并返回成功，`freshness.ok` 仍可能为真；下一次正常 build 或 upgrade 会按未改变的 YAML 重建，使已“成功应用”的账户或标的变更静默消失。错误的 market/path 组合还可能改错市场并回报请求市场。
- **直接证据**：writer 最终调用 `Path.write_text()`；freshness 只校验生成源指纹，没有校验 runtime effective payload；仓库已有 `check_runtime_config_identity()`，但 account writer 未调用。隔离临时配置复现中，无确认的 account add 返回 `write_applied=true`；重建后新增账户消失，而 mutation 后 freshness 仍为 `ok=true`。
- **影响**：账户、portfolio source、Futu intake mapping 和 symbol 策略可能在升级/重建后回退；误操作可直接删除账户或改错市场，且成功收据无法反映真正权威状态。
- **建议改法和验证点**：收敛为单一 YAML authoring service；默认 dry-run，apply/confirm 明确分离，remove 强确认；写前做 market/path/generated identity fail-closed；迁移并审计 runtime-only 差异。新增“默认不写”“重建不丢”“US/HK 交叉路径拒绝”“失败时文件字节不变”回归。
- **修复风险**：高
- **严重程度**：高

### 2-未修复-高-YAML authoring 与 runtime snapshot 发布不是原子事务

- **入口/函数**：canonical symbol mutation、Inbound symbol/model mutation、跨市场 runtime build。
- **文件（行号）**：`src/application/config_yaml_symbols.py:25-94,319-370`；`src/application/assistant/symbol_operations.py:105-136,267-319`；`src/application/assistant/model_operations.py:117-148,217-281`；`src/application/config_yaml.py:744-785`。
- **触发输入**：修改 `config.yaml` 后，US build 成功但 HK build 或 assistant config rebuild 失败；也包括进程在连续写入之间退出。
- **实际分支**：authoring source 先备份并覆盖，再按顺序写 US、HK 和 assistant 派生配置；后续任一步失败不会恢复此前已写入的 source/snapshot。
- **预期行为**：source 与所有派生产物属于同一 generation：先在 staging 目录完整构建、验证和计算身份，再一次性提交；失败时旧 generation 保持完整可用。
- **实际行为**：操作返回失败，但 source 与部分 snapshot 已生效，另一些仍是旧 generation。
- **直接证据**：`config_yaml_symbols.py` 先写 source，再循环 build；Inbound symbol/model 路径也分别加载、修改、落盘和重建，没有跨文件 commit/rollback 边界。
- **影响**：US/HK、CLI/assistant、当前进程/下一次进程可能消费不同 generation；失败收据不能代表“无效果”，恢复依赖人工判断。
- **建议改法和验证点**：引入 generation staging + 全量 validate + 原子 pointer/rename commit；或提供明确的 compensation rollback。用 fault injection 覆盖 source 后、US 后、HK 后、assistant 后失败，确认全部文件仍指向同一旧或新 generation。
- **修复风险**：高
- **严重程度**：高

### 3-未修复-高-Inbound preview 签名未绑定配置 revision，确认时可应用不同输入

- **入口/函数**：Inbound operation preview/confirm、symbol/model operation apply。
- **文件（行号）**：`src/application/assistant/operation_signature.py:70-82`；`src/application/assistant/operation_lifecycle.py:193-245`；`src/application/assistant/symbol_operations.py:105-136,267-319`；`src/application/assistant/model_operations.py:117-148,217-274`；`src/application/runtime_config_paths.py:87-90`。
- **触发输入**：用户 preview 后、confirm 前，另一个 CLI/Inbound 操作修改同一个 authoring source；或两个确认并发执行。
- **实际分支**：签名只覆盖 operation fields 与 payload hash，没有包含 source SHA/revision；apply 阶段重新读取当前文件并基于新状态计算 before/after。runtime JSON 临时文件名也是固定路径。
- **预期行为**：确认只能提交 preview 时看到的 source revision；revision 已变化时返回 `STALE_PREVIEW`，并发写入通过每配置锁/CAS 序列化。
- **实际行为**：有效签名可在不同 source revision 上应用，产生未预览的 diff、覆盖并发修改，或因固定临时文件互相干扰。
- **直接证据**：operation signature payload 中没有 source hash；symbol/model apply 均在 confirm 阶段重新 load；temporary target 不是请求唯一名称。
- **影响**：preview/confirm 的安全承诺失效，审计记录无法证明用户确认了最终写入内容。
- **建议改法和验证点**：签名加入 canonical source SHA、generation id 和目标身份；apply 使用 lock + CAS；临时文件使用唯一名称。并发测试覆盖 stale preview、双 confirm、不同 symbol 同源写入和进程中断。
- **修复风险**：中
- **严重程度**：高

### 4-未修复-高-inline defaults 变更不会使旧 runtime snapshot 判定为 stale

- **入口/函数**：runtime config build metadata、freshness check、tick/tick-cron preflight。
- **文件（行号）**：`src/application/config_yaml.py:624-654,687-720`；`src/application/runtime_config_freshness.py:371-448`；`src/application/tick_cron.py:170-201`；`src/application/multi_account_tick.py:175-187`。
- **触发输入**：代码内 `DEFAULT_CONFIG` 或 inline defaults 改变，但 `config.yaml` 不变，运行旧 runtime snapshot。
- **实际分支**：snapshot 记录 `default_config_sha256`，freshness 对 inline source 只检查该字段非空，不与当前 defaults 重新计算值比较。
- **预期行为**：当前 defaults hash 与 snapshot metadata 不一致时 fail closed，要求 rebuild。
- **实际行为**：旧 snapshot 继续通过 `freshness.ok=true`，tick/tick-cron 将其视为可运行。
- **直接证据**：隔离复现修改当前 inline default hash 后，旧 snapshot 仍被接受为 fresh；对应分支没有 equality comparison。
- **影响**：发布改变默认策略、安全阈值或控制项时，生产可能继续使用旧 effective config，且 readiness 不报警。
- **建议改法和验证点**：为 inline defaults 建立可解析的 source ref，freshness 每次重新计算并比较 hash；新增 defaults-only drift、YAML-only drift、两者同时变化与 rebuild 恢复测试。
- **修复风险**：低
- **严重程度**：高

### 9-未修复-高-upgrade 在 release 切换前覆盖 live runtime config，失败可留下旧代码配新配置

- **入口/函数**：`om update apply` / service upgrade apply。
- **文件（行号）**：`src/application/service_upgrade.py:936-1002,1051-1089,2050-2059,2121-2138`；`src/application/config_yaml.py:744-785`。
- **触发输入**：目标 release 已下载，config rebuild 成功，但随后 target validation、symlink switch、unit reconcile 或 restart 失败。
- **实际分支**：upgrade 使用目标 release 代码直接写 live runtime paths，然后才切换 current release symlink。
- **预期行为**：目标 release 的配置先写 staging generation，目标验证全部通过后与 release pointer 一起提交；失败保持旧 release + 旧 config。
- **实际行为**：失败后可能运行旧代码 + 新格式/新默认值配置；部分失败结果还会报告 `changed=false`。
- **直接证据**：forward flow 中 `_build_runtime_configs` 先于 `_switch_current_symlink`，底层 builder 直接写 runtime target path。
- **影响**：升级的回滚边界被破坏，旧服务进程重启后可能无法读取新配置或产生未发布行为。
- **建议改法和验证点**：将 target configs 构建到 release/generation staging；验证、identity、service plan 全通过后原子提交 pointer/config；为 symlink、reconcile、restart、health 失败增加 compensation 测试。
- **修复风险**：高
- **严重程度**：高

### 10-未修复-高-rollback 只切换 symlink 和重启，没有恢复目标版本配置与 service profile

- **入口/函数**：service upgrade rollback。
- **文件（行号）**：`src/application/service_upgrade.py:1664-1721,2050-2095,2263-2357`；`tests/test_service_deploy.py:3719-3751`。
- **触发输入**：新版本已写入 config 或新增/删除 unit，随后执行 rollback 到旧版本。
- **实际分支**：rollback 切换 current symlink，并可选 restart；不按旧 release 重建/验证 runtime config，不 reconcile 旧 release unit/profile，也不执行完整 healthcheck。
- **预期行为**：rollback 与 forward apply 使用同一 staging/reconcile/health pipeline，只是目标版本不同。
- **实际行为**：代码回到旧版本，但 config 和 systemd topology 可能仍属于新版本。
- **直接证据**：forward flow 包含 build/reconcile/verify，rollback flow 缺失这些步骤；现有 rollback 测试只验证 `restart=false` 时 symlink。
- **影响**：所谓 rollback 不能恢复完整可运行状态，可能留下 retired/new units、配置 schema 不匹配和错误 runtime health。
- **建议改法和验证点**：复用 target-release apply pipeline；记录 rollback receipt 的 config generation、unit diff、restart 与 health；测试跨 schema、增删 unit、health 失败与二次 compensation。
- **修复风险**：高
- **严重程度**：高

### 11-未修复-高-service drift 不检查已安装 timer 的 enabled/masked 状态

- **入口/函数**：`om service drift`、upgrade service reconcile。
- **文件（行号）**：`src/application/service_drift.py:199-230,481-515,624-711`；`src/application/service_upgrade.py:630-665`；`tests/test_service_deploy.py:506-606`。
- **触发输入**：unit 文件内容正确且存在，但 timer 被 `systemctl disable` 或 mask。
- **实际分支**：drift 比较 expected unit 文件与磁盘内容，不读取已存在 unit 的 enable/mask 状态；apply 只 enable missing timer。
- **预期行为**：read-only drift 报告 `disabled` / `masked`；受控 apply 在 confirm 后修复并 read back。
- **实际行为**：disabled timer 可显示 zero drift，定时业务不会运行。
- **直接证据**：service inventory 没有 `systemctl is-enabled` 分支；测试只覆盖 missing/mismatched 文件。
- **影响**：生产调度停止但 readiness/upgrade 验证仍可能绿色。
- **建议改法和验证点**：为每个 expected timer 采集 `is-enabled`、`is-active`/`masked` 状态；将文件 drift 与 activation drift 分开；测试 disabled、masked、static、indirect 和 repair readback。
- **修复风险**：中
- **严重程度**：高

### 12-未修复-高-upgrade 失败状态仍编码为 `ok=true`，CLI 与 runtime_status 可吞掉失败

- **入口/函数**：service upgrade result、manual CLI exit、verify/runtime_status aggregation。
- **文件（行号）**：`src/application/service_upgrade.py:1575-1624,1750-1753,1803-1808,2096-2186`；`src/interfaces/cli/service_ops.py:336-353`；`src/interfaces/cli/main.py:170-172`；`src/application/agent_tools/runtime_status_impl.py:940-990`。
- **触发输入**：restart、service reconcile 或 post-upgrade healthcheck 失败。
- **实际分支**：多个 terminal failure status 仍返回 `ok=true`；CLI 依据 `ok` 返回 exit 0；runtime_status 只识别少数失败枚举，忽略 reconcile/health failure。
- **预期行为**：manual apply 的任何未完成 terminal state 都必须 `ok=false`、非零 exit，并被 verify/runtime_status 标红；自动 transport 需要的 exit 语义应单独表达。
- **实际行为**：操作可在服务未恢复或 health 未通过时以成功退出，后续聚合状态也可能漏报。
