### S1-DR-01-未修复-高-实现指纹在首次写入时读取可变源文件，可能把旧进程代码标记为新实现
- **入口/函数**: 任一长生命周期旧进程首次调用 `publish_full_position_projection()` 或 `read_current_position_projection()` -> `loaded_projector_implementation_fingerprint()`。
- **文件(行号)**: `src/application/ledger/position_projection_publication.py:41-103,120-139`; `src/application/ledger/projector_implementation.py:124-138,249-307`。
- **输入场景**: 进程已经 import 并在内存中执行旧版 projector；随后 release 目录或 checkout 中的 `.py` 文件被原地升级；该进程在升级后第一次发布完整投影。
- **实际分支**: implementation digest 没有在模块加载/进程启动时冻结，而是在首次 publication/read 时通过 `Path(__file__)` 向上解析当前磁盘目录并读取当时的源文件；`lru_cache` 只缓存这次延迟读取的结果。
- **预期行为**: head/source state 必须绑定当前进程实际已加载、正在执行的 semantic implementation；旧进程不得把其输出标记成新文件版本的实现指纹。
- **实际行为**: 旧进程可以使用内存中的旧 projector 生成 rows，却将升级后磁盘中新源码的 digest 写入 source/head，并产出 `trusted` head；新进程看到相同 digest、generation 和 row fingerprint 后可能错误接受该结果。
- **直接证据**: `publish_full_position_projection()` 在 diff 后才调用 `loaded_projector_implementation_fingerprint()`；缓存函数第一次执行才调用 `verify_expected_projector_implementation()`；resolver 和 hasher 均读取磁盘路径/bytes，没有任何 module-import-time freeze 或已加载 module byte binding。接受计划明确要求“at process startup”构造并缓存 loaded-projector fingerprint。
- **影响**: 版本切换窗口可产生语义实现与 durable trust metadata 不一致的 falsely-trusted projection；这直接破坏新/旧 binary fail-closed 边界。
- **建议改法和验证点**: 在 semantic modules 被 import 后立即冻结一次 loaded implementation result，publication/read 只消费冻结值；不要在交易 transaction 内首次读取文件。增加回归测试：先加载旧 module/result，再修改 release-style source tree，确认当前进程仍保持原 frozen identity 或 fail closed，且 transaction 内 file-read spy 为零。若项目的受控安装保证绝不原地替换，也应把该前提固化为可验证契约而非隐含假设。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### S1-DR-02-未修复-中-head 账户发现重新扫描完整交易历史，违反 O(A) 发布边界
- **入口/函数**: `publish_full_position_projection()` -> `publish_full_position_projection_heads()` -> `list_position_projection_accounts()`。
- **文件(行号)**: `src/application/ledger/repository.py:1824-1844,1920-1931`; accepted plan `docs/gateflow/data-storage-runtime-projection-p3a/plan.md:733-758`。
- **输入场景**: 任意 full publication，特别是交易历史持续增长但账户数稳定的 store。
- **实际分支**: account discovery 对 heads、全部 lots、全部 trade events 做 `UNION`，其中 `SELECT account FROM trade_events` 必须遍历历史事件索引/表后去重；随后调用方还已持有 `known_accounts=diff.accounts` 和 touched old/new accounts。
- **预期行为**: account set 由既有 heads 与本次 known/touched accounts 组成；zero-lot accounts 由 durable head 保留，不扫描 event history，head fanout 为 O(A)。
- **实际行为**: 每次发布额外增加 O(E+L) account discovery 和 UNION 去重；历史越长，哪怕没有新账户，该步骤也持续变慢。
- **直接证据**: SQL 明确包含 `SELECT account FROM trade_events WHERE account IS NOT NULL` 和 lot-table UNION；接受计划 8.3 明确规定集合来源并写明 “without scanning event history”。
- **影响**: 重复加载大量历史数据的问题被带入新的 publication boundary；它会掩盖后续 S3/S4 fast-path 收益，并增加 writer 持锁时间。
- **建议改法和验证点**: `list_position_projection_accounts()` 只读取既有 heads；union 本次 diff 返回的 all/touched accounts。首次有 lot 的账户由 lot trigger/diff 创建 head，删除后的 zero-lot account由旧 head保留。增加 SQL trace/authorizer 测试，证明 head publication 不读 `trade_events`、不全扫 `position_lots`，并覆盖首次账户、账户迁移和 zero-lot 保留。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### S1-DR-03-未修复-中-trusted reader 在发现 head 不可用前仍解码并哈希全部账户持仓
- **入口/函数**: `read_current_position_projection()` -> `read_position_projection_account_state()`。
- **文件(行号)**: `src/application/ledger/position_projection_publication.py:136-195`; `src/application/ledger/repository.py:2017-2045`。
- **输入场景**: migration window 没有 head、direct mutation 令 generation stale、schema cookie drift、binary fingerprint mismatch，或 head status 已是 untrusted；账户保留大量 closed lots。
- **实际分支**: repository 在读取 source/head 后无条件执行 `position_projection_account_snapshot(include_records=True)`；上层直到 snapshot 完成后才依次检查 source/head/status/generations/schema cookie。
- **预期行为**: 先用 O(1) metadata 判断是否有资格信任；任何 head/source/version/generation/cookie mismatch 立即返回 `not_initialized`/`data_unavailable`。只有 metadata 全部通过时才扫描 authoritative account lots 并验证 fingerprint。
- **实际行为**: 已知不可信的读取仍执行 indexed row scan、JSON decode、完整 canonical serialization/hash 和 list materialization，之后才丢弃结果。
- **直接证据**: `read_position_projection_account_state()` 无条件构建 snapshot；上层 checks 位于其返回之后。对于 head missing 的路径，完整 lot work 已发生才执行 `if source is None or head is None`。
- **影响**: fail-closed correctness 仍在，但故障/迁移/版本偏移时每次读都付出 O(L_account) CPU 和内存，可能放大超时并阻塞诊断。
- **建议改法和验证点**: 将 metadata read 与 snapshot read 分开但保持同一 read transaction：先读取 source/head/cookie并完成便宜 checks，再按需流式扫描 rows。加入 head missing、generation mismatch、cookie mismatch、implementation mismatch 的 SQL/decoder spy，断言零 lot-row visits；成功路径仍精确验证 fingerprint并返回全部 retained rows。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### S1-DR-04-未修复-中-指纹查询排序与唯一规范化索引不匹配，每次 changed-account hash 都建立临时 B-tree
- **入口/函数**: `publish_full_position_projection_heads()` / trusted read -> `position_projection_account_snapshot()`。
- **文件(行号)**: `src/application/ledger/repository.py:283-289,1846-1879`; plan index contract `docs/gateflow/data-storage-runtime-projection-p3a/plan.md:391-404`。
- **输入场景**: 对拥有大量 retained current/closed lots 的 changed account 发布 head 或执行 trusted read。
- **实际分支**: snapshot 要求 `ORDER BY record_id ASC`；唯一 normalized lot index 是 `(account, expiration, record_id)`。SQLite 查询计划使用该索引过滤 account 后仍报告 `USE TEMP B-TREE FOR ORDER BY`。
- **预期行为**: 接受计划所称“stable ordered SQLite cursor -> canonical streaming encoder”应由索引直接提供 canonical `record_id` 顺序，避免额外排序分配。
- **实际行为**: 每次 hash 在 O(L_account) serialization 之外再承担 O(L_account log L_account) 排序和 O(L_account) 临时结构；所谓 streaming 只避免 Python record list，未避免 SQLite materialization。
- **直接证据**: 实测 `EXPLAIN QUERY PLAN SELECT record_id FROM position_lots WHERE account='lx' ORDER BY record_id ASC` 返回 `USE TEMP B-TREE FOR ORDER BY`；同一索引仅能直接满足 `ORDER BY expiration, record_id`，但 fingerprint contract 按 `record_id` 排序。
- **影响**: retained closed rows增长时 changed-account fingerprint和 trusted read的时间/空间效率明显劣化，可能让后续 500-ms gate失败。
- **建议改法和验证点**: 将 lot normalized indexes 分为用途明确的 `(account, record_id)`（fingerprint/trusted read）和仅在确有 expiration query需要时的 `(account, expiration, record_id)`；若只允许一个索引，应根据真实 query inventory选择，不能让 canonical hash长期排序。新增 query-plan assertion禁止 fingerprint SQL出现 `USE TEMP B-TREE`，并重跑 10k/retained-lots 性能证据。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 中

### S1-DR-05-未修复-中-full publication 对非 SQLite/旧 repository 静默退回无 head 写入，违反“每个 writer 都走 diff/head”完成条件
- **入口/函数**: 任一 writer facade -> `publish_full_position_projection()`。
- **文件(行号)**: `src/application/ledger/position_projection_publication.py:49-79`; `src/application/ledger/repository.py:80-87,4915-4922`。
- **输入场景**: repo wrapper/adapter 满足既有 `upsert_trade_event + replace_position_lots` Protocol，但未实现新 `apply_position_lot_diff` 或 `publish_full_position_projection_heads`；这也是当前 structural guard 允许的对象。
- **实际分支**: application 使用 `getattr` 探测两个新方法；缺少任一方法时继续调用 legacy `replace_position_lots`，返回成功且仅把 result metadata 标成 `repository_projection_metadata_unavailable`。
- **预期行为**: S1 writer publication boundary必须强制其新 contract；旧 writer可以通过直接 bypass留下 stale generation/head而 fail closed，但新 writer facade自身不得静默绕过 diff/head。SQLite 是当前 authoritative persistence owner，unsupported adapter应在写入前明确拒绝。
- **实际行为**: 新 writer返回业务成功但不建立/刷新 durable heads；而 Protocol/runtime guard仍宣称该 adapter满足 event-write接口。这把新契约降级成 optional duck-typing shim。

- **影响**: 替换实现、测试 adapter或未来 wrapper可无声失去 freshness metadata；调用方只消费既有 lot count时看不到降级，导致契约漂移和难以审计的半实现状态。
- **建议改法和验证点**: 为 publication定义明确 Protocol，要求 diff/head primitives；生产 writer入口在任何 DML前拒绝不支持的新 contract。若确需 legacy repository，保留独立、显式命名的 compatibility入口且不得被 S1 writer facades调用。新增 unsupported repo zero-write test和 facade inventory。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 中

### S1-DR-06-未修复-中-diff publication 改变了公共 lot 列表的排序语义
- **入口/函数**: 任何调用 `list_position_lots()` 的 read model、resolver、CLI 或 decision snapshot。
- **文件(行号)**: `src/application/ledger/repository.py:2091-2100`；base implementation `main:src/application/ledger/repository.py:996-1005`。
- **输入场景**: store 中有至少两条 lot，且某条发生合法变更后其 `updated_at_ms` 比其他行新，或现有 consumer依赖最近更新优先。
- **实际分支**: S1 将查询从 `ORDER BY updated_at_ms DESC, record_id DESC` 改成只按 `record_id DESC`，以适应 unchanged row不再刷新 timestamp。
- **预期行为**: S1 明确不改变 full-oracle public behavior；diff DML应停止无谓更新，但 read API既有排序契约仍应保持，除非单独迁移所有 consumer并冻结新契约。
- **实际行为**: 返回顺序从“最近更新优先”变成字典序 record id，可能改变使用 `[0]`、FIFO候选或未显式排序的下游选择。现有 suite大量调用 `list_position_lots()[0]`，只覆盖特定生成 id顺序，不能证明一般等价。
- **直接证据**: diff 是单行 SQL order change；base 与 current 查询可直接比较。接受 S1 stop condition 是“any full-oracle public behavior changes”。
- **影响**: public read ordering regression，可能使调用方选择错误 lot或改变展示/证据顺序；风险取决于未显式排序 consumer。
- **建议改法和验证点**: 恢复既有 `updated_at_ms DESC, record_id DESC`。若业务真正需要稳定 projection order，应在拥有该语义的 resolver/read model显式排序，不能通过 repository全局换序。增加差异化 timestamp fixture冻结 legacy order，并确认 unchanged diff不改 timestamp。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
