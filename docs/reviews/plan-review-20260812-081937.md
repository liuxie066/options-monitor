1. A stable calculation reason may be used directly as a Candidate Engine top-level reject reason.
2. `net_premium_non_positive` is the only currently proven opening-ready deterministic calculation rejection.
3. Existing unavailable/input-invalid decisions remain fail closed if the deterministic case is projected separately.
4. Contract-level sealed reject detail can replace a generic strategy-level reason without rewriting the snapshot.

## Special-lens conclusions

- **Goal-bound minimal design**: the two slices map directly to confirmed success signals and do not pull the DeepSeek provider failure or release/deploy into scope.
- **Architecture boundary**: Candidate Engine remains the reject vocabulary owner, sealed snapshot remains the fact source, and Daily Brief remains a projection. Finding PR-01 is required to preserve that boundary.
- **Best-practice / optimal solution**: a canonical top-level classification with the stable calculation code nested as detail is simpler and safer than expanding the public reject vocabulary.
- **Overengineering**: no new schema, storage layer, or classifier is justified. The explicit one-reason allowlist is proportional to the evidence.
- **Overcoupling**: the source/report slice split is appropriate. Finding PR-02 is required so unrelated user presentation changes do not become coupled to this work unit's commits or validation.

## Findings

### PR-01-未修复-高-计划把不在 Candidate Engine 契约中的计算代码当成顶层 reject reason
- **位置**: `Contracts and interface decisions / Candidate evidence projection`；Slice 1 exact changes
- **问题类型**: 契约缺失 / 不可直接实施 / 架构边界
- **当前写法**: 对 allowlist 中的 opening-ready 计算原因，“seal that stable reason as the decision's top-level reject reason”，即拟直接使用 `net_premium_non_positive`。
- **反例/失败场景**: `_calculation_decision_record()` 把 `net_premium_non_positive` 传给 `build_candidate_decision()`；`normalize_candidate_reject()` 在构建决策时立即拒绝该 reason，扫描不会产出计划声称的零候选事实。
- **为什么有问题**: Candidate Engine 已定义封闭的顶层 reject vocabulary；任意计算代码是详细诊断，不是已批准的公共分类。计划按当前文字无法生成通过域校验的代码。
- **直接证据**: `domain/domain/engine/candidate_engine.py` 的 `CANDIDATE_REJECT_REASONS` 包含 `policy_rejected`但不包含 `net_premium_non_positive`；`normalize_candidate_reject()` 对非集合 reason 抛出 `ValueError("unsupported candidate reject reason")`。
- **影响**: Slice 1 一实施就失败，或实施者为让计划工作而未经确认地扩展 Candidate Engine 公共 reason 契约，造成 schema/consumer 漂移。
- **建议改法和验证点**: 顶层使用现有 `REJECT_POLICY_REJECTED`，将 `net_premium_non_positive` 保留在 `metric_value.reason_code`；明确 allowlist 只选择顶层分类，不扩展 vocabulary。断言 decision 可通过 `validate_candidate_decision_payload()`、summary 计入 `policy_rejected_count`、且具体 reason 仍可审计。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### PR-02-未修复-高-计划没有定义重叠的用户在途改动如何不被带入 Gateflow 提交
- **位置**: Slice 2 allowed files/completion signal；Aggregate validation；Commits boundary 缺失
- **问题类型**: 范围漂移 / file ownership / 测试缺口 / review 不可验收
- **当前写法**: Slice 2 允许整个 `daily_decision_brief_renderer.py` 和其测试，只要求 diff 包含列出的文件；计划未记录用户已确认保留的四个 pre-existing modified files，也未规定 partial staging 和 clean committed-tree validation。
- **反例/失败场景**: 执行常规 `git add src/application/daily_decision_brief_renderer.py tests/test_daily_decision_brief_renderer.py` 会把用户的紧凑固定简报重构、事件文案、标题删减和容量提醒变更全部带入本 work unit。反之，只在当前 dirty tree 跑测试又可能让本 work unit 依赖不会进入 PR 的用户代码。
- **为什么有问题**: Goal Confirmation 不包括紧凑卡片全面重构，Gateflow 又要求 protected commit 只包含当前 gate 范围。用户刚确认“原样保留并在其基础上继续”，这解决了 ownership，没有将所有现有 hunks 纳入当前 goal。
- **直接证据**: `git diff` 显示四个 tracked files 已有 202 行未提交改动；其中 renderer/test 与 Slice 2 文件相同，而修改内容还包括 Goal 未确认的标题、事件、聚合和容量文案。
- **影响**: 误提交用户工作、goal drift、PR 范围不可审计，或测试在 dirty tree 通过但在真实 PR commit 上失败。
- **建议改法和验证点**: 在计划中记录四个 pre-existing files 和基线 diff hash；Slice 2 只允许新增的特定 hunks；用 interactive/patch staging 而非 whole-file staging；每次提交前审阅 `git diff --cached`；提交后从 HEAD 创建本地 clean clone 跑同样测试，确保 PR 不依赖未提交 hunks；最终确认用户 hunks 仍未被暂存、回退或提交。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高
