### AGG-CR-01-未修复-高-Agent 候选解释绕过 terminal manifest 并可采信未提交的 owner snapshot

- **入口/函数**: `candidate_filter_explain_tool()` / `candidate_rank_explain_tool()` -> opening snapshot loader
- **文件(行号)**: `src/application/agent_tools/candidate_filter_impl.py:47`; `src/application/agent_tools/candidate_rank_impl.py:41`; `src/application/candidate_snapshot_manifest.py:500`
- **输入场景**: 当前运行在写入 `opening_candidate_snapshot.json` 后、发布 `candidate_snapshot_manifest.v1.json` 前中断，随后 Agent 工具按显式 `run_id` 或 latest 查询过滤原因或排序。
- **实际分支**: 两个 Agent 工具直接调用 `load_opening_candidate_snapshot()` / `load_latest_opening_candidate_snapshot()`；owner snapshot 自身有效即被返回，不要求 terminal manifest、v2 status index 或 exact owner/scope coverage。
- **预期行为**: 所有当前运行候选消费者都应先通过 manifest-first bundle loader；缺失或无效 manifest 时整个 account-run 候选证据不可用，不得挽救部分 owner。
- **实际行为**: 未完成 account-run 可被 Agent 工具解释为已封存候选事实；latest 无 pointer 时还可能跳过较新的不完整运行并回退到较旧 snapshot，造成陈旧但看似当前的解释。
- **直接证据**: 已有 `load_candidate_snapshot_bundle()` 严格先验证 manifest，再绑定 status index 和 exact owner set；Agent 两处完全未调用该 gate，而批准计划 `plan.md:67-76` 明确禁止 partial-owner salvage。
- **影响**: 过滤原因、零候选结论和 sealed rank 可在运行尚未终态提交时被错误展示，破坏本 work unit 的核心终态权威保证。
- **建议改法和验证点**: 在 manifest owner 模块增加 fail-closed 的 latest bundle resolver；两个 Agent 工具只从 manifest-bound bundle 取 `opening` owner。新增显式 run 缺 manifest、latest 指向不完整运行、有效 manifest 三类回归。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### AGG-CR-02-未修复-高-Opening snapshot 允许拒绝候选越出本次 symbol/mode 扫描范围

- **入口/函数**: `seal_opening_candidate_snapshot()` -> `_snapshot_decisions()` -> `validate_opening_candidate_snapshot()`
- **文件(行号)**: `src/application/opening_candidate_snapshot.py:744`; `src/application/opening_candidate_snapshot.py:793`; `src/application/opening_candidate_snapshot.py:536`
- **输入场景**: status index/scan statuses 仅声明 `NVDA/put`，但 `candidate_evaluations[put]` 混入一个被拒绝的 `AAPL` Put 决策。
- **实际分支**: sealer 只验证 mode 是否被扫描，并把不在 `quote_bindings` 的 AAPL 记录写成 `quote_snapshot_id=None`；validator 只要求 contract scopes 与 decisions 自洽，没有要求每个完整 decision 的 `(symbol, mode)` 属于 strategy scopes。Accepted 行会被 manifest 的 candidate-count 投影间接拦截，但 rejected 行不会进入 ranked count，因而可以逃逸。
- **预期行为**: opening owner 内所有 accepted/rejected decision 都必须属于 v2 index 所声明的精确 symbol/mode scope；拒绝事实不能从另一个标的泄入当前运行。
- **实际行为**: 伪造或组装错误的跨标的拒绝原因可通过 owner 校验和 terminal manifest，并被 Agent、Research 或 Daily Brief 当成本次扫描事实。
- **直接证据**: `_snapshot_decisions()` 的 `expected_modes` 丢失 symbol 维度；`quote_bindings.get()` 对未知 symbol 静默返回 `None`；full-current validator 重建 strategy scopes 时没有对 decision symbol/mode 做 membership check。
- **影响**: 候选拒绝统计与“为什么被过滤”的解释可能污染标的边界，是错误事实而非仅格式问题。
- **建议改法和验证点**: sealer 和 full-current validator 都以 strategy status/scope 的 `(canonical symbol, mode)` 集合作为 allowlist，任何 decision 越界立即 fail closed；保留 pre-manifest minimal v1 只读兼容。新增 rejected cross-symbol sealer 和 tampered validator 回归。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### AGG-CR-03-未修复-中-Combo v2 validator 未验证顶层 candidate_owner 身份

- **入口/函数**: `validate_combo_yield_candidate_snapshot()`
- **文件(行号)**: `src/application/combo_yield_candidate_snapshot.py:420`; `src/application/combo_yield_candidate_snapshot.py:456`; `src/application/combo_yield_candidate_snapshot.py:552`
- **输入场景**: 有效 SP+LC snapshot 的顶层 `candidate_owner` 被改为 `cc_lp`，随后重新计算合法 content hash 并交给 loader/manifest gate。
- **实际分支**: sealer 固定写入 `sp_lc`，scope normalizer 也固定按 `sp_lc` 校验嵌套 scope，但 validator 从未核对顶层字段；重新哈希后自相矛盾的 owner 身份仍可通过。
- **预期行为**: Combo v2 的 schema、文件、顶层 owner 和嵌套 scope owner 必须共同绑定到 `sp_lc`，与 CC+LP v2 的 identity 校验对称。
- **实际行为**: snapshot 可同时声称顶层归属 `cc_lp`、内部 scopes 归属 `sp_lc`，而 loader 仍将文件当作 SP+LC authority。
- **直接证据**: payload 在 sealer 中包含 `candidate_owner: sp_lc`，但 validator 在 schema/run/account 后直接进入 hash、market、dependency 和 scope 校验，没有检查该字段。
- **影响**: owner identity contract 可被重新哈希的错误/篡改 payload 绕过，削弱 terminal manifest 的 owner 绑定与审计一致性。
- **建议改法和验证点**: validator 明确要求 `candidate_owner == sp_lc`，增加重算 content hash 后仍因 owner mismatch 被拒绝的回归。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
