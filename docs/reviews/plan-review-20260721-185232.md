## 2. Goal / non-goal / success-signal summary

计划目标是收敛 Tick 普通通知、System Notice 和 Receipt 的重复 Markdown renderer，同时保持 P0 transport identity、发送确认、幂等和业务决策不变。主要成功信号包括：scheduled sender 不再读取 Compact/Legacy Markdown、旧 renderer 配置 fail-closed、无候选进入 Daily Brief 状态、System/Receipt 只共享窄 presentation shell，以及 multi-market 不再静默成功跳过。

计划明确排除新 scheduler、successful current、delivery envelope、provider retry 重写、通用 DTO/registry/DSL 和生产配置/部署动作。该边界总体合理，但当前文本在 manual/force、旧配置迁移、公共 artifact read surfaces 和 multi-market 失败终态上没有保持一致。

## 4. Findings

### PR-01-未修复-高-manual/force 被无授权地并入普通通知 cutover，且与上位产品合同直接冲突
- **位置**: §1.1 目标 1；§1.2 非目标；Slice 1 第 1 项；§7.1 `manual/force` case
- **问题类型**: 范围漂移 / 契约缺失 / 过度耦合
- **当前写法**: 计划把 `scheduled、manual、force` 的普通 Tick 消息全部改为无条件经过 Daily Brief，并在测试中要求 manual/force “继续使用 Daily Brief renderer；仅 context label 不同；不在本 P1 改发送节奏”。
- **反例/失败场景**: operator 执行 manual 或 `--force` 扫描。按本 P1，当前自动普通通知副作用被保留，只是 renderer 改成 Daily Brief；按已经评审通过的通知体验计划，`trigger_kind != scheduled` 只能更新 successful current，不生成 fixed report、不自动发送普通候选通知，也不推进 alerted state。两套计划先后落地时，同一个 `tick_notification_flow.py` 会拥有相反合同，后实现者只能重新设计或覆盖前一 work unit。
- **为什么有问题**: 用户锁定的是 “Daily Brief 成为 scheduled notification 唯一主 renderer”，而不是为 manual/force 决定新的长期发送合同。P1 又把 scheduler/delivery 语义列为非目标，因此不能在 renderer consolidation 中顺带把 manual/force 自动发送固化为 acceptance criterion。这不是单纯 context label 差异，而是用户可见消息和后续 delivery-state 语义。
- **直接证据**:
  - P1 第 16 行把范围扩大到 scheduled/manual/force；第 568 行要求 manual/force 继续发送节奏。
  - 上位计划 `option-notification-experience-implementation-plan-20260721.md:280-290` 明确：非 scheduled 仍可更新 current，但不生成 fixed report、不自动发送普通新增候选通知；未来手工发送应使用显式、需确认的独立 operator 命令。
  - 当前 `multi_account_tick.py:90-94` 已明确区分 `scheduled`、`manual`、`force`，因此无需为了 renderer 收敛把三者视作同一产品事件。
- **影响**: 实施 Agent 会把未批准的 manual/force 行为写入主发送链；P1 与上位 work unit 无法安全叠加；可能出现手工扫描意外发送、重复通知或 alerted/delivery state 语义返工。
- **建议改法和验证点**:
  1. 把 P1 的 authority 成功信号限定为 **scheduled automatic ordinary notification**。
  2. 在 plan 中显式选择 non-scheduled 过渡合同：推荐 `trigger_kind != scheduled` 只生成/更新结构化结果，不自动 dispatch 普通消息；如确需手工发送，留给独立、需确认的 operator command。
  3. 删除“manual/force 继续当前发送节奏”的 acceptance；增加测试证明 manual/force 不进入 automatic ordinary delivery、不生成 fixed delivery identity、不推进普通通知状态。
  4. 若 CEO 决定 P1 现在就收紧 manual/force，则把它列为显式产品 scope，并同步修订/重审上位计划，而不是作为 renderer 内部实现细节。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR-02-未修复-高-旧配置 key 的同版本删除与严格拒绝缺少 version-skew 迁移，并使已批准回滚合同失效
- **位置**: §4.3 Legacy 删除 gate；§5.1 Runtime config；Slice 1；Slice 5；§9.1 Renderer rollback；§12 Gate Order
- **问题类型**: 状态机漏洞 / 最佳实践偏离 / 不可直接实施 / open question 未收敛
- **当前写法**: Slice 1 同时删除 defaults/examples 中的 `notifications.daily_brief.enabled`、让 Daily Brief 无条件 canonical，并让 validator 对 `daily_brief.enabled` 和 `notifications.render_style` 的任意出现立即报 migration error。生产 config 迁移、release 和部署则在后续分别授权；renderer 回退只允许 code/version rollback。
- **反例/失败场景**:
  1. 使用当前 committed example/default 生成、且仍包含 `daily_brief.enabled=false` 的旧用户配置先遇到新代码：配置在 tick 之前直接失败，所谓 “compatibility release” 对旧配置并不兼容。
  2. 若先清理配置、节点仍运行旧代码，当前 `_daily_brief_enabled()` 在 key 缺失时返回 false，旧节点会重新选择 Compact。
  3. 上位通知体验计划实施后发生紧急行为回退时，它要求使用 `notifications.daily_brief.enabled=false`；P1 新 validator 会拒绝该配置，两个已评审计划无法同时满足。
- **为什么有问题**: 计划把 code、committed defaults、generated/user config、生产 config 和 rollback 分成不同授权动作，却没有给出可验证的 mixed-version 顺序。仅在 gate 中说“发现旧 key 就停止”不能指导如何安全越过该 gate。更严重的是，上位计划仍把被删除的 key 当作最小行为回退权威，P1 没有声明 supersede、替代机制或必须先修订上位计划。
- **直接证据**:
  - 当前 `src/application/tick_notification_flow.py:581-585` 在 `enabled` 缺失或非 true 时返回 false；`run_tick_notification_flow()` 随后走 Compact/Legacy branch。
  - 当前 `src/application/config_defaults.py:128-134`、`configs/system.json:135-146`、`configs/examples/user.common.example.json:21-30` 都发布 `enabled=false`。
  - P1 第 331-337 行要求同一迁移中删除并严格拒绝旧 key，第 523-524 行把生产 config/release/deploy 留到后续授权，第 673 行取消 runtime renderer rollback。
  - 上位计划 `option-notification-experience-implementation-plan-20260721.md:197` 明确“不改变 daily_brief.enabled 默认值”，第 1053-1055 行明确用 `enabled=false` 做最小紧急行为回退。
  - 本次只读检查发现当前主工作区 `config.us.json` / `config.hk.json` 未显式包含这两个 key；这降低当前单一实例的即时迁移风险，但不能替代 repo 发布合同和其他旧配置的 version-skew 方案。
- **影响**: 升级可在配置加载阶段中断；旧/新节点或 code/config 不同步时 renderer 行为反转；紧急回退 runbook 失效；P1 和上位 work unit 需要高成本返工后才能集成。
- **建议改法和验证点**:
  1. 明确 P1 与 `option-notification-experience` 的实施顺序，并在 P1 release 前同步修订后者的 config/rollback 合同后重新 PlanReview。
  2. 采用两阶段迁移：Phase A 新代码让 Daily Brief canonical，但对旧 key 做 **显式 deprecated warning/audit 且不再赋予选择权**；完成 committed/generated/production config 清理后，Phase B 才严格拒绝旧 key。
  3. 如果坚持单阶段严格拒绝，必须提供原子 code+config rollout、失败回滚和旧节点行为证明；不能只写“分别请求授权”。
  4. 增加 version-skew matrix：old code+old config、new code+old config、old code+clean config、new code+clean config，并验证启动、renderer identity、rollback 和无双发。
  5. 在删除 `enabled=false` 行为回退前，定义并演练替代的 operator-controlled rollback，且不得通过恢复 Compact runtime switch 引入第二 authority。
- **修复风险（低/中/高）**: 高
- **严重程度（低/中/高/严重）**: 高

### PR-03-未修复-中-Compact artifact 仍以无标记的 canonical notification 暴露给公共 read surfaces
- **位置**: §3.1 兼容代码；§4.1；§5.3 `symbols_notification.txt`；Slice 2；§11 残余风险
- **问题类型**: 架构边界 / 契约缺失 / 测试缺口
- **当前写法**: Phase A/B 继续正常生成 Compact `symbols_notification.txt`，只通过文档把它定义为 compatibility artifact；reader inventory 和 artifact migration 被延期。Slice 2 只更新 `preview_notification` 的 warning/schema，没有把 `runtime_status` 等既有 readers 列入 write scope。
- **反例/失败场景**: scheduled 实际投递的是 Daily Brief，但 operator/agent 调用 `runtime_status` 时，返回的 `shared.notification`、每账户 `notification` 和 latest-run `notification` 仍包含 Compact 全文；系统还会在 Compact 文件缺失时发出 “No symbols_notification.txt found...” 健康警告。模型或人工排障会把这份不同于实际发送内容的 Compact 文本当作“本轮通知”，造成错误验收、错误客服解释或错误恢复判断。
- **为什么有问题**: Compatibility preview 可以保留，但必须在公共 read boundary 上明确标识 authority。当前计划只证明 Compact 不进入 sender，不能证明它不再是 operator/agent 看到的第二个 notification truth。把 reader inventory 延到未来 artifact retirement 超出了最低必要延期：本 P1 不必删除文件，但必须消除无标记的 canonical 命名和健康语义。
- **直接证据**:
  - P1 第 270、353-357、444 行继续生成并保留文件，仅靠文档重新定义；第 726-727 行把 reader/AccountResult 风险延期。
  - `src/application/agent_tools/runtime_status_impl.py:285-298` 会读取并返回文件全文。
  - 同文件 `1432-1436`、`1942-1946`、`2081-2085` 把该文件放在名为 `notification` 的字段下；`2135-2140` 把缺失当作 notification warning；`2257-2261` 继续公开 `shared.notification`。
  - `src/application/account_run.py:758-766` 仍将组合后的 Compact/legacy-compatible text 写入 run account `symbols_notification.txt`。
- **影响**: scheduled delivery authority 在代码中虽唯一，但公共可观测面仍有两个互相不一致的“通知”；验收和事故诊断可能读取错误 renderer；Compact retirement 会继续被 reader 耦合阻塞。
- **建议改法和验证点**:
  1. 在 P1 内盘点所有 `symbols_notification.txt` / `AccountResult.notification_text` readers，不要求删除文件，但要求公共输出显式标记 `renderer=compact`、`authority=compatibility_only`、`sent=false/unknown`。
  2. `runtime_status` 将字段改为明确的 compatibility artifact 名称，或保留旧字段但增加 deprecation metadata；canonical sent/prepared view 应读取 Daily Brief evidence，而不是 Compact 文件。
  3. canonical cutover 后，Compact artifact 缺失不得继续被当作普通通知健康失败；若仍需监控，应使用 compatibility-specific warning code。
  4. 增加 agent-tool contract tests：runtime status/diagnostics 不把 Compact 文本描述为实际 scheduled message；旧字段兼容期有明确 warning 和 removal gate。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 中

### PR-04-未修复-中-multi-market fail-closed 没有定义 tick idempotency 的失败终态和重试合同
- **位置**: §2.5；Slice 1 第 4 项；§7.1 multi-market case；§12 停止条件
- **问题类型**: 状态机漏洞 / 并发恢复风险 / 不可直接实施
- **当前写法**: 计划要求 multi-market 在 assembler/repository/provider 前报 `daily_brief_multi_market_delivery_unsupported`，不生成 revision、不推进 pointer/“完成态”，但没有指定异常/返回类型、tick idempotency record、run-end audit 或 retryability。
- **反例/失败场景**: 当前 tick 在 account pipeline 前已经 claim `tick_execution` 为 `in_progress`；multi-market 检查则发生在 account execution 后、notification preparation 开始时。若实现直接 `raise ValueError`，record 会保持 `in_progress`。同一常驻进程或 PID 仍存活的同分钟 retry 会被判定为 active duplicate；runtime status/audit 也无法区分“仍在运行”与“明确不支持而失败”。若实现调用现有 completion helper 写 `status=failed`，该 helper 又固定写 `ok=true`，会生成语义错误的成功 idempotency record。
- **为什么有问题**: “不推进完成态”不能替代明确失败状态。该路径是计划主动新增的 fail-closed contract，implementation agent 不应被迫临时设计 idempotency、return code 和 retry semantics。计划同时声称不改变幂等，这意味着必须说明如何复用或窄扩现有状态机。
- **直接证据**:
  - `src/application/multi_account_tick.py:284-306` 在 account execution 前 claim `tick_execution`，payload 为 `ok=false,status=in_progress,pid=<current>`。
  - `domain/storage/repositories/state_repo.py:315-375` 对非 stale、PID 仍活动的 non-success record 拒绝再次 claim。
  - `src/application/tick_run_context.py:51-76` 的现有 completion helper 无论传入何种 status 都写 `ok=true`。
  - P1 第 406、567 行只定义 no revision/pointer/provider/完成态，没有定义 failed record、返回码或 reclaim 行为。
- **影响**: unsupported multi-market run 可能留下误导性的 active claim，阻塞可恢复重试或让监控无法判定终态；不同 implementation agent 可能产生互不兼容的异常和审计行为。
- **建议改法和验证点**:
  1. 在 plan 中定义明确状态转换：`claimed -> unsupported_failed`，record 必须 `ok=false`、含稳定 error code、finished timestamp 和 run id；CLI 返回非零。
  2. 规定该失败是否可立即 retry；若可，扩展 claim 语义使 terminal failed record 可重新 claim，而不是依赖 PID 死亡或 15 分钟 stale timeout。
  3. 明确 runlog/audit/finalization 必须写入的 event，并保证 no provider/revision/current/delivered pointer mutation。
  4. 增加同进程 retry、下一进程 retry、同分钟 duplicate、失败 record runtime-status 的测试。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 中

## 5. Architecture boundary review

- **通过部分**：`notification_shells.py` 的两个 public helper 足够窄；System Notice/Receipt 的业务事实、rate limit、dedupe、retry、receipt persistence 和 provider confirmation 仍留在 caller。renderer 不感知 Feishu/WeChat，符合 transport boundary。
- **未通过部分**：scheduled authority 已从 sender boundary 收敛，但 public read boundary 仍把 Compact 命名为 canonical `notification`；P1 与上位 work unit 对 `tick_notification_flow.py`、config key 和 rollback 的 ownership 没有形成单一合同。
- **结论**：presentation shell 边界可接受；trigger/config/read-model 边界需修订后才能实施。

## 6. Best-practice review

- 正面：poisoned `notification_text`、no fallback、P0 identity、Legacy exit evidence、provider ambiguity 不跨 renderer 补发等测试方向正确。
- 缺口：breaking config removal 没有 version-skew matrix；新增 fail-closed 分支没有 terminal failure/retry state；公共兼容 surface 只有文档标签，没有 machine-readable authority metadata。
- 最佳实践要求：兼容期应可观测且无控制权；状态机失败必须有明确 terminal state；跨 work unit 的 public config/rollback contract 必须先排序和修订。

## 7. Optimal-solution review

- Shared shell + caller-owned facts 是当前最小且可维护的方案；没有理由改成 renderer registry、DTO 或模板 DSL。
- Daily Brief 作为 scheduled automatic notification 的唯一 renderer 也是正确主方向。
- 当前 config 方案不是最优路径：两阶段“接受旧 key 但显式废弃且无选择权 -> 清理配置 -> 后续严格拒绝”比同版本硬拒绝更安全，且不恢复第二 authority。
- manual/force 不应被 renderer consolidation 顺带决定；复用既有 `trigger_kind` 边界即可，无需新增抽象。

## 8. Overengineering review

- 未发现需要阻断的过度设计。
- 计划明确拒绝 registry、DSL、继承、通用 DTO 和 provider-specific business renderer，是正确的 ROI 选择。
- `notification_shells.py` 只含两个 public function 和最多一个 private flat helper，规模合理。
- 修复本 review findings 不需要新增框架：只需收窄 trigger contract、补 rollout/state transition、给兼容 read surfaces 加清晰 metadata。

## 9. Overcoupling review

- **主要问题**：P1 把 renderer consolidation 与 manual/force 产品语义、config hard removal、上位计划的 rollback 同时绑定在 Slice 1，迫使后续 scheduler/delivery work unit 重写相同边界。
- Compact 文件保留本身可接受，但 reader 名称/健康判断仍与 canonical notification 绑定，形成隐藏耦合。
- System/Receipt shell 没有把 caller state machine 耦合进 helper，属于通过项。

## 10. Open questions
