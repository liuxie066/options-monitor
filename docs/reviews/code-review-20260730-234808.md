### 1-未修复-高-成功空链证据失效后，blocked Brief 仍保留先前装配的主动持仓建议

- **入口/函数**: `assemble_daily_decision_brief()` -> Position Advice v2 持仓/行动装配 -> `_append_success_empty_strategy_gaps()`
- **文件(行号)**: `src/application/daily_decision_brief_service.py:366-399, 448-483, 607-632`
- **输入场景**: Position Advice v2 初始解析为 `available/fresh`，其中有一条 `recommendation=roll`、`actionable=true` 的持仓；同一 run 又存在 `success_empty` 策略状态，但被冻结的 required-data bytes 或 receipt hash 已损坏，导致后续 source-integrity 校验返回 `position_advice_source_integrity_invalid`。
- **实际分支**: 函数先把 v2 row 写入 `positions`，并把 `position_roll` 写入 `actions`；随后才校验 success-empty source graph 并把 `advice_authority` 改成 `authority_conflict`。该降级只设置 `close_available=False` 和 blocker，没有撤销已经装配的持仓与行动。最终 `_dedupe_actions()` 和返回 payload 仍使用旧列表。
- **预期行为**: 一旦 Position Advice authority 被判定为冲突，Brief 中不得继续发布由该 authority 产生的主动交易建议；blocked payload 应只包含数据阻断行动，或明确把原建议转换为不可行动的诊断信息。
- **实际行为**: 复现结果为 `status=blocked`、`actionability=blocked`、`normal_delivery_allowed=false`、`fixed_failure_delivery_allowed=true`，但 `positions` 仍包含 `recommendation=roll, actionable=true`，`actions` 同时包含 `resolve_data_blocker` 和 `position_roll`。
- **直接证据**: `src/application/daily_decision_brief_service.py:366-375` 在 source-integrity 复核前装配 v2 持仓和行动；`455-475` 只重写 `advice_authority`；`607-632` 原样归一化并返回既有 `actions/positions`。现有 `test_success_empty_frozen_source_corruption_uses_fixed_failure` 只断言 blocked/notification authority，没有放入可行动 v2 row，也没有断言持仓行动被清除。
- **影响**: Daily Brief 作为结构化决策事实会同时表达“权威无效、禁止正常投递”和“建议滚仓”。即使当前 fixed-failure renderer 不展示该行，其他结构化消费者、查询页或后续投影仍可能读取并展示失去 authority 的交易建议。
- **建议改法和验证点**: 将 success-empty adopted-source/manifest 校验前移到任何 Position Advice row 装配之前；或在 authority 降级时按来源精确删除已装配的 Position Advice `positions/actions`，并重新计算 summary。新增回归测试：v2 actionable row + success-empty frozen bytes 损坏时，结果只保留 blocker，不含 `position_roll`、不含 actionable position；同时覆盖 v1/v2_shadow 的 `human_review_rows`。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### 2-未修复-高-Quote receipt 和 frozen snapshot 接受带非空 rows 的 `provider_error`，破坏 fail-closed 契约

- **入口/函数**: `publish_required_data_quote_snapshot()` -> `_validate_complete_required_data_bundle()` -> required-data manifest seal/read
- **文件(行号)**: `src/application/opend_symbol_outputs.py:195-224`; `src/application/required_data_snapshot.py:488-550`
- **输入场景**: required-data JSON 为 `meta.status=ok`、`meta.source_outcome=provider_error`、`meta.reason_code=RATE_LIMIT`，同时包含至少一条 row；CSV 和路径均合法。
- **实际分支**: 发布边界只拒绝 `status != ok`、零行缺少 success-empty 证据，以及“非空 rows + success_empty”；因此 `provider_error`、`parse_error` 或未知 outcome 只要带非空 rows 就能产生合法 quote receipt。冻结 bundle validator 重复同一缺口，并在末尾直接返回任意非空 `source_outcome`。
- **预期行为**: 非空成功数据只能是 `success_rows`；`provider_error`、`parse_error` 和未知 outcome 在任何 row 数量下都不能发布或被 sealed snapshot 接受。部分成功但存在 provider error 也必须继续走既有失败路径。
- **实际行为**: 用公开 publisher 构造上述 payload 可得到 `accepted=True` 的 `quotes` receipt；该 receipt 随后具备进入 manifest ready 路径的条件。
- **直接证据**: `src/application/opend_symbol_outputs.py:211-224` 没有为非空 rows 建立 `source_outcome == success_rows` 白名单；`src/application/required_data_snapshot.py:546-550` 只排除 `success_empty` 后返回其余任意 outcome。当前新增测试只覆盖合法 success-empty 与零行缺证据，没有覆盖“非空 rows + provider/parse/unknown outcome”。
- **影响**: 新增的 typed evidence 仍可被自相矛盾的 producer payload 绕过。Position Advice 和 Daily Brief 可能把 provider 失败或解析失败期间的部分/异常 rows 当作已冻结、可授权的报价事实，直接违背本 work unit 的 provider-error fail-closed 边界。
- **建议改法和验证点**: 在 publisher 与 frozen bundle validator 同时执行精确状态机校验：非空 rows 必须为 `success_rows` 且不得带 success-empty reason；零行必须为受控 `success_empty`；`provider_error`、`parse_error`、`not_attempted` 和未知值一律拒绝。补充 publisher、seal、resolve 三层参数化回归测试，并覆盖 partial rows + provider error。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### 3-未修复-中-手工 deal-json 可以伪造被提升为顶层的“可信 Push 来源”审计字段

- **入口/函数**: `auto_intake.main()` 的 `--deal-json` 路径 -> `process_trade_payload()` -> `build_trade_intake_audit_event()`
- **文件(行号)**: `src/application/trades/auto_intake.py:428-477`; `src/application/trades/intake.py:361-389`
- **输入场景**: 操作者或 replay 文件提供普通 manual payload，并在其中加入自定义 `_trade_intake_source`，声明任意 `source_id/account/futu_account_id/opend_host/opend_port/received_at_utc`。
- **实际分支**: `--deal-json` 将原始 JSON 直接传给 `_process_payload(..., source="manual")`；审计 helper 只检查嵌套值是不是 dict，未检查事件来源必须是 push、schema/transport、source 配置绑定或与规范化 deal 的一致性，就把这些值提升为顶层审计字段。
- **预期行为**: 顶层 OpenD Push provenance 只能来自 `_bind_push_payload_to_source()` 已验证的内部上下文；manual、poll/backfill 或任意原始 payload 不得自行声明可信 source identity。
- **实际行为**: `received`/`enriched` 审计可以同时出现 `source=manual` 和伪造的 `account/source_id/opend_*`。后续 normalized 事件可能给出正确账户，但最初的“消息来自哪个 OpenD/账户”记录已经不再具备可信性。
- **直接证据**: `src/application/trades/auto_intake.py:440-477` 保留并处理 replay JSON；`src/application/trades/intake.py:374-389` 无条件信任 payload 内的保留键。新增测试仅验证合法 push 上下文被提升，没有验证 manual payload、错误 schema、错误 transport 或上下文与 normalized deal 冲突时必须忽略/拒绝。
- **影响**: 不会直接改变 ledger identity，但会污染用于事故追踪、账户过滤和来源归因的 durable audit；在重复成交或跨账户事件调查中，系统可能把手工 replay 错认成特定 OpenD Push。
- **建议改法和验证点**: 不从公共 raw payload 直接读取可信 provenance；优先把验证后的 source context 作为独立内部参数/值对象传给 intake/audit。若保留嵌套字段，至少仅在 `source=="push"` 且 schema、transport、source binding 和 normalized account 全部一致时提升，否则拒绝或只保留在原始 payload。新增 manual/backfill spoof、错误 schema、账户冲突回归测试。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
