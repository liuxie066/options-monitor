### CR-S3-001-已修复-高-历史 v1 full delivery key 会被当前 additive schema 摘要误拒绝
- **入口/函数**: `delivery-inspect` / `delivery-migrate` -> `_build_v2_state_from_legacy_pointer()`
- **文件(行号)**: `src/application/daily_decision_brief_repository.py:1525-1533`; `domain/domain/daily_decision_brief.py:187-195`
- **输入场景**: 线上存在由 Slice 2 以前代码确认的合法 v1 `delivery_kind=full` pointer；其 immutable revision 不含后来增加的 `funds` 和 `candidate_index` 字段。
- **实际分支**: 迁移把旧 revision 用当前 normalizer 补齐 additive fields，再调用当前 `_full_brief_semantic_digest()` 重算 full key，并要求与历史 pointer key完全相等。
- **预期行为**: 迁移应保留并结构化验证历史 delivery key，同时仅从 immutable revision 重算新的 `brief_digest`；不应要求历史 key 能被当前版本的可演进语义摘要重新生成。
- **实际行为**: 当前 normalizer 会增加 `funds` 和 `candidate_index`，改变 `_full_brief_semantic_digest()` 输入；合法历史 full pointer 因 key mismatch 被 fail closed，生产 v1 -> v2 迁移无法执行。
- **直接证据**: 当前 normalizer 明确把 `funds`/`candidate_index` 写入 normalized brief（`domain/domain/daily_decision_brief.py:187-195`），而 Slice 2 前 normalizer 没有这些字段；迁移在 `1526-1533` 使用当前 semantic digest 构造 expected key 并精确比较。
- **影响**: 已确认线上 pointer 无法迁移；用户要求的 lx/sy HK 最小迁移会在第一步 inspect/confirm 被阻断。
- **建议改法和验证点**: 对 legacy full key只验证不可漂移的结构：`daily-brief:<market>:<date>:<account>:full:<64hex>`，保留原 key；继续从 immutable revision 重算 v2 `brief_digest`。增加一个模拟 pre-Slice-2 revision/key 的回归测试，证明 additive default/derived fields 不会阻断迁移。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### CR-S3-002-已修复-中-跨交易日新增候选审计沿用了上一交易日基线
- **入口/函数**: `persist_daily_decision_brief_success()`
- **文件(行号)**: `src/application/daily_decision_brief_repository.py:65-75,135-145`
- **输入场景**: current 指向前一市场交易日，下一交易日首个成功 brief 包含同一个候选身份。
- **实际分支**: 函数把任意日期的可靠 current 都赋给 `previous`，随后用 `current_ids - previous_ids` 计算 `newly_detected_candidate_identities`。
- **预期行为**: 新市场交易日以空集合为检测审计基线；首个成功扫描中的当前身份都应记为 newly detected，delivery day 的 pending/alerted 也按新日隔离。
- **实际行为**: 与前一日相同的身份不在 `newly_detected_candidate_identities` 中；repository 返回的检测审计与计划定义的新日空基线不一致。
- **直接证据**: `previous` 的赋值不比较 `market_trading_date`（`65-75`），差集直接使用该 previous（`135-145`）。
- **影响**: 当前 pending 计算仍可由日隔离 delivery state 恢复，因此不一定漏发，但审计/指标和后续调用方若使用 `newly_detected` 会得到错误结果。
- **建议改法和验证点**: 保留 `previous_successful_brief` 供审计，但仅在 previous 与 current 同一市场交易日时使用其 candidate identities；增加跨日同身份测试，断言新日 `newly_detected` 包含全部当前身份。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中


### CR-S3-003-已修复-中-候选已从 pending 消失后 retry reader 仍会返回旧 envelope
- **入口/函数**: `record_daily_decision_brief_candidates()` -> `read_retryable_daily_decision_brief_delivery()`
- **文件(行号)**: `src/application/daily_decision_brief_repository.py:151-161,430-444`
- **输入场景**: 13:30 准备 candidate envelope 但未确认；14:00 成功扫描显示这些身份已不再有效，因此 pending 集合被清空；14:10 是 no-scan delivery-only tick。
- **实际分支**: candidate envelope 保留为 `status=pending`，retry reader 不检查其 identities 是否仍在当日 `pending_candidates`，直接返回旧 exact message。
- **预期行为**: `pending_candidates` 表示“仍当前有效且未送达”；已消失身份不应由普通 pending retry 发出。ambiguous envelope 仍冻结并交由原 key 核验，但 definite-pending envelope 应等下一 scheduled scan 按当前 pending 重新准备或静默。
- **实际行为**: 14:10 可发送已经由 14:00 成功快照判定失效的候选消息。
- **直接证据**: candidate pending 会由每次成功快照整体替换（`151-161`），但 retry selection 只检查 envelope status（`430-444`），没有与 day pending 集合核对。
- **影响**: 用户收到过期普通候选，违背“仍当前有效”与非高频监控的可读/可信要求。
- **建议改法和验证点**: candidate prepare 必须要求 identities 是当日 pending 子集；pending candidate retry 仅在 envelope identity set 仍全部处于 pending 时返回。ambiguous 分支保持原 envelope 优先不变。增加“后续成功扫描清空 pending 后 no-scan 不重试旧 candidate envelope”测试。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中


### CR-S3-004-已修复-高-candidate envelope 可在相同 delivery key 下静默换 payload
- **入口/函数**: `prepare_daily_decision_brief_delivery()` -> `_resolve_prepared_envelope()`
- **文件(行号)**: `src/application/daily_decision_brief_repository.py:397-405,1470-1493`
- **输入场景**: 一个 pending candidate envelope 已按身份集合 A 生成 stable key；后续 scheduled scan 仍是集合 A，但 revision/rendered message 变化，或集合变为 B 生成新 key。
- **实际分支**: candidate 分支无条件传 `allow_pending_upgrade=True`；pending 且 content 不同时会用新 candidate 覆盖旧 envelope，并总是继承旧 `first_prepared_at_utc`/`last_attempt_at_utc`。
- **预期行为**: 同一 candidate key 必须绑定同一个 exact payload；只有 pending 身份集合变化导致 key 变化时才可旋转 envelope，并应以新 key 的准备/尝试时间重新开始。ambiguous 仍冻结。
- **实际行为**: 集合未变时，同一个 provider idempotency key 可对应不同消息；集合变化时，新 key 带着旧 key 的尝试时间，审计无法区分哪个 payload 被尝试。
- **直接证据**: candidate call site 对所有 pending content change 开启 replacement；resolver 不比较 old/new key，并无条件复制时间字段。
- **影响**: provider 幂等语义与 durable audit 不一致；重试可能被 provider 当作旧消息吸收，或 operator 无法判断实际尝试的是哪个 payload。
- **建议改法和验证点**: candidate replacement 仅允许 old/new delivery key 不同；新 key 不继承旧时间。fixed failure -> fixed report 是同 scheduled target 的显式特例，可保留原 target 的首次准备/尝试元数据。增加 same-key changed-message fail-closed 与 rotated-key fresh timestamp 测试。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高
