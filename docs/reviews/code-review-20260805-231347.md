## Findings

### DR-01-未修复-高-多请求校验仍用聚合行判定单个子请求作用域，完整空子请求和同方向分窗口会被误拒
- **入口/函数**: `validate_required_data_payload_candidate()` -> `_validate_required_data_payload_candidate()` -> `required_data_frame_covers_fetch_plan_debug()`
- **文件(行号)**: `src/application/required_data_coverage.py:487-527`; `src/application/opend_symbol_outputs.py:212-225`
- **输入场景**: 同一 symbol 的 multi-request plan 中，一个 child 对某 side/expiration 提供了可验证的空代码集，但另一 child 对同 side/expiration 有行；或者一个 side 的所有 scope 均为空，但其他 child/side 仍有行。
- **实际分支**: evaluator 先对整个 aggregate DataFrame 执行 `_filter_option_type(df, option_type)`，并按 expiration 取出所有 child 的聚合行；它没有先用当前 `(request_index, option_type, expiration)` 的 `proven_codes` 限定行。因此空 proof 会看到其他 child 的行并在 `row_codes != proven_codes` 失败；整个 side 空时还会在进入 scope 循环前被 `side_df.empty` 直接拒绝。
- **预期行为**: v2 的 completion unit 是 `request_option_type_expiration`；每个 scope 应只用自己 proof 绑定的 code set 选行。当该 code set 为空、chain status 为 `cache`/`fetched`、且没有 exact held strike 时，应接受该 scope；只有整个 plan 所有 scope 都空时才 fail-closed。
- **实际行为**: 符合新契约的 partial-empty multi-request payload 仍会被判为 `required-data payload does not cover expected fetch contract`，导致重新拉取或抑制正常 Daily Brief。
- **直接证据**: `side_df` 在 request 维度之前从 aggregate `df` 计算（line 487）；`side_df.empty` 在 proof 取值前即返回 false（lines 488-489）；`exp_df` 同样从 aggregate side rows 计算（lines 503-505），随后要求其全部 code 与当前 child scope proof 相等（lines 524-527）。现有新测试只覆盖单 request 内某个 expiration 为空，未覆盖 empty child/side 或同 side/expiration 多 child。
- **影响**: 本改动声明支持的 multi-request 部分空语义并未完整实现；FUTU 类多 child 计划仍可因可靠空 scope 被阻断，直接延续本次消息失败的核心故障模式。
- **建议改法和验证点**: 当 `scope_evidence` 存在时，先用当前 `proven_codes` 从 aggregate frame 中精确选取该 request scope 的行，再做 side/expiration/DTE/strike/exact-strike 校验；仅 legacy strict path 按 aggregate side/expiration 选行。新增回归：(1) 一个 empty child + 另一个 non-empty child 通过；(2) 同 side/expiration 的两个分离 strike-window child 通过；(3) proof code 的 side/expiration/window 篡改仍失败；(4) 所有 child 全空仍失败。
