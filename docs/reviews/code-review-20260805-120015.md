## Findings

### DR7-01-未修复-高-active case 的 compact query 仍按该 case 全量 evidence 计数

- **入口/函数**: `reconcile_due_lifecycle_cases_for_source()` -> `list_trade_lifecycle_due_candidates()` -> `case_scope_fingerprint()`
- **文件(行号)**: `src/application/trades/lifecycle_runtime.py:432-440`; `src/application/ledger/repository.py:1051-1125`; `src/application/trades/settlement_attempts.py:349-392`; `tests/test_settlement_observation.py:1864-2115`
- **输入场景**: 一个仍处于 active/non-absorbing 状态的 lifecycle case 长期累积大量 evidence；当前 fingerprint 和 control classification 均未变化，listener 仍按分钟运行。
- **实际分支**: compact SQL 对每个 active case 执行相关子查询 `SELECT COUNT(*) FROM trade_lifecycle_evidence WHERE case_id = ...`。即使使用 case 索引，SQLite 仍须遍历该 case 的全部 evidence index entries 才能得到精确计数；runtime 单 tick在 plan/provider/post-write路径还可能多次执行该 compact query。
- **预期行为**: idle cache-invalidation token 应通过每次 evidence mutation 时 O(1) 更新的 per-case monotonic revision 取得；tick 读取只能做有界索引查找，不应重新计算历史总量。
- **实际行为**: DR6 已把终态 case 排除并把 account snapshot 只索引一次，但只要一个 active case 的 evidence 历史继续增长，普通 idle tick 的 SQL CPU 仍随历史量线性增长。现有 2,100-row资源测试只计 account materialization/provider调用，没有约束相关 `COUNT(*)` 的 SQLite 工作量，因此会漏过该问题。
- **直接证据**: repository 1069-1073 行是逐 case 的相关精确计数；fingerprint 387 行直接依赖该值；现有 latest-evidence子查询已经通过 `(case_id, created_at_ms, rowid)` 顺序取一条，但 count无法 LIMIT。计划 74 行还把“从 covering index读取 count”误当成有界操作。
- **影响**: 本迭代仍不能保证 `trade-intake` 的每分钟空闲成本只随当前工作量增长；该问题与 cash flow capability 是否存在无关，长期 active case 可以再次推高持续 CPU并拖慢飞书响应。
- **建议改法和验证点**: 在 lifecycle evidence 的持久化 owner 增加 per-case monotonic revision，由 INSERT、case_id变更和DELETE触发器原子递增；compact query以主键 join读取 revision，fingerprint升级版本并改用 revision，保留 latest tuple作诊断。无需回填精确历史计数：既有 case从0开始，任一后续 mutation都会改变 token。新增迁移/触发器回归覆盖新插入、旧时间戳插入、case重新绑定和删除，并用 query-plan/resource断言证明 idle query不再包含 evidence count scan。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### DR7-02-未修复-中-control DB 每个 tick 两次扫描 source 的历史 attempt rows

- **入口/函数**: `reconcile_due_lifecycle_cases_for_source()` -> `list_settlement_attempt_states()` / `settlement_attempt_summary()`
- **文件(行号)**: `src/application/trades/lifecycle_runtime.py:432-447,1247-1253`; `src/application/trades/inbox.py:366-392,662-693,835-866`; `docs/plans/trade-intake-settlement-collector-resilience-plan-20260805.md:137-174`
- **输入场景**: source长期处理 lifecycle cases；完成、冲突或superseded case已从 ledger due candidates消失，但其一行 overwrite-in-place attempt state仍保留在 inbox SQLite中。
- **实际分支**: tick开始的 state listing按 `(source_id, account)`取出全部历史控制行；tick末尾 summary只按 `source_id`再次取出全部历史行，再在Python中过滤、计数和找最新状态。schema没有终态清理或active-scope marker，两个读取都会随历史 case数持续增长，summary还会把已终态 case的旧 blocked/backoff状态计入当前运行状态。
- **预期行为**: control row可以保留作崩溃恢复/诊断，但调度读取和当前 summary只能按本 tick 的 compact candidate IDs做主键范围内的有界查询；没有 candidate时不应反序列化任何历史控制行。
- **实际行为**: ledger侧终态过滤越有效，control侧留下的历史 rows 与当前 active work偏差越大；idle CPU、内存分配和可观测计数仍由累计历史决定。当前测试只验证单个 cached blocked row，未放入大量stale terminal control rows。
- **直接证据**: `list_settlement_attempt_states()` 的谓词没有 case_id；`settlement_attempt_summary()` 的谓词甚至没有 account或case_id；attempt table主键虽然包含 `(source_id, account, case_id)`，运行时没有用 candidate IDs命中它。
- **影响**: 服务运行越久，source-local cache本身会成为另一条与cash flow无关的常驻扫描路径；summary也可能向运维错误报告已经不再active的 blocked/backoff case。
- **建议改法和验证点**: 为 listing和summary增加显式 account + candidate ID scope，使用有上限的分批主键查询；runtime传入首次 compact candidate集合，使单 tick成本受active集合约束，同时继续保留历史rows。新增大量历史控制行 + 少量active IDs回归，证明listing只返回active rows、summary不计stale rows、无candidate返回零值，且查询计划使用复合主键。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 中
