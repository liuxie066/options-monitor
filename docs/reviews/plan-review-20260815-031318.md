# Plan Review — Sell Put Top1 HK Terminal Fee Contract

- Reviewed target: `docs/gateflow/sell-put-top1-hk-terminal-fee-contract/plan.md`
- Work unit: `sell-put-top1-hk-terminal-fee-contract`
- Branch/base: `feat/sell-put-top1-hk-terminal-fee-contract` / `origin/main@8528de6b`
- Scope: versioned HK terminal-fee calculator, assigned-stock lifecycle and portfolio assignment consumers, tests, and W0 evidence boundary
- Excluded: implementation correctness review, provider calls, real account receipt, W1B and later modules
- Conclusion: `fail`

## Assumptions tested

- A plain `account_fee_plan` mapping is sufficient input for current production projections.
- Strict validation at the new calculator boundary prevents lossy numeric coercion end to end.
- The proposed `dict` result is sufficiently specified for two current consumers and later W1B economics.
- The slice remains minimal and does not need a provider, persisted receipt, registry, or new configuration.

## Required review lenses

- Architecture boundary: fee arithmetic correctly stays in `domain/domain/fee_calc.py`, but fee-plan evidence ownership is not defined.
- Best practice: missing inputs fail closed, but the planned trust boundary and result schema are not yet safe enough for a money path.
- Optimal solution: the pure calculator plus two narrow consumer corrections is the smallest credible shape; a registry/provider layer would be unnecessary here.
- Overengineering: no speculative framework is proposed.
- Overcoupling: passing an unvalidated plan mapping through current event/position payloads couples projection completeness to data with no owning receipt contract.

## Findings

### PR-HKF-01-未修复-高-任意事件或持仓字典可以冒充账户费率事实并解锁净收益
- **位置**: `Public source contract`、`Consumer behavior`、`Non-goals`
- **问题类型**: 架构边界 / 契约缺失 / 最佳实践偏离
- **当前写法**: plan 只要求 `commission_free/platform_fee/fee_plan_ref` 三个字段；同时要求 assigned-stock 和 portfolio consumer 从现有 payload 传入该 mapping，并在完整时产出 estimated fee/net outputs；又明确本 work unit 不实现真实 receipt owner。
- **反例/失败场景**: 手工 event、旧 artifact 或调用方在普通字典里加入 `fee_plan_ref="x"`、`commission_free=true`、`platform_fee=0`。计算器无法区分它与已验证的账户套餐，consumer 会把 lifecycle/scenario 从 missing 变成 complete 并输出净收益。
- **为什么有问题**: `fee_plan_ref` 只是任意字符串，不是 receipt。当前仓库除本草稿外没有 `account_fee_plan` 的 intake、validator 或 authority；plan 自己也承认真实 `lx` receipt 缺失。让无 owner 的字段改变 money-path completeness 与“runtime remains no-go”边界冲突。
- **直接证据**: `rg account_fee_plan` 仅命中本草稿的 calculator、两个 consumer 和测试；`assigned_stock.py` 计划从 `raw_payload` 直接取值，`portfolio_assignment_scenario.py` 从 option mapping 直接取值。preflight 明确 `lx` 套餐仍为 red/unknown。
- **影响**: 非权威输入可产生看似完整的净 PnL/资金效率，审计无法证明使用的套餐事实来自哪里。
- **建议改法和验证点**: 本 slice 保留纯 calculator 对显式 plan binding 的支持，但当前两个 production consumers 在没有既有验证 receipt owner 时不得接受普通 payload 中的 plan mapping；它们应继续 fail closed，actual broker fee 仍可优先。把 validated plan receipt/intake 明确留给独立 W0R work unit。删除 consumer “任意 mapping 解锁 complete”测试，增加测试证明注入普通 `account_fee_plan` 仍不能解锁 net outputs。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### PR-HKF-02-未修复-高-消费者在调用严格计算器前已经把小数和布尔值截断成整数
- **位置**: `Public source contract`、`Consumer behavior`、`Validation`
- **问题类型**: 契约缺失 / 测试缺口 / 不可直接实施
- **当前写法**: plan 要求 calculator 拒绝布尔、小数、非有限值和截断，但没有规定 consumer 必须把原始数值交给该边界或使用同一严格解析。
- **反例/失败场景**: assignment payload 给出 `shares=100.9` 或 `contracts=1.5`。`_stock_event_shares()` 与草稿 `_stock_event_contracts()` 都执行 `int(abs(float(raw)))`，先变成 `100`/`1`；calculator 随后看到合法整数并产出费用。`True` 同样可变成 `1`。
- **为什么有问题**: calculator 的局部校验无法恢复已丢失的原始输入，因而 plan 的成功信号“不能静默截断”在真实 consumer path 不成立。
- **直接证据**: `domain/domain/assigned_stock.py::_stock_event_shares()` 和草稿 `_stock_event_contracts()` 使用上述 lossy coercion；portfolio `_integer()` 已经采用 Decimal integral check，两个 consumer 行为不一致。
- **影响**: 无效的券商/事件数据可能产生可接受但错误的费用，且测试只覆盖直接调用 calculator 时无法发现。
- **建议改法和验证点**: 计划明确 assigned-stock fee path 必须在 coercion 前保留并严格验证 raw shares/contracts；不要为此改变无关 stock-sale/lifecycle 解析。新增 consumer-level fractional/bool regression，断言 fee missing、net outputs suppressed。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### PR-HKF-03-未修复-中-版本化返回合同没有冻结必需键和金额分项不变量
- **位置**: `Public source contract`
- **问题类型**: 契约缺失 / 不可直接实施
- **当前写法**: plan 说明若干字段语义，但公开签名只有 `-> dict`；没有定义三个状态都必须出现的键、`components` 是否包含 option leg，或 `amount/estimated_amount` 与分项的求和关系。
- **反例/失败场景**: expired-worthless 省略 `fee_plan_ref`，assignment 把 `option_leg_fee` 放在 `components` 外，后续 W1B 或第二个 consumer各自猜测字段存在性/求和方式；同一 `schedule_version` 下形成多个兼容性不同的 payload。
- **为什么有问题**: 此 work unit 的目标就是“锁定版本化费用合同”。未冻结最小 schema 和不变量，实施完成后 W1B 仍需重新设计合同，无法形成稳定前置。
- **直接证据**: 草稿返回结构在分支之间通过多次 `dict.update()` 组装，expired-worthless 与 assignment/exercise 的 key set 不同；两个 consumer 使用 `get()` 规避缺键而非验证合同。
- **影响**: 后续 economics 可能误算或被迫增加兼容层；v1 版本无法可靠重放。
- **建议改法和验证点**: 在 plan 中冻结一个最小、所有状态共有的 exact key set，并写明 HKD 单位、stock components 与 separate option-leg 的求和不变量；测试三个 kind 的 exact keys、amount invariants 和 missing-state `amount=None`。不需要新增 dataclass 或 schema framework。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

## Open Questions

None. All three findings can be resolved within the existing file boundary without adding a provider or persistence layer.

## Residual risks

- Futu fee schedule drift remains external; track by requiring a new schedule version and evidence when formulas change.
- Per-order aggregation and tiered platform pricing remain outside this single-position calculator; W1B must bind an already resolved per-outcome plan fact and must not infer account readiness.
- A real `lx` receipt and verified intake remain W0R work, not this plan.

## Final conclusion

`fail`. The architecture shape is minimal, but the plan must close the fee-plan trust boundary, preserve strict validation through consumers, and freeze the v1 output contract before implementation is safe.
