## Findings

### DR15-01-未修复-高-leader claim 在首 case 完成后释放，重叠 worker 仍可为后续 case 重建全量快照

- **入口/函数**: `reconcile_due_lifecycle_cases_for_source()` -> shared provider preparation -> per-case provider loop -> `complete_claim()`
- **文件(行号)**: `src/application/trades/lifecycle_runtime.py:959-1137,1139-1259,1611-1641`; `src/application/trades/inbox.py:594-637`; `docs/plans/trade-intake-settlement-collector-resilience-plan-20260805.md:76-82,379-389`
- **输入场景**: 同一 source/account 有两个 eligible provider case。worker A 取得第一个 case 的 leader claim并完成一次共享账户快照；当 A 完成第一个 case、尚未进入第二个 case 的 JIT claim 时，worker B 开始或恢复一个 tick。
- **实际分支**: DR14 guard 在共享 preparation 后停止并把 lease 时间交给首 case。首 case 在循环尾调用 `complete_claim()`，该函数通过 `complete_settlement_attempt()` 清除 `claim_id/claim_until_ms`。随后 A 才进入下一次循环并 claim 第二个 case。B 如果落在这段窗口内，会看到没有 active claim、把第二个 case 选为自己的 leader、成功 claim，并再次执行 `lifecycle_case_read_models_for_account()`。A 随后的第二 case claim失败并跳过，但重复账户历史物化已经发生。
- **预期行为**: source/account 的 provider-batch leader ownership 必须从共享快照构建前持续到本批所有 eligible case 完成或被安全跳过；per-case attempt completion 可以即时持久化，但不应同时释放批次级互斥。任何重叠 worker 在整批结束前都应做零 account-wide materialization。
- **实际行为**: 两 case/两 worker 可构建两份全量账户快照；推广到多个等待 worker 和多个 case，最坏仍接近 `O(worker_or_case_count × account_history)`。DR14 新增测试只覆盖“快照开始前已有 leader”及“首 claim 同时竞争”，没有覆盖 leader case completion 与下一 case claim之间的 handoff。
- **直接证据**: shared preparation 仅由首 case claim保护（`lifecycle_runtime.py:959-1137`）；逐 case 循环每轮独立 claim（`1139-1259`）；首 case 在 `1611-1641` 完成并释放 ownership 后才进入下一轮。`complete_settlement_attempt()` 明确把 `claim_id` 和 `claim_until_ms` 设为 `None`（`inbox.py:629-637`）。不存在独立的 `(source_id, account)` provider-batch lease。
- **影响**: 多 case 与重启/命令重叠时仍会重复解析膨胀的 lifecycle history，持续占用 CPU 并拖慢同进程飞书响应；这仍属于原故障类，且违反资源验收中“provider path builds the full account-history index exactly once”的上界。
- **建议改法和验证点**: 在 source-local inbox DB 增加独立、overwrite-in-place 的 `(source_id, account)` provider-batch lease，原子 claim/renew/release并校验 owner。local-only planning完成后、任何 provider account read之前取得；用单个 monotonic guard覆盖共享 preparation和整个 per-case loop，并在统一 `finally` 中停止与 owner-checked release。保留现有 per-case JIT claim和即时 completion，不把批次锁语义塞进业务 case状态。新增确定性回归：在 worker A 完成 leader case的 control row后同步启动 worker B，证明 B 的 account read/provider call均为零而 A仍处理第二 case；另测 batch guard慢调用续租、owner crash后 lease expiry可接管、release ownership loss不删除新 owner。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高
