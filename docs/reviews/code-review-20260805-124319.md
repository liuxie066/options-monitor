## Findings

### DR10-01-未修复-高-重复语义在业务状态缺失时仍被当作成功，可能永久压住应有的生命周期迁移

- **入口/函数**: `_prepare_settlement_admission()` -> `apply_lifecycle_allocation_atomically()` / `record_lifecycle_evidence_issue_atomically()`
- **文件(行号)**: `src/application/ledger/writer.py:188-246,1191-1228,2317-2352`; `tests/test_settlement_observation.py:2382-2426`
- **输入场景**: 升级前写入、人工恢复或版本错配留下最新的可解析 settlement evidence，但对应 case 仍停留在 `waiting_settlement_evidence`，或缺少该证据应产生的 allocation/status/reason state；新版本收到语义完全相同、且基于当前 generation token 的观测。
- **实际分支**: admission head 会从最新 evidence 自动补种；fingerprint 相同后两个 writer 都在任何 evidence/allocation/status/state-fingerprint 一致性校验之前直接返回 `duplicate_semantic`。现有 legacy bootstrap 测试正是只插 evidence、不推进 case，却把该返回视为成功。
- **预期行为**: 重复语义不得重放业务写入，但必须执行只读、幂等的 branch-specific state-coherence check；只有 canonical evidence 与当前业务状态一致时才返回 `duplicate_semantic`，否则应 fail closed 并给出可诊断错误，避免把缺失迁移当成已完成。
- **实际行为**: runtime 会把这次 provider observation 作为已处理结果并更新 control backoff，而 canonical lifecycle transition 仍缺失；后续相同观测继续被 admission head 抑制，形成静默的业务状态缺口。
- **直接证据**: `_prepare_settlement_admission()` 的 duplicate 返回只携带 head/evidence identity；allocation writer 与 issue writer 的 duplicate 分支立即组装结果并返回，没有读取 canonical evidence 绑定、allocation、case status、reason codes 或 state fingerprint。计划第 242 行明确要求 duplicate 只做 state-coherence check。
- **影响**: 恢复、升级和版本错配路径可能丢失 terminal allocation 或 review/conflict 状态，且表面指标显示 `duplicate_semantic` 而不是故障；这是生命周期账本完整性风险。
- **建议改法和验证点**: 在同一事务内为 issue 与 terminal 分支分别增加只读 coherence validator。校验 canonical evidence 仍存在并绑定本 case；issue 校验 status、reason codes 与 conflict evidence 绑定；terminal 校验 evidence allocations、terminal events、投影数量、derived status/summary/state fingerprint 与当前状态一致。任何缺口返回 typed fail-closed error，绝不补写。新增 legacy evidence-only、缺 allocation、错误 status/reason、健康 duplicate，以及 A->B->A 合法演进回归测试。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### DR10-02-未修复-中-writer 接受与指纹矛盾的冻结 semantic_projection

- **入口/函数**: `settlement_semantic_from_evidence()` -> `_prepare_settlement_admission()`
- **文件(行号)**: `src/application/ledger/lifecycle_settlement_semantics.py:261-285`; `src/application/ledger/writer.py:154-186`
- **输入场景**: adapter 回归、手工构造或跨版本 payload 提供正确的 observation 与 `semantic_fingerprint`，但顶层 `semantic_projection` 被篡改、过期或属于另一观测。
- **实际分支**: writer 从 observation 重算 semantic 和 fingerprint，只比较 `semantic_schema` 与 `semantic_fingerprint`；它从不比较传入的 `semantic_projection`。payload 随后原样持久化，因此一个 evidence row 可同时保存正确指纹和相互矛盾的冻结投影。
- **预期行为**: 对带当前 semantic metadata 的新输入，writer 应要求 schema、fingerprint 与 frozen semantic projection 三者都等于从 observation 重算的 canonical 值；只有真正缺 metadata 的 legacy row 才走兼容投影路径。
- **实际行为**: 业务去重仍按重算指纹运行，但审计 envelope 的冻结语义可以失真，违反计划中“recompute/validate incoming semantic projection and fingerprint”的 contract。
- **直接证据**: `settlement_semantic_from_evidence()` 读取 `observation`、`semantic_schema`、`semantic_fingerprint` 后直接返回；函数没有读取或比较 `semantic_projection`。当前 semantic 单测也没有 mismatch/fail-closed 用例。
- **影响**: 审计、故障分析及未来基于 frozen projection 的迁移/读取会看到与实际 admission identity 不一致的事实；这会削弱 evidence contract 的可证明性，但当前业务去重仍由重算 fingerprint 保护。
- **建议改法和验证点**: 当前-schema payload 必须包含 canonical `semantic_projection`，并用 canonical structural equality 与重算 semantic 比较；缺失或不一致均抛出 `SettlementSemanticUnavailable`。保留 legacy evidence 无 metadata 的兼容行为。补充 projection 缺失、字段篡改、仅 key/order 表示差异、健康 current payload 与 legacy payload 测试，并覆盖 issue/terminal writer rollback。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
