# Option Performance 全量重构计划对抗性审查

- **Review 时间**: 2026-07-17 22:19:08（本机时钟）
- **Reviewed target**: 当前会话中形成的“期权收益/表现统计彻底重构方案”摘要；仓库中未发现对应的独立 plan 文件，因此本审查以会话方案为计划真源。
- **Review scope**: PeriodSpec、经济事实投影、统一 PnL、费用、历史估值与 FX、assignment/exercise 生命周期、capital/return、Agent/CLI/analysis 公共契约、portfolio bridge、迁移与测试。
- **未执行事项**: 未实施方案、未修改运行配置、未写入交易/持仓/券商/Feishu 数据。

## 1. 计划目标重建

计划希望把当前分散在 `positions/reporting.py`、ledger lot projection、close advice、assigned-stock lifecycle、analysis views 和 portfolio bridge 中的收益口径，重建为：

```text
canonical facts
  -> Economic Fact Projection
  -> Period Performance Engine
  -> Agent / CLI / Analysis / Portfolio Bridges
```

目标输出按以下 section 分层：

```text
activity / cash / pnl / capital / assignment-lifecycle / quality
```

时间输入拟统一支持：

```json
{"kind":"mtd","as_of_date":"2026-07-17"}
{"kind":"ytd","as_of_date":"2026-07-17"}
{"kind":"month","month":"2026-06"}
{"kind":"year","year":2025}
{"kind":"range","start_date":"2026-04-01","end_date":"2026-06-30"}
```

计划同时提出：

1. 一套正式的 gross/net PnL 引擎；
2. 历史 `valuation_marks` 和 `fx_rate_facts`；
3. assignment/exercise 一等支持；
4. 新工具 `option_performance_report` 和新 CLI；
5. 把现有 capital bridge 拆成 `portfolio_pnl_bridge` 和 `portfolio_cash_bridge`；
6. shadow migration、cutover、删除 legacy adapter；
7. 不改写现有 immutable history，缺失数据保持 null/incomplete。

## 2. 成功标准审查

方向性成功标准是合理的：现金、活动、PnL、资本占用和数据质量必须分开；MTD/YTD/自然月/自然年必须统一；历史结果必须可重放；assignment 不能把正股交割现金流当亏损。

但当前计划还没有达到可直接交给 implementation agent 的程度。多个核心 contract 仍未收敛，implementation agent 将不得不在实现过程中重新决定账本 ownership、时间边界、费用缺失语义、资本分母、历史 mark 选择和桥图恒等式。这些不是局部实现细节，而是会改变用户看到的收益数字和历史数据一致性的产品/会计语义。

## 3. Assumptions tested

| Assumption | Review 结果 |
|---|---|
| 新 Economic Fact Projection 可以安全放在 canonical ledger 之上 | 未证实；当前描述可能形成第二套 lot/lifecycle state machine |
| `PeriodSpec` 的日期字段足以表达自然月、MTD、YTD | 不成立；缺 reporting timezone、半开区间和 current-day cutoff 语义 |
| 新建 mark/FX 表即可保证历史确定性 | 不成立；缺事实身份、修订、择值、假日和 stale policy |
| 历史费用可以统一得到 net PnL | 不成立；legacy `fees=0` 同时可能代表真实零和缺失 |
| 四类 assignment/exercise 可以在本次 performance refactor 内统一 | 不成立；现有 assigned-stock 事实边界只覆盖 Sell Put 接货及其卖出 |
| capital section 可以直接产出可信 period return | 未证实；没有历史资本暴露序列和明确 denominator contract |
| PnL bridge/cash bridge 只是替换 bridge 指标 | 不成立；两类 bridge 的 balance sheet 基础和恒等式不同 |
| shadow compare 可以自然判断新旧结果一致 | 不成立；新旧口径有预期语义差异，必须先定义 reconciliation matrix |

## 4. Special lens 结论

- **Architecture boundary review**: 主要风险是 Economic Fact Projection 与现有 ledger projection 的 ownership 重叠，以及把 stock inventory 生命周期扩入 option performance 层。
- **Best-practice review**: 历史估值、FX、费用和 period boundary 尚无 versioned fact contract、provenance 和 deterministic selection policy。
- **Optimal-solution review**: “一次性完成所有 assignment 类型、total PnL、capital、两个 bridge”不是当前证据下最安全的路径；应先锁定可重放的 gross realized/cash/activity 核心，再逐层启用 net、valuation、capital 和 bridges。
- **Overengineering review**: 预先指定 18 个新模块，但没有给每个模块唯一 ownership 和依赖图，容易先造层再找职责。
- **Overcoupling review**: 当前计划把 ledger correction、事实存储、performance API、stock inventory、portfolio bridge 和 public cutover 绑成一个大迁移；任一未收敛 contract 都会阻塞全部交付。

## 5. Findings

### PR-01-未修复-严重-Economic Fact Projection 的 ownership 未定义，可能产生第二套账本状态机
- **位置**: 目标架构 `canonical facts -> Economic Fact Projection -> Period Performance Engine`；Phase 3 “Unified economic fact and PnL projection”；拟新增 `event_normalizer.py`、`cashflow.py`、`pnl.py`、`assignment.py`、`aggregation.py`。
- **问题类型**: 架构边界 / 过度耦合 / 过度设计 / 不可直接实施
- **当前写法**: 计划要求新建统一 economic fact/PnL projection，同时保留 `trade_events -> projection -> position_lots` 为 canonical boundary，并要求新的 PnL engine 做 lot fee allocation、assignment attribution 和 realized PnL。
- **反例/失败场景**: 一个 partial close 被 canonical ledger 投影到目标 lot；Economic Fact Projection 再次依据事件顺序做 lot matching 和费用分摊。repair/void、同合约多 lot、事件乱序或历史 adjust 后，两套投影产生不同 closed quantity、open basis 或 fee allocation。风险视图读取 `position_lots`，收益报表读取 Economic Fact Projection，于是同一账户同时出现“持仓已关闭”和“收益引擎仍有剩余 lot”等不一致。
- **为什么有问题**: lot matching、void/repair、close quantity 和 assignment target 是账本状态机职责，不应由 performance aggregation 再实现一次。当前计划没有说明 Economic Fact 是纯派生值对象、可重建 materialization，还是拥有生命周期状态的独立 projection；也没有说明新 PnL 的 closed-lot allocation 应归 ledger 还是 performance。
- **直接证据**:
  - 项目 contract 明确 canonical 边界为 `trade_events -> projection -> position_lots`。
  - `domain/domain/ledger/projection.py` 已负责 target lot 校验、partial close、void/repair 和 position state。
  - `src/application/positions/reporting.py:2480-2547` 当前又独立做 open-lot matching 和 realized PnL，正是计划想消除的重复计算。
  - `domain/domain/ledger/lots.py:30-45,124-131` 已在 lot projection 中累计 realized PnL。
  - `src/application/ledger/repository.py:143-190` 将 `trade_events`、`position_lots`、`assigned_stock_events` 分为不同存储边界。
- **影响**: 状态不一致 / 生成错误代码 / repair 后历史收益漂移 / review 无法判断哪套结果是权威 / 后续返工。
- **建议改法和验证点**:
  1. 在 ADR 中只允许一个 lifecycle allocation owner：建议由 ledger domain 输出 versioned、可重放的 `LotEconomicAllocation`（open allocation、close allocation、assignment/exercise settlement link、fee facts），performance engine 只做 period filtering、valuation 和 aggregation。
  2. 明确 Economic Fact Projection 是 **无独立业务状态、从 canonical streams 可重建** 的只读 projection；不得自行选择 target lot 或修改 lifecycle state。
  3. 若需要持久化，只能作为带 `projection_version`、`source_event_ids`、`built_at` 的 disposable materialization；删除后能从事实流完全重建。
  4. 先画 dependency/ownership 图，再决定文件拆分；不要在 contract 未定前锁死 18 个模块。
  5. 验证：同合约多 lot、partial close、多次 close、void close、repair open、repair close、assignment 后 replay，ledger state 与 performance allocations 必须共享同一 allocation IDs 且数量恒等。
- **修复风险（高）**: 需要重写计划的核心边界和 Phase 3 ownership，但越晚修成本越高。
- **严重程度（严重）**: 属于 implementation 前 blocker。

### PR-02-未修复-高-PeriodSpec 未定义时区、区间和 current-day cutoff，MTD/YTD 仍会在月界错归
- **位置**: Period 输入设计；Phase 1 `PeriodSpec`；历史 as-of 规则。
- **问题类型**: 契约缺失 / 状态机漏洞 / 测试缺口
- **当前写法**: 计划用 `as_of_date`、`month`、`year` 或 `start_date/end_date` 归一化 requested/effective start/end 和 valuation cutoff，但没有指定 reporting timezone、边界包含关系、当前日的有效截止时刻或多市场账户规则。
- **反例/失败场景**:
  - 美股 2026-07-31 20:30 America/New_York 的成交，在 UTC/北京时间已是 2026-08-01。按交易所自然月属于 7 月，按当前代码 UTC 月份属于 8 月。
  - `as_of_date=2026-07-17` 在当天上午查询，若归一到当日 23:59:59，会表达未来 cutoff；若归一到当前时刻，又与历史日期的 EOD 语义不同。
  - HK 与 US 账户组合报表若各自按市场时区切月，combined row 的 period boundary 不再相同；若统一北京时间，则必须明确这是 operator-reporting month，不是 exchange month。
- **为什么有问题**: period contract 是所有 cash/PnL/valuation/capital aggregation 的根。边界不明确会直接造成跨月、跨年 double count 或遗漏，而且 shadow comparison 也无法区分代码 bug 与时区口径变化。
- **直接证据**:
  - `src/application/positions/reporting.py:32-50` 把 naive datetime 当 UTC，并用 UTC 生成 `YYYY-MM`。
  - `src/application/portfolio_capital_bridge.py:14-18,44-60` 对 portfolio cutoff 使用 `Asia/Shanghai` 日末。
  - 现有两条路径已存在 UTC 月归属与北京时间 EOD 的不一致。
- **影响**: 月度/YTD 数字错归 / 同一事件跨工具归属不同 / 期末估值错位 / 迁移对账无法验收。
- **建议改法和验证点**:
  1. `PeriodSpec` 必须包含或解析出 `reporting_timezone`，并明确默认策略。建议 operator-facing 报表统一使用显式配置的 reporting timezone；若产品选择 exchange-local month，也必须禁止跨不同时区直接生成 combined period。
  2. 所有内部 period 使用半开区间 `[start_instant, end_exclusive_instant)`；输出同时给出 requested/effective local dates 和 UTC instants。
  3. 明确 `as_of_date=today` 的有效 cutoff 是 `min(now, local_day_end)`，历史日期才使用 local EOD；未来日期应拒绝或降为 today 并给 diagnostic，不能静默。
  4. 将 transaction attribution cutoff 与 valuation cutoff 分开命名。
  5. 验证：UTC/月界、DST、闰年、1 月 1 日、month-end 周末、跨 US/HK 账户、当天盘中和历史 EOD。
- **修复风险（中）**: 主要是 contract 和测试矩阵，但会改变现有月份归属。
- **严重程度（高）**: MTD/YTD 的前置 blocker。

### PR-03-未修复-高-valuation_marks 与 fx_rate_facts 只有表名，没有 deterministic fact/selection contract
- **位置**: “Historical determinism”；Phase 5 valuation/historical FX/total PnL；拟新增 `valuation_service.py`、`fx_service.py`。
- **问题类型**: 契约缺失 / 最佳实践偏离 / 并发恢复风险 / 不可直接实施
- **当前写法**: 计划提出新增 `valuation_marks` 和 `fx_rate_facts`，禁止历史报告使用当前价格/当前 FX，缺失时返回 null。
- **反例/失败场景**:
  - 月末是周末，没有月末当天 mark；实现 A 选上一个交易日 close，实现 B 要求 exact timestamp，于是同一月 total PnL 一个有值、一个缺失。
  - 同一标的同一 valuation date 后续补入 broker corrected close。若表只做 upsert，历史报表被静默改写；若 append-only 又没有 revision selection，查询结果不确定。
  - 交易现金流按当前 FX 转 CNY，期末 mark 按历史 FX 转 CNY，产生无法解释的 FX PnL；或 USD/HKD 使用不同 source/calendar 导致 combined CNY 不可重复。
  - 两个并发 backfill 对同一 key 写入不同 source，缺少唯一键和冲突策略。
- **为什么有问题**: “不能用 live 值”只是负面约束，不能定义应使用哪个历史事实。total PnL、CNY bridge 和 shadow replay 需要稳定的 fact identity、source precedence、revision 和 stale rules。
- **直接证据**:
  - `src/application/positions/reporting.py:53-79,2822-2841` 当前只接收一个 rates snapshot，并未按 event/valuation date 选择 FX。
  - `docs/ASSIGNED_STOCK_RETURN_DESIGN.md:260-270` 已要求历史 as-of 只能使用保存 mark 或历史行情，缺失则 explicit missing，但未实现统一存储选择规则。
  - `src/application/ledger/repository.py:143-190` 当前 SQLite 初始化采用直接建表；计划没有给新事实表 schema、版本或迁移规则。
- **影响**: 历史结果随补数/调用顺序变化 / PnL 与 FX attribution 不可解释 / backfill 冲突 / 报表大量不可预测 null。
- **建议改法和验证点**:
  1. 在实施前定义 `ValuationMarkFact`：instrument identity、price、currency、mark kind（close/manual/broker snapshot）、effective_at、observed_at、source、source_id、revision/supersedes、quality/staleness。
  2. 定义 `FxRateFact`：base/quote、rate、effective date/time、source、observed_at、revision、conversion convention。
  3. 定义 deterministic selector：exact/as-of、previous trading close 最大回看天数、source precedence、修订选择、stale threshold；输出 selected fact id 和选择理由。
  4. 明确 CNY PnL decomposition：transaction-date FX、period-open FX、period-end FX，以及是否单列 FX translation PnL。
  5. 表必须有唯一约束、append/correction policy、schema version、幂等 backfill 和 dry-run comparison。
  6. 验证：周末月末、停牌、缺 quote、late correction、相同时间多 source、FX 缺失、回放前后结果稳定。
- **修复风险（高）**: 会决定 storage schema 和 total PnL 口径。
- **严重程度（高）**: total/unrealized PnL 和历史 CNY 输出的 blocker。

### PR-04-未修复-高-legacy `fees=0` 无法区分真实零与未知，net PnL 计划会制造虚假精度
- **位置**: “One formal PnL engine”；Phase 3/4 typed fee facts；gross/net metric contract；legacy migration。
- **问题类型**: 数据质量 / 契约缺失 / 迁移风险 / 测试缺口
- **当前写法**: 计划要求统一 gross/net PnL，partial close 按比例分配 open fee，并新增 typed fee facts；但没有定义既有事件 `fees=0` 的历史解释和 net PnL availability rule。
- **反例/失败场景**: 历史 open event 没有录入手续费，codec/default 将其变成 `0.0`。新引擎把它当 actual zero，并输出精确 `realized_pnl_net`；另一个 assignment settlement 的 `fees=0` 带 `fee_provenance.basis=actual`，两者存储数值相同但语义不同。结果是部分历史净利润被高估且 quality 仍显示 complete。
- **为什么有问题**: 缺失数据不能被当零是项目硬约束。net PnL 只有在所有所需 fee components 有 actual/approved estimate 时才成立；否则 gross 可用、net 应 null 或明确 incomplete。
- **直接证据**:
  - `domain/domain/ledger/events.py:36-66` 定义 `fees: float = 0.0`，并把 falsy/missing 都归一为 `0.0`。
  - `domain/domain/ledger/lots.py:124-131` 直接从 gross 减 `event.fees`，且不处理 open fee。
  - `docs/ASSIGNED_STOCK_RETURN_DESIGN.md:105-127` 对 assignment stock fee 已引入 `basis/source/reason` provenance，说明数值本身不足以表达证据质量。
  - `src/application/positions/reporting.py:2093-2122` assigned-stock lifecycle 已区分 actual/estimated/missing fee components；option lot 侧尚未统一。
- **影响**: 历史 net PnL 系统性偏高 / 用户误以为费用完整 / shadow migration 误判 / partial close fee 重复或遗漏。
- **建议改法和验证点**:
  1. 在 metric ADR 中规定 gross 是基础权威值；net 只有 fee coverage 达标才非 null。
  2. 设计 tri-state `FeeFact`：`amount`、`basis=actual|estimated|missing`、component、source、reason、source_event_id；legacy bare `fees=0` 默认不能升级为 actual zero，除非 raw payload/provenance 明确。
  3. 明确 open fee allocation：按 opened contracts 分摊，已关闭部分进入 realized net，剩余部分进入 open cost basis；最后一笔 close 吸收 rounding remainder。
  4. assignment/exercise fee 必须拆分 option close fee 与 stock settlement fee，禁止重复计入 lifecycle net。
  5. 验证：显式零、缺失、estimated、partial closes、rounding、void/repair fee、跨币种 fee、最后 lot close。
- **修复风险（中）**: 主要影响 schema adapter 和 net availability，但会暴露更多 null。
- **严重程度（高）**: 净收益可信度 blocker。

### PR-05-未修复-严重-四类 assignment/exercise 矩阵越过现有 stock inventory 边界
- **位置**: “Assignment support must be first-class”；settlement matrix；typed assigned-stock event types；Phase 6。
- **问题类型**: 范围漂移 / 架构边界 / 过度耦合 / 非最优方案
- **当前写法**: 计划在本次 performance refactor 中统一支持 Short Put assignment 买股、Short Call assignment 卖股、Long Call exercise 买股、Long Put exercise 卖股，并加入 dividend、withholding tax、split 等 stock events。
- **反例/失败场景**:
  - Covered Call 被行权卖出 100 股，但这 100 股来自普通股票买入，不是 Sell Put assignment lot。当前 `assigned_stock_events` 明确不记录普通股票交易，因此没有 canonical stock cost basis 可以计算 lifecycle PnL。
  - Long Put exercise 需要知道被卖出股票的具体 inventory lot 和成本；当前 option ledger 无法唯一归属。
  - Short Call 是 naked 或部分 covered 时，卖出产生 short stock/混合 inventory，当前 assigned-stock model 不能表达。
  - split/dividend/tax 对普通持股与 assigned stock 混合持仓的分配也依赖完整股票账本，而不是 option performance 层的局部 event list。
- **为什么有问题**: 这不是“assignment 收益统计补全”，而是引入通用 stock inventory/corporate-action ledger。若没有新的 canonical stock ledger 或可靠外部 portfolio ledger contract，performance engine 只能靠 heuristic attribution，违反“不能猜历史事实”。
- **直接证据**:
  - `docs/ASSIGNED_STOCK_RETURN_DESIGN.md:3-5,37` 明确当前只覆盖 Sell Put 接货；Short Call、普通股票账本、分红和税务不在当前设计范围。
  - 同文档 `:166-184` 明确 `assigned_stock_events` 只保存由 assignment 产生的正股 lot sale/adjust/void/repair，普通股票买卖不进入该流。
  - 当前 broker intake 只把唯一匹配 assigned-stock lot 的 stock sell 写入该事件流；无法匹配时保持 unresolved，而不是猜测。
- **影响**: 错误 stock basis / lifecycle PnL 重复或遗漏 / 普通股票与 assigned stock 混淆 / scope 无限扩大 / 本次重构无法收敛。
- **建议改法和验证点**:
  1. 本次 performance v1 的一等 assignment 范围限定为已有可靠事实链的 **Short Put assignment -> assigned stock lot -> sale/mark**。
  2. 所有 option assignment/exercise 都可以先记录 option close 和 stock settlement cash fact；但若缺 canonical inventory basis，stock/lifecycle PnL 必须 `unsupported` 或 `incomplete`，不能估算。
  3. Short Call、Long Put exercise、普通股票 basis、dividend/tax/split 单列为 “Stock Inventory Ledger / Portfolio Ledger Integration” 设计项目，先决定由 OM 自建还是消费 portfolio-management 的权威 lot facts。
  4. 如果 CEO 明确要求本次一起做，必须先提交独立 stock-ledger ADR、event/state machine、corporate-action allocation 和迁移计划，再回接 performance；不能把它隐藏在 `assignment.py`。
  5. 验证：covered/naked/partial covered、mixed inventory、specific-lot/FIFO、partial exercise、split 后 exercise、dividend withholding、unresolved inventory。
- **修复风险（高）**: 需要缩小当前 scope 或新增独立大型子项目。
- **严重程度（严重）**: 当前 scope 下不可安全实施。

### PR-06-未修复-高-capital/return 仍无 denominator contract，YTD 回报率可能继续错误
- **位置**: `capital.py`、target `capital` section、annualized capital efficiency、metric naming cleanup。
- **问题类型**: 契约缺失 / 动机未闭环 / 测试缺口
- **当前写法**: 计划识别了现有 `realized_pnl / current_open_cash_secured` 的错误，并要求所有 return 显式带 `capital_basis`，但没有决定 period capital exposure 的计算方法、证据来源和聚合公式。
- **反例/失败场景**:
  - 1 月持有 cash-secured put，2 月已关闭；7 月做 YTD 时 current collateral 为 0。若仍使用 current snapshot，return 不可算；若使用 open notional，又必须按持有天数积分。
  - assigned stock 上同时卖 covered call，若 stock capital-days 和 call locked-share capital-days都进入 denominator，会重复计算同一资本。
  - broker margin account 的实际 capital at risk 与 strike notional 不同；把 estimated cash-secured notional 称为“投资回报率”会误导。
  - realized PnL numerator 只含 period closes，但 denominator 若含期末所有 open exposure，scope 不一致。
- **为什么有问题**: return 不是金额的简单聚合。没有明确 numerator/denominator/time weighting，就无法为 MTD/YTD/year 给出稳定、可比较或可年化的 rate。
- **直接证据**:
  - `src/application/positions/reporting.py:733-838` 当前按月聚合后使用 `cash_secured_by_account` 当前 snapshot，并输出 `return_basis=current_cash_secured`。
  - `src/application/positions/reporting.py:2082-2110` assigned-stock lifecycle 已使用 capital-days，但它只覆盖特定 lifecycle，不能自动推广为整个账户 period return。
  - 工具 contract 仍把 `realized_return_rate` 和 annualized rate 暴露为 primary fields（`src/application/agent_tools/positions.py:23-43`）。
- **影响**: YTD/年度回报率仍不可解释 / 不同策略不可比较 / annualization 放大错误 / 用户决策风险。
- **建议改法和验证点**:
  1. 在 Phase 0 明确至少两种不同 metric，不能混名：
     - `capital_efficiency_on_notional_days = period_pnl * 365 / sum(defined_notional * active_days)`；
     - broker/account return 若无权威 daily NAV/capital facts则不提供。
  2. 每个 rate 输出 `numerator_metric`、`capital_basis`、`capital_days`、coverage、annualization method。
  3. 明确 open unrealized PnL 是否进入 numerator；realized-only 与 total-PnL return 分开。
  4. 对 covered call 定义 shared-capital attribution，避免 stock 与 call 重复 denominator。
  5. 若现阶段没有完整历史 capital facts，v1 先交付 cash/activity/PnL，capital rates 返回 `not_available`；不要为满足字段而估算。
  6. 验证：期内开平、跨期持仓、0 denominator、partial close、assigned stock + covered call、margin/cash account、跨币种 notional days。
- **修复风险（高）**: 需要产品口径决策和新历史 exposure projection。
- **严重程度（高）**: 所有 period return/annualized output 的 blocker；不阻塞纯金额报表。

### PR-07-未修复-严重-PnL bridge 与 cash bridge 未定义不同的 balance-sheet 恒等式和上游事实
- **位置**: “Asset bridge target”；Phase 8 “PnL bridge and cash bridge”。
- **问题类型**: 动机不成立 / 契约缺失 / 架构边界 / 非最优方案
- **当前写法**: 计划正确指出现有 bridge 使用 option cash 而非 option PnL，并建议替换为 `portfolio_pnl_bridge` 与 `portfolio_cash_bridge`，但没有定义两者各自桥接的是 total assets 还是 cash balance，也没有说明 portfolio-management 需要提供哪些 opening/ending facts。
- **反例/失败场景**:
  - total-assets bridge 中加入权利金现金流和 assignment settlement cashflow：二者只是资产内部现金与证券转换，不应作为 total asset change；这样会把同一经济变化又放入 residual 抵消。
  - cash bridge 继续使用 `/analysis/capital-facts` 的 opening/ending assets，而不是 opening/ending cash，数学上可以造出 waterfall，但没有现金恒等式意义。
  - `option_total_pnl` 包含 assigned-stock PnL，而 PM residual/stock category也包含该正股 PnL；若分类边界不明确，option 与 stock attribution 发生双重归类。
  - OM 用 gross PnL、PM period PnL 用 net-of-fee NAV；两者相减后的 residual 含 fee mismatch，却被标成 portfolio/other。
- **为什么有问题**: PnL bridge 和 cash bridge 是两种不同报表，不是把 step 名称替换一下。必须先确定 balance sheet 基础、valuation/FX/fee basis 和 component ownership，才能使用 OM 子账本对 PM 总账做 carve-out。
- **直接证据**:
  - 当前 `src/application/portfolio_capital_bridge.py:113-149` 从 PM 读取 `opening_assets/external_cash_flow/period_pnl/ending_assets`，却用 `period_pnl - option_cash_change` 生成 residual。
  - 当前 option evidence 明确取 `monthly_income_report.return_summary[].net_income_cny`（同文件 `:68-81,155-185`），该字段排除了 assignment principal，既不是真正完整 cash movement，也不是 PnL。
  - `tests/test_portfolio_capital_bridge.py:47-113` 只验证算术闭合和月份选择，没有验证经济分类恒等式。
- **影响**: waterfall 数学闭合但经济语义错误 / 现金与总资产混淆 / assignment 重复归因 / residual 无法诊断 / 用户被误导。
- **建议改法和验证点**:
  1. 在 bridge ADR 中分别定义：
     - Total-assets/PnL bridge：`ending_assets = opening_assets + external_flows + option_total_pnl_net + non_option_pnl_net + explicit_reconciliation_residual`。
     - Cash bridge：`ending_cash = opening_cash + external_cash_flows + option_trade_cash + stock_settlement_cash + stock_sale_cash + dividends/taxes + non_option_cash`。
  2. Cash bridge 必须要求 PM 或 broker 提供 opening/ending cash；若没有，上线状态应为 unavailable，不得复用 assets。
  3. PnL bridge 必须统一 valuation cutoff、FX、fee basis，并明确 assigned-stock lifecycle 是归 option strategy 还是 stock；同一 PnL 只能属于一个 component。
  4. residual 不应作为自动吸收错误的“other”；输出 mismatch components、basis differences 和 tolerance。
  5. Phase 8 应拆成两个独立 work unit，各自有输入 contract 和 golden reconciliation fixtures。
  6. 验证：premium-only open、buy-to-close、assignment、assigned stock mark/sale、跨币种、fee mismatch、missing mark、PM/OM cutoff mismatch。
- **修复风险（高）**: 需要 portfolio-management contract 配合，cash bridge 可能暂时不可交付。
- **严重程度（严重）**: bridge 方案当前不可直接实施。

### PR-08-未修复-高-shadow migration 没有 metric reconciliation matrix、consumer inventory 和 cutover gate
- **位置**: Phase 7-9；新 `option_performance_report`、legacy adapter、analysis views、bridge cutover、legacy deletion。
- **问题类型**: 迁移风险 / 切片过粗 / 测试缺口 / 不可直接实施
- **当前写法**: 计划提出 shadow migration、comparison、cutover、删除 `monthly_income_report`，但没有说明哪些新旧字段应严格相等、哪些因 fee/FX/time semantics 应预期不同，也没有列出所有内部/外部 consumer 和删除门槛。
- **反例/失败场景**:
  - 新 realized net 与旧 gross 不相等，comparison 报大量 diff；实现者为了过 gate 放宽 tolerance，真实 lot allocation bug 也被吞掉。
  - `analysis_query` 的 monthly views、portfolio bridge、copilot answer contract 仍读取旧字段；Agent tool 已切新，内部分析结果却继续走旧口径。
  - adapter 把 period summary 再拆成 monthly rows时丢失 quality/FX/valuation coverage；旧 consumer把 null 当 0。
  - 删除 old tool 后，plugin contract、CLI docs、Copilot eval 和 bridge loader 一部分仍引用 schema version/field names。
- **为什么有问题**: 这是 public contract 和 historical metric migration。没有逐字段 reconciliation 和 consumer graph，shadow 模式只能发现“不同”，不能证明“正确”；legacy 删除也无法安全验收。
- **直接证据**:
  - `src/application/agent_tools/positions.py:23-110,264-311` 定义了稳定 output schema 和大量 fact fields。
  - `src/application/agent_tools/analysis.py:65-115,600-735` 把 return summary 暴露为多组 analysis views/aliases。
  - `tests/test_agent_plugin_contract.py:205-292` 对 schema versions 和 contract fields 有显式断言。
  - `src/application/portfolio_capital_bridge.py:155-205` 直接消费 `return_summary[].net_income_cny`。
  - performance 相关 consumer 分布在至少 19 个测试文件，而计划尚未给出 consumer inventory。
- **影响**: 迁移 gate 失真 / 混合新旧口径长期存在 / public contract regressions / legacy 无法删除 / silent data mismatch。
- **建议改法和验证点**:
  1. 在 implementation 前建立 old-to-new metric matrix：字段、grain、gross/net、currency/FX date、time attribution、assignment inclusion、expected equality/delta、null policy。
  2. 建立 consumer inventory：Agent tool、CLI、analysis views、portfolio bridge、assistant/copilot renderer/evals、docs 和任何 scripts。
  3. shadow gate 分层：
     - native-currency cash/activity identity 精确相等；
     - gross realized 按 allocation IDs 对账；
     - net/FX/valuation 只与明确 expected-delta model 对账；
     - quantity invariants、coverage/null regression、replay determinism 单独 gate。
  4. 每 phase 必须有独立可交付 vertical slice，建议顺序：Period + metric contracts → realized gross/cash/activity → fee-aware net → valuation/FX total PnL → capital → Sell Put lifecycle → bridges → consumer cutover。
  5. legacy adapter 至少保留一个明确 deprecation window；删除门槛包括 consumer graph 为零、shadow fixtures 通过、rollback 路径验证。
  6. 加入 version-skew 测试：旧 DB + 新代码、新 DB + adapter、部分 mark/FX backfill、mixed schema startup。
- **修复风险（中）**: 主要是完善计划、fixtures 和迁移工具，但工作量不可忽略。
- **严重程度（高）**: cutover 前 blocker。

## 6. Open Questions

以下问题必须由计划 owner/CEO 在 implementation 前明确，不能留给实现 Agent 临场决定：

1. **自然月的 reporting timezone 是什么？** 统一 `Asia/Shanghai`、按交易所时区，还是账户配置？跨市场 combined 如何处理？
2. **v1 是否真的要求四类 assignment/exercise lifecycle PnL？** 若是，canonical stock inventory 的 owner 是 OM 还是 portfolio-management？
3. **核心 period return 的 denominator 是什么？** cash-secured notional-days、stock cost-days、broker margin、daily NAV，还是只提供 capital efficiency 不称“return”？
4. **历史 total PnL 的 mark selection policy 是什么？** 月末非交易日、停牌、manual correction、stale threshold 如何定义？
5. **CNY PnL 是否分解 FX translation？** 交易现金流 FX 与期末估值 FX 分别取哪一天/哪一来源？
6. **legacy bare `fees=0` 如何解释？** 默认 missing，还是可根据 source/version 推断 actual zero？
7. **assigned-stock lifecycle PnL 在 portfolio PnL bridge 中归 option strategy 还是 stock？** 该选择必须与 PM 分类一致。
8. **cash bridge 的 opening/ending cash facts 从哪里来？** 当前 `/analysis/capital-facts` 只证明有 assets/PnL contract，未证明 cash balance contract。
9. **是否需要 persisted Economic Fact Projection？** 若需要，重建、版本、invalidate、rollback 和并发 build 规则是什么？

|---|---|

## 8. 建议的计划修订顺序

在进入 `/execute` 前，先把原计划修订为以下 code-generation-ready gates：

1. **ADR-1 Metric & Period Contract**：金额/活动/现金/PnL/return 命名、reporting timezone、半开区间、null/quality。
2. **ADR-2 Projection Ownership**：ledger allocation 是唯一 lifecycle owner；performance 只聚合；明确 materialization 是否存在。
3. **ADR-3 Fee & Money Facts**：gross/net、legacy fee unknown、Decimal/rounding、partial-close allocation。
4. **Slice A**：只实现 native currency 的 activity、complete cash movements、realized gross、MTD/YTD/month/year/range；不做 total PnL/return/bridge。
5. **ADR-4 Historical Valuation & FX**：schema、source precedence、revision、selector、backfill、FX translation。
6. **Slice B**：fee-aware net + historical total PnL + quality coverage。
7. **Slice C**：现有可靠范围内的 Sell Put assignment lifecycle；其它 settlement 先 explicit incomplete。
8. **ADR-5 Capital Methodology** 后再实现 Slice D capital efficiency/return。
9. **ADR-6 Portfolio Bridge Contracts** 后把 PnL bridge 与 cash bridge作为两个 work units。
10. **Migration/Cutover**：metric matrix、consumer inventory、shadow gates、rollback、deprecation window、legacy deletion。

## 9. Final conclusion

**Conclusion: fail**

计划方向正确，尤其是拆分 cash/PnL/activity、支持统一 period、禁止 live 值污染历史、first-class data quality 和 staged migration；但当前仍有 3 个严重 blocker 和 5 个高风险 blocker。最关键的是：

1. lifecycle/PnL projection ownership 未定；
2. assignment scope 实际扩成通用 stock inventory ledger；
3. PnL/cash bridge 没有合法的独立恒等式和上游事实 contract；
4. time、fee、mark/FX、capital 和 migration gates 仍欠规格。

因此该计划目前**不应直接交给 implementation agent**。先完成上述 ADR/contract 修订后，再做一次 planreview；通过后从 Slice A 开始实施，而不是直接创建全部模块或修改 `monthly_income_report` 参数。
