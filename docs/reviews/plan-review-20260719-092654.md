# Plan Review — 远端日志防复发配置方案

## Reviewed target and scope

- **目标方案**：
  1. 新增 `/etc/systemd/journald.conf.d/options-monitor-storage.conf`：
     `SystemMaxUse=512M`、`SystemKeepFree=2G`、`MaxRetentionSec=7day`；
  2. 将 `/etc/logrotate.d/rsyslog` 从 `weekly / rotate 4` 改为
     `daily / rotate 7 / compress / delaycompress / maxsize 250M`；
  3. 通过 `systemctl restart systemd-journald` 和
     `logrotate --debug /etc/logrotate.d/rsyslog` 应用/验证。
- **Review scope**：配置语义、容量保证、Incus 共享存储边界、日志洪泛根因、rollout/rollback、验证充分性。
- **不在范围**：本 review 不修改远端配置、不重启服务、不清理更多数据。

## Current evidence

- 清理后根盘：约 99 GB，总使用约 91%，普通可用约 9.0 GB。
- 容器可见根目录数据约 9.5 GB，但底层共享文件系统已使用约 91 GB；根挂载来自
  `/var/lib/incus/storage-pools/default/containers/liuxie/rootfs`，说明大部分占用在容器命名空间之外。
- journald 清理后约 500 MB；当前没有本地容量 drop-in。
- `/etc/logrotate.d/rsyslog` 当前为 weekly、rotate 4、compress、delaycompress。
- `logrotate.timer` 仅 `OnCalendar=daily`，且 `AccuracySec=1h`。
- 最近 100,000 行 syslog 中约 95,802 行来自 `om-agent`，另有约 3,456 行来自 `om`；其中
  `需要手机验证码` 1,925 次、`RemoteClose` 1,439 次、`init connect fail` 2,018 次。
- 本机 logrotate 3.21.0 man page 说明 `maxsize` 是 logrotate 执行时的轮转判断；它不提供独立的实时文件大小监控。

## Assumptions tested

1. `SystemMaxUse=512M` 能把整个磁盘保留在安全水位。
2. `SystemKeepFree=2G` 在 Incus 容器内等价于宿主存储池的可靠安全阈值。
3. `daily + maxsize 250M` 能把 syslog 文件实时限制在 250 MB 左右。
4. 日志轮转是当前增长问题的主要修复，而非仅缓解症状。
5. `logrotate --debug` 足以证明 postrotate、文件重建、权限和 rsyslog 继续写入均正常。
6. 直接覆盖生产配置并 restart 的 rollout 已有充分的备份和回滚定义。

## Findings

### PR-001-未修复-高-`maxsize 250M` 不是实时硬上限，方案仍允许单日洪泛写满磁盘
- **位置**: rsyslog logrotate 方案与成功信号
- **问题类型**: 契约缺失 / 最佳实践偏离 / 非最优方案
- **当前写法**: 声称“单次 logrotate 检查时，超过 250 MB 即轮转”，并将其作为防止 syslog 再次增长到数 GB 的主要保护。
- **反例/失败场景**: `logrotate.timer` 每日只触发一次且允许约 1 小时调度误差。若 Futu/OM 在两次检查之间持续洪泛，`syslog` 可以远超 250 MB，甚至在下一次 logrotate 前耗尽当前 9 GB 可用空间。
- **为什么有问题**: `maxsize` 只在 logrotate 被调用时参与判断，不监控实时文件大小。当前证据已经显示一周产生过 3.3 GB 的未压缩 `syslog.1`，且近期 95.8% 日志来自 `om-agent`，存在高突发风险。
- **直接证据**: `/usr/lib/systemd/system/logrotate.timer` 为 `OnCalendar=daily`、`AccuracySec=1h`；logrotate 3.21.0 man page把 `maxsize` 描述为轮转判断条件；当前日志洪泛计数见上文。
- **影响**: 方案实施后仍可能再次磁盘写满；“250 MB 上限”形成错误安全感。
- **建议改法和验证点**:
  - 将成功目标改成“每日检查下的轮转阈值”，不要称为硬上限；
  - 如果需要近似硬保护，增加受控的 hourly logrotate timer override，或采用 rsyslog 原生输出限额/独立 OM 日志文件；
  - 先测量 15–60 分钟峰值写入速率，再决定 250 MB 阈值和检查频率；
  - 验证在人工注入超过阈值的测试日志后，下一次计划检查能轮转且 rsyslog 继续写入。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR-002-未修复-高-方案把容器内日志上限误当成共享 Incus 存储池保护
- **位置**: journald `SystemKeepFree=2G` 目标与整体磁盘成功标准
- **问题类型**: 架构边界 / 契约缺失 / open question 未收敛
- **当前写法**: 认为 journald 保留 2 GB 空间后可防止根盘再次写满。
- **反例/失败场景**: 其他 Incus 容器、镜像或快照在宿主侧增长 9 GB，即使本容器 journal 固定在 512 MB、syslog 正常轮转，本容器看到的共享文件系统仍会达到 100%。
- **为什么有问题**: 容器内 `du /` 只能解释约 9.5 GB，而底层文件系统已使用约 91 GB。`SystemKeepFree` 只约束 journald 自身写入与清理，不会限制宿主侧其他消费者，也不会约束 rsyslog、OM 数据或其他容器。
- **直接证据**: 根挂载源为 Incus storage pool 中的容器 rootfs；`df` 与容器内 `du` 相差约 80 GB；跳板账号无 shell，当前无法审计宿主侧占用。
- **影响**: 方案即使完全正确实施，也不能满足“防止远端磁盘再次写满”的整体目标；风险被留在不可见宿主边界。
- **建议改法和验证点**:
  - 将方案拆成“容器日志控制”和“宿主存储池治理”两个独立 work item；
  - 必须获得 Incus 宿主只读审计能力，统计 containers/images/backups/snapshots；
  - 为宿主池设置告警阈值（建议至少 15% 或明确 GiB 水位），不能只依赖容器内 2 GB；
  - success signal 同时包含容器日志上限和宿主池 free-space 告警。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR-003-未修复-高-日志洪泛的业务根因未进入方案，轮转只会压缩故障证据
- **位置**: 动机、scope 与 non-goals
- **问题类型**: 动机不成立 / 范围漂移 / 非最优方案
- **当前写法**: 将 journald/logrotate 配置视为防复发方案，未包含 OM/Futu 连接重试异常的诊断和遏制。
- **反例/失败场景**: 手机验证码未处理导致多个 `om-agent`/`om` 进程持续创建连接、断开、重试。日志被更快轮转后，磁盘增长速度有所受控，但远端运行仍可能产生连接风暴、会话风暴、CPU/网络负载和业务不可用；7 天保留也可能很快只剩高频重复信息。
- **为什么有问题**: 最近 100,000 行中 95,802 行来自 `om-agent`，明确不是正常均匀系统日志；验证码、连接失败和 RemoteClose 各出现上千次。容量治理不能替代生产故障治理。
- **直接证据**: syslog 最近 100k 行来源与错误计数；5 秒采样期间 syslog 仍持续增长；Strategy Lab timers 和其他 OM 服务保持 active。
- **影响**: 隐藏真实生产故障，日志信噪比恶化，磁盘/CPU/连接资源仍可能被消耗，后续故障诊断证据被短保留策略覆盖。
- **建议改法和验证点**:
  - 在修改保留策略前或并行创建独立 incident：定位产生 `om-agent` 洪泛的具体 unit、触发频率和 Futu 验证状态；
  - 验证是否存在重叠 timer、失败重试无退避、并发探针或每次运行重复初始化 OpenD；
  - 修复后以“每分钟日志行数、验证码错误数、连接创建数”作为验收指标；
  - 日志容量配置保留为 defense-in-depth，而不是 root-cause fix。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR-004-未修复-中-rollout 缺少原配置备份、原子写入、真实轮转验证和明确回滚
- **位置**: 应用与验证步骤
- **问题类型**: 不可直接实施 / 测试缺口 / 并发恢复风险
- **当前写法**: 新增 journald drop-in、直接修改 `/etc/logrotate.d/rsyslog`、restart journald，再运行 `logrotate --debug`。
- **反例/失败场景**: logrotate 配置语法可解析，但 postrotate 脚本、权限、create owner/group 或 rsyslog reopen 在真实轮转时失败；`--debug` 不修改日志，无法证明真实轮转链路。配置覆盖后若服务异常，也没有文档化恢复旧文件的命令。
- **为什么有问题**: 生产日志路径是故障时的主要可观测性边界。仅 debug 验证 happy path，不证明写入恢复、文件权限和 postrotate。
- **直接证据**: 当前 `/etc/logrotate.d/rsyslog` 有 `sharedscripts` 和 `/usr/lib/rsyslog/rsyslog-rotate` postrotate；方案没有备份、checksum、atomic install、rollback 或真实 canary。
- **影响**: 可能静默停止 syslog 写入或破坏日志权限；故障发生时缺乏恢复证据。
- **建议改法和验证点**:
  - 实施前保存带时间戳备份和 SHA-256；使用临时文件 + `install` 原子替换；
  - 先运行 `systemd-analyze cat-config systemd/journald.conf` 和 `logrotate --debug`；
  - 在低风险窗口运行一次受控真实轮转（或对临时测试日志使用同等配置），验证新文件 owner/group/mode、rsyslog 继续写入、journal 可查询；
  - 明确 rollback：恢复备份、重启/重新打开日志、验证写入；
  - 记录变更前后磁盘、日志速率和服务状态。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### PR-005-未修复-中-`MaxRetentionSec=7day` 与排障/审计需求没有证据化权衡
- **位置**: journald 保留周期
- **问题类型**: open question 未收敛 / 最佳实践偏离
- **当前写法**: 同时设置 512 MB 上限和 7 天保留，但没有说明事故追溯、审计或周末无人值守时所需的最短窗口。
- **反例/失败场景**: 在当前高日志率下，512 MB 容量上限可能远早于 7 天淘汰日志；发生周末或低频故障时，关键日志在人工介入前已经被覆盖。反过来，容量上限已经是主约束，7 天可能并不提供实际保障。
- **为什么有问题**: `SystemMaxUse` 与 `MaxRetentionSec` 是两个竞争约束，实际保留窗口取更严格者。方案没有基于当前日志率计算可实现的 retention，也没有远端日志汇聚或关键事件单独保留。
- **直接证据**: journal 曾达到 4 GB；最近日志存在明显洪泛；计划上限仅 512 MB。
- **影响**: 运维人员误以为拥有 7 天日志，实际可能只有数小时或数天，影响事故复盘和审计。
- **建议改法和验证点**:
  - 先修复洪泛并测量稳定状态下每天 journal 增量；
  - 用实测速率验证 512 MB 是否覆盖目标排障窗口；
  - 明确关键 OM audit/state 文件与普通 stdout/stderr 的保留边界；
  - 若必须保证 7 天，采用远端日志汇聚或提高容量，而不是只写 `MaxRetentionSec`。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

## Architecture boundary review

当前计划只操作容器内 journald/rsyslog，却把成功目标表述为整个远端磁盘防复发。Incus 宿主存储池是更高层 ownership boundary，且当前不可观测。应拆分责任：容器负责日志和 OM 数据保留；宿主负责 storage pool、镜像、快照、其他容器和容量告警。

## Best-practice review

容量上限和轮转是必要的 defense-in-depth，但缺少日志速率基线、根因处理、原子 rollout、rollback、真实轮转 canary 和宿主告警，不满足生产日志变更的可验证与可恢复要求。

## Optimal-solution review

更优路径不是直接应用原方案，而是分两步：

1. **立即安全治理**：保留当前已完成的一次性清理；诊断并停止 OM/Futu 日志洪泛；测量稳定日志速率。
2. **基于证据配置**：journald 容量 drop-in + 更高频/可验证的 rsyslog 轮转 + 宿主池告警；按目标排障窗口选容量，而不是先固定 512 MB/7 天。

## Overengineering review

方案本身没有明显过度设计；两个标准配置文件属于最小原生机制。风险来自保护强度不足和边界误判，而不是抽象过多。

## Overcoupling review

不应把 journald、rsyslog、OM/Futu 重试和 Incus 宿主容量作为一次不可分割的配置发布。它们应成为可独立验证和回滚的 work units，但共享统一的磁盘水位与日志速率验收指标。

## Open questions

1. 哪个具体 systemd unit 或 timer 产生 95.8% 的 `om-agent` 日志？是否存在并发/重叠运行？
2. Futu “需要手机验证码” 是持续认证故障、某个账号独有问题，还是 OpenD 会话失效？
3. 稳定状态下 journald 与 syslog 的每日增长量是多少？目标排障窗口是 3 天、7 天还是更长？
4. 谁拥有 Incus 宿主权限，如何审计约 80 GB 容器外占用并设置告警？
5. 是否有集中式日志/备份，允许远端只保留短窗口？

## Residual risks and suggested tracking

- **宿主池仍可能被其他消费者写满**：建立独立 infrastructure issue。
- **OM/Futu 日志洪泛与潜在业务不可用**：建立 production incident，优先于配置 rollout。
- **Shadow Replay receipts 会继续增长**：建立 retention automation issue，避免依赖人工删除。
- **日志变更回滚与 canary 缺失**：纳入修订后的实施计划和 runbook。

## Final conclusion

**fail**

原方案适合作为紧急缓解的草案，但尚不应直接实施。至少需要先修复 PR-001、PR-003、PR-004，并把 PR-002 作为独立但必须跟踪的宿主存储治理工作；否则方案会制造“已设置上限所以安全”的错误结论，同时继续掩盖 OM/Futu 日志洪泛。
