# Plan Review — Copilot Option Performance MTD

- Reviewed target: `docs/gateflow/copilot-option-performance-mtd/plan.md`
- Scope: Copilot input adaptation, option/assigned-stock PnL decomposition, deterministic rendering, prompt/eval, Gateflow sequencing
- Review timestamp: 2026-07-23 16:43:51
- Review posture: adversarial pre-implementation review
- Conclusion: `fail`

## Goal and boundary tested

The plan intends to make the first Copilot `option_performance_report` call valid for MTD,
preserve strict public period validation, expose canonical option-versus-assigned-stock
realized PnL, and make cash/assignment/scope semantics visible without production writes.

The review tested:

- whether the proposed payload cleanup preserves fail-closed input semantics;
- whether period normalization stays at the correct ownership boundary;
- whether option and assigned-stock facts can be separated without source-ID inference;
- whether the account-scope success criterion is implementable from current scene provenance;
- whether the tests prove the production failure rather than only a rendered answer;
- whether the proposed adapter hook is narrower and safer than hard-coded Copilot routing.

## Assumptions tested

1. `None` and empty-string values are equivalent optional omissions.
2. Copilot can distinguish an account explicitly requested now from an account inferred from
   conversation history.
3. Option and assigned-stock realized facts can be separated at generation time without
   changing existing fact kinds.
4. A tool-owned optional Copilot normalizer does not leak into public execution semantics.
5. Exact payload validation plus deterministic eval is sufficient to cover the online failure.

## Findings

### PR-01-未修复-高-全局删除空字符串会把错误输入静默扩大为默认市场或全部账户

- **位置**: 3.1 AgentTool Copilot adapter；Slice 1 第 3 项；Risk “Copilot normalizer silently hides a genuinely ambiguous public request”
- **问题类型**: 契约缺失 / 最佳实践偏离 / failure handling
- **当前写法**: 合并 safe/static/model/scene inputs 后，“删除值为 `None` 或空字符串的 optional 输入”，再执行 tool normalizer 和 canonical validation。
- **反例/失败场景**: 模型明确提交 `account=""`、`config_key=""`、`month=""` 或 static payload 配置错误。全局 cleanup 删除这些值后，`account` 变成全部账户，`config_key` 回落到默认 `us`，或者 period field 被默认日期代替。原本应被 schema/validator 拒绝的请求会成功返回更宽或不同市场的数据。
- **为什么有问题**: 线上根因是 `safe_default_input` 自身发布了 fake `None` defaults，不是所有调用方显式空值都应视为 omission。金融报告边界应 fail closed；静默扩大 scope 比清晰的 `INPUT_ERROR` 更危险。
- **直接证据**: `src/application/copilot/tools.py:41-53` 当前把 safe defaults、static payload 和 scene/model payload 合并；`src/application/copilot/engine.py:693-699` 的 `_tool_input()` 已只忽略 UI scene 的 `None`/empty，但保留模型 arguments；`src/application/agent_tools/positions.py:246-259` 是 hidden `None` defaults 的具体来源。`account` 的 input description 明确规定“omitted aggregates all accounts”，所以删除显式空值会改变 scope。
- **影响**: Copilot 可能在输入错误时返回错误市场或全部账户的金额，同时表面上显示工具成功；这是比当前可见失败更难发现的财务口径错误。
- **建议改法和验证点**:
  - 只删除 option-performance `safe_default_input` 中的 fake `None` entries；`tool_descriptions()` 和 schema default injection 只发布真实非-null defaults。
  - 不做 generic final-payload empty-string cleanup；model/static 显式 `None`/`""` 继续交给 execution schema fail closed。
  - period normalizer 只删除与已选择 period 不相关的 period discriminator fields；对当前 period 所需字段的 `""`/invalid value 不修复。
  - 新增测试：hidden defaults 不出现；`account=""` 和 `config_key=""` 仍失败；MTD 的 irrelevant `month/year/range` 被删除，但 invalid `as_of_date=""` 仍失败。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### PR-02-未修复-中-“只有明确当前账户才缩小范围”在现有 scene contract 中不可判定

- **位置**: Success criteria 6；2.3 Answer quality；Slice 2 acceptance；Risk “Account scope inherited incorrectly”
- **问题类型**: 不可直接实施 / open question 未收敛 / 测试缺口
- **当前写法**: 未指定账户时聚合全部账户；只有当前请求或“明确会话范围”提供账户时才缩小。计划又把 model input 视为 explicit input。
- **反例/失败场景**: 用户当前只问“7月 MTD 的期权收益”，历史消息中曾讨论 `lx`。模型可在 tool arguments 中发出 `account="lx"`。Host 只看到模型参数，没有字段说明该值来自当前消息、UI scene、还是历史推断，因此 normalizer 无法判断是否应保留。
- **为什么有问题**: 计划的硬成功标准需要 account provenance，但当前 runtime scene 只显式注入 `config_key`、`symbol`、`month`、`reference_year`，没有 account 或 provenance。靠 prompt 可以改善但不能形成 deterministic contract。实施 Agent要么过度扩展 scope parser，要么声称一个无法证明的保证。
- **直接证据**: `src/application/copilot/scene.py:125-132` 的 runtime context 不含 account；`src/application/copilot/engine.py:693-699` 只 overlay `config_key/symbol/month/reference_year`；tool call arguments 与 conversation source 没有 provenance。`src/application/assistant/renderer.py:755-759` 可以展示结果 scope，但不能判断 scope 来源。
- **影响**: Gate acceptance 无法客观判定；线上仍可能继承历史账户，或为满足硬标准而新增不可靠的关键词/account parser，违反“不用关键词硬编码”的 non-goal。
- **建议改法和验证点**:
  - 将本 work unit 的 deterministic contract 收敛为：tool 默认不含 account 即聚合；任何实际 account filter 必须在 renderer/answer 明示；prompt 要求只有当前请求或明确会话上下文才提交 account。
  - 不在本 slice 新增 account-provenance parser。若产品需要“只认当前消息”的强保证，另开 scene scope/provenance work unit。
  - 测试：无 account argument 的 payload 保持 omitted 且 report scope 为 all；有 explicit account argument 时保留且标题明确；eval 检查实际 scope 被回答，不声称能证明参数来源。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

## Architecture boundary review

The optional `AgentTool.copilot_input_normalizer` is acceptable if it remains a pure adapter
hook adjacent to existing `copilot_input_schema`, is omitted from public manifests, and is used
only after source-aware payload merge. It is preferable to hard-coding
`option_performance_report` inside the Copilot engine.

The proposed PnL split is aligned with domain ownership: `build_period_performance()` currently
constructs option allocation/missing facts and assigned-stock facts in separate calls before
sorting. Retaining those exact collections is safer than the current
`_assigned_stock_report_summary()` source-ID reclassification, where an assignment close event
can share its source ID with an option allocation.

## Best-practice and optimal-solution review

- Keep public period validation strict and adapt only model-produced mutually exclusive fields.
- Preserve invalid explicit inputs so the canonical validator remains observable and auditable.
- Additive component metrics are safer than changing existing fact kinds or deriving stock PnL
  in the renderer.
- A single optional tool-owned normalizer is proportionate to the proven problem; a registry,
  discriminator framework, or keyword router would be unnecessary.

## Overengineering and overcoupling review

No new state, persistence, migration, or external dependency is required. The plan should avoid
turning the payload normalizer into a generic cleanup framework. The three slices are reviewable
independently if Slice 1 limits itself to input adaptation, Slice 2 owns canonical semantics and
rendering, and Slice 3 changes only model guidance/evidence gates.

## Open Questions

- None after accepting the account-provenance limitation as an explicit residual boundary.

## Residual Risks

- Prompt-only account intent can still be inferred incorrectly from conversation history; track
  a separate scene-scope/provenance work unit if this becomes a recurring production defect.
- The report will split realized PnL but retain one combined period-total PnL. The renderer must
  label that total as combined so it cannot be mistaken for pure-option mark-to-market.
- This work unit uses deterministic local regressions and does not run a live Feishu model
  canary. A post-release no-send production canary would require separate authorization.

## Final conclusion

`fail`: the plan should not enter implementation until PR-01 and PR-02 are incorporated and
re-reviewed. The core architecture direction is otherwise credible and appropriately scoped.
