# Plan Review

## Reviewed target and scope

- **Target**: 对 2026-07-28 13:00 `lx` / `sy` Sell Put 推荐分叉所提出的“同一 `run_id` 只获取一次行情并冻结 `required_data`，所有账户只读同一快照”修复方案。
- **Claimed goal**: 消除同一整点运行内因账户先后取数导致的候选差异，同时保留账户资金、持仓和策略覆盖层造成的合法差异。
- **Proposed boundary**:
  - 在 `tick_account_execution.py` 的账户流水线之前执行一次 run 级 required-data prefetch；
  - 删除 `account_run.py` 内按账户触发的重复 prefetch；
  - 将 `--shared-required-data` 解释为冻结、只读且禁止兜底取数；
  - 向每个账户复制同一份 prefetch summary，并修复 Daily Brief 对 summary 的解析；
  - 用串行、并行、force、部分失败、报价漂移和文件哈希测试验收。
- **Review scope**: run 级行情计划、账户特定需求、冻结快照契约、并发屏障、失败传播、Daily Brief 可观测性、Position Advice 候选捕获和公共 CLI 兼容性。
- **Out of scope**: 实施代码、修改原方案、发布、部署或触发真实通知。
- **Repository state**: 当前 `main` 工作树包含未提交的 Position Advice / `VERSION` 相关改动；本次仅新增此审查 artifact，未触碰这些在途文件。

## Assumptions tested

1. **run 级基础配置足以生成覆盖所有账户的唯一预取计划**：被反例推翻。Sell Call 的有效最小行权价会在账户 portfolio context 加载后按 `avg_cost` 改写。
2. **账户流水线只要不执行 fetch，就不会再次受实时行情影响**：被反例推翻。现有 fetch-plan 构建会先实时查询 spot 和到期日，再用新计划校验冻结 CSV。
3. **冻结快照缺失或覆盖不足会稳定地产生可审计的 symbol/strategy data gap**：未成立。required-data 异常发生在策略级异常边界之前，当前外层只返回通用失败 summary。
4. **账户 futures 启动前的 prefetch 即形成可靠完成屏障**：方向正确，但必须把 snapshot manifest/receipts 的完整发布作为屏障完成条件，而不能只依赖 `errors == 0` 或目录存在。
5. **把现有 `--shared-required-data` 全局改成只读是最小且兼容的修复**：证据不足。该参数是公共 pipeline CLI 和 infrastructure adapter 的既有契约，方案没有盘点非 tick 调用者。

## Special review lenses

- **Architecture boundary**: run 级 market-data 获取应由 tick orchestration 持有；账户流水线只消费 manifest 所绑定的事实。当前方案的 ownership 方向正确，但没有把 planning authority 一并移出账户流水线。
- **Best practice**: 不可变快照需要显式 manifest、计划摘要、内容哈希、完成状态和 typed failure；“同一个目录里已经有文件”不足以证明快照可消费。
- **Optimal solution**: 最实际的路径是发布一个 run-scoped snapshot manifest，并让账户流水线按该 manifest 校验和读取；不应在消费端重新发现 spot/expirations。
- **Overengineering**: 无需新增配置系统、数据库或通用 snapshot framework；现有 quote receipt、fetch plan debug 和 run state 已足够承载最小 manifest。
- **Overcoupling**: 不应为了 tick 的冻结语义，把所有 `--shared-required-data` 调用统一绑定到只读模式；冻结模式应由 run manifest 或显式内部执行参数限定。

## Findings

### PR-01-未修复-高-run级预取计划没有覆盖账户特定的有效取数范围
- **位置**: “在账户流水线前统一预取一次”及“账户只保留资金/持仓覆盖层差异”的核心 slice。
- **问题类型**: 契约缺失 / 不可直接实施 / 架构边界
- **当前写法**: 方案要求从 base watchlist/config 构造一次 market fetch plan，随后 `lx`、`sy` 都只读该快照。
- **反例/失败场景**: 某账户持有深度浮亏的股票，`avg_cost` 明显高于当前 spot。账户流水线把 Sell Call `min_strike` 提高到成本线后，需要的最高行权价也随之提高；基础配置按 spot 构造的 run 级快照可能没有覆盖该区间。冻结模式下该账户只能失败，若允许兜底则又重新引入按账户取数和行情分叉。
- **为什么有问题**: “同一市场快照”不等于“按第一个或基础账户需求取一次”。共享快照必须覆盖所有活跃账户的策略输入并集，否则该修复会以牺牲某个账户的合法分析为代价。当前方案没有定义如何在 market prefetch 前取得并合并账户特定需求，implementation agent 必须临场重新设计。
- **直接证据**: `src/application/pipeline_watchlist.py:214-225` 在账户 pipeline 内才构建 portfolio context；`src/application/symbol_monitoring.py:108-136` 使用该 context 执行账户 prefilter，并以 `stock.avg_cost` 改写 Sell Call `min_strike`；`src/application/required_data_planning.py:303-340` 又依据这个最小行权价生成 call-side fetch 上下界。
- **影响**: 生成错误代码 / 状态不一致 / 某账户策略静默缺数或被迫重新取数 / 后续返工
- **建议改法和验证点**:
  - 在计划中明确 snapshot coverage policy。推荐在 market prefetch 前先只读收集所有扫描账户的 portfolio context，按账户解析有效策略需求，再对每个 symbol/side 合并 `min_dte`、`max_dte`、expirations 和 strike bounds；market data 仍只获取一次。
  - 若不希望预取阶段依赖账户 context，则必须定义并证明一个配置有界的 superset，覆盖账户成本线可能产生的合法范围；不能默认基础配置天然足够。
  - 新增回归测试：两个账户同一 symbol、不同 `avg_cost`，其中一个成本高于 spot 默认 call 上界；断言 run manifest 覆盖两者且账户流水线均不触发新行情调用。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR-02-未修复-高-消费冻结快照时仍会重新发现实时spot和到期日
- **位置**: “`--shared-required-data` 为冻结只读，禁止 fallback fetch”契约及报价漂移测试。
- **问题类型**: 状态机漏洞 / 最佳实践偏离 / 不可直接实施
- **当前写法**: 方案只要求 `ensure_required_data` 在已有共享文件时不再 fetch，并用文件哈希验证账户执行前后不变。
- **反例/失败场景**: run 级 prefetch 用 spot A 生成 CSV。数秒后 `lx` 或 `sy` 进入账户流水线，重新查询到 spot B，并基于 B 重建 fetch plan。即使完全没有写文件或执行链数据 fetch，覆盖校验仍会因为 CSV 内 spot A 与计划 spot B 不一致而失败；不同账户进入时间不同，失败结果仍可能分叉。
- **为什么有问题**: 冻结语义要求 planning facts 与 payload 一起被冻结。只冻结 CSV 字节、却允许消费端重新发现 spot/expirations，仍然把实时行情带入决策路径。现有 spot 校验容差极小，普通报价变化足以触发失败。
- **直接证据**: `src/application/symbol_monitoring.py:151-178` 在每个账户、每个 symbol 内重建 fetch plan；`src/application/required_data_planning.py:161-189` 优先调用实时 `get_underlier_spot`，`src/application/required_data_planning.py:610-635` 同时实时发现 spot 和 expirations；`src/application/required_data_coverage.py:68-72,190-202` 要求 CSV spot 以约百万分之一的相对容差匹配新计划；`src/application/required_data_steps.py:93-109,130-202` 在覆盖失败后进入真实 fetch 路径。
- **影响**: 同一 run 仍受时间漂移影响 / 冻结快照被误判不可用 / 若实现不严谨则发生二次取数 / review 不可验收
- **建议改法和验证点**:
  - 将 run 级 fetch plan、snapshot id、raw/CSV hash、quote receipt 和完成状态发布为 immutable snapshot manifest。
  - 账户流水线直接消费 manifest 中已解析的 plan/receipt；冻结模式禁止调用 spot/expiration discovery，也禁止从账户配置重新生成 market plan。
  - 校验应验证 manifest 绑定的 plan 与文件内容，而不是用新实时事实重新规划。
  - 报价漂移测试必须让第二次 discovery 返回不同 spot/expiration，并断言 discovery 根本未被调用，而不仅是断言 fetch 函数未被调用。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR-03-未修复-高-冻结快照失败没有定义到策略产物和决策简报的完整传播
- **位置**: “缺失/覆盖不完整按 symbol 降级”“总失败阻断 brief”“修复 Daily Brief prefetch gap”测试 slice。
- **问题类型**: 契约缺失 / 测试缺口 / 最佳实践偏离
- **当前写法**: 方案要求 partial failure 只影响对应 symbol，并让 Daily Brief 呈现 data gap；但没有规定异常类型、捕获边界、空产物、candidate capture status 和账户最终状态。
- **反例/失败场景**: 某 symbol 的冻结 CSV 缺失或 manifest 校验失败。异常在策略扫描之前抛出，Sell Put/Sell Call/Combo 的各自异常处理没有运行；外层 watchlist 仅返回通用“处理失败”summary。canonical candidate/reject artifacts 可能完全缺失，Daily Brief 随后得到多个 `source_artifact_missing`，Position Advice capture 也没有 typed completion/failure，无法区分“确定没有候选”和“行情快照不可用”。
- **为什么有问题**: 用户看到的推荐消息必须 fail-closed 且可解释。只修正 prefetch summary 的 JSON shape 不能保证策略产物、brief authority 和候选捕获在同一个失败事实上收敛；implementation agent 仍需自行决定哪些错误阻断账户发送、哪些只降级单个 symbol。
- **直接证据**: `src/application/symbol_monitoring.py:186-209` 的 required-data 调用发生在策略级 `try` 之前，而 Sell Put 的 materialize/capture failure 逻辑从 `src/application/symbol_monitoring.py:273-333` 才开始；`src/application/pipeline_watchlist.py:239-271,273-338` 的外层捕获只返回 normalized failure rows；`src/application/daily_decision_brief_service.py:614-617` 对缺失策略产物记录 `source_artifact_missing`；同文件 `1957-1983` 仍按旧的 `symbols: Mapping` 和嵌套 `summary.errors` 解析 prefetch。
- **影响**: 用户可见消息语义含混 / 数据缺口被错误归类 / Position Advice 输入不完整 / 风险后移
- **建议改法和验证点**:
  - 在计划中定义 typed `FrozenRequiredDataUnavailable`（或等价结果类型）及唯一处理边界。
  - 对受影响 symbol，统一物化每个已启用策略的 canonical empty/error artifact，写入 candidate capture failure，并把 snapshot/manifest reason 传入 Daily Brief；明确这是“数据不可用”，不是“0 候选”。
  - 明确账户级发送策略：单 symbol partial failure 是否允许带醒目缺口发送；全量 required-data failure 必须阻断 normal actionable brief。
  - 用端到端 artifact 测试验证 summary、策略 CSV/reject log、capture status、brief `status/actionability/data_gaps` 和最终 notify decision，而不只测 prefetch 计数。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR-04-未修复-中-把公共shared-required-data参数全局改成冻结模式扩大了兼容范围
- **位置**: “明确 `--shared-required-data` 即冻结只读，无 fallback fetch 或 multiplier 写入”的接口修改。
- **问题类型**: 过度耦合 / 范围漂移 / 非最优方案
- **当前写法**: 方案复用一个既有路径参数，同时改变所有调用场景下的行为语义。
- **反例/失败场景**: 开发者或非 tick adapter 传入一个部分填充的 shared directory，当前行为会在 coverage 不足时补取；全局改成 frozen 后，同一命令变成失败。由于计划未盘点所有外部调用者，这个兼容变化可能在与 13:00 bug 无关的流程中出现。
- **为什么有问题**: 路径共享和不可变 run snapshot 是两个独立概念。把它们绑定到同一个 bool-like presence contract，会让 future caller 无法表达“共享但可补齐”与“严格冻结”，也迫使所有入口同步采用新语义。
- **直接证据**: `src/application/pipeline_runtime.py:56,92-100,188-190` 将该参数暴露为公共 pipeline CLI；`src/infrastructure/external_services.py:85-113` 从 adapter 透传路径；`src/application/required_data_steps.py:83-109,130-202` 的现有契约是在 coverage 不足时补取。现有搜索未发现直接覆盖该公共兼容变化的测试。
- **影响**: 非目标流程回归 / 公共契约不清 / 后续返工
- **建议改法和验证点**:
  - 保留 shared directory 的既有一般能力；为 tick run 传递 snapshot manifest 或显式内部 `required_data_mode=frozen`，冻结语义仅在 manifest 存在且验证成功时生效。
  - 不新增生产配置键；该模式属于执行契约，可由 tick adapter 传递。
  - 增加兼容测试：普通 shared mode 维持现状；run-frozen mode 缺失/不匹配时 fail-closed 且零外部行情调用、零文件修改。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

## Open Questions

1. run snapshot 的覆盖策略选择哪一种：先读取所有账户 context 后合并有效计划，还是采用不依赖账户 context 的配置有界 superset？前者精确但增加前置读取和时序，后者简单但必须证明上界可控且不会漏掉成本线。
2. partial symbol failure 的发送规则是什么：允许发送带明确 data gap 的 degraded brief，还是任一 required-data gap 都阻断该账户？方案目前只明确“全量失败阻断”。
3. snapshot manifest 的发布完成条件是什么：每个 symbol receipt 全部成功、允许带显式 failed symbol 的完整 manifest，还是两种状态都支持？必须在账户 futures 提交前固定。
4. `--shared-required-data` 是否存在仓库外操作脚本或人工使用依赖“覆盖不足自动补取”的行为？本地代码和测试无法证明外部调用情况。

## Residual risks and tracking

- 不同 `run_id` 之间因行情变化产生不同候选是预期行为；修复只能保证同一 run 内事实一致，不能把跨 run 结果解释成回归。
- required-data 当前按 symbol 分文件发布，不是跨 symbol 事务。即使采用 barrier，进程在中途崩溃仍会留下部分文件；manifest 必须是最后发布的 commit marker，未完成 manifest 不得被账户消费。
- multiplier enrichment 若仍会改写 frozen CSV，会破坏 receipt/hash 绑定；应在 prefetch 发布 manifest 前完成，账户消费阶段只读。
- 建议把以上风险跟踪到修订后的 implementation plan，并将 PR-01 至 PR-03 作为进入实现前必须关闭的 acceptance gates；PR-04 可与公共兼容测试一起在同一 work unit 关闭。

## Final conclusion

**fail**

方案把 market-data ownership 上移到 run orchestration 的方向是正确的，也直接对应 13:00 的根因；但当前仍缺少跨账户计划并集、planning facts 冻结以及失败产物传播三个关键契约。按现稿交给 implementation agent，会迫使其在核心边界上重新设计，并且存在“文件没变但仍因实时 spot 校验而分叉”的可信反例。先修订并关闭 PR-01 至 PR-03，再进入实现。
