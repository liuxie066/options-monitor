## Findings

### DR2-01-未修复-高-单次 provider 调用可超过固定租约并被另一 worker 并发重取

- **入口/函数**: `reconcile_due_lifecycle_cases_for_source()` -> `claim_settlement_attempt()` -> `SettlementObservationCollector.collect_outcome()` -> `complete_settlement_attempt()`
- **文件(行号)**: `src/application/trades/lifecycle_runtime.py:774-969`; `src/application/trades/inbox.py:462-508,514-548`; `src/application/trades/settlement_observation.py:315-410`; `src/infrastructure/futu_gateway.py:165-208`
- **输入场景**: 一个已取得 claim 的 settlement case 执行多源 provider collection，其中历史订单或成交查询因 OpenD/网络缓慢、分页量大或调用挂起而超过 120 秒；同一 source 的另一 worker 在租约到期后处理同一 case。
- **实际分支**: runtime 在调用前把 claim 续到固定 `now + 120_000ms`，随后同步执行 provider collection、canonical reconciliation 和 control completion。该临界区没有与租约绑定的强制超时，也没有 heartbeat/续租。SQLite 在 `claim_until_ms <= now_ms` 后允许另一 claim 取得 ownership，而旧 worker 不会在 provider I/O 期间察觉并停止。
- **预期行为**: claim 的有效期必须覆盖它保护的 provider I/O、canonical write 和 control completion；只要原 worker仍在正常执行，第二 worker就不能为同一 case 发起 provider 调用。若采用固定租约，collector 必须有严格小于租约且可实际终止 I/O 的上界；否则必须安全续租。
- **实际行为**: 租约到期后两个 worker 可同时执行同一组 provider 查询。旧 worker可能已经写入 canonical ledger，最后却因 claim ownership 已改变而在 completion 失败；下一轮仍会产生额外 control error 或重试。
- **直接证据**: runtime 以 `lease_ms=120_000` claim 后直接调用 collector，直到 canonical reconciliation 和 `complete_settlement_attempt()` 之前均无 ownership renewal（`lifecycle_runtime.py:774-969`）。collector 顺序执行 history deals、history orders、positions 和 trading calendar（`settlement_observation.py:315-410`）；Futu history adapter 每项允许最多 100 页，调用本身没有 timeout（`futu_gateway.py:165-208`）。claim SQL 明确允许过期 lease 被新 claim 覆盖（`inbox.py:488-504`）。现有慢调用回归只证明后续 case 不会被提前 claim，没有覆盖单个正在运行的调用自身超过 lease。
- **影响**: 破坏“有效 claim 防止第二 worker provider call”的核心止血保证；恰逢 provider 变慢时仍可能放大重复网络 I/O、CPU 占用和 60 秒循环错误，重新触发本次要消除的同类故障。
- **建议改法和验证点**: 为每次已 claim 的 provider attempt 增加窄范围可续租 guard，覆盖 collection、canonical reconciliation 到 control completion；续租必须核对同一 claim 和 case scope，进程退出后自然停止。若续租失去 ownership，应产生 typed control outcome，且不得以旧 claim 覆盖新 owner。新增短租约/可控时钟的并发回归，证明单次慢调用跨越多个 lease interval 时竞争 worker始终不能取得 claim；停止续租后 lease 才能被回收。不要用无法取消底层 SDK 调用的线程 timeout 冒充真正边界。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高
