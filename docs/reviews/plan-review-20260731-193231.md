## Goal and boundary understood

方案的目标是取消“交易前声明组合”的阻断式流程：每笔成交先按真实交易事实进入
`trade_events -> position_lots`，Long Call 或 Sell Put 任一腿先到都进入可重算的未分组集合；批次封口、
后续成交、回补或定时 sweep 时，再从所有合法 Put/Call 边中做一对一全局匹配。精确、充分且无冲突的证据
可自动形成 Combo；证据不充分但结构合法时，在成交后向用户确认；证据弱时继续保持单腿，不阻断交易和单腿管理。

方案还区分推荐身份与真实组合身份：以 run-scoped `candidate_occurrence_id` 证明某一时间范围内的具体候选，
以 `combo_pair_inferences` 保存推理过程，只有 `inferred_high` 或 `user_confirmed` 才写入 canonical
`strategy_group_identities`。计划采用先只读复算、再确认写入、最后才启用高置信自动写入的 rollout。

这一产品方向成立。本次 review 只判断它是否已经具体到可以安全交给 implementation agent，不重新设计 Combo
策略、候选排名或重复 Funding Put 周期。

## Assumptions tested

1. 当前推荐和 Daily Brief 证据能够唯一证明一个精确、近期且当时可执行的 `candidate_pair_id` occurrence。
2. 两个已经按单腿入账的 lot 可以通过现有 ledger/identity 写路径事后、原子地升级为 canonical Combo。
3. append-only 模型可以安全表达自动误配后的 `superseded`/纠正，而不会让下游继续消费旧身份。
4. 部分成交可先聚合，再无损映射回当前以 open event/record ID 为核心的 Combo identity。
5. “mutual best + runner-up margin + High/Medium/Low”已经足够确定，不会让实现者自行发明评分和阈值。
6. 重放、乱序到达和并发 sweep 不会重复占用同一 lot 或产生 inference/identity 半完成状态。

## Review lenses applied

- **Architecture boundary review**: trade intake、ledger projection、inference state、candidate/Brief provenance、
  immutable group identity 和 downstream attribution 的 ownership 与事务边界。
- **Best-practice review**: event-time、幂等、one-to-one allocation、fail-closed provenance、原子状态转换、
  可纠正性、确定性重放和审计。
- **Optimal-solution review**: 优先复用当前 run-scoped Brief、exact event/lot identity 和 SQLite transaction，
  避免为 V1 引入通用图评分器或多腿/多批次组合模型。
- **Overengineering review**: 挑战尚无校准数据支持的连续置信度评分、runner-up margin 和多 lot 聚合。
- **Overcoupling review**: 检查 candidate delivery、inference、lot retag、identity 和下游归因是否被迫跨多个
  非原子存储同步更新。

## Findings

### PR-01-未修复-[高]-事后归组与当前 immutable membership/identity 契约冲突，canonical 转换和纠正都没有可执行写协议

- **位置**: “Persistence”“High/confirmed becomes canonical”“append-only corrections”“superseded”及 rollout 第 3/4 步
- **问题类型**: 架构边界 / 状态机漏洞 / 并发恢复风险 / 不可直接实施
- **当前写法**: 推理先独立持久化；`inferred_high` 或 `user_confirmed` 后原子建立 canonical identity；误判或后续变化用 append-only `superseded` 纠正。
- **反例/失败场景**: Long Call 和 Sell Put 已经作为两个未分组 open lot 入账。用户确认后若直接调用现有 identity adoption，校验会因为两腿尚未带 `strategy=combo_yield`、`leg_role` 和目标 `strategy_group_id` 而失败。若先追加两个 adjust 事件再插 identity，当前 membership resolver 会把 empty-to-group 的变化计为 retag history，并将 group 判为 conflict。即使绕过这一点，identity 表对同一 `group_id` 也是 insert-only；一次高置信自动误配后，计划中的 `superseded` 没有 authoritative effective-identity 语义，下游仍可能继续读取旧 identity。
- **为什么有问题**: 这不是实现细节。成交后反向归组的核心动作，正好跨越 inference、两个 lot 的 membership、projection 和 immutable identity 四个状态；若没有单一事务 authority 和明确的纠正语义，就会出现 inference 已确认但 identity 不存在、lot 已打组但 identity 写失败、或旧 identity 永久污染归因的状态。
- **直接证据**: `src/application/ledger/writer.py:482-524` 的现有 adoption 要求两个精确 record/open event 已带目标 group、Combo strategy 和合法 leg role；`src/application/ledger/combo_membership.py:94-106,132-156` 将任何 retag history 视为 membership conflict；`src/application/ledger/repository.py:1899-1919` 对同一 `group_id` 只允许相同 hash 的幂等重放，不提供 supersede/update。当前代码已有的 second-leg atomic writer适用于事前已有 intent 的路径，不能直接覆盖两个既存未分组 lot。
- **影响**: 核心确认动作无法落地，或只能通过跨事务补丁落地；并发 sweep/用户确认可制造双占用、半完成状态和不可恢复的错误组合归因。
- **建议改法和验证点**: 在计划中先锁定一个且仅一个 post-trade adoption command，由 ledger application boundary 在同一 SQLite transaction 内完成：重读 exact events/lots 和当前 claim；验证未被占用；写入两腿的合法 adoption facts；重建 projection；验证 exact membership；插入 immutable identity；将 exact `inference_id` 转为终态；readback 和 foreign-key 校验。必须明确“首次从 ungrouped 变为 adopted membership”与非法 retag 的区别。若保留自动归组，还必须先定义 append-only identity supersession 的 authoritative read rule；在该规则存在前，rollout 只能停在“建议/用户确认”，不得让 `inferred_high` 自动写 canonical identity。测试至少覆盖任一步失败回滚、重复确认、sweep 与确认并发、两个 inference 争抢同一 lot、误配纠正后下游不再读取旧 identity。
- **修复风险（低/中/高）**: 高
- **严重程度（低/中/高/严重）**: 高

### PR-02-未修复-[高]-当前候选与交付契约不能证明“精确命中某次 candidate_pair_id occurrence”

- **位置**: “candidate_occurrence_id”“exact candidate intersection”“delivery-confirmed is strongest evidence”和 High confidence gate
- **问题类型**: 契约缺失 / 最佳实践偏离 / 不可直接实施 / 测试缺口
- **当前写法**: 以 `hash(account, market, run_id, revision, candidate_pair_id, row_hash)` 标识一次候选；该 occurrence 必须在首笔成交前生成、在两笔成交时都有效、属于同一账户，且 delivery-confirmed 时证据最强。
- **反例/失败场景**: 同一 Put/Call 合约在上午和下午两个 run 中重复出现。上午候选已失效、下午候选在第一腿成交后才生成；或者用户收到的 Brief 只证明该账户/标的存在 Combo Yield 候选，并未证明消息中包含这一个精确 pair。若 reconciler 仅按 `candidate_pair_id`、CSV 路径或当前 delivery state 查找，它可能选择未来 occurrence、过期 occurrence，或把“同标的策略族已送达”误当成“这一 pair 已送达”。
- **为什么有问题**: 计划定义了目标 ID 形状，却没有指定 row canonicalization、immutable source digest、revision 与 occurrence 的 authoritative binding、候选是否真的进入用户可见 envelope，以及 artifact 缺失/清理后的 fail-closed 行为。实现者仍需自行决定哪些文件和 delivery 字段算证据。
- **直接证据**: `src/application/sell_put_call_helper.py:280-304` 的 `candidate_pair_id` 只含 symbol 和两腿 contract symbol，不含 account、run、revision 或时间；`domain/domain/daily_decision_brief.py:75-96` 的交付 candidate identity 仅为 `account + market + symbol + strategy_family`；`src/application/daily_decision_brief_repository.py:331-355` 只校验并交付这些粗粒度 identities。Brief 虽保留 run/revision/time 和 representative contract fields，但当前 delivery confirmation 没有 pair-scoped occurrence identity。
- **影响**: 方案声称的最强自动证据实际上无法审计；future look-ahead、stale recommendation 和同标的多候选都可能被误判为精确命中。
- **建议改法和验证点**: 在计划中把 pair occurrence 定义为冻结 Brief revision 内的正式契约，而不是运行时从文件名猜测：至少绑定 schema、account、market、run ID、revision、Brief digest、两腿 canonical contract keys、`candidate_pair_id`、generated/data-as-of/valid-until 和 canonical row hash。delivery envelope 若作为 High 证据，必须枚举实际展示/发送的 pair occurrence IDs；只有 strategy-family identity 时最多进入确认，不得自动归组。找不到 frozen revision、digest 不匹配、occurrence 在首腿后生成、任一成交超出有效期或来源是 fixed/stale artifact 时都 fail closed。测试覆盖同 pair 跨 run 重复、未来 run、过期、未送达、送达其它 pair、账户不一致和 row 重排。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR-03-未修复-[高]-“聚合部分成交”和当前 one-open-event/one-lot、exact-two-member identity 无法同时成立

- **位置**: “batch seal 后聚合 partial fills”“ratio compatibility（例如 2:2）”“global one-to-one matching”
- **问题类型**: 契约缺失 / 过度设计 / 状态机漏洞 / 不可直接实施
- **当前写法**: 批次封口后先聚合同一订单的部分成交，再按可兼容数量的一对一 Put/Call 腿做全局匹配；2:2 可视为 1:1 ratio-compatible。
- **反例/失败场景**: Long Call 同一订单分两次各成交 1 张，形成两个 open events/lots；Sell Put 一次成交 2 张，形成一个 lot。聚合层看到 2:2，但 current identity 无法同时绑定两个 Call record IDs 和一个 Put record ID。反过来，如果 inference 只选择其中一个 Call lot，则另一张数量被遗留；若把聚合结果伪装成一个 lot，又丢失 canonical event/record lineage。部分平仓后再归组也会使 original/open quantity 语义不一致。
- **为什么有问题**: 当前 canonical identity 是 exact event/lot identity，不是可任意切片的仓位数量。计划没有定义 grouping unit、订单封口权威、lot slice/claim、剩余数量和多成员 group schema，因此“先聚合”会在 inference 与 ledger 之间制造不可逆的信息落差。
- **直接证据**: `domain/domain/ledger/events.py:101-102` 明确一个 open event 生成一个 `lot_<event_id>`；`domain/domain/combo_identity.py:183-208` 要求正好一个 Funding Put 和一个 Participation Call、两个 exact open event/record IDs，且数量相等；当前手动 staggered V1 在 `src/application/positions/combo_pairing.py:120-130` 更严格，只接受 1 张 Put + 1 张 Call。
- **影响**: 常见的 broker partial fill 会导致误占用、漏数量、identity 无法生成或迫使实现者扩大成未经 review 的多-lot identity/schema migration。
- **建议改法和验证点**: 不在本 work unit 内引入多-lot grouping。V1 明确只处理“一个 fully-open Put lot + 一个 fully-open Call lot，whole-lot 数量相等，且无部分平仓/既有 claim”的 exact pairing；同订单多 deal、多 lot、需要 quantity slice 或数量不等时保持 unresolved，并可让用户选择具体 lot，但不能写 canonical identity。若未来确实要支持多-lot group，单独设计 identity/membership schema。测试覆盖 Call 两次 partial fill + Put 一次 full fill、两腿各一个 2-contract lot、部分平仓腿、多个相同 contract lots 和剩余未分配数量。
- **修复风险（低/中/高）**: 低（收窄 V1）；高（若当前即扩展多-lot schema）
- **严重程度（低/中/高/严重）**: 高

### PR-04-未修复-[中]-High/Medium/Low 与 mutual-best margin 没有确定性判定契约，自动归组阈值仍会由实现者发明

- **位置**: “build all legal edges”“solve globally”“mutual best and sufficient margin”“confidence tiers”
- **问题类型**: 非最优方案 / 过度设计 / 契约缺失 / 测试缺口
- **当前写法**: 对合法边评分，执行全局一对一匹配；只有双方 mutual best 且领先 runner-up 足够多才形成 High，结构合理但证据不足为 Medium，其余为 Low。
- **反例/失败场景**: 两个完全相同 contract 的 Call lots 和一个 Put lot 同时存在。candidate occurrence 命中 contract，但不能区分两个 Call lot；不同输入排序、先前 rejection 或 sweep 时点会改变 runner-up 集合。若实现使用时间距离、成交价、candidate quote 或自定义权重，算法可以在相同事实下得到不同 High 结果。算法版本字段只能记录差异，不能定义正确性。
- **为什么有问题**: 没有 feature list、权重、时间窗、margin 单位、tie 规则和校准目标时，连续评分不能成为安全的 write authority；而本需求并不需要先构建通用评分器。
- **直接证据**: 计划只给出 hard gates 和定性 confidence 描述；当前 repo 没有 post-trade Combo edge score 或已校准阈值。normalized trade 能提供 deal/order/time/price，但这些字段的存在不等于它们能证明组合意图。
- **影响**: 同一历史重放可能产生不同配对；High 自动写入缺乏可验收断言，用户确认频率和误配率也无法测量。
- **建议改法和验证点**: V1 删除连续 score/margin 作为自动 authority。exact pair occurrence、exact whole lots、唯一双向候选、无竞争 claim 和明确时间有效性全部成立时才产生一个 deterministic `exact_candidate_match`；任何 contract-level duplicate、多个 occurrence、仅结构/时间接近或仅 economics 合理都进入 confirmation/unresolved。全局求解只负责检测唯一 maximum matching；多解即 ambiguous，不用 tie-break 猜。持久化 sorted input fact IDs、input snapshot hash 和 algorithm version。测试输入顺序不变性、同时到达、乱序/回补重放、相同 contract 多 lot、多解图和 rejection 后重算。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

## Open questions

1. V1 是否接受“所有 canonical 归组都需用户确认”，把 `inferred_high` 自动写入严格留到 supersession/correction authority 完成之后？这是当前最安全、也最不扩边界的 rollout。
2. High 证据是否明确要求 pair-scoped delivery confirmation？若只生成了 live-actionable Brief 但未确认送达，建议固定降为 confirmation，而不是留给实现参数决定。
3. V1 是否接受 exact whole-lot 边界：每腿只能绑定一个 open event/lot；多 deal partial fill 保持 unresolved？若不接受，就需要单独的多-lot identity 设计，已超出本 work unit。

## Final plan review conclusion

`fail`

方向是对的：成交事实优先、第二腿到达后从未分组集合反向重算、证据不足时成交后确认，能够避免交易前声明阻断用户。
但当前方案还不能安全交给 implementation agent。PR-01 阻断 canonical 写入与纠正，PR-02 使所谓“精确候选命中”
缺少现成可审计证据，PR-03 会在真实 partial fill 下迫使实现者临时扩展 identity 模型；PR-04 则让自动阈值没有确定性。

最小修订路径不需要扩大边界：V1 只做 exact whole-lot 推理；把 pair occurrence 固化进 frozen Brief/delivery；
先定义一个原子 post-trade adoption authority；删除未校准的 score/margin；在可纠正 identity 之前，所有 canonical
写入都经用户确认。完成这些修订后再做一次 plan re-review，才能进入实现。
