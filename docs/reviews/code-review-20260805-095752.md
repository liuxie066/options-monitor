## Findings

### 1-未修复-高-子进程内的 prepared option 完整性失败被误分类为普通扫描失败，可进入固定失败通知路径

- **入口/函数**: `run_one_account()` -> `run_pipeline_script()` -> `pipeline_runtime.main()` -> `run_watchlist_pipeline_default()` -> `build_pipeline_context()` -> `load_prepared_option_positions_context()`
- **文件(行号)**: `src/application/pipeline_context.py:502-536`; `src/application/pipeline_watchlist.py:279-319`; `src/application/pipeline_runtime.py:337-405`; `src/application/account_run.py:102-107, 619-677`; `src/application/tick_notification_flow.py:754-789, 844-918`
- **输入场景**: 父进程已准备并传入 ready manifest，但 manifest/payload 在子进程实际读取前缺失、冲突、哈希不匹配，或以 `unavailable` 状态重入。
- **实际分支**: `build_pipeline_context()` 抛出 `PreparedOptionPositionsContextError`；`pipeline_runtime.main()` 没有把该错误转换为 `[CONFIG_ERROR] ACCOUNT_CONFIG_*`，因此子进程仅输出普通 traceback。父进程的 `_pipeline_account_config_error_code()` 只识别 `ACCOUNT_CONFIG_*`，最终保留 scheduler 的 `should_notify`，并根据普通非零返回码将 `ran_scan` 设为 true。
- **预期行为**: supplied prepared authority 失效应在扫描前转换为类型化 `ACCOUNT_CONFIG_PREPARED_OPTION_CONTEXT_INVALID`，父进程应记录 `ran_scan=false` / `should_notify=false`，不允许它获得任何扫描或通知权威。
- **实际行为**: 该完整性故障成为 `PIPELINE_FAILED`；Daily Brief 会因 `ran_scan=true` 继续组装 blocked brief，并在 fixed-failure authority 允许时进入固定失败通知准备。
- **直接证据**: prepared loader 异常在 `pipeline_context.py` 被原样重抛；`pipeline_runtime.py` 直接调用 watchlist runner 而无对应 catch；父进程正则明确只匹配 `ACCOUNT_CONFIG_` 代码；Daily Brief 的 `ran_scan` 门控会信任 AccountResult 中的 true，失败分支可选择 `fixed_failure`。
- **影响**: 完整性故障的分类、扫描指标和通知边界同时不正确；在通知安全敏感的 scheduled tick 中，这会把应 fail-closed 的 authority 错误变成可通知的扫描失败。
- **建议改法和验证点**: 在 `pipeline_runtime` 的 prepared consumer 边界将 `PreparedOptionPositionsContextError` 转换为稳定的 `[CONFIG_ERROR] ACCOUNT_CONFIG_PREPARED_OPTION_CONTEXT_INVALID`；增加真实 `main()` 路径回归测试，再验证父进程解析后 `ran_scan=false` / `should_notify=false` / typed code 保留。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### 2-未修复-中-物理 OpenD host 未规范化，仅大小写不同就会重复 Spot 观测和 provider 任务

- **入口/函数**: `prefetch_required_data()` -> `build_prefetch_symbol_plan()` / `_dedupe_key()` -> `_build_prefetch_fetch_plan()` -> `build_required_data_fetch_plan()` -> `_spot_observation_cache_key()`
- **文件(行号)**: `src/application/required_data_prefetch_planning.py:289-309, 482-515, 806-821`; `src/application/required_data_planning.py:585-616, 1146-1176`; `src/application/multi_tick/required_data_prefetch.py:1138-1149`
- **输入场景**: 两个账户对同一 `NVDA` 的 fetch route 分别配置 `OpenD.EXAMPLE:11111` 与 `opend.example:11111`；DNS hostname 语义上是同一物理 endpoint。
- **实际分支**: `_dedupe_key()` 与 Spot/expiration cache key 都保留 host 原始大小写，因此产生两个 symbol plan 和两个 cache key。同一运行会对同一物理 endpoint 重复观测 Spot，并可并发执行两次完整 provider fetch。
- **预期行为**: physical binding identity 应使用与项目 Futu route 一致的 hostname 规范化（trim + lowercase），路由比较、symbol 去重和 run-local Spot cache 必须得到同一 identity。
- **实际行为**: 只有 symbol 和 source 被规范化，host 大小写会穿透到去重及观测 key。
- **直接证据**: 确定性反例调用 `build_prefetch_symbol_plan()` 对上述两项返回 `requested_count=2, unique_count=2`；`_spot_observation_cache_key()` 分别返回 `('NVDA','futu','OpenD.EXAMPLE',11111,'2026-08-05')` 和 `('NVDA','futu','opend.example',11111,'2026-08-05')`。项目其他 Futu route/broker identity 边界已将 hostname 转为 lowercase。
- **影响**: 违反 S6-lite 的 one-binding/day Spot 不变式，浪费 OpenD 限额，且两个任务会竞争同一 symbol 的 required-data 输出。
- **建议改法和验证点**: 在计划层统一规范化 physical host，并同步用于 candidate/position binding 比较、prefetch 去重、expiration/Spot cache key；新增 host 仅大小写不同的多账户回归，断言单一 symbol plan 和单一 Spot provider call。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
