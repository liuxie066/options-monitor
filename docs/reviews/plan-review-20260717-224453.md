# 飞书机器人表情 ACK 延迟修复计划对抗性审查

- **Review 时间**: 2026-07-17 22:44:53（本机系统时钟，Asia/Shanghai）
- **Reviewed target**: 当前会话上一轮提出的飞书 Reaction 延迟修复方案；仓库中没有对应独立 plan 文件，因此本审查以会话方案为计划真源。
- **Review scope**: Reaction 调用时序、sender allowlist/静默契约、单 worker 队列、outbox retry、飞书 HTTP 重试、同步 handler 公共行为、并发/关闭语义、观测与测试。
- **未执行事项**: 未实施修复、未修改原计划、未修改运行配置、未发送飞书消息或 Reaction。

## 1. 被审计划重建

上一轮方案的核心方向是：

```text
收到事件
  -> 快速解析 sender/message_id
  -> 校验 sender allowlist
  -> 立即添加 reaction
  -> 处理历史 outbox
  -> Assistant/Copilot
  -> 文字回复
```

并提出两个层级：

1. **最小修复**：把 Reaction 移到当前 worker 内的重逻辑之前；保持未授权发送者静默、Reaction 失败不阻断业务。
2. **条件性后续**：如果要求上一条 Copilot 仍在运行时，下一条消息也能亚秒级 ACK，再增加独立 bounded ACK queue/worker。

同时建议增加 `queue_wait_ms`、`inbound_ms`、`reaction_ms` 等结构化耗时观测，但没有形成明确的 SLO、公共契约或切片验收表。

## 2. Goal、non-goals 与 success signal 审查

### 计划声称的 goal

降低飞书机器人对入站消息添加表情的用户可见延迟，使 Reaction 更接近“已收到”的 ACK，而不是 Assistant/Copilot 完成标记。

### 可推断的 non-goals

- 不改变 Assistant/Copilot、Control 和工具执行的业务逻辑；
- 不改变未授权发送者的静默行为；
- 不让 Reaction 失败影响最终文字回复；
- 不扩大飞书写入或通知权限边界。

### 缺失的 success signal

计划没有定义：

- ACK 延迟从哪个时点开始计算：Feishu `create_time`、SDK callback、queue submit，还是 worker dequeue；
- 健康依赖下的 P50/P95/P99 目标；
- 上一条消息正在执行 Copilot 时，下一条消息是否仍必须满足目标；
- 飞书 Reaction API 超时/限流时，是允许快速放弃还是必须重试；
- 重复事件、关闭过程、queue full 时的可接受行为。

因此当前计划不能客观判断“修复成功”。

## 3. Assumptions tested

| Assumption | Review 结果 |
|---|---|
| 把 Reaction 移到当前 worker 开头即可解决响应慢 | 仅对没有前序积压的第一条消息成立；并发/积压时不成立 |
| fast preflight 可以安全地在 transport 内做 allowlist 判断 | 未成立；allowlist/idempotency 当前由 Assistant/Control 边界拥有 |
| 独立 ACK worker 自然能提供快速 ACK | 不成立；当前 Reaction HTTP 最多 3 次、单次 20 秒，ACK lane 本身仍可队头阻塞 |
| Reaction 的现有同步返回契约可以自然适配异步提前发送 | 未成立；缺少 send-once ownership、状态汇合和 duplicate suppression 设计 |
| 增加几个耗时字段即可验证方案 | 不充分；缺 SLO、时钟边界、并发场景和 degraded dependency 验收 |
| 第二个 worker 应立即增加 | 未证实；没有并发 SLO 时可能是过度设计，但有并发 SLO 时又是必要条件 |

## 4. Special review lenses

- **Architecture boundary review**: 计划把 allowlist fast preflight 放到 `src.application.inbound.feishu_ws`，但项目文档明确 sender allowlist 和 message-id idempotency 属于 Assistant/Control；若 transport 复制判断，会形成双重 policy ownership。
- **Best-practice review**: ACK 是 best-effort、低延迟信号，通常需要独立且更紧的网络预算；复用通用 Feishu HTTP 的 20 秒 × 3 次重试会使 ACK 通道在依赖退化时失去意义。
- **Optimal-solution review**: “同 worker 提前发送”是最小 diff，但不能满足积压下的 prompt ACK；“直接加独立 worker”能覆盖并发，却在没有 SLO 和网络预算前可能做错并发模型。计划必须先锁定语义/SLO，再选最小满足方案。
- **Overengineering review**: 预先增加 ACK queue/worker、跨线程状态汇合和 shutdown protocol 可能超过当前需求；只有当 success signal 明确要求前序消息在运行时仍快速 ACK，才有足够证据支持。
- **Overcoupling review**: 如果让同步 `handle_feishu_ws_event()`、WS worker、ACK worker、Assistant policy 和 Reaction 状态 envelope 同时共享可变状态，局部时序修复会绑死 transport、Control 和测试。计划尚未定义这些边界。

## 5. Findings

### PR-01-未修复-高-同一 worker 内提前 Reaction 仍无法解决队头阻塞
- **状态**: accepted-candidate
- **位置**: “推荐方案：快速预检后先加表情，再执行重逻辑”；“只有观测到明显队列等待后，再拆独立 ACK 通道”
- **问题类型**: 并发恢复风险 / 非最优方案 / 成功标准缺失
- **当前写法**: 先在现有 worker 中把 Reaction 移到 `service.handle_inbound()` 之前，独立 ACK worker 作为后续优化。
- **反例/失败场景**: 消息 A 已从唯一 worker dequeue 并进入 30 秒 Copilot；5 秒后消息 B 入队。即使 Reaction 位于 handler 开头，B 仍要等待 A 剩余约 25 秒后才会被 dequeue，B 的表情仍然慢。
- **为什么有问题**: 计划把“单条空闲队列优化”描述为推荐根因修复，但已确认的系统结构是一个 queue、一个后台线程、整条事件串行处理。若用户观察发生在连续消息或前序长任务期间，该 slice 不会解决目标，只会让第一条消息看起来改善。
- **直接证据**:
  - `src/application/inbound/feishu_ws.py:278-279` 只有一个 queue 和一个 `om-feishu-ws-worker`；
  - `src/application/inbound/feishu_ws.py:294-306` worker 完整同步执行 `handle_feishu_ws_event()` 后才取下一条；
  - 当前 Copilot scene 在 `src/application/copilot/om_chat.scene.json:29-33` 允许 180 秒总预算。
- **影响**: 实施后仍可能收到“表情还是慢”的用户反馈；修复结论无法验收；随后被迫再做第二次并发改造。
- **建议改法和验证点**:
  1. 先明确 success signal 是否覆盖“前序消息仍在运行”的场景。
  2. 若不覆盖，在 plan 中明确本 slice 只解决 idle-queue latency，并把 queue backlog 标成已知上限，不宣称完整修复。
  3. 若覆盖，独立 ACK lane 必须进入当前 slice，而不是无指标的 future work。
  4. 加入阻塞测试：A 的 inbound 被 event 卡住时提交 B，断言 B 的 Reaction 在 A 释放前发生。
- **修复风险（中）**: 主要风险是选错并发模型；需要先锁定 SLO。
- **严重程度（高）**: 当前推荐路径是否满足用户目标的 blocker。

### PR-02-未修复-高-fast preflight 的 policy ownership 与项目架构边界冲突
- **状态**: accepted-candidate
- **位置**: “快速解析 sender/message_id -> 校验 sender allowlist -> 立即添加 reaction”
- **问题类型**: 架构边界 / 过度耦合 / 契约缺失
- **当前写法**: 在 Feishu WS transport 进入完整 inbound 前先做 sender allowlist 判断，以保持未授权发送者静默。
- **反例/失败场景**: 实现 Agent 为了最小改动，直接在 `feishu_ws.py` 解析 allowlist；之后 Assistant/Control 更新 sender normalization、missing-sender 或 tenant/channel policy，但 transport fast path 未同步。结果可能是 transport 先给最终会被 Control 拒绝的消息加表情，或把应该允许的消息静默丢弃。
- **为什么有问题**: 项目设计明确 `src.application.inbound` 应保持 thin，只提取 payload、处理渠道 receive/reply mechanics 和构建 transport request；sender allowlist 与 message-id idempotency 由 Assistant/Control 拥有。计划没有指定可复用的 authoritative preflight boundary，迫使实现 Agent复制 policy 或反向穿透 Assistant internals。
- **直接证据**:
  - `docs/ARCHITECTURE.md:119-142` 明确 transport/application 分离，并声明 allowlist/idempotency 属于 Assistant boundary；
  - `docs/INBOUND_CONTROL.md:14-20` 明确 Control owns sender allowlist and message-id idempotency；
  - `docs/INBOUND_CONTROL.md:81-84` 要求 channel adapter 不直接导入 Control/Copilot internals；
  - 当前 authoritative allowlist/idempotency 在 `src/application/assistant/inbound_service.py:43-70`。
- **影响**: policy 漂移、未授权可见性变化、跨层依赖、边界测试失败，或为一个 ACK 修复引入新的公共 preflight abstraction。
- **建议改法和验证点**:
  1. 先定义 Reaction 语义：是“transport 已收到”还是“Control 已接受”。
  2. 如果必须保持“仅 authorized sender 可见”，plan 必须指定一个 Assistant-owned、无业务执行副作用的最小 acceptance decision，并让 transport 只消费其结果；不要在 `feishu_ws.py` 重写 allowlist parser。
  3. 如果 CEO 接受 Reaction 只是 transport receipt，则明确授权改变当前静默边界，并单独评估安全影响；不能把它当实现细节。
  4. 增加 architecture guard 和跨渠道测试，证明 policy 只有一个 owner。
- **修复风险（中）**: 需要小心避免为了 preflight 造一个过宽的新服务层。
- **严重程度（高）**: 未收敛前不可直接交给实现 Agent。

### PR-03-未修复-高-ACK 沿用通用 Feishu 重试预算会让 ACK lane 自身再次队头阻塞
- **状态**: accepted-candidate
- **位置**: “立即添加 reaction”；“必要时使用独立 bounded ACK queue/worker”
- **问题类型**: 最佳实践偏离 / degraded dependency / 并发恢复风险
- **当前写法**: 调整 Reaction 调用时序，但继续复用现有 `add_message_reaction()` 和通用 `http_json()`。
- **反例/失败场景**: Feishu API 或网络短暂不可用。一个 Reaction 调用按默认策略最多进行 3 次、每次 20 秒，并 sleep 1 秒和 2 秒。单 worker 的 ACK lane 可被第一条失败请求占用约 63 秒，后续所有 ACK 继续排队；冷 token 获取还可能先消耗同类预算。
- **为什么有问题**: ACK 的价值是快速、best-effort 可见反馈；通用持久投递的重试策略不适合低延迟 ACK。仅拆线程而不拆网络预算，只是把原队头阻塞搬到新队列。
- **直接证据**:
  - `src/infrastructure/feishu_bot.py:54-83` Reaction 同步调用 `http_json_fn`；
  - `src/infrastructure/feishu_bitable.py:215-225` 默认 timeout 20 秒、3 attempts；
  - `src/infrastructure/feishu_bitable.py:317-329` 使用 1 秒、2 秒指数退避；
  - `src/infrastructure/feishu_bitable.py:334-387` token refresh 也是同步网络路径。
- **影响**: Feishu 退化时 ACK P95/P99 失控；ACK queue 堆积或满载；“独立 ACK worker”实现后仍不能满足低延迟目标。
- **建议改法和验证点**:
  1. 在 plan 中定义 ACK-specific delivery policy：总时间预算、attempt 数、超时后 drop/record 行为。
  2. Reaction 应保持 best-effort，不进入 durable reply outbox，也不阻断 inbound/reply。
  3. 用注入的慢/超时 `http_json_fn` 验证总预算，并测试第一条 ACK 超时后第二条不会长期饥饿。
  4. 不要为 ACK 引入新的通用 HTTP client；在现有函数上增加最小可选预算，或使用已有注入点。
- **修复风险（低到中）**: 修改面可以很小，但默认值选择必须与 SLO 一致。
- **严重程度（高）**: 低延迟方案在依赖退化时是否成立的 blocker。

### PR-04-未修复-中-异步提前发送后的 send-once ownership 和同步返回契约未定义
- **状态**: accepted-candidate
- **位置**: 最小修复与独立 ACK lane 的切换边界；`handle_feishu_ws_event()` 返回 `data.reaction`
- **问题类型**: 契约缺失 / 不可直接实施 / 过度耦合
- **当前写法**: Reaction 可能在 worker handler 前发送，也可能由未来 ACK worker 发送，但计划没有指定谁是唯一 sender，也没有说明原 handler 的 `reaction_status` 如何获得。
- **反例/失败场景**:
  - preflight 先发一次，`handle_feishu_ws_event()` 中现有 `_maybe_react()` 未禁用，再发第二次；
  - 为防重复直接删除 `_maybe_react()`，导致单元测试和直接调用 handler 时不再返回真实 Reaction 状态；
  - ACK worker 尚未完成时 handler 已返回，`data.reaction` 只能填 `queued`，改变现有 `sent/reaction_failed` 契约；
  - shutdown 时 ACK 已出队但状态未汇合，既无法确认发送，也无法安全重试。
- **为什么有问题**: 当前 `handle_feishu_ws_event()` 是同步可测试函数，Reaction 状态属于其 response envelope。把副作用提前或异步化会改变 ownership 和可观察契约，不能只靠移动一行代码解决。
- **直接证据**:
  - `src/application/inbound/feishu_ws.py:220-230` 同步发送 Reaction 并把状态放入 response；
  - `tests/test_inbound_feishu_ws.py:73-78` 断言 `reaction.reason == sent` 及调用参数；
  - `serve_feishu_ws()` 的 worker 当前忽略 handler 返回值，生产 transport 与直接 handler 测试已有不同消费方式。
- **影响**: 重复 Reaction、错误状态报告、测试为了贴实现而降级、shutdown 下出现无法解释的 partial completion。
- **建议改法和验证点**:
  1. plan 必须明确 send-once owner：同步 handler 或 ACK dispatcher，只能有一个。
  2. 明确两种入口的契约：直接 `handle_feishu_ws_event()` 是否继续同步发送；`serve_feishu_ws()` 是否使用一个内部 pre-acked handler 参数。
  3. 如果引入异步 ACK，状态枚举至少区分 `queued/sent/failed/dropped`，并明确哪些状态进入日志而非最终 inbound response。
  4. 测试同一 payload 在每个入口只调用一次 Reaction，并覆盖 stop/queue-full。
- **修复风险（中）**: 容易因兼容同步测试而引入跨线程状态汇合；应选择最小明确契约。
- **严重程度（中）**: 不一定造成安全事故，但当前计划不够 code-generation-ready。

### PR-05-未修复-高-没有可验收的延迟 SLO、时钟边界和失败路径测试矩阵
- **状态**: accepted-candidate
- **位置**: “加入结构化耗时日志”；验证方案
- **问题类型**: 测试缺口 / review 不可验收 / open question 未收敛
- **当前写法**: 建议记录若干耗时，并在必要时根据队列数据决定是否拆 ACK worker。
- **反例/失败场景**: 实现后日志显示 `reaction_ms=200`，但用户仍等待 20 秒，因为 19.8 秒发生在 queue wait；或者以 worker dequeue 为起点计算，完全隐藏 SDK callback 到 dequeue 的等待。测试只断言 Reaction 调用发生，不证明它早于 inbound 或不被上一条消息阻塞。
- **为什么有问题**: “响应慢”是时间行为，必须用明确起点、终点和负载条件验收。当前计划没有 timing contract，也没有要求 monotonic clock、event timestamp 差异、queue wait 或 degraded API 测试。
- **直接证据**:
  - 当前 `feishu_ws.py` 成功路径没有 elapsed/queue-depth 日志，只记录 enqueue/process 异常；
  - 现有 `tests/test_inbound_feishu_ws.py` 覆盖功能正确性，但没有阻塞顺序、并发 backlog、queue full、Reaction timeout 或 latency assertions；
  - 本机审计库没有 Feishu 渠道记录，当前也缺生产基线可用于验收。
- **影响**: 实施 Agent 可以通过所有测试但没有改善真实体验；controller 无法判断是否需要 ACK lane；风险被推到生产反馈。
- **建议改法和验证点**:
  1. 计划先写出 SLO，例如健康依赖、空闲队列和前序消息运行中分别要求什么；具体数值由 owner 决定。
  2. 观测至少包含 `sdk_received_at/queue_wait_ms/preflight_ms/reaction_ms/inbound_ms/reply_ms/outbox_retry_ms`，耗时使用 monotonic clock。
  3. 测试矩阵覆盖：idle、前序 inbound blocked、unauthorized、malformed、duplicate、Reaction timeout/rate-limit、queue full、shutdown。
  4. 验收不能只看单元测试；在 dry-run/fake Reaction adapter 下做可重复时序测试，不调用真实飞书。
- **修复风险（低）**: 主要是完善 plan 和测试，不要求先做生产埋点系统。
- **严重程度（高）**: 没有它无法证明用户目标已达成。

## 6. Open Questions

进入 implementation 前必须收敛：

1. Reaction 的正式语义是“transport 已收到”还是“Control 已接受并授权”？
2. 未授权 sender 是否必须继续完全静默，包括不出现 Reaction？当前行为是必须静默。
3. 成功标准是否要求：上一条 Copilot 仍在执行时，下一条消息也快速出现 Reaction？
4. 健康依赖下 ACK 的目标 P50/P95 是多少？从 SDK callback 还是 Feishu event `create_time` 计时？
5. Reaction API 退化时允许几次尝试、总预算多少、超时后是否直接 drop？
6. 直接调用 `handle_feishu_ws_event()` 的同步 Reaction 契约是否需要兼容？
7. 重复 Feishu event 是重发 Reaction、返回已有状态，还是只记录 duplicate？
8. ACK queue 满和服务 shutdown 时，允许 drop 还是需要 drain？由于 Reaction 是装饰性信号，倾向明确允许 drop，而不是引入 durable state。

## 7. Residual Risks 与跟踪建议

| Residual risk | 建议跟踪位置 |
|---|---|
| Feishu API 自身成功响应后客户端 UI 仍延迟显示 | 结构化日志中保留 API completion 时间；必要时单独做真实环境观测，不在本 slice 猜测 |
| SDK callback 调度或 reconnect 导致事件本身晚到 | 记录 event `create_time` 与本地 callback time，但不要把远端时钟差直接当本地 latency |
| 单 ACK worker 在异常网络下饥饿 | ACK-specific deadline + drop metric；若仍有吞吐压力再考虑极小固定并发，不做 unbounded thread-per-event |
| allowlist policy 在 fast path 漂移 | 保持 Assistant/Control 单一 ownership，并增加 architecture guard |
| Reaction 重复或 API 返回 already-exists 类结果 | 明确 duplicate policy，测试业务错误分类；不为装饰性 ACK增加持久状态机 |
| 增加日志泄漏 message/sender 标识 | 日志只记录 event/message hash 或既有安全标识，不写正文、token、secret |

## 8. 建议的计划修订顺序

在进入 `/execute` 前，把计划改成以下 code-generation-ready gates：

1. **ACK Contract**：定义语义、未授权静默、duplicate、best-effort、失败不阻断、是否兼容同步 handler。
2. **Latency Contract**：定义起点、P50/P95 目标，以及是否覆盖前序消息仍在运行的场景。
3. **Ownership Decision**：确定 authoritative acceptance decision 仍由 Assistant/Control 拥有，transport 不复制 allowlist policy。
4. **Architecture Choice**：
   - 若目标只覆盖 idle queue：同 worker 提前 Reaction，明确已知队头阻塞上限；
   - 若目标覆盖前序长任务：当前 slice 使用 bounded ACK lane，而不是 deferred follow-up。
5. **ACK Network Budget**：为 Reaction 定义短 deadline/attempt 策略，超时后 drop + metric，不进入 durable outbox。
6. **Send-once Contract**：明确同步 handler、serve worker、ACK dispatcher 的唯一发送 owner和 response/log 状态。
7. **Focused tests**：先写 blocked-A/B、unauthorized、timeout、duplicate、queue-full、shutdown 的时序测试，再改实现。
8. **Observability**：增加一条脱敏 stage timing 记录；验收使用 fake adapter，不发送真实飞书 Reaction。
9. **Rollout**：先在服务日志验证 queue wait 和 ACK latency；只有固定单并发 ACK lane 仍达不到目标时，才评估更高并发，避免提前设计线程池。

## 9. Final conclusion

**Conclusion: fail**

方向判断正确：Reaction 必须脱离完整 Assistant/Copilot 完成时点，且不能被历史 outbox retry 排在前面。但当前计划还不能安全交给 implementation agent，主要 blocker 是：

1. 推荐的同 worker reorder 无法解决已确认的队头阻塞；
2. fast preflight 没有 authoritative policy ownership，可能违反 Control 边界；
3. ACK 仍沿用最长约 63 秒的通用重试预算；
4. 异步化后的 send-once 和同步返回契约未定义；
5. 没有可验收的 SLO 和并发/退化测试矩阵。

修订上述 contract 后，方案可以保持很小：不要持久化 Reaction、不要引入通用事件框架、不要增加 unbounded concurrency，只实现满足明确 SLO 的最小 ACK lane。
