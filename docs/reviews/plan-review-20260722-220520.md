# Plan Review — Close Advice Decision Safety Boundaries

## Review target

- **Plan**: `docs/gateflow/close-advice-safety-boundaries-plan-20260722.md`
- **Reviewed baseline**: `feature/option-notification-experience@58ce2a90`
- **Review mode**: adversarial implementation-plan review
- **Scope**: fee authority/net economics, expiration lifecycle routing, manual-review projection, public output, Daily Decision Brief materiality, and validation coverage
- **Excluded**: implementation, production/config/state changes, threshold calibration, order execution, release/deployment

## Assumptions checked

- Close Advice remains advisory and must not write trade, lot, broker, Feishu, or notification state.
- The shared fee calculator is used outside Close Advice and therefore has a wider compatibility surface.
- `close_advice.txt` is appended to the account notification text by the normal account run.
- quote acquisition has more than one path: required-data coverage fetch, fallback OpenD fetch, event/short-vol enrichment, and coverage classification.
- Daily Decision Brief action identity already includes `action_type`, but generic non-opening action diffing does not compare metrics/reason evidence.
- Current user-owned renderer and renderer-test changes must remain untouched during this plan gate.

## Findings

### PR-01 — Major — The plan simultaneously excludes notification behavior and requires changes that will alter notification delivery

**Evidence**

- The plan's out-of-scope list says notifications are excluded.
- S3 requires an explicit review selector and a new Close Advice “人工复核” section in rendered text.
- `src/application/account_run.py:697-700` appends any non-empty `close_advice.txt` to the account message.
- S3 also maps review rows to P0/P1 `state=active`; `domain/domain/daily_decision_brief.py:502-517` makes a newly active P0/P1 non-opening action a material change.

**Why material**

The plan does not tell an implementer whether a manual review should be operator-visible only in read artifacts, or should enter the existing delivery path. Either interpretation can satisfy some plan language while violating another. This is a public product/safety decision, not an implementation detail.

**Required plan fix**

Choose one behavior explicitly. Recommended decision: notification classification/rendering is in scope, because an active manual review is intended to reach the operator; live send/canary/release remains out of scope and requires later approval. State that `close_advice.txt` will contain a separate review section and therefore changes post-release notification content, while implementation validation must use deterministic no-send tests only.

### PR-02 — Major — Filtering only `_build_position_fetch_specs` does not guarantee that expired lots make no quote/data request

**Evidence**

- S2 says to exclude expired rows from quote fetch specs.
- `src/application/close_advice_runner.py:2386-2415` passes the full `positions` list through required-data coverage, quote loading/classification, fallback OpenD fetching, and event snapshot enrichment.
- `_build_position_fetch_specs()` covers the first required-data path, but `_fetch_missing_quotes_via_opend()` and `_merge_event_snapshot_for_short_vol_positions()` receive positions independently.

**Why material**

The success signal promises no quote request for expired-open rows, but the prescribed code change only blocks one of multiple acquisition paths. An implementation could pass the specified test narrowly and still issue fallback/event requests.

**Required plan fix**

Resolve lifecycle once at the start of `run_close_advice`, split `all_positions` from `quote_required_positions`, and pass only the latter into every coverage/fetch/enrichment path. Continue iterating over all positions to build final rows. Require gateway assertions across both required-data and fallback OpenD paths, plus event enrichment.

### PR-03 — Major — The shared currency behavior change is broader than the Close Advice work unit

**Evidence**

- S1 says `calc_futu_option_fee` should reject unsupported non-empty currencies.
- Current `domain/domain/fee_calc.py:102-123` defaults everything except normalized HKD to the US calculation.
- The facade is called by assigned-stock economics, sell-put, sell-call, and Combo Yield helpers in addition to Close Advice.
- The plan otherwise promises facade compatibility and a narrow safety fix.

**Why material**

Changing exception behavior at the shared facade can alter unrelated scanner/candidate flows and expand the review surface without being necessary to make Close Advice fail closed.

**Required plan fix**

Keep the shared function signature and routing compatibility in this work unit. Validate Close Advice's position broker and normalized currency before invoking the fee facade: broker must normalize to `富途`, currency must be `USD` or `HKD`. Emit `unsupported_broker`, `unsupported_currency`, or `unavailable` at the Close Advice boundary. A strict shared facade can be a separate contract change.

### PR-04 — Major — Fee status semantics for non-actionable rows would discard useful calibration evidence

**Evidence**

- S1 says non-close holds should use `fee_calc_status=not_required` if no close estimate is needed.
- Current `src/application/close_advice_runner.py:1445-1495` uses `buy_to_close_cost` as one component of close-calibration completeness even when the current tier is a hold.
- The plan's strategy objective includes preserving evidence and only changing the final decision when fee failure affects an otherwise-actionable close.

**Why material**

Skipping fee estimation for all holds would make calibration less complete and change unrelated observation data. Conversely, failing every hold on fee unavailability would create noise. The desired rule is neither of those.

**Required plan fix**

Attempt fee estimation for every active priced row with supported Futu/currency inputs. Preserve the status and estimate for calibration. Fee unavailability changes the decision only when the pre-fee exit state proposes a close; an existing hold remains a hold with unavailable fee evidence. Reserve `not_required` for lifecycle routes where no close economics are evaluated.

### PR-05 — Major — Review evidence transitions are required by tests but not specified in the diff algorithm

**Evidence**

- S3 requires a review reason/lifecycle transition to be material.
- `action_type` is part of the stable action ID in `domain/domain/daily_decision_brief.py:46-59`, so `review_position` itself is distinguishable.
- For an existing non-opening action, `domain/domain/daily_decision_brief.py:619-672` compares priority and state but not reason, lifecycle, willingness, evaluation status, or metrics.

**Why material**

Two P0 `review_position` actions for the same lot can change from thesis revocation to expired reconciliation without producing a material diff. A test request alone is not code-generation-ready guidance.

**Required plan fix**

Define a review-only evidence fingerprint over stable fields: `manual_review_reason_type`, `position_lifecycle_state`, `continued_willingness`, `continued_willingness_source`, `evaluation_status`, and `quote_status`. Do not put these fields into `action_id`. When the fingerprint changes for an existing active P0/P1 review, emit a material `review_evidence_changed`; ignore volatile price metrics for repeat-notification purposes.

### PR-06 — Moderate — The business-date authority is described but not concretely wired

**Evidence**

- S2 requires one run business date but leaves its source conditional.
- Current `_calc_dte()` calls `expiration_business_today()` per row at `src/application/close_advice_runner.py:1039-1046` and can fall back to quote DTE.
- `run_close_advice()` has no explicit as-of-date parameter.

**Why material**

An implementation could still read the clock repeatedly or use quote DTE in fetch planning, recreating inconsistent lifecycle decisions around the date boundary.

**Required plan fix**

At the start of `run_close_advice()`, call `expiration_business_today()` exactly once and pass the resulting `business_date` into the lifecycle/DTE helper. Resolve DTE from canonical position expiration before quote access. Quote DTE may be retained as observability evidence but must not override lifecycle state. Tests should assert one date authority and ignore conflicting quote DTE.

## Open questions

1. Does the CEO want manual-review rows to enter normal post-release notification content? The recommended plan decision is yes, because otherwise P0/P1 `active` has no reliable operator path; this must be highlighted at handoff before implementation.
2. Are the deployed accounts known to use Futu's ordinary fixed option-fee package and HK Tier 1 tariff? If not, implementation must stop rather than introduce a hidden config assumption.

## Residual risks after required fixes

- Official fee schedules can change again; dated constants are deterministic but require periodic audit.
- Midpoint pricing remains advisory rather than executable.
- New P0/P1 review delivery can increase notification volume; scenario tests can bound semantics but only a later no-send/no-write canary can measure real row counts.
- The renderer overlap remains an implementation blocker until ownership is resolved.

## Conclusion

**Fail pending plan revision.**

The work-unit framing and three-slice decomposition are sound, but the six findings above leave material ambiguity at notification, quote-fetch, shared-contract, calibration, diff, and date-authority boundaries. The plan should be amended and re-reviewed before implementation.
