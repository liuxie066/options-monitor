# Plan Review — True Diagonal Combo Yield Lifecycle

- **Gate**: plan review
- **Work unit**: 真正错期 Combo Yield 的端到端处理
- **Reviewed target**: `docs/gateflow/diagonal-combo-yield-plan-20260718-130000.md`
- **Scope**: opening config/metrics, trade-intake identity, lifecycle inventory, assignment lineage, Close Advice synthesis, rollout/compatibility
- **Artifact path**: docs/reviews/plan-review-20260718-130142.md
- **Current gate / next entry point**: `fix`

## Assumptions Tested

1. Option-position context has enough canonical facts to reconstruct partial assignment and assigned-stock inventory.
2. “Explicit durable strategy_group_id required” is actionable from the opening candidate through broker trade intake.
3. Group-level Close Advice can consume the proposed lifecycle truth table without querying ledger internals or inventing stock state.
4. Additive config defaults preserve same-expiry runtime behavior.
5. Diagonal ranking can exclude terminal metrics without silently treating nulls as favorable zeros.
6. Multiple partial lots can be aggregated without selecting an arbitrary companion leg.

## Findings

### PR-1-未修复-高-计划让 Close Advice 使用其输入契约中不存在的 assignment/assigned-stock facts
- **位置**: §4.4、§4.6、Slice S2/S3/S4
- **问题类型**: 架构边界 / 契约缺失 / 状态机漏洞 / 不可直接实施
- **当前写法**: S2 要把 `combo_yield_groups` 加到 option-position context；S3 再把 assigned-stock quantities 合入 inventory；S4 truth table 直接区分 `assigned_stock_with_residual_call`。
- **反例/失败场景**: Put 部分 assignment 1 张、仍 open 1 张，同时 Call open 2 张。`positions/context_builder.build_context(records, ...)` 当前只接收 projected option records，不接收 trade events 或 assigned-stock report。PositionLot 聚合只保留 close event IDs/最后 close fields，无法从一条 lot snapshot可靠拆分“1 张 assignment + 其它普通 close”，也没有 assigned-stock remaining shares。因此 Close Advice 无法证明 assigned stock 是否存在或剩余多少。
- **为什么有问题**: 计划把完整生命周期事实、option risk context 和 assigned-stock reporting 三个不同 source-of-truth 混成一个未定义输入，implementation agent 必须重新决定是否扩展 pipeline、重复查询 ledger、还是猜测 close_type。
- **直接证据**: `src/application/positions/context_builder.py:80-85` 仅接收 `records`；输出只含 open option positions。`domain/domain/ledger/lots.py:48-59` 聚合 contracts/close event ids，不记录每种 close event 的数量。Assigned-stock lots 由 `src/application/positions/reporting.py:1733+` 从 assignment events 单独派生。
- **影响**: partial assignment 被误分类、Close Advice 虚构 stock handoff、跨层查询、review 无法验收。
- **建议改法和验证点**:
  1. 将 lifecycle inventory 明确拆成两个 projection：`option_group_inventory`（position snapshots，可供 Close Advice）与 `full_group_lifecycle`（trade events + assigned-stock lots，仅 reporting/analysis）。
  2. Close Advice truth table只依赖 option inventory；Put 已结束 + Call open 统一为 `residual_call`，不得声明 assigned stock。Assigned-stock + Call 组合语义只在 full lifecycle report 中输出。
  3. 若坚持 Close Advice 显示 assigned stock，则 plan 必须明确扩展 context builder 的输入和 pipeline call path，传入 canonical trade events/assigned-stock rows，并覆盖 partial event tests；不能从 last close_type 推断。
- **修复风险（中）**: 缩窄 Close Advice 输入最安全。
- **严重程度（高）**: 当前计划不可直接实施。

### PR-2-未修复-高-explicit group identity 没有定义从候选到 intake 的生产者和交接契约
- **位置**: §4.2、§4.3、Slice S1/S2、Residual Risk 3
- **问题类型**: 契约缺失 / 恢复风险 / 不可直接实施
- **当前写法**: diagonal fill 必须携带 explicit `strategy_group_id`，但 candidate/report schema 不生成该字段，broker intake 也没有将候选 intent 写入 fill payload 的现有通路；同时计划把这个缺口归为后续 work unit。
- **反例/失败场景**: 用户按 diagonal candidate 在券商下两张独立订单。真实 broker fill raw payload没有 OM 的 `strategy_group_id`。Call-first 和 Put-first 都会按新规则 fail closed；系统能够筛选 diagonal，却无法把实际开仓登记为 diagonal group，所谓端到端处理只存在于手工构造测试 payload。
- **为什么有问题**: “明确 fail closed”可以是安全 fallback，但计划的成功信号同时声称 opening candidate → trade intake end-to-end。没有 identity producer/hand-off，两个 contract 断裂。
- **直接证据**: 当前 pair row只输出合约/经济字段；`src/application/trades/resolver.py` 只从 deal raw payload/companion lot推断。现有 broker group ID以单腿 expiry构造，无法表达两 expiry。Plan §9 又承认 broker payload不能自动携带 intent。
- **影响**: 功能不可实际使用、restart/fill-order tests只验证人工注入、交付声明失真。
- **建议改法和验证点**:
  1. Candidate row生成稳定 `strategy_group_id`/`pair_fingerprint`，至少由 canonical account、symbol、put contract、call contract构成并写入报告。
  2. 明确 v1 intake contract：结构化/manual open必须把 candidate group ID写入两腿 metadata；raw broker-only fills明确进入 unresolved review queue，不声称自动归组。
  3. 增加从 candidate row → manual/structured open preview → projected lot → restart resolver companion 的契约测试。如果当前 repo没有 order-intent写路径，success signal必须明确限定为“explicit-intent path end-to-end + broker-only fail closed”。
- **修复风险（中）**: 需要收窄 success wording并补 identity producer，而不是新建 order subsystem。
- **严重程度（高）**: 当前计划的核心 identity contract未闭环。

### PR-3-未修复-中-同一个 inventory_status 仍被写成互斥生命周期真相，且状态集合与 truth table 不一致
- **位置**: §4.4、§4.6
- **问题类型**: 状态机漏洞 / 契约缺失
- **当前写法**: §4.4 定义 `inventory_status: complete | residual_call | assigned_stock_with_residual_call | closed | review_required`，§4.6 又使用 `active_diagonal`, `missing_call`, `mixed_inventory`, `assigned_stock_only`。
- **反例/失败场景**: 一个 mixed state同时有 Put open、Put assigned、Call open 和 assigned stock。实现者必须猜哪个枚举优先，容易重建此前被 planreview否决的互斥 phase。
- **为什么有问题**: 目标明确要求 compositional inventory。状态可以是展示摘要，但必须由一套完整、稳定、同名 truth table派生，且不可替代独立 labels/quantities。
- **直接证据**: Plan 自身两个章节的枚举集合不一致；repo partial close已允许混合库存。
- **影响**: 不同模块产生不同 classification，Close Advice/report contract漂移。
- **建议改法和验证点**: 只保留 quantities + labels + issues为 canonical output；定义一个一致的 `summary_classification` 集合，并声明 mixed facts优先 `review_required`。把完整 derivation order写入 plan和测试矩阵。
- **修复风险（低）**: 文档/契约修订即可。
- **严重程度（中）**: 不修会导致跨模块语义分叉。

## Architecture Boundary Review

- 正确方向：domain pure projection、ledger/event source-of-truth、leg-first/group-second、assigned-stock execution独立。
- 阻断项：plan尚未决定 Close Advice 如何合法获得 assigned-stock事实；不能让 runner自己查询 reporting/ledger internals。

## Best-practice Review

- 明确 fail-closed是正确做法。
- 但 durable identity 必须有 producer、transport、consumer、restart reconstruction 四段完整 contract；当前仅定义 consumer。

## Optimal-solution Review

最实际的修复不是扩建 order-intent subsystem，而是：

1. Candidate输出稳定 pair/group fingerprint；
2. structured/manual path显式携带它并完成真正 end-to-end；
3. raw broker-only path fail closed并进入 review diagnostics；
4. option Close Advice仅消费 option inventory；assigned-stock + Call语义由 event-based lifecycle report负责。

## Overengineering Review

若为让 Close Advice知道 assigned stock而把 monthly reporting/event queries嵌进 runner，会过度耦合。缩窄 runner输入并把完整 lifecycle留在 reporting projection更小、更安全。

## Overcoupling Review

当前 plan把 context builder、assigned-stock reporting、Close Advice绑定到同一未定义 inventory。应共享纯 domain classifier，但由两个 adapter分别提供不同证据等级，不能假装 inputs相同。
