## Findings

### 1-未修复-中-完整 exercise/assignment 的 component-sum 不变量在极大 contracts 下可被 float 求和静默破坏
- **入口/函数**: `calc_futu_hk_terminal_fee()` -> 完整结果分支 `amount = round(sum(effective_components.values()), 6)`
- **文件(行号)**: `domain/domain/fee_calc.py:399-419`（完整分支）；plan 合同条款 "a complete result obeys `amount == round(sum(components.values()), 6)`"
- **输入场景**: 严格合法的输入（正整数 contracts、正有限 price/shares、完整 plan），但 contracts 极大，例如 `exercise` + `contracts=10**16` + commission-free plan
- **实际分支**: 所有严格校验通过 → 完整分支 → `exercise_fee = 2.0 * 10**16`（精确 float），但 `sum()` 按字典序累加，小额 component（platform_fee=15 等）被 float 吸收
- **预期行为**: 按 plan 的显式合同，任何 complete 结果都必须满足 `amount == round(sum(components.values()), 6)`；被断言为不变量的等式不应对合法输入失效
- **实际行为**: `amount = 2e16`（round 后），而 `round(sum(components.values()), 6) = 2.0000000000000064e16`，两者相差 6400 万 HKD 的表示值；合同不变量被违反。实跑复现（见下）
- **直接证据**: `fee_calc.py:381-389`（exercise_fee 进入 estimated_components），`fee_calc.py:410-419`（`effective_components = dict(estimated_components)`、`amount = round(sum(...), 6)` 与 components 同源但 round 时机不同导致不一致）；实跑输出：`f("exercise", order_price=450.0, shares=100, contracts=10**16, account_fee_plan=commission_free_plan)` → `complete=True, amount=2e16, components.exercise_fee=2e16, amount != round(sum(components.values()),6)`（返回 True 的等式检查失败）
- **影响**: 合同级不一致而非现实资金风险：真实 contracts 数量级（个位到数百）下 float 完全精确，两个 consumer 也不会传入 1e16；但 v1 合同把该等式写成无条件不变量，测试 `_assert_terminal_result_contract` 又把它固化为每次断言，任何未来依赖该不变量做校验/对账的下游会在极端输入上得到自相矛盾的 artifact
- **建议改法和验证点**: 最小修复是二选一：(a) 把 `amount` 直接定义为 `round(sum(effective_components.values()), 6)` 并用同一个已 round 的值回填语义——即 amount 就是 sum 的 round（当前两者不同源于 `2.0 * 10**16` 在 estimated_components 阶段已 round 成 `2e16`，而 sum 用未 round 的小额项；统一为先 sum 后 round 一次即可消除分歧）；或 (b) 在完整分支加 `contracts` 的实际上限校验（例如 `<= 10**9`，超出则 fail closed `stock_fee_inputs_incomplete`），把不变量定义域收紧到 float 精确区。验证点：对 (a) 断言所有组合（assignment/exercise × 两种 plan）`amount == round(sum(components.values()), 6)` 在 1e16 边界成立；对 (b) 断言超限 contracts fail closed
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 2-未修复-低-plan `platform_fee` 接受任意可转 float 的字符串，与"finite non-negative"校验的严格度不一致
- **入口/函数**: `calc_futu_hk_terminal_fee()` -> plan 校验 `_finite_float(plan.get("platform_fee"))`
- **文件(行号)**: `domain/domain/fee_calc.py:341-352`；对照同函数内 `commission_free` 严格要求 `isinstance(..., bool)`
- **输入场景**: `account_fee_plan={"commission_free": False, "platform_fee": "15", "fee_plan_ref": "x"}`（字符串数值）
- **实际分支**: `_finite_float("15")` 返回 `15.0` → 三个 plan fact 全部通过 → 完整结果 `complete=True, basis=estimated`
- **预期行为**: plan 合同要求 "strict boolean `commission_free`, finite non-negative `platform_fee`, and non-empty `fee_plan_ref`"；在刻意设计的严格信任边界（普通 payload 不得解锁 completeness、类型错误即 missing）下，数值字段静默接受字符串 coercion 与该边界精神不一致
- **实际行为**: 字符串 `"15"` 被接受并解锁完整结果。实跑：`platform_fee str '15' -> complete=True, amount=79.215`
- **直接证据**: `_finite_float()`（`fee_calc.py:297-306`）只做 `float(value)` 转换 + isfinite，不拒绝 `isinstance(value, str)`；而同一 plan 内 `commission_free` 用 `isinstance(commission_free, bool)` 严格类型检查，两者严格度不对称
- **影响**: 仅局部严格性问题：未来 receipt owner 若传入字符串化数值会被静默接受而非 fail closed；当前 slice 两个 consumer 都不传 plan，无实际触发路径
- **建议改法和验证点**: 在 `_finite_float` 或 plan 校验处拒绝 `isinstance(value, str)`（与 bool 拒绝对称），或在 `missing_plan_facts` 判定前加 `isinstance(plan.get("platform_fee"), (int, float)) and not isinstance(..., bool)`。验证点：`platform_fee="15"` 应落入 `missing_plan_facts=["platform_fee"]`、`complete=False`
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低
