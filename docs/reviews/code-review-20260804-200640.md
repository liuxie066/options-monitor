### DR-S3-R2-01-未修复-高-显式空账户范围会静默回退到 `user1`

- **入口/函数**: `./om run tick --accounts ...` / runtime `accounts` -> `accounts_from_config()` -> `normalize_accounts()`
- **文件(行号)**: `src/application/multi_account_tick.py:115-120,193-197`; `src/application/account_config.py:53-87`; `src/application/config_validator.py:924-942`; `tests/test_account_config.py:6-31`
- **输入场景**: 自动任务通过 `--accounts "$OM_ACCOUNT"` 显式传入空环境变量，或 runtime config 明确包含 `accounts: []`、`accounts: [""]`、`accounts: [0]`、`accounts: [false]`。
- **实际分支**: CLI 将显式参数包装成 `{"accounts": args.accounts}`，但 `normalize_accounts()` 用 `str(item or "").strip()` 丢弃所有 falsey item；没有剩余账户时又启用 legacy fallback，返回 `['user1']`。配置校验器同样跳过这些 item，不把显式空 scope 判为账户错误。
- **预期行为**: 只有根本未提供 `accounts` 时才允许 legacy `user1` fallback；显式 CLI/config scope 为空、含空 item 或非字符串时应在 workspace、scheduler、provider 和账户状态之前 fail closed。
- **实际行为**: 操作员指定的账户范围被静默替换，后续链路可针对 `user1` 读取、计算和写状态，表面上却是一次合法运行。
- **直接证据**: 临时 probe 对 `[]`、`['']`、`[0]`、`[False]` 调用 `accounts_from_config({'accounts': value})`，四种输入全部得到 `['user1']`。现有测试只覆盖“字段缺失时 fallback”和“有效列表中忽略空串”，没有覆盖显式全空 scope。
- **影响**: 多账户生产任务可能运行错误账户，且不会留下“账户输入无效”的 typed failure；这是账户隔离边界上的高影响错误。
- **建议改法和验证点**: 区分字段缺失与显式输入；CLI override 使用 `fallback=()` 的严格解析，配置校验拒绝空列表、空 item 和非字符串 item，仅在 `accounts` key 缺失时保留 legacy fallback。新增上述四种输入和 `--accounts ""` 回归，断言 guard、scheduler、workspace、provider、prepared worker 和状态写入均未启动。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### DR-S3-R2-02-未修复-高-配置 authority 在阶段间漂移时仍会触发共享 I/O，最终 typed 错误又被降级为普通 pipeline failure

- **入口/函数**: `run_tick_account_execution()` -> `prepare_portfolio_contexts()` -> shared plan/prefetch；`run_one_account()` -> event prefetch -> `run_pipeline_script()` -> child config validation
- **文件(行号)**: `src/application/tick_account_execution.py:309-323,366-502,633-692`; `src/application/account_run.py:254-340,422-590`; `src/application/pipeline_runtime.py:94-123`; `domain/domain/engine/decision_engine.py:472-490`
- **输入场景 A**: 两个 config artifact 在 prepared worker 完成后被一致替换为另一份合法 JSON；manifest 仍携带 parent-retained 的原 config SHA。
- **实际分支 A**: parent 只在 prepared 前重验 config；prepared 返回后只比较 manifest 中的旧 SHA，不再验证 published bytes，随后仍把该账户纳入 cross-account union、Close Advice plan 和 required-data provider prefetch。到 AccountRun 入口才因 parent bytes mismatch 拒绝该账户。
- **输入场景 B**: 两个 artifact 在 `run_one_account()` 首次校验后、scan-pipeline child 校验前漂移。
- **实际分支 B**: parent 已创建 account output/state、写 metrics，并可执行 event provider 与 shared-state/audit 写入；child 随后正确拒绝 hash mismatch，但 AccountRun 只按 return code 映射为 `pipeline failed`、`ran_scan=True`，丢失 `ACCOUNT_CONFIG_*` typed reason。
- **预期行为**: 同一 authority generation 应贯穿 parent、prepared、shared planning、event 和 child；如果 published divergence 是 fatal，则异常账户必须在其后续 shared/provider/output 之前成为吸收态，且原 typed code 不得被 subprocess adapter抹平。
- **实际行为**: parent 一部分阶段信任 retained bytes，另一部分阶段要求 mutable path 仍相等，导致同一账户先参与 provider/shared side effect、后失败；最终 metrics 又错误声称已运行 scan。
- **直接证据**: 双账户临时 probe 在 fake prepare 返回前一致替换 `lx` 两份 config，得到 `plan_scopes=[['lx','sy']]`、`prefetch_calls=1`，最终 reasons 为 `['account_config_parent_bytes_mismatch','ok']`。另一 probe 在 event prefetch 内替换两份 config，child 得到 `ACCOUNT_CONFIG_HASH_MISMATCH`，但最终 `metrics_reason='pipeline failed'`、`ran_scan=True`，且此前已有 3 次 state write。
- **影响**: 无效账户消耗 provider budget、扩大共享 plan，并留下错误运行语义；健康账户虽可继续，但同一 run 的审计无法证明 config failure 在物质副作用前隔离。
- **建议改法和验证点**: 明确唯一 generation 规则：要么让 parent-retained canonical bytes 成为所有 parent/child consumer 的不可变输入，要么在每个外部副作用 barrier 前重验并过滤 divergence；不要继续混用两套准入语义。child 应输出结构化 config failure，AccountRun 保留 code、`ran_scan=False` 和零通知。新增 post-prepare 双账户 drift、post-AccountRun-validation drift、typed child failure 和 provider/state zero-call 测试。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### DR-S3-R2-03-未修复-高-Prepared context 只绑定可覆盖路径和自声明 hash，父子可消费不同持仓且 foreign-account payload 仍被接受

- **入口/函数**: `prepare_portfolio_contexts()` -> parent `load_prepared_portfolio_context()` -> cross-account union -> AccountRun -> pipeline `load_prepared_portfolio_context()`
- **文件(行号)**: `src/application/prepared_portfolio_context.py:214-346`; `src/application/tick_account_execution.py:388-455,667-669`; `src/infrastructure/external_services.py:137-143`; `src/application/pipeline_context.py:418-432`; `src/application/portfolio_context_service.py:40-74`; `tests/test_prepared_portfolio_context.py:74-136`
- **输入场景**: parent 已加载 ready context A 并据此构造 union；在 final pipeline 读取前，同一 run/account 下的 `portfolio_context.json` 与 manifest 被一起替换成 context B，保留同一 config SHA并重新计算 payload hash。另一反例是在 `lx` manifest 下放入明确声明 `filters.account=sy`、stock row `account=sy` 的 context。
- **实际分支**: producer 用 `atomic_write_json()` 覆盖固定文件名；parent 只保留 manifest path并传给 child。loader 校验 manifest 自己声明的 config SHA和 payload SHA，但不接收 parent-retained manifest/payload generation，也不校验 payload 的账户语义。
- **预期行为**: parent planning 与 final scan 必须消费同一不可变 prepared generation；ready payload 还必须绑定 resolved source account/holdings account，不能仅依赖目录名和 manifest account。
- **实际行为**: coherent replacement 在两个 consumer 处都合法；parent 可用 avg cost A 规划 Covered Call strike window，child 又用 avg cost/holdings B 扫描。显式 foreign-account payload 也会原样返回。
- **直接证据**: 临时 probe 先发布 `avg_cost=100` 并由 parent load，再完整替换 manifest+payload为 `avg_cost=999`，第二次 loader 同样成功，得到 `parent_avg_cost=100, child_avg_cost=999`。另一 probe 得到 `manifest_account=lx, payload_filter_account=sy, payload_row_account=sy`。现有测试只修改 payload而不更新 manifest，不能覆盖 coherent replacement。
- **影响**: required-data union/prefilter、最终候选和 Covered Call 可基于不同持仓事实，或直接混入另一账户的持仓/成本；config SHA仍相同，现有审计无法识别 split-brain。
- **建议改法和验证点**: 为 prepared 结果建立 parent-retained authority（canonical manifest bytes/hash、payload bytes/hash、run/account/config SHA与 resolved source identity），write-once/adopt 发布，并把 expected generation传到 child。prepared loader在解析后的 raw payload上执行 exact-account/source-account postcondition。外部持仓映射应绑定 resolved holdings account，不能简单假设它等于 OM label。新增 coherent swap、foreign/missing identity、same-run re-entry和 parent/child same-generation 回归。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### DR-S3-R2-04-未修复-高-安全目录链拒绝 symlink 后，config failure handler 仍可沿同一 symlink 向 workspace 外写 metrics

- **入口/函数**: config publish/load typed failure -> `_account_config_failure_outcome()` -> `state_repo.write_account_run_state()`
- **文件(行号)**: `src/application/tick_account_execution.py:778-843`; `domain/storage/paths.py:27-44`; `domain/storage/repositories/state_repo.py:123-125`; `src/application/tick_run_workspace.py:342-432`
- **输入场景**: workspace 初检之后、config publication/validation 或 failure projection 之前，`output_runs`、run/account 或 state ancestor 被替换成指向外部目录的 symlink；dir-fd config owner因此返回 typed unsafe/unavailable failure。
- **实际分支**: config owner 使用 `O_NOFOLLOW` 的 descriptor chain，能拒绝 unsafe ancestor；但 failure handler 随即调用通用 state repository。该 repository先用 `.resolve()` 跟随 symlink，再创建并写 `account_metrics.json`，没有 descriptor anchor 或 expected-root containment。
- **预期行为**: 一旦路径链已被判 unsafe，失败投影也不得通过该链写任何文件；最多写到独立、已锚定的安全 audit surface。
- **实际行为**: success path fail closed，但 error path又突破同一 run/account 边界。
- **直接证据**: 临时目录 probe 设置 `base/output_runs -> outside` 后直接进入 failure handler，稳定得到 `outside/run-r2/accounts/lx/state/account_metrics.json`。这是上一轮 symlink finding 在错误写路径上的残余窗口。
- **影响**: 损坏、遗留或并发替换的运行目录可把错误状态写到另一 run/account 或 runtime root 外；path-safety完成信号不成立。
- **建议改法和验证点**: failure metrics使用同一个 descriptor-anchored run-state writer并验证每个 ancestor，或在 unsafe-chain错误上完全跳过该文件写入。增加 workspace 后 swap、account/state ancestor symlink和 outside-zero-write测试；仍应保留内存 outcome/安全 audit中的 typed reason。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### DR-S3-R2-06-未修复-中-部分 prepared worker 启动失败会遗留已启动子进程并降级健康账户

- **入口/函数**: `prepare_portfolio_contexts()` worker spawn loop
- **文件(行号)**: `src/application/prepared_portfolio_context.py:120-201`; `src/application/tick_account_execution.py:366-387`; `tests/test_prepared_portfolio_context.py:139-218,257-282`
- **输入场景**: 双账户准备期间，第一个 `Popen` 已成功启动并可能正在读取 broker/holdings，第二个 `Popen` 因资源、executable或 OS error 抛异常。
- **实际分支**: spawn loop没有 per-account catch或函数级 process cleanup；异常直接退出 `TemporaryDirectory`，后续 timeout 的 terminate/kill/wait逻辑完全未运行。tick caller再把所有账户发布成普通 `portfolio_context_preparation_failed`，健康账户也失去 prepared context。
- **预期行为**: 已启动 child必须在所有 exit path被收割；单账户 spawn failure应形成该账户稳定 unavailable结果并允许健康 sibling继续，或明确执行全局取消并等待所有 child结束后再返回。
- **实际行为**: 第一个 child成为未收割进程，仍可能继续 provider I/O；其 result目录同时被清理，且一个局部 spawn错误扩散到全部账户。
- **直接证据**: 临时 fake-process probe让第二次 spawn抛 `OSError`，函数返回异常后第一进程状态为 `terminated=False, killed=False, waited=False`。现有测试覆盖 child timeout和单 worker invalid config，但没有覆盖 partial spawn。
- **影响**: provider I/O和子进程生命周期脱离本轮 barrier，健康账户被无谓降级；在资源故障下可能累积孤儿进程。
- **建议改法和验证点**: spawn逐账户捕获并写 typed unavailable，外层 `finally` 对所有未收割 child执行 terminate -> bounded wait -> kill -> wait；决定继续健康 sibling还是全局取消，并用测试固定。覆盖第一/第二账户 spawn failure、cleanup次数、健康 peer promotion和零 orphan。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 中
