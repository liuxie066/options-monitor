### 1-未修复-高-supersede 后原 pair 与替代 pair 都进入永久黑名单，已释放 lot 无法重新推理

- **入口/函数**: `supersede_post_trade_combo_pair()` -> 下一轮 `reconcile_combo_pair_inferences()` -> `_reconcile_with_repo()` -> `match_post_trade_combo_pairs()`
- **文件(行号)**: `src/application/ledger/combo_reconciliation.py:35-40, 319-444, 474-510`; `src/application/ledger/repository.py:2337-2392`; `docs/plans/post-trade-combo-reconciliation-v1-plan-20260731.md:322-334`
- **输入场景**: 同账户、同标的存在 1 个 Sell Put 与 2 个均满足硬约束的 Long Call；系统生成两个 ambiguous inference，用户先确认了错误的 Call，随后 sweep，再执行 supersede，希望仍 open 的 Put 与另一个 Call 重新成为可确认候选。
- **实际分支**: 确认后的 sweep 因已确认腿被排除，调用 `expire_stale_combo_pair_inferences()` 把共享 Put 的另一个未决 inference 标为 `expired_unresolved`；supersede 只把已确认 inference 改为 `superseded` 并 void adoption events。下一轮 reconcile 虽重新释放三个 lot，却把 `expired_unresolved` 和 `superseded` 的 inference ID 都放入 `forbidden_inference_ids`，domain matcher 因而不能重新产出原 pair 或替代 pair。
- **预期行为**: supersede 完成原子撤销后，仍 open 且满足条件的 lot 应重新进入全局推理；由“腿曾被确认占用”导致的临时失效替代项，不应与用户明确 reject 或 TTL 真过期共用永久禁止语义。
- **实际行为**: 纠错释放了 canonical membership，却没有恢复任何可确认 inference；用户无法通过现有 post-trade 推理流程把释放的 Put 与正确 Call 组成 Combo。
- **直接证据**: 临时 SQLite 反例的初始 inference 数为 2；确认后重新 sweep 为 0，另一个 inference 状态变为 `expired_unresolved`；supersede 后再次 reconcile 仍为 0，`waiting_for_counterpart` 为 3，存量两条 inference 分别为 `superseded` 与 `expired_unresolved`。当前测试只验证 supersede 能撤销 membership，没有覆盖 `confirm -> sweep -> supersede -> reconcile`。
- **影响**: 已确认错误组合的正式纠错流程无法完成文档承诺的重新推理，用户只能停留在三个独立 lot 或绕过新流程处理；这是 Combo correction 主路径的功能性阻断。
- **建议改法和验证点**: 区分 `proposal_expired`、用户 reject 与“因临时 confirmed claim 失活”的状态/原因；supersede 后只允许由该 claim 导致的替代 inference 重新派生或进入新 generation，同时保持用户 reject、真实 TTL 过期和同一错误确认不会被静默复活。增加最小回归：1 Put + 2 Call，确认错误项、执行一次 sweep、supersede、再次 reconcile，正确替代项必须重新出现且原错误确认不会自动恢复。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### 2-未修复-中-同日后续 candidate alert 覆盖早先 confirmed envelope，已投递的精确证据无法重放

- **入口/函数**: `prepare_daily_decision_brief_delivery()` -> `confirm_daily_decision_brief_delivery_v2()` -> 后续 candidate batch -> `read_combo_candidate_exposures()`
- **文件(行号)**: `src/application/daily_decision_brief_repository.py:417-447, 1333-1390`; `docs/plans/post-trade-combo-reconciliation-v1-plan-20260731.md:154-183`
- **输入场景**: 同一账户/市场/交易日先确认发送一个包含 Combo occurrence A 的 candidate alert；稍后新 revision 出现 occurrence B，系统准备并确认第二个不同 delivery key 的 candidate alert；随后成交 A 对应的两条腿并回放证据。
- **实际分支**: 准备第二个 candidate alert 时，若单槽 `day["candidate_delivery"]` 已 confirmed 且 delivery key 不同，代码先把 `existing` 置空，再用新 envelope 覆盖该槽。虽然每个 run 写过 `daily_decision_brief_delivery_plan.*.json`，`read_combo_candidate_exposures()` 只读取日状态中的 `fixed_reports` 和当前单个 `candidate_delivery`，不读取历史 run plan 或 append-only confirmation 记录。
- **预期行为**: 每个已经 provider-confirmed、digest 和 render context 均可验证的 frozen candidate delivery 都应保留可重放证据；后续批次不能改变早先 occurrence 的 `exact_delivered_candidate` 事实。
- **实际行为**: A 的 frozen Brief revision 仍可导出 exposure，但找不到其 confirmed envelope，`delivery_confirmed` 被降为 false；A 从 `exact_delivered_candidate` 退化成 `exact_live_candidate`，即使用户确实已经收到过该消息。
- **直接证据**: 写路径明确以新的 candidate envelope 覆盖 `day["candidate_delivery"]`；读路径只构造当前日状态中的 envelope 列表，并以该列表判断 revision/digest/exposure/occurrence 是否 confirmed。现有 rolling-candidate 测试只断言 coarse `alerted_candidates` 保留两项，没有验证两批精确 Combo exposure 的 delivery confirmation 都可重放。
- **影响**: 匹配证据等级会随同日后续通知发生非事实性倒退；在多解图中，字典序目标可能因此改变 proposal/ambiguity，审计也无法证明早先实际投递过的精确候选。
- **建议改法和验证点**: 为 candidate delivery 保留 append-only confirmed envelope 历史，或从现有 run-scoped plan/confirmation artifact 建立经过完整 schema、digest、transport-key 校验的只读历史索引；不要仅凭 coarse `alerted_candidates` 反推精确投递。新增同日两次不同 candidate alert 均 confirmed 的回归，确保两次各自的 occurrence/exposure 都持续为 `delivery_confirmed=true`。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 中

### 3-未修复-中-candidate alert 的实际渲染上限与 evidence selector 不一致，消息中的 Combo 可能未写入 render context

- **入口/函数**: `tick_notification_flow` -> `select_rendered_combo_candidate_rows()` -> `render_candidate_alert()` / `render_candidate_alert_card_markdown()` -> `prepare_daily_decision_brief_delivery()`
- **文件(行号)**: `src/application/tick_notification_flow.py:943-965, 978-1013`; `src/application/daily_decision_brief_renderer.py:225-292, 1811-1839`
- **输入场景**: `daily_limits.max_candidates_per_strategy` 配置为 1 或 2，而同一 candidate alert 的前三个新增 identity 中包含多条 Combo representative。
- **实际分支**: evidence selector 使用传入的 `daily_limits` 调 `_candidate_views()`，所以只选择每策略 1/2 条；真正的文本和卡片 renderer 却都强制把 `max_candidates_per_strategy` 改为默认 3。随后 delivery `render_context` 仅记录 selector 返回的 occurrence/exposure ID，而发送内容可实际展示 3 条。
- **预期行为**: 写入 envelope 的 occurrence/exposure 集必须与实际文本/卡片渲染选择完全一致，才能用 message digest 和 render context 证明用户看到的是哪一条精确候选。
- **实际行为**: 实际展示的第 2/3 条 Combo 没有进入 `candidate_occurrence_ids` / `candidate_exposure_ids`；即使 provider confirmed，也只能降级为未投递的 live evidence。
- **直接证据**: `render_candidate_alert*()` 在构建 view 前无条件覆盖 limit 为 `_DEFAULT_MAX_CANDIDATES`，而 `select_rendered_combo_candidate_rows()` 直接解析 caller limits；两者由同一 tick 分支依次调用并把 selector 结果写入 delivery render context。现有 Combo evidence 测试固定使用 limit 3，没有覆盖 1/2。
- **影响**: 配置允许的合法值会让 delivery evidence 与用户实际收到的消息不一致，破坏精确投递证据的完整性并改变后续匹配等级；消息本身仍可发送，因此常规通知测试不容易暴露该问题。
- **建议改法和验证点**: 抽取并复用唯一的 candidate-alert projection/selection 结果，由文本、卡片与 evidence context 同时消费；如果产品语义要求 candidate alert 永远展示 3 条，selector 也必须显式使用同一固定上限。为 limit=1、2、3 分别断言文本/卡片内 Combo keys 与 render context IDs 完全一一对应。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 4-未修复-中-runtime environment 被按 sweep 常量写入所有历史 lot，跨 OpenD 来源硬门实际永远相等

- **入口/函数**: trade intake/backfill 保存 `_trade_intake_source` -> listener `_run_combo_reconciliation()` -> `_ledger_lot_facts()` -> domain `_build_edge()`
- **文件(行号)**: `src/application/trades/auto_intake.py:952-989`; `src/application/trades/backfill.py:635-647`; `src/application/ledger/preflight.py:792-812`; `src/application/ledger/combo_reconciliation.py:545-640`; `domain/domain/combo_reconciliation.py:425-443`; `docs/plans/post-trade-combo-reconciliation-v1-plan-20260731.md:97-117`
- **输入场景**: 同一 ledger/account 中一个 open lot 来自 OpenD endpoint A，另一个来自 endpoint B，或 endpoint 配置在两笔成交之间发生轮换；两笔 trade event 的 immutable raw payload 都保存各自 `_trade_intake_source.opend_host/opend_port`。
- **实际分支**: listener 只根据当前 source 的 host/port 计算一个 `runtime_environment`；`_ledger_lot_facts()` 不读取各 open event 的 source context，而是把这个当前值复制给所有历史 lot。domain 虽检查 Put/Call 的 `runtime_environment` 相等，但两边一定是同一个注入常量。
- **预期行为**: 文档定义的 broker/runtime-environment 硬约束应基于每条 immutable open event 的来源事实；字段缺失或两条来源不一致时 fail closed。
- **实际行为**: 当前 runtime gate 是恒真条件，无法识别跨 endpoint lot；endpoint 轮换还会在每次 sweep 中把所有历史 lot 重新标成新的当前环境，从而允许生成跨来源 proposal。
- **直接证据**: push/backfill intake source context包含 host/port，open `TradeEvent.raw_payload` 原样保留；但 lot fact builder 在第 595 行直接使用函数参数，而不是 event raw payload，domain 第 433 行比较的正是这两个相同常量。当前 domain/application 测试也只给全部 lot 使用同一个 `"test"` environment。
- **影响**: 配置轮换或多 endpoint 共享 ledger 时，系统会把不满足已批准硬约束的两笔成交作为合法 pair 提示用户确认；虽然仍需用户确认，不会自动写 canonical identity，但 proposal 的“非常证据”边界已经失真。
- **建议改法和验证点**: 从每条 open event 的可信 `_trade_intake_source` 派生稳定 runtime environment，并对 legacy/missing/malformed provenance fail closed 或显式降级到不进入匹配图；若仓库架构另有“每 account 永远单一 endpoint”的强不变量，应在 intake/persistence 边界验证并持久化，而不是保留一个恒真的 lot-level gate。新增 endpoint A Put + endpoint B Call、endpoint 轮换和 legacy missing provenance 测试。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 中
