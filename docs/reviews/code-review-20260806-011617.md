### DR-01-已修复-高-未请求 RV 的正常空集仍会被 payload 边界拒绝
- **入口/函数**: `fetch_symbol_request()` -> `validate_required_data_payload_candidate()` -> `_validate_required_data_payload_candidate_impl()`
- **文件(行号)**: `src/application/opend_symbol_fetching.py:476,622-630,782-819`; `src/application/opend_symbol_outputs.py:165-184`
- **输入场景**: 一个合法 required-data 请求设置 `include_realized_volatility=False`；OpenD 完整返回目标到期日，所有合约被请求范围过滤掉，因此 scope 均为 `cache`/`fetched` 且代码集为空。
- **实际分支**: producer 把结果规范化为 `success_empty/no_contract_rows`，但因为请求未启用 RV，`rv_snapshot` 保持 `status=skipped, reason=not_requested`。payload validator 对所有 `success_empty` 无条件要求 RV 状态为 `not_applicable_no_contracts`。
- **预期行为**: 当 expected fetch contract 的 `require_realized_volatility` 为 false 时，已证明完整的 filtered-empty 结果应通过，RV 的 `skipped/not_requested` 与请求契约一致；只有要求 RV 的请求才需要 no-contract RV 证据。
- **实际行为**: validator 抛出 `internal_contract_error: success-empty required-data lacks no-contract RV evidence`，本 PRD 要接纳的正常空集仍被判非法。
- **直接证据**: producer 仅在 `request.include_realized_volatility` 为 true 时改写 RV snapshot（622-630），新增 empty normalization 不受该 flag 限制（782-801）；consumer 在读取 contract 的 RV authority 之前无条件检查固定 RV 状态（175-183）。新增 producer 测试使用默认 `include_realized_volatility=False`，但只断言 producer payload，没有把它送入 candidate validator，因此未覆盖真实闭环。
- **影响**: 合法无 RV 请求在 prefetch/finalization 边界失败，账户 required-data barrier 被阻断；正常空集瘦身只对部分请求生效。
- **建议改法和验证点**: 先从 validated expected contract 读取 `coverage_policy.require_realized_volatility`。为 true 时要求 `not_applicable_no_contracts`；为 false 时要求 producer 的未请求状态，或在 producer 统一产生一个与未请求/无合约均一致的明确状态。新增端到端测试，把无 RV filtered-empty producer payload 连同匹配 contract 交给 `validate_required_data_payload_candidate()`，并保留 require-RV=true 的回归。
- **修复结果**: payload validator 现按 expected contract 的 RV authority 校验 empty RV evidence；新增 require-RV false/true 两个闭环回归，均通过。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### DR-02-已修复-中-结构化 reason code 在真实 payload 路径仍把串数据和计划缺陷归为错误类别
- **入口/函数**: `validate_required_data_payload_candidate()` -> `_validate_required_data_payload_candidate_impl()` / `evaluate_required_data_frame_fetch_plan_debug()`
- **文件(行号)**: `src/application/opend_symbol_outputs.py:270-287,666-768`; `src/application/required_data_coverage.py:619-687,860-901`
- **输入场景**: 子请求 hash/symbol/underlier/type/expiration 与计划错配，或者非空 debug fetch plan 的 RV flag、side plan、数值声明等内部契约畸形。
- **实际分支**: payload 的 child validators 在 structured coverage evaluator 之前抛出无 reason prefix 的 `PositionAdviceSourceError`，外层 wrapper 将所有这类错误统一加成 `internal_contract_error`。对于直接 evaluator，旧布尔实现只返回 false，随后仅探测“是否缺 exact strike”；其他所有失败统一返回 `invalid_row_identity`。
- **预期行为**: 串请求、错 option type/expiration、wrong symbol/underlier 应稳定归为 `scope_identity_mismatch` 或 `invalid_row_identity`；计划 schema/hash/flag/count 的自相矛盾应归为 `internal_contract_error`。reason code 应由实际失败事实决定，而不是由抛错先后或一个 bool fallback 决定。
- **实际行为**: 同一类错配在 evaluator 和真实 payload 入口得到不同 reason；真实 payload 的 wrong side/expiration 被 blanket wrapper 标成内部契约错误，而 malformed plan 又可能被 evaluator 标成 row identity 错误。
- **直接证据**: child identity/binding/row checks 在 666-768 抛出的消息都没有 reason prefix，270-287 对所有未加前缀异常统一套 `internal_contract_error`。coverage evaluator 在 666-687 对旧 bool 的任意 false 仅区分 exact-missing 与 `invalid_row_identity`，而 860-901 的 exact probe 对非法 exact 声明还会静默返回 false。现有 output tests 只匹配 `child request` 文本，没有断言 reason code。
- **影响**: 校验仍会 fail closed，但运营诊断会把 OpenD/请求错配、行数据错配和内部契约故障混在一起，导致错误恢复方向和告警归因；这违背本 PRD 将四层失败拆开的主要可观测性目标。
- **建议改法和验证点**: 让 owning validator 直接返回/抛出 typed reason，而不是在最外层根据“是否已有前缀”兜底猜测；至少把 child request identity/binding/type/expiration 和 row identity 分支显式映射，并在调用旧 bool 前先做独立的 debug-plan contract validation。为 wrong hash、wrong symbol、wrong type、wrong expiration、malformed RV flag 和 malformed exact-strike schema 分别断言 reason code。
- **修复结果**: payload/child binding、scope 与 row identity 分支现由 owning validator 产生明确 reason；structured evaluator 在旧 bool 前校验 plan contract。新增 wrong hash/type/expiration 与 malformed RV/exact schema reason 回归，均通过。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 中
