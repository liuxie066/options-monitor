## Previous finding resolution

### PR-01 — resolved

计划已把候选身份从未定义的 `hash(...)` 改为版本化 canonical string：

```text
candidate:v1:<account>:<market>:<canonical_symbol>:<strategy_family>
```

并明确：

- 禁止 Python 内置 `hash()`；
- identity 必须跨进程、跨重启稳定；
- 组件先 canonicalize/validate，非法输入 fail closed；
- identities digest 使用现有 canonical digest helper，或标准库 SHA-256 + canonical JSON sorted list；
- 测试覆盖独立进程、不同 `PYTHONHASHSEED`、normalization、排序和 repository round-trip。

该修复消除了跨 cron 进程 candidate pending/alerted 失配和重复通知风险。

## Assumptions tested

1. **Cadence**：现有 timer 每 10 分钟唤醒；真实 pipeline 仅在 report targets 与有效 `HH:30` 的并集执行。
2. **Opening exception**：`09:30` 不扫，`09:40` 承担开盘后首次扫描与完整报告。
3. **No-op**：非目标 tick 不启动 pipeline、不写 revision/current、不发送或重试普通监控消息。
4. **Catch-up**：若目标 tick 缺失，现有 `cron_interval_min + 2` grace 可由下一 timer 唤醒补跑；若目标已处理则 no-op。
5. **Calendar**：HK 午休、非交易日、US DST/gates 和账户级 `last_run` 去重继续由 scheduler 单一边界处理。
6. **Capacity**：最短相邻目标间隔是 20 分钟；计划没有错误地只按 30 分钟评估。
7. **Snapshot authority**：只有 reliable success 推进 immutable revision/current；pipeline failure、blocked、malformed、no-op 不推进。
8. **Candidate retry**：pending 独立于相邻 snapshot diff，provider failure/no-send/quiet 后不会丢候选。
9. **Delivery ambiguity**：ambiguous envelope 冻结 key/revision/identity set/message hash；不通过新 key 绕过幂等。
10. **Fixed recovery**：14:00 failure 在 14:30 成功扫描后才有机会升级/重试，不再暗含 14:10 pipeline。
11. **Cross-day**：未确认普通 backlog 不自动跨交易日补发；ambiguous 保留给 operator。
12. **Migration**：v1 pointer 只按 immutable revision 证据迁移，normal tick 不隐式迁移。
13. **Query**：latest 读取 successful current，完全只读，不读取 last delivered pointer，不推进 delivery state。
14. **Architecture**：没有新增第二 scanner、sender、broker fetch、数据库、ranking authority 或频率配置。

## Architecture boundary review

- domain 拥有 candidate identity、eligible extraction 和纯通知决策；
- application scheduler 只生成 scan/report targets 和 DTO；
- repository 拥有 immutable revision、current、delivery v2 和 migration；
- notification flow 编排 persist/decide/render/send/confirm；
- provider adapter、candidate ranking、ledger、Close Advice 和 broker fetch 不被复制。

依赖方向符合项目边界，没有发现 domain 反向依赖 `src/` 或 notification 层重做策略权威的计划。

## Best-practice / optimal-solution review

- 复用现有 10 分钟 timer，而不是修改生产 timer 或增加候选 timer，是最小且可回滚的实现。
- `report_targets ∪ candidate_check_targets` 比完整 10 分钟扫描网格更符合当前低频需求，HK/US 预计分别约 12/14 次真实扫描。
- deterministic canonical identity 比 opaque process hash 更易审计、更适合持久化状态。
- pipeline failure 不覆盖 current，解决了“失败误报为正常无候选”的根因边界。
- migration dry-run 默认、生产迁移显式批准、等待自然调度点观察，符合 operations-sensitive 合同。

## Overengineering / overcoupling review

未发现需要删除的新抽象。以下新增状态均有当前需求支撑：

- `pending_candidates`：防止 provider failure 后候选丢失；
- `alerted_candidates`：实现同交易日去重；
- fixed report state：实现固定点确认与重试；
- run-scoped delivery plan：确认 message hash/revision/key，处理 ambiguous send；
- successful current：支持随时查询且不被失败覆盖。

半点没有新增配置键，避免为当前固定产品规则引入过早泛化。

## Open questions / execution gates

1. 候选身份粒度是否正式采用“账户 + 市场 + 标的 + 策略族”。
2. 默认“期权监控”是否聚合全部启用账户和市场。
3. 是否接受 force/manual 扫描只更新 successful current，不发送普通 fixed/candidate 通知，也不推进 alerted 状态。
4. 远端只读容量证据是否证明 pipeline P95、OpenD 限频和双账户运行能承受 20 分钟最短目标间隔。

## Residual risks

- 半点检查不是行情级实时；HK 午休跨段等待到下一个有效目标点。
- no-op tick 不重试普通 delivery；失败后额外等待到下一真实 scan target，换取更简单的一套状态机。
- provider 长时间故障可能形成多个 fixed backlog，恢复后出现延迟且连续的完整报告。
- fixed + half-hour revisions 增加磁盘占用；当前没有容量证据要求本 work unit 同时引入 retention。
- v1 state 无法恢复历史 fixed target，只能保守迁移有证据的 legacy confirmation/candidate identities。

## Conclusion

计划已达到可交给 implementation agent 的具体程度。开始 `/execute` 前，应先确认三个产品/操作决策，并完成远端只读容量基线；生产配置、迁移和真实发送仍需单独批准。
