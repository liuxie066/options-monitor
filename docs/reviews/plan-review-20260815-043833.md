## Findings

### PR-W1B-01-未修复-高-调用者提供的费用结果没有绑定 strike、multiplier 和合约数量
- **位置**: `Public contracts -> Expiry economics`
- **问题类型**: 契约缺失 / 最佳实践偏离
- **当前写法**: `calculate_expiry_efficiency()` 接收一个已算好的 `terminal_fee`，只验证 kind/currency/version/amount 等输出字段。
- **反例/失败场景**: 调用者用错误的 stock settlement price、错误 shares 或多张合约计算费用，再把同版本的完整 result 交给 W1B。result 的现有 schema 不含这些输入，W1B 无法发现它与本行 strike/multiplier/1-contract 口径不一致，却会产出可采纳净效率。
- **为什么有问题**: 当前 HK terminal-fee contract 的输出没有 input binding；仅验证 schedule version 不证明 fee amount 属于当前经济事实。净费用是资金效率的直接输入，错误会静默改变最终排序结论。
- **直接证据**: PR #157 的 `calc_futu_hk_terminal_fee()` 输出包含 kind/currency/source/schedule/amount/components 等，但不包含 `order_price`、`shares`、`contracts`；产品合同要求所有终态费用来自绑定版本的 calculator，且缺失时不得产出净效率。
- **影响**: 生成错误经济 PnL、LCB 和 adoption gate，review fixture 也无法证明费用与候选条款一致。
- **建议改法和验证点**: W1B 从 exact `account_fee_plan` 和当前经济事实直接调用 canonical `calc_futu_hk_terminal_fee()`：assignment 使用 `order_price=strike`、`shares=multiplier`、`contracts=1`，expired-worthless 使用同一 owner 的零费用分支。严格验证 fee-plan keys；完整性 false 时 fail closed。测试必须证明改变 strike/multiplier 会通过 calculator 改变费用，且调用者不能注入 amount。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR-W1B-02-未修复-中-计划把已确认的 current_tie_break level 排除在 variants 之外
- **位置**: `ExperimentSpec shapes -> variants`
- **问题类型**: 范围漂移 / 契约缺失
- **当前写法**: 非 baseline patch 只允许 `without_concentration | concentration_first`，明确拒绝 `current_tie_break`。
- **反例/失败场景**: 按批准的“baseline 与三个 ranking profiles”构造首期 research spec 时，包含 `current_tie_break` 的控制 arm 被 validator 拒绝；实现者被迫修改设计输入或跳过一组已确认 level。
- **为什么有问题**: W1A 已交付三值 profile，模块控制文档 W1B/W5 写的是 baseline 与全部 levels；W1B 没有授权缩窄实验 arms。baseline-equivalent control 可能无法通过正均值门，但这属于研究结果，不是 schema 拒绝理由。
- **直接证据**: 产品文档 §6.1 列出 `without_concentration`、`current_tie_break`、`concentration_first` 三个 level；技术/控制计划要求 baseline 和全部 levels。
- **影响**: 真实 spec 无法通过，W5 需返工 schema 或偏离已确认实验设计。
- **建议改法和验证点**: 非 baseline patch 允许 W1A 的全部 `SELL_PUT_RANKING_PROFILES`，仍要求 profile 唯一；baseline `{}` 保留生产封存顺序。增加 current-tie control 验证 fixture，并证明它的 paired delta 为零且不能成为正改善 leader。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### PR-W1B-03-未修复-中-仅为共享异常类型引入 economics/statistics 到完整 contracts 依赖
- **位置**: `Import boundary`、`Top1CoreContractError`
- **问题类型**: 过度耦合 / 过度设计
- **当前写法**: `economics.py` 和 `statistics.py` 都 import `contracts.py` 只为一个共享错误；`contracts.py` 又依赖 opening snapshot、ranking、fee 和 hashing owners。
- **反例/失败场景**: 仅计算一组日差值也必须加载整个 ExperimentSpec/ranking/snapshot contract 链。后续任一 spec owner import 调整都可能破坏独立统计函数，architecture guard 只能批准这条无业务必要的耦合。
- **为什么有问题**: 三个模块的结构错误并不需要统一捕获类型；稳定产品 reason code 已在函数结果中。为了一个错误类增加横向依赖违反本 work unit 的纯模块边界和最小依赖原则。
- **直接证据**: 计划明确写 `economics.py -> contracts.py only for the shared error`、`statistics.py -> contracts.py only for the shared error`；没有调用方需求证明需要统一异常层级。
- **影响**: 不必要的传递依赖、循环导入风险和更宽 architecture allowlist。
- **建议改法和验证点**: `Top1CoreContractError` 仅归 `contracts.py`；economics/statistics 对 malformed programmer input 使用本地 `ValueError`，对实验性证据问题继续返回稳定结果。architecture test 证明二者不 import contracts/ranking/opening snapshot。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### PR-W1B-04-未修复-中-ExperimentSpec 的 market 大小写与产品文档仍有两个真源
- **位置**: `ExperimentSpec shapes -> market`、`Documentation decision`
- **问题类型**: 公开契约缺失 / design document alignment
- **当前写法**: 计划要求 exact `market=HK`，但同时决定不修改产品文档；产品 JSON 示例仍是 `market=hk`。
- **反例/失败场景**: 工程师或后续 Agent 按产品文档生成 spec 得到 lowercase `hk`，严格 validator 拒绝；若实现者为迁就示例改成 lowercase，W1A point/projection 又使用 uppercase `HK`，跨模块绑定出现隐式转换。
- **为什么有问题**: 这是进入 canonical hash 前的公开值，不能留给实现者临场选择。W1A 已严格要求 `HK|US` 并与 opening snapshot 精确匹配。
- **直接证据**: 产品文档 §6.2 JSON 为 `"market": "hk"`；W1A `_validate_point_binding()` 只接受 `US|HK`；本计划选择 `HK` 却未安排设计真源修正。
- **影响**: spec 创建失败、hash 不一致或后续 seam 重复大小写转换。
- **建议改法和验证点**: 以现有 producer artifact 的 uppercase `HK` 为 canonical 值；把产品 JSON 示例同步为 `HK` 并在文档注明 account 才固定 lowercase。该单点文档修正加入 allowed files 和测试 fixture。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
