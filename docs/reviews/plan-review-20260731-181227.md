## Assumptions tested

1. A transaction-local repository read alone is insufficient unless claims, timing, legacy bridge ownership, effective allocations, relevant events/voids and competing cases are in the same decision closure.
2. A case-local lifecycle resolver cannot make reservation action safe when another case can target the same lot; live and snapshot paths require the same account arbitration graph.
3. Direct anchors need explicit multi-anchor, replay, claim and quantity rules; otherwise the implementation must invent behavior for overlap and duplicate evidence.
4. Current projected Combo members do not prove occurrence identity because `strategy_group_id` is mutable through adjust events; effective event history is required.
5. A membership hash is not stable without an explicit schema, hash preimage and canonical ordering, and external-account diagnostics must not become positive actionability evidence.
6. Preparing a close-reason decision before provider collection is unsafe unless every due-path writer compares the prepared generation inside its write transaction.
7. Snapshot v3 is not safe if any source publisher, input builder, reader, promotion replay or notification consumer can still accept `trusted + actionable + 64-char fingerprint` without strict schema/hash validation.
8. An incompatible nested snapshot cannot safely retain indistinguishable outer artifact paths for previous binaries; the minimum public envelopes and current pointer must be versioned together.
9. Intermediate additive resolver work can remain testable, but no partial v3 producer/consumer state is releasable.

## Special review lenses

### Architecture boundary review

No material finding. Repository ownership is limited to coherent raw reads; lifecycle and membership semantics live in pure application resolvers; the domain fingerprint module owns contract validation; writers alone own mutation and transaction-local preconditions. The v3 contract inventory now closes source, input, current, reader, promotion and notification boundaries without moving broker-source ownership.

### Best-practice review

No material finding. The plan uses fail-closed required-data semantics, versioned canonical hashes, immutable evidence ownership, dry-run/apply revalidation, typed case-data errors, transaction-local generation CAS, previous-version compatibility checks and adversarial concurrency tests.

### Optimal-solution review

No material finding. Keeping the old outer artifact versions would let a previous binary misidentify nested v3 bytes; versioning the minimum envelopes and current pointer is the safer path. Conversely, the plan does not add a new database, mutable migration state or a second lifecycle/group truth source.

### Overengineering review

No material finding. The account arbitration graph and effective group history are directly required by demonstrated counterexamples. New values are frozen/hashable views, not persistent entities. Unsupported multi-anchor bridges, multi-leg Combo generalization, automatic identity repair and cross-case batch transactions remain out of scope.

### Overcoupling review

No material finding. R1, R2 and R3 keep separate business owners and tests. Their only synchronized slice is the intentionally atomic public v3 cutover; additive resolver work precedes it, and old-path deletion follows it. This prevents schema skew without forcing lifecycle, Combo and due reconciliation into one shared framework.

## Residual risks and tracking destination

- **Previous-binary executable compatibility**: run the compatibility harness and controlled rollback checklist before release. If the previous binary cannot be exercised, the release gate remains manually blocked; this is not an implementation-plan blocker.
- **Temporary v3 availability gap**: after new code starts, old v2 artifacts are audit-only until a complete Account Run publishes v3 current. Track in rollout verification; never fallback to v2 bytes.
- **Existing invalid identity or retag history**: read paths fail closed, but correction remains a separately authorized operator work unit.
- **Legacy multi-anchor bridge**: remains review-only under bridge v1; track only if production inventory proves a real need for a new contract.
- **Malformed case repeat reporting**: remains deterministic and write-free but can recur each tick; a future suppress/ack design belongs in a separate issue.
- **Production facts**: this review does not establish counts or current state of production bridges, identities or due cases. Inventory/migration/apply require a separate read-first workflow and authorization.
