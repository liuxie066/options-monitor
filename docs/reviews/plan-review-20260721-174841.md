# Plan Review — 期权监控通知体验升级

- Review 时间：2026-07-21 17:48:41 Asia/Shanghai
- Reviewed target：`docs/plans/option-notification-experience-implementation-plan-20260721.md`
- 产品真源：`docs/OPTION_NOTIFICATION_EXPERIENCE_PRD.md`
- Review scope：scheduler 目标与去重、半点/固定点执行、delivery retry、状态迁移、字段传播、测试与 rollout
- Review posture：adversarial；本轮只检查计划并写 review artifact，不修改计划、不实施代码、不改生产配置、不触发通知

## Goal / non-goal / success signal

计划目标是复用现有 10 分钟 timer，在固定报告点和有效半点执行同一套 canonical pipeline；成功扫描更新唯一快照，随后选择固定完整报告、新增候选通知或静默。非目标包括第二套扫描器、第二套 sender、候选排名分叉和 broker 重复请求。

目标方向成立，但当前计划仍有会漏掉计划点或丢失最终固定报告的状态机缺口，尚不适合直接交给 implementation agent。

## Assumptions tested

1. 现有 scheduler 的去重水位是否代表“已处理 target”，而不是“pipeline 完成时间”。
2. catch-up 执行跨过下一 target 后是否会错误抑制下一批次。
3. `09:40 -> 10:00`、`15:30 -> 15:50` 的 20 分钟目标间隔，在 10 分钟 timer/catch-up 下是否仍安全。
4. no-op tick 完全不处理 delivery 时，`15:50` 最终报告能否在 provider 短暂失败后重试。
5. provider definite failure、ambiguous send、quiet/no-send 的 envelope 是否有明确的后续状态转换。
6. 新增 `scheduled_scan_target_market` 是否能穿过 scheduler normalization、domain DTO/view、account execution 和 notification flow。
7. 多账户 scheduler 水位是否仍保持 account isolation。
8. pipeline failure/no-op 是否被禁止推进 successful current。
9. pending candidate 是否能跨相邻成功快照保留，避免 provider failure 后候选丢失。
10. candidate identity 是否跨进程确定；当前版本化 canonical string 已解决上一轮 hash 风险。
11. v1 pointer 迁移是否只使用 immutable revision 证据，并保持 dry-run 默认。
12. 资金口径是否复用现有 `cash_by_currency - reliable cash_secured_total_by_ccy` 业务语义。
13. fixed/candidate/query 是否继续读取同一份结构化快照。
14. 计划是否引入第二 scanner、sender、database 或候选权威。

## Findings

### PR-01-未修复-高-scheduler 用完成时间去重会吞掉后续计划点
- **位置**: Plan 6.1、6.2、16.1；`src/application/scan_scheduler.py::mark_scheduler_accounts()`、`decide()`；`src/application/tick_account_execution.py::run_tick_account_execution()`
- **问题类型**: 状态机漏洞 / 并发恢复风险 / 契约缺失 / 测试缺口
- **当前写法**: 计划继续复用 account-scoped `last_run_utc_by_account` 做 target 去重，只新增 `scheduled_scan_target_market`，没有规定 scheduler 水位必须写“已处理的计划 target”。
- **反例/失败场景**: `09:40` tick 缺失，`09:50` 在 catch-up grace 内补跑 `09:40` target；pipeline 在 `10:00` 之后完成。现有 `mark_scheduler_accounts()` 把完成时刻写入 `last_run_utc_by_account`。下一次 scheduler 判断 `10:00` target 时使用 `last_run >= due_target`，因此把从未执行过的 `10:00` target 误判为已处理。`15:30` 补跑跨过 `15:50` 时同样可能直接吞掉收盘前完整报告。
- **为什么有问题**: 计划把相邻目标缩短到最少 20 分钟，同时保留 10 分钟 catch-up。真实可用执行间隔可能只剩约 10 分钟；P95 小于 20 分钟不能证明 target watermark 正确。资源指标不能替代状态身份。
- **直接证据**:
  - 当前 `mark_scheduler_accounts()` 在扫描结束后写 `datetime.now()` 到所有已运行账户的 `last_run_utc_by_account`；
  - `decide()` 以该值是否 `>= due_target_utc` 判定 target 已处理；
  - `run_tick_account_execution()` 只传账户列表，不传每账户实际处理的 scheduled target；
  - 计划测试只有普通 catch-up/去重，没有“上一 target 晚完成但下一 target 尚未执行”的反例。
- **影响**: 漏掉固定完整报告 / 漏掉半点候选检查 / next-run 状态失真 / 生产问题难以从 audit 还原。
- **建议改法和验证点**:
  - scheduler 去重必须以 per-account `processed_scan_target_utc` 或等价 target identity 为权威，不得用完成时间代替；
  - account execution 把 `account -> scheduled_scan_target_market` 显式传给 mark 边界；实际开始/完成时间如需观测，保存为独立字段；
  - 明确 legacy `last_run_utc_by_account` 的兼容读取/首次写入语义，避免隐式错误迁移；
  - 增加测试：09:40 在 09:50 catch-up、10:01 完成后，10:10 仍补跑 10:00 target；15:30 晚完成不得抑制 15:50；多账户各自 target 水位独立。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR-02-未修复-高-no-op tick 禁止 delivery retry 导致 15:50 最终报告只有一次发送机会
- **位置**: Plan 6.1、11.1、16.1、20 residual risk；PRD 7.2、13；fixed delivery retry 状态机
- **问题类型**: 状态机漏洞 / 恢复风险 / 产品契约冲突 / 测试缺口
- **当前写法**: 非 scan target 的 10 分钟 tick 完全 no-op，“不重试普通监控消息”；pending delivery 只等下一真实 scan target。未解决 backlog 跨交易日直接转 `expired_unconfirmed`。
- **反例/失败场景**: `15:50` pipeline 成功并准备最终完整报告，但 provider 返回 definite failure。`16:00` timer 唤醒时，因为 `15:50` target 已扫描，计划要求 no-op 且不得重试。当天没有后续真实 scan target；次日切换时该 fixed report 被标记 `expired_unconfirmed`。这份固定报告从未获得第二次发送机会。
- **为什么有问题**: PRD 要求 provider 确认成功前不得标记计划点已发送，并要求相同计划点重试不重复。计划当前把“不要额外扫描”错误扩展成“不要重试已经准备好的 delivery”，导致收盘前核心报告在瞬时 provider 故障下永久丢失。
- **直接证据**:
  - PRD 7.2 第 6、7 条要求 provider confirmed 和稳定重试；PRD 13 第 1、2、4 条要求失败不推进且同一固定点可幂等重试；
  - Plan 6.1 明确 no-op tick 不重试消息；
  - Plan 16.1 指定 15:50 后停止，没有 final-batch retry 场景；
  - Plan 11.2 的 backlog 优先级只会在下一轮通知 flow 被执行，但 15:50 后当天不存在下一真实 scan target。
- **影响**: 最终固定报告丢失 / 与“固定可预期”目标冲突 / provider 短暂故障被放大成整日不可恢复缺口。
- **建议改法和验证点**:
  - 分离“是否运行 pipeline”和“是否处理已准备 delivery”：非 target tick 仍不得扫描或产生新通知，但可在同交易日内重试已持久化的 pending/ambiguous envelope；
  - 最小方案可允许 `16:00` timer 执行 delivery-only retry，复用原 key、revision、candidate set 和 message hash，不请求 broker、不写新 snapshot；
  - 明确定义 definite failure 可否刷新 envelope：无新扫描时只能精确重试；后续成功扫描若允许换 revision/content，必须保留同 key 并重写 validated plan；ambiguous 始终冻结；
  - 增加测试：15:50 definite failure -> 16:00 delivery-only retry；15:50 ambiguous -> 16:00 exact envelope；retry 不启动 pipeline、不新增 revision、不改变 candidate diff。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR-03-未修复-中-新 scan target 字段会在现有 domain normalization 边界被丢弃
- **位置**: Plan 5 模块表、6.2 SchedulerDecision 合同；`domain/domain/tool_boundary.py`；`domain/domain/engine/decision_engine.py`
- **问题类型**: 架构边界 / 范围遗漏 / 不可直接实施 / 测试缺口
- **当前写法**: 计划新增 `scheduled_scan_target_market`，并笼统要求 `decision_engine.py` 和 scheduler propagation 透传，但模块表没有列出拥有 scheduler payload allowlist 的 `domain/domain/tool_boundary.py`，也没有明确 DTO schema 的 additive contract。
- **反例/失败场景**: implementation agent 只修改 `scan_scheduler.py` 和 `decision_engine.py`。`normalize_scheduler_decision_payload()` 当前只 allowlist `scheduled_target_market`，会静默删除新的 `scheduled_scan_target_market`。后续 account execution、target watermark、brief context 和 audit 收不到真实 scan target。
- **为什么有问题**: 该字段不仅用于展示；PR-01 的正确修复也依赖 per-account target identity。把它丢在 normalization 边界会让 scheduler 再次退回“用当前时间猜 target”。
- **直接证据**:
  - `domain/domain/tool_boundary.py::normalize_scheduler_decision_payload()` 使用显式字段 allowlist；
  - `SchedulerDecisionView` 当前只有 `should_run_scan / is_notify_window_open / reason`；
  - `AccountSchedulerDecisionView` 当前只有 `is_notify_window_open`；
  - Plan 模块表未列 `domain/domain/tool_boundary.py`，测试矩阵也没有 schema round-trip assertion。
- **影响**: 实施 Agent 跑偏 / 新字段静默丢失 / scheduler target 去重无法正确实现 / audit 不完整。
- **建议改法和验证点**:
  - 把 `domain/domain/tool_boundary.py`、相关 schema/DTO tests 和必要的 account scheduler view 加入明确修改范围；
  - 决定该字段是 scheduler decision v1 的 optional additive field，还是需要 schema version 升级，并写清兼容行为；
  - 增加完整 round-trip：raw scheduler payload -> normalize -> global DTO -> per-account DTO/view -> account request -> notification context，字段值保持不变；force/manual 时为 `None`。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

## Architecture boundary review

方向正确：candidate rank/filter 仍由 canonical domain owner 负责，repository 拥有 revision/current/delivery state，flow 负责 I/O 编排，renderer 只做用户投影，sender 不被复制。

但 PR-01/PR-03 显示 scheduler target identity 尚未形成一个完整的跨层合同：计划定义了字段，却没有定义 target watermark 的写 authority、schema normalization 和 account execution 写回边界。

## Best-practice review

- 固定调度系统应使用 scheduled occurrence identity 做幂等，而不是用任务完成时间推断 occurrence 是否已执行。
- 扫描 cadence 与 delivery retry cadence 可以分离；delivery-only retry 不等于第二套扫描器，也不应重新请求 broker 数据。
- provider ambiguous 状态必须冻结 envelope；definite failure 与 not-called 可以按明确合同重试，但不能由实现者自行猜测是否刷新内容。
- optional additive DTO 字段必须覆盖 normalization、validation、round-trip 和 mixed-version 行为。

## Optimal-solution review

“10 分钟 timer 唤醒 + fixed/half-hour pipeline”仍是比新增 timer 或完整 10 分钟扫描更合理的路径。最小安全修订不是增加第二个 scheduler，而是：

1. 用 scheduled target 做现有 scheduler 的 per-account 去重水位；
2. 允许现有 no-op timer 只处理已经持久化的 delivery retry；
3. 补齐一个 additive scheduler field 的既有 normalization 路径。

## Overengineering review

没有发现需要删除的 database、framework 或第二 sender。delivery v2、pending/alerted、run-scoped plan 都有 provider confirmation 和跨 tick 幂等需求支撑。

需要避免的过度修复是新建独立 delivery daemon。PR-02 可直接复用当前 10 分钟 tick，在 no-scan 分支做窄的 persisted-envelope retry。

## Overcoupling review

当前最大耦合风险是 `last_run_utc_by_account` 同时承担运行观测时间和 target 去重水位。应拆分语义，而不一定拆成新服务。actual start/completion 属于 observability；processed scheduled target 属于 scheduler state machine，两者不能共享一个模糊时间戳。

## Open questions

1. 现有 `last_run_utc_by_account` 是改为存 scheduled target，还是新增明确的 `last_processed_scan_target_utc_by_account` 并保留 completion observation？
2. production state 从旧 completion-time watermark 到 target watermark 如何首次切换，是否允许一次保守重复扫描？
3. 是否接受 `16:00` 作为 delivery-only retry 点，以保障 15:50 最终报告？
4. fixed provider definite failure 后，在下一成功扫描到来时是精确重试旧 envelope，还是允许同 key 更新到最新 revision/content？
5. 候选身份粒度是否正式采用“账户 + 市场 + 标的 + 策略族”？
6. 默认查询是否聚合全部启用账户和市场？
7. force/manual 是否保持只更新 successful current、不发送普通通知？

## Residual risks

- provider 长时间故障仍可能形成 fixed backlog；即使增加 delivery-only retry，也需要明确是否合并或按最早批次发送。
- HK 午休会扩大 wall-clock 候选发现延时，但符合有效市场目标点合同。
- fixed + half-hour revisions 会增加磁盘使用；当前仍没有证据要求本 work unit 同时引入 retention。
- v1 pointer 无 fixed target，迁移只能保守保存 legacy confirmation 和可验证候选身份。
- 远端 pipeline P95、OpenD 限频和双账户运行容量仍需 execute 前只读验证，但容量证据不能替代 PR-01 的状态身份修复。

## Final conclusion

**fail**

半点调度产品方向和大部分模块边界成立，但 PR-01 与 PR-02 会分别造成计划点被跳过、15:50 最终报告无法重试；PR-03 会让修复所需的新 target 字段在现有 normalization 边界被静默删除。应先修订计划，再进行一次 planreview。
