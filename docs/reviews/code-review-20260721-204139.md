## Findings

### 1-未修复-高-缺失 trigger 的请求仍默认 scheduled，绕过 manual no-send fail-safe

- **入口/函数**: `TickNotificationRequest` construction -> `run_tick_notification_flow()`; `build_tick_idempotency_context()` default normalization
- **文件(行号)**: `src/application/tick_notification_flow.py:74`; `src/application/tick_run_context.py:21-34`
- **输入场景**: 新的内部 caller、测试 harness 或兼容调用构造 `TickNotificationRequest` 时遗漏 `trigger_kind`，或直接调用 idempotency helper 时不提供 trigger。
- **实际分支**: dataclass 和 idempotency helper 都把缺失值默认成 `scheduled`；`run_tick_notification_flow()` 因此进入 Daily Brief preparation 和普通 provider delivery path。
- **预期行为**: 计划明确规定未知/缺失 trigger source 必须 fail-safe 为 manual no-send；只有显式、已分类的 `scheduled` 才拥有普通通知发送权。
- **实际行为**: 当前唯一 production caller 显式传值，但公共内部契约本身是 fail-open；任何漏传都会恢复 scheduled authority。
- **直接证据**: `TickNotificationRequest.trigger_kind: str = "scheduled"`；`_normalize_trigger_kind(value or "scheduled")`；runtime guard 仅判断值是否等于 `scheduled`。
- **影响**: 后续入口或兼容调用可在没有 scheduler provenance 的情况下自动发送普通通知，破坏本 Slice 的核心安全边界。
- **建议改法和验证点**: 将缺失/default trigger 统一为 `manual`，production scheduled caller继续显式传 `scheduled`；测试 request factory 必须显式声明 scheduled，并增加 omission/`None` 回归，证明不会 prepare/resolve provider。
- **修复风险**: 低
- **严重程度**: 高

### 2-未修复-高-terminal failure 的 idempotency 写入异常被静默吞掉，CLI 仍返回既定业务码

- **入口/函数**: multi-market failure -> `request.complete_tick_idempotency_fn(ok=False, status="unsupported_failed")` -> nested `complete_tick_idempotency()`
- **文件(行号)**: `src/application/tick_notification_flow.py:148-174`; `src/application/multi_account_tick.py:258-279`
- **输入场景**: 多市场请求已被判定为 unsupported，但写 `tick_execution` terminal record 时发生磁盘、权限或原子写异常。
- **实际分支**: nested completion closure 对所有异常执行裸 `except Exception: pass`；notification flow 随后返回 `2`，没有任何 idempotency error event，持久记录仍可能是 `in_progress`。
- **预期行为**: `unsupported_failed` 是计划定义的 terminal state；若无法持久化，不能静默声称 terminal transition 已完成，必须 fail closed 并留下明确错误证据。
- **实际行为**: run-end/last-run 显示业务失败，但 idempotency state machine 未完成且错误不可见；同进程重复调用可能把仍活跃 PID 的 `in_progress` 记录当普通 duplicate skip 返回 `0`。
- **直接证据**: completion closure 无条件吞掉 `_complete_tick_idempotency()` 异常；multi-market path不检查返回状态。
- **影响**: 失败重放不再 deterministic，可能把已知 unsupported 请求降级成成功 skip，并留下无法诊断的孤儿执行状态。
- **建议改法和验证点**: 保持现有 successful/skipped completion 的兼容 best-effort 行为，但当 `ok=False` 时记录 `TICK_IDEMPOTENCY_TERMINAL_WRITE_FAILED` 并重新抛出，让 CLI fail closed；新增测试模拟 terminal write exception，证明不会静默返回 `2`/`0`，且有 error event。
- **修复风险**: 低
- **严重程度**: 高
