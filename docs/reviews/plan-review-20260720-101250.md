## Summary

第二轮的五项 finding 已经得到实质修复：远端 annotated/lightweight tag identity、semantic confidence、静态 Tool requirements、SemVer ownership 和 detached HEAD 行为都已收敛，方案的总体方向仍然正确。

第三轮仍发现 2 个高严重度和 3 个中严重度问题。最重要的问题是：`Unreleased` 中混合出现受支持和不受支持的非空分类时，当前规则会静默忽略未知内容并继续给出 patch/minor 推荐；另外 freshness digest 没有绑定 `remote_name` 或其解析出的 remote URL，preview digest 可以被带到另一个 remote namespace 使用。其余问题集中在写入响应丢失后的重试恢复、staging-only freshness 与 digest 字段不一致、以及公开输出 schema 的字段位置互相矛盾。

这些问题都可以局部修正，不需要推翻 advisory-only、复用 `version_update` 或 Changelog-driven 的总体设计，但在修复前仍不宜交给 implementation agent。

## Goal and boundary reconstructed

方案目标是：以远端最高稳定 tag 为版本基线，以当前 `CHANGELOG.md / ## Unreleased` 为唯一语义声明，确定性推荐 bump；preview 只读，用户确认后重新计算全部证据并只原子更新 `VERSION`。手动 bump 路径必须兼容，工具不修改 Changelog、Git refs、release 或生产环境。

实施边界是：新增只读 recommendation module，SemVer primitives 下沉到 `release_target.py`，现有 `version_update` 接入 `bump=auto`，文档和 focused tests 随之更新。

## Assumptions tested

1. 只要存在至少一个受支持 bullet，就可以安全忽略同一 `Unreleased` 中其它非空 heading 或无 heading 内容。
2. remote raw/peeled SHA 相同足以证明 apply 使用的是 preview 时同一个 remote authority。
3. `recommendation_digest` 字段列表覆盖了所有声明为 freshness-sensitive 的状态。
4. 成功写入后的相同 apply 请求不需要定义重试或响应丢失恢复语义。
5. `review_flags`、`warnings`、remote raw/peeled identity 和失败 reason code 的公开位置已经唯一确定。
6. 现有 `release_target.parse_release_tags()` 的 prerelease/service-upgrade 语义不会被新的 stable raw/peeled parser意外替换。
7. 静态 `requires=("local_repo", "git_remote")` 只是 manifest metadata，不会在 handler 前阻断离线手动模式。
8. bounded untracked hashing 和两次 remote recheck 与真实 stale/race 风险匹配，没有引入不必要的持久化状态。

## Findings

### PR3-01-未修复-高-混合的未知 Unreleased 内容会被静默忽略并产生可能过低的推荐
- **位置**: 4.3 Release intent、5.1 Deterministic precedence、12 Classification tests
- **问题类型**: 契约缺失 / 状态机漏洞 / 最佳实践偏离
- **当前写法**: 只识别 `Breaking Changes`、`Added`、`Changed`、`Fixed` 下以 `- ` 开头的 bullet；没有任何受支持 bullet 时才返回 `needs_input`。分类表只按已识别 bullet 计算，测试仅覆盖“Unsupported headings only”。
- **反例/失败场景**:
  ```markdown
  ## Unreleased

  ### Removed
  - Removed the legacy CLI flag used by automation.

  ### Fixed
  - Fixed a typo in help text.
  ```
  按当前规则，`Removed` 被忽略，因为仍存在一个受支持的 `Fixed` bullet，最终推荐 `patch`。同类问题也会发生在 `Deprecated`、`Security`、直接放在 `Unreleased` 下的 bullet、未知三级标题或 malformed heading 中。
- **为什么有问题**: 方案明确把 Changelog 声明设为唯一 semantic authority，不再从源码补救。当 parser 对部分非空声明选择静默忽略时，工具会把“不理解全部 release intent”误表示成“声明完整且可推荐”，这是会造成 under-bump 的 fail-open 行为。`manual_review_required=true` 不能替代结构化工具对未知输入的显式拒绝。
- **直接证据**: plan `:150-170` 只定义四个支持标题和 bullet 形式；`:191-196` 只在“没有受支持 bullet”时返回 `needs_input`；`:621-628` 没有“受支持 + 不受支持内容混合”的测试。当前仓库 release metadata 校验只检查目标版本段存在，不会替 recommendation parser 证明未知 `Unreleased` 内容安全，见 `scripts/release_check.py:64-73`。
- **影响**: 生成错误的 patch/minor 推荐；用户确认后写入过低版本；公开兼容性信号错误；review 很难发现被 parser 丢弃的声明。
- **建议改法和验证点**:
  1. 对 `Unreleased` 建立 fail-closed grammar：必须恰有一个 `## Unreleased`；section 到下一个 `##` 结束；非空 release item 必须归属于受支持标题。
  2. v1 最简单安全方案是：任何非空未知三级标题、标题外 bullet、重复 `Unreleased` 或无法归属的内容均返回 `needs_input / UNSUPPORTED_UNRELEASED_CONTENT`，不要猜测其 bump。
  3. 明确 fenced code、heading continuation、重复受支持 heading 和 bullet continuation 的处理；无法可靠解析时 fail closed。
  4. 增加 mixed `Removed + Fixed`、`Security + Added`、heading 外 bullet、重复 `Unreleased`、code fence 内伪 heading 测试。
- **修复风险（低）**: 收紧 parser 和补测试即可，不需要新增语义 detector。
- **严重程度（高）**: 当前规则存在可信的 silent under-bump 路径。

### PR3-02-未修复-高-recommendation digest 没有绑定 remote selector 和 remote endpoint
- **位置**: 3.3 freshness 与用户授权分离、4.1 版本基线、6.3 recommendation digest、7.1/7.2 Preview/Apply
- **问题类型**: trust boundary / freshness 契约缺失 / 状态机漏洞
- **当前写法**: preview/apply 都接受 `remote_name`；digest 绑定 remote stable tag/version、raw SHA、peeled commit SHA，但字段列表没有 `remote_name`，也没有该 remote 当前解析出的 fetch URL 或其它 endpoint identity。
- **反例/失败场景**:
  1. 用户 preview 使用 `remote_name=origin` 并确认 digest D。
  2. apply 改用 `remote_name=upstream`；upstream 当前恰好有同名 baseline tag且 raw/peeled SHA 与 origin 相同，target tag 也不存在。
  3. 因 digest 未包含 remote selector，重新计算仍可得到 D，VERSION 被写入，但最终 collision/release authority 已换成另一个 namespace。

  同样地，preview 后执行 `git remote set-url origin <different-repo>`，只要新 endpoint 暂时返回同一 baseline identities，当前 digest也无法发现 authority发生变化。
- **为什么有问题**: 方案声称 digest 证明“recommendation 输入没有变化”，而 `remote_name` 是显式输入，remote endpoint 又是最高稳定 release 和 target collision 的 trust boundary。只绑定 tag SHA 证明代码 baseline相同，不能证明用户确认的是同一个发布 namespace。
- **直接证据**: plan `:332-350` 在 preview/apply payload 中暴露 `remote_name`；`:289-304` 的 digest schema没有 remote name/URL；`:354-361` 重新查询 tags但没有验证 remote endpoint identity。当前 Tool Gateway 的 payload会原样传给 handler，write gate只验证 apply/confirm，不约束 remote，见 `src/application/tool_execution.py:28-40` 和 `src/application/agent_tools/permissions.py:18-32`。
- **影响**: preview confirmation 可跨 remote 重放；target collision 检查针对错误 namespace；审计信息无法证明 recommendation 使用了哪个 endpoint。
- **建议改法和验证点**:
  1. digest 至少加入规范化 `remote_name`。
  2. preview 时读取并返回、digest-bind `git remote get-url --fetch <remote>` 的精确结果；apply 重新解析并要求一致。若项目支持多 URL，必须定义选择和排序规则。
  3. output 的 `base` 中显示 masked/canonical remote endpoint identity，避免只显示易重映射的别名。
  4. 增加 apply 改 remote name、preview 后 remote set-url、同 commit不同 remote target collision 的测试。
- **修复风险（中）**: 需要定义 URL canonicalization/masking，但不需要网络协议层重构。
- **严重程度（高）**: freshness proof 当前没有覆盖外部 authority selector。

### PR3-03-未修复-中-成功写入但响应丢失后没有可判定的重试语义
- **位置**: 7 State transitions、7.2 Apply recommendation、12 Compatibility and permission tests
- **问题类型**: 并发恢复风险 / idempotency gap / partial failure
- **当前写法**: apply 先重算 recommendation并要求当前 `VERSION` 等于 remote baseline，digest相同后写入 target。状态机只有 `applied`，没有 `already_applied`、replay 或 unknown-outcome recovery。
- **反例/失败场景**: Tool 已成功执行 `VERSION.tmp -> VERSION`，但 CLI/MCP transport在返回 response 前断开。用户用相同 digest和 confirm重试。此时 `VERSION` 已等于 target而不再等于 baseline，完整 recommendation会先触发 `VERSION_BASE_MISMATCH`；调用方得到 blocked，看不出上一次实际上已经成功。
- **为什么有问题**: 本地 write 虽小，但“写成功、响应失败”是标准 partial-failure 场景。当前设计会把成功操作报告成失败状态，促使用户做不必要的人工修复或绕过检查。现有 `update_local_version()` 对同一显式 target天然可返回 no-change，但 auto流程的新 baseline guard会破坏这种恢复能力。
- **直接证据**: plan `:314-325` 和 `:354-363` 没有 retry branch；test matrix `:667-671` 只覆盖首次成功。当前 write 在 replace后才构造返回结果，见 `src/application/version_check.py:68-92`，因此 replace成功后 response丢失是可信窗口。
- **影响**: 操作结果不确定；重复确认无法安全恢复；审计和用户提示与磁盘状态矛盾。
- **建议改法和验证点**:
  1. 定义 auto apply replay语义。最小方案：当 current VERSION 已等于由同一 baseline/Changelog evidence导出的 target时，重建“写入前 digest”并与传入 digest比较；其它 evidence仍相同则返回 `status=applied, changed=false, replayed=true`。
  2. 若不接受 replay，至少定义 `outcome_unknown` recovery：Tool返回当前 VERSION和只读检查指令，而不是普通 baseline mismatch。
  3. 增加“replace成功后模拟 response failure，再用同 digest重试”和“VERSION被人工改成相同 target但其它 evidence变化时不得误认 replay”测试。
- **修复风险（中）**: 需要谨慎区分 genuine replay 与人工同值写入，但无需数据库或持久化 receipt。
- **严重程度（中）**: 不会写错值，但会让成功状态不可恢复和不可判定。

### PR3-04-未修复-中-staging-only 变化被要求 stale，但 digest schema无法检测
- **位置**: 6.1 Evidence collection、6.3 recommendation digest、12 Freshness tests
- **问题类型**: 不可直接实施 / 测试与设计不一致
- **当前写法**: evidence collection列出 staged/unstaged状态；digest字段只列一个 `tracked diff digest`；测试要求“Staged state changes -> stale”。另有描述将该 digest定义为 baseline-to-worktree binary diff。
- **反例/失败场景**: preview时文件内容处于 unstaged状态，之后仅执行 `git add file`。HEAD、worktree内容、baseline-to-worktree binary diff、Unreleased、remote identities和target全部不变；只有 index/worktree边界改变。按列出的 digest字段，apply无法得到不同 digest。
- **为什么有问题**: baseline-to-worktree diff表示最终内容，不编码相同内容位于 index还是 worktree。plan同时要求 staging状态参与 freshness，却没有为它定义 canonical evidence，implementation agent只能自行改变 digest schema或削弱测试。
- **直接证据**: plan `:259-272` 收集 staged/unstaged状态；`:289-304` digest未列 index或 staged/unstaged digest；`:651-655` 要求 staged state变化 stale。实测临时 Git repo中，修改文件后 `git diff --binary HEAD` 的 SHA-256 在 `git add` 前后完全相同，而 `git status --short` 从 ` M f.txt` 变为 `M  f.txt`。
- **影响**: test无法按当前设计通过，或实现与文档不一致；freshness语义在不同实现者之间漂移。
- **建议改法和验证点**:
  1. 先决定 staging-only变化是否真的影响版本推荐。ROI更高的方案是：digest只绑定最终 tracked content，staging状态仅作为展示信息，不因 `git add` 单独 stale。
  2. 如果必须绑定 staging，则分别加入 canonical `index_diff_digest` 和 `worktree_diff_digest`，并使用 NUL-safe路径/二进制输出规则。
  3. 将 test 26与最终选择同步，增加 staged->unstaged、partial staging和intent-to-add测试。
- **修复风险（低）**: 删除不必要的 staging freshness要求最简单；若保留则测试复杂度中等。
- **严重程度（中）**: 当前 plan内部契约无法同时满足。

### PR3-05-未修复-中-结构化输出字段位置和失败契约不唯一
- **位置**: 4.2 Detached HEAD、5.2 Declaration status and review flags、8.3 Output、Final implementation handoff
- **问题类型**: public contract / 架构边界 / 不可直接实施
- **当前写法**:
  - detached示例把 `review_flags` 放在顶层；
  - declaration示例也把 `review_flags`、`warnings` 放在同一对象层；
  - 完整成功输出把 `review_flags` 放在 `evidence` 内，而 `warnings` 留在顶层；
  - remote evidence只展示 `base.commit`，没有区分已被方案定义为关键证据的 raw tag object SHA和 peeled commit SHA；
  - 只列出 `blocked|needs_input|stale|applied`，没有给这些 data-status 的统一 required fields/reason code schema，也没有说明哪些失败使用 Tool envelope `ok=false`。
- **反例/失败场景**: implementation agent按 4.2 实现 `data.review_flags`，docs renderer按 8.3 读取 `data.evidence.review_flags`，detached或敏感路径警告被静默漏掉。另一个实现可能把 `blocked` 作为 `ok=true,data.status=blocked`，而调用方按现有 `AgentToolError`/`ok=false` 处理，造成 failure path不可互操作。
- **为什么有问题**: 这是 Agent Tool 的用户可见结构化契约，字段位置不一致不是命名偏好；它直接决定 Codex/CLI能否可靠展示确认依据和处理失败。当前 `VERSION_UPDATE_TOOL` 还没有 `output_contract`，因此不能依赖已有 schema替 plan消歧。
- **直接证据**: plan `:122-131`、`:228-250` 与 `:420-453` 对 `review_flags` 层级不一致；`:425-430` 只显示单一 commit；`:457-464` 只枚举 status。当前 `src/application/agent_tools/runtime.py:167-190` 创建 `VERSION_UPDATE_TOOL` 时没有 output contract；Tool executor区分 handler data成功和 `AgentToolError`失败，见 `src/application/tool_execution.py:33-47`。
- **影响**: implementation agent必须重新设计 public schema；renderer、contract tests和docs可能各自实现不同层级；关键 review flag或失败原因丢失。
- **建议改法和验证点**:
  1. 在 plan中给出唯一 `release_version_recommendation.v1` schema，固定 `review_flags`、warnings、base raw/peeled identities、reason_code和workspace字段位置。
  2. 明确 permission/input errors使用 Tool envelope `ok=false`；业务可恢复状态是否使用 `ok=true,data.status=...`，并为每个 status列 required fields。
  3. 给 `VERSION_UPDATE_TOOL` 增加 mode-sensitive output contract/resolver，或明确它保持宽 envelope但由 contract tests固定 auto输出。
  4. 增加 detached+sensitive flags组合、每个 status shape、raw/peeled evidence可见性和 docs renderer测试。
- **修复风险（低）**: 主要是方案消歧和 schema tests。
- **严重程度（中）**: 当前公开契约不够 code-generation-ready。

## Architecture boundary review

总体边界合理：recommendation engine保持只读，VERSION write仍由 `version_check.py` 拥有，Tool adapter只做payload和response adaptation，domain层不被牵涉。SemVer primitives下沉到已经拥有 parse/compare 的 `release_target.py` 也符合依赖方向。

需要保护的兼容边界是：现有 `release_target.parse_release_tags()` 同时服务 update check和service upgrade，且支持 prerelease。新的 stable raw/peeled identity parser应新增为独立函数/类型，不应把现有 `(version, tag)` parser直接改成 stable-only richer结构。`tests/test_version_check.py` 已覆盖 prerelease ordering，但方案还应明确这个非目标，避免 S1在共享模块内造成隐性 API churn。

PR3-05 表明 Tool public contract边界仍未完全收敛；在进入实现前必须固定 schema，而不是让 recommendation module、adapter和docs各自决定字段位置。

## Best-practice review

- **Fail closed**: 对唯一 semantic authority中的未知非空内容必须 `needs_input`，不能只忽略。
- **Trust binding**: freshness receipt应绑定 remote selector/endpoint，而不只是该 endpoint当前返回的commit。
- **Retry safety**: 写操作需要处理“副作用已发生但响应丢失”的标准窗口。
- **Deterministic digest**: 所有声明为 freshness-sensitive 的状态都必须有明确 canonical字段；否则应从 freshness范围移除。
- **Public schema**: 结构化 Tool必须明确 data-status和transport error的边界。

## Optimal-solution review

当前总体方案仍是可信 alternatives中较实际的一条：由维护者声明 release intent，比构建源码语义 detector更简单、更可审计；复用 `version_update` 比新增第二个 Tool更低成本。

本轮 finding不要求扩大系统：

- 未知 Changelog内容直接 fail closed，不增加更多启发式分类器；
- remote binding只增加现有 evidence字段；
- replay可通过重建 prior digest处理，不需要数据库receipt；
- staging-only freshness最好删除而不是引入复杂index状态；
- output schema只需一次性统一。

## Overengineering review

bounded untracked hashing、remote apply recheck和raw/peeled解析都有明确 stale/identity风险支撑，不属于无依据的过度设计。

唯一需要收缩的是 staging-only invalidation：它不改变待发布内容或推荐结果，却会要求额外index digest和partial-staging tests。除非有明确发布流程要求，建议仅展示 staging状态而不把它纳入 freshness token。

不要为了修复 PR3-01扩展成通用 Markdown AST或语义 NLP；一个严格、有限、fail-closed 的 line parser足够。

## Overcoupling review

未发现新的跨 domain耦合。主要风险是共享 `release_target.py`：新的 stable identity功能不能改变现有 prerelease/update consumers的数据结构。建议新增窄类型，如 `RemoteStableTagIdentity`，同时保留现有 parser facade和服务升级 tests。

Tool output schema不应让调用方理解 recommendation模块内部对象；adapter应把内部结果映射为固定 v1 contract。

## Open Questions

1. 对任何非空未知 `Unreleased` heading，是否统一返回 `needs_input`？本 review建议是。
2. remote endpoint identity绑定 fetch URL、push URL，还是两者？该工具查询使用 fetch URL，但后续 release通常 push到 origin；至少应明确并展示 fetch authority。
3. auto apply在响应丢失后希望返回 `replayed=true`，还是要求调用方先执行单独只读 recovery检查？
4. staging-only变化是否真的必须使推荐过期？若没有业务理由，应删除该要求。
5. `blocked|needs_input|stale` 是 `ok=true` 的业务状态还是 `ok=false` 的 Tool error？需要唯一答案。

## Residual risks and tracking

- Changelog声明本身仍可能错误；继续保留 `manual_review_required=true`，在 `docs/RELEASE_PROCESS.md` 追踪。
- apply最后一次remote查询与后续GitHub workflow之间仍有race；由workflow tag collision继续兜底，在 release workflow tests/operations docs追踪。
- sensitive-path warnings有误报/漏报；作为 advisory warning即可，不应扩大成 semantic detector。
- remote URL可能包含credentials；若加入output/digest，必须使用不会泄露secret的 canonical/masked表示，同时digest可绑定内部完整或安全规范化值。
- 后续若建立 CLI/Tool contract snapshots，应作为独立work unit，不扩大本v1。

## Final conclusion

**fail**。

第二轮问题已经闭环，但在进入 implementation 前仍需修复：

1. 未知和受支持 Changelog内容混合时必须 fail closed；
2. digest绑定 remote selector/endpoint identity；
3. 定义成功写入后的 retry/recovery语义；
4. 对 staging-only freshness作出可实现的唯一选择；
5. 统一结构化输出和失败 envelope。

这些都是局部方案修正；不需要改变 advisory-only、显式 `bump=auto`、复用 `version_update` 或“只写 VERSION”的核心方向。
