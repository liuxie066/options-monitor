# Plan Review — Combo Yield 完整退出与持仓生命周期方案

- **Reviewed target**: 上一轮会话中提出的 Combo Yield 生命周期改造方案，主要包括：
  - Put 关闭后将 Call 作为保留 Combo 血缘的 residual call；
  - assignment 后进入 `assigned_stock_plus_call`；
  - 采用“腿级评估、组合级合成”的 Close Advice；
  - P0 生命周期只读视图、P1 group action synthesizer、P2 动作/显示修正、P3 真正错期开仓支持；
  - 未来 group ID 不再包含 expiry。
- **Review scope**: 状态机、错期经济模型、group identity、assignment/部分关闭、Close Advice ownership、兼容与实施切片。
- **Review timestamp**: 2026-07-18 11:57:31 Asia/Shanghai
- **Review posture**: adversarial；目标是判断该方案是否已经足够 code-generation-ready，而不是判断总体方向是否合理。

## Goal / Non-goals / Success Signal 识别

### Plan 声称的目标

1. 为 Combo Yield 建立从两腿开放、单腿退出、assignment 到最终关闭的完整生命周期语义。
2. 防止 Put/Call 腿级建议相互冲突，由组合级动作给用户最终建议。
3. 为未来真正的不同 expiry Combo Yield 建立可演进身份和状态基础。

### Plan 隐含的 non-goals

- 第一版不支持一张长期 Call 跨多个 Put 周期。
- Close Advice 不直接写股票卖出事件。
- 不迁移性重写历史 group ID。

### 当前缺失的 success signal

Plan 给出了测试场景列表，但没有定义可验收的公共输出契约、状态派生真值表、混合旧/新数据兼容标准、group action 冲突优先级或 diagonal 经济指标的正确性标准。因此目前无法仅按 plan 判断 implementation 是否完成。

## Assumptions Tested

1. 不同 expiry 只需放宽配对校验并增加 expiry-gap policy。
2. 一个互斥 phase enum 足以表示 Combo 生命周期。
3. `strategy_group_id` 可以在推荐/订单意图生成，并可靠到达两条 broker fill。
4. assigned stock 可以自然并入现有 Close Advice。
5. 腿级 evaluator 之后增加一个 group action synthesizer 即可得到确定动作。
6. assignment event 和 assigned-stock projection 复制 group 元数据不会引入真源歧义。
7. 只读 `ComboLifecycleView` 足以在不迁移历史数据的情况下覆盖已有生命周期。

## Findings

### PR-001-未修复-[严重]-真正错期的经济与估值契约未定义，P3 不能直接实施
- **位置**: “真正支持错期 Combo Yield”与 P3“扩展真正错期的开仓引擎”
- **问题类型**: 契约缺失 / 不可直接实施 / 非最优方案
- **当前写法**: Plan 建议把同 expiry 校验改成 `call_expiration >= put_expiration`，并增加 `min/max_expiry_gap_days`、资金比例等约束。
- **反例/失败场景**: Put 30 DTE、Call 180 DTE。Put 到期时 Call 仍有 150 天时间价值。现有 `combo_breakeven`、`upside_breakeven`、scenario payoff 和 annualized return 把 Call 当作与 Put 同一 horizon 的到期 payoff，无法判断 Put 到期时 Call 的剩余价值。即便两个候选初始净权利金相同，远期 Call 的 vega、term structure 和 residual value 可能完全不同，当前 ranking 会把不可比结构放在一起。
- **为什么有问题**: 不同 expiry 不是结构校验的小扩展，而是目标函数和估值时点变化。若 implementation agent 只按 plan 放宽 expiry，会生成数学上错误但表面可运行的候选排序。
- **直接证据**:
  - `domain/domain/engine/yield_enhancement.py:128-129` 当前明确拒绝 `expiration_mismatch`。
  - `domain/domain/engine/yield_enhancement.py:162-177` 使用单一 `dte=min(put_dte, call_dte)` 计算 expected move 和 annualized yield。
  - `domain/domain/engine/yield_enhancement.py:179-207` 用同一 horizon 的静态 Call intrinsic payoff 计算 breakeven/scenario score，没有 Put 到期时的 Call residual value 模型。
  - `docs/STRATEGY_ARCHITECTURE.md:155` 当前产品定义明确为同到期组合。
- **影响**: 错误候选筛选与排序、错误收益率、用户可能基于虚假经济指标开仓；后续 replay 无法解释。
- **建议改法和验证点**:
  1. 将真正 diagonal 开仓从当前 implementation plan 移出，先形成单独 design decision。
  2. 明确 valuation horizon：Put expiry、Call expiry，还是持仓管理中的动态 horizon。
  3. 明确 Call residual value 来源：禁止模型估值、使用历史 surface/replay、还是只采用保守下界。若没有可信来源，第一版不得产出 diagonal 开仓推荐。
  4. 定义 diagonal 专属指标和排序，禁止复用当前 same-expiry `combo_breakeven/scenario_score`。
  5. 用至少三种 term-structure 反例验证：远期 IV 高、远期 IV 低、Put expiry 前重大事件。
- **修复风险（高）**: 需要产品与策略判断，不是局部代码修补。
- **严重程度（严重）**: 当前 P3 方向交给 implementation agent 会产生错误金融语义。

### PR-002-未修复-[高]-互斥 phase 状态机无法表达部分 assignment 和混合库存
- **位置**: 推荐生命周期状态机与 `assigned_stock_plus_call` / `put_only` / `residual_call`
- **问题类型**: 状态机漏洞 / 契约缺失
- **当前写法**: Plan 把 group 表示为一个互斥 phase，例如 `active_combo`、`assigned_stock_plus_call`、`put_only`、`residual_call`。
- **反例/失败场景**: 一个 Put lot 有 2 contracts，assignment 1 contract，另 1 contract 仍开放；Call 有 2 contracts 仍开放。此时真实库存同时包含：open short put、assigned stock、long call。它既不是单一 `active_combo`，也不是单一 `assigned_stock_plus_call`。类似地，Call 部分卖出或 assignment 后股票部分卖出也会形成混合状态。
- **为什么有问题**: 当前 ledger 原生支持按 `contracts_to_close` 部分关闭；互斥 enum 会丢失库存事实，或迫使正常部分生命周期全部进入 `review_required`，导致 Close Advice 在最需要帮助时失效。
- **直接证据**:
  - `src/application/ledger/lifecycle.py:114-215` lifecycle close 按 `contracts_to_close` 分配并支持部分目标数量。
  - `domain/domain/ledger/lots.py:48-59` close event 只扣减相应 contracts，lot 可保持 open。
  - `src/application/positions/reporting.py:1924-1942` assigned stock sale 支持部分卖出和 remaining shares。
  - 当前 Close Advice pairing `src/application/close_advice_runner.py:1512-1518` 每个 group 只保留第一条 Call，尚未处理多 lot/数量匹配。
- **影响**: phase 错误、数量重复归因、组合 P&L 错误、错误执行建议，或大量正常仓位退化为不可评估。
- **建议改法和验证点**:
  1. 不把 phase 作为库存真源。先定义 compositional inventory view：`open_put_contracts`、`open_call_contracts`、`assigned_shares_remaining`、各 lot IDs。
  2. phase 仅作为从库存派生的展示分类，允许 `mixed_partial_assignment` 等派生状态，或者使用多个正交状态维度。
  3. 明确 contract/share matching：`multiplier × assigned_contracts` 与 Call contracts 如何对应；数量不等时哪些 units 可组合评估。
  4. 添加部分 assignment、部分 Call close、多个 Put/Call lots、部分股票卖出的状态真值表测试。
- **修复风险（中）**: 需要重写状态模型，但可保持 event source 不变。
- **严重程度（高）**: 不修复会让正常合法 ledger 状态无法被正确表达。

### PR-003-未修复-[高]-新 group identity 缺少从策略意图到 broker fills 的持久化和幂等契约
- **位置**: “Group ID 不能再包含 expiry”“在策略意图或订单生成时创建 UUID”
- **问题类型**: 架构边界 / 并发恢复风险 / open question 未收敛
- **当前写法**: Plan 建议未来生成 expiry-independent UUID，并要求成交 intake 携带显式 group ID。
- **反例/失败场景**: 两腿由独立 broker orders 成交；Call 先成交、Put 延迟或部分成交；broker deal payload 不回传本地 UUID；进程重启后 intake 只能看到成交事实。系统无法把第二条腿恢复到同一 group。重复 intake 或 order retry 还可能生成新 UUID，形成两个半组合。
- **为什么有问题**: Repo 当前没有被 plan 指定的 durable order-intent/group-link store，也没有说明 UUID 如何进入 broker round-trip。仅要求“显式 group ID”不能解决真实成交恢复与外部手工成交。
- **直接证据**:
  - `src/application/trades/resolver.py:704-708` 当前 group ID 可由 account/symbol/expiry 对成交事实确定性重建。
  - `src/application/trades/resolver.py:711-732` 当前 companion 查找只依赖可从 broker deal 获得的合约字段。
  - `tests/test_trades_resolver_open.py:172-196` 当前允许没有 companion 的 Call 先入账并用确定性 group ID 等待同 expiry Put。
- **影响**: 重启后配对丢失、重复 group、半组合、历史无法恢复、人工 repair 增多。
- **建议改法和验证点**:
  1. 在决定 UUID 方案前，明确 group identity authority：candidate/order intent、broker order mapping、manual intake，或显式 link event。
  2. 定义 durable mapping、幂等键、重启恢复、部分成交和订单取消行为。
  3. 对没有本地 order intent 的外部成交定义 fail-closed/manual-link 流程。
  4. 保留当前 deterministic legacy ID 的读取；混合 old/new ID 必须有 schema/version 标记。
  5. 测试 Call-first、Put-first、restart、duplicate deal、partial fill、cancelled sibling order。
- **修复风险（高）**: 涉及 trade-intake 与外部协议边界。
- **严重程度（高）**: group identity 是后续所有状态和 P&L 的基础，当前方案不可恢复。

### PR-004-未修复-[高]-把 assigned stock evaluator 纳入 Close Advice 会穿透现有 ownership 和安全边界
- **位置**: “腿级评估、组合级合成”中的 `Assigned-stock evaluator` 以及 `review_stock_sale_keep_call` / `review_close_stock_and_call`
- **问题类型**: 架构边界 / 过度耦合 / 范围漂移
- **当前写法**: Plan 建议 Close Advice 同时装配 Put、Call 和 assigned-stock evaluator，并输出 stock + Call 的组合动作。
- **反例/失败场景**: Close Advice runner 为了形成 `close_stock_and_call`，需要读取 assigned-stock events、实时股票报价、部分股票出售、holdings reconciliation 和 option quote。任一来源缺失时 action policy 需要理解 assigned-stock 的完整数据质量状态；这会把现有独立的 assigned-stock reporting/workflow 反向耦合进 option Close Advice。
- **为什么有问题**: 当前 Close Advice 合同明确是 open option lot 的退出决策；assigned-stock sale 是独立受控事实和 CLI。Plan 虽然说不自动卖股，但 group action 命名和 evaluator ownership 已经把股票退出策略引入 Close Advice，scope 与模块 owner 未收敛。
- **直接证据**:
  - `docs/CLOSE_ADVICE_CONTRACT.md:1-12` 将目标限定为 open option lot 的定价和退出。
  - `docs/CLOSE_ADVICE_CONTRACT.md:43-50` 规定 domain/runner ownership，不包含 stock lifecycle。
  - `README.md:452-456` assigned-stock sale 使用独立入口并要求目标 stock lot。
  - `src/application/positions/reporting.py:1676+` assigned-stock lifecycle 已拥有复杂的 quote、sale、fee 和 reconciliation 逻辑。
- **影响**: Close Advice runner 变成跨 option ledger、stock lifecycle、holdings、quotes 的 orchestration hub；测试只能依赖大集成链路；后续股票策略变更会破坏期权建议。
- **建议改法和验证点**:
  1. 第一阶段只让 `ComboLifecycleView` 暴露 assignment phase 和 stock reference，不在 `domain.domain.close_advice` 增加股票退出 thesis。
  2. assignment 后 Close Advice 可输出 `manual_review_assigned_stock_plus_call`，并附 stock report/tool reference。
  3. 若确实需要 stock + Call 联合建议，先建立独立的 portfolio lifecycle advisory contract，复用只读 position views，而不是扩张现有 option Close Advice。
  4. 验证 Close Advice 在 assigned-stock 数据源不可用时仍可独立处理普通期权仓位。
- **修复风险（中）**: 收窄 scope 比扩张模块更安全。
- **严重程度（高）**: 当前 plan 会造成明显跨域耦合并模糊安全责任。

### PR-005-未修复-[高]-Group Action Synthesizer 只有动作枚举，没有确定的冲突和 actionability 规则
- **位置**: P1“Close Advice 改成组合合成”及各 phase 动作列表
- **问题类型**: 不可直接实施 / 契约缺失 / 测试缺口
- **当前写法**: Plan 罗列 `hold_both`、`close_put_keep_call`、`sell_call_keep_put`、`close_both` 等动作，但没有定义腿级结果到 group action 的真值表。
- **反例/失败场景**:
  - Put=`profit_capture`，Call=`take_profit`，但 Call spread too wide；应 close Put、hold Call，还是整个 group not_evaluable？
  - Put=`hold`，Call=`take_profit`；卖 Call 会使剩余结构退化为 short put only，是否允许取决于组合 thesis，而不是 Call 的 2x 阈值。
  - Put 可盈利买平，但 `combo_net_if_close_both < 0`；当前 plan 说不再仅凭可计算显示“组合止盈”，但没有定义最低 group outcome。
  - 两腿 action 都可执行，但不同账户/币种/数量或报价时间不一致。
- **为什么有问题**: Implementation agent 必须重新设计 policy、优先级和 fail-closed 行为，plan 不是 code-generation-ready；不同实现可能产生完全不同的用户建议。
- **直接证据**:
  - `src/application/close_advice_runner.py:1293-1323` 当前 action mapper 是确定的单腿 exit-state 映射。
  - `src/application/close_advice_runner.py:1283-1290` 当前 `close_both_optional` 只检查可计算性，不检查正收益。
  - `docs/CLOSE_ADVICE_CONTRACT.md:106-108` 明确 action policy 不得改变 thesis evaluator 结果。
- **影响**: 用户可见建议不稳定、review 无法验收、可能把不可执行或经济上不合理的动作标记为推荐。
- **建议改法和验证点**:
  1. 在 implementation 前写出每个 lifecycle inventory state 的 group action truth table。
  2. 明确三类状态：leg thesis、group economic qualification、execution readiness，禁止用一个 `not_evaluable` 混合。
  3. 定义冲突优先级、数据缺失传播、报价时间一致性、数量一致性和 group profit 条件。
  4. 决定 group synthesizer 位于 domain 还是 application；若规则改变 thesis，应在 domain，而不是 runner 临时拼装。
  5. 将每个真值表行做参数化测试，尤其覆盖一腿 actionable、一腿 not-evaluable。
- **修复风险（中）**: 需要产品决策，但实现范围可控。
- **严重程度（高）**: 当前 P1 仍要求 implementation agent 自行完成关键策略设计。

### PR-006-未修复-[中]-Assignment 元数据继承方案没有指定 canonical source，可能制造双真源和历史断层
- **位置**: P0“让 assignment event/assigned-stock projection 继承源 Put 的 strategy_group_id 等字段”
- **问题类型**: 架构边界 / 兼容风险 / 最佳实践偏离
- **当前写法**: Plan 同时建议 assignment event 和 assigned-stock projection 都复制源 Put 的 group/strategy/paired-call 信息。
- **反例/失败场景**: Put 开仓后通过受控 adjust event 修复 `strategy_group_id`，随后发生 assignment。assignment event 应快照修复后的 lot metadata，还是保持 open event 原始 metadata？若 event、position lot 和 assigned-stock row 各自存一份，repair/void/rebuild 后可能出现三个不同值。历史 assignment event 没有这些字段，又会与新事件形成 mixed schema。
- **为什么有问题**: 当前 canonical relation 已有 `target_lot_id`、`source_option_lot_id` 和 source assignment event。Plan 没有说明复制字段是 immutable snapshot、derived cache 还是新真源。
- **直接证据**:
  - `src/application/ledger/lifecycle.py:307-323` assignment event 已保存 target lot 和 close-target source event，但不复制策略字段。
  - `src/application/positions/reporting.py:1796-1834` assigned-stock lot 是派生 read model，当前通过 source option lot/event 关联。
  - `src/application/ledger/publisher.py:70-84` position lot 由 open/adjust/close events 重建，策略字段可能被 adjust event 修复。
- **影响**: rebuild 结果不一致、repair 语义不清、历史与新数据产生难以诊断的 group drift。
- **建议改法和验证点**:
  1. 明确 canonical ownership：建议 assignment event 只保留稳定 target/source IDs；`ComboLifecycleView` 在重建时从目标 lot 的有效策略元数据派生 group。
  2. 如果审计要求 assignment-time snapshot，则定义带版本的 `strategy_context_snapshot`，并明确它不覆盖 lot 当前元数据。
  3. assigned-stock row 只作为派生缓存，不成为 group identity authority。
  4. 测试 open → adjust group metadata → assignment → rebuild，以及 void/repair assignment 后的结果。
- **修复风险（低）**: 主要是收敛数据契约和补测试。
- **严重程度（中）**: 不会立即损坏交易事实，但会制造长期数据一致性债务。

## Architecture Boundary Review

- **正面**: 保留腿级 evaluator，避免把 Put 与 Call 的 thesis 强行合并，是正确方向；使用 event-derived view 而非直接写 mutable group status 也符合 repo canonical ledger 约束。
- **未通过项**:
  1. assigned-stock strategy 被直接拉进 option Close Advice，跨越 `positions/reporting` 与 `domain.close_advice` ownership。
  2. group synthesizer 放置位置未确定；若在 runner 中定义经济政策，会违反 runner “must not invent thesis”的现有 contract。
  3. UUID group identity 需要新 durable boundary，但 plan 未定义 owner 和 protocol。

## Best-practice Review

- 缺少显式 state/inventory truth table。
- 缺少 mixed-version 和 rebuild determinism 测试。
- 缺少 external fill、restart、partial fill 的 recovery contract。
- 缺少 shadow-first rollout，直接改正式 Close Advice 风险过高。

## Optimal-solution Review

更实际的顺序不是立即引入完整 group state machine 和 stock evaluator，而是：

1. 先建立**纯只读、compositional 的 Combo inventory/lifecycle shadow view**；
2. 只修复当前同 expiry 组合的错误 action label、负 combo outcome 和多 lot/数量歧义；
3. assignment phase 第一版只输出 manual review handoff，不在 Close Advice 中设计股票退出；
4. 真正 diagonal 作为独立策略 design，不复用当前 same-expiry 经济模型。

该替代路径更小、更安全，也更符合当前“Combo close design pending”和 ops-sensitive repo 的约束。

## Overengineering Review

- `strategy_program_id + combo_cycle_id` 被正确延期，不构成当前 blocker。
- 但一次性引入 Put/Call/Stock 三种 evaluator、完整 group action 与 diagonal identity，范围过宽。当前需求可先通过 derived inventory view + shadow group recommendation 验证，避免在没有真实 lifecycle replay 数据前固化过多状态和动作。

## Overcoupling Review

当前 plan 会把以下本可独立演进的概念同步绑定：

- option Close Advice；
- assigned-stock reporting/sale lifecycle；
- trade-intake group identity；
- opening candidate diagonal valuation；
- notification public contract。

建议拆成独立可验证 slices，并以只读 view 作为窄接口，避免一个 feature 同时改动 opening、ledger、stock reporting、Close Advice 和通知。

## Open Questions

1. 当前产品是否真的要求“开仓即不同 expiry”，还是只要求处理 Put 提前退出后 Call 留存？若是后者，P3 应完全移出当前 work unit。
2. assignment 后是否需要系统给股票出售建议，还是只需把组合上下文交给现有 assigned-stock workflow？
3. 部分 assignment 是否属于必须支持的常规状态，还是第一版允许显式 `review_required`？如果允许 review，最大可接受覆盖损失是多少？
4. group action 的最终目标是收益兑现、风险退出、保持原 thesis，还是仅避免腿级通知冲突？
5. 对新 broker fills，是否存在可持久化且可回传的 order-intent ID？
6. 历史 adjust 后的策略 group，应按开仓时、assignment 时还是当前修复后的 metadata 解释？

## Residual Risks and Suggested Tracking

- **Diagonal valuation/model risk**: 单独建立 strategy design issue/document，不应作为普通 implementation slice。
- **Historical group coverage**: 在 research/shadow artifact 中统计可解析 group、缺失 group、重复 legs、数量不等比例。
- **Assignment mixed inventory**: 建立 fixture 覆盖 partial assignment + partial stock sale + open Call。
- **Notification behavior**: 在 shadow replay 中跟踪新增/消失/变化的建议，并由 CEO 审核 promotion。
- **External trade recovery**: 在 trade-intake design 中跟踪 restart/duplicate/partial fill 测试。

## Final Plan Review Conclusion

**Conclusion: `fail`**

总体方向——保留策略血缘、从事件派生生命周期、腿级评估后组合级合成——是合理的；但当前计划尚不能安全交给 implementation agent。两个主要 blocker 是：

1. 真正 diagonal 的估值/排序契约没有定义，不能通过放宽 expiry 校验实现；
2. 生命周期使用互斥 phase，无法表达 repo 已支持的部分 assignment 和混合库存。

此外，group identity 的 durable propagation、Close Advice 与 assigned-stock 的 ownership、group action truth table 和 shadow-first rollout 都需要先收敛。建议重写为更窄的第一阶段计划：**同 expiry Combo lifecycle shadow view + 当前 action correctness 修复**，将 diagonal opening 和 stock exit advisory 拆成后续独立设计。
