# Plan Review

- Timestamp: `20260804-151803`
- Conclusion: `fail`
- Reviewed target: the immediately preceding architecture proposal to use one shared quote plane, retain per-account broker/trade planes, initially run two OpenD processes (`lx@127.0.0.1:11111` as quote owner plus lx broker endpoint; `sy@127.0.0.1:11112` as sy broker endpoint), move each OpenD to an independent HOME/data directory, and later split trade capture by account behind one canonical ledger applier.
- Review mode: adversarial implementation-plan review; no implementation, production mutation, plan repair, release, or deployment.
- Related but not replaced target: `docs/plans/incus-opend-reclaim-remediation-plan-20260804.md`. That existing plan deliberately excludes quote ownership redesign, trade-intake changes, and HOME migration, so this review treats the new proposal as a separate future work unit.

## Scope

Included:

- whether the proposed topology can materially reduce the observed OpenD reclaim/refault load;
- quote-versus-broker ownership and Futu client boundaries;
- configuration authority and market-data entitlement behavior;
- trade listener, inbox, SQLite ledger, failure, retry, and service-dependency semantics;
- independent HOME/data migration safety;
- implementation slicing, validation, rollback, and residual risk.

Excluded:

- reviewing the already-implemented v1.9.3 Strategy Lab recorder fix as code;
- changing source, runtime config, systemd, Incus, OpenD state, credentials, broker data, or production services;
- choosing a production account or performing an entitlement/capacity experiment.

## Normalized plan claims

The reviewed proposal makes these material claims:

1. Generic quotes, option chains, Strategy Lab marks, Close Advice marks, cache, and rate limiting should use one canonical quote endpoint, initially `lx@11111`.
2. Account cash, positions, deal push, history backfill, reconciliation, and future broker writes should remain bound to each account's own OpenD endpoint.
3. The first topology should retain two OpenD processes rather than add a third quote-only OpenD; the lx process therefore has two logical roles.
4. Each OpenD should have an independent installation/config/HOME/data directory.
5. True listener isolation may later use one capture service per account and one serialized canonical-ledger applier.
6. A post-change cold-start and steady-state capacity experiment should determine whether the topology closes the resource incident.

## Assumptions tested

- Removing generic quote traffic from `sy@11112` materially reduces the heavy mmap working set or refault rate.
- Two processes with lx serving both quote and broker roles constitute the intended separation boundary.
- Current Futu gateway code can route broker facts without creating or requiring a quote client on the same account endpoint.
- One global quote owner is valid for US/HK stocks and options and does not create a second endpoint authority.
- Current trade-intake can be split safely without duplicating intake, weakening identity, or introducing concurrent canonical-ledger writes.
- Existing per-account inbox/state paths are sufficient to support a separate capture/applier state machine.
- Moving from one shared HOME to per-account HOME directories is reversible and will improve resource behavior.
- Quote outage, lx broker outage, and sy broker outage can be observed and recovered independently.

## Findings

### PR-01-未修复-高-共享行情拓扑尚未证明能降低本次 reclaim/refault，且把逻辑路由误写成权限隔离

- **位置**: normalized claims 1、3、6；目标动机、成功信号和两进程拓扑。
- **问题类型**: 动机不成立 / 非最优方案 / 契约缺失
- **当前写法**: 将 generic quote 全部路由到 `lx@11111`，保留 lx/sy 两个 OpenD，预期减少重复行情负载；同时把共享行情和平账户交易描述成两个权限域。
- **反例/失败场景**: sy 为了持续 deal push、balance、positions 和 backfill 仍须常驻 `11112`。若主要 mmap 工作集来自 OpenD 初始化、证券列表、后台同步或 trade login，而非 OM generic quote 请求，那么改路由后两个大工作集仍然存在，NVMe refault 和 `memory.high` 不会下降。独立 HOME 还可能把原本可共享的 page-cache 页面变成两份。反过来，如果目标是权限隔离，复用 lx OpenD 同时承载行情与 lx 交易能力也不是权限边界，只是客户端路由约定。
- **为什么有问题**: 计划把尚未证实的性能收益作为架构动机，也把资源优化和安全隔离两个需要不同拓扑的目标合在一起。实施完成后可能既没有缓解 IO，也没有获得真正的最小权限隔离。
- **直接证据**: `docs/plans/incus-opend-reclaim-remediation-plan-20260804.md:31-35` 只支持“两个冷工作集在既有 memory envelope 下产生 reclaim/refault”，并明确不支持“共享 HOME 是原因”或“HOME 分离会降低压力”；该计划 `:54-60` 要求另行证明双 OpenD 的冷启动和稳定态容量。当前提案没有 endpoint 级 OM 调用量、每 PID/PSS、`memory.events`、refault 或 IO 归因基线。Futu 的 live trade unlock 是 OpenD 交易能力上的独立操作，但复用同一 OpenD 进程并不会形成 OS 或 credential 级权限隔离：<https://openapi.futunn.com/futu-api-doc/en/trade/unlock.html>。
- **影响**: 可能投入跨配置、gateway、service 和迁移的大改动，最终没有关闭主机事故；验收也无法判断失败来自架构方向错误还是容量仍不足。
- **建议改法和验证点**: 先把目标拆成“资源减载”“账户事实隔离”“权限隔离”三个独立目标，并明确本 work unit 只解决哪一个。增加 Phase 0 只读/受控实验计划：记录每 endpoint 的 OM quote/trade 调用分类与计数、两 PID 的 RSS/PSS/major faults/read bytes、cgroup `memory.events`/PSI 和 NVMe 延迟；预注册最小改善阈值。两进程方案只能称为“逻辑路由隔离”。若资源实验不能证明 sy generic quote 是 material contributor，停止 quote-owner 重构，优先走容量、启动序列或主机隔离方案。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### PR-02-未修复-高-当前 Futu gateway 会同时创建 quote 和 trade client，计划中的 sy trade-only 路径无法按现有边界实现

- **位置**: normalized claims 1、2；architecture boundary 和第一 implementation slice。
- **问题类型**: 架构边界 / 过度耦合 / 不可直接实施
- **当前写法**: generic quote 只去 `11111`，账户级 balance、positions、deal 和 backfill 继续去各自 endpoint，并暗含 `11112` 不再承担行情连接。
- **反例/失败场景**: `fetch_futu_portfolio_context(account="sy")` 使用 `build_ready_futu_gateway(host=11112)`。当前 backend 的 `_ensure_clients()` 在任一 client 缺失时同时构建 `OpenQuoteContext` 与 `OpenSecTradeContext`，而 ready builder 又先执行 `ensure_quote_ready()`。即使所有扫描行情都改去 `11111`，一次 sy portfolio read 仍会在 `11112` 创建 quote connection，并以 quote login 作为 broker read 的前置条件。trade-intake 的 trade client 也通过同一个 `_ensure_clients()` 触发 quote client 创建。
- **为什么有问题**: 计划把配置路由当成足够的分层，但真正的耦合位于 infrastructure gateway。implementation agent 若只改 config/resolver，无法达到声明行为；若临时绕过 readiness，又可能让账户读取在未验证 trade login/identity 时运行。
- **直接证据**: `src/infrastructure/futu_gateway.py:39-48` 同时创建 quote/trade contexts，`:56-62` 两种 accessor 都经过同一个 `_ensure_clients()`；`:570-586` 的 ready builder只检查 quote readiness。`src/application/futu_portfolio_context.py:497-521` 使用账户 endpoint 构建该 gateway 后读取 balance/positions。
- **影响**: sy quote 权限和工作集仍会被激活；quote 权限被踢或未登录时，sy 的账户事实读取也可能失败；测试可能只证明 config 输出变了而没有证明真实 socket/client 边界变了。
- **建议改法和验证点**: 在计划中加入一个窄的 gateway ownership slice：quote client 与 trade client必须独立 lazy-create；定义 typed `quote readiness`、`trade readiness` 和 `broker identity readiness`，禁止 portfolio/trade path 以 quote readiness 代替 broker readiness。先列出所有 `build_futu_gateway` / `build_ready_futu_gateway` callers 并分类。新增 spy/fake backend tests，证明 sy balance/positions/trade-intake 路径不构造 `OpenQuoteContext`，generic quote 路径不构造 `OpenSecTradeContext`，同时保留 close、timeout 和 error mapping。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR-03-未修复-高-单一 lx quote owner 会形成第二套 endpoint 权威，且未收敛跨市场权限与降级契约

- **位置**: normalized claim 1；配置 authority、market entitlement、fallback 和 health contract。
- **问题类型**: 架构边界 / 过度设计 / open question 未收敛
- **当前写法**: 新增一个显式 quote owner/resolver，初始固定 `lx@11111`，所有 US/HK 股票与期权 generic quote consumers 共用。
- **反例/失败场景**: 某市场或期权权限只在 sy 登录上可用；lx 在桌面/手机端发生最高行情权限互踢；US 和 HK runtime snapshots 对 lx endpoint 或 security firm 不一致；symbol-specific fetch 已明确指向另一个合法 provider/endpoint。一个全局 `lx` 选择会把所有账户的扫描同时降级或失败。若同时保留 `symbols[].fetch.host/port`，则新 quote-owner 配置与现有 fetch binding 发生双真源漂移。
- **为什么有问题**: 账户归属不是行情正确性的充分条件。计划没有定义 owner 是全局、按 market、按 security firm 还是按 symbol/provider，也没有定义权限不足、quota 耗尽、market kicking、mixed config 和 fallback 的 fail-closed 行为。
- **直接证据**: `src/application/required_data_prefetch_planning.py:797-805` 已以 `symbol + source + host + port` 作为 fetch dedupe/binding 身份，说明现有 fetch 配置已经承担 endpoint authority。刚完成的 Strategy Lab binding 还专门要求跨 market endpoint 一致，而不是从账户名直接猜 endpoint。Futu 官方说明同一账户的多个终端只有一个可持有最高行情权限，并提供 `auto_hold_quote_right` 控制：<https://openapi.futunn.com/futu-api-doc/en/qa/opend.html>。订阅 quota 也按 OpenD 全部连接汇总：<https://openapi.futunn.com/futu-api-doc/en/quote/query-subscription.html>。
- **影响**: 全账户无候选、错误使用降级行情、配置漂移被隐藏，或为了处理例外继续增加 provider/account/market 层级，造成过度设计。
- **建议改法和验证点**: 不要先新增重复 host/port authority。计划应先选择唯一真源：优先保留现有 canonical fetch binding，让 service/profile 只投影该 binding；如确需以账户选择 endpoint，只存 `owner_account`，host/port 必须从 canonical account config 派生并与每个 market 的 fetch binding做一致性校验。明确支持范围是 per-market 还是 global，记录 security firm、所需股票/期权 quote rights、quota 和 `auto_hold_quote_right` 策略。权限不足、跨市场不一致或 binding 冲突必须在 render/validate 阶段 fail closed；不得运行时静默改去另一个交易 endpoint。测试至少覆盖 US/HK mismatch、权限/quote-login unavailable、quota exhausted、symbol override、旧新 config mixed state。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR-04-未修复-高-交易故障域拆分需要新的 capture/apply 状态机，当前一句“单一 applier”不足以安全实施

- **位置**: normalized claims 2、5；trade-intake service、durable inbox、SQLite writer 和 failure/recovery sequencing。
- **问题类型**: 状态机漏洞 / 并发恢复风险 / 切片过粗 / 过度设计
- **当前写法**: 未来把 lx/sy 各自做成 capture service，写各自 durable inbox，再由一个串行 applier 写 canonical SQLite ledger，以避免两个进程并发写账本。
- **反例/失败场景**: 直接渲染两个现有 trade-intake service 时，CLI 没有 listener-only 的 account selector；两个进程可能各自解析全部 sources，重复订阅/回补。同一 source capture 成功、applier crash、receipt/outbox 部分提交、cursor 未推进时，重启可能重复应用或永久卡住。若改为两个 listener 直接写 ledger，又引入跨进程 SQLite contention、通知/outbox ordering 和部分账户活着但 systemd 总体看似健康的问题。
- **为什么有问题**: 现有 per-account inbox path 和 broker deal key 只提供身份基础，不等于已经存在 capture/apply handoff protocol。计划未定义 inbox ownership、claim/lease、ack、cursor、transaction boundary、poison row、retry、backfill/push race、shutdown、schema migration、mixed-version 或 receipt authority。
- **直接证据**: `src/application/trades/account_mapping.py:352-397` 已解析 per-account sources、state/audit/status/inbox；`src/application/ledger/external_event_key.py:6-12` 已将 broker event key 命名为 `futu:<account>:<futu_account_id>:<deal_id>`。但 `src/application/trades/auto_intake.py:300-359` 明确规定任一 source 结束即停止 siblings，`:377-390` 默认加载全部 sources，`:408-410` 还限制 `--account` 只用于 reconcile-state。`src/application/service_deploy.py:1246-1306` 只渲染一个 trade-intake unit，并让它依赖全部 OpenD units。
- **影响**: 重复成交、漏成交、账户状态与 canonical ledger 不一致、恢复不可判定，或 implementation agent 被迫在一个性能 work unit 内重新设计关键交易状态机。
- **建议改法和验证点**: 从当前 shared-quote work unit 中删除 capture/applier 实现，只保留为独立后续设计议题；先决定“交易分开”是否仅指 OpenD credential/state，还是还要求 listener process failure isolation。若确需后者，单独编写 state-machine plan，至少定义 source-select public contract、一个 capture 只能拥有一个 source、inbox row lifecycle、claim/lease/ack、ledger+outbox transaction、crash points、retry/poison policy、push/backfill convergence、mixed-version migration和 per-account health aggregation。用 deterministic crash-restart、duplicate delivery、late backfill、one-account auth failure、SQLite busy 和 applier unavailable tests 验证。
- **修复风险（低/中/高）**: 高
- **严重程度（低/中/高/严重）**: 高

### PR-05-未修复-高-HOME/data 分离被放进同一方向但没有可回滚迁移契约，也没有证据表明它会减载

- **位置**: normalized claims 4、6；production migration、rollback 和 completion evidence。
- **问题类型**: 范围漂移 / 并发恢复风险 / 测试缺口
- **当前写法**: 为 lx/sy 设置独立安装目录、配置、HOME 和数据目录；不要复制 live DB/Device.dat；迁移后做冷启动和 IO 验证。

## Architecture boundary review

The proposal currently crosses four ownership boundaries in one direction: fetch binding, Futu infrastructure clients, trade-intake state machine, and production OpenD state directories. The quote/broker boundary cannot be implemented only in config because the infrastructure gateway couples both SDK clients. The listener/applier split cannot be implemented only in service rendering because it creates a new durable handoff protocol. The HOME migration cannot be implemented as source delivery because it changes external device/login state. These must be separate work units with independent acceptance and rollback.

## Best-practice review

The plan is missing pre-registered performance signals, typed readiness by capability, a single endpoint authority, a crash-recovery state machine, and an operational migration runbook. Those are necessary for testability and recovery in a broker-connected system. Existing account-scoped identity and inbox paths are useful foundations, but they do not close these gaps.

## Optimal-solution review

The most credible minimal path is not the whole reviewed proposal. It is:

1. prove whether duplicate quote activity on `11112` is material;
2. if material, split quote/trade client creation and readiness at the existing gateway boundary;
3. project one already-canonical fetch binding into generic quote consumers and service dependencies;
4. validate resource impact before changing listener topology or HOME;
5. track trade listener isolation and HOME migration as separate follow-up work units only if their independent goals justify them.

This path produces an observable answer sooner and avoids coupling a performance experiment to a new transaction state machine.

## Overengineering review

The proposed capture/applier protocol and a new quote-owner configuration authority are not yet justified by measured pressure or an explicit security requirement. Existing fetch bindings, per-account source definitions, inbox paths, and broker event keys should be reused. New public entities or state transitions require concrete failure cases and independent plans.

## Overcoupling review

The current proposal couples quote routing success, trade process isolation, canonical ledger serialization, OpenD device state, systemd graph changes, and capacity closure. A failure in any one would make the entire rollout difficult to attribute or roll back. Each slice needs one owning boundary and a success signal that does not depend on future slices.

## Open Questions

1. Is the primary goal resource reduction, broker-account correctness, process fault isolation, or credential/privilege isolation? A two-process lx-dual-role topology satisfies only the first two partially.
2. Is continuous sy deal push/backfill mandatory? If not, a bounded activation schedule may be simpler than a new quote/trade architecture.
3. Which login currently owns the required US/HK stock and options quote rights, security firm, and subscription quota? Can one endpoint legally and operationally serve every configured market?
4. Should generic quote authority remain the existing per-symbol fetch binding, become per-market, or become one global account-derived binding?
5. Must sy portfolio reads work when sy quote login is unavailable? If yes, what typed trade readiness and account identity probe replaces the current quote readiness gate?
6. Does “交易分开” require separate OpenD processes only, or separate OM listener processes too?
7. If listener processes are split, who owns inbox apply, notification/outbox authority, and crash recovery?
8. What measured threshold would justify independent HOME migration despite its potential increase in unique page cache?

## Residual Risks

- A single shared quote endpoint remains a scanning single point of failure even after a correct implementation.
- Highest quote rights can be displaced by another terminal; entitlement availability remains an external-state dependency.
- The two required trade endpoints may still exceed the current cgroup memory envelope without any OM quote load.
- Distinct HOME/data directories improve state ownership but may increase working-set size.
- Reusing lx OpenD for quote and lx trading cannot provide strong least-privilege isolation.
- Cross-host/container separation may ultimately be required for resource and blast-radius isolation; it should be tracked only after the two-process capacity evidence exists.

Suggested tracking destinations:

- shared quote/broker gateway boundary: new source-only architecture plan;
- trade listener/capture/applier: separate transaction-state-machine plan or Gateflow work unit;
- HOME/device migration: separate production migration runbook and authorization gate;
- memory/refault validation: append-only host experiment artifact tied to the existing Incus remediation plan.

## Final Plan Review Conclusion

`fail`

The direction “共享市场事实、账户级券商事实独立” is sound, but the reviewed proposal is not code-generation-ready. It assumes an unproven performance benefit, overlooks the current gateway's quote/trade client coupling, creates a competing endpoint authority, sketches a new transaction state machine without recovery semantics, and combines a high-risk HOME/device migration with source architecture work.

Before implementation, revise the plan into a measured gateway/fetch-binding slice and explicitly defer listener-state-machine and HOME migration work. Re-run planreview on that narrower artifact.
