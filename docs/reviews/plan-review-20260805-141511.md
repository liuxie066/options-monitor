## Special review lenses

### Architecture boundary review

The core implementation preserves one-way ownership: the trade runtime owns due planning and provider invocation; the source inbox owns disposable attempts and leases; the pure ledger semantic module owns normalization/fingerprinting; and the ledger writer owns atomic business admission. Additional `ledger.api`/`queries` and `lifecycle_reconciliation` changes are necessary plumbing for the planned compact query and shared account snapshot, not new business scope. No ledger-to-trades/provider dependency was introduced.

### Best-practice review

The later evidence-revision, scoped-control-query, state-coherence, unified-completion, lease-renewal, and source/account batch-lease changes are justified correctness repairs. Each closes a concrete history-growth, crash, claim-leak, stale-state, or overlap counterexample. Removing them to reduce line count would reopen a reviewed failure mode.

### Optimal-solution review

The core design remains the smallest credible durable solution under the stated crash/restart/concurrency requirements. A kill switch alone would not protect new required sources; a source-local checkpoint cannot own canonical idempotency; a global semantic unique key would suppress `A -> B -> A`; and a per-case lease cannot serialize the shared account snapshot after the first case completes.

### Overengineering review

The settlement-specific capability contract, attempt row, admission head, evidence revision, and batch lease all have current failure evidence. The generic inbox-summary revision/cache does not depend on settlement semantics and can be delivered independently. Keeping it in the same work unit increases review and rollback surface without being required to prove canonical settlement correctness.

### Overcoupling review

The delivery-status cache reaches lifecycle cases/evidence/timing/outbox/batches/receipts because its existing snapshot reads all of them; the mutation revision is broad but coherent with that snapshot owner. The inbox-summary cache is source-local and technically separable, even though it shares `inbox.py` and `auto_intake.py` with core attempt state.

## Findings

### PR-SCOPE-01-未修复-中-final plan 后补了通用 inbox retry 优化，与通过评审时的 settlement-only 范围不一致

- **位置**: current plan `Decision`/`Non-goals` lines 5-7 and 39-44; later-added status design lines 281-295; S3 lines 326-327; resource tests lines 419-422; accepted review `plan-review-20260805-075711.md` lines 12-14, 26, and 44; implementation `src/application/trades/inbox.py::trade_inbox_revision()`, `src/application/trades/auto_intake.py::_cached_trade_inbox_summary()`.
- **问题类型**: 范围漂移 / 过度设计 / review traceability
- **当前写法**: The plan says the work is generic only inside `settlement_observation`, changes no unrelated periodic CPU fault, and requires other collectors to opt in separately. The same final plan now requires a revision/cache for the complete `trade_inbox` history, independent of settlement cases or collector capabilities.
- **反例/失败场景**: A source with no lifecycle settlement case still benefits from and executes the generic inbox-summary cache. A regression or rollback in that cache affects listener retry/status behavior even though the settlement collector is disabled. Reviewers cannot tell from the current plan that this was added after the original pass rather than part of the accepted baseline.
- **为什么有问题**: DR9-02 correctly identified another fixed-frequency history scan, and the user's broader concern was same-class CPU faults. However, the written work-unit boundary deliberately narrowed generality to settlement. Updating the plan after the finding makes final code appear aligned but does not erase the scope amendment. This weakens minimality, rollback isolation, and approval traceability.
- **直接证据**: The accepted review states that generality is intentionally limited to settlement and does not repair unrelated periodic jobs. DR9-02 explicitly calls the inbox path independent of cash flow, settlement capability, and ledger evidence. The final plan later adds the inbox revision/cache to design, S3, tests, and completion evidence. Current source implements that cache in the generic listener path.
- **影响**: The work unit is larger than the reviewed settlement contract; a single commit would mix canonical settlement correctness with an independently deployable listener-history optimization; future rollback or blame cannot isolate them cleanly.
- **建议改法和验证点**:
  - Preferred: retain the lifecycle delivery-status cache in the core work unit because DR9-01 proves it still scans the incident's inflated settlement history on every heartbeat; split only the generic inbox-summary revision/cache and its tests into a separate follow-up commit/work unit.
  - Alternative: if “same-type problem” intentionally includes every 60-second historical scan in trade-intake, explicitly amend `Decision`, `Goals`, and `Non-goals` and add a dated scope-amendment section naming DR9-02. Do not continue calling the result settlement-only.
  - In either case, preserve the existing resource tests and verify unchanged summary semantics, revision-before/after cache safety, and listener retry behavior.
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

## Non-findings: expansions that should not be removed

- DR7/DR8's evidence revision and candidate-scoped control reads enforce the original bounded-idle-cost invariant; they replace an accidentally linear implementation and are not optional optimization.
- DR10/DR11's duplicate-state coherence checks prevent semantic deduplication from permanently suppressing a missing business transition.
- DR12/DR13's completion owner and renewal guards prevent ordinary exceptions or resource exhaustion from leaking a live claim and bypassing persistent backoff.
- DR14/DR15's source/account batch lease is required by the plan's one-account-snapshot optimization; without it, a second worker can rematerialize history after the first case releases its per-case claim.
- `ledger/api.py`, `ledger/queries.py`, and `lifecycle_reconciliation.py` were not all named as primary S3 files, but their changes are direct adapters for planned storage/query and coherent-snapshot ownership, not feature expansion.
- The absence of changes in `src/infrastructure/futu_gateway.py` and `src/application/config_validator.py` is not an implementation gap: current main no longer has the cash-flow production requirement, typed query metadata is preserved at the settlement adapter, and config validation is enforced by `config_yaml.py` plus account mapping tests.

## Process drift

The final plan says each S1-S3 slice is reviewed independently before aggregate review. Actual work used iterative aggregate DeepReview findings DR1-DR15 and a final clean aggregate review rather than three explicit slice-completion reviews. Full regression and the clean aggregate review mitigate code risk, but the plan should not be treated as a literal execution log.

## Open questions

## Residual risks and suggested tracking

- Production CPU thresholds and natural-tick behavior remain unverified until separately authorized release/deployment/start; local deterministic tests cannot prove host contention.
- Source/account leases coordinate only workers sharing the same source-local inbox database. Cross-source or cross-host provider-call duplication remains a topology risk, while canonical ledger admission remains authoritative.
- The implementation is large enough that future maintenance should preserve the current settlement-specific interfaces rather than generalize them into a repository-wide retry framework without a new design review.
- Track the generic inbox-summary cache as a separate work unit/commit unless its expanded scope is explicitly accepted.

## Final conclusion

**pass-with-risks**

There is no material goal drift and no unrelated business-feature expansion. The final code is aligned with the final plan, and almost all growth is necessary correctness hardening discovered by DeepReview. The one real horizontal expansion is the generic inbox-summary revision/cache. It is technically sound and addresses the same broad performance pattern, but it exceeds the settlement-only plan that originally passed. Split it or explicitly record the scope amendment before treating this as a minimal, review-stable work unit.
