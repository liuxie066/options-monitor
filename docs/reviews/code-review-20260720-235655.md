## Findings

### B1-未修复-中-展示上限会静默隐藏候选和持仓
- **入口/函数**: `render_full_brief` / `render_daily_brief_lifecycle` -> `_candidate_views` / `_position_views`
- **文件(行号)**: `src/application/daily_decision_brief_renderer.py:235-286`, `330-352`
- **输入场景**: 任一策略候选数超过 `max_candidates_per_strategy`，或持仓数超过 `max_actions_per_priority`。
- **实际分支**: `_RenderBudget.take()` 截断列表，返回值只包含被选中的记录；投影和 Markdown 都没有记录被省略数量。
- **预期行为**: 紧凑简报可限制明细数量，但必须提示仍有未展示项，避免用户把“未显示”误解为“不存在”。
- **实际行为**: 超限记录完全消失，且没有省略提示。
- **直接证据**: `_candidate_views` 对每个 family 调用 `budget.take(rows, limit)` 后只遍历 `selected`；`_position_views` 同样只返回 `selected`。旧 renderer 曾明确输出省略数量，当前改写删除了该语义。
- **影响**: 用户可能错误判断候选或持仓全集，属于局部但直接影响决策理解的展示错误。
- **建议改法和验证点**: 在 allowlisted user view 中增加候选/持仓省略摘要；测试超过上限时显示省略数量，且摘要不得包含内部字段。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### B2-未修复-中-资金区绕过候选展示上限导致消息不再紧凑且上下文不一致
- **入口/函数**: `_render_user_view` -> `_capacity_views`
- **文件(行号)**: `src/application/daily_decision_brief_renderer.py:396-429`
- **输入场景**: Sell Put 或 Covered Call 候选数量大于配置的 `max_candidates_per_strategy`。
- **实际分支**: 候选区按 limit 截断，但 `_capacity_views` 再次遍历原始全部候选，未接收任何 limit。
- **预期行为**: 资金区只解释本条消息中展示的候选容量，并保持与候选区相同的确定性上限。
- **实际行为**: 候选区可能只显示 3 个候选，资金区却列出所有候选；大列表可挤占消息长度并造成“资金项对应哪个候选集”的歧义。
- **直接证据**: `_capacity_views` 使用 `source.get("sell_put")` / `source.get("covered_call")` 全量循环；调用点没有传入 `limits`。
- **影响**: 可读性退化，且消息截断时可能丢失后续持仓/资金内容。
- **建议改法和验证点**: 将同一候选上限传入资金投影，只为展示中的候选生成容量说明；加入候选区与资金区一致性回归测试。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
