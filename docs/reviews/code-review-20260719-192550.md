# Deepreview — Daily Decision Brief Aggregate

## Findings

### CR-AGG-1 — High — Crash after immutable revision write permanently wedges future preparation

- **Code location**: `src/application/daily_decision_brief_repository.py:94-112`, `src/application/daily_decision_brief_repository.py:204-208`.
- **Entry point / triggering input**: `prepare_daily_decision_brief()` has an existing same-day current revision, allocates the next revision, successfully writes the immutable revision JSON, then the process is interrupted before `current.json` is replaced.
- **Actual branch**: the next invocation trusts the still-old current revision to calculate the same next revision; because the orphan immutable file already exists, line 111 raises `DailyDecisionBriefStateError("daily brief revision already exists")` before any reconciliation or forward allocation.
- **Expected behavior**: a completed atomic immutable revision write must not make the account+market state permanently unavailable; the next locked preparation should preserve the orphan and allocate a revision strictly after every existing same-day immutable revision.
- **Actual behavior**: every later scheduled scan repeats the same conflicting allocation and fails, so the default recovery slot cannot recover without manual state deletion.
- **Direct evidence**: an injected failure on the second `atomic_write_json()` call leaves `r0001.json` plus a current pointer at revision 0; the next unmodified prepare fails on the pre-existing `r0001.json`. The accepted plan explicitly names revision/delivery-pointer crash windows as an aggregate-review target.
- **Impact**: once production enablement occurs, one process interruption in the publication window can suppress all later Daily Brief generation and monitoring for that account+market+day, defeating the 10:00/later-slot recovery contract.
- **Fix direction**: under the existing account+market lock, calculate the next revision as one greater than the maximum of the validated current revision and all existing same-day immutable revision filenames. Preserve orphan files; do not delete or rewrite immutable history. Add a crash-injection regression for both an existing-current and no-current first-publication window.
- **Fix risk**: low; the change remains inside revision allocation and keeps current/delivery validation fail-closed.
- **Severity**: High.

### CR-AGG-2 — Medium — Existing high-priority action becoming active is silently dropped from the delta

- **Code location**: `domain/domain/daily_decision_brief.py:199-246`.
- **Entry point / triggering input**: the last delivered brief contains a stable P0/P1 action in `blocked`, `observe`, or `invalidated` state, and a later scan returns the same action ID as `active`; a P2 action can likewise cross into active P1 without changing identity.
- **Actual branch**: the action is not new, is not necessarily upgraded to P0, is not downgraded, and does not transition away from active, so no change is emitted.
- **Expected behavior**: entry into the active P0/P1 actionable set is material, just as a new P0/P1 action is material and leaving that set is an invalidation. A recovered Close Advice action must not remain silent merely because its stable position identity did not change.
- **Actual behavior**: `diff_daily_decision_briefs()` returns `material=false` and `changes=[]` for `blocked -> active`, `observe -> active`, and `invalidated -> active` on the same P0 action.
- **Direct evidence**: a direct domain reproduction for all three prior states returns no changes. The assembler intentionally preserves stable `position_lot_id` / group identity across quote recovery, making this a reachable Close Advice path.
- **Impact**: monitoring can omit the exact scan where a previously unavailable or non-actionable close/open decision becomes executable; the user sees neither a recovery nor a new-action delta.
- **Fix direction**: treat transition into `active` P0/P1 from outside the active P0/P1 set as material, reusing the existing `action_added` change contract unless a P0-upgrade change already communicates the transition. Add domain and scenario-level regressions, including stable Close Advice identity.
- **Fix risk**: low; same-tier rank/price noise remains excluded because already-active P0/P1 actions do not match the transition.
- **Severity**: Medium.
