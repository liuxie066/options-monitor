# Plan Review — Automatic Release Version Recommendation（重要性校准复审）

- **Reviewed target**: `docs/plans/automatic-version-recommendation-plan-20260720-094901.md`
- **Review date**: 2026-07-20
- **Review scope**: 产品目标、版本分类规则、preview/confirm/apply 状态、远端基线、写入安全、手动路径兼容、架构边界、实施切片与测试计划
- **Review posture**: adversarial，但只报告正常发布流程中真实、重要、会改变实施决策的问题
- **Conclusion**: **pass-with-risks**

## 1. 本轮重要性门槛

本轮不再把“理论上还能更严密”视为 implementation blocker。只有满足以下至少一项，才作为 finding：

1. 在正常 release workflow 中有现实概率产生错误的 `major|minor|patch` 推荐；
2. 有现实概率导致未经确认或基于过期证据写错 `VERSION`；
3. 会破坏现有手动 `patch|minor|major|target_version` 行为；
4. 会越过项目核心安全边界；
5. 计划缺少关键决策，implementation agent 必须重新设计才能实施。

以下内容不再升级为 blocker：超出声明格式的畸形输入、极低概率并发窗口、受控 tag namespace 中尚未出现的异常、已有明确 ownership seam 的实现细节，以及不影响 v1 正确性的通用加固项。

## 2. 为什么前几轮一直能找到“问题”

前几轮后期的主要偏差不是方案始终不成立，而是 review 门槛发生了漂移：

- 把 v1 advisory 工具按通用发布事务系统的强度审查；
- 把可选 hardening 当成必须先解决的 correctness blocker；
- 每次为低概率场景增加新机制后，又继续攻击新机制的边界，形成无限加固循环；
- 没有充分利用现有发布链的下游保护：`release_check.py`、VERSION 驱动的 GitHub workflow、tag/release collision，以及最终人工确认。

Planreview 应阻止高代价错误，而不是证明系统对所有异常输入和所有并发模型完备。按本轮门槛，方案已经达到可实施状态。

## 3. Goal and success signal understood

方案目标明确：

1. 使用远端最高稳定版本作为计算基线；
2. 使用标准化 `CHANGELOG.md / ## Unreleased` 作为唯一语义声明；
3. 按 `Breaking Changes > Added > Changed/Fixed` 推荐 `major > minor > patch`；
4. preview 默认只读，用户明确确认后才采用；
5. apply 只写 `VERSION`，不自动修改 Changelog、commit、push、tag、release 或生产环境；
6. 保持现有手动升级路径兼容；
7. 无法可靠分类时返回 `needs_input`，而不是猜测。

这些成功信号与用户要求一致，并且可以通过现有 Tool、Git 临时仓库测试和 VERSION 文件断言验证。

## 4. Assumptions tested

### 4.1 Unreleased 可以作为 v1 的语义 authority

**成立。** 方案没有声称从源码自动证明兼容性，而是要求维护者用有限标题显式声明影响。错误声明仍可能发生，但这是产品明确接受的人工判断边界，不是分类器内部不确定性。

### 4.2 自动路径不会绕过用户确认

**成立。** `bump=auto, apply=false` 只读；写入需要 `apply=true`、现有 write permission gate、expected base/target 和 recommendation digest。方案也明确 digest 只证明 freshness，不伪装成用户授权凭据。

### 4.3 手动路径兼容

**成立。** 现有 `patch|minor|major|target_version` 保留，safe default 仍为 patch preview，并计划用既有 contract/smoke tests 固定离线手动行为。

### 4.4 基线选择不会依赖陈旧本地 tag 列表

**成立。** 自动路径重新查询指定 remote 的稳定 tag，并校验本地对象、ancestry、current VERSION 和目标 tag collision。该设计比仅使用本地 tag 更符合真实发布流程。

### 4.5 写入范围受控

**成立。** 自动路径最终只原子替换顶层 `VERSION`；不修改生产配置、运行状态、Changelog、Git refs 或远端资源。失败状态均要求 no-write。

### 4.6 现有代码边界能够承载实现

**成立。** 当前代码已有：

- `version_update` Tool 与 write gate；
- `AgentTool.input_validator`，可实现 auto apply 的条件必填校验；
- `release_target.py` 的 SemVer 解析/比较边界；
- `version_check.py` 的 VERSION 读写 facade；
- contract、smoke 和 version tests。

implementation agent 不需要重新设计公共入口或引入新的状态存储。

## 5. Findings

**无 material findings。**

没有发现满足本轮重要性门槛、需要阻止 implementation 的问题。

## 6. 对上一轮五个 finding 的重新裁决

### PR4-01 — 未知二级标题终止 Unreleased

**裁决：非阻塞 residual risk。**

方案已规定唯一、严格的 `## Unreleased` 和有限三级标题 grammar。未知 H2 属于未遵守标准 authoring contract 的输入。进一步限定“下一个 H2 必须是合法 release heading”是合理 parser hardening，但正常发布路径有人工 Changelog review，且后续 `release_check.py` 仍验证目标版本段。它不构成 v1 实施阻塞。

### PR4-02 — remote 查询后的本地 TOCTOU / VERSION CAS

**裁决：非阻塞 residual risk。**

方案在 apply 时重新计算证据、再次检查 remote，并以原子替换写入单个本地 `VERSION`。理论上另一个进程仍可在最终检查与替换之间修改本地文件，但这要求非常窄的并发窗口和非标准的平行本地发布操作。为 v1 引入 repo lock 或通用 CAS 会显著增加复杂度，不符合当前风险收益比。

### PR4-03 — 条件 required 输入未映射到 validator

**裁决：普通实现细节。**

代码已经提供 `AgentTool.input_validator`。把 auto apply 的 digest/base/target 条件校验放在该 seam 即可；方案无需为此重新设计 schema 系统。实现和测试时固定即可。

### PR4-04 — remote Git 没有 timeout / non-interactive 契约

**裁决：建议 hardening，不阻塞 correctness。**

bounded timeout 和禁用交互式 credential prompt 是良好实践，应在实现时采用；缺少这两项最可能造成调用等待或运维体验差，不会静默生成错误推荐或错误写入。远端失败本身仍应 fail closed。

### PR4-05 — leading-zero stable tags

**裁决：低概率 namespace 风险。**

当前仓库有 444 个 stable-like tags，未发现 leading-zero stable tag。受控发布流程也使用 `v${VERSION}`。auto parser 采用 canonical stable SemVer 是便宜的改进，但当前不存在会让正常发布基线不确定的实际证据，因此不应阻塞实施。

## 7. Architecture boundary review

**通过。**

- recommendation engine 只读并位于 application 层；
- SemVer primitives 归 `release_target.py`；
- VERSION write 仍归 `version_check.py`；
- Tool adapter 只负责输入、输出与权限适配；
- domain、生产 service upgrade、release workflow 和 inbound confirmation state machine 不被拉入本 slice。

没有发现跨层反向依赖或必须重构现有架构才能实现的问题。

## 8. Best-practice review

**通过，附非阻塞建议。**

方案具备该类功能最重要的实践：显式 intent、fail-closed、preview-before-write、freshness 校验、幂等 no-op 结果、手动兼容、确定性输出和 Git topology tests。

实现时建议但不设 gate：

1. 条件字段使用现有 `input_validator`；
2. remote Git 使用参数数组、合理 timeout 和 non-interactive 环境；
3. canonical stable tag parser 只服务 auto path，避免影响既有 prerelease consumers。

## 9. Optimal-solution review

**当前方向是可接受的实际方案。**

相较于解析任意源码 diff、建立 API/schema compatibility detector 或把推荐强制施加到所有发布路径，使用标准化 Changelog intent 更简单、可解释、可测试，也符合 advisory 定位。

计划中的 freshness digest 和 remote identity 校验略偏保守，但已经被限制在一个新只读 recommendation module 与 auto apply 分支内；现阶段没有充分理由要求再次重写成更小或更通用的系统。

## 10. Overengineering review

**没有需要阻塞实施的过度设计 finding。**

方案经过多轮 review 后包含较多 defensive checks 和 64 个测试场景，实施时应防止把文档中的每个说明扩展成新抽象。以下内容明确不需要：

- 数据库或持久化 confirmation receipt；
- 通用 repo transaction/lock framework；
- Markdown AST 框架；
- GitHub API 依赖；
- 自动源码兼容性推断；
- 第二个 version recommendation Tool。

如果实现严格保持三个 slice 和现有 facade，复杂度仍可控。

## 11. Overcoupling review

**通过。**

计划已经把 semantic declaration、Git evidence、Tool permission 和 VERSION write 分开。需要继续保持：

- auto 的 canonical tag/remote 规则不要改变 service upgrade 的 prerelease 解析行为；
- Tool validator 不进入 recommendation engine；
- generic VERSION writer 不依赖 Changelog 或 remote；
- docs 和 release test mapping 不反向驱动生产逻辑。

这些均属于已明确的实施边界，不是未决设计问题。

## 12. Open questions

没有必须在 implementation 前由产品方裁决的 open question。

以下可由 implementation agent按现有项目惯例选择，不改变公共行为：

1. remote Git timeout 的具体秒数；
2. canonical stable tag 检查放在新 parser 的正则还是解析后校验；
3. auto apply 条件字段 validator 的具体错误消息。

## 13. Residual risks and tracking

1. **Changelog 声明可能与真实兼容性不一致。** 这是 advisory 工具的已知产品边界；由人工 review 和发布检查承担，不在 v1 自动推断源码语义。
2. **极窄的本地并发修改窗口。** 第一版接受 single-operator release workflow；若未来出现真实并发发布证据，再增加窄 CAS/lock。
3. **畸形 release heading。** 实现可顺手验证 canonical release H2，但不需要引入通用 Markdown parser。
4. **remote command 等待。** 实现建议增加 timeout/non-interactive；作为可靠性 hardening 跟踪，不改变分类规则。
5. **非 canonical stable tag。** 当前仓库没有此类 tag；建议 auto parser拒绝 leading-zero 形式，不迁移现有全局 parser。
6. **方案文本偏长。** 实施应以 S1/S2/S3 的 exit criteria 为主，不为每个 defensive note创建独立 abstraction。

建议 tracking destination：实现 PR 的 checklist 和 focused tests；无需另建阻塞 issue。

## 14. Final conclusion

**pass-with-risks**。

当前方案已经可以交给 implementation agent。没有发现会在正常发布流程中现实地导致错误推荐、错误写入、手动路径回归或核心安全边界失守的 material blocker。

上一轮五项问题应降级为实现提示或 residual risk，而不是继续修改 plan 的理由。下一步应停止循环加固，按 S1 -> S2 -> S3 实施，并用 focused tests 和 release preflight 验证。
