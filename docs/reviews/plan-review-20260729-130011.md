## Previous finding closure

上一轮 5 个 findings 均已在 plan 中实质收敛：

1. **账户级 integrity failure**：plan 现在明确通过 `AccountRunOutcome.ran_pipeline=False -> ran_pipeline_accounts -> pipeline_succeeded=false` 阻断 normal Daily Brief，并保留未受影响账户的可靠性。
2. **watchlist 外持仓 routing**：plan 现在只接受 resolved account/base runtime symbol config，禁止默认 source/localhost/port，并为 missing config、unsupported source 和 route conflict 定义 typed failure。

5. **business date 漂移**：plan 现在捕获一次 `run_started_at_utc` / `business_date`，frozen consumer 从 verified artifact读取，不再重新读取 wall clock。

新增的 canonical hash、deterministic ordering、report pending/success/failed commit-marker 和 S1 release gate 也补上了上一轮 residual sequencing/re-entry 风险。

4. **Frozen receipt 可以成为唯一 freshness authority**：通过。现有 snapshot validator 已校验 receipt hash、producer run、payload、timestamps、expiry、fetch plan/policy 和 exact raw/CSV bytes。

## Special review lenses

### Architecture boundary review

requirements 构造、routing resolution、frozen consumption 和 notification reliability 的 owner 已基本正确。剩余边界问题是 candidate route 与 Close Advice route 的冲突裁决：candidate demand 是既有 planning authority，不能被新增 position requirement 反向撤销。

### Best-practice review

单一 receipt authority、manifest-bound recovery、commit-marker-last、pending/failed invalidation 和 failure projection符合 fail-closed / audit / re-entry 最佳实践。缺口集中在 eligibility 和 partial-failure isolation，而不是 provenance 机制。

### Optimal-solution review

不需要为 route conflict 增加第二套 output path 或多 endpoint snapshot。最小安全方案是给既有 candidate route 优先权：相同 binding 的 position requirement 合并，不同 binding 的 position requirement typed unavailable；只有没有 candidate demand且 position routes 自身冲突时，才让该 symbol 不 fetch。

### Overengineering review

requirements artifact 与 report status state machine 均有跨账户审计、恢复和 stale-success invalidation 的直接需求，不构成无依据抽象。相反，为 disabled Close Advice 账户仍读取 ledger、构造 requirements 和扩大 prefetch 是不必要工作，应在 eligibility 入口消除。

### Overcoupling review

当前 route-conflict 写法把新增 Close Advice coverage 与原 candidate availability 绑成全有或全无，违反 plan 自身的单账户/position failure isolation。应保持单向依赖：Close Advice 可以复用 candidate route，但 Close Advice-specific route failure不能降低 candidate route。

## Findings

### PR2-01-未修复-高-route conflict 会撤销既有 candidate fetch，违反 plan 的隔离目标
- **位置**: plan §6 第 294 行、§7.1 第 323-327 行、§10.4 第 661-663 行
- **问题类型**: 状态机漏洞 / 架构边界 / 过度耦合
- **当前写法**: §6 明确要求 Close Advice requirements 失败不能移除 Sell Put / Covered Call / Combo Yield 的原有 market demand；但 §7.1 又规定 candidate demand 与任一 position requirement 的 binding 不同就让整个 symbol `required_data_route_conflict`，两侧都不 fetch；验收进一步要求该 symbol fetch count=0。
- **反例/失败场景**: candidate plan 已有 `0700.HK -> opend:11111` 的合法 demand；某账户 active position 因 account override 解析到 `opend:11112`。新增 Close Advice requirement 触发 route conflict 后，plan 让 `0700.HK` 完全不 fetch，原本可正常执行的 candidate scan也变成 snapshot unavailable，可能阻断该账户或另一个账户的 Daily Brief。
- **为什么有问题**: 本 work unit 的目标是让 Close Advice 不再破坏共享 candidate authority。将 Close Advice-specific routing conflict 升格为整 symbol failure，等于用 planning-time failure 重新制造同类跨消费者耦合；它还直接与 plan 第 16、294 行的明确隔离约束冲突。
- **直接证据**: plan 第 294 行写明 requirements failure 不能移除原有 demand；第 323-327 行要求不同 binding 时“不执行任何一侧 fetch”；第 661-663 行把 `fetch count=0` 列为验收。当前 `build_cross_account_prefetch_config()` 已先从 base/account watchlist构造 candidate source items（`src/application/required_data_prefetch_planning.py:50-116`），因此新增 requirement 可以在合并阶段识别为附加 demand，而不必反向撤销已有 candidate item。
- **影响**: 原本可靠的 candidate symbol 变为 unavailable；未受影响账户也可能丢消息；计划违反自己的 root-fix success criteria；实施后仍出现 order/route-dependent notification failure。
- **建议改法和验证点**:
  - 明确 route precedence：已有 candidate demand 的 canonical binding 保持权威且必须继续 fetch。
  - position binding 相同时合并 exact contracts；不同时只把冲突 position requirement 标为 `required_data_route_conflict` / not-evaluable，不改变 candidate fetch。
  - 无 candidate demand时：所有 position requirements binding 相同则 fetch once；position bindings 互相冲突则这些 positions typed unavailable，symbol 不 fetch。
  - global plan 和 diagnostics 同时记录 preserved candidate binding 与 rejected position requirement ids，禁止静默改路由。
  - 增加回归：valid candidate binding + conflicting position binding，断言 candidate fetch count=1、candidate consumer可靠、冲突 position not-evaluable、另一个账户不受影响；只有 position-only route conflict 才 fetch count=0。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR2-02-未修复-中-requirements eligibility 未与 effective `close_advice.enabled` 对齐
- **位置**: plan §1 第 12-16 行、§6 第 272-283 行、S2；`src/application/account_run.py:781-798`
- **问题类型**: 范围漂移 / 过度设计 / 测试缺口
- **当前写法**: plan 对“本轮所有 scanning accounts”的 active positions 读取 ledger、解析 route 并加入 requirements，没有先筛选该账户是否会实际运行 Close Advice。
- **反例/失败场景**: `sy` 参加 candidate scan，但 effective account config 中 `close_advice.enabled=false`。当前 runner 根本不会调用 `run_close_advice()`；plan 却仍为 sy 读取 ledger并拉取 position contracts。若这些 positions 缺 config 或与 candidate route 冲突，会增加 typed errors、rate-limit budget，按当前 PR2-01 规则甚至可能移除其它账户的 candidate fetch。
- **为什么有问题**: requirement 应由实际 consumer demand 驱动。为没有 Close Advice consumer 的账户规划持仓行情违反最小改动和单一 prefetch 的 budget约束，也让 disabled feature 影响 enabled feature。
- **直接证据**: 当前 `account_run.py:781-782` 只有在 `bool(close_advice_cfg.get("enabled", False))` 时才执行 Close Advice；plan §6 则对全部 scanning account 构造 requirements，没有 eligibility 状态或 disabled test。
- **影响**: 不必要的 ledger I/O 和 OpenD calls；rate-limit budget被扩大；disabled account 可能影响 candidate/其它账户 availability；artifact status产生无消费方的噪声。
- **建议改法和验证点**:
  - 在 ledger读取前定义 `close_advice_eligible_accounts`：仅包含 scanning 且 effective account runtime config 中 `close_advice.enabled=true` 的账户。
  - artifact 可选择省略 disabled 账户，或显式记录 `status=not_applicable`；必须在 plan 中二选一并说明其不计入 complete/partial/failed denominator。
  - disabled account 不读 ledger、不生成 requirements、不参与 route conflict、budget 或 prefetch。
  - 新增测试：disabled account 有 active positions、missing binding 和 divergent route，断言 requirements/fetch/plan id 与删除该账户 positions 时相同，且 enabled account candidate/Close Advice 均不受影响。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

## Open Questions

- 无需产品级新决策。PR2-01 可按“candidate demand 优先、conflicting position typed gap”收敛；PR2-02 可优先选择 artifact 显式 `not_applicable`，便于审计 scanning account 为什么没有 requirements。

## Residual risks and suggested tracking

- **Off-watchlist position**：即使修复 findings，找不到 canonical runtime binding 的 position 仍会 not-evaluable。保留 `required_data_symbol_config_missing` metric，并在频率持续非零时单独决定是否扩展 config authoring contract。
- **External writer race**：plan 能检测并阻断，但不能阻止进程外 writer。继续跟踪 snapshot integrity audit；不要在本 work unit 引入跨进程锁或第二套缓存。
- **Rate-limit growth**：exact position expirations 仍可能增加 prefetch budget。跟踪 dedup 后 symbol/expiration/contract counts 及 wave waits。
- **Large dirty worktree**：实施前必须检查 core files 是否与现有未归属改动重叠；若重叠，按 plan 的停止条件确认所有权或使用 clean worktree。

## Conclusion

**fail**

上一轮 5 个 blockers 已关闭，修订后的 provenance、re-entry 和 failure-projection 设计已接近可实施。但新的 routing precedence 自相矛盾：Close Advice route conflict 仍可撤销既有 candidate demand；同时 requirements 尚未按 `close_advice.enabled` 限定 consumer scope。这两点应在交给 implementation agent 前收敛，并补对应隔离测试。
