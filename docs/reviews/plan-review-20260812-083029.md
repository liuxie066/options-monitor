## Findings

### PRR1-01-未修复-高-Daily Brief 与 AI Advice 仍可绕过 terminal manifest 消费部分 snapshot

- **位置**: Goal and exit contract item 3; Authority model; Slice S1 items 5-6; Slice S2/S3 consumer lists
- **问题类型**: authority bypass / slice omission
- **当前写法**: 计划新增 `candidate_snapshot_manifest.v1.json` 并声明新运行只有 manifest 才证明完整，但实施步骤只要求发布 manifest；没有要求当前运行的 Daily Brief 和 AI Advice 在读取 opening/Combo/CC+LP snapshot 前先验证它。
- **反例/失败场景**: opening snapshot 已写入，Combo snapshot 或 manifest 写入前进程中断；随后 Daily Brief 仍直接加载 opening snapshot，并把 Sell Put/Covered Call 候选视为可用。反向场景中，Combo snapshot 已写入但 manifest 缺失，Daily Brief 仍可直接加载 Combo 行。
- **直接证据**: `assemble_daily_decision_brief()` 分别调用 `_load_opening_candidate_families()`、`_load_combo_yield_snapshot_family()`、`_load_cc_lp_snapshot_family()`，后两者直接调用 owner loader，没有 terminal manifest gate (`src/application/daily_decision_brief_service.py:145-171,815-931`)；AI Advice orchestration 直接验证调用方提供的 opening snapshot (`src/application/ai_decision_advice/orchestration.py:96-137`)。
- **影响**: 同一不完整 account-run 在 research/replay 中 fail closed，却可能在实际通知/Advice 中被当作有效候选，破坏新增 manifest 的唯一目的并造成事实口径分裂。
- **建议改法和验证点**: 在 S1 明确新增单一 account-run candidate authority loader：先验证 manifest，再按 manifest hash 加载 owner snapshots；Daily Brief 和 Advice 当前运行入口都只消费该 loader 的结果。对 pre-manifest 历史读取另走显式 limited 分类，不允许当前运行静默降级。增加“每个 owner seal 后、manifest 前中断”的 Brief/Advice 回归，必须输出 candidate evidence unavailable，不能展示部分候选。
- **修复风险**: 中
- **严重程度**: 高

### PRR1-02-未修复-高-status index v1 无法独立给出 Combo owner，legacy completeness 仍可误判

- **位置**: Authority model manifest owner derivation；Historical compatibility classification；Slice S1 item 5；Slice S3 item 3
- **问题类型**: expected-owner authority / legacy classification ambiguity
- **当前写法**: manifest 的 exact owner set 被描述为由 status scopes 和 configured Combo variant 推导；pre-manifest history 则只写“use the validated strategy status index to derive expected scopes”。计划没有固定 variant 来自哪个 immutable artifact，也没有决定 status index 是否升级。
- **反例/失败场景**: v1 index 只有 `(symbol, strategy_family=combo_yield)`；同一 scope 可能应由 `combo_yield_candidate_snapshot.json` (SP+LC) 或 `cc_lp_candidate_snapshot.json` (CC+LP) 承担。若期待 CC+LP 但只有 SP+LC 文件，文件发现无法证明 owner 正确；若缺失目标 owner，更无法从 v1 index 判断应该缺哪一个。
- **直接证据**: `publish_strategy_scan_status_index()` 仅排序/保存 market、symbol、strategy_family 和 status payload，不含 variant/owner，也不绑定 account-config hash (`src/application/strategy_scan_status.py:145-227`)；variant 目前只在 pipeline 的 resolved account config 中计算 (`src/application/pipeline_watchlist.py:913-946`)；每个 run 已有 write-once `state/config.override.json` 和 `account_config_sha256` authority (`src/application/tick_run_workspace.py:21-117`)。
- **影响**: 新 manifest 的构建规则可能由实现者临场选择；旧 v1 run 可能在 SP+LC/CC+LP owner 错配或缺失时被标为 limited-supported，而不是 unsupported/incomplete。
- **建议改法和验证点**: 计划必须锁定新契约：将 index 升为 v2，每个 expected item 明确 `candidate_owner` (`opening|sp_lc|cc_lp`) 和 strategy mode，并绑定 account config hash；manifest 只接受 v2。pre-manifest v1 仅在验证 write-once account config、其 hash 与所有可读 snapshots 一致，并用该 config 将 Combo symbol 映射到 variant 后，才可成为 limited；任何无法唯一映射的 scope 为 `unsupported_snapshot_schema`/missing。增加同一 symbol 的 SP+LC/CC+LP 错配、缺 config authority、config-hash mismatch 测试。
- **修复风险**: 中
- **严重程度**: 高

### PRR1-03-未修复-中-零 expected scope 的终态没有定义

- **位置**: Authority model；Historical compatibility states；Cross-slice no-false-authority
- **问题类型**: state-machine gap
- **当前写法**: 新运行缺 manifest 一律 incomplete，manifest 又由 expected owner snapshots 发布，但未说明扫描确实执行且 prefilter 后 expected scopes 为空时是否发布空 manifest，以及它属于 `supported` 还是 `not_scanned`。
- **反例/失败场景**: watchlist 存在，但本账户经过 holdings/capacity prefilter 后没有 SP/CC/Combo scope。若不发布 manifest，该正常运行被误报 `unsupported_snapshot_missing`；若按文件缺失归 `not_scanned`，又无法区分“扫描执行且无适用 scope”和“根本未执行”。
- **直接证据**: 当前 expected status set 在运行时经过 `apply_prefilters()` 才形成，合法地可能为空 (`src/application/pipeline_watchlist.py:516-568`)；opening snapshot 当前拒绝空 modes，正是既有 Combo-only 问题的一部分。
- **影响**: 正常的 no-applicable-scope 账户持续产生假告警，或被错误归入未扫描历史，影响 Daily Brief、research coverage 和 readiness。
- **建议改法和验证点**: 固定：只要 candidate scan 阶段成功抵达 terminal commit，就发布允许 `expected_owners=[]`/`expected_scopes=[]` 的 manifest，并分类为 `supported` + stable `no_applicable_scope`（不是 `no_candidate`，也不是 `not_scanned`）；`not_scanned` 只用于没有 scan-attempt authority 的历史运行。增加空 watchlist-after-whitelist/prefilter 的正常完成与中断对照测试。
- **修复风险**: 低
- **严重程度**: 中

### PRR1-04-未修复-中-`output_mode` 迁移仍未选定唯一可执行边界

- **位置**: Slice S2 item 5 and primary files
- **问题类型**: code-generation ambiguity / version skew
- **当前写法**: “generated-runtime input boundary” 和 “previous generated schema/metadata” 没有指定函数、schema/version 判定、是否在 freshness 前后执行，或多个入口如何保持一致。
- **反例/失败场景**: scheduled tick 经 `multi_account_tick.py` 直接 `json.loads` 后走 identity/freshness，再由 pipeline config loader 验证；Agent tools 经 `agent_tool_config.load_runtime_config()` 读取；两条路径不是同一 loader。只改其中一处会令 old generated runtime 在另一处保留/报错。仅看 `_generated.source_format=yaml` 又不足以证明它确为受信生成文件。
- **直接证据**: scheduled runtime 在 `src/application/multi_account_tick.py:317-350` 直接加载并验证 identity/freshness；pipeline validation 在 `src/application/config_loader.py:86-143`；Agent tools 使用 `src/application/agent_tool_config.py:58-111`。当前 generated schema 固定为 `1.0` 且 source hashes 由 freshness contract 校验 (`src/application/runtime_config_freshness.py:15,107-226`)。
- **影响**: 实施者可能添加多个不一致 compatibility branches，或遗漏主 tick/Agent 任一入口；后续升级/应急 stale-config 行为不可预测。
- **建议改法和验证点**: 在计划中选择一个可证明、共享的纯函数（例如 runtime-config contract 模块中的 `normalize_retired_generated_fields`），输入完整 root config，仅对明确上一生成 schema、generator/source_format、且已通过 source/freshness proof 的 runtime payload 删除 no-op key；main tick、pipeline loader、Agent loader 复用该函数。或者明确选择受控 upgrade 强制重建并让旧 runtime fail closed，不能同时保留模糊的两套方案。测试必须覆盖 scheduled、Agent、authored YAML、forged/unproven JSON、allow-stale 五条入口。
- **修复风险**: 中
- **严重程度**: 中

## Open questions

- 现有 `strategy_scan_status.v1` 单文件会 hash Combo candidate CSV。计划应明确升级后的 per-symbol status 不再要求候选 artifact，且 index v2 的 owner/scope metadata 来自 parent-resolved config，而不是从这些单文件反推。
- `not_scanned` 需要一个可验证的 scan-attempt定义；新 manifest 的空 terminal commit 可解决新运行，历史无 terminal marker 时只能保持 unknown/not-scanned 的有限语义。

## Residual risks

- Combo v2 的体积风险仍应在 S1 artifact 中记录；当前 compact-record 选择足以继续设计，不构成本轮阻塞。
- 历史 v1 status index 本身不是 write-once seal；即使结合 immutable config，它也只能支撑 limited、非 promotion-authoritative 读取。
- 历史 CSV 文件物理删除仍不在本 work unit。

## Final conclusion

`fail`。首次 review 的 pair-state、owner-independent sealing、legacy-v1 category 已收敛，但 terminal manifest 还未成为 Daily Brief/Advice 的强制消费门，Combo owner 真源和零-scope 状态仍未闭合，`output_mode` 迁移也没有唯一实现边界。修订这些点后再进入 implementation。
