# Plan Review — Required Data and Multi-Account Integrity

- Review target: `docs/gateflow/required-data-multi-account-integrity/plan.md`
- Work unit: `required-data-multi-account-integrity`
- Review mode: mandatory adversarial PlanReview before implementation
- Scope: the seven confirmed fixes, their contracts, state machines, slice ownership, recovery behavior, and validation plan
- Base: `origin/main@ed2531e956f7ff818b3198a6dc3d918bb5328b3f`
- Review timestamp: `20260804-100017`

## Assumptions tested

- Tested whether the files allowed by each slice include the actual receipt, seal, planner, repository, consumer,
  and CLI owners required to implement its claims.
- Tested fresh, cached, success-empty, subprocess, crash-after-publication, and same-run terminal re-entry paths for
  required-data publication.
- Tested whether sequential per-account reads can prove one SQLite generation when lifecycle, allocation, assigned
  stock, or combo identity changes without changing the three global projection hashes.
- Tested prepared option-context authority against every current ledger/cache fallback, including global path-risk
  loading and Close Advice output promotion.
- Tested zero-position accounts, missing or untrusted decision snapshots, cross-midnight lifecycle evaluation, and
  partial ledger-group publication.
- Tested FX and event provider failure separately from artifact publication/integrity failure.
- Tested exact-spec execution with cached `None` spot, pre-existing tool idempotency records, malformed spec payloads,
  and mixed physical bindings.
- Tested the scheduler failure boundary against current CLI/runtime-path owners rather than only scheduler-domain
  tests.

## Findings

### PLR-01-未修复-高-S1 没覆盖 receipt、seal 和直接发布路径的真实所有者

- **位置**: S1 `Allowed files/modules`、`Exact allowed changes`、完成信号。
- **问题类型**: 架构边界 / 不可直接实施 / 契约缺失。
- **当前写法**: S1 要求所有 fresh/cache/subprocess/success-empty publication 经过唯一 finalizer，并由 seal
  exact-compare plan、binding、policy，但允许文件没有列出 receipt publisher、seal resolver 和另一个直接 receipt
  publication caller。
- **反例/失败场景**: 实现只改 `multi_tick/required_data_prefetch.py`，而
  `required_data_steps.py` 或 `opend_symbol_outputs.py` 仍能绕过 post-write coverage 发布 receipt；seal 继续以
  `bundle.fetch_plan or plan_item.fetch_plan` 接受不一致计划。
- **为什么有问题**: S1 的核心成功信号是所有 publication path 都受强制后置条件保护；没有修改真实 owner，
  该成功信号无法由代码结构保证。
- **直接证据**: `src/application/opend_symbol_outputs.py:187-306,374-470`；
  `src/application/required_data_snapshot.py:315-365`；`src/application/required_data_steps.py:227`；原计划 S1
  allowed-files 列表。
- **影响**: 实施 Agent 被迫越界或留下旁路；subset、bad RV、wrong plan 仍可能获得成功 authority。
- **建议改法和验证点**:
  - 将上述三个 owner 纳入 S1，或让所有生产 caller 必须调用同一个 publication boundary；
  - publisher 强制验证 final CSV/fetch contract，seal 强制 exact plan/binding；
  - 增加直接 publisher 的 subset、bad RV、wrong binding 测试，以及 bundle/plan mismatch seal 测试。
- **修复风险（低/中/高）**: 中。
- **严重程度（低/中/高/严重）**: 高。

### PLR-02-未修复-高-S1 的 expected contract、partial 语义和 crash re-entry 未闭合

- **位置**: `Required-data result contract`、S1 state transition/error handling/invariants/tests。
- **问题类型**: 契约缺失 / 状态机漏洞 / 并发恢复风险。
- **当前写法**: plan 同时要求“symbol 无有效 receipt 时 partial”和“receipt identity 冲突中止 manifest”；
  声称 exact policy match，却没有定义 plan 侧的 policy authority；也只写了 exactly-one publication，没有定义
  receipt 已发布但 summary/seal 前崩溃后的 adoption。
- **反例/失败场景**:
  - 一个 symbol receipt policy 或 binding 错误导致整个 run 无 terminal manifest，而确认目标要求该 symbol typed
    failed/partial；
  - finalizer 在 receipt publication 后崩溃，重入用新的 completion time 构造非逐字节相同 receipt，触发 immutable
    destination conflict；
  - RV-required 但 discovery 无合约时，`success_empty` 被错误当作 RV 缺失，或反向无条件跳过 RV 契约；
  - plan 没有独立 policy authority，只能让 receipt 自证 policy 正确。
- **为什么有问题**: receipt 是 commit record，必须有稳定 expected identity 和可恢复的 adopt 语义；单 symbol
  故障不能扩大成全局 plan 损坏。
- **直接证据**: `src/application/opend_symbol_outputs.py:277-304` 默认 completion time；
  `src/application/position_advice_source_receipts.py:76-155,891-896` write-once byte equality；原计划
  `Required-data result contract` 与 S1 error handling。
- **影响**: same-run 无法恢复、重复 observation、错误扩大故障域，或错误 receipt 仍被 seal。
- **建议改法和验证点**:
  - 先构造 canonical `expected_fetch_contract`，绑定 exact specs、physical binding、RV/coverage policy，并把 hash
    纳入 plan identity；policy 只比较由 plan 明确拥有的稳定字段；
  - 全局 plan 自身损坏才阻止 manifest publication；每个 symbol 的 receipt/fetch-contract/binding mismatch 形成
    typed failed entry，manifest terminal status 为 partial/failed；
  - 无合约 discovery 明确定义 RV 为 `not_applicable_no_contracts` 且不调用 RV provider；
  - finalizer 先查找并严格验证同 run、同 bytes、同 expected contract 的已有 receipt，匹配则 adopt；fresh/cache/
    success-empty 使用 frozen evidence 的稳定 observation/completion identity；
  - fault-injection 测试 receipt-last 后崩溃与重入，断言 path/bytes 不变、无第二次 publication；测试 wrong-policy
    receipt 与 correct receipt 同时存在时只能选择正确者。
- **修复风险（低/中/高）**: 中。
- **严重程度（低/中/高/严重）**: 高。

### PLR-03-未修复-高-S3 的归档顺序与“启动前失败”语义矛盾

- **位置**: S3 `State transition`、`Error handling`、tests。
- **问题类型**: 状态机漏洞 / 不可直接实施。
- **当前写法**: state transition 写成 run-state publish -> child start -> compatibility archive，下一行又要求
  archive failure 在 child start 前阻断。
- **反例/失败场景**: child 已读取并产生输出后 compatibility archive 失败；调用方却将账户报告为未启动或失败，
  留下部分副作用，且无法证明 archive bytes 与 consumed bytes 相同。
- **为什么有问题**: 两条要求不能同时实现；配置 authority 必须在任何 child side effect 前形成一个完整原子
  publication transaction。
- **直接证据**: 原计划 S3 state transition/error handling；当前 archive 位于
  `src/application/account_run.py:971` 的 pipeline/Close Advice 之后。
- **影响**: 重叠 run 仍可能留下不可解释的半完成状态，测试和实现会选择不同顺序。
- **建议改法和验证点**:
  - 明确为：canonical serialize once -> atomic consumed-state write -> atomic compatibility write from the same bytes
    -> verify both hashes -> child start；
  - archive failure fault injection 必须断言 pipeline/Close Advice child 未调用。
- **修复风险（低/中/高）**: 低。
- **严重程度（低/中/高/严重）**: 高。

### PLR-04-未修复-高-S5 用顺序账户读取和三个全局 hash 不能证明完整 ledger generation 一致

- **位置**: `Coherent ledger and Close Advice plan v2`、Implementation decision 6、S5 exact changes/invariants。
- **问题类型**: 架构边界 / 并发恢复风险。
- **当前写法**: 对共享 ledger 的账户逐个调用 `decision_state_snapshot()`，比较 global event、stored-lot、
  reprojected-lot fingerprints，不同则全组 unavailable。
- **反例/失败场景**: `lx` 读取后、`sy` 读取前，另一个 writer 只更新 lifecycle evidence/allocation、assigned-stock
  或 combo identity。这些事实进入 account context，但可不改变三项 global projection hash；两个账户仍被错误声明为
  同一 generation。
- **为什么有问题**: 目标要求同一 run 的共享账户消费同一事实 generation；事后比较一组不完备 hash 不能替代
  同一数据库读事务。
- **直接证据**: `src/application/ledger/repository.py:2939-3073` 在每账户 read 中还读取 lifecycle、assigned-stock、
  combo facts；`src/application/positions/context_builder.py:163-181,270-306` 消费这些事实。
- **影响**: 账户上下文跨 generation 混合，核心一致性目标失效且难以从 manifest 检出。
- **建议改法和验证点**:
  - 在 ledger repository/API 增加窄的 `read_decision_state_rows_many(accounts)`：同一 resolved SQLite path、一个
    connection 和一个 `BEGIN` transaction 内读取组内所有账户；application 从返回 rows 构造 snapshots；
  - 保留单账户 API 兼容，不增加 schema/lock/framework；将 repository/API owner 加入 S5 scope；
  - 并发测试在两个 account snapshot construction 之间尝试 lifecycle/identity-only write，结果必须全为事务前或
    全为事务后，绝不混合。
- **修复风险（低/中/高）**: 中高。
- **严重程度（低/中/高/严重）**: 高。

### PLR-05-未修复-高-S5 没定义 trusted snapshot、共享时间和 ledger-group 重入的完整后置条件

- **位置**: S5 state transition/error handling/invariants/tests。
- **问题类型**: 契约缺失 / 并发恢复风险 / 测试缺口。
- **当前写法**: 只要求比较 fingerprints、发布每账户 manifest，并按账户复用已有 manifest；stable position hash
  仅以 “such as” 描述排除 temporal decoration。
- **反例/失败场景**:
  - `decision_state_snapshot()` 返回 `snapshot_unavailable` 或 `projection_untrusted`，代码仍把稀疏/空 rows 解释为
    zero-lot ready；
  - 两个账户跨午夜或 lifecycle deadline 构造 context，ledger rows 相同但 DTE/lifecycle state 不同；
  - `lx` manifest 已发布后崩溃，重入复用旧 `lx`、为缺失 `sy` 读新 generation；
  - position hash 字段和排序未封闭，两个实现得出不同 identity。
- **为什么有问题**: unavailable 不是空仓，时间也是决策 authority；ledger group 的 terminal set 必须整体复用或
  整体拒绝，不能按账户拼接 generations。
- **直接证据**: `src/application/ledger/decision_snapshot.py:146-168` 返回 untrusted/unavailable；现有
  `validate_position_fact_snapshot_contract()`；原计划 S5 re-entry 和 hash 描述。
- **影响**: 错误 ready、跨账户决策分叉、terminal re-entry 混代、不可复现 hash。
- **建议改法和验证点**:
  - ready 前强制 schema、normalized account、portfolio scope、`snapshot_status==trusted`、`actionable is True`、
    合法 SHA-256 和 `validate_position_fact_snapshot_contract()==()`；zero-lot 只有 trusted contract 才 ready；
  - barrier 捕获唯一 `position_observed_at_utc`、`business_date`、`lifecycle_now_ms` 并传给所有 context builder；
  - 精确定义 position-state canonical fields、sorting、normalization；
  - terminal re-entry 只有组内全部 manifests 存在、合法且同 generation 才零读复用；任一 missing/tampered/
    cross-generation 时整个 group unavailable，禁止单账户补读；如允许 pre-seal rebuild，必须整组重建；
  - 测试 projection-untrusted、snapshot-unavailable、trusted zero-lot、跨午夜/deadline、partial manifest crash、
    tampered-one-of-two 和 terminal re-entry ledger-read count=0。
- **修复风险（低/中/高）**: 中高。
- **严重程度（低/中/高/严重）**: 高。

### PLR-06-未修复-高-Prepared authority 没有封闭实际消费 bytes、config/broker/ledger 和 live fallback

- **位置**: `Prepared option-position context`、S4/S5 exact changes、Close Advice plan v2。
- **问题类型**: 契约缺失 / 过度耦合 / 并发恢复风险。
- **当前写法**: plan 要求验证 prepared manifest/context，随后仍允许既有 pipeline/Close Advice 路径；把账户级
  generation hashes 加入每个 lot 的 stable `requirement_id`；没有绑定 exact child config、broker 或 ledger path
  identity，也没处理 prepared 模式的 global option-risk live loader。
- **反例/失败场景**:
  - validator 检查 manifest 后，consumer 再从 mutable `option_positions_context.json` 打开不同 bytes；
  - Close Advice 在输出 promote 前 context 被替换，report provenance hash 当前文件而计算使用旧内存；
  - prepared path-risk 分支又调用 global live ledger loader；
  - 同 run config/broker/ledger path 改变但 manifest 仍通过；
  - 无关 lot 或 FX 变化导致其他 lot stable requirement IDs 全部变化。
- **为什么有问题**: prepared 模式必须是一条单向且完整的 authority chain，不能“先验后重开”、不能再读 live
  ledger；stable requirement identity 不应承载 account-wide generation。
- **直接证据**: `src/application/account_run.py:799` 只向 Close Advice 传 mutable context path；
  `src/application/pipeline_context.py:163` 可改写 context；现有 global risk loader 位于
  `src/application/pipeline_context.py`; 原计划 S5 requirement-id 设计。
- **影响**: T0/T1 漏洞继续存在、通知 provenance 错误、同 run authority 可串线、identity churn。
- **建议改法和验证点**:
  - manifest loader 返回并解析一次经过 path/run/account/hash 校验的 exact bytes；prepared pipeline/Close Advice
    均从这些 bytes 消费，prepared mode 禁止 cached/shared/direct/global-live fallback；
  - 若 path-risk 真需要 global aggregate，必须从同一 batch generation 构造 broker-scoped、无外国账户明细的
    aggregate 并嵌入 prepared payload；不可用则相关账户 fail closed；
  - 在 output `os.replace()` 前重新验证 manifest、payload bytes 和 plan-v2 binding；typed integrity failure 阻断通知，
    report manifest 记录 prepared manifest/payload hash；
  - authority envelope 绑定 canonical `account_config_sha256`、normalized broker、不可逆的
    `ledger_binding_id=sha256(resolved path)`、decision/position/context/FX hashes；child config 使用同一 canonical
    serialization/hash；
  - 保持 lot-local `requirement_id` 稳定，新增 account authority hash 或 `requirement_snapshot_id`；
  - 测试 pipeline 后篡改、promotion 前篡改、prepared ledger/FX read count=0、config/broker/binding mismatch、以及
    unrelated-lot change 不改变 stable requirement id。
- **修复风险（低/中/高）**: 高。
- **严重程度（低/中/高/严重）**: 高。

### PLR-08-未修复-高-S7 混淆 artifact integrity 与 provider outcome，且遗漏真实 consumer 和重入语义

- **位置**: `Run-level FX and events`、S7 allowed files/state/error handling/tests。
- **问题类型**: 契约缺失 / 状态机漏洞 / 架构边界。
- **当前写法**: event snapshot 只有 ready/unavailable terminal status；计划说 provider failure 保持 best-effort，
  但未区分可可靠消费的 failed observation 与 artifact 不可用，也未把三处真实 reader 纳入 slice。
- **反例/失败场景**:
  - provider 对部分/全部 symbols 返回 typed error，但 artifact 原子发布成功；实现可能把它标 ready-success 或把它
    扩大为 artifact unavailable；
  - annotator 读取篡改文件后静默返回 `{}`，Daily Brief 用另一套弱 schema loader，Close Advice 得到第三种结果；
  - same-run terminal re-entry 缺失或篡改 snapshot 后再次请求 provider，形成新 generation。
- **为什么有问题**: provider 事实失败和 commit-record 失败是两条独立轴；所有账户和消费者必须共享同一已验证
  observation，而不是各自降级。
- **直接证据**: `src/application/events/prefetch.py:26-109` 无 run/status/hash 且允许 per-symbol errors；
  `src/application/events/annotator.py:16-23` 静默吞错；
  `src/application/daily_decision_brief_service.py:1326-1393` 独立 loader；
  `src/application/close_advice_runner.py:1414` 另一个 consumer。
- **影响**: 同 run 风险判断分叉、篡改被当 clean empty、provider 调用重复或账户被错误全局阻断。
- **建议改法和验证点**:
  - 定义两轴 terminal schema：artifact `ready|unavailable`（path/run/hash/schema/publication），observation
    `complete|partial|failed`（exact union coverage + per-symbol typed errors）；
  - 在 events owner 提供唯一 strict loader/validator，由 annotator、Daily Brief、Close Advice 复用；扩充 S7 files；
  - provider partial/failed 仍是 durable ready artifact，并在业务层一致 unknown/fail-closed；只有 terminal artifact
    无法发布才阻止 account start；
  - terminal re-entry 只 validate/reuse，零 provider call；missing/tampered terminal snapshot 阻断，不重抓；
  - 测试 partial/all-failed、path/run/hash/schema tamper、consumer consistency、success/failure 单次 provider call 和
    re-entry zero call。
- **修复风险（低/中/高）**: 中。
- **严重程度（低/中/高/严重）**: 高。

### PLR-09-未修复-中-FX generation 没有归属 slice 的可执行终态契约

- **位置**: `Run-level FX and events`、S4/S5 exact changes、cross-slice validation。
- **问题类型**: 契约缺失 / 切片过粗 / 测试缺口。
- **当前写法**: 计划只说 parent observes once、manual 使用 shared path、所有 context 同 generation；没有定义
  fresh/cache/stale/unavailable 状态、数值合法性、重入、账户是否依赖换算，也没有把 manual fallback 明确归入
  S4 或 S5。
- **反例/失败场景**: 部分 position manifests 发布后 FX 再抓一次；`None` 被当 empty-success；stale fallback 丢失
  reason；FX unavailable 无条件阻断 zero-lot/CNY-only account，或反向给需要换算的账户制造数值。
- **为什么有问题**: 一个 generation hash 只有在其 payload/status/source time/reason 和 re-entry 规则封闭时才是可验证
  authority。
- **直接证据**: 当前 loader 仍在 `src/application/pipeline_context.py:227,348` 使用 account state；原计划未在
  slice exact changes 中分配 shared fallback；cross-slice commands 漏
  `tests/test_pipeline_context_exchange_rates.py`。
- **影响**: 账户 FX 时间点分叉、错误成功、错误阻断或重入混代。
- **建议改法和验证点**:
  - 明确归入 S5：run-level immutable FX observation 状态
    `ready|stale_fallback|unavailable`，绑定 run、rates、source timestamp、reason 和 canonical hash；rates 必须 finite
    positive；
  - prepared consumer 只能用嵌入 observation，不调用 loader；terminal re-entry validate/reuse，零 provider call；
  - unavailable 时 FX-dependent values 为 `None` + reason，仅真正需要 conversion 的账户 blocked；trusted zero-lot/
