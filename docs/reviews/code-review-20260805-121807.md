## Findings

### DR9-01-未修复-高-heartbeat 每分钟仍全量反序列化 lifecycle 历史

- **入口/函数**: `_run_listener_source_loop()` -> `_refresh_lifecycle_delivery_status()` -> `_lifecycle_delivery_status()`
- **文件(行号)**: `src/application/trades/auto_intake.py:1864-1874,1980-2188`; `tests/test_settlement_observation.py:2098-2338`
- **输入场景**: 账户已因历史settlement loop累积大量、且单条payload较大的 lifecycle evidence/cases/outbox rows；collector现已被静态阻断或backoff，ledger在后续十个tick完全不变。
- **实际分支**: 生产listener每60秒heartbeat仍调用delivery status。该函数加载并JSON反序列化该账户全部cases和全部evidence，逐个pending case再查timing；随后读取全库notifications、全库delivery batches和全库migration receipts，再在Python按账户过滤、计数和排序。多source listener会对同一全局通知/批次历史重复执行这些读取。
- **预期行为**: 昂贵的历史诊断快照只能在其输入事实发生变化时重建；普通heartbeat应读取一个O(1)持久化mutation revision并复用上一份账户快照，或直接消费有界/增量聚合。revision读取与快照发布必须避免并发写导致把stale snapshot标成current。
- **实际行为**: DR6/DR7虽使due runtime不再重扫历史，但生产heartbeat仍沿独立路径访问同一膨胀数据。现有2,100-row回归直接调用 `reconcile_due_lifecycle_cases_for_source()`，从未进入listener heartbeat，因此十次blocked tick测试仍会全绿。
- **直接证据**: heartbeat调用位于1864-1872行；status函数1989-2065行执行全cases/evidence读取，2084-2183行执行全局notifications/batches/receipts读取。资源测试2281行以后只循环调用due runtime并计数 `read_lifecycle_account_rows()`，没有调用 `_refresh_lifecycle_delivery_status()`。
- **影响**: 即使provider调用、semantic duplicate写入和due candidate查询均已止血，线上 `trade-intake` 仍可每分钟用历史JSON做长时间CPU工作，继续挤占飞书agent共享主机资源；这直接否定“idle cost受当前工作量约束”的完成信号。
- **建议改法和验证点**: 在ledger存储owner增加单调status mutation revision，覆盖delivery status真正读取的case/evidence/timing/outbox/batch/receipt表，并由同事务trigger推进；listener为每个source缓存最后成功快照，只在revision变化时重建。读取revision前后若变化，不得缓存为current，下一次必须重建。新增真实refresh/heartbeat级2,100-row回归：首次允许一次历史读取，十个无mutation heartbeat为零次；任一相关表mutation后恰好再重建一次，dispatcher动态状态仍每次更新。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### DR9-02-未修复-中-inbox retry tick 每分钟按全部历史deal rows重新聚合

- **入口/函数**: `_run_listener_source_loop()` -> `trade_inbox_summary()`
- **文件(行号)**: `src/application/trades/auto_intake.py:1697-1727`; `src/application/trades/inbox.py:303-337,880-944`; `tests/test_trades_inbox.py:1-165`
- **输入场景**: source长期运行后 `trade_inbox` 保留大量handled历史deal，当前没有pending/retryable row；listener仍每60秒执行inbox retry检查和status刷新。
- **实际分支**: `trade_inbox_summary()` 每次执行 `GROUP BY status` + `COUNT(*)` + `MAX(attempt_count)`，必须遍历全部inbox rows；现有retry索引不覆盖 `attempt_count`，而即使增加covering index也仍是O(history)扫描。summary在无任何row变化时没有revision/cache短路。
- **预期行为**: 无mutation的retry tick应通过O(1) source-local revision复用上次summary；enqueue/status/attempt变更和delete必须与业务写同事务推进revision，且首次升级无需历史回填即可安全做一次全量snapshot。
- **实际行为**: 另一条与cash flow、settlement capability和ledger evidence无关的自然历史增长曲线仍位于常驻60秒循环中；当前测试只验证summary值，没有资源上界。
- **直接证据**: retry tick 1719行无条件重算summary；summary SQL 318-321行对整个 `trade_inbox` 分组；schema仅有 `(status, updated_at_ms, received_at_ms)` retry索引，没有materialized counts、mutation token或缓存owner。
- **影响**: 即使lifecycle历史路径完全修复，长期deal历史仍可逐步提高listener idle CPU并拖慢同机飞书响应；这与本迭代要解决的“固定频率任务反复扫描自然增长历史”属于同一故障类型。
- **建议改法和验证点**: 为inbox DB增加由INSERT/UPDATE/DELETE触发器推进的单调revision；listener缓存summary并用revision前后校验控制重建，保留现有summary作为首次/变更后的权威计算。新增大量handled rows回归，证明十个无mutation retry ticks只聚合一次，enqueue、retry状态变更和delete均使revision推进并触发一次新snapshot。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 中
