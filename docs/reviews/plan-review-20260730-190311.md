## Goal and boundary understood

The work unit only promotes provider-successful zero option data to a reliable,
non-actionable `success_empty` outcome. It must preserve a complete frozen quote
and candidate source graph, show a local warning, and continue the existing
normal degraded-delivery path. Provider, parse, partial, not-attempted, and
adopted-source integrity failures remain fail-closed. Notification persistence,
delivery kinds, authority-token contracts, and retry state are explicitly
outside the change boundary.

## Special review lenses

### Architecture boundary review

Acquisition, source sealing, strategy projection, Brief assembly, and rendering
remain assigned to their existing owners. The plan correctly avoids moving raw
provider classification into the renderer. One notification assertion,
however, conflates authority-token availability with the downstream delivery
decision and therefore crosses the plan's explicit notification-flow boundary.

### Best-practice review

Positive empty evidence, exact target propagation, immutable receipt binding,
and fail-closed source integrity are sound. Tests should assert the public
decision actually selected, rather than require removal of an otherwise valid
recovery capability from the authority object.

### Optimal-solution review

The existing plan-time discovery and existing delivery state machine remain the
smallest credible path. No new source schema or notification workflow is
needed. Correcting the acceptance language is safer than changing the
notification authority contract.

### Overengineering review

No new abstraction is required. Treating normal and fixed-failure capability
tokens as mutually exclusive would force an unnecessary notification-contract
change that the work unit explicitly excludes.

### Overcoupling review

The success-empty classifier is not coupled to delivery persistence. The
remaining issue would create such coupling by making a local data-quality
feature dictate which recovery token the notification authority may expose.

## Findings

### PR-01-未修复-高-计划把互斥的投递选择误写成互斥的 authority capability

- **位置**: §5.7 Notification flow；§7.4 不回归；§8 Slice B 直接断言；§9 完成定义
- **问题类型**: 架构边界 / 契约缺失 / 范围漂移 / 测试缺口
- **当前写法**: 计划同时要求“不修改 notification decision 或 repository”“normal 与 fixed-failure authority 互斥”，并要求正确 warning 和 projection mismatch “只授权 normal delivery”。
- **反例/失败场景**: 当前可靠 Brief 的 `notification_authority` 可以同时携带 `normal_delivery_allowed=true`、`fixed_failure_delivery_allowed=true` 以及各自用途受限的 token。下游先计算 `normal_report_reliable`，再由 `decide_daily_brief_notification()` 单选 `fixed_report|candidate_alert|fixed_failure|none`。因此可靠的 degraded Brief 会选择 normal action，但 fixed-failure recovery capability 仍可存在。
- **为什么有问题**: 若实现 Agent 按字面满足“只授权 normal”，必须修改现有 authority-token 生成或通知决策契约；这直接违反本计划“不修改 notification flow/token/retry”的边界。若保持现有契约，则 §7.4、§8 和 §9 的验收无法按字面通过。该矛盾会诱导范围漂移，或让测试把正确行为判成失败。
- **直接证据**:
  - 计划 §5.7 明确排除 notification decision、repository、delivery key、confirmation 和 retry 改造。
  - 计划 §7.4、§8、§9 又要求 normal 与 fixed failure 不会同时授权，并要求 success-empty 只授权 normal。
  - `src/application/daily_decision_brief_service.py:1010-1140` 独立构造 normal token 与 fixed-failure token，没有以 normal capability 抑制 fixed-failure capability。
  - `src/application/tick_notification_flow.py:784-852` 先计算 `normal_report_reliable`，再把两种 capability 交给现有 decision owner 单选 delivery action。
  - `tests/test_daily_decision_brief_notification_flow.py:180-226` 的可靠 Brief fixture 明确保留两种 capability，证明这是现有受测契约。
- **影响**: 实施 Agent 可能越界修改 notification authority/public contract；或者完成定义永久不可满足；或者测试错误地要求删除 fixed-failure recovery token。
- **建议改法和验证点**:
  - 把所有“normal 与 fixed_failure authority/授权互斥”改为“单次 delivery action/envelope 互斥”。
  - 对 success-empty 和 projection mismatch 断言：`normal_delivery_allowed=true`、Brief 非 blocked、decision action 为现有 normal action，且不生成 fixed-failure artifact/envelope；不要断言 `fixed_failure_delivery_allowed=false`。
  - 对 adopted-source integrity failure 断言：`normal_delivery_allowed=false`、decision action 为 `fixed_failure`，且只生成 fixed-failure envelope。
  - 保持 authority-token 生成、repository、delivery key、confirmation 和 exact retry 不变。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高
