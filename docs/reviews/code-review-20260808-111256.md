## Findings

### 1-未修复-低-containment 检查不防符号链接逃逸

- **入口/函数**: `read_notification_perception_events()` -> `_audit_paths()` -> `_resolve_path(containment=base/"output_runs")`
- **文件(行号)**: `src/application/notification_perception_read.py:212-224`
- **输入场景**: 运行环境中 `output_runs`（或其下某个 run_id 目录）是指向仓库外目录的符号链接，例如运维把运行产物目录挂到外部数据盘。
- **实际分支**: `_resolve_path` 对目标路径和 containment root 都调用 `.resolve()`，符号链接被解引用后再比较。若 `output_runs -> /external/data/output_runs`，则 `output_runs/<run_id>/...` 解析到 `/external/data/...`，`relative_to(root)` 仍然通过，读取发生在仓库边界之外。
- **预期行为**: 与仓库既有先例一致（`src/application/opening_candidate_snapshot.py:231` 对快照指针显式拒绝符号链接），containment 边界要么拒绝符号链接，要么明确记录"允许经符号链接外置 output_runs"这一部署前提。
- **实际行为**: 静默跟随符号链接。`run_id` 单组件校验堵住了 `../` 穿越，但符号链接维度仍开放。已用临时目录实测：symlink 的 output_runs 指向外部目录时，外部 `audit_events.jsonl` 被成功读取并返回事件。
- **直接证据**: `_resolve_path` 第 216-219 行 `path.resolve()` / `(containment or base).resolve()`；全程无 `is_symlink()` 检查。
- **影响**: 低。攻击面要求攻击者已能控制 run_id 且运行目录被放置符号链接；正常部署 output_runs 在仓库内为普通目录。但与本次修复"收窄路径边界"的目标不一致，属于同一问题的残留维度。
- **建议改法和验证点**: 取决于 Open Question 1 的答案。若生产不存在符号链接部署：在 run_id 分支解析前对 `base/"output_runs"` 及目标 run 目录做 `is_symlink()` 拒绝，并加符号链接回归测试。若生产确实外置：保持 resolve 语义，在注释/文档中记录此前提。验证点：symlink 场景下读取被拒绝（或文档化的允许），普通目录场景全部 121 个相关测试保持绿。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低
