## Findings

### 1-未修复-高-run-global coverage scope 未绑定账户级需求，可能把一个账户的缺口扩散到另一个账户

- **位置**: provider outcome scope identity；`required_data_coverage` producer contract；candidate source account-relevant scope selection
- **问题类型**: 架构边界 / tenant isolation / 契约缺失
- **当前写法**: opening scope key 是 `market + symbol + purpose + strategy_family + option_type`；coverage payload覆盖跨账户 union fetch plan；各 Account Run 再选择“自己的 ready opening scopes”，但没有定义 account-to-union-plan projection identity。
- **反例/失败场景**: `lx` 和 `sy` 都配置 `0700.HK covered_call`，但 DTE、strike window 或 position requirements 不同。共享 planner 合并两份 side plans；只覆盖 `lx` 所需 expiration A，`sy` 所需 expiration B 失败。当前 opening scope key 对两账户相同，coverage 只能把这个 scope标成 ready 或 incomplete：标 ready 会让 `sy` 使用不完整数据，标 incomplete 会无谓降级 `lx`。
- **为什么有问题**: 物理 fetch outcome 属于 run-global，但“该结果是否完整覆盖某账户的策略需求”属于 account plan projection。当前计划只定义前者的共享 artifact 和后者的消费动作，没有定义两者之间可校验的绑定。
- **直接证据**:
  - 目标计划 `72-85,219-230,276-279,307-318`；
  - `src/application/multi_tick/required_data_prefetch.py:125-180` 会把同 symbol 的多个 source configs 合并成一个 fetch plan；
  - `src/application/multi_tick/required_data_prefetch.py:305-370` 当前 global plan summary 以合并后的 symbol/fetch plan 为身份，而不是账户级策略 scope。
- **影响**: 局部 provider/coverage failure 可能跨账户扩散，或更严重地把未覆盖账户误判为可靠；直接违反“局部问题不阻断全局”和账户隔离要求。
- **建议改法和验证点**: 在 coverage payload 同时保存：
  1. run-global `physical_fetch_outcomes[]`，按 fetch binding/spec identity 标识实际请求结果；
  2. `consumer_scope_projections[]`，以 `account + market + symbol + purpose + strategy_family/requirement_id + account_plan_hash` 为稳定 identity，列出所需 physical outcome refs 并计算 ready/degraded outcome。
  Account Run 只能消费与自身 account/plan hash 精确匹配的 projection；缺失、重复、跨账户或 projection/physical refs 不一致均 blocked。测试两账户不同 DTE、不同 strike、一个账户 position-only requirement、单一 expiration 局部失败、账户顺序/worker 数变化和 projection tamper。
- **修复风险（低/中/高）**: 高
- **严重程度（低/中/高/严重）**: 高

## Open Questions

- consumer projection 是否包含明文 account label？建议包含 normalized account 与 account plan hash；这是本地运行证据，不包含 portfolio payload，清晰度高于额外哈希间接层。

## Residual Risks

- global coverage payload 采用所有 consumer projections 后体积会增长，但当前账户和 watchlist 规模有限；不要为此引入数据库或分页协议。
- 物理 fetch 可被多个 consumer projection 引用；validator 必须校验引用集合，不能复制 provider outcome 后各自漂移。
- account plan hash 必须来自冻结后的策略/position requirement plan，而不是 mutable config 文件 mtime。

## Conclusion

`fail`

第四轮已解决上一轮 2 项 findings，但仍有 1 个高风险的跨账户 projection 缺口。
在共享物理取数结果与账户级需求之间建立可验证映射前，不建议进入实现。
