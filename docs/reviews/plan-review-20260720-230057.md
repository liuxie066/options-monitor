## Review posture

本轮按 adversarial posture 审查：默认假设新增时间方案会把“通知可读性问题”错误扩大成全市场 scheduler 改造，或因隐藏 fallback、manual/force 识别、生产配置边界和切换时序而产生不可预测行为。只有直接证据能关闭这些风险。

## Goal / boundary understood

Revision 3 的核心目标是：

1. 保留 Daily Brief structured lifecycle、last-confirmed baseline、retry/idempotency 和审计真源；
2. 把 canonical opening lifecycle records 在用户侧稳定投影为“候选”，不是执行行动；
3. 使用 allowlist structured projection 输出紧凑、自包含、无内部字段的中文通知；
4. 将 US 运行点从 09:40 + 10:00 + 整点收敛为美东 `:40` 检查点；首轮成功扫描发送，之后仅 material change 发送；
5. HK cadence、通用 scheduler fallback、provider/transport、候选算法和持久化模型不在本次范围；
6. production schedule 作为独立、需批准、可单独回滚的配置 rollout，不与 renderer release 强绑定。

## Assumptions tested

### A1 — 09:40 后 10:00 的 20 分钟双运行点确实由现有配置产生

**成立。** `origin/main:src/application/config_defaults.py:208-275` 对 US/HK 均配置 `start_plus_min=10`、`hourly_minute=0`、`end_minus_min=10`；`origin/main:src/application/scan_scheduler.py:296-330` 分别生成 start、hourly、end targets 并去重。因此 09:30 开盘产生 09:40，下一 hourly target 是 10:00。

### A2 — 将 US `hourly_minute` 改成 40、`end_minus_min` 改成 20 可以在不新增状态机的情况下得到稳定节奏

**成立。** `_scheduled_run_targets()` 对 targets 使用 `sorted(set(targets))`，US 09:40 start target、hourly `:40` targets 和 15:40 end target会自然去重；现有 Beijing-before-02:00 gate 继续过滤 14:40/13:40 等尾部 target。Plan 给出的夏令时和冬令时 target list 与现有 `< cutoff` 实现一致。

### A3 — 这是 scan cadence 变更，不是单纯通知展示变更

**成立，且 Revision 3 已显式承认。** `scan_scheduler.decide()` 在同一个 due target 上同时产出 `should_run_scan` 和 `is_notify_window_open`。修改 US `run_points` 会把首轮之后的扫描、候选/持仓计算和 artifacts 从整点移动到 `:40`。Plan 不再把它包装成 renderer-only change，并说明夏令时/冬令时扫描次数不增加。

### A4 — 为了只解决 US 用户反馈，不需要顺手改变 HK cadence

**成立。** US/HK schedule defaults 是独立 market entries。Revision 3 将 Slice D 限定为 US entry，并要求 HK exact target regression，避免 HK 从 7 个现有 targets 意外减少为 6 个。

### A5 — 通用 missing-config fallback 和 migration default 若继续是 `10/0/10`，不会破坏本次 production guarantee

**有条件成立。** Production guarantee 必须建立在 canonical US runtime config 显式包含 `run_points` 上。Revision 3 已将该条件写成 preflight/build assertion：生成的 US snapshot 必须是 `10/40/20`，缺失时停止 rollout，不依赖 `scan_scheduler.py:395-397` 的 generic fallback。它也明确不修改 `scripts/migrate_runtime_config.py::DEFAULT_RUN_POINTS`，避免借 US UX 问题扩大通用 migration semantics。

### A6 — Manual/force 标签不能从 scheduler reason 文本推断

**成立，且 plan 已补齐 ownership。** 当前 `SchedulerDecision` 和 normalized scheduler DTO 没有 structured `force` 字段；但 `multi_account_tick.py` 已持有 `force_mode`，构造 `TickNotificationRequest` 时尚未传入。Revision 3 要求用 flow-local explicit bool/trigger kind 传递，不扩 persisted brief schema，不解析 `reason`。

### A7 — Schedule 可以与 projection code 分阶段部署和独立回滚

**成立。** Renderer/diff/trigger-context 可以先发布并在旧 US schedule 下工作；production cadence 只有在批准后从 canonical `config.yaml` + system defaults rebuild `config.us.json` 才启用。Schedule 回滚到 `10/0/10` 不需要回退用户投影代码，降低了跨层联动风险。

### A8 — `--no-send` 可以当成完全只读 canary

**不成立，但 Revision 3 已修正计划。** `--no-send` 仍可能生成 runtime artifacts；Plan 现在只允许在隔离 output root 使用它，并把远端 no-write preflight 指向 read-only status/config surfaces，不再把 no-send tick 称为只读。

## Architecture boundary review

**通过。**

- Canonical brief、diff、delivery pointer 继续由现有 service/domain/repository ownership 管理；
- user-safe projection 不删除 canonical audit identity；
- scheduler 只决定 scan/check point，Daily Brief diff 决定 send/no-send，renderer 只消费 explicit trigger/time/status；
- manual trigger 走 notification flow-local context，不污染 persisted brief schema，也不把 free-text reason 升格为协议；
- US schedule config rollout 与 projection code release 可独立启用和回滚，避免把时间策略与 renderer 强耦合。

## Best-practice review

**通过。**

Plan 采用 market timezone + `zoneinfo`、显式 data-as-of、confirmed-delivery baseline、fail-closed missing structured fields、配置 dry-run/build、隔离 no-send artifacts、exact target fixtures 和 mid-session transition tests。它没有依赖 raw ISO、broker code、reason 文本或未确认 delivery state 来生成用户语义。

## Optimal-solution review

**通过。**

可选路径主要有三类：

1. 保持现有扫描点，再增加 notification-only cooldown/第二套发送时钟；
2. 修改 scheduler 算法为“从开盘锚定每 60 分钟”；
3. 复用现有 `run_points`，只调整 US explicit config 到 `10/40/20`。

Revision 3 选择第 3 类，改动最小、无需新增状态、可用现有 target generator 和 gate 验证，也能直接消除 09:40→10:00 的 20 分钟间隔。它同时承认这是 scan cadence change，并用独立配置 rollout 控制风险。相较于新增 delivery scheduler，这是当前最实际的方案。

## Overengineering review

**通过。**

没有新增 scheduler state machine、cooldown/pending-message 状态、模板 DSL、持久化模型、配置 key 或通用 presentation framework。Manual trigger 只增加 narrow flow context；US timing 只修改既有 market entry。Plan 拒绝为一次 UX 修复重写 scheduler 或迁移全部市场。

## Overcoupling review

**通过。**

- Candidate semantics、projection、notification context、US schedule 和 docs 被拆为独立 slices；
- projection/diff 需要同版本保持用户语义和 canonical identity 一致，但 production US schedule 不被强制绑入同一启用步骤；
- HK 和 generic fallback 被明确排除；
- 测试既覆盖 pure renderer/domain，也覆盖 scheduler exact targets、config build 和 end-to-end delivery lifecycle，不要求只能通过单一大集成链路证明。

## Findings

## Open questions

以下问题不阻塞 implementation，但必须在对应 gate 留下证据：

1. `configs/system.json` 是否由脚本从 `config_defaults.py` 生成，还是需要双写维护？Implementation preflight 应确认唯一生成/校验命令，避免两个 US defaults 漂移。
2. 当前 config build 是否会在 `config.yaml` 未显式写 schedule 时稳定继承新的 US system default？必须用 dry-run fixture 证明最终 `config.us.json` 为 `10/40/20`，不能只断言 Python 常量已修改。
3. `force_mode` 是否存在除 CLI `--force` 之外的受控调用入口？所有允许实际发送的 manual path 都必须传 explicit trigger context；未知来源不得默认标“手动触发”。
4. Schedule 在交易日中途启用时，产品是否允许 10:00 已扫描后 10:40 再扫描？Plan 的技术语义允许，这是新 cadence 的第一个未处理 target；rollout 操作上更稳妥的默认是收盘后切换或下个交易日前启用。
5. 用户最终更偏好“美东固定节奏”还是“北京时间固定节奏”？本计划选择美东市场时间为 authority，因此 DST 会使北京可见时间季节性移动一小时；这应在用户文档中说明，但不需要在每条通知展示 scheduler 细节。

## Residual risks and suggested tracking destination

### R1 — DST 仍会改变北京时间观感

- **Risk**: 美东固定 `:40` 对应的北京时间在夏令时/冬令时相差一小时，用户仍可能感觉季节切换后“时间变了”。
- **Why accepted**: 交易监控以 market timezone 为 authority；强行固定北京时间会让相对开盘时间漂移。
- **Mitigation**: 文档列出夏令时/冬令时窗口；通知正文只展示 localized data-as-of，不展示 raw target/cron。
- **Tracking**: user-facing notification docs + first DST transition observation。

### R2 — 扫描延后 40 分钟改变盘中发现时点

- **Risk**: 10:00/11:00 的候选或持仓变化会到 10:40/11:40 才在 scheduled scan 中被发现。
- **Why accepted**: 扫描次数不减少，且用户明确反对 09:40→10:00 的紧邻节奏；新增独立通知时钟会带来更高复杂度。
- **Mitigation**: rollout 后观察 candidate/close-advice latency；若业务上要求整点扫描但 `:40` 发送，另开独立 policy work unit，不在本次临时加 cooldown。
- **Tracking**: first-week scheduler/run artifact review。

### R3 — Config default sources可能漂移

- **Risk**: `config_defaults.py`、`configs/system.json` 和 generated `config.us.json` 若没有单一验证命令，可能只改到一处。
- **Mitigation**: config-build fixture + production dry-run diff + generated snapshot exact assertion。
- **Tracking**: Slice D implementation evidence and release checklist。

### R4 — Copy quality仍需真实 fixture 验收

- **Risk**: 技术上无内部字段且节奏正确，但中文层次、长度和变化 banner 仍可能不够直观。
- **Mitigation**: representative initial/material/blocked/recovered/manual rendered snapshots；CEO visual sign-off before rollout。
- **Tracking**: implementation acceptance artifact。

### R5 — Revision 3 仍依赖 latest-main preflight

- **Risk**: 当前 workspace HEAD 为 `v1.2.419`，而计划依据 `origin/main v1.3.4`；实施时 upstream 可能继续变化。
- **Mitigation**: 在基于最新 `origin/main` 的干净 branch/worktree 实施，重新 inventory consumers/files/tests，禁止覆盖当前 untracked `paseo.json`。
- **Tracking**: Gateflow preflight evidence。

## Validation required during implementation

除计划已列 quality gates 外，implementation review 必须核实：

- US default/build output exact `start_plus_min=10, hourly_minute=40, end_minus_min=20`；
- HK exact targets 仍为 09:40/10:00/11:00/13:00/14:00/15:00/15:50；
- summer/winter US target list和 Beijing mapping；
- 09:40 已处理后 10:00 不再 due，10:40 正常 due；
- mid-session 切换、catch-up grace、manual force、no-send 和 already-processed paths；
- manual banner 来自 structured trigger context，而不是 scheduler reason；
- no-material lifecycle 在 provider route resolution 前结束；
- provider failure/no-send/quiet-hours 不推进 confirmed pointer；
- production config build 由 canonical authoring path生成，不手改 snapshot；
- projection release 与 schedule config activation 可独立 rollback。

## Final plan review conclusion

**pass-with-risks**

Revision 3 已达到 code-generation-ready。发送时间问题不再被模糊地处理成“改一下文案”：计划明确锁定为 US 市场时间 `:40` 的检查节奏、首轮发送 + 后续 material-only、structured manual trigger，以及独立批准/回滚的 production schedule activation。剩余风险主要是 DST 的北京时间观感、扫描时点延后和 config source drift，均已有明确验证与跟踪位置，不构成 implementation blocker。
