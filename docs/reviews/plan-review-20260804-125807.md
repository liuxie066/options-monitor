## Goal, boundary, and assumptions tested

The amendment must make S1's receipt authority true on the real canonical
in-process path without pulling all of S6 forward. It also must preserve every
ready position's exact expiry-local strike before lossy planning, bind every
successful child to the request actually invoked, and give typed and debug
coverage one numeric identity rule.

The re-review tested these assumptions:

1. A legal multi-spec in-process plan now has an explicit real execution path,
   not fixture-created `meta.requests` or one flattened Cartesian provider call.
2. The expected contract and child evidence have an exact, deterministic
   one-to-one identity rather than only a count/time relationship.
3. Every malformed ready position requirement fails before the planner can
   project a smaller valid-looking demand set.
4. Both coverage entry points use the same fixed exact-strike comparison.
5. Deferring subprocess multi-spec JSON plumbing to S6 is fail-closed, tested,
   and does not hide a current canonical-default dependency.
6. The changes remain inside existing planning, fetching, aggregation,
   publication, and coverage owners rather than creating a parallel protocol.

Assumptions 1-6 are now sufficiently specified for implementation. The current
source proves that `_resolve_execution_mode()` defaults to `inprocess`, and a
search of the authored/generated local canonical config files finds no
`runtime.prefetch.execution_mode` override. The existing pipeline path also
proves the proposed per-spec mechanics are available: it already builds one
request per `merged_specs` item, executes those requests, merges returned
payloads, and binds aggregate evidence. The amendment correctly makes the
canonical prefetch path reuse that ownership instead of inventing children.

## Prior finding closure

### PR-S1A-01 — closed — real per-spec execution is now an S1 requirement

The amendment moves the minimum evidence-critical execution into S1:

- every ordered in-process `RequiredDataFetchSpec` is invoked exactly once via
  `build_fetch_request_from_spec` on the existing gateway;
- only returned typed children are aggregated;
- the aggregate is saved/finalized once and no partial child is published;
- the existing aggregation owner is moved/exposed from
  `required_data_steps.py` through `required_data_fetching.py`, avoiding a
  second implementation;
- tests require a real two-spec call sequence and prohibit synthetic child
  metadata.

This closes the previous contradiction between S1's multi-child acceptance
contract and the current one-call Cartesian prefetch implementation. S6 keeps
only scoped-union, spot reuse, public/CLI plumbing, and subprocess multi-spec
completion.

### PR-S1A-02 — closed — ordered child request identity is frozen

Child evidence v1 is now an ordered list whose entries carry zero-based
`request_index`, canonical planned-request SHA-256, canonical symbol, physical
source/host/port binding, typed status/outcome, source observation time, and
completion time. The finalizer recomputes hashes from the expected contract and
rejects count, order, duplicate, unexpected hash, symbol, binding, non-ok
outcome, and time drift. The coordinator may bind request identity only at the
actual invocation boundary; it may not synthesize provider outcome or time.

The validation plan explicitly covers hash/count/order/binding drift and a
failed child with zero receipt. This is strong enough to distinguish two
same-count request sets and prevents aggregate plan metadata from masquerading
as provider child evidence.

### PR-S1A-03 — closed — malformed ready input is fail-closed before projection

The amendment now freezes strict validation for every ready item before any
side-plan merge: supported option type, strict ISO expiration, and positive,
finite, non-boolean strike. One invalid ready peer is a typed symbol planning
failure and cannot be skipped while valid peers form a smaller plan. Explicit
unavailable/non-ready entries retain their existing exclusion semantics.

The tests require per-field malformed cases and the success signal explicitly
places failure before provider/cache use. This closes the provenance-loss gap at
the owning planner boundary rather than asking the output validator to infer a
demand that was already discarded.

### PR-S1A-04 — closed — one exact-strike helper and tolerance are frozen

The amendment specifies one shared identity helper for typed and debug coverage:

```python
math.isclose(actual, expected, rel_tol=0.0, abs_tol=1e-9)
```

It explicitly forbids reuse of range-edge tolerance and any scale-dependent
tolerance. Parameterized tests must feed the same within/outside-boundary cases
to both coverage entry points. The two public conclusions therefore cannot
legitimately diverge for the same rows and expected contract.

## Special review lenses

- **Architecture boundary review**: the expiry-local strike mapping stays on
  `OptionSideFetchPlan`, where provenance is first projected. Shared execution
  and aggregation remain in `required_data_fetching.py`; the coordinator owns
  attaching request identity at invocation, and the finalizer owns validation.
  No dependency inversion or new persistence/public schema is introduced.
- **Best-practice review**: immutable success authority is bound to exact
  request identity, typed child outcome, durable readback, and fail-closed input
  validation. The plan includes negative evidence tests rather than accepting a
  happy-path count check.
- **Optimal-solution review**: moving only real in-process per-spec execution
  into S1 is the smallest correction that makes S1's evidence contract true.
  Reusing the existing request builder/merge owner is safer than either widening
  one Cartesian call or pulling the entire CLI/subprocess redesign into S1.
- **Overengineering review**: the plan avoids per-lot quote entities, a generic
  demand graph, Decimal migration, new receipt versions, and a new aggregation
  layer. One expiry-local map, one shared comparator, and ordered request hashes
  are proportional to the proven failure modes.
- **Overcoupling review**: S1 no longer depends on S6 for the first valid
  multi-spec provider facts. The remaining dependency is explicit and one-way:
  S6 extends S1's request-bound aggregate to subprocess/CLI without replacing
  or weakening the in-process contract.

No material unresolved plan findings.

## Open Questions

None blocking implementation. Implementation should reuse the repository's
existing canonical JSON/SHA-256 convention for each exact `merged_requests`
item; it must not introduce a second serialization convention.

## Residual risks and tracking

- **Temporary subprocess capability boundary**: a configured multi-spec
  subprocess run is deliberately typed unsupported from the protected S1
  commit until S6. This is safer than the current lossy Cartesian execution,
  current canonical configs use the in-process default, and tests require zero
  subprocess/output/receipt effects. Track closure in S6 and do not accept or
  deliver the aggregate work unit until the S6 completion signal is met.
- **Configuration drift**: the default-mode evidence is current-worktree
  evidence, not a guarantee about an independently changed runtime config.
  Retain the explicit pre-effect typed guard even while in-process is canonical;
  verify configured mode again at final aggregate review.
- **Interior provider omission**: range fetching can still omit an interior
  contract. Exact post-write coverage now rejects that result; selective retry
  remains outside S1 and should be tracked only as operational cost unless live
  evidence shows it needs its own work unit.
- **Numeric representation**: `1e-9` is intentionally only a serialization
  tolerance. Tests at high strikes and immediately inside/outside the boundary
  must prevent future relative-tolerance widening.

## Final conclusion

`pass-with-risks`

The revised amendment closes `PR-S1A-01` through `PR-S1A-04` and is sufficiently
specific to resume S1 implementation. The only material residual is the
explicit, fail-closed subprocess multi-spec gap, which is bounded by the current
in-process default, negative side-effect tests, and mandatory S6 closure before
aggregate acceptance or delivery.
