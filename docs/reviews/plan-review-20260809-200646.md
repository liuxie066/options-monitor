## New finding

### 5-未修复-中-S6 要求传递 PM 对象但遗漏 TickNotificationRequest 所有者文件
- **位置**: Plan S6 allowed files 与 call path
- **问题类型**: 架构边界 / 不可直接实施 / scope ownership
- **当前写法**: S6 明确要求“Tick notification request 传递 S2 已验证的 PM object + artifact
  authority maps”，allowed files 却只列 orchestration、Daily Brief、tick execution、
  multi-account tick 和模糊的 prepared loaders。
- **反例/失败场景**: implementation agent 遵守 allowed files 时，无法给
  `TickNotificationRequest` 新增 typed fields，也无法在 `_prepare_daily_brief_notification()`
  调 `assemble_daily_decision_briefs()` 时传入 per-account PM object。它只能越界修改未批准
  文件、退回按路径重读，或把 private object 塞进不合适的 `tick_metrics/results`。
- **为什么有问题**: `TickNotificationRequest` 和调用 Daily Brief 的真实 owner 是
  `src/application/tick_notification_flow.py`；plan 的数据流与文件所有权不闭合。
- **直接证据**: Plan 607–610 要求 explicit request handoff，但 S6 allowed files 578–590
  不含该文件；source `tick_notification_flow.py:67-93` 定义 request，`:767-776` 是 Daily Brief
  调用点。
- **影响**: 实施越界、重新引入隐式路径依赖，或把敏感 PM 数据塞进 metrics，破坏审查边界。
- **建议改法和验证点**: 把 `src/application/tick_notification_flow.py` 加入 S6 allowed files，
  明确 request 新增 internal-only per-account verified PM object + artifact authority maps；
  `_prepare_daily_brief_notification()` 只按当前 account 取对应 object 传给 assembler。字段不得
  序列化进 metrics/audit/receipt，delivery-only path 不使用它。加入 request account isolation、
  missing-map soft unavailable、delivery-only no-read/no-model regression。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
