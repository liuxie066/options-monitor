## Assumptions Tested

1. 删除错期只影响开仓路径，ledger/生命周期保留不动（Q2）→ 验证：`trades/resolver.py`、
   `positions/combo_pairing.py`、`combo_yield_lifecycle.py`、`combo_reconciliation.py` 的 staggered 引用
   均为自身 `structure_mode` 判断，不调用被删的 domain 指标/排序函数（rg 证据：domain 函数唯一生产消费者是
   `sell_put_call_helper.py`）。
2. S1 删除 domain 错期分支后没有其他调用方 → 验证：`compute_yield_enhancement_metrics` /
   `validate_yield_enhancement_pair` / `compute_yield_enhancement_funding_decision` /
   `rank_yield_enhancement_calls_for_put` 在 `src/`、`domain/` 中的调用点仅 `sell_put_call_helper.py`
   与 `engine/__init__.py` 导出；ledger 侧无调用。
3. `rank_yield_enhancement_shadow_rows` 是同期路径既有 shadow/baseline 机制，非错期专属 → 验证：
   `sell_put_call_helper.py:1096` 对所有行统一计算 shadow_rank，无 staggered 条件；plan 列为 non-goal 正确。
4. S2 删除配置面后旧配置会显式报错而非静默忽略 → 需确认实现机制（见 Finding 2）。
5. `strategy_attribution.py` 的 staggered 分支可安全删除且 `diagonal` 语义不受影响 → 需确认（见 Finding 1）。
6. research/shadow 测试删除后无残留 import 依赖（`test_combo_yield_research.py` 使用
   `combo_settlement`、`required_data_planning` 类型）→ 需确认（见 Finding 3）。

## Findings

### 1-未修复-高-`strategy_attribution.py` 的 staggered 删除与 `diagonal` 语义必须一次性定死，plan 当前写法会让实现 agent 自行发明

- **位置**: plan §6 S3 文件清单、§8 Implementation Decision 5、§12 风险表"diagonal 与 staggered 共享分支"
- **问题类型**: 契约缺失 / 不可直接实施
- **当前写法**: "`strategy_attribution.py` 删除 staggered 归因分支（`diagonal` 是否保留以现有语义为准——若
  diagonal 是独立形态且无 staggered 耦合则保留）"
- **反例/失败场景**: 实现 agent 按"以现有语义为准"自行判断，可能误删 `diagonal` 分支或保留整套集合，
  导致 ledger 归因对 diagonal 形态行为变化或 review 无法验收。
- **直接证据**: `strategy_attribution.py:145` 是 `if structure in {"diagonal", "staggered_expiry_pair"}`，
  两者共享"call expiry 不得早于 put expiry"校验，`diagonal` 是独立 ledger 形态（`expiry_structure`），
  不属于开仓 `structure_mode`。Q2 保留 ledger 生命周期，`diagonal` 不得删除。
- **影响**: 实现跑偏 / 误删保留范围语义
- **建议改法**: plan 明确写死：`strategy_attribution.py` 只把 `staggered_expiry_pair` 从该 set 移除，
  保留 `diagonal` 分支与校验；并注明该文件属于保留的 ledger/归因面，仅因共享 set 需做最小修改。
- **修复风险（中）**:
- **严重程度**: 高

### 2-未修复-中-配置 validator"已移除"错误需要显式 removed-fields 检查，plan 未写机制

- **位置**: plan §7 生产公开面、§8 Implementation Decision 3、Slice 2 Exact allowed changes
- **问题类型**: 契约缺失 / 不可直接实施
- **当前写法**: "`min/max_expiry_gap_days` 从允许字段集合移除并给出'已移除'错误，不做静默兼容"
- **反例/失败场景**: `_reject_unknown_keys` 对不在 allowed set 的字段只会给出 generic unknown-field
  错误（附 suggestion），不会输出"已移除"文案。若实现 agent 仅把字段从 allowed set 删除，则旧配置报错
  文案不满足 plan 契约，review 无法验收；若保留在 allowed set 中则不会报错，语义更差。
- **直接证据**: `config_validator.py:623` `_reject_unknown_keys(cfg, YIELD_ENHANCEMENT_ALLOWED_FIELDS, path)`；
  `YIELD_ENHANCEMENT_ALLOWED_FIELDS`（line 207-226）当前含 `min_expiry_gap_days`/`max_expiry_gap_days`；
  同文件已有 removed-fields 显式检查先例（`removed_funding_keys` → `die(...)` line 629-633）。
- **影响**: 旧配置报错信息不符合契约 / review 不可验收
- **建议改法**: plan 写死实现方式：仿照 `removed_funding_keys` 模式，在 `_reject_unknown_keys` 之前显式
  检查 `min_expiry_gap_days`/`max_expiry_gap_days` 并 `die("...已移除，Combo Yield 仅支持 same_expiry_pair")`，
  同时从 `YIELD_ENHANCEMENT_ALLOWED_FIELDS` 移除这两个字段。
- **修复风险（低）**:
- **严重程度**: 中

### 3-未修复-中-domain 函数 `structure_mode` 参数去留必须写死，当前"实现时决定"不可直接实施

- **位置**: plan §8 Implementation Decision 1、Slice 1 Exact allowed changes
- **问题类型**: 契约缺失 / 不可直接实施
- **当前写法**: "`structure_mode` 参数保留但单一化……若 S1 内确认无生产调用点传 staggered，可直接删除参数
  ——由实现时 `rg` 结果决定，plan 默认走'保留签名、单一语义'"
- **反例/失败场景**: 实现 agent 需自行选择保留或删除参数；保留会导致 dead parameter（用户诉求是消除冗余），
  删除则需要同步改 `engine/__init__.py` 导出与所有调用点，两案验收标准不同。
- **直接证据**: `compute_yield_enhancement_metrics` / `validate_yield_enhancement_pair` /
  `compute_yield_enhancement_funding_decision` 的唯一生产调用方是 `sell_put_call_helper.py`（S1 同 slice 文件）；
  `engine/__init__.py:55-80` 导出这些函数。删除错期分支后 `structure_mode` 参数只剩 `same_expiry_pair` 一个值。
- **影响**: 实现跑偏 / 冗余残留 / review 不可验收
- **建议改法**: plan 写死：S1 直接删除这三个 domain 函数的 `structure_mode` 参数及其调用点传参（
  `sell_put_call_helper.py` 同 slice 内同步），同步更新 `engine/__init__.py` 导出；`structure_mode` 仅保留
  在 row/alert 数据字段层（值为 same）。
- **修复风险（中）**:
- **严重程度**: 中
