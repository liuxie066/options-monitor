## Findings

### DR8-01-未修复-中-control API 仍公开静默退化为历史全扫描的默认分支

- **入口/函数**: `list_settlement_attempt_states()` / `settlement_attempt_summary()` -> `_fetch_settlement_attempt_rows()`
- **文件(行号)**: `src/application/trades/inbox.py:368-387,661-695,814-877`; `src/application/trades/lifecycle_runtime.py:441-447,1248-1255`; `tests/test_settlement_attempts.py:397-477`
- **输入场景**: 后续新增一个状态页、健康检查、补偿入口或第二个runtime调用这两个本迭代新引入并导出的control API，按默认参数省略 `case_ids`；summary还可以省略 `account`。
- **实际分支**: `case_ids=None` 被解释为合法的无界模式，helper执行 `WHERE source_id=? [AND account=?]`并 `fetchall()`。`settlement_attempt_summary()` 默认连account都不要求，因此会扫描并物化该source所有账户、所有历史case的控制行。当前唯一runtime调用点恰好传入scope，但owner接口不保护该性能不变量。
- **预期行为**: 调度型control读取必须要求显式account和candidate IDs；空集合代表当前无工作并返回空结果。若未来确有历史审计需求，应使用名字和契约明确的独立审计API，而不能让热路径owner默认降级为全表/前缀扫描。
- **实际行为**: 一次普通的参数遗漏即可静默恢复DR7-02的同类故障，且类型检查与现有测试都不会失败。由于这些函数在main中不存在、是本work unit新引入的接口，不存在必须保留该默认行为的兼容约束。
- **直接证据**: 两个公开函数均声明 `case_ids: Iterable[str] | None = None`；summary声明 `account: str | None = None`；helper 830-838 行为None显式执行无case谓词的 `fetchall()`。全仓仅runtime和测试调用，runtime已经拥有完整account/candidate集合。
- **影响**: 修复依赖“所有现在和未来调用者都记得传scope”，不能作为解决历史增长型CPU问题的通用边界；一次新调用或重构即可让飞书响应延迟与trade-intake高CPU复发。
- **建议改法和验证点**: 把两个API及helper的account/case_ids改为必填非可空参数，删除None归一化和无界SQL分支；保留空tuple的快速空结果与分批主键查询。测试应覆盖空scope、1,200条历史rows下的小scope、超过单批大小的scope，并证明所有生产调用点显式传参。
- **修复风险（低/中/高）**: 低
