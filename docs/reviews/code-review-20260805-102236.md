## Findings

### DR3-01-未修复-高-CLI 与默认 collector 路径冻结续租时钟，heartbeat 不会推进租约

- **入口/函数**: `reconcile_due_lifecycle_cases_for_source()` -> `require_collector()` -> `_SettlementClaimLeaseGuard.renew_now()`
- **文件(行号)**: `src/application/trades/lifecycle_runtime.py:355-373,935-964`; `src/interfaces/cli/option_positions.py:1651-1660`; `src/application/trades/inbox.py:524-565`
- **输入场景**: CLI `lifecycle reconcile-due` 或其他调用方不传 `settlement_collector`/factory，由 runtime 使用 gateway 构造默认 collector；一次 provider collection 超过 120 秒。
- **实际分支**: 默认 collector 的 `now_ms_fn` 固定返回函数入口的 `now_ms`。lease guard 每 30 秒调用该函数，并把 `claim_until_ms` 再次写成同一个 `now_ms + 120_000`，因此日志上发生了 renewal，实际到期时间却没有向前移动。CLI 正是走这个默认构造分支。
- **预期行为**: 续租时间必须随真实经过时间单调前进，且不能依赖调用方恰好提供动态 wall clock。即使 collector 的业务观察时钟被冻结用于确定性重放，claim liveness 仍应独立推进；系统 wall clock 回拨也不应让续租停滞。
- **实际行为**: 初始租约到期后另一 worker仍可取得 claim，并与 CLI/默认 worker并发执行 provider I/O；第二轮修复只对常驻 listener 的动态 `time.time()` factory 和显式推进 fake clock 生效。
- **直接证据**: `require_collector()` 将 `now_ms_fn` 绑定为 `lambda: int(now_ms)`（`lifecycle_runtime.py:355-370`）；guard 原样用 collector clock 计算每次续租的绝对到期值（`lifecycle_runtime.py:935-964`）；renew SQL 只写 `int(now_ms) + lease_value`，没有单调 elapsed floor（`inbox.py:524-565`）。CLI 调用不传 collector/factory（`option_positions.py:1651-1660`）。现有 heartbeat 测试主动把 fake clock 从 1,000 推到 122,000，未覆盖冻结时钟。
- **影响**: 受支持的生产维护入口仍会破坏“活跃 worker 持续独占 provider attempt”的核心止血保证；慢分页场景可重新产生重复 provider I/O、CPU 放大与 stale-owner completion。
- **建议改法和验证点**: lease guard 在启动时记录 claim 的初始逻辑时间与 `time.monotonic()`，续租使用 `max(provider_clock, initial_claim_ms + monotonic_elapsed_ms)`；业务 observation clock 不必改变。允许测试注入 monotonic clock，新增冻结 collector clock + 多次 interval + competing claim 回归，证明租约持续前移；同时验证 wall clock 前进更快时仍采用较大值。
- **修复风险（低/中/高）**: 低
