## Findings

### S4-CR-01-已修复-高-外部 snapshot raw 值可使当前报告在 fact ID 生成阶段崩溃
- **入口/函数**: `build_option_period_performance(... refresh_quotes=True)` -> `collect_current_performance_evidence()` -> `ValuationMarkFact.__post_init__()`
- **文件(行号)**: `src/application/performance/evidence_collection.py:117-143`; `domain/domain/performance/models.py:384-394, 423-438`
- **输入场景**: OpenD/pandas snapshot row 的 `raw` 含 `pandas.Timestamp`、NumPy scalar、NaN 或其他非标准 JSON 值。
- **实际分支**: collector 把 `dict(row)` 原样放进 `ValuationMarkFact.raw`; fact_id 未提供时 `_canonical_json()` 直接 `json.dumps(payload)`。
- **预期行为**: 外部 adapter 应把 raw evidence 规范化为稳定 JSON 值；无法规范化的非经济字段不能击穿整个报告。Domain/infrastructure canonical JSON 还应拒绝 NaN。
- **实际行为**: `json.dumps` 可抛 `TypeError`，或默认写出非标准 `NaN`; 当前循环没有捕获 fact 构造异常，整个当前报告失败。
- **直接证据**: raw 在 `ValuationMarkFact` 生成 ID 的 payload 内；`json.dumps` 没有 `allow_nan=False`，collector 没有 JSON-safe normalization。
- **影响**: 当前 option-performance 读路径可因正常外部数据类型崩溃；capture/import 的 byte-semantic 稳定性也被破坏。
- **建议改法和验证点**: 在 collection adapter 递归转换 Mapping/list/datetime/Decimal/NumPy scalar，非有限 float 转 null；domain/repository canonical JSON 使用 `allow_nan=False`; 添加 Timestamp/NumPy/NaN raw 回归测试。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### S4-CR-02-已修复-中-persisted 与 live evidence 未做 identity conflict 验证
- **入口/函数**: `build_option_period_performance()` current report merge
- **文件(行号)**: `src/application/performance/service.py:77-105`
- **输入场景**: 已持久化 fact 与本次 live fact 使用相同 `(source, source_id, revision)`，但价格/raw/quality 或 fact_id 不同。
- **实际分支**: service 直接 tuple 拼接 persisted/live，selector 依 effective/source/revision/fact_id 选一个。
- **预期行为**: 与 import 相同的 source-identity invariant 应在 current merge 时 fail closed；冲突 live batch 不应被静默采用。
- **实际行为**: 冲突没有 diagnostic，输出由 fact_id 字典序偶然决定，和证据 repository 的冲突规则不一致。
- **直接证据**: service 没有调用 `validate_evidence_facts`; domain selector 不负责 duplicate/source conflict validation。
- **影响**: 当前结果可能在相同 source identity 下静默选择不同经济事实，破坏 deterministic evidence contract。
- **建议改法和验证点**: merge 前用 persisted 作为 existing 验证 live batch；冲突时保留 persisted、丢弃 live batch并输出 scoped valuation diagnostic；添加 current merge conflict 测试。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### S4-CR-03-已修复-中-unsupported evidence schema 不会降级 report quality
- **入口/函数**: `build_option_period_performance()` evidence read
- **文件(行号)**: `src/application/performance/service.py:50-60, 79-105`
- **输入场景**: evidence schema 版本不支持或结构化列/raw_json 损坏，同时请求期内没有需要 mark 的 open position，或其他 activity facts 完整。
- **实际分支**: repository 返回 `unsupported_schema`; service 只把状态放到 `payload.evidence`，不加入 diagnostics。
- **预期行为**: 不支持/损坏的 evidence store 是 report quality warning，至少当前 scope 应为 partial，不能仅靠旁路 metadata 暴露。
- **实际行为**: engine 可返回 `quality.status=observed`，尽管 evidence store 明确不可读。
- **直接证据**: diagnostics 只包含 ledger/opening/ending/collection items；schema state/message 没进入 engine quality。
- **影响**: Agent/CLI consumer 只读 top-level quality 时会把证据基础设施损坏误判为完整结果。
- **建议改法和验证点**: 对 `unsupported_schema` 添加 `context=valuation` 的 scoped diagnostic；保留 schema message；测试无 open position 时 top-level quality 仍 partial。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### S4-CR-04-已修复-中-cross-account dedupe 会丢失后出现的 stored exact market code
- **入口/函数**: `collect_current_performance_evidence()` option identity dedupe
- **文件(行号)**: `src/application/performance/evidence_collection.py:73-98`
- **输入场景**: 同一 account-independent instrument 的第一个 position 没有 `market_code`，后一个 position 有 canonical stored code。
- **实际分支**: `setdefault` 永远保留第一个无 code position；后一个 stored code 不会提升为代表值。
- **预期行为**: 任一账户已有一致 stored canonical code 时优先直接使用，避免无必要 chain resolution。
- **实际行为**: collector 走 chain discovery；在 chain 不可用时 mark 缺失，即使 ledger 已有精确 code。
- **直接证据**: 非冲突分支只执行 `unique_options_by_key.setdefault(key, position)`。
- **影响**: 账户顺序影响 current mark 可用性，违反 cross-account instrument reuse 和 stored-code-first contract。
- **建议改法和验证点**: existing 无 code、new 有 code 时替换代表 position；测试输入顺序为 no-code -> stored-code 且 fetch seam 收到 stored code。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### S4-CR-05-已修复-中-report collection provenance 内嵌完整 raw evidence
- **入口/函数**: `CurrentEvidenceCollection.to_dict()` -> service `payload["evidence"]["collection"]`
- **文件(行号)**: `src/application/performance/evidence_collection.py:33-40`; `src/application/performance/service.py:107-115`
- **输入场景**: current report 使用真实 OpenD snapshot/FX payload，raw 包含整行 quote/greeks/source payload。
- **实际分支**: `to_dict()` 返回完整 envelope，envelope 又返回每个 fact 的完整 `raw`。
- **预期行为**: report 只暴露 collection status/count/diagnostics/fact IDs/provenance；完整 envelope 只属于 explicit capture/import surface。
- **实际行为**: 每次 report 都复制并暴露完整 raw evidence，扩大 payload、潜在泄露 adapter/internal fields，并给 S7 public contract 带来不必要耦合。
- **直接证据**: `"evidence": self.envelope.to_dict()` 无裁剪；service 原样嵌入。
- **影响**: public consumer 迁移后可能意外依赖/暴露 raw broker payload，且大持仓报告显著膨胀。
- **建议改法和验证点**: `to_dict()` 改为 counts、diagnostics、mark/rate fact IDs；capture 继续显式使用 `.envelope`; 添加报告不含 raw/evidence envelope 测试。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
