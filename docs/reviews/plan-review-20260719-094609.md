# Plan Review — log-stability-hardening

- Reviewed target: `docs/gateflow/log-stability-hardening-plan.md`
- Scope: implementation readiness, architecture boundaries, retry/lifecycle semantics, validation, overengineering/overcoupling
- Conclusion: **fail**

## Assumptions tested

- Existing `./om status` output is inherently bounded.
- A quote-context readiness probe proves readiness for durable quote and trade contexts.
- `RuntimeMaxSec=600` is safe for every listed one-shot.
- A preflight failure alone stops the long-running trade-intake restart/log loop.
- The proposed slices are narrow enough to review independently.

### PR-1-未修复-高-`./om status` 不是严格有界输出，计划无法证明核心成功信号
- **位置**: Slice 1, success criteria, decision 1
- **问题类型**: 契约缺失 / 测试缺口
- **当前写法**: 改用现有 compact facade，并仅用 representative envelope 断言不超过 20 行/16 KiB；同时声明不截断真实 warnings。
- **反例/失败场景**: `format_runtime_status_summary` 会逐条输出 envelope warnings 和 ledger warnings，warning 数量未设上限。一次真实调用可超过 20 行或 16 KiB，即使 representative fixture 通过。
- **为什么有问题**: 计划把“典型样本较小”误当作“输出有界”，无法验收用户确认的硬成功信号。
- **直接证据**: `src/application/runtime_status_cli.py` 末尾对 `warnings`/`ledger_warnings` 全量 `lines.extend(...)`。
- **影响**: 日志洪泛在异常时回归；测试给出错误安全感。
- **建议改法和验证点**: 明确一个 service-only bounded summary 参数或 formatter 参数，保留默认人工 CLI 的完整 warnings；service 传入上限并输出 omitted count。测试至少覆盖大量、超长 warnings，证明行数和字节数硬上限。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR-2-未修复-高-Quote readiness 不能完整证明 trade auth，且没有阻断 systemd 永久重启
- **位置**: Slice 2, decision 4
- **问题类型**: 状态机漏洞 / 架构边界
- **当前写法**: 在 `OpenDTradePushListener.start` 前调用基于 `get_global_state` 的共享 quote probe，失败时抛稳定异常。
- **反例/失败场景**: quote probe 成功但 `OpenSecTradeContext` 因交易登录/手机验证失败；CLI 退出后生成 unit 的 `Restart=always` 每 10 秒重启，仍形成无限日志循环。
- **为什么有问题**: 该方案只减少部分启动尝试，不满足“auth-required fail fast”在长运行服务生命周期上的含义，也把 quote readiness 当成 trade readiness。
- **直接证据**: `src/application/trades/push_listener.py` 创建 `OpenSecTradeContext`；`src/application/service_deploy.py` 为 trade-intake 配置 `Restart=always`/`RestartSec=10`；现有 classifier 只观察 quote `get_global_state`。
- **影响**: trade-intake 仍可持续洪泛；计划声称修复但生产反例未关闭。
- **建议改法和验证点**: 当前 work unit 不应伪称 quote probe 解决 trade auth。要么设计稳定的 distinct exit status + `RestartPreventExitStatus` 并在 trade context 构造异常处复用现有 classifier，要么把 trade-intake auth loop 单独列为 later work unit，并将本 work unit成功信号限定为 observed stuck one-shots。后者更小、更安全。
- **修复风险（低/中/高）**: 高
- **严重程度（低/中/高/严重）**: 高

### PR-3-未修复-中-`RuntimeMaxSec=600` 应用范围过宽且与 tick 自身 600 秒超时竞争
- **位置**: Decision 3, Slice 1
- **问题类型**: 范围漂移 / 非最优方案
- **当前写法**: 对 tick、auto-close、projection verify、Runtime Status、Strategy Lab one-shots 全部设置 600 秒。
- **反例/失败场景**: tick 的应用层 `--timeout 600` 尚未来得及清理/写最终状态时 systemd 同时 SIGTERM；runtime-status 当前约 3 秒且无卡住证据；projection verify 也无当前证据。
- **为什么有问题**: 把观察到的两个卡住服务扩展到所有 one-shot，增加无证据行为改变和 timeout race。
- **直接证据**: generated tick args 已传 `--timeout 600`；远端证据只确认 auto-close 和 Strategy Lab sample 的 `RuntimeMaxUSec=infinity` 且处于 activating。
- **影响**: 正常长 tick 被服务管理器提前终止，状态/审计不完整；review 面扩大。
- **建议改法和验证点**: 首批仅对已观察卡住且依赖 OpenD 的 `auto-close-*` 和 `strategy-lab-sample` 设置 600 秒；其它 unit 保持不变并用 negative assertions 锁定。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### PR-4-未修复-中-Slice 2 同时改三个 ownership 边界，收益证据不足
- **位置**: Slice 2
- **问题类型**: 过度耦合 / 切片过粗
- **当前写法**: 同时修改 watchdog、generic Futu gateway、trade push listener。
- **反例/失败场景**: generic gateway 被众多扫描、持仓、事件路径复用；一个为日志问题设计的启动 probe 改变所有调用方延迟和失败语义。
- **为什么有问题**: 当前已观察 one-shot 卡住可以先由 unit runtime bound 止损；没有调用链证据证明 generic gateway 的重试属于无限循环。计划扩大到全局基础设施边界。
- **直接证据**: `build_ready_futu_gateway` 被 snapshot、performance、events、portfolio、positions、symbol fetching 等多处调用。
- **影响**: 广泛回归风险，难以把日志改善归因到单一改动。
- **建议改法和验证点**: 本 work unit 移除 generic readiness 改造；只做 compact bounded output + observed one-shot runtime bounds。将 trade-intake/auth-aware restart 作为独立 work unit，先补真实异常/exit behavior 证据再设计。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
