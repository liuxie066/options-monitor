## Findings

### 1-未修复-高-同一 broker observation 的第二条结算成交必然复用旧 generation token，首条已提交后整案失败

- **入口/函数**: `collect_broker_settlement_observation()` -> `reconcile_lifecycle_close_reason()` -> `reconcile_polled_stock_settlement_evidence()` -> `apply_lifecycle_allocation_atomically()`
- **文件(行号)**: `src/application/trades/settlement_observation.py:406-420,903-1029,519-522`; `src/application/trades/close_reason_reconciliation.py:44-80,599-618`; `src/application/trades/lifecycle.py:354-390,533-543,686-764`; `src/application/trades/lifecycle_reconciliation.py:774-858`; `src/application/ledger/writer.py:114-145,978-1017`; `src/application/ledger/lifecycle_overlay.py:964-1092`; `tests/test_settlement_observation.py:361-417,420-503`
- **输入场景**: 一次完整 history-deals observation 返回同一 case 的两条股票结算行。最简单的可达形式是 provider payload 中重复出现同一 `deal_id`；真实 split fill 则会以两个不同 `deal_id` 返回，例如两张合约分别产生两笔 100 股结算。
- **实际分支**: collector 对每个 history row 独立生成 candidate，没有按 source identity 去重，也没有把同一冻结 observation 的候选集合合并成一个 case-level decision。`reconcile_lifecycle_close_reason()` 在循环前只读取一次 generation token，并把同一个 token 传给每个 candidate。第一条 candidate 在独立事务内写 evidence、allocation、terminal event、case summary 和 projection，因而 generation preimage 已变化；第二条仍以旧 token 进入 writer，必然触发 CAS `ValueError`。
- **预期行为**: 同一冻结 broker observation 应先形成一个确定的、完整的 case-level settlement decision，再以一次 generation precondition 原子提交；重复 source row 应幂等，合法 split fills 应整体结算，冲突或超量集合应在任何写入前 fail closed。
- **实际行为**: 第一条写入已经提交，第二条抛 `lifecycle generation compare-and-set failed`。直接调用返回异常；due batch 只捕获 `LifecycleCaseDataError`，因此该普通 `ValueError` 还会停止后续 cases。结果是“部分已写、整案/整批报错”，而不是 generation drift 所承诺的零写入失败。
- **直接证据**: `_stock_settlement_candidate()` 以每条 row 的 `deal_id` 生成独立 evidence；`:406-420` 原样保留所有非空 candidate。close-reason loop 的 `expected_generation_token` 在 `:62-64` 只计算一次。generation preimage显式包含 case、evidence、allocations、position lots 和相关 trade events，首条成功必然改变 token。定向反例构造两个相同 candidate，实际输出为 `candidates 2`、`ValueError lifecycle generation compare-and-set failed`，异常后仍有 `1` 条 allocation 和 `2` 条 trade event；现有测试只断言单 candidate 和外部并发发生在首写之前。
- **影响**: broker 重复行或 split settlement 可制造已提交的部分生命周期事实和失败的定时任务，延迟同账户后续到期 case；重试虽可能逐步收敛，但运行结果、告警和一次 observation 的审计语义均不再原子。
- **建议改法和验证点**: 不需要新增通用 batch framework。在现有 close-reason owner 内，写前先 canonicalize 整个候选集合：同 source identity 去重；对合法 split fills 做确定性汇总或在同一 SQLite transaction 中按冻结顺序应用并只检查一次初始 generation；冲突、超量或无法唯一归属时零写入 review。新增 duplicate row、两笔合法 split fill、总量超限、第二笔经济冲突、以及后续 case 是否继续的回归测试，并断言每个失败场景的 evidence/event/allocation/Outbox 全部为零。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### 3-未修复-中-membership strict validator 只校验外形和自哈希，重复或错误的两腿 binding 仍会被判为 exact valid

- **入口/函数**: Position Advice `_group_structure_states()` -> `validate_combo_group_membership()` -> `classify_combo_structure()`
- **文件(行号)**: `src/application/ledger/combo_membership.py:207-300,445-469`; `src/application/position_advice_plan_builder.py:1414-1489,1490-1518`; `docs/plans/position-fact-deepreview-remediation-plan-20260731.md:344-350,387-403`
- **输入场景**: snapshot 带有一个字段齐全、自哈希正确、top-level counts 都为 2 的 `status=exact` membership；`current_account_member_record_ids` 是 identity 的 Put/Call 两个 record id，但 `member_bindings_for_current_account` 重复两次 Funding Put binding，或含错误 role/strategy/account/symbol/open-event。
- **实际分支**: validator只要求 bindings 是可排序的两个 mapping 且 key 集合正确；没有要求 binding record IDs 唯一并等于 record-id list，也没有验证一 Put 一 Call、`strategy=combo_yield`、非空 open-event、同账户/同标的或 zero-count redacted hashes。plan builder随后只比较独立的 `current_account_member_record_ids` 与 identity IDs，不读取 binding 语义，因此 validation status 为 `valid` 后继续 classify。
- **预期行为**: `status=exact` 的 consumer validator 应独立证明这两个 allowlisted bindings就是 identity 所绑定的两条合法腿；自哈希只证明 payload 自洽，不能替代字段语义校验。
- **实际行为**: malformed exact fact 可以开启 `active_combo` / group action。定向反例使用两个完全相同的 Funding Put binding，并重算合法 membership hash，实际返回 `ComboMembershipValidation(status='valid', ...)`。
- **直接证据**: `validate_combo_group_membership()` 在 `:240-268` 只检查排序和 key shape，`:279-293` 只检查数量/flags；producer 侧有完整 roles/strategy/account/symbol检查，但 consumer validator 没有复现这些不变量。plan builder `:1447-1481` 信任 validator，只对独立 ID list做 identity comparison。冻结方案明确要求 duplicate/wrong binding fail closed以及 roles/strategy/account/symbol 全匹配。
- **影响**: 正常 current producer 不会生成该 payload，因此风险低于前两项；但 artifact corruption、兼容转换、测试 fixture 或未来 producer drift 可绕过本次新增的主要读侧防线，并让一个看似严格、带 hash 的 fact错误地授权组合级建议。
- **建议改法和验证点**: 直接补强现有 validator，不新增层：要求两个 binding record IDs 唯一且精确等于 ID list；角色恰好一 Funding Put、一 Participation Call；strategy、account、symbol、open-event 均合法并与 identity/consumer context一致；zero external/retag count 时对应 hash 必须是 canonical empty hash。新增 duplicate binding、wrong role、wrong strategy/account/symbol/open-event、ID-list mismatch 和 bad redacted hash 测试，并断言 plan 零 group action。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
