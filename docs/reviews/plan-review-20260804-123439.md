## Goal, boundaries, and success signals

The revised plan has two linked but independently authorized goals:

1. Correct the repository defect where one sampler using the implicit `lx@127.0.0.1:11111` endpoint declares both `lx` and `sy` OpenDs as dependencies.
2. Prove, rather than guess, the smallest host-safe memory envelope that supports both required OpenDs under both sequential and parallel cold-start conditions.

The source implementation boundary is limited to the service-render CLI, service bundle/profile projection, service-drift compatibility, tests, and public service/Strategy Lab docs. Strategy Lab result semantics, OpenD restart/readiness policy, account schema, runtime production config, Incus state, Futu HOME/device state, release, deployment, and business writes are excluded from Gate A.

The incident is closed only after the installed sampler has one matching dependency without restarting OpenD, the host-authorized capacity gate passes, business-write-capable consumer restoration is separately authorized, and a natural sampler run plus cgroup/IO deltas satisfy the observation contract. Source tests or healthy unit status alone are explicitly insufficient.

## Assumptions tested

1. **The current sampler really consumes only one endpoint while depending on both services. — Supported.** `src/application/service_deploy.py:1244-1279` does not append host/port and applies all `opend_dependency_units`; `src/interfaces/cli/research.py:206-207` defaults to `127.0.0.1:11111`. Read-only production facts map that endpoint uniquely to `lx`, while `sy` uses `11112`.
2. **Making `lx` explicit preserves behavior instead of changing quote ownership. — Supported with a rollout recheck.** The current US/HK configs agree on `lx@11111`, the installed sampler has historically used the CLI default, and the latest unit result was successful. Plan lines 233-236 require a fresh canonical-config check and plan amendment if this drifts.
3. **The two-hour OpenD-backed recorder should remain active. — Supported.** `docs/SHADOW_REPLAY_RUNBOOK.md:56-67` documents the recorder and two-hour mark-path sampling. Plan lines 15-19 and 45-50 correctly avoid inventing a benign unavailable outcome or silent evidence gap.
4. **Account/endpoint selection belongs to existing account configuration, not service order. — Supported.** Existing runtime plans already expose Futu account type, host, port, and root. Plan lines 84-98 require all-market agreement and prohibit first-account/lowest-port/default selection for fresh multi-account rendering.
5. **A matching unit can be projected without making the renderer a second source of truth. — Supported.** Plan lines 100-146 resolve endpoint identity from canonical config, limit unit projection to the matching account, and treat the profile endpoint as a receipt that drift re-resolves rather than replays as authority.
6. **Legacy production profile migration can be deterministic. — Supported.** The live schema-v1 profile records `accounts=[lx,sy]`, markets, canonical YAML/config paths, and an OpenD recorder with no binding. Plan lines 148-175 match the historical effective endpoint against canonical config, fail on zero/multiple matches, expose a stable warning, and eliminate inference after the first confirmed profile write.
7. **The first rollout can avoid an OpenD cold start. — Supported.** The CLI already exposes `--no-restart-services` (`src/interfaces/cli/service_ops.py:158-168`). Service drift writes mismatched units/profile and may reload/restart affected timers, but does not restart long-running services. Plan lines 227-261 require unchanged OpenD PIDs/timestamps, separate trade-intake reactivation, and a rollback that stops the persistent sampler timer before restoring the old broad dependency.
8. **A fixed memory target can be derived from the incident peak. — Rejected by the revised plan.** Linux documents `memory.high` as a throttling/reclaim boundary, so a peak clamped near it is not an uncapped working-set upper bound. Plan lines 263-342 instead start with the unchanged limit as candidate 0, use host-approved monotonic increments only after failure, and judge deltas/slopes against pre-registered thresholds. See the [Linux cgroup v2 memory controller documentation](https://docs.kernel.org/admin-guide/cgroup-v2.html) and [Incus instance memory options](https://linuxcontainers.org/incus/docs/main/reference/instance_options/).
9. **A sequential cold start alone proves container-boot safety. — Rejected during this review and fixed in the target plan.** Both OpenD units are enabled under `multi-user.target`; direct boot can overlap them. Plan lines 322-342 now use the sequential phase only as a safety screen and require a second parallel two-unit cold-start phase before any candidate passes.
10. **The capacity experiment can be treated as read-only except for services/limits. — Rejected during this review and fixed in the target plan.** Production trade intake runs in apply mode and reconnect/backfill may write normal intake state. Plan lines 310-320 now stop trade intake before OpenD, isolate its reactivation as an explicit business-write-capable boundary, avoid scheduled mutation/notification timers, and prohibit active probes/backfills/ticks.
11. **Per-account HOME isolation is required for this incident fix. — Rejected.** Futu documents non-Windows program/device state under the user's HOME and warns that device-state changes can trigger verification. Plan lines 357-382 defer this to a provider-state migration with its own identity/2FA/rollback design. See the [Futu OpenD FAQ](https://openapi.futunn.com/futu-api-doc/qa/opend.html).

## Findings

No material unresolved findings.

The strongest counterexamples found in the second pass were incorporated before this review artifact was finalized:

- stopping/restarting OpenD while trade intake remained active could create normal business-state writes;
- raising memory before testing the unchanged limit would defeat the smallest-change objective;
- sequential cold-start success would not cover the existing parallel `multi-user.target` activation path.

The revised plan now has explicit consumer quiescence/reactivation authority, candidate 0, and a mandatory parallel cold-start phase. These are plan corrections, not implemented changes.

## Architecture-boundary review

- **Account/config ownership:** canonical account runtime configuration owns account type and endpoint. The service renderer only validates and projects that identity into command arguments and platform dependencies.
- **Strategy Lab ownership:** application-level missing-data/error/receipt semantics remain unchanged and are not invented by systemd rendering.
- **Service/profile ownership:** the profile records an additive binding receipt; service drift re-resolves canonical config and handles only one deterministic legacy compatibility case.
- **Host ownership:** Incus limits, host reserve, and rollback are a separate operator gate. The container SSH boundary is explicitly not mistaken for Incus-host authority.
- **Provider-state ownership:** Futu HOME, `Device.dat`, login, and 2FA are excluded from this work unit.
- **Business-write ownership:** trade-intake reconnection is separated from capacity measurement and requires its own reactivation authority.

No improper dependency inversion or new parallel source of truth remains in the plan.

## Best-practice review

- Fresh multi-account input fails closed rather than relying on ordering or defaults.
- Cross-market endpoint/root skew, missing endpoints, non-Futu accounts, externally managed endpoints, launchd behavior, and legacy-version skew all have explicit tests.
- Rollout captures pre/post process identity and validates generated systemd units before install.
- Capacity thresholds are registered before candidate results, use counter deltas, include host reserve/OOM stops, and preserve an exact rollback value.
- Timer persistence, reconnect/backfill side effects, 2FA, and restart loops are treated as operational states rather than happy-path footnotes.

## Optimal-solution review

The selected first slice is the smallest root-boundary correction supported by current facts: explicitly bind the sampler to the endpoint it already uses and remove the unrelated dependency. It preserves the research contract and avoids introducing a new readiness state machine. Testing candidate 0 before increasing memory prevents unnecessary host allocation; requiring a parallel phase covers the actual concurrent activation risk.

Alternatives such as removing all activation, silently skipping unavailable samples, fixed memory values, IO throttling, or immediate HOME migration either change semantics, mask the mechanism, or cross higher-risk boundaries without being necessary to validate the first slice.

## Overengineering review

The plan adds one CLI/render parameter, one internal resolver, one additive profile receipt, and one bounded compatibility path. It explicitly prohibits new public domain entities, account schema, unavailable-result semantics, readiness orchestration, IO controls, and HOME migration. The implementation surface is proportionate to the defect.

## Overcoupling review

Repository implementation, source delivery, release/production apply, host capacity mutation, business-write-capable consumer restoration, observation, startup orchestration, and provider-state migration are independent gates with independent evidence and rollback. A failure in one no longer forces simultaneous code, Incus, systemd lifecycle, and Futu-state changes.

## Execution, recovery, and version-skew review

- Fresh profiles require an explicit account when multiple Futu accounts exist.
- The installed legacy profile can migrate only through unique historical-endpoint matching; ambiguity blocks writes.
- The first rollout uses the existing no-restart path and proves both OpenD processes were untouched.
- Rollback stops the sampler timer before restoring the old dependency and does not silently restart OpenD.
- Capacity candidates begin at the original limit, increase monotonically inside a host cap, and fall back to one pre-approved safe account before lowering a failed candidate.
- Auth/2FA, OOM, host-reserve breach, sustained reclaim/refault, wrong-account mapping, and restart loops are explicit stop conditions.
- Trade intake remains stopped unless its normal write-capable reconnection is separately authorized.

## Validation review

The plan specifies thirteen focused renderer/profile/drift/CLI cases, including negative and version-skew paths; focused pytest, lint, full tests, `git diff --check`, Linux `systemd-analyze verify`, production unit/profile inspection, PID/timestamp invariance, capacity deltas, endpoint identity, and a natural two-hour sample. Assertions prove the intended dependency and endpoint rather than only service health.

No material validation gap remains for Gate A. Gates C-D correctly require live evidence that cannot be fabricated by unit tests.

## Open questions

No open question blocks Gate A implementation.

Gate D intentionally cannot begin until the host owner supplies the current/maximum memory values, minimum host reserve, candidate step, safe fallback account, maintenance window, and rollback ownership. Trade-intake reactivation also requires a separate explicit decision because it can perform normal intake writes. These are authorization-gate inputs, not values an implementation agent may infer.

## Residual risks and suggested tracking destination

- **Exact full-container reboot not exercised:** the parallel two-unit cold-start trial covers the primary OpenD concurrency mechanism, but other boot-time workloads are not identical. Track an exact reboot canary in the Incus operator runbook if separately authorized; keep it outside Gate A.
- **Provider-owned login/rate limits:** sampling may remain incomplete despite a successful unit. Track in Strategy Lab evidence-quality monitoring, without changing service dependency semantics.
- **Shared Futu HOME/device state:** still a correctness/authentication risk. Track in a dedicated Futu state-isolation migration with its own planreview.
- **No host-safe passing candidate:** if the parallel phase fails within the approved cap, track a dedicated startup-sequencing work unit with bounded readiness and restart suppression; do not extend this implementation slice.
- **Pre-Gate-D operational exposure:** normal all-service upgrades and container reboots remain held until capacity is proven.

## Final plan review conclusion

`pass-with-risks`

Gate A is code-generation-ready: ownership, public behavior, compatibility, failure cases, files, tests, acceptance, and rollback are sufficiently specified without asking the implementation agent to redesign the solution. Gates C-D are also operationally executable once their independent release/service/host/business-write authorizations and host-specific inputs are supplied.

The remaining risks are external operational facts or explicitly deferred provider/lifecycle work, not unresolved defects in the current implementation slice. No source implementation or production mutation was performed by this review.
