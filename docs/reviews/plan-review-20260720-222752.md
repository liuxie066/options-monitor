# Plan Review — Daily Decision Brief 用户通知回归方案

- **Review 类型**: adversarial implementation-plan review
- **Review 日期**: 2026-07-20
- **Review 目标**: 评估“保留 Daily Brief 后台结构化生命周期，但恢复旧版紧凑监控通知作为用户界面；阻塞时短告警；恢复或重大变化时发送完整当前通知；隐藏内部 ID、原始枚举、ISO UTC 时间、券商合约编码和拒绝诊断”的方案是否已经可直接交付实现。
- **Review 范围**: 用户通知投影、候选与行动语义、Daily Brief revision/diff/delivery 生命周期、渲染器 ownership、重试与幂等、展示契约和测试边界。
- **不在范围**: 修改策略筛选/排名算法、自动下单、改变账本事实、实施代码修复、关闭 Daily Brief 能力。
- **代码基线**: 当前 worktree `HEAD=6a30bcd4b3e7`（`v1.2.419`）早于 Daily Brief；本 review 以 `origin/main=bee60f201e1b`（`v1.3.4`）中的实际实现为证据。未触碰现有未跟踪文件 `paseo.json`。

## 总体判断

方案的产品方向正确：用户界面应该回答“现在该关注什么、为什么、与上一轮有什么变化”，而不是展示审计模型；同时不能因为通知文案回退而丢掉 Daily Brief 已建立的基线、revision、material diff、blocked/recovered、last-delivered pointer 和结构化读取能力。

但当前方案仍然是**方向性决策，不是 code-generation-ready implementation plan**。它没有收敛候选与行动的业务语义，也没有定义新旧渲染器的结构化接口和 ownership；“重大变化发送完整当前通知”与现有 delta delivery 状态机、幂等键和确认指针之间的关系也未说明。直接交给实施 Agent，最可能出现两类错误：一是简单关闭 Daily Brief，安全生命周期随之丢失；二是在现有错误 action 模型上仅换文案，继续把多个候选行误报为多个可执行行动。

## Reviewed target and scope

### 目标方案的核心主张

1. Daily Brief 不再以“每日决策简报 / 日内决策恢复”的审计式 Markdown 直接面向用户。
2. 后台继续保留结构化 snapshot、revision、blocked/recovered、material diff、delivery pointer 和审计能力。
3. 用户通知恢复到旧监控消息的紧凑信息层次。
4. blocked 发送短告警；恢复或重大变化发送一份自包含的当前完整通知，而非只发 revision delta。
5. 用户展示层隐藏内部标识、原始状态值、UTC ISO 时间、券商合约编码和大规模拒绝诊断。

### 成功标准

- 最新一条通知无需查找旧消息即可理解当前候选、持仓建议和资金容量。
- 用户不会看到 `position_lot_id`、`strategy_group_id`、`leg_role`、`LIVE`、`READY`、原始 ISO 时间或 `US.TCOM260821P40000` 等实现细节。
- 两个 TCOM 行权价不会被无条件表述为两个独立的“新增行动”；必须明确是候选、备选关系或真正的可执行计划。
- 没有 material change 时保持静默；重试不会重复发送；delivery confirmation 仍只推进到确认送达的 revision。
- CLI / Agent / audit JSON 仍保留结构化身份和完整诊断，不因用户脱敏而损失可追踪性。

## Assumptions tested

| 假设 | 压测结果 |
|---|---|
| 只改 renderer 就能解决问题 | 不成立。`daily_decision_brief_service.py` 已把有容量的候选同时放入 `candidate_payloads` 和 `actions`。重复和“候选即行动”来自上游语义。 |
| “恢复旧通知”天然意味着只改展示 | 不成立。`tick_notification_flow.py` 中 Daily Brief 已替代 legacy notification preparation；若用 feature flag 直接关闭，会连 lifecycle authority 一起回退。 |
| 旧 renderer 可被直接复用 | 不成立。旧监控格式以 legacy text 为输入，而 Daily Brief 是结构化 mapping；直接复用需要反向解析或字符串 round-trip，违反原始设计“不解析最终 Markdown”的约束。 |
| recovery/material change 改发完整消息不会影响 delivery 语义 | 未证明。repository 当前在首份 full 后固定产出 `delivery_kind="delta"`，且 last confirmed delivery 是安全边界；需要明确 payload 形态与内部 event kind 是否解耦。 |
| `valid_until_utc` 可直接显示为“有效至” | 不成立或至少欠规格。它是状态/会话边界，不自动证明报价或建议在该时间之前持续可成交。 |
| 隐藏内部字段等同于删除字段 | 不成立。内部身份是 stable diff、持仓关联和审计所需；应在 presentation DTO 做 allowlist，而不是从 canonical model 删除。 |

## Special review lenses

- **Architecture boundary**: canonical Daily Brief、diff/repository/delivery 生命周期应继续拥有决策状态；用户通知只能是其受控 projection。不能由 formatter 反推事实，也不能让 legacy text renderer 成为新权威。
- **Best practices**: 要保留 last-confirmed pointer、retry/idempotency、no-change silence，并用显式 presentation contract 做数据最小暴露；不能依赖黑名单过滤任意 mapping。
- **Optimal solution**: 最实际路径不是“完全回滚旧消息”或“继续修补审计 Markdown”，而是保留后台状态机，建立一个窄的结构化 compact notification projection；material diff 只负责触发与生成变化摘要，消息正文始终携带当前完整快照。
- **Overengineering**: 本 work unit 不应新增执行计划器、通用模板 DSL、新发送栈或第二份持久化 read model。候选/行动语义先做最小纠正，不为未来自动交易设计抽象。
- **Overcoupling**: 必须避免 Daily Brief 结构、legacy alert text、Feishu Markdown 和 delivery state machine 互相穿透。共享的应是窄 DTO/formatter，不是彼此的完整内部 schema 或渲染后字符串。

## Findings

### PR-01-未修复-高-回退边界未锁定，可能为修文案而删除 Daily Brief 安全生命周期
- **位置**: 方案中的“恢复之前的监控通知作为用户体验”与 implementation boundary
- **问题类型**: 架构边界 / 范围漂移 / 不可直接实施
- **当前写法**: 方案说明保留后台 Daily Brief，但没有列出必须保留的模块、状态和明确禁止的回退方式。
- **反例/失败场景**: 实施 Agent 通过关闭 `daily_brief.enabled` 或恢复 legacy notification preparation 达到视觉效果；通知变短了，但 last-delivered baseline、material-change silence、blocked/recovered、action invalidation、delivery confirmation pointer 以及 CLI/Agent canonical read model 一并失效。后续每轮又成为互不关联的独立消息。
- **为什么有问题**: 用户投诉的是展示和语义，不是 Daily Brief 生命周期本身。把 feature flag 关闭是表面成功、架构回归，并重新引入原设计要解决的“无法回答相对早盘计划发生了什么变化”。
- **直接证据**: `docs/gateflow/daily-decision-brief-goal-confirmation-20260719.md:12-20,24-26,39-50` 将 per-day/account baseline、material diff、blocked state、shared read model 和复用既有 delivery/idempotency 定义为核心目标；`src/application/tick_notification_flow.py:113-120,594-660` 显示启用 Daily Brief 后由其接管通知准备和发送；`src/application/daily_decision_brief_repository.py:159-185` 维护首次 full、后续 delta 和 last-confirmed delivery 比较。
- **影响**: 实施 Agent 跑偏 / 安全属性回归 / 状态不可审计 / 重复通知 / 后续返工
- **建议改法和验证点**:
  1. 在 plan 中列出保留边界：domain schema/diff、service assembly、repository revisions、last-confirmed pointer、delivery retry/idempotency、CLI/Agent read tools、blocked/recovered 和 no-material silence。
  2. 明确本 slice 只替换 outbound user projection 与必要的 delivery envelope 渲染语义。
  3. 明确禁止以 `daily_brief.enabled=false`、恢复独立 legacy notification authority 或绕过 repository 作为验收方案。
  4. 加回归测试：关闭/替换 presentation 后，revision 仍增加、无 material change 不发送、失败发送不推进 confirmed pointer、重试不重复。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### PR-02-未修复-高-候选被建模成行动，单纯换文案仍会产生错误决策含义
- **位置**: “有效行动”“恢复后新增行动”的用户语义及 Daily Brief action construction
- **问题类型**: 契约缺失 / 架构边界 / 非最优方案 / 不可直接实施
- **当前写法**: 方案要求通知更直观并隐藏系统字段，但没有先定义“候选”“行动”“备选方案”的判定条件，也没有说明两个 TCOM strike 是同时执行还是互斥选择。
- **反例/失败场景**: 账户有容量时，TCOM 40 Put 和 35 Put 都进入 `actions`，recovery diff 产生两条 `action_added`。紧凑 renderer 即使把合约格式改成人话，也仍会告诉用户“新增两个行动”，却没有合约数量、限价、优先级关系或只能二选一的约束。用户可能把扫描候选误解为明确交易指令。
- **为什么有问题**: 这是 domain/application assembly 的语义错误，不是 presentation-only 问题。一个可执行行动至少需要明确的选择关系和执行参数；仅有现金容量不代表所有入选 strike 都应执行。继续以 `open_candidate` 作为 user-facing action，会让“行动容量 8 手”进一步被误读为每个候选都可以各做 8 手。
- **直接证据**: `src/application/daily_decision_brief_service.py:117-126` 对每个 selected Sell Put 同时写入 `candidate_payloads`，并在有容量时追加 action；`:133-158` 对 Covered Call/Combo/close 也组装 actions；`domain/domain/daily_decision_brief.py:18-31,355-370` 使用 contract 和内部身份形成稳定 action identity 并输出 change view，因此不同 strike 自然成为不同 `action_added`；当前示例正出现 TCOM 40 Put 与 35 Put 两条新增行动。
- **影响**: 生成错误代码 / 用户误判 / 风险暴露被放大 / review 不可验收 / 后续返工
- **建议改法和验证点**:
  1. 在 plan 中明确最小语义：`open_candidate` 默认属于“机会/候选”，不能称为执行行动；close/adjust/invalidated position 可以继续属于行动生命周期。
  2. 若暂不设计执行计划器，则不要为 opening candidate 补造 quantity/limit；只把 diff 命名为 `candidate_added/removed/changed`，或在 user projection 中按候选变化处理。
  3. 同一标的多个 strike 必须呈现为有顺序的备选项或明确选择关系，不默认同时执行。
  4. 测试包含两个 TCOM strike：消息不得出现“两项新增行动”；容量只能显示为账户级上限，不能复制成每个候选的下单数量。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR-03-未修复-高-“复用旧 renderer”缺少结构化接口，会把新旧通知链路过度耦合
- **位置**: 用户展示层实现方式与 renderer ownership
- **问题类型**: 架构边界 / 过度耦合 / 最佳实践偏离 / 不可直接实施
- **当前写法**: 方案说恢复旧版紧凑监控通知，但未说明是复制旧格式、调用旧 renderer，还是建立新的结构化 projection。
- **反例/失败场景**: 实施 Agent 将 Daily Brief mapping 先拼成 legacy alert text，再交给 `notify_symbols.py` 解析；或者把完整 Daily Brief mapping 直接传给通用字符串 formatter。前者形成业务事实的字符串 round-trip，后者容易再次透出任意新增字段。之后 Daily Brief schema、legacy alert 语法或 Markdown 任一变化，都要求跨层同步修改，且错误只能靠端到端消息快照发现。
- **为什么有问题**: 原 Daily Brief 目标明确禁止解析最终 Markdown 反推业务事实。旧 renderer 的输入契约与结构化 Daily Brief 不兼容；“直接复用”并不是可执行设计。用黑名单隐藏几个已知字段也不安全，未来新增内部字段会默认外泄。
- **直接证据**: `docs/gateflow/daily-decision-brief-goal-confirmation-20260719.md:34-43` 要求从结构化运行产物/canonical services 组装，并复用 delivery 栈而非解析最终 Markdown；`src/application/notify_symbols.py:6-9` 声明旧监控布局 authority，但其实现消费并解析 legacy text；`src/application/daily_decision_brief_renderer.py:55-95,187-240,243-316` 直接遍历完整 brief 并展示 header、身份后缀、容量、候选、拒绝统计，形成另一套展示 ownership。
- **影响**: 过度耦合 / 内部数据再次泄漏 / 双 authority 漂移 / 单元测试困难 / 后续维护成本上升
- **建议改法和验证点**:
  1. 定义一个窄的、用户展示专用结构化 DTO，例如 account/market/as-of/status/change banner/candidate cards/position cards/capacity summary；字段采用 allowlist。
  2. Daily Brief projection 从 canonical mapping 映射到该 DTO；legacy notification 如仍需兼容，也通过独立 adapter 映射到同一 compact card formatter，禁止把 Markdown/text 当中间协议。
  3. 明确 formatter 只负责布局和本地化，不负责候选排序、行动判定、身份关联或 delivery 状态。
  4. 不新增模板 DSL、通用 renderer framework 或第二发送栈；一个 DTO、一个 compact formatter、必要的两个输入 adapter 足够。
  5. 契约测试保证 DTO 中不存在内部 ID、raw enum、raw broker symbol、rejection dump；新增 canonical 字段不会自动出现在消息中。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR-04-未修复-高-完整快照与 delta delivery 的状态机关系未定义，存在重复发送和确认指针错误
- **位置**: “恢复/重大变化发送完整当前通知”与 delivery/retry/idempotency 设计
- **问题类型**: 状态机漏洞 / 并发恢复风险 / 契约缺失 / 测试缺口
- **当前写法**: 方案规定 recovery/material change 不再只发 delta，而是发完整当前通知；但没有说明所有 material change 还是仅 recovery、内部 `delivery_kind` 是否改变、delivery key 如何生成、confirmed revision 何时推进、变化摘要如何保留。
- **反例/失败场景**: revision 2→3 发生 material change，系统以 full 类型发送当前快照；发送成功但确认写入失败，下一轮又把 revision 3 当首份 full 或再次从 revision 2 生成通知。另一种情况是把 full payload 当新基线重新建立 delivery key，导致同一 revision 的 retry 绕过原幂等键重复发送。若完全丢弃 diff，用户又看不到“为什么此刻收到消息”。
- **为什么有问题**: 当前 repository 以 last confirmed delivered revision 作为比较基线，这是重要的失败恢复属性。用户 payload 是否自包含与内部事件是 initial full 还是 material delta 是两个概念；plan 若不拆开，会迫使实现者重写或绕过状态机。
- **直接证据**: `src/application/daily_decision_brief_repository.py:159-185` 规定首次 delivered brief 为 full，之后 material change 固定为 `delivery_kind="delta"`，并相对最后确认送达 revision 比较；`src/application/daily_decision_brief_renderer.py:132-164` 当前 delta/recovery 只渲染变化摘要；`tests/test_daily_decision_brief_renderer.py:158-198` 将 revision-only delta/recovery 固化为现行契约。
- **影响**: 重复通知 / 漏通知 / confirmed pointer 错位 / 恢复不可预测 / 状态不一致
- **建议改法和验证点**:
  1. 推荐把“触发/审计事件”与“用户 payload 形态”解耦：内部继续保留 delta event、from/to revision、原 delivery key 和 confirmed-pointer 语义；用户消息渲染为“一行较上一版变化/恢复 banner + 当前完整 compact snapshot”。
  2. 明确所有 material user notifications 均自包含，而不只是 recovered；blocked 可使用短告警，但仍绑定当前 revision 和既有 delivery record。
  3. no-material runs 保持静默；失败发送不得推进 confirmed pointer；同一 delivery record retry 必须复用幂等键。
  4. 增加 crash-window 测试：发送前失败、provider 成功后本地确认失败、重复 scheduler run、blocked→recovered、多次连续 material changes。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR-05-未修复-中-“有效至”把状态边界表达成报价保证，时间本地化仍不足以避免误导
- **位置**: 时间和有效性展示契约
- **问题类型**: 契约缺失 / 最佳实践偏离 / 测试缺口
- **当前写法**: 方案只要求把 `2026-07-20T20:00:00+00:00` 等 ISO UTC 时间改得可读，未定义时区、日期省略规则、字段名称和有效性含义。
- **反例/失败场景**: 消息显示“有效至 16:00”，用户理解为候选报价/建议在 16:00 前有效，但数据其实截至 10:00，盘中价格、delta、收益率已经变化；或者账户市场与用户本地时区不同，省略时区后时间含义不唯一。
- **为什么有问题**: `valid_until_utc` 更接近本轮 actionability/session boundary，不是订单价格的有效期证明。仅把 ISO 转成本地字符串解决了可读性，没有解决语义准确性。
- **直接证据**: `src/application/daily_decision_brief_renderer.py:187-199` 当前把 `as_of_utc` 和 `valid_until_utc` 原样放入 header；目标文档 `docs/gateflow/daily-decision-brief-goal-confirmation-20260719.md:14-20,55-56` 把 valid/actionability 与 scheduled scan、市场状态相连，而未声明报价在整个窗口内保证可成交。
- **影响**: 用户误判时效 / 交易风险 / 消息契约反复修改
- **建议改法和验证点**:
  1. 优先显示“数据截至：美东 10:00（北京时间 22:00）”或产品选定的单一明确时区；同一交易日可省略日期，跨日必须带日期。
  2. 如确需显示 boundary，命名为“本轮状态有效至”，不能写成报价/订单“有效至”。也可在紧凑通知中只显示数据截至时间。
  3. 测试夏令时、跨日、市场时区与用户时区不同、缺少 valid-until、stale quote 等场景。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

## Open Questions

1. opening candidate 在 canonical Daily Brief schema 中是否继续保留 `action_type="open_candidate"` 以兼容已有 audit/read API，还是在 domain diff 层正式拆成 candidate lifecycle？建议本 slice 至少先定义 user-facing 语义，schema migration 可单独评估兼容性。
2. 同一标的多个 strike 的产品规则是什么：严格互斥、按 rank 展示首选+备选，还是允许组合执行？在没有明确资金分配/数量计划前，不应称为多个独立行动。
3. compact notification 的 canonical owner 应落在哪个模块？建议由通知展示层拥有 DTO/formatter，Daily Brief service 只提供结构化事实；需要在 implementation plan 中给出具体文件边界。
4. 用户时区固定为 Asia/Shanghai、按市场时区显示，还是两者同时显示？必须选定单一默认规则并覆盖 DST。
5. blocked 短告警是否包含上一次有效快照的摘要？若包含，必须明确标为历史/不可执行；若不包含，应给出下一次自动重试时间或用户应采取的动作。
6. rejection diagnostics 是否仅从主动通知删除，仍保留在 CLI/Agent/audit JSON？建议答案为是，并写入 non-goal，避免误删诊断能力。

## Revised plan required before implementation

建议将方案重写为以下最小可实施 slices：

1. **锁定不回退的后台边界**
   - 保留 Daily Brief canonical model、revision、diff、repository、last-confirmed delivery、blocked/recovered、read tools 与 audit。
   - 明确禁止 feature-flag 回退为 legacy authority。

2. **收敛候选/行动语义**
   - opening rows 在没有完整执行计划前均为候选；close/adjust/invalidated position 保持行动语义。
   - 定义同标的多 strike 的备选展示和 diff 词汇，不新增自动执行 planner。

3. **定义窄 presentation contract**
   - 使用字段 allowlist 的 compact DTO；将 broker contract code 转为如“TCOM 2026-08-21 $40 Put”。
   - 本地化状态、时间、风险与资金信息；禁止 identity suffix、raw enum、raw ISO、reject dump 进入 DTO。
   - formatter 只布局，不承担业务判定。

4. **保持 delta trigger，发送自包含 snapshot**
   - initial、material change、recovery 的用户消息均包含当前完整 compact snapshot；material/recovery 顶部增加一行变化 banner。
   - blocked 使用短告警；no change 静默。
   - 内部 delivery event/key/confirmation 继续沿用现有 delta lifecycle，除非另有证据要求 schema 迁移。

5. **契约与恢复测试**
   - 展示脱敏、合约人类可读、时间/DST、无 candidate/action 重复、多 strike 备选关系。
   - latest message 自包含、no-material silence、blocked→recovered、发送失败不推进 pointer、retry 不重复。
   - canonical audit payload 仍保留 lot/group/leg identity 和 rejection diagnostics。

## Residual risks and suggested tracking destination

- **Schema/API 兼容风险**: 如果正式拆分 `open_candidate` 与 action lifecycle，可能影响现有 read tool 消费者。建议单独记录到 Gateflow implementation plan 的 compatibility section，并增加 schema fixture tests。
- **消息长度风险**: “每次 material change 都发完整快照”在候选很多时可能超出渠道限制。建议由 compact DTO 明确 top-N、分组和总长度上限，同时在 audit/read tool 保留完整列表；不要回退成审计式全量 dump。
- **旧 renderer 双 authority 风险**: 迁移期若 legacy 与 Daily Brief 两套 formatter 同时存在，可能继续漂移。建议在模块 ownership 文档标注唯一 compact formatter，并为旧入口保留薄 adapter 后逐步收敛。
- **历史消息兼容性**: 已发送消息无需迁移；只需保证新 revision 的 delivery record 可继续与旧 confirmed pointer 比较。建议在 release notes 记录用户展示变化，不改历史 artifact。
- **产品语气风险**: “行动”“机会”“建议”具有不同交易含义。建议把术语表和示例输出纳入实施 plan 的 acceptance fixtures，而不是只靠 renderer snapshot 临时决定。

## Final plan review conclusion

**fail**

方案方向值得保留，但当前还不能安全交给 implementation agent。必须先修正并明确四个 blocker：

1. 锁定只改 user projection、不回退 Daily Brief lifecycle；
2. 收敛 candidate 与 action 的语义及多 strike 关系；
3. 定义结构化 compact DTO/formatter ownership，禁止 legacy text round-trip；
4. 明确 self-contained payload 与现有 delta delivery/idempotency/confirmed-pointer 的关系。

完成上述修订并补齐恢复/幂等/脱敏契约测试后，可重新 review；无需大规模重写，也不应引入新的 planner、发送栈或持久化模型。
