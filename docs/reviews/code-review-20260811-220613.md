## Findings

### CR-S1-RR-01-未修复-高-Combo 资金预过滤在 Candidate Engine 前删行，再次丢失财报证据诊断

- **入口/函数**: `run_combo_yield_scan_and_summarize()` ->
  `enrich_and_filter_combo_funding_cash()` -> `enrich_and_filter_sell_put_underwriting()` ->
  `evidence_summary_from_decisions()`
- **文件(行号)**: `src/application/combo_yield_steps.py:138-176,276-300,443-452`;
  `src/application/candidate_scanning.py:265-343`; `domain/domain/engine/candidate_engine.py:733-753`
- **输入场景**: Combo Yield `sp_lc` 的 Funding Put 在到期前 0–6 自然日财报硬窗口证据不可用，
  同时该合约资金不足或资金上下文不可用，使 `max_new_contracts < 1`。
- **实际分支**: Combo 的独立 cash helper 根据与 Candidate Engine 同一个 capacity 结果先过滤 DataFrame。
  被删行不会进入 underwriting，因而没有 per-contract opening decision。对于 metrics 已可计算的行，
  scan sink 也不会产生决策记录，最终 evidence summary 将其计为“从未评估”，并投影为干净
  `no_candidate`。
- **预期行为**: cash helper 只附加资金/capacity 事实；唯一正式过滤由 Candidate Engine
  underwriting 完成。该合约应生成同时含 `risk_earnings_unavailable` 和 `hard_capacity_put`
  的决策，结果为确定 capacity reject，但财报 diagnostic gap 仍可审计。
- **实际影响**: 最终不会放行资金不足的合约，但 `evaluated_contract_count` 和
  `diagnostic_evidence_gap_count` 会偏小；简报/审计会再次把“财报证据缺失但有其他确定拒绝”
  误表达为完整扫描。
- **直接证据**: `enrich_and_filter_combo_funding_cash()` 在行 158–173 使用
  `compute_sell_put_cash_capacity(...).accepted` 删行；行 288–296 只对存活行调用能够输出
  `decision_sink_fn` 的 underwriting。Candidate Engine 本身已在 `max_new_contracts < 1` 时输出
  `hard_capacity_put`，因此预过滤既重复又绕过正式决策权威。
- **建议改法和验证点**: 将 Combo cash stage 改为只 enrich 不 filter，保留旧 CSV 文件名仅作审计
  兼容；让 underwriting/Candidate Engine 产生唯一 capacity 结果。增加真实 cash helper 回归：
  earnings gap + 资金不足 -> `no_candidate`、`eligibility_unresolved_count=0`、
  `diagnostic_evidence_gap_count=1`，且 evaluated count 包含该合约。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### CR-S1-RR-02-未修复-中-JSON snapshot 集合校验在类型检查前调用 `row.get`

- **入口/函数**: `load_opening_candidate_snapshot()` / `validate_opening_candidate_snapshot()` ->
  Daily Brief `_load_opening_snapshot_family()` 或 AI Advice frozen-input 装配
- **文件(行号)**: `src/application/opening_candidate_snapshot.py:403-429,484-505`;
  `src/application/daily_decision_brief_service.py:690-707`;
  `src/application/ai_decision_advice/contexts.py:117-131`
- **输入场景**: content hash 与顶层字段正确，但 `strategy_results`、`candidate_decisions` 或
  `ranked_candidates` 数组中存在 scalar/list 元素，例如 `strategy_results=[null]`。
- **实际分支**: validator 在 `isinstance(row, Mapping)` 之前已经调用 `row.get(...)`。因此抛出
  `AttributeError`，而不是 `OpeningCandidateSnapshotError`。Daily Brief 只捕获后者，AI Advice 的预期
  fail-closed 边界也无法获得稳定的 snapshot-unavailable 错误分类。
- **预期行为**: 所有外部 JSON 集合先验证“是 list 且每个元素是 mapping”，再访问字段；
  所有畸形 snapshot 统一抛 `OpeningCandidateSnapshotError`并被消费者 fail closed。
- **直接证据**: `strategy_results` 的新 mapping 检查位于 set comprehension 之后；
  `candidate_ids` 也在 decision mapping 检查之前构建；ranked loop 未先验证元素类型。这些路径都可绕过
  本 slice 要求的加强校验。
- **影响**: 损坏/手工篡改/新旧版本不兼容的 JSON 可以使 14:00 批次简报或 Advice 装配
  直接失败，而不是输出明确的“候选证据不可用”。
- **建议改法和验证点**: 在任何 comprehension/loop 前对 results/decisions/ranked/scopes 完成统一
  collection item 类型校验；补参数化回归，确认每种畸形元素都只抛
  `OpeningCandidateSnapshotError`。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
