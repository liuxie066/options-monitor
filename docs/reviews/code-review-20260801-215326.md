## Findings

### DR-01 - 未修复 - 高 - A malformed profile can still send persistent OpenD state back into the release tree

- **Entry path**: `research strategy-lab update --profile-path ... --source opend --write` -> `_shadow_replay_runtime_root()` -> `run_strategy_lab_update()` -> `collect_shadow_replay_marks()`.
- **Current behavior**: The new limit loader fails closed for bad `config_paths`, but the runtime root resolver may return `None` when a supplied profile omits `runtime_root` and has no inferable canonical paths. `opend_base_root=None` then deliberately falls back to `repo_root`, and write mode persists limiter/cache state below the release tree.
- **Impact**: A partially malformed production profile can recreate the primary incident even though its limit configs are valid. This violates the plan's runtime-ownership goal and allows immutable releases to accumulate mutable provider state.
- **Required fix**: For `source=opend` plus `write=True`, if a non-empty supplied profile cannot resolve a runtime root, fail with `CONFIG_ERROR`. Preserve repository-root fallback only for profile-free local/developer invocations. Add a CLI regression that proves the update service is not called.
- **Severity**: high
- **Fix risk**: low

## Residual Risk

- Direct application callers can still intentionally omit `opend_base_root` and retain the historical repo-root default. That is a backward-compatibility contract outside the service-profile CLI safety boundary.
- Endpoint-limit merging assumes each canonical config is a complete runtime config; `opend_fetch_kwargs()` supplies canonical defaults for omitted endpoint blocks.
