## Findings

### DR-01-未修复-高-批量预占的 claim 可能在真正调用 provider 前过期并允许并发重复调用

- **入口/函数**: `reconcile_due_lifecycle_cases_for_source()` -> `claim_settlement_attempt()` -> `SettlementObservationCollector.collect_outcome()`
- **文件(行号)**: `src/application/trades/lifecycle_runtime.py:487-631,635-846`; `src/application/trades/inbox.py:462-506`; `tests/test_settlement_observation.py:1657-1756`
- **输入场景**: 同一 source 同时有多个可调用 provider 的 settlement case，前一个 case 的多源查询或写入耗时较长，导致后一个 case 从最初批量 claim 到实际 provider 调用超过 120 秒；另一 worker 在租约到期后开始同一 case。
- **实际分支**: runtime 先为所有 case 写入固定 `now_ms + 120_000` 的 claim，再一次性物化 account snapshot，随后串行调用 provider。后续 case 在调用前既不续租，也不重新核对 claim ownership。SQLite 允许另一 worker 在 `claim_until_ms <= now_ms` 时取得新 claim。
- **预期行为**: claim 的有效期应覆盖它保护的 provider I/O；任何 case 在实际调用前都必须持有当前有效且属于自己的 claim。等待前序 case 的时间不能消耗后序 case 的全部租约。
- **实际行为**: 后序 case 的租约可能在尚未调用时已失效，两个 worker 都可执行 provider I/O。旧 worker 最终还会在 completion 阶段因 ownership 已改变而失败，留下额外重试和 60 秒循环错误。
- **直接证据**: claim 在 `lifecycle_runtime.py:612-631` 全部收集完成，provider 调用直到 `lifecycle_runtime.py:664-846` 才顺序执行；租约下限固定为 120 秒且从传入的 tick `now_ms` 计算（`inbox.py:475-506`）。现有 2100-row resource regression 只有一个 provider case，未覆盖多 case 等待与 lease expiry。
- **影响**: 破坏“有效 claim 防止第二 worker provider call”的核心止血保证；慢 provider 或多 case 批次下仍可能出现重复网络调用、额外 CPU 与控制状态异常。
- **建议改法和验证点**: 将 claim 推迟到每个 case 真正准备调用 provider 之前，并用可注入的当前时钟计算租约；调用前原子核对/取得 ownership。新增两个 provider case + fake slow first call + competing worker 回归，证明第二 case 只能被一个 worker 调用，且 stale owner 不会执行 provider I/O。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### DR-02-未修复-中-provider input fingerprint 未包含实际使用的有效锚点身份

- **入口/函数**: `provider_input_scope_fingerprint()` -> `prepare_provider_required_state()` -> `collect_broker_settlement_observation()`
- **文件(行号)**: `src/application/trades/settlement_attempts.py:396-430,433-500`; `src/application/trades/lifecycle_reconciliation.py:235-285,624-629`; `src/application/trades/settlement_observation.py:185-260`
- **输入场景**: 原有效 option-close anchor 被 void/replaced，新有效 anchor 保持相同 case、target、数量与 timing，但 source event/evidence identity 不同；旧 case 正处于最长 6 小时 no-progress/unknown backoff。
- **实际分支**: case-scope change 会触发一次 replan，但 provider fingerprint 仅包含 case/target/timing/remaining/reserved/terminal fields，没有 `reservation_evidence_ids` 或 collector 实际选择的 validated anchor identity。`prepare_provider_required_state()` 因 provider scope 未变而保留旧 `next_attempt_at_ms`。
- **预期行为**: collector 将要使用的有效 anchor/pairing identity 变化属于 provider input 变化，应立即清除旧 scope 的退避；无关 evidence 变化仍应保留退避。
- **实际行为**: runtime 读到了新 anchor，却可能继续沿用旧 anchor 的最长 6 小时退避，延迟新的、已获授权的 settlement observation。
- **直接证据**: collector 从 `validated_anchors` 选择 anchor 并使用其 `source_event_id` 和执行时间构造查询（`settlement_observation.py:227-260`）；read model 已暴露有效 `reservation_evidence_ids`（`lifecycle_reconciliation.py:624-629`），但 fingerprint allowlist 未引用这些字段或 context anchor。
- **影响**: 有效生命周期事实改变后仍被旧失败状态抑制，settlement close reason/terminal resolution 最多延迟一个 6 小时 backoff 窗口。
- **建议改法和验证点**: 在 provider-input scope 中加入 canonical effective-anchor identity（至少有效 reservation evidence identity，最好是 collector 使用的 source event、execution time、account/contract role 的稳定投影）。新增测试证明有效 anchor replacement 重置 backoff，而添加无关 evidence 只触发 replan、不重置 provider backoff。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 中

### DR-03-未修复-中-所有 semantic projection 失败都会被误停成 legacy permanent block

- **入口/函数**: `_prepare_settlement_admission()` -> `reconcile_lifecycle_close_reason()` -> runtime exception classification
- **文件(行号)**: `src/application/ledger/lifecycle_settlement_semantics.py:15-16`; `src/application/ledger/writer.py:176-209,227-230`; `src/application/trades/lifecycle_runtime.py:759-807`
- **输入场景**: incoming/current observation 因版本偏差、字段损坏或 semantic metadata mismatch 无法投影，或 admission head 出现非 legacy 的一致性异常。
- **实际分支**: incoming、latest legacy 与 head inconsistency 都抛出同一个 `SettlementSemanticUnavailable` 基类。runtime 捕获整个基类并一律写成 `legacy_semantic_unavailable`；该 outcome 没有 next retry，后续 unchanged ticks 永久跳过。
- **预期行为**: 只有“最新已存储 legacy evidence 无法安全投影”可以进入人工检查型 permanent block。incoming/current contract failure 应保持 typed unknown/case-data outcome 和有限重试/显式状态，不能冒充 legacy 事实。
- **实际行为**: 非 legacy 的当前输入或状态问题被错误标记成 legacy，自动路径永久停止，且状态诊断掩盖真实故障类型。
- **直接证据**: writer 对 incoming projection 直接传播基类（`writer.py:176-185`），对 latest legacy 又包装成同一基类（`writer.py:202-209`）；runtime 仅按基类匹配并生成 `legacy_semantic_unavailable`（`lifecycle_runtime.py:791-805`）。
- **影响**: 一个可恢复的 current-contract/version 问题可把 case 无限期停放，违反 unknown errors 永不升级为永久阻断的契约。
- **建议改法和验证点**: 引入只表示 stored latest legacy incompatibility 的专用异常子类；runtime 仅对该子类写 permanent legacy block，其余 semantic unavailable 映射为有限 `unknown_error`（或明确的 current-contract error）。分别新增 malformed latest legacy、malformed incoming/current observation 与 head inconsistency 的分类测试。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
