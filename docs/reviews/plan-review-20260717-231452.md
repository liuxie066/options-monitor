## 1. Goal、non-goals 与 success signal

修订计划把 Reaction 定义为“allowlisted 文本事件已进入 business queue”的 best-effort ACK，并明确不代表业务或回复成功。目标覆盖前序 Copilot 阻塞时的下一条消息，而不是只优化 idle queue。

Success signal 已分成三类：

1. deterministic happens-before：B 的 Reaction invocation必须发生在 A release前；
2. fake-adapter steady-state：dispatch P95 ≤ 50ms、invocation-start P95 ≤ 250ms；
3. 经批准的受控/生产观测：warm healthy completion P95 ≤ 2s。

Non-goals 已排除通用 executor、durable ACK outbox、配置/schema扩展和未经批准的真实写入。

## 3. Special review lenses

### Architecture boundary review

通过。allowlist仍由 `assistant/policy.py` authoritative ownership；`inbound/feishu.py` 只做 channel-specific extraction和public policy调用；`feishu_ws.py` 不拥有 policy parser。没有引入跨层反向依赖、数据库或通用 channel contract。

### Best-practice review

通过。装饰性 ACK采用 bounded queue、短网络预算、无 backoff、失败隔离、stale/drop和脱敏阶段日志；同时保留普通 reply/send/token defaults。

### Optimal-solution review

通过。只在已明确需要“前序 Copilot阻塞时仍快速 ACK”的前提下增加一个固定单 worker。相比同 worker reorder，它满足目标；相比线程池、thread-per-event或durable outbox，它更小且风险更低。

### Overengineering review

通过。计划删除了不必要的 response `data.timings_ms` 扩展，不增加 metrics backend、配置项、repository、scheduler或generic coordinator class。40样本 timing evidence复用 fake adapter，不增加新框架。

### Overcoupling review

通过。同步 handler不等待异步 worker，也不共享 ACK完成状态；真实 ACK result只在 transport logs，inbound audit/reply receipt不被绑定到 ACK lifecycle。

## 4. Findings

**No unresolved material findings.**

复审中发现并已在 target plan 内修正的两个问题：

1. token refresh全局锁可能让 ACK绕过2秒HTTP budget继续等待；最终计划增加 ACK-only optimistic cache read和 `lock_timeout=0.0`，普通 caller语义不变。
2. submit/stop可能把 job放到 sentinel之后；最终计划要求 lifecycle lock原子化 accepting check、enqueue和 stop transition，并增加并发测试。

以上修正已进入 implementation contract，不再作为未修复 finding。

## 6. Residual Risks and Tracking

| Residual risk | Tracking destination |
|---|---|
| Feishu API成功后客户端 UI仍晚显示 | `feishu_ws_ack.total_ms` 与人工 UI时间分开观察；必要时单独建外部依赖 issue |
| DNS/OS scheduling可超过 urllib request timeout直觉 | ACK error/total log；不承诺硬 wall-clock deadline |
| shutdown时 in-flight HTTP可能在 join后完成 | `inflight_unfinished` 日志；queued jobs先drop；不尝试强杀线程 |
| ACK optimistic cache read可能撞上并发 force-refresh并使用旧 token | auth retry/lock争用后drop；仅影响 best-effort ACK，普通 caller不用该 fast path |
| 单 ACK worker在持续故障或 burst下丢 ACK | queue-full/stale指标；仅在健康依赖仍不达SLO时另开固定小并发 work unit |
| 真实 completion P95尚无生产证据 | 实施完成后先做 fake timing；真实验证必须另行批准，不能在单元测试伪造 |
