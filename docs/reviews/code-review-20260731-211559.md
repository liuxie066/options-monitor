### 1-未修复-高-生命周期 resolution 未与同快照原始事实绑定，完整结算证据可被省略后重新产生 actionable 建议

- **入口/函数**: `validate_position_fact_snapshot_contract()` -> `build_lifecycle_read_models_from_decision_snapshot()` -> `build_position_advice_plan()` -> `_position_lifecycle()`
- **文件(行号)**: `src/application/ledger/decision_snapshot.py:167-213,246-252`; `src/application/ledger/lifecycle_overlay.py:356-419`; `src/application/trades/lifecycle_reconciliation.py:151-166`; `src/application/position_advice_plan_builder.py:130-163,1603-1630`; `src/application/ledger/writer.py:1554-1601,1709-1733`
- **输入场景**: 一个 future-expiry short Put 已通过合法 `option_zero_price_close` broker evidence 建立 lifecycle case、source claim 与 direct resolution。冻结 snapshot 保留完整 raw case/evidence/claim/lot facts，但把 `account_lifecycle_resolution` 替换为同账户的 canonical empty resolution，并按现有规则重算外层 decision fingerprint。
- **实际分支**: contract validator 只分别检查 raw 字段是 object list、resolution 的自包含 hash/order 合法、account 相同，以及外层 fingerprint 匹配；它不要求 active raw case IDs 与 resolution/generation-token case IDs 精确覆盖，也不把 resolution 绑定到 raw case/evidence/allocation/source/timing/lot/void facts。read-model builder 只遍历 `case_resolutions`，因此 raw case 被静默省略；future-expiry fallback 把该 lot 判为 `open`。
- **预期行为**: 同一 frozen snapshot 中的 lifecycle resolution 必须是 raw lifecycle facts 的确定性派生，任何省略 case、改变 evidence/claim 冲突语义或加入 orphan resolution 都应 fail closed，不能回退成普通 open lot。
- **实际行为**: 最小反例中完整 resolution 得到 `settlement_pending / actionable=False / not_evaluable / 0 selected proposals`；替换为空 resolution 后 `validate_position_fact_snapshot_contract()` 返回 `()`，同一 raw facts 得到 `open / actionable=True / roll / 1 selected proposal`。
- **直接证据**: `validate_account_lifecycle_resolution()` 只重算每条 resolution hash 与 arbitration hash；`validate_position_fact_snapshot_contract()` 没有 raw-to-derived coverage/binding；`build_lifecycle_read_models_from_resolved_account()` 从 resolution 列表出发而不是 raw case 列表。`accept_option_close_evidence_atomically()` 可在到期前收到 zero-price close 并建立 case，因此 future-expiry 反例来自正式写路径，不是纯畸形 fixture。
- **影响**: producer drift、artifact graft/corruption 或兼容转换可把已进入结算流程的仓位重新解释为可滚仓，绕过刚新增的 position-fact capability 边界；这会直接制造错误的正式 Position Advice 候选。
- **建议改法和验证点**: 在现有 position-fact contract boundary 绑定 raw facts 与 derived resolution，不新增平行 authority。优先从冻结 facts 确定性重算并比较 canonical resolution；若必要的 receive-time authority 尚未包含在 snapshot，则增加一个由 producer 计算、consumer 可验证的 lifecycle-resolution input hash，并同时要求 active case IDs、case resolutions 与 generation tokens 精确一致。新增 omitted case、orphan resolution、raw conflict 改 clean、direct anchor omitted 与 superseded case coverage 回归，并断言 plan 零 actionable proposal。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### 2-未修复-高-supersede 将原 pair 与临时失活的替代 pair 一并永久禁止，释放的 lot 无法重新推理

- **入口/函数**: `adopt_post_trade_combo_pair()` -> 后续 `reconcile_combo_pair_inferences()` -> `expire_stale_combo_pair_inferences()` -> `supersede_post_trade_combo_pair()` -> 下一轮 reconcile
- **文件(行号)**: `src/application/ledger/combo_reconciliation.py:35-40,319-444,447-530`; `src/application/ledger/repository.py:2283-2392`; `docs/plans/post-trade-combo-reconciliation-v1-plan-20260731.md:314-334`
- **输入场景**: 同账户/标的有 1 个 Put 与 2 个均满足硬约束的 Call；系统生成两个 ambiguous inference，用户确认了错误 Call，执行一次 sweep，再 supersede 该确认，希望释放后的 Put 与另一个 Call 重新形成 proposal。
- **实际分支**: 确认后 sweep 排除已 claim 的两腿，并把共享 Put 的另一个 pending inference 以 `facts_drifted_or_leg_claimed` 标为 `expired_unresolved`。supersede 只把已确认 inference 标为 `superseded` 并 void adoption events。下一轮把 `expired_unresolved` 与 `superseded` 都加入 `forbidden_inference_ids`，两个 pair 均不能重新生成。
- **预期行为**: append-only supersede 完成纠错后，仍 open 且满足硬约束的 lot 应重新进入全局推理；因某次 confirmed claim 临时失活的替代 proposal，不应与用户 reject 或真实 TTL 到期共享永久禁止语义。
- **实际行为**: 最小 SQLite 反例输出 `initial=2`、确认后 `after_claim=0`、supersede 后 `after_supersede=0, waiting=3`；存量状态为一条 `superseded/wrong pair` 与一条 `expired_unresolved/facts_drifted_or_leg_claimed`。
- **直接证据**: `_TERMINAL_PAIR_STATUSES` 无条件包含 `expired_unresolved` 和 `superseded`；`expire_stale_combo_pair_inferences()` 把“facts drifted”与“leg claimed”压成同一个终态；supersede 不建立新 generation 或恢复由该 claim 导致的替代项。当前测试只验证 membership 被撤销，没有覆盖 `confirm -> sweep -> supersede -> reconcile`。
- **影响**: 文档承诺的错误确认纠正流程在常见多候选图中功能性阻断，用户撤销错误组合后仍无法通过正式流程确认正确组合。
- **建议改法和验证点**: 区分用户 reject、真实 proposal TTL 到期与“因 active confirmed claim 暂时失活”；supersede 后仅允许受该 claim 影响的 lot 进入新 generation/re-derivation，同时保持 user-rejected、真实过期和原错误 pair 不被静默复活。增加 1 Put + 2 Call 的完整状态机回归。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高
