## Findings

### R413-PR-001-未修复-中-readiness evidence 来自落后 76 个提交的 v1.2.402 checkout
- **位置**: `Direct facts` 的 local read-only audit claim，以及 `OpenD` residual-risk classification
- **问题类型**: 测试缺口 / open question 未收敛
- **当前写法**: plan 把本机 Python 3.12、US/HK config valid/fresh、无 Python runtime failure 作为 release-candidate direct fact。
- **反例/失败场景**: audit 实际从主工作区 `main@34e56cac`、`VERSION=1.2.402` 执行；该 checkout 落后 `origin/main` 76 个提交，不包含 PR #81 的 selector/import-guard contract。旧 launcher 能成功运行并不能证明 v1.2.413 release candidate 能读取同一生产 config/runtime artifacts。
- **为什么有问题**: 计划把 host/config baseline 与 release-candidate compatibility 混成同一证据，可能在发布前遗漏最新代码对 runtime/config 输入的读取回归。
- **直接证据**: preflight 输出显示主工作区 `main...origin/main [behind 76]`、`VERSION=1.2.402`；clean release branch 才位于 `929aae4b`，且目前没有自己的 `.venv`/runtime config。
- **影响**: release plan 可能错误宣称 readiness 已验证；生产 canary 风险被过早降级，发布后才发现最新代码无法消费现有 runtime config。
- **建议改法和验证点**: 将旧 audit 降级为 host/runtime-data baseline；在 clean release branch 上通过显式 Python 3.12 和临时 runtime-dependency venv，向 `runtime_status`、`healthcheck`、`config_validate` 传入主工作区 US/HK config 的绝对路径，记录最新代码结果。OpenD offline 可继续分类为外部依赖，不要求启动服务。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### R413-PR-002-未修复-中-success/stop conditions 没有对应的可执行 release evidence
- **位置**: `Success signals` 3、R1 stop conditions、`Validation Plan`
- **问题类型**: 测试缺口 / 不可直接实施
- **当前写法**: plan 要求 rendered notes 只包含 1.2.413，并要求在 main/tag drift 时停止；命令矩阵只运行不带 `--render-notes-out` 的 `release_check.py`，也没有列出实现前/PR 前的 remote main/tag/release recheck。
- **反例/失败场景**: changelog heading 可通过 metadata check，但 release notes body 仍可能错误包含旧 section；或 branch 建立后远端出现同名 tag/新 main commit，而 implementation agent 按现有命令继续创建 PR。
- **为什么有问题**: 自动发布会直接使用 `/tmp/release-notes.md` 并写 tag/release；这些是 release 的外部可见、难以撤销边界，不能只依赖文字 stop condition。
- **直接证据**: `_release-reusable.yml` 调用 `release_check.py --render-notes-out /tmp/release-notes.md` 后直接交给 `softprops/action-gh-release`; 当前 plan 的 validation command 未生成/检查该文件。
- **影响**: release notes 错误或版本/tag collision 可能在 merge 后才暴露，导致自动发布失败或错误 release metadata。
- **建议改法和验证点**: 增加 render-notes 命令并静态断言只含 `# options-monitor 1.2.413`、不含 `1.2.412`；在 implementation 前和 draft-PR 前执行 `git fetch origin main`、比较 `origin/main` 与 base，并只读确认 `v1.2.413` tag/release 不存在。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
