# Plan Review

## Reviewed target and scope

- **Target**: `docs/plans/daily-brief-local-gap-degraded-delivery-plan-20260730.md`
- **Review mode**: full adversarial re-review after the fixes recorded in `plan-review-20260730-171637.md`
- **Scope**: strict `success_empty` boundary, expiration discovery ownership, required-data planning/prefetch, quote evidence sealing, completed-zero projection, Brief authority, implementation slices, and tests
- **Excluded**: implementation, source edits, production execution, real notification, release, and deployment

## Goal and boundary understood

The plan must allow a genuinely successful zero-row option-data result to remain a complete, non-actionable decision source and continue through normal degraded Daily Brief delivery. Provider, parse, not-attempted, partial, and integrity failures remain fail-closed. Local display or strategy gaps should not suppress unrelated reliable content; only loss of global report authority should select fixed failure.

## Re-review of previous findings

- **Previous PR-01**: partially fixed. The plan now forbids `except Exception -> expirations=[]` and `expiration=None` fallback inside `fetch_symbol_option_chain()`, but it still models discovery as if that were the only owner. Scheduled prefetch performs an earlier discovery in `required_data_planning.py`, so the real orchestration remains under-specified.
- **Previous PR-02**: evidence-validation mechanics are fixed in the plan. The frozen manifest/resolver equality check is now explicit. However, the plan newly classifies every status/manifest mismatch as fixed failure without defining whether global source authority was actually lost, creating a product-boundary conflict.

## Assumptions tested

1. There is one authoritative expiration discovery stage per scheduled symbol fetch.
2. The typed discovery outcome named by the plan survives required-data planning and prefetch without a second discovery.
3. A valid discovery-empty result can produce a fetch plan, zero-row quote snapshot, receipt, and ready manifest entry without an option-chain fallback.
4. A projection-empty plan cannot silently become an unscoped second discovery.
5. Frozen manifest/status equality is sufficient to validate the displayed warning.
6. Failure of optional warning projection is distinct from failure of the adopted Position Advice source graph.
7. Candidate capture/source v1 can remain complete with zero decisions and non-empty quote dependencies.
8. The focused test gate covers the actual scheduled planning and prefetch owners.
9. The plan remains within the strict boundary and does not require provider peers, source v2, or notification persistence changes.

## Special review lenses

### Architecture boundary review

The plan correctly keeps rendering separate from classification and uses the frozen resolver rather than reading mutable raw files. The unresolved architecture issue is earlier: scheduled discovery ownership spans `required_data_planning.py`, `multi_tick/required_data_prefetch.py`, and the symbol fetch modules, while Slice A names only the latter fetch modules.

### Best-practice review

One external observation should have one typed outcome and be carried forward. Repeating discovery after planning introduces time-of-check/time-of-use drift and makes “provider succeeded empty” ambiguous. Separately, optional presentation evidence should not be promoted to a global blocker unless it invalidates the adopted decision-source graph.

### Optimal-solution review

The narrow solution remains preferable to provider-peer health or a new coverage model. The optimal local correction is to make the existing plan-time discovery result authoritative for the run and pass its typed result/targets into prefetch, avoiding a second call. No new public service or generalized state machine is required.

### Overengineering review

No material overengineering finding. Existing v1 source, manifest, Brief, and delivery contracts are reused. The plan appropriately rejects a new alert type, database, revision protocol, source v2, and provider-health model.

### Overcoupling review

Manifest/status equality is a narrow, defensible coupling because both describe the same sealed quote evidence. It becomes excessive only if any mismatch automatically controls global delivery despite the complete Position Advice source graph remaining valid. Authority must remain attached to the owning source graph, not to an optional display projection.

## Findings

### PR-01-未修复-高-计划遗漏 scheduled prefetch 的第一次 discovery，仍可能重复调用并改变空结果语义

- **位置**: Work unit 边界 §2.1；Typed outcome §4；Option-chain fetch result §5.1；Slice A；测试与质量门 §8
- **问题类型**: 架构边界 / 状态机漏洞 / 不可直接实施 / 测试缺口
- **当前写法**: 计划把 expiration discovery 和 per-expiration chain 描述为一个连续 fetch-owner 状态机，要求 discovery success-empty 直接终止、不调用 chain，并要求移除 `fetch_symbol_option_chain()` 的异常吞噬。Slice A 没有纳入 required-data plan/prefetch owners。
- **反例/失败场景**: scheduled tick 在 `_build_single_prefetch_fetch_plan()` 中先调用 `build_required_data_fetch_plan()`；后者已经通过 `list_option_expirations()` 做第一次 provider discovery。若 discovery 成功但 DTE/config projection 后所有 side plan 的 explicit expirations 为空，`_prefetch_fetch_kwargs_from_plan()` 把它转成 `explicit_expirations=None`。随后 `_fetch_one_inprocess()` 调用 `fetch_symbol()`，后者再次 discovery。第二次可能返回不同 expirations、成功空或失败，导致原 planning observation 被覆盖；更严重的是，计划声称 projection-empty 必须 fail closed，但实际空 projection 会进入第二次 unscoped discovery。
- **为什么有问题**: `success_empty` 的正向证明必须绑定一次明确的 provider observation。当前方案只修第二次 discovery owner，没有规定第一次 planning discovery 的 typed outcome、时间与结果如何进入 fetch plan，也没有决定哪一次是权威。Implementation Agent仍需自行重构最关键的 ownership 和 TOCTOU 语义。
- **直接证据**:
  - 计划第 115-128、146-154、187-203 行描述单一 discovery -> chain 状态机，并要求 projection-empty fail closed。
  - `src/application/required_data_planning.py:663-688` 在 build fetch plan 时已调用 `list_option_expirations()`，并只保存 `expiration_discovery_complete/error`，没有保存 success-empty、observation time 或 typed result。
  - `src/application/multi_tick/required_data_prefetch.py:217-237` 从 planning owner 建立 scheduled fetch plan。
  - `src/application/multi_tick/required_data_prefetch.py:240-280` 在所有 projected expirations 为空时输出 `explicit_expirations=None`。
  - `src/application/multi_tick/required_data_prefetch.py:420-451` 又调用 `fetch_symbol()`，使 symbol fetch owner重新 discovery。
  - `src/application/multi_tick/required_data_prefetch.py:328-356` 对有 strategy requirements 但零 expirations 的计划仍估算至少一次 option-chain call，与计划“discovery empty 不进入 chain”冲突。
  - Slice A 第 379-395 行未包含 `src/application/required_data_planning.py` 或 `src/application/multi_tick/required_data_prefetch.py`；focused gate 也遗漏直接 owner 测试 `tests/test_required_data_fetch_planning.py`。
- **影响**: 同一 run 可能基于两次不同 provider observation 分类；planning success-empty 可能被第二次失败变成 fixed failure，projection-empty 可能反而重新扩大为 unscoped fetch，或第二次 success-empty 被错误当成原计划 scope 的证明。报告行为不稳定且无法从 receipt 解释采用了哪次 observation。
- **建议改法和验证点**:
  - 明确 scheduled path 的唯一权威 discovery owner。推荐复用现有 plan-time discovery：`RequiredDataFetchPlanBundle` 保留最小 typed discovery result、observed/completed time 和 exact targets，prefetch 不再重复 discovery。
  - 将 `required_data_planning.py` 与 `multi_tick/required_data_prefetch.py` 纳入 Slice A；不需要新增公共框架。
  - discovery success-empty 由 prefetch 使用该 frozen plan observation 直接形成零行 payload/receipt；discovery failure 阻断 seal；projection-empty 与 discovery-empty必须是不同状态，前者按本计划 fail closed。
  - 若选择 fetch-time discovery 为权威，则 planning 不得先调用 provider；必须给出等价的单调用重排方案。不可保留两次 discovery 再“取最后一次”。
  - 增加测试：planning success-empty 只调用 provider 一次且不调用 option chain；planning error 无第二次 discovery；projection-empty 无第二次 discovery；plan targets 与 receipt fetch-plan identity 一致；inprocess/subprocess 两条路径一致。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR-02-未修复-高-局部 warning projection mismatch 被定义为 fixed failure，重新引入单点阻断全局消息

- **位置**: 决策 §1；不变量 §3.8；Daily Brief §5.5；Notification flow §5.7；验收矩阵 §7.2；完成定义 §9
- **问题类型**: 动机不成立 / 状态机漏洞 / 范围漂移 / 过度耦合
- **当前写法**: §5.5 规定 status/manifest 任一不一致时不形成 success-empty warning，并“按现有 status/source integrity 规则处理”；但 §7.2 第 13 项把任何 snapshot、receipt、outcome 或 reason mismatch 一律列为“必须继续 fixed failure”。同时 §5.5 又声明 normal authority 不依赖新降级契约、Position Advice source graph 仍然 complete。
- **反例/失败场景**: Position Advice candidate source graph 已采用并验证同 run 的 quote dependency，其他候选、资金和持仓 authority 完整；只有可选的 strategy-status display projection 写错 reason 或 receipt path。按 §7.2，整个 Daily Brief 转 fixed failure，可靠的其他内容被抑制。这正是用户要求改掉的“单标的/局部问题阻断全局消息”。
- **为什么有问题**: 必须区分两类失败：
  1. frozen manifest/receipt/bytes 或 adopted candidate source graph 失效——全局/权威证据受损，应沿现有 fixed failure；
  2. status warning projection 与已验证 authority 不一致，但 adopted source graph 仍完整——只是不足以展示该局部 warning，应记录 data gap/告警并继续 normal degraded delivery。
  当前计划把两者合并，既与核心需求冲突，也没有指定修改 `pipeline_succeeded`、notification authority 或 Brief blocker 的 owning transition。
- **直接证据**:
  - 计划第 18-19、298-309 行说明 warning 是非行动型展示，normal authority 仍来自 complete Position Advice source graph。
  - 计划第 341-342 行只说 mismatch 不形成 warning，并未定义它使 actionability blocked。
  - 计划第 448-462 行却把所有 status/manifest mismatch 列入 fixed failure。
  - `src/application/daily_decision_brief_service.py:427-440` 当前把 strategy status index 作为 `required=False` artifact 加载。
  - `src/application/daily_decision_brief_service.py:488-526` 只有 pipeline failure、全部 source unavailable、candidate execution failure、context/cash failure或 Position Advice authority conflict 进入 blockers；普通 data gap 不阻断。
  - `src/application/daily_decision_brief_service.py:528-564` 非 blocker 的 data gap 只产生 `degraded`，仍可保持非 blocked actionability。
- **影响**: 一个局部、非行动型告警投影错误会重新压制整个正常 Brief；实现 Agent可能为了满足验收矩阵把 optional status mismatch 接入 global blocker 或 `pipeline_succeeded=false`，扩大 authority 边界并违背产品目标。
- **建议改法和验证点**:
  - 在 §5.5/§7.2 明确按 authority ownership 分流：
    - frozen manifest/receipt/bytes 本身无效，或 adopted candidate source dependency 无效：existing fixed failure；
    - 仅 strategy-status projection mismatch，而 adopted source graph完整：不展示 success-empty warning，嵌入 `strategy_status_projection_mismatch` 非行动型 data gap，继续 normal degraded delivery。
  - 不修改 notification repository/state machine；让 existing Brief blocker/source-authority 规则决定全局失败。
  - 增加成对测试：同一 mismatch 在 source graph完整时 normal degraded；同一 underlying quote/receipt integrity failure导致 source graph失效时 fixed failure；两条路径 normal/fixed authority 互斥。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

## Open Questions

## Residual risks and suggested tracking

- Header-only CSV 仍不满足通用 coverage predicate，因此非冻结路径可能重取；scheduled frozen path 应只依赖 run-scoped manifest。建议在 Slice A source review 中确认未放宽通用 coverage。
- Close Advice 对 exact contract 缺失的 authority 仍独立，可能合法阻断带 open position 的账户；计划已明确不扩展该语义。
- `success_empty` 只证明当前 observation/request scope，不证明产品永久不适用、退市或未来为空；继续由非行动型文案和测试约束。
- 建议跟踪位置：本 plan 的 Slice A owner/sequence 与 Slice B authority matrix；无需新建 provider-health 或 notification 项目。
