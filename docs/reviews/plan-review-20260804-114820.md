# Plan Review — Incus `liuxie` OpenD reclaim/refault incident

- Review timestamp: `2026-08-04 11:48:20 Asia/Shanghai`
- Reviewed target: the conversational remediation plan that proposed (1) removing Strategy Lab's OpenD `Wants=`, (2) raising the Incus memory envelope, (3) starting `lx` then `sy` behind a readiness gate, and (4) adding per-account OpenD HOME/state directories.
- Review scope: root-cause assumptions, Strategy Lab recorder dependency semantics, systemd lifecycle and recovery, Incus memory sizing, per-account Futu state migration, rollout boundaries, and validation evidence.
- Excluded: implementing any fix, changing Incus limits, rendering/applying service units, restarting services, migrating Futu state, sending notifications, or writing broker/business state.
- Evidence basis: current repository source/tests/docs, the read-only incident observations already collected from `liuxie-incus`, and official Futu/cgroup documentation.

## Goal, boundaries, and claimed success signals

The plan's goal is to prevent a recurrence of the prolonged mmap file refault and NVMe read storm while keeping both account gateways usable. The stated success signals are bounded cold starts, no material growth in `memory.events:high`, `pgscan`, or `workingset_refault_file`, correct API/Telnet/account routing, and no surprise Strategy Lab activation of both OpenD services.

Log cleanup, release publication, production deployment, live notification, broker writes, and destructive Futu state cleanup are not part of this plan review. Repository changes, service application, Incus resource changes, and Futu state migration remain independent authorization boundaries.

## Assumptions tested

1. **Strategy Lab can simply stop pulling OpenD and report a benign skip.** Rejected. No such success/skip contract currently exists for an unavailable OpenD; fetch exceptions become action errors and the CLI reports `ok=false`.
2. **Strategy Lab needs both account OpenD services.** Rejected. The generated sampler does not pass `--opend-host` or `--opend-port`; the CLI defaults to `127.0.0.1:11111`, while the unit declares every rendered OpenD as a dependency.
3. **Removing all Strategy Lab `Wants=` is necessarily the optimal fix.** Unresolved. The documented recorder contract intentionally performs an OpenD-backed sample every two hours; removing activation without choosing a missing-sample policy can create silent evidence gaps.
4. **A generic readiness gate is safe with the current OpenD units.** Rejected as specified. The units are `Type=simple`, `Restart=always`, `RestartSec=10`, and have no rendered start-limit policy; a failing readiness hook can amplify cold-start pressure.
5. **A `7 GiB` / `8 GiB` first memory setting is evidence-derived.** Rejected. The old `memory.peak` was clamped near `memory.high`, so the uncapped cold-start working set remains unknown.
6. **Per-account HOME is a routine configuration migration.** Rejected. HOME owns Futu's program data and `Device.dat`; a new or copied state directory can require device-lock verification or create identity conflicts.
7. **All four changes belong in one implementation handoff.** Rejected. They cross repository contract, systemd lifecycle, host resource allocation, and authentication-bearing state migration boundaries with different rollback and authorization requirements.

## Findings

### PR-01-未修复-高-Strategy Lab 修复目标选错层级：真正缺陷是单端点采样却依赖全部 OpenD

- **位置**: 原计划第 1 步“移除 Strategy Lab sample 的 OpenD `Wants=`，OpenD 不在线时返回 `skipped/opend_unavailable`”。
- **问题类型**: 动机不成立 / 非最优方案 / 契约缺失 / 过度耦合
- **当前写法**: 将 Strategy Lab 从所有 OpenD 的自动激活中完全解耦，并把无 OpenD 视为良性跳过。
- **反例/失败场景**: 运维希望持续积累每 2 小时的 mark path，但 OpenD 平时不在线。去掉所有 `Wants=` 后，当前实现会将连接异常记为 `action_exception`/error；若同时改成成功 skip，又会在没有 receipt/alert 契约时静默丢失时间路径采样。反过来，保留当前实现会因一个只连 `11111` 的采样任务同时拉起 `lx` 和 `sy`。
- **为什么有问题**: 计划在没有先决定“采样必须保持还是允许缺口”的情况下改变了公开运维语义；同时没有修正过宽的账户依赖映射。
- **直接证据**: `src/application/service_deploy.py:1244-1279` 渲染的 sample 命令未传 `--opend-host/--opend-port`，却把全部 `opend_dependency_units` 同时放入 `After=` 和 `Wants=`；`src/interfaces/cli/research.py:206-207` 的默认端点是 `127.0.0.1:11111`；`src/application/shadow_replay/data_plan.py:291-319` 将 OpenD 异常收敛为 error，`src/interfaces/cli/research.py:1003-1007` 会据此返回 `ok=false`；`docs/SHADOW_REPLAY_RUNBOOK.md:56-67` 明确记录了 OpenD-backed 的 2 小时采样契约。
- **影响**: 实施 Agent 可能在“继续同时拉起两个 OpenD”和“静默丢掉 research evidence”之间二选一，二者都不满足目标。
- **建议改法和验证点**: 先把 recorder 的 endpoint/account 变成明确契约（例如显式选择 `lx`/`11111`），将 host/port 传入 sample 命令，并且只对应一个 OpenD unit。然后由用户明确选择：(a) 为保持采样而只自动拉起该单端点；或 (b) 不自动拉起，但增加可审计的 `deferred_opend_unavailable` receipt、计数器和缺口告警。新增 multi-account render test，证明 sampler 的 endpoint 和唯一 dependency 同一。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR-02-未修复-高-“readiness gate”未定义失败状态，会被 `Restart=always` 放大成冷启动循环

- **位置**: 原计划第 3 步“`lx` 真正 ready 后再启动 `sy`，然后启动 trade-intake”。
- **问题类型**: 状态机漏洞 / 并发恢复风险 / 不可直接实施 / 最佳实践偏离
- **当前写法**: 要求一个非固定 sleep 的就绪门，但未指定它属于 OpenD unit、独立 oneshot、还是一个 bootstrap orchestrator；也未定义 timeout/auth-required/resource-pressure 的退出语义。
- **反例/失败场景**: `lx` 进程已经监听端口，但尚在 DB 预热、等待手机验证，或 cgroup 再次出现高回收压力。如果把 probe 放到 `ExecStartPost=` 并返回失败，当前 `Restart=always` + `RestartSec=10` 会反复重启最昂贵的冷启动路径。只加 `After=` 又无法阻止 `sy` 在 `lx` 进程已 spawn 但尚未 ready 时启动。OpenD units 自身还可被 `multi-user.target` 直接激活，不仅是 trade-intake/Strategy Lab 的依赖问题。
- **为什么有问题**: 方案为了避免同时冷启动，反而可能创建高频冷启动风暴；对交易账户的 2FA 状态也缺少 fail-closed 处理。
- **直接证据**: `src/application/service_deploy.py:391-454` 的渲染器在有 `restart` 时固定加 `RestartSec=10`，不渲染 `StartLimit*`；`src/application/service_deploy.py:959-979` 将每个 OpenD 渲染为 `Type=simple`/`Restart=always` 并安装到 `multi-user.target`；`src/infrastructure/opend_watchdog.py:225-298` 已有 `ensure=False` 的 READY/qot/trd 只读 probe，但原计划未说明如何复用且避免它触发 start。
- **影响**: 更高的 IO/system time，两个账户网关反复上下线，手机验证循环，trade-intake 无法得到稳定依赖，且回滚时难以区分资源问题与认证问题。
- **建议改法和验证点**: 计划必须先定义 `inactive -> starting -> ready | auth_required | resource_blocked | failed` 状态和所有者。采用有界 timeout/backoff 的独立就绪步骤，只用 `ensure=False` probe；`auth_required` 和 `resource_blocked` 必须停止自动重启，而不是每 10 秒重试。明确 `Requires=/After=`、直接 boot activation、进程意外退出和容器重启四条路径。添加 readiness timeout、2FA、端口已开但 global state 未 READY、第二实例不得启动和 start-limit 回归测试；对渲染后 unit 运行 `systemd-analyze verify`。
- **修复风险（低/中/高）**: 高
- **严重程度（低/中/高/严重）**: 高

### PR-03-未修复-高-Incus 内存目标值无法从被 `memory.high` 截断的峰值推导

- **位置**: 原计划第 2 步“经宿主资源评估后，首次受控试验可考虑 `memory.high≈7 GiB` / `memory.max≈8 GiB`”。
- **问题类型**: 动机不成立 / 权限边界 / 测试缺口 / 不可直接实施
- **当前写法**: 以稳态约 `5.0 GiB` 和希望的 `1.5–2 GiB` 余量提出一组首次参数。
- **反例/失败场景**: 真实的双实例冷启动 working set 是 `9 GiB`，但原 `memory.peak` 只显示紧贴 `5.4 GiB` 的 `memory.high`；设为 `7/8 GiB` 后仍进入 reclaim，只是把事故延后。另一个反例是宿主的其他 workload 同时上升，容器放宽后把压力转移成宿主级 reclaim/OOM。
- **为什么有问题**: `memory.high` 的语义正是超限后节流并进入高压 reclaim；在该状态下的 peak 不能作为未受限需求的上界。计划没有给出宿主 reserve、试验步长、立即停止条件和独立回滚值。
- **直接证据**: 事故观测中 `memory.peak` 几乎等于 `memory.high=5.4 GiB`，`memory.events:high` 约 121.7 万次；[Linux cgroup v2 官方文档](https://docs.kernel.org/admin-guide/cgroup-v2.html) 明确说明，超过 `memory.high` 会节流进程并迫使它们进入 heavy reclaim，`memory.events:high` 记录的就是这种 direct reclaim。
- **影响**: 可能对事故无效，或将风险转移到其它容器/宿主；如果和启动链变更同时上线，还无法判断哪个变量真正有效。
- **建议改法和验证点**: 将 Incus 参数改成独立 operator experiment，不在 repository implementation plan 中固定数值。先明确宿主可用 reserve 和回滚值，然后在维护窗口以“单 OpenD 冷启动 -> 记录压力斜率 -> 第二 OpenD 冷启动”测定需求。指标使用前后 delta，而不是累积总数；任一 `memory.pressure full` 持续增长、`memory.events:high` 连续增长或读盘进入持续平台即停止第二实例并回滚。
- **修复风险（低/中/高）**: 高
- **严重程度（低/中/高/严重）**: 高

### PR-04-未修复-高-每账户 HOME 计划缺失 Futu 设备身份与登录迁移状态机

- **位置**: 原计划第 4 步“新增 `futu.state_home`，分离 `lx`/`sy` 状态与日志，不盲目复制或删除当前文件”。
- **问题类型**: 数据迁移风险 / 契约缺失 / 范围漂移 / 切片过粗
- **当前写法**: 在 `AccountRuntimePlan`、validator、service plan/profile/drift 中增加独立 HOME，维护窗口逐个初始化。
- **反例/失败场景**: 新 HOME 中没有 OpenD 自带程序数据，实例直接退出；或空 HOME 生成新 `Device.dat` 并触发设备锁/2FA。若为了避免验证而将共享 `Device.dat` 同时复制到两个 HOME，则可产生重复设备身份。分家后两套 `SecListDB.dat`/页缓存又可能增大内存工作集，使性能问题更容易重现。
- **为什么有问题**: HOME 不是普通 cache path，而是带登录和设备身份的外部协议状态。这个改动既不是解决当前 reclaim 的必要条件，也不能仅靠 config/schema 测试证明安全。
- **直接证据**: `src/application/account_config.py:35-48` 只有 `futu_opend_root`，`src/application/service_deploy.py:674-680,959-974` 将单个 global HOME 传给所有 OpenD。[Futu 官方 OpenD FAQ](https://openapi.futunn.com/futu-api-doc/qa/opend.html) 说明非 Windows 程序数据在 `~/.com.futunn.FutuOpenD/F3CNN`，`Device.dat` 被删除/损坏会重新生成设备标识并要求设备锁验证，复制相同 `Device.dat` 也可导致重复验证。官方多 OpenD 指引要求复制完整命令行 OpenD 目录并使用不同端口，但未证明“复制当前 HOME 为两份”是安全迁移策略。
- **影响**: OpenD 无法启动、账户误映射、行情权限互踢、2FA 阻塞，或新状态已创建但回滚路径不再等价。
- **建议改法和验证点**: 将 HOME 隔离拆成独立后续 work unit，只在启动链+资源修复已验收后执行。该 work unit 必须有明确的 migration matrix：每账户的旧/新 HOME、程序自带数据来源、是否创建唯一 device identity、2FA 和 qot/trd readiness 负责人、严禁同账户旧新实例同时运行、旧 HOME 保留时间和可执行回滚。首个 slice 仅做 Linux/systemd；除非有 Mac 多实例需求，不同时扩张 launchd 契约。
- **修复风险（低/中/高）**: 高
- **严重程度（低/中/高/严重）**: 高

### PR-05-未修复-中-一个 plan 跨越四个独立变更与回滚边界，无法归因也无法安全交付

- **位置**: 原计划整体 sequencing：代码依赖变更、Incus 参数、systemd 就绪编排、Futu HOME 迁移。
- **问题类型**: 范围漂移 / 切片过粗 / 过度耦合 / 权限边界
- **当前写法**: 虽然给出了先后顺序，但没有将每阶段定义为独立可停止、可回滚、需再授权的 work unit。
- **反例/失败场景**: 代码上线的同时放宽内存并迁移 HOME；事故消失后无法判断是 dependency scope、启动顺序、容量还是 state layout 起效。若失败，软件 rollback、Incus rollback 和 Futu state rollback 必须同时决策，增大交易时段的操作风险。
- **为什么有问题**: 这些变更属于不同 owner：应用层决定 recorder unavailable 语义，service renderer 拥有 unit 关系，宿主 operator 拥有 cgroup 限制，Futu/operator 拥有登录和设备状态。把它们作为一个 implementation handoff 违反项目的生产变更授权边界。
- **直接证据**: 项目 `AGENTS.md` 要求服务启停/修改、生产配置与业务数据写入各自明确授权；原计划同时涉及 repository source、systemd apply、Incus host config 和 HOME 状态。
- **影响**: 实施范围被默认扩大，验证不能归因，一个阶段的回滚可破坏另一阶段的状态。
- **建议改法和验证点**: 重写为四个独立 gate：A) 只修 recorder endpoint/dependency 和 unavailable 契约，仅交付 source；B) 独立的 Incus 容量试验，每次变更需 host 授权；C) 只做 bounded startup/readiness 状态机与 service rollout；D) 可选的 HOME migration。每个 gate 必须有 baseline、单独成功信号、单独 rollback 和下一 gate 的明确授权。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 中

## Architecture-boundary review

- Strategy Lab/Shadow Replay owns whether unavailable market-data sampling is `error`, `deferred`, or `skipped`, including receipt semantics. The service renderer must not invent that application outcome.
- Account configuration owns the endpoint/account identity. The service renderer may project that identity into unit dependencies but should not infer it from service-list position.
- systemd owns process activation/order/restart, but it should consume an existing read-only OpenD health contract instead of duplicating broker readiness logic in shell.
- Incus/host configuration is an operator boundary and must not be hidden inside repository deployment.
- Futu HOME contains external-provider identity state; it is a migration boundary, not merely a generated unit environment value.

## Best-practice, optimal-solution, overengineering, and overcoupling review

- **Best practice**: define the unavailable dependency outcome and bounded retry state before changing unit relationships. Current plan does not.
- **Optimal solution**: the smallest credible incident fix is to bind Strategy Lab to the single endpoint it actually uses and avoid pulling the unrelated second OpenD. Removing all automatic activation is a policy change, not the minimal correction.
- **Overengineering**: per-account HOME plus launchd parity is not required to validate or fix the reclaim incident. It should not be in the first work unit.
- **Overcoupling**: code, systemd, host resources, and provider state cannot be one release/rollout unit because their owners, evidence, authorization, and rollback differ.

## Open questions

1. Must the production Strategy Lab recorder preserve every scheduled OpenD-backed sample, or is an auditable missing interval acceptable when the selected gateway is offline?
2. Which account/endpoint owns research quote sampling: `lx@127.0.0.1:11111`, `sy@127.0.0.1:11112`, or an explicitly separate quote gateway? This must be based on quote entitlements and intended data ownership, not service ordering.
3. Are both OpenD services enabled directly under `multi-user.target` in the installed state, and which unit(s) are allowed to activate each one after the fix?
4. What host memory reserve may the `liuxie` container consume without harming sibling workloads, and who owns the Incus rollback?
5. Does the operator want two independent Futu device identities and the associated one-time 2FA workflow? If not, per-account HOME must not proceed.

## Residual risks and tracking destination

- The current system is stable and the exact cold-start storm has not been intentionally reproduced; the cgroup counters and activation timeline are strong causal evidence but still require a controlled maintenance-window confirmation. Track this in the Incus operator experiment, not in unit tests.
- Futu's internal mmap/database working-set behavior is externally owned. Even correctly isolated homes may duplicate cache and require more memory. Track only after the dependency and resource fixes are measured.
- If host protection is still required after reclaim is fixed, an `io.max`/IO-governance investigation may be warranted, but adding an IO throttle now would mask the root cause and is outside this plan.
- A no-restart source delivery does not prove production unit semantics. Track rendered-unit verification, service drift, activation timestamps, and cgroup delta evidence in the separately authorized rollout artifact.

## Minimum revision required before implementation

1. Resolve Open Question 1 and 2, then define one explicit Strategy Lab sampling endpoint and exactly one matching dependency.
2. Specify the application-level unavailable outcome and receipt/exit-code contract before editing systemd dependencies.
3. Define the bounded startup/readiness state machine, including restart suppression for 2FA/resource pressure and all activation paths.
4. Move Incus memory tuning and HOME migration into independent operator work units with their own authorization and rollback.
5. Add multi-account dependency tests, unavailable-path tests, restart/timeout tests, `systemd-analyze verify`, and trigger-specific production validation.

## Final plan review conclusion

`fail`

The diagnosis that cgroup reclaim/refault was the primary performance mechanism remains credible. The implementation plan is not code-generation-ready because it chooses an unproven Strategy Lab policy, leaves restart failure semantics unspecified, proposes an unsupported memory target, and includes an authentication-bearing HOME migration in the same delivery path. The first revised slice should be limited to explicit recorder endpoint ownership plus its single OpenD dependency and unavailable-state contract.
