# Plan Review — Close Advice Bug-First Boundary

## Reviewed target and scope

- **Target**: `docs/gateflow/close-advice-safety-boundaries-plan-20260722.md`, revision 1
- **Repository baseline checked**: `feature/option-notification-experience@58ce2a90`
- **Review mode**: `$planreview`, constructively adversarial
- **User boundary added during review**: “先修改 bug，不改策略”
- **In review scope**: fee correctness/fail-closed behavior, lifecycle quote routing, public/read contracts, shared fee consumers, Daily Brief projection/delivery authority, slice boundaries, tests, and dirty ownership
- **Out of review scope**: implementation, plan edits, threshold calibration, new strategy policy, real notification, release/deploy, config/state/broker/ledger/Feishu writes

## Goal and assumptions tested

The plan currently claims one work unit can safely deliver all of the following:

1. repair stale fee calculations and fee fail-open behavior;
2. stop expired lots from entering normal quote/data-gap evaluation;
3. convert explicit thesis revocation and lifecycle states into P0/P1 operator actions;
4. make those actions part of post-release notification semantics;
5. preserve existing shared-calculator compatibility and existing strategy behavior except for unsafe Close Advice actions.

The review tested these assumptions against current Close Advice, fee consumers, Daily Brief notification authority, delivery persistence, relevant tests, and the user's bug-only boundary.

## Findings

### PR-20260722-01-未修复-高-当前 work unit 把可证实 bug 与新策略优先级和通知语义捆在一起

- **位置**: 计划第 2 节目标 3、第 4 节 in-scope、第 5.2–5.6 节、S3
- **问题类型**: 范围漂移 / 过度耦合 / 非最优方案 / 切片过粗
- **当前写法**: 计划同时修复费用与过期路由 bug，并把 `continued_willingness=false`、`expiry_day`、`expired_open` 新映射为 `review_position` P0/P1 active action，改变通知内容和 material diff 语义。
- **反例/失败场景**: 一个远期、低风险、当前不满足任何平仓条件的 Covered Call，只因 lot snapshot 中 `called_away_acceptable=false` 就被提升为 P0 active action。这是新的紧急度/通知策略，不是修复既有函数违反已有契约的 bug。
- **为什么有问题**: 用户已明确要求“先修 bug，不改策略”。当前 S3 会改变哪些行被视为紧急操作、什么时候打扰用户、如何去重，而且没有 replay/实际生命周期证据支持 P0/P1 选择。
- **直接证据**: 计划 `:20,40-45,136,147-151,196-255,408-472`；当前 `src/application/close_advice_runner.py:1445-1495` 只将明确 false 记为 `close_calibration_status=review_required`，并没有 P0/P1 action 契约。
- **影响**: 实施 Agent 会在 bug fix 中同时做产品/策略决策；导致通知量、操作优先级和 public action contract 改变，之后无法区分收益是来自 bug 修复还是新策略。
- **建议改法和验证点**:
  - 把当前计划收缩成 bug-only work unit：费用真值/失败关闭，以及 expired/expiry-day 不应进入正常报价与年化收益评估。
  - 整个 S3，以及 `thesis_revoked -> P0`、`expiry_day -> P1`、`expired_open -> P0`、review fingerprint/diff 和新通知 selector 移到后续 strategy/product work unit。
  - bug-only 生命周期修复只输出可观测的 `position_lifecycle_state` 和显式 non-evaluable/reconciliation reason，不新建 active action 或通知优先级。
  - 验证活跃持仓分类/阈值/通知完全不变；只允许受费用 bug 或过期路由 bug 直接影响的行改变。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR-20260722-02-未修复-高-计划假设 review action 会进入通知，但当前唯一调度通知权威根本不消费 action diff

- **位置**: 计划第 5.5、5.6 节，S3 步骤 3、5–7、9，S3 允许文件
- **问题类型**: 架构边界 / 契约缺失 / 不可直接实施 / 测试缺口
- **当前写法**: 计划认为 `close_advice.txt` 会成为正常 account message，且 P0/P1 `review_position` 的 material diff 会进入已有 Daily Brief 通知路径；S3 只规划改 service/domain/renderer/repository tests，没有修改实际 delivery decision 边界。
- **反例/失败场景**: 非 fixed-report 时点首次产生 P0 `review_position`，brief diff 正确记录 `action_added`，但没有新 opening candidate。`decide_daily_brief_notification()` 仍返回 `none/no_pending_candidates`，不准备 envelope，用户收不到计划声称的 P0 复核。
- **为什么有问题**: scheduled ordinary notification 的项目契约是 Daily Brief 单一权威，不是 `symbols_notification.txt/close_advice.txt` legacy 文本。当前 decision 仅支持 fixed report 和 pending opening candidate；计算出来的 general action diff 只被附在 lifecycle audit，不决定发送。
- **直接证据**:
  - `tests/test_multi_tick_contract_batch2.py:18-27` 和 `tests/test_domain_engine_batch5.py:45-53` 锁定 scheduled renderer 只能是 Daily Brief。
  - `domain/domain/daily_decision_brief.py:97-122` 的 decision 只查 `fixed_due` 和 `pending_candidate_identities`。
  - `src/application/tick_notification_flow.py:664-725` 虽计算 brief diff，但只将 candidate pending set 传入 notification decision。
  - `src/application/daily_decision_brief_repository.py:160-225` 持久化的是 candidate pending/alerted state，没有 general action alert state。
  - 计划 `:249-263,424-456` 未包含 `src/application/tick_notification_flow.py` 或对应的 durable action-delivery contract。
- **影响**: 计划的核心“可见 P0/P1 复核” success signal 在真实调度路径上无法实现；或者实施 Agent 被迫临时设计新的 pending state、delivery kind、retry/idempotency 和 renderer，大幅超出 slice 范围。
- **建议改法和验证点**:
  - 按用户当前 bug-only 决策，首批直接移除通知/review action 变更，不要扩展 delivery 状态机。
  - 若后续确认需要即时复核通知，必须单独计划扩展现有 Daily Brief 权威：定义 durable action identity/pending/alerted state、delivery kind、优先级、fixed-report 竞合、retry/exact-envelope/idempotency 和 confirmation 测试；不能靠 `close_advice.txt` 旁路。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR-20260722-03-未修复-高-共享费率 bug 修复会改变候选计算与过滤，计划却把这些消费者定义为范围外

- **位置**: S1 allowed files/code decision 3/focused validation，aggregate acceptance
- **问题类型**: 过度耦合 / 范围不完整 / 测试缺口 / 最佳实践偏离
- **当前写法**: 计划在共享 `domain/domain/fee_calc.py` 替换 US/HK option fee 公式，但称 assigned-stock/scanner callers 在本 work unit 之外；聚焦测试只包含两个部分消费者。
- **反例/失败场景**: 一个 Sell Put candidate 的年化净收益刚好在 `min_annualized_net_return` 附近。更正 settlement/OCC/CAT/ORF 后它从 accepted 变为 rejected，或 Combo Yield 的 net credit/rank 变化。Close Advice 测试全通过，但候选输出和实际通知组成已改变。
- **为什么有问题**: 这个变化是共享 bug 修复的必然效果，不是可以用“caller 范围外”忽略的部分。用户要求不改策略，意味着阈值/排名算法不变；但更正输入费用后的结果变化必须被明确验收，不能隐藏。
- **直接证据**:
  - `calc_futu_option_fee()` 还被 `src/application/scan_sell_put.py:102,159`、`scan_sell_call.py:117,172`、`sell_put_call_helper.py:239-240`、`domain/domain/assigned_stock.py:388` 直接调用。
  - Sell Put 在 `src/application/scan_sell_put.py:101-130` 用 fee 计算 net income/cash basis/annualized net return，并在后续与最低年化阈值比较。
  - Sell Call 在 `src/application/scan_sell_call.py:116-139` 用 fee 计算 annualized net premium return。
  - Combo Yield 在 `src/application/sell_put_call_helper.py:239-249` 将 put/call fee 传入组合经济性。
  - 计划 `:288-310,329-338,525-531` 没有定义这些下游行为变化的验收边界。
- **影响**: 可能在未审查的情况下改变 Sell Put/Covered Call/Combo Yield 候选接纳、排名、资金占用与展示数据；full suite 即使通过也可能只是断言被随新常量改写，而没有证明阈值边界符合预期。
- **建议改法和验证点**:
  - 将 S1 拆成 S1a “共享费率真值 bug”和 S1b “Close Advice fee fail-closed bug”，先验收 S1a 再改 action gate。
  - S1a 明确列出全部直接消费者，不改 threshold/rank algorithm；为 Sell Put/Sell Call 添加阈值下/上的反例，为 Combo Yield 加 fee 传导和 rank/economics 回归，为 assigned-stock 加 estimate 回归。
  - 验证至少覆盖 `tests/test_fee_calc.py`、`test_sell_put_linked_call_helper.py`、`test_sell_call_strategy_unification.py`、`test_candidate_filter_trace.py`、`test_assigned_stock_quotes.py`、`test_positions_reporting.py` 和对应 scanner 边界场景。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR-20260722-04-未修复-中-HK option tariff tier 被错当成账户套餐，`fee_calc_status=ok` 会夸大精确性

- **位置**: 计划第 3.2 节 HK fee assumption、第 5.1 节 fee status、S1 code decision 1、S1 stop condition、risk table
- **问题类型**: 动机不成立 / 契约缺失 / 非最优方案
- **当前写法**: 计划称“account tier 不在 contract 中”，因此统一使用 HK Tier 1 `3/contract`，并将成功结果标记为 `fee_calc_status=ok`；实施停止条件也围绕“实际账户套餐/tier”。
- **反例/失败场景**: 某 HK Tier 3 option 的真实 tariff 是 `0.5/contract`，但计划以 `3/contract` 计算并标记 `ok`。边际平仓被误判为费后不经济；输出却看不出这是保守上界而不是精确费用。
- **为什么有问题**: Futu 官方页将 Tier 1/2/3 定义为 stock option 类别，并要求参考 HKEX 的 option classification；它不是用户账户的高频/固定费率套餐。Tier 1 作为 fail-closed 上界是可以辩护的 bug-fix 选择，但不能对外宣称是 exact/ok。
- **直接证据**: Futu HK 官方 fee schedule `https://www.futuhk.com/en/support/topic2_335` 的 Hong Kong Options 表列出 Tier 1/2/3 `3/1/0.5 per contract per side`，紧接着注明参考 HKEX 的 options classification；计划 `:92-100,179,293-317,342-344,545-549` 则把它建模为 account tier。
- **影响**: 费用状态失真，HK 边际平仓产生 false negative；之后无法从输出区分“确切费用”和“保守上界”。
- **建议改法和验证点**:
  - bug-only 最小方案：保留 Tier 1 上界，但把状态/依据显式标记为 `conservative_estimate` / `hk_tier1_upper_bound`，并允许它用于 fail-closed gate；不再询问“account tier”。
  - 若要 `ok/exact`，必须在后续工作中从可靠 instrument metadata 解析 HKEX tariff classification，不能根据账户推断。
  - 添加 Tier 1 上界可操作/Tier 1 上界不可操作的边界测试，并断言 public row 不会将上界标记为 exact `ok`。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### PR-20260722-05-未修复-中-“整个 run 只用一个 business date”没有覆盖现有 event enrichment 日期读取

- **位置**: S2 code decisions 1–5，S2 tests
- **问题类型**: 不可直接实施 / 状态机漏洞 / 测试缺口
- **当前写法**: 计划要求 `run_close_advice()` 开始时只调用一次 `expiration_business_today()`，但只明确把它传给 lifecycle/DTE helper；测试只要求冲突 quote DTE 不改变 lifecycle。
- **反例/失败场景**: run 在 Asia/Shanghai 零点附近开始，lifecycle 以前一天计算；随后 short-vol event enrichment 再读一次时钟得到次日。同一 row 的 DTE/lifecycle 与 event date-distance 基于不同日期。
- **为什么有问题**: 当前 `_merge_event_snapshot_for_short_vol_positions()` 在 `src/application/close_advice_runner.py:1268-1273` 内部再次调用 `expiration_business_today()`。S2 的 allowed files 能修，但计划没有要求改该 helper 签名或测试这条路径。
- **直接证据**: `src/application/close_advice_runner.py:1245-1273`；计划 `:358-390`。
- **影响**: 日期边界上仍可产生内部不一致的生命周期/事件风险证据，违反 S2 的单日期权威 success signal。
- **建议改法和验证点**:
  - 将 `business_date` 显式传入 `_merge_event_snapshot_for_short_vol_positions()` 及所有 run-local date consumer，禁止 helper 内部重读时钟。
  - 测试 monkeypatch date provider 对第二次调用直接失败，并断言 lifecycle 与 event annotation 获得相同 `business_date`。

- **严重程度（低/中/高/严重）**: 中

## Open questions

1. Bug-only 阶段是否接受 HK Tier 1 作为明示的保守上界，还是要求取得 instrument-level HKEX tariff classification 后才对 HK 输出可操作平仓？
2. 费用方向是否仅修正确定性常量/公式，并把所有下游候选变化作为 bug-fix 预期效果？审查建议是“是”，但必须保证 threshold/rank policy 本身不变。
3. S3 被延后后，当前 dirty `daily_decision_brief_renderer.py` 和对应测试不再与首批 bug fix 重叠；实施前仍应重新确认 S1/S2 没有新的 dirty overlap。

## Residual risks and tracking destination

- **Fee schedule drift**: bug-only 计划仍需 dated constants/source URLs；后续建立周期性人工审核，不加 runtime network dependency。
- **Midpoint fill risk**: 保留为后续 strategy/replay work unit，本批不改决策价。
- **Manual review strategy**: `review_position`/P0/P1/delivery state machine 转移到单独 strategy/product plan，与 bug-fix 效果分开回放和验收。
- **Expired broker outcome**: 本批只标记和跳过错误报价路径，不推断 assignment/exercise；真正 reconciliation workflow 另建 issue/work unit。

## Final conclusion

**fail**

当前 revision 1 不应交给 implementation agent。它违反用户新确认的 bug-only 边界，并对 Daily Brief 通知权威、共享费率影响面和 HK tariff tier 有会导致错误实施的假设。

建议下一步是先把计划改为两个 bug slices：

1. shared fee truth + all-consumer regression，随后 Close Advice fee fail-closed；
2. expiration lifecycle routing + single business-date authority，只输出 diagnostic/read evidence。

`review_position`、thesis revocation priority、manual-review notification/diff/delivery 全部延后到单独 strategy/product work unit。
