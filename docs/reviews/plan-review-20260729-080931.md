# Plan Review — Combo Yield 同期与跨期统一筛选排序

- Reviewed target: `docs/plans/combo-yield-unified-selection-plan-20260729-080931.md`
- Review scope: opening candidate filtering/ranking, research variants, required-data, evidence, rollout, and cross-expiry promotion boundary
- Review date: 2026-07-29
- Review posture: adversarial, implementation-readiness
- Conclusion: `fail`
- Artifact: `docs/reviews/plan-review-20260729-080931.md`

## Goal and boundary understood

The plan intends to unify the candidate-processing skeleton for
`same_expiry_pair` and `staggered_expiry_pair` without collapsing their economics into one score.
It keeps Combo Yield independent of standalone Sell Put runtime results, reuses Combo-owned
underwriting order for the Funding Put, moves cost/retention to hard gates, and evaluates target
Delta/expiry-gap policies in Shadow before any production promotion.

The intended implementation boundary excludes production config mutation, ledger writes, automatic
pairing/roll/close, portfolio-level exposure caps, and cross-expiry formal promotion.

## Assumptions tested

1. Existing required-data collection can supply every proposed same/staggered Shadow variant without
   changing production configuration.
2. Existing Shadow Replay and Strategy Lab group evaluation can compare outcomes for alternative
   pairs that were not actually traded.
3. Proposed ranking can be introduced without changing production selection before explicit
   promotion.
4. Funding Put rank provenance fields named in the plan exist or have an identified authority.
5. Retention and legacy Call-cost constraints have an unambiguous compatibility contract.
6. Existing lifecycle/accounting boundaries remain separate from candidate ranking.

## Review lenses applied

- **Architecture boundary review**: domain ranking ownership, application orchestration, research
  evidence, required-data planning, ledger/group identity, and public artifact consumers.
- **Best-practice review**: immutable experiment inputs, counterfactual outcome validity, fail-closed
  missing data, baseline/proposed isolation, and deterministic promotion evidence.
- **Optimal-solution review**: reuse of Combo-owned underwriting rank and existing group attribution
  rather than a new composite score or duplicate lifecycle engine.
- **Overengineering review**: research-only parameters should not prematurely expand production
  config or create a generic optimizer.
- **Overcoupling review**: baseline and proposed rank policies must not share one mutable authority
  before promotion; candidate research must not require canonical trade-group identity.

## Findings

### PR-01-未修复-[高]-跨期 Shadow 变体没有可执行的 required-data 获取路径
- **位置**: Sections 4, 7.2, 12.2 and S3
- **问题类型**: 契约缺失 / 不可直接实施 / 测试缺口
- **当前写法**: required-data planning remains globally fail-closed, and Shadow compares staggered
  variants with gap `14/28/45` without changing production config.
- **反例/失败场景**: A production run configured as `same_expiry_pair` plans Call expirations from
  Funding Put expirations only. It does not need later Call expirations. A research variant cannot
  rank a 28-day residual Call that was never fetched. A staggered production config with an existing
  `30-90` gap can likewise omit the proposed 14-day boundary. The Shadow artifact can then appear
  empty or select from a truncated universe and falsely label the result as a variant comparison.
- **为什么有问题**: The plan requires research isolation from production config, but supplies no
  separate research fetch plan or immutable evidence bundle that unions variant expirations.
  Required-data completeness cannot be asserted after the missing expirations were never requested.
- **直接证据**: `src/application/required_data_planning.py::_resolve_combo_yield_call_plan()` branches
  on the configured `structure_mode`; `docs/STRATEGY_ARCHITECTURE.md` states that staggered
  expirations are planned from configured relative gap fields and that global planning occurs before
  fetch. The proposed plan adds research gap variants but names no research collector or planning
  authority.
- **影响**: Shadow results can be incomplete, non-comparable and non-reproducible; S3 cannot prove
  the intended selection behavior.
- **建议改法和验证点**: Define a research-only required-data plan that takes an explicit immutable
  variant set, unions all required expirations before fetch, records planned/discovered/fetched
  expirations and completeness per variant, and cannot alter the production candidate universe.
  Add tests for a same-expiry production run evaluating staggered research variants and for a
  configured gap that does not cover the research gap.
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR-02-未修复-[高]-现有 group outcome evaluator 无法比较未成交的排序变体
- **位置**: Sections 10, 12.3, S2, S3 and S4
- **问题类型**: 动机不成立 / 契约缺失 / 不可直接实施
- **当前写法**: Candidate replay measures rank changes without claiming PnL, while promotion
  requires completed multi-horizon group outcomes. Proposed rows connect to the existing group-level
  evaluator only when canonical group identity and outcome evidence exist.
- **反例/失败场景**: Baseline selected Put A/Call X and was actually traded, but the Delta-20 variant
  would have selected Put A/Call Y. Only X has canonical `strategy_group_id`, lifecycle facts and
  synchronized marks. The existing group evaluator can measure X but has no counterfactual group
  outcome for Y. Repeating this over historical actual groups systematically evaluates baseline
  choices, not the proposed policy.
- **为什么有问题**: Candidate rank replay and observed-group outcome evaluation answer different
  questions. The plan correctly refuses to infer PnL from rank changes but provides no mechanism to
  obtain outcomes for the alternative candidates, so the stated promotion evidence cannot be
  produced.
- **直接证据**: `docs/PRODUCT_ARCHITECTURE.md` states that Combo Yield Strategy Lab V1 is an
  observed-universe group outcome evaluator and does not generate parameter variants or single-leg
  patches. `src/application/strategy_lab/combo_evaluator.py` requires group identity, capital-at-risk
  and multi-horizon outcome/mark-path evidence. The plan explicitly limits proposed rows to groups
  with canonical identity.
- **影响**: S4 is forced to promote based on coverage/rank aesthetics or on a biased subset of actual
  trades, not comparative risk/return evidence.
- **建议改法和验证点**: Choose and specify one evidence path before implementation: either
  (a) counterfactual Shadow settlement from immutable entry quote snapshots plus synchronized Put
  expiry/Call expiry marks for every selected variant, or (b) a separately authorized paper/manual
  pilot that records research group identities outside the canonical trade ledger. Define valuation
  horizons, fee/slippage treatment, missing-mark behavior and selection-bias disclosure. Prove that
  baseline and each variant are evaluated on the same decision instances.
- **修复风险（低/中/高）**: 高
- **严重程度（低/中/高/严重）**: 高

### PR-03-未修复-[高]-正式排序切换时点在正文和 implementation slices 中相互冲突
- **位置**: Section 9 versus S1-S4
- **问题类型**: 不安全 sequencing / 范围漂移 / 过度耦合
- **当前写法**: Section 9 says to remove `premium_funding_score` from
  `yield_enhancement_rank_key()` and make candidate, summary and alert use the new authority. S1 says
  preserve production selection unchanged; S4 says switch formal rank authority only after explicit
  approval.
- **反例/失败场景**: An implementation agent follows Section 9 in S1 and edits the shared
  `yield_enhancement_rank_key()`. Candidate materialization, report summary and alert rendering all
  consume that same function, so the research slice silently changes production ranking before
  evidence or approval.
- **为什么有问题**: Baseline and proposed policies currently share the same ranking entry point.
  The plan has no explicit separate proposed-rank API, so “centralize proposed ranking” and “preserve
  production” cannot both be implemented safely from the current wording.
- **直接证据**: `src/application/sell_put_call_helper.py`, `src/application/report_summaries.py` and
  `src/application/render_yield_enhancement_alerts.py` all call
  `rank_yield_enhancement_rows()`/the current domain rank authority. Existing
  `build_yield_enhancement_rank_shadow()` already demonstrates the safer baseline-versus-shadow
  separation.
- **影响**: A Shadow-only work unit can alter user-visible recommendations and notifications, making
  replay evidence self-referential and violating the plan's non-goals.
- **建议改法和验证点**: Define separate named baseline and proposed rank policies/functions. S1-S3
  may only write proposed Shadow artifacts. The shared production
  `rank_yield_enhancement_rows()` remains baseline until S4 approval. At promotion, change the
  production delegate in one reviewed slice and prove candidate/summary/alert parity from the same
  selected row.
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR-04-未修复-[中]-Funding Put rank provenance contract names facts that are not currently propagated
- **位置**: Section 5 and S1
- **问题类型**: 契约缺失 / observability gap / 不可直接实施
- **当前写法**: `funding_put_rank_scope` includes account, run ID, quote snapshot ID and policy hash,
  and every pair preserves rank scope evidence.
- **反例/失败场景**: The current Combo Yield Put scan call does not pass
  `risk_policy_version`/`quote_snapshot_id`, and `_put_risk_fields()` does not copy run/policy rank
  provenance. An implementation may fill these fields with nulls, derive them from filenames, or
  silently omit them while still claiming reproducible rank evidence.
- **为什么有问题**: Run-scoped integer rank is meaningful only when the exact candidate universe and
  ranking policy are identifiable. The plan specifies the desired envelope but not the canonical
  source or missing-data behavior.
- **直接证据**: `src/application/combo_yield_steps.py::run_combo_yield_scan_and_summarize()` invokes
  `run_put_scan_fn()` without the scan provenance arguments. `src/application/sell_put_call_helper.py::_put_risk_fields()`
  copies underwriting/risk fields but not the proposed rank-scope facts.
- **影响**: Cross-run comparisons can combine non-equivalent universes and policies; rank-change
  explanations become unauditable.
- **建议改法和验证点**: Name the existing run manifest/policy snapshot as authority, pass exact IDs
  into the Combo-owned scan, and fail the proposed experiment closed when required provenance is
  missing. Do not derive identity from artifact paths. Add replay tests for mismatched quote/policy
  scope.
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 中

### PR-05-未修复-[中]-legacy Call 成本字段的冲突语义仍留给 implementation agent 决定
- **位置**: Section 6
- **问题类型**: open question 未收敛 / 配置契约缺失
- **当前写法**: Keep `max_call_cost_to_put_credit` for compatibility and either reject conflicting
  explicit values or define one documented precedence before implementation.
- **反例/失败场景**: A symbol explicitly configures retention `0.75` and max cost `0.30`. One
  implementation rejects config, another applies the stricter gate, and another lets the later
  merged value win. Generated snapshots and runtime behavior diverge despite the same authoring
  input.
- **为什么有问题**: The plan's central simplification is that these values are algebraic
  complements. Leaving two alternative compatibility behaviors unresolved makes the config/public
  contract non-deterministic.
- **直接证据**: Current config validation accepts both optional values independently;
  `_candidate_pair_reject_reasons()` applies retention while
  `compute_yield_enhancement_funding_decision()` separately applies max Call-cost ratio.
- **影响**: Implementation-time product decision, config drift and surprising candidate rejection.
- **建议改法和验证点**: Select one normative rule in the plan. The smallest compatible rule is:
  when both are explicit, both hard gates apply and diagnostics expose both; new defaults author
  retention only. If the long-term goal is deprecation, define warning/removal timing separately.
  Add equality, stricter-on-either-side and generated-config round-trip tests.
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

## Open questions

1. Which counterfactual outcome path is acceptable: immutable historical mark replay or a separate
   paper/manual pilot?
2. What exact existing manifest fields own `quote_snapshot_id` and policy hash for Combo-owned Put
   ranking?
3. Should same-expiry promotion be allowed independently while staggered remains blocked on
   portfolio/residual-call exposure control?
4. What human decision rule will adjudicate Delta 20 versus Delta 25 when neither strictly dominates
   across return, drawdown and coverage?

## Residual risks

| Risk | Suggested tracking destination |
|---|---|
| Delta, retention and expiry-gap values are unproven hypotheses | Strategy Lab experiment and decision record |
| Canonical underwriting rank is return-first after hard gates | Same-expiry/cross-expiry rank-change and outcome evidence |
| Single-stock skew and term IV are regime-dependent | Research evidence fields; no hard gate |
| Cross-expiry residual Call can accumulate exposure across groups | Separate reviewed opening-cap work unit before promotion |
| Missing synchronized marks can prevent multi-horizon evaluation | Shadow evidence completeness/quality envelope |
| Production defaults/config changes require separate explicit approval | S4 promotion work unit |

## Final plan review conclusion

`fail`

The unified strategy direction is materially better than the current duplicate composite score:
Combo-owned Put underwriting remains authoritative, cost becomes a hard gate, and same/staggered
economics remain separate. It is not yet safe to hand to an implementation agent. PR-01 through
PR-03 block the evidence and rollout path; PR-04 and PR-05 leave provenance and config behavior
underspecified. The plan needs a reviewed fix before implementation.
