## Findings

### PR-01-未修复-高-直接改变现有 fetch API 会破坏 event-source probe 公共入口
- **位置**: Slice A / Event source payload contract / allowed files
- **问题类型**: 架构边界 / 公共契约缺失 / 切片范围不完整
- **当前写法**: First-party `fetch_symbol_events_futu()` and `fetch_symbol_events_yfinance()` will return a mapping instead of the current event list, while Slice A excludes `src/application/events/probe.py` and does not define compatibility for direct callers.
- **反例/失败场景**: `om event-source probe` calls each function directly, stores the return value as `events`, and computes `len(events)`. A structured mapping would report key count as event count and expose the wrong response shape. Existing tests also directly assert list ordering.
- **为什么有问题**: The plan claims no public CLI change and a narrow compatibility adapter, but the proposed return-type replacement changes an existing callable/publicly exported function used outside EventStore.
- **直接证据**: `src/application/events/probe.py:95-97,120-122`; `src/application/events/__init__.py`; direct tests in `tests/test_event_source_futu.py` and `tests/test_event_risk_warn.py`.
- **影响**: Public diagnostic output silently corrupts event count/shape; Slice A cannot pass its own no-public-contract-change claim.
- **建议改法和验证点**: Preserve the list-returning functions. Add narrowly named evidence functions (or an internal optional evidence mode) used only by orchestrator/EventStore; keep probe behavior unchanged and add a regression proving direct fetch APIs still return lists.
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### PR-02-未修复-高-无 occurrence anchor 时的日期变化匹配会把正常事件滚动误报为日期调整
- **位置**: Section 4.2 Event identity and Slice C material diff
- **问题类型**: 状态机漏洞 / 不可直接实施 / 测试缺口
- **当前写法**: Material matching falls back to “a single unambiguous same-series nearest occurrence” when event IDs differ, but does not define the temporal guard or rollover behavior.
- **反例/失败场景**: A candidate survives an earnings date. The previous confirmed brief points to the now-past quarterly earnings event, while the new snapshot’s nearest earnings is the next quarter. Both are one event in the same `symbol+earnings` series. The proposed matcher can announce that the old earnings date was “adjusted” by roughly three months instead of recognizing that the previous occurrence elapsed and a new occurrence appeared.
- **为什么有问题**: Date-change notification is user-visible and risk-sensitive. Provider-neutral stable IDs are unavailable for some yfinance rows, so the fallback rule must be exact and fail closed rather than heuristic.
- **直接证据**: `source_yfinance.py` emits only type/date for earnings rows; recurring events are returned as multiple dates. Revision-1 plan leaves the fallback matcher unspecified.
- **影响**: False material alerts, misleading event-to-expiry statements, and failure of the “stable event identity/date change” success metric.
- **建议改法和验证点**: Lock matching rules: semantic occurrence anchors match directly; without an anchor, date-change pairing is allowed only when each side has exactly one non-conflicting next occurrence for the series and the previous date has not elapsed as of the current market date. Otherwise classify as an ambiguous evidence transition, never as date change/removal. Add tests for a genuine future date correction, multiple-date conflict, and post-event quarterly rollover.
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

## Special Review Lenses

- **Architecture boundary**: PR-01 blocks a silent public diagnostic contract break.
- **Best practice**: Evidence completeness is correctly placed at acquisition; the plan must preserve existing facade return shapes.
- **Optimal solution**: A narrow evidence fetch API is safer and smaller than changing all list-returning callers.
- **Overengineering**: No new store/state machine/config is justified or proposed.
- **Overcoupling**: Slices remain separable once direct fetch APIs are decoupled from evidence acquisition.

## Conclusion

**fail** — two high-severity, actionable plan defects must be fixed before implementation.
