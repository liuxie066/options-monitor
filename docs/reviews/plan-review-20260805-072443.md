# Plan Review

## Reviewed target and scope

- **Target**: `docs/reviews/plan-review-20260805-065205.md:123-128` 的 Minimal corrected plan，以及当前会话补充的“通用机制 + cash flow 首个回归用例”边界
- **Review mode**: adversarial implementation-plan review
- **Scope**: generic capability contract、collector eligibility、permanent/transient/no-progress classification、semantic evidence identity、attempt backoff、generation/concurrency/crash recovery、恢复验收
- **Excluded**: 代码实现、生产服务启动、历史 evidence 清理、发布、部署和真实 provider 写操作

## Goal and boundary understood

计划要解决的不是所有高 CPU，而是这一类可重复故障链：一个周期性 reconciliation 因 capability 缺失或长期无进展而持续运行；attempt timestamp 等易变元数据让等价结果获得新 identity；canonical evidence、revision 和 read-model 成本因此无界增长。

`cash_flow_query unavailable` 应只是第一个确定性 fixture。计划声称的通用性必须来自 collector contract、typed outcome、semantic admission 和 bounded retry，而不是来自一个 Futu 方法名特判。与此同时，这仍应是恢复 trade intake 的最小 work unit，不应演变为仓库级通用任务平台。

## Assumptions tested

1. source-level capability gate 可以在任何 case read 前安全跳过 due reconciliation，且不会阻断不需要该 capability 的本地 reconciliation 分支。
2. provider method 存在/不存在足以区分永久 blocked、账户权限问题和瞬时 provider 故障。
3. runtime status/checkpoint 可以同时承担 backoff 与 canonical business evidence admission authority。
4. “排除时间戳和其他易变字段”的 semantic fingerprint 足够明确，不会吞掉 query scope、coverage 或新 settlement facts。
5. case generation 改变、进程崩溃、服务重启或两个 worker 竞争时，no-progress guard 仍不会漏写或重复写。
6. 现有旧 evidence 可以不迁移，只要 gate 位于膨胀 read path 之前。
7. cash-flow fixture 能证明 generic contract，而不是只证明单个 hardcoded branch。

## Special review lenses

### Architecture boundary review

collector 声明 required capability；gateway 提供 typed capability/result；scheduler 只决定 eligibility/backoff；canonical ledger writer 决定 business evidence 是否首次 admitted。当前计划方向上区分了 attempt 和 business state，但仍把 source gate、checkpoint 和 writer admission 的具体 ownership 留空，导致 implementation agent 必须重新设计最关键边界。

### Best-practice review

永久 park 需要确定性错误分类；未知错误必须保守地视为 retryable。业务幂等必须由 canonical storage transaction 强制，不能只靠进程内状态或 JSON checkpoint。semantic fingerprint 必须是版本化、字段级定义的 projection，而不是“忽略一些 volatile fields”的约定。

### Optimal-solution review

无需建设通用 job platform，但也不能省略一个小而明确的 collector-attempt state owner 和 canonical semantic-idempotency owner。最实际的方案是 collector-local typed contract + bounded eligibility record + ledger writer semantic admission；cash flow 仅作为 fixture。

### Overengineering review

把所有 provider、所有任务和所有重试统一为公共 framework 会过度设计。当前 work unit 只需为 lifecycle settlement observation 定义窄 contract，并让以后同类 collector 可以复用这一形状。无需同时拆 systemd 服务、建设通用 DSL 或迁移所有历史 evidence。

### Overcoupling review

一个 source-wide capability gate 会把 optional settlement-observation branch 与整个 due lifecycle owner 绑定；一个 source 的 cash-flow capability 缺失可能阻断不需要 provider observation 的 case。runtime checkpoint 若同时拥有业务 admission，又会把 source-local control state 与 canonical ledger truth 绑定。

## Findings

### PR-01-未修复-高-source-wide capability gate 会阻断不需要 cash-flow capability 的 due lifecycle 分支

- **位置**: Minimal corrected plan 第 1 步；前一评审第 63-66、105-106 行
- **问题类型**: 过度耦合 / 架构边界 / 状态机漏洞
- **当前写法**: required capability 不满足时，在任何 account/case read 前跳过“整个 account due reconciliation”，以避开已膨胀的 read-model 热路径。
- **反例/失败场景**: 同一 account 中既有 pairing-present、需要 broker settlement observation 的 case，也有 pairing unavailable、到 deadline 后可由本地 lifecycle facts推进到 review 的 case。cash-flow capability 缺失后，source-wide gate 把两类 case 全部跳过，后者即使完全不需要 cash flow 也不再推进。
- **为什么有问题**: cash flow 是 settlement-observation collector 的 requirement，不是整个 due lifecycle owner 的 requirement。用 source gate 解决 read amplification，会把一个 optional provider branch 的故障域扩大到全部 lifecycle aging。
- **直接证据**:
  - `docs/reviews/plan-review-20260805-065205.md:125` 要求 source preflight 在 account/case read 前整体短路。
  - `src/application/trades/close_reason_reconciliation.py:683-720` 对没有 effective pairing 的 due case 走 `_reconcile_deadline_without_effective_pairing()`，不调用 observation collector。
  - `src/application/trades/close_reason_reconciliation.py:727-769` 只有 pairing-present 且 settlement observation required 的分支才调用 collector。
  - `src/application/trades/close_reason_evidence.py:233-240` 把 cash flow 表达为 settlement observation 的 required source，而非 lifecycle 全局 capability。
- **影响**: 修复 CPU 的同时会静默冻结无关 case，形成新的 lifecycle 延迟和人工 review 缺口；“通用 capability gate”实际上成为过宽的 source kill switch。
- **建议改法和验证点**:
  - kill switch 和 capability key 必须命名并限定为 `settlement_observation` collector，不得关闭整个 due lifecycle owner。
  - 把 due work 先分为 local-only 与 provider-observation 两类；local-only 分支继续执行，provider 分支才读取 capability/attempt eligibility。
  - 为避免重入旧全量 evidence 热路径，增加一个小而有界的 provider-due eligibility projection/query，所需字段只包含 case id、account、status/timing、generation/eligibility token；不要先构建 account lifecycle bundle。
  - 测试一个 account 同时包含 local-only 和 provider-required cases：capability blocked 时前者正常推进，后者只产生 typed blocked runtime result，provider calls/evidence writes 均为 0。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR-02-未修复-高-capability 与错误分类未定义，无法安全决定 permanent park

- **位置**: Minimal corrected plan 第 1-2 步；前一评审第 84-87、113-114 行；当前“required_capabilities”补充
- **问题类型**: 契约缺失 / 状态机漏洞 / 不可直接实施
- **当前写法**: collector 声明 required capabilities；缺失时 blocked；永久错误 park，generation/capability fingerprint 变化或 operator resume 后重试。
- **反例/失败场景**: SDK 上存在 `cash_flow_query`，但特定账户返回 permission denied；或 provider timeout/rate limit 被包装成普通 `RuntimeError`；或一次 gateway receipt shape 不合法。若 implementation agent 按“重复失败即永久”park，瞬时故障会永久冻结；若全部 retry，又重现当前热循环。
- **为什么有问题**: method presence 只能证明静态 API surface，不能证明账户权限、市场支持和运行时健康。计划没有定义谁把 provider result 分类为 static unsupported、account blocked、retryable、unknown 或 semantic no-progress，也没有定义 unknown 的安全默认值。
- **直接证据**:
  - `src/infrastructure/futu_gateway.py:214-222` 只通过 `hasattr` 检测 method 是否存在；这是当前 cash-flow fixture 的确定性证据，但不是通用运行时 capability contract。
  - `src/application/trades/settlement_observation.py:544-576` 把所有 query exception 压入 `retcode=error/status=incomplete` 和字符串 error，丢失 permanent/transient taxonomy。
  - `src/infrastructure/futu_gateway.py:589-632` 另一层已有 transient、rate-limit、auth/2FA 分类，但最终可包装成普通 `RuntimeError`；settlement receipt 当前未保留该 typed class。
  - `tests/test_settlement_observation.py:869-963` 只区分 case-local `SettlementObservationDataError` 和向外传播的 unclassified provider error，没有 park/retry classification contract。
- **影响**: 所谓通用方案会在“永不重试”和“无限重试”之间由实现者临场猜测；错误分类一旦错，可能长期漏处理或重新形成资源风暴。
- **建议改法和验证点**:
  - 定义窄的 `SettlementCollectorEligibility/Outcome` contract：至少 `supported`、`blocked_static`、`blocked_account_explicit`、`retryable`、`unknown`、`no_progress`。
  - 只有 method/API-version 明确缺失或 provider 明确返回不可恢复的 account capability code 才能 park；`unknown` 默认 bounded retry，不得升级为 permanent。
  - outcome 必须携带 `source_id`、account、collector contract version、capability fingerprint、typed reason code 和 retry eligibility；raw error text 仅用于诊断，不参与决策。
  - 用 fixtures 覆盖 method absent、permission denied explicit code、auth expired、rate limit、timeout、malformed receipt、empty complete、incomplete unchanged 和恢复后的 capability change。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR-03-未修复-严重-runtime checkpoint 不能承担 canonical evidence 去重；当前 sequencing 存在崩溃漏写或重复写窗口

- **位置**: 前一评审第 85-88、113 行；Minimal corrected plan 第 2 步
- **问题类型**: 并发恢复风险 / 数据一致性 / 架构边界 / open question 未收敛
- **当前写法**: 相同 generation + semantic fingerprint 时不写 evidence；attempt/backoff 可以复用 source checkpoint/status；admission guard 位于 canonical writer 之前。持久化 owner 仍留作 open question。
- **反例/失败场景**:
  1. collector 得到一个新的 semantic result，先更新 checkpoint 为“已见/park”，随后进程在 canonical writer 前崩溃；重启后 checkpoint 抑制该结果，业务 evidence 永远漏写。
  2. 先写 canonical evidence，进程在更新 checkpoint 前崩溃；重启后再次执行。因为现有 `observation_id` 含新时间戳，第二次获得新 evidence id，再次写入并推进 revision。
  3. 两个 worker 同时读取旧 checkpoint、得到相同 semantic result，均进入 writer；source-local JSON 或内存状态无法提供 canonical uniqueness。
- **为什么有问题**: attempt throttling 与 business admission 是两个 ownership。checkpoint 可以减少调用次数，但只有 ledger transaction 能证明某个 case generation 的 semantic evidence 已被首次接纳。把业务 no-write 决策放在 writer 外部违反了现有 generation CAS/transaction authority。
- **直接证据**:
  - `docs/reviews/plan-review-20260805-065205.md:86-87,113` 同时提出 source checkpoint/status 和 writer 前 admission，并把 owner 留作 open question。
  - `src/application/trades/close_reason_evidence.py:268-326` 当前 identity 对完整 payload hash，attempt time 变化即生成新 observation id。
  - `src/application/ledger/repository.py:416-446` canonical uniqueness 只有 `evidence_id`、source event tuple 和 `(case_id,evidence_id)`，没有 semantic fingerprint/generation 唯一键。
  - `src/application/ledger/writer.py:113-144,2065-2113` generation CAS 与 evidence insert 已在 ledger transaction 内；这是应复用的 canonical authority。
  - `src/application/trades/inbox.py:337-375` source-local SQLite 已展示 bounded retry state 可有独立 control storage，但它不是 lifecycle business truth。
- **影响**: 崩溃或并发时可能漏掉真正的新 settlement evidence，或继续制造重复 evidence/revision/outbox；这正是本计划声称要消除的核心故障模式。
- **建议改法和验证点**:
  - 明确 ledger writer 是 semantic admission authority。canonical key 至少绑定 `case_id + lifecycle_generation_token + evidence_type + semantic_schema_version + semantic_fingerprint`。
  - 可以用 deterministic evidence/source-event id 复用现有唯一索引，或增加明确的 semantic 唯一约束；无论哪种方式，都必须在 generation CAS 同一 transaction 内 first-write-wins。
  - attempt receipt/backoff 放在独立、有界 control store，只负责 eligibility；checkpoint 丢失最多导致一次额外调用，不能导致业务重复或漏写。
  - 明确 crash ordering：canonical writer 成功后再更新 attempt state；若其间崩溃，重试由 writer semantic idempotency 安全吸收。
  - 增加 crash-point 和双 worker 测试：checkpoint-before-write 禁止成为合法 sequencing；writer-after-crash 重试不新增 evidence/revision/outbox；generation 改变后旧 attempt state 不得抑制新 evidence。
- **修复风险（低/中/高）**: 高
- **严重程度（低/中/高/严重）**: 严重

### PR-04-未修复-高-semantic fingerprint 没有字段级契约，可能把真正的新 coverage/facts 当成重复

- **位置**: 前一评审第 84-88 行；Minimal corrected plan 第 2 步
- **问题类型**: 契约缺失 / 数据损坏 / 测试缺口
- **当前写法**: fingerprint 排除 `observed_at_ms`、attempt receipt timestamps 和“其他易变传输字段”；相同语义 incomplete result 不写业务 evidence。
- **反例/失败场景**: 第二次 attempt 的查询窗口延伸到新的 clearing day，或 source 从 stale/incomplete 变为 fresh/complete，或 provider rows/coverage/error class 改变。如果实现者把 query window、freshness 或 receipt status 也视为 volatile，新的 settlement proof 会与旧 incomplete attempt 碰撞并被抑制。反之，如果保留 raw error text/request metadata，相同失败仍会不断产生新 fingerprint。
- **为什么有问题**: `observed_at_ms` 不只是 transport decoration：当前 complete observation 用它证明观测发生在 deadline 之后，并将其作为 terminal evidence event time。计划没有区分 attempt identity、semantic no-progress identity 和最终 canonical evidence payload，也没有给 implementation agent 可执行的投影 schema。
- **直接证据**:
  - `src/application/trades/close_reason_evidence.py:153-193` source receipt 同时包含 query input、coverage、pagination、stale/fallback、rows hash、observed time 和 error。
  - `src/application/trades/close_reason_evidence.py:224-246` completeness 明确依赖 receipt status/observed time 和 settlement deadline。
  - `src/application/trades/settlement_observation.py:211-249,500-518` clearing-date/query window、source receipts 和 business booleans 会随新事实变化。
  - `src/application/trades/close_reason_reconciliation.py:397-420` complete observation 的 observed time、observation hash 和完整 payload进入 terminal evidence。
- **影响**: 过宽 projection 会漏接新 settlement 事实；过窄 projection 会继续数据膨胀。两者都无法通过只测试“不同 timestamp、相同 payload”发现。
- **建议改法和验证点**:
  - 定义版本化的 `settlement_observation_semantic.v1` projection，而不是通用“删除 volatile fields”函数。
  - projection 至少纳入 case/generation、contract/target manifest、query scope、required-source typed statuses、coverage/pagination/freshness、canonical rows/payload hashes、calendar hash、business booleans、complete flag 和 normalized reason/error class；排除 attempt wall clock、raw error text、request id 和 transport timing。
  - 首次 admitted evidence 保留其真实 observed time；后续相同 semantic key 为 no-op。incomplete→complete、query scope 扩展、rows/coverage/freshness/error class 或 generation 变化必须产生新 key。
  - 测试矩阵覆盖：仅时间变化、row order 变化、raw error 文本变化、query window 扩展、stale→fresh、incomplete→complete、empty→row、generation change 和 deadline 前→后。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

## Open Questions

- provider-due eligibility 的最小 bounded projection 应落在 canonical ledger 的独立查询/表，还是 source-local control DB 中的可重建索引？无论选择哪种，必须证明 local-only lifecycle 分支不被 capability gate 阻断，且索引丢失时 fail-safe。
- current systemd topology 是否保证单个 account 只有一个 due worker？即使当前保证，canonical semantic idempotency 仍应承受人工命令、重启重叠或未来拆服务造成的第二 writer。
- 首个 hotfix 是否允许一个窄 schema/index 变更？若不允许，必须给出基于 deterministic evidence/source-event id 的等价原子方案，不能退回 JSON checkpoint 去重。

## Residual risks and suggested tracking

- 历史约 30 MB settlement evidence 不在本 work unit 内清理；完成入口 gate 后，偶发 case read 仍可能慢。建议单独跟踪 bounded lifecycle reader/data compaction，并在 admission 修复上线前禁止 destructive migration。
- provider capability contract 只覆盖 lifecycle settlement collector 的同类故障，不应宣传为所有周期任务或所有高 CPU 的平台级解决方案。
- 一个 service 内共享 `process_lock` 仍会放大 collector latency；完成 typed eligibility 后，可把服务隔离作为独立 hardening work unit。
- 生产 service 继续保持停止，直到修订计划通过、实现验证完成并获得受控恢复授权；本次 PlanReview 未启动服务或修改业务数据。

## Final conclusion

**fail**

当前方案已经超越 cash-flow 单点特判，但还不能安全称为“同类型问题的通用最小方案”。source-wide gate 会误伤不需要 cash flow 的 lifecycle 分支；permanent/transient taxonomy 未定义；runtime checkpoint 与 canonical writer 之间存在崩溃一致性漏洞；semantic projection 也未达到 code-generation-ready。修复以上四项后，方案才会成为窄而通用的 settlement-collector resilience contract，而不是另一个隐性 cash-flow 补丁。
