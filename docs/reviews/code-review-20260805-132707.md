## Findings

### DR14-01-未修复-高-首个 case claim 既不是批次互斥锁也未覆盖共享快照构建

- **入口/函数**: `reconcile_due_lifecycle_cases_for_source()` -> provider eligibility -> initial claim -> `lifecycle_case_read_models_for_account()`
- **文件(行号)**: `src/application/trades/lifecycle_runtime.py:945-1007,1149-1200`; `src/application/trades/inbox.py:492-541`; `docs/plans/trade-intake-settlement-collector-resilience-plan-20260805.md:76-82,379-382`
- **输入场景**: 同一 source/account 有至少两个可调用 provider 的 case，两个进程或重叠 worker 同时执行 tick；或者账户历史读取/索引构建超过 120 秒 claim lease。
- **实际分支**: worker A claim 第一个 case 后进入账户级共享快照构建。worker B 如果看到第一个 case 已被 claim，或抢占失败，会在 `while` 中 `pop(0)` 并继续 claim 第二个 case；成功后也进入同一个账户级快照构建。因此每个 worker 都会解析同一份账户历史。与此同时，初始 claim 与真正进入逐 case provider 分支之间没有 `_SettlementClaimLeaseGuard`；lease guard 直到共享快照、compact candidate refresh 和 validation 全部完成后才启动。慢读超过 lease 时，首 claim 可以在仍然工作的 owner 手中自然过期。
- **预期行为**: “首个 attempt claim”应当作为该 source/account 本轮 provider 批次的确定性 leader election；未取得 leader 的 worker 本 tick 不得进入账户级全量读取。取得 leader 后，claim 必须在共享快照构建和逐 case handoff 期间持续续租，确保一个 provider generation 只构建一次账户历史索引。
- **实际行为**: 有 N 个 eligible case 时，重叠 worker 最多可分别 claim 不同 case 并并发构建 N 份相同账户快照；慢历史读取还可能让 leader claim 在构建中失效。per-case provider claim 仍能抑制大部分重复 provider 调用，但无法抑制本次方案要消除的高 CPU/历史解析放大。
- **直接证据**: `lifecycle_runtime.py:948-981` 在首 claim 失败后删除该 case 并继续尝试下一 case；`lifecycle_runtime.py:983-1007` 随后无批次级互斥地执行账户级 read-model、compact refresh 和 validation；第一个 lease guard 仅在 `lifecycle_runtime.py:1183-1200` 创建。claim SQL 只按 `(source_id, account, case_id)` 互斥（`inbox.py:515-525`），没有 account/batch 互斥语义。计划明确要求“acquire the first attempt claim, read one coherent account snapshot”且资源回归要求 provider path 只构建一次 full account-history index。
- **影响**: 在多 worker、重启重叠或慢历史场景中，CPU 和 SQLite/ledger 读取会按 eligible case/worker 数放大，能够重新触发 `trade-intake` 高 CPU 与飞书响应受拖累的问题；这违反本 work unit 的核心资源上界，而不只是 cash-flow 特例。
- **建议改法和验证点**: 将排序后的首个 eligible case 固定为 batch leader；claim 失败时本 tick 跳过整个 provider batch，不再 fall through 到下一 case。claim 成功后立即启动 lease guard，覆盖账户快照、candidate refresh、validation，并在转入逐 case claim 前显式 renew/stop；start、renew、ownership-loss 和 control-store error 均沿现有 typed fail-closed 路径收口。新增确定性并发回归：两个 worker/两个 case 只能有一个账户级 read；loser 不 claim 第二 case；准备阶段推进 monotonic/control clock 越过 120 秒后竞争者仍不能取得 leader；准备阶段 ownership loss 时不得调用 provider 或写 canonical state。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高
