### DR-S3-01-未修复-高-非法账户标签在 S3 校验前后仍可逃逸 run/account 根目录并写状态

- **入口/函数**: `./om run tick --accounts ...` / runtime `accounts` -> `normalize_accounts()` -> `prepare_tick_run_workspace()` -> `run_tick_account_execution()` -> `_account_config_failure_outcome()`

- **实际分支**: `normalize_accounts()` 原样保留这些标签；`prepare_tick_run_workspace()` 在 S3 的 `_identity_component()` 生效前，先用 `accounts_root / default_account` 创建目录。随后 publisher 虽返回 `ACCOUNT_CONFIG_IDENTITY_INVALID`，新加入的 `_account_config_failure_outcome()` 又把同一标签交给会 `.resolve()`、但不校验 containment 的 `write_account_run_state()`。

- **实际行为**: 调用最终可显示为 typed config failure，但此前或失败处理期间已经在目标 account/run 根之外创建目录或写入 `account_metrics.json`。

### DR-S3-02-未修复-高-`account_config_sha256` 未到达最终 pipeline reader，校验后换包会形成 split-brain

- **入口/函数**: `run_one_account()` -> `run_pipeline_script()` -> `scan-pipeline` -> `pipeline_runtime.main()` -> `load_config()`
- **文件(行号)**: `src/application/account_run.py:254-290,500-519,797-822,998-1007`; `src/infrastructure/external_services.py:80-145`; `src/application/pipeline_runtime.py:47-78,101-168`; `src/application/config_loader.py:121-142`; `tests/test_account_run.py:327-381`
- **输入场景**: `state/config.override.json` 在 `run_one_account()` 入口完成双制品/parent bytes/SHA 校验后、scan-pipeline 子进程实际读取前，被迟到写入或并发进程替换成另一份合法 JSON，例如把 `portfolio.account` 从 `lx` 改为 `sy`。
- **实际分支**: AccountRun 只在入口校验一次，随后仅把可写 `state_path` 交给 subprocess；subprocess API、CLI parser 和 config loader 均没有 expected SHA 或 compatibility path。`pipeline_runtime.main()` 甚至先创建 report/state 目录，再由 `load_config()` 重新 `read_text()`。父进程后续 Close Advice 继续使用入口时已加载的旧 `cfg`，metrics 仍记录旧 authority SHA。
- **预期行为**: pipeline 实际解析的 bytes 必须与 parent-retained canonical bytes、compatibility artifact 和 `account_config_sha256` 同时一致；失败必须发生在创建业务输出、provider access、pipeline 和 Close Advice 之前。
- **实际行为**: pipeline 可按新配置完成并写当前账户 report/state，Close Advice 又按旧配置运行；整个账户 outcome 仍可返回 `ran_pipeline=True`，审计 SHA 与真实消费字节不一致。
- **直接证据**: `run_pipeline_script()` 的唯一配置 authority 是 `config: Path`；`pipeline_runtime` 没有 hash 参数；`config_loader.py:137` 直接重开文件。现有测试只断言 mocked subprocess 调用时文件尚相等，没有覆盖 parent validation 与 child read 之间的窗口。确定性临时复现把 state config 在 fake child boundary 改为 `sy`，得到 `pipeline_consumed_account=sy`、`pipeline_received_expected_sha=False`、`account_outcome_ran_pipeline=True`。
- **影响**: prepared portfolio、candidate pipeline、Close Advice、报告与通知可基于不同账户或策略事实，且审计仍宣称消费了原 SHA；这直接破坏 S3 的核心完成信号。
- **建议改法和验证点**: 把 run/account、state path、compatibility path 和 expected SHA 作为 internal scan-pipeline authority 传到底层；在任何 report/state 创建或业务访问前一次读取、校验并从同一批 bytes 解析，禁止“先验 hash、再重开路径”。在 `tests/test_pipeline_runtime_paths.py` 增加校验后换包、账户不匹配和 compatibility drift，断言 typed failure 且 pipeline/Close Advice/provider/output 零副作用。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### DR-S3-03-未修复-高-一个账户的配置漂移会降级全部 prepared context，随后仍执行规划和行情预取

- **入口/函数**: `run_tick_account_execution()` -> `prepare_portfolio_contexts()` -> `build_cross_account_prefetch_config()` -> `_build_close_advice_barrier_plan()` -> `prefetch_required_data()`
- **文件(行号)**: `src/application/tick_account_execution.py:308-356,357-434,489-510,565-624,670-683`; `src/application/prepared_portfolio_context.py:78-87`; `src/application/required_data_prefetch_planning.py:70-124`; `src/application/prefilters.py:22-43`; `tests/test_tick_account_execution_barrier.py:758-813`
- **输入场景**: `lx`、`sy` 均需扫描；其中 `lx` 的 config artifact 在父进程首次发布/校验后、prepared barrier 二次校验前发生 bytes/hash 漂移，`sy` authority 仍合法。
- **实际分支**: prepared owner 在启动任何 worker 前用一个 all-or-none 循环校验所有账户；`lx` 抛出的 `AccountRunConfigError` 让整个函数退出。调用方用宽泛 `except Exception` 把全部 scanning accounts 写成普通 `portfolio_context_preparation_failed`，没有把 typed error写回 `account_config_errors`，然后无条件继续构造 union、Close Advice required-data plan 和 provider prefetch。健康的 `sy` 也失去 prepared context，`apply_prefilters()` 会据此关闭 Sell Call；若后续 prefetch 再失败，terminal barrier 还会用 required-data reason 遮蔽原 config failure。
- **预期行为**: config authority 失败应是该账户的吸收态，在其 prepared/plan/prefetch/pipeline/Close Advice 前形成 typed failure；健康账户应继续使用自己的 prepared context，除非明确采用停止全部后续 I/O 的全局 barrier。
- **实际行为**: 坏账户把健康账户的 prepared 事实一并降级，同时 authority 已失效的账户仍参与 Close Advice planning 和外部行情预取。

- **建议改法和验证点**: 进入 prepared barrier 前逐账户重验并把 typed failure 固化到对应账户，随后从 scanning/prepared/union/plan/prefetch scope 中移除该账户；或让 prepared API 返回逐账户 config failure，而不是抛出全局异常。新增双账户测试：篡改 `lx`、保持 `sy` 正常，断言 `lx` 零 worker/plan/prefetch/pipeline/Close Advice，`sy` worker 与 Sell Call union 正常，且 downstream failure 不得覆盖 config reason。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### DR-S3-04-未修复-高-祖先目录 symlink 可绕过 run/account 路径校验并把双制品重定向到其他 run 或外部目录

- **入口/函数**: `publish_account_run_config()`、`load_published_account_run_config()`、`_write_once_or_adopt()`、`_read_regular_file()`
- **文件(行号)**: `src/application/tick_run_workspace.py:70-84,185-196,248-321,331-338`
- **输入场景**: `output_runs/<run>/accounts/lx` 或其 `state` 目录预先是指向另一 run/account 或 runtime root 外部目录的 symlink。
- **实际分支**: expected/actual path 比较只使用 lexical `abspath`，不解析祖先 symlink；`mkdir`、`os.open`、`os.link` 和 `read_bytes()` 都会跟随祖先链接。`follow_symlinks=False` 只作用于 link 操作本身，`_read_regular_file()` 也只拒绝最终 leaf 是 symlink。
- **预期行为**: 两个 config artifact 的真实物理位置必须位于可信的 `<resolved-base>/output_runs/<run>/accounts/<account>` 内；任何祖先链接或 containment 变化都应在写入/读取前 typed fail closed。
- **实际行为**: 返回的 authority 保持看似正确的 lexical run/account 路径，但真实写入和读取发生在其他 run/account 或 base 外，并且 load 校验成功。
- **直接证据**: `account_run_config_paths()` 只 resolve `base` 后再拼接；第 190-196 行用 `_absolute_without_symlink_resolution()` 做相等比较；第 257-288 行沿父目录创建和 hard-link；第 316-321 行只检查 leaf。确定性临时复现中，`run-a/accounts/lx` 指向外部账户目录后，authority 的 `state_path.resolve()` 已位于外部目录，`load_account_run_config()` 仍接受该配置。
- **影响**: S3 的跨 run/账户物理隔离在损坏、遗留或人为构造的运行目录下失效，可造成配置污染、信息暴露、永久 conflict 和报告错位。
- **建议改法和验证点**: 将 resolved `output_runs` 作为可信 dir-fd/root，拒绝其下 run/accounts/account/state 任一祖先为 symlink，并验证 resolved containment；写读使用 dir-fd + `O_NOFOLLOW`/`fstat` 或等价机制关闭检查后替换竞态。增加 account-dir、state-dir、compatibility-parent symlink 测试，断言外部目标零写入且两个 artifact 均不存在。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### DR-S3-05-未修复-中-Prepared manifest 记录了 config SHA，但所有消费者都忽略该绑定

- **入口/函数**: `prepare_portfolio_contexts()` -> `load_prepared_portfolio_context()` -> cross-account prefetch / `build_pipeline_context()`
- **文件(行号)**: `src/application/prepared_portfolio_context.py:203-218,256-309,449-497`; `src/application/tick_account_execution.py:357-392`; `src/application/pipeline_context.py:383-428`; `tests/test_tick_account_execution_barrier.py:82-112`; `tests/test_prepared_portfolio_context.py:205-245`
- **输入场景**: ready prepared manifest 的 `account_config_sha256` 缺失，或与当前 `AccountRunConfigAuthority` 不同，但 manifest 的 run/account/path 和 portfolio payload hash 都合法。
