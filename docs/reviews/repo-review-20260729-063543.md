## Findings

### 1-已修复-高-`schedule.enabled=false` 在显式 US/HK tick 中仍会扫描并允许通知

- **入口/函数**: `tick-cron --market us|hk` → `select_markets_to_run()` → scheduler `decide()`
- **文件（行号）**: `domain/domain/multi_tick.py:168-217`; `src/application/scan_scheduler.py:91-121,478-529,645-668`; `src/application/multi_tick_scheduler.py:232-298`
- **输入场景**: runtime config 明确设置 `schedule.enabled=false`，正式 timer 仍以 `--market-config us` 或 `hk` 调用，当前时间落在 report target。
- **实际分支**: 显式市场直接返回 `US/HK`；`decide()` 不读取 `enabled`，仍生成 `should_run_scan=true`、`is_notify_window_open=true`。scheduler CLI 只打印 disabled 提示，没有改变已经生成的 decision。
- **预期行为**: schedule 关闭应在 decision owner 生成 terminal disabled decision，global/per-account/CLI 都不得扫描或普通通知。
- **直接证据**: 以 2026-07-27 09:40 ET 复现，返回 `markets=['US']`、`should_run_scan=true`、`should_notify=true`。
- **影响**: 运维关闭配置后仍可能访问上游、扫描并发送通知，配置安全开关静默失效。
- **建议改法和验证点**: 在 scheduler decision owner 统一处理 `enabled=false`；增加 explicit US/HK + disabled 的端到端测试，断言零 pipeline、零 provider attempt。
- **修复风险**: 中
- **严重程度**: 高

### 2-已修复-高-`tick-cron --symbols` 会消费正式调度点并抑制后续完整扫描和通知

- **入口/函数**: `build_tick_cron_plan()` → `multi_account_tick` → `_commit_scan_targets_before_delivery()`
- **文件（行号）**: `src/application/tick_cron.py:83-139`; `src/application/tick_notification_flow.py:97-117,593-613,807-832`; `src/application/multi_account_tick.py:313-347,423-432`; `src/application/tick_run_context.py:28-52`; `src/application/scan_scheduler.py:505-570`
- **输入场景**: 操作者用 `tick-cron --symbols NVDA` 做局部诊断。
- **实际分支**:
  - `--symbols` 自动附加 `--no-send`，但 trigger 仍是 `cron/scheduled`；
  - 局部扫描完成后仍提交 exact scheduled target；
  - `no_send` 不创建可投递 Brief envelope；
  - 下一次完整 cron 看到 target 已处理而跳过；
  - 同分钟 idempotency key 又未包含 symbols/no-send/job scope，完整 tick 还可能直接被判 duplicate。
- **预期行为**: symbol-scoped/no-send 诊断不得推进正式 scheduler waterline，也不得与完整 scheduled work 共享 idempotency identity。
- **影响**: 一个局部诊断可吞掉整批 watchlist scan 和正式 Daily Brief。
- **建议改法和验证点**: 将 symbol-scoped cron 明确标为 non-committing diagnostic/manual；idempotency key 纳入 effective work scope；测试 partial no-send → full scheduled 同 target。
- **修复风险**: 中
- **严重程度**: 高

### 3-已修复-高-scheduler subprocess 失败返回成功退出码并遗留 `in_progress` idempotency

- **入口/函数**: `run_scheduler_flow()` → `build_tick_scheduler_context()` → `multi_account_tick.main()` → tick-cron
- **文件（行号）**: `src/application/multi_tick_scheduler.py:179-219`; `src/application/tick_scheduler_context.py:124-159`; `src/application/multi_account_tick.py:313-348,400-403`; `src/application/tick_cron.py:280-299`
- **输入场景**: scheduler subprocess 非零退出或解析 authority 失败。
- **实际分支**: scheduler flow 抛 `RuntimeError`；context builder 写 `run_end:error`，却返回 `TickSchedulerOutcome(False, 0, ...)`。顶层原样返回 0，并且没有终结此前 claim 的 tick idempotency。
- **预期行为**: scheduler authority 不可用应非零退出，并把 idempotency 写为 stable terminal failure。
- **影响**: systemd/timer 显示成功；同分钟重试又被残留 `in_progress` 当 duplicate 成功跳过。
- **建议改法和验证点**: 返回稳定非零码；失败返回前写 `status=failed/ok=false/error_code=SCHEDULER_FAILED`；测试 process rc、run_end、guard、idempotency 四层一致。
- **修复风险**: 低
- **严重程度**: 高

### 4-已修复-高-per-account scheduler 异常会 fail-open 到 global 决策

- **入口/函数**: `run_scheduler_flow()` account decision → `run_one_account()` → `decide_should_notify()`
- **文件（行号）**: `src/application/scan_scheduler.py:453-475`; `src/application/multi_tick_scheduler.py:239-317`; `domain/domain/multi_tick.py:275-312`; `src/application/account_run.py:328-359`

### 5-已修复-高-watchdog 外层异常 fail-open，并同时记录 error 与 ok

- **入口/函数**: `run_multi_tick_watchdog()` → `run_tick_guard_flow()`
- **文件（行号）**: `src/application/multi_tick_watchdog.py:43-66,242-254`; `src/application/tick_guard_flow.py:147-173`
- **输入场景**: watchlist resolution、port coercion 或 watchdog 数值配置转换抛异常。
- **实际分支**: outer `except` 只记录 `WATCHDOG_EXCEPTION`；随后继续写 `watchdog/ok`，返回 `should_continue=true, rc=0`。
- **预期行为**: watchdog 自身无法执行时应停止 pipeline，且只能产生一个一致 terminal state。
- **直接证据**: 注入 `resolve_watchlist_config()` 异常后得到 `should_continue=True`，events 为 `start → error → ok`。
- **影响**: 系统在没有证明 OpenD 健康的情况下继续生成决策；运行证据彼此矛盾。
- **建议改法和验证点**: outer exception 返回 fail-closed outcome；不要写 ok；在 config validation 层验证 watchdog 数值。测试异常时 scheduler 不被调用。
- **修复风险**: 低至中
- **严重程度**: 高

### 6-已修复-高-单个账户非预期异常会中断整个多账户收敛且不写全局终态

- **入口/函数**: `run_tick_account_execution()` → `run_account_outcomes()` → `multi_account_tick.main()`
- **文件（行号）**: `src/application/tick_account_execution.py:81-100,149-172`; `src/application/account_run.py:256-275,484-503`; `src/application/multi_account_tick.py:313-348,486-586`
- **输入场景**: 一个账户在 config override、output dir 或 pipeline subprocess invocation 处抛 OSError；其他账户已经完成。
- **实际分支**: sequential path 直接抛；parallel path 对 `future.result()` 无隔离。整个 account execution 冒泡，跳过 notification/finalizer/idempotency terminalization。
- **预期行为**: exception 应转换为账户级失败 outcome，继续收齐其他账户，并由全局 finally 写一致终态。
- **影响**: 成功账户结果和可投递消息丢失；run 留下 partial artifacts 与 `in_progress` identity。
- **建议改法和验证点**: per-account exception isolation + top-level terminalizer；测试一账户 OSError、另一账户成功，确认结果、通知、run_end 与 idempotency 都收敛。
- **修复风险**: 中
- **严重程度**: 高

### 7-已修复-高-tick-cron timeout 只终止直接进程，可能留下继续写状态的 orphan pipeline

- **入口/函数**: `run_tick_cron()` → `subprocess.run(timeout=...)` → tick → scan-pipeline
- **文件（行号）**: `src/application/tick_cron.py:257-294`; `src/infrastructure/external_services.py:19-35,38-77,80-145`
- **输入场景**: scan-pipeline 或其下游挂起超过 outer timeout。
- **实际分支**: outer subprocess 未建立独立 process session/group；timeout 只 kill/wait 直接 tick。内部 scheduler/pipeline 也没有共享 deadline/process-group cleanup。finally 随即释放 cron lock。
- **预期行为**: timeout 应终止整棵工作进程树并确认退出后再释放互斥锁。
- **影响**: orphan 旧 run 可与下一次 cron 并发访问 OpenD、写 shared/account/run 状态，产生 late stale write。
- **建议改法和验证点**: 为 tick 建 process session；TERM group → grace → KILL → wait；传播 terminal timeout receipt。集成测试让孙进程延迟写 sentinel，断言 timeout 后不再存活。
- **修复风险**: 中高
- **严重程度**: 高

### 8-已修复-高-调度目标提交失败会把下一次 fixed scan 卡在旧 pending envelope

- **入口/函数**: `_prepare_daily_brief_notification()` → `_commit_scan_targets_before_delivery()` → 下一次 scheduled scan
- **文件（行号）**: `src/application/tick_notification_flow.py:112-117,593-613,807-901`; `src/application/daily_decision_brief_repository.py:82-107,393-405,1742-1762`; `tests/test_daily_decision_brief_notification_flow.py:560-572`
- **输入场景**: fixed Brief 已持久化，但发送前 scheduler state commit 瞬时失败。
- **实际分支**: 第一次留下 pending exact envelope；target 未提交，所以第二次再次扫描并生成新 revision。retry 复用逻辑只覆盖 `candidate_alert`，fixed report 会重新 prepare；repository 因 frozen pending 内容变化抛错。
- **预期行为**: 同 target 有 pending retry 时应复用原 envelope，先恢复 target commit，再按原内容/幂等键发送。
- **影响**: 一次状态写失败即可让 fixed batch 失去自动恢复能力，provider 从未被调用。
- **建议改法和验证点**: fixed report/failure 与 candidate alert 共享 exact retry 优先级；补两次 invocation 的 commit-failure recovery 测试。
- **修复风险**: 中
- **严重程度**: 高

### 9-已修复-高-人工解决 unknown receipt 后 Daily Brief delivery 状态不会收敛

- **入口/函数**: authority send unknown → Brief ambiguous → `resolve_notification_unknown()` → delivery-only
- **文件（行号）**: `src/application/position_advice_notification_authority.py:145-176,264-336,407-418,499-500`; `src/application/tick_notification_flow.py:1129-1160`; `src/application/daily_decision_brief_repository.py:475-608`
- **输入场景**: provider command 完成但 delivery 未确认；operator 将 receipt 判定为 `delivered` 或 `failed`。
- **实际分支**:
  - resolution 只写 authority 文件，不绑定/更新 Daily Brief delivery identity；

  - 两种 resolution 后都返回 `AUTHORITY_NOTIFICATION_RESOLVED`；
  - Brief 仍永久 ambiguous。

- **建议改法和验证点**: 让 receipt 绑定 delivery key/source digest/message hash；提供受锁 reconciliation，分别覆盖 delivered/failed、重复 apply 和 identity mismatch。
- **修复风险**: 中高
- **严重程度**: 高

### 12-已修复-高-Feishu 明确业务拒绝被误分类为 unknown 并冻结后续投递

- **入口/函数**: Feishu transport → `normalize_feishu_app_send_output()` → scheduled retry → authority terminal status
- **文件（行号）**: `src/infrastructure/feishu_bitable.py:258-315`; `src/application/notification_delivery_adapter.py:159-190,203-283`; `src/application/scheduled_notification.py:184-239,350-398`; `src/application/position_advice_notification_authority.py:407-418`
- **输入场景**: HTTP 200，但 Feishu 业务码非零，例如 `code=230001`。
- **实际分支**:
  - normalizer 用 `http_status==200` 定义 `command_ok=true`；
  - `provider_response_code` 没有从 `feishu_code` 填充；
  - scheduled layer 产出 `SEND_UNCONFIRMED` 且不重试；

- **预期行为**: 非零 provider code 是 definite rejection，应保留 code/classification，不能进入 ambiguous/unknown。
- **直接证据**: 最小复现得到 `command_ok=true, delivery_confirmed=false, provider_response_code=None, authority_status=unknown`。

- **建议改法和验证点**: 分离 transport success 与 provider acceptance；保留 provider code；authority 只根据显式 ambiguity 判 unknown。覆盖 code!=0、code=0 missing message_id、timeout、confirmed 四种合同。
- **修复风险**: 中
- **严重程度**: 高

### 13-已修复-高-Card transient 后 permanent fallback 会换 UUID 并把潜在重复投递确认为成功

- **入口/函数**: Feishu Card send/retry → `_card_permanent_failure_allows_fallback()` → post fallback → Daily Brief confirm
- **文件（行号）**: `src/infrastructure/feishu_bot.py:187-223`; `src/infrastructure/feishu_bitable.py:280-329`; `src/application/notification_delivery_adapter.py:121-145,193-227,256-283`; `src/application/scheduled_notification.py:366-501`; `src/application/tick_notification_flow.py:1129-1150`
- **输入场景**: Card 第一次网络超时/5xx（送达未知）；同 UUID 后续得到 permanent 4xx/business rejection；adapter 自动改用 `<key>:fallback` 发 post。
- **实际分支**: fallback gate 只看最终异常，不看此前 transient attempt。fallback 成功后 normalized result 同时为 `delivery_confirmed=true` 和 `ambiguous_send=true`，但 outer layer只看 confirmed，推进 Brief pointer；原 key 存在又让 `duplicate_risk=false`。
- **预期行为**: 任何历史 transient/unknown 都禁止换 transport UUID；`fallback_used && ambiguous_send` 不得进入 accepted/confirmed。

- **影响**: 用户可能同时收到已送达但响应丢失的 Card 和 fallback post，系统却记录为干净成功。
- **建议改法和验证点**: provider adapter 输出显式 `definitely_not_sent/safe_to_fallback`；fallback gate检查完整 attempt history；增加 transient→permanent→no fallback 的三层回归。
- **修复风险**: 中
- **严重程度**: 高

## Resolved Design Decisions

- Scheduled Feishu Daily Brief 以 Card 为主；只有 complete attempt history 证明 definite-not-sent 的 permanent rejection 才允许换 `:fallback` key 发 post。
- `send_failed_or_unconfirmed`、partial failure 和 duplicate risk 进入 runtime overall failure；no-send、scheduler skip、no-content 不误报。
- retry metrics 拆分为 provider HTTP retry、outer retry、fallback attempt，同时保留总计。
- 未完成的 pending/ambiguous Brief 不主动取消；它们阻止 authority mode/generation change，直到 exact reconciliation 或成功重试。
- repository 内现已提供 Daily Brief/authority 联合 reconciliation；operator resolution 必须绑定 exact delivery identity、证据、actor 和显式 confirm。
