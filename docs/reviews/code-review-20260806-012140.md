## Findings

### DR3-01-已修复-中-request_index 去顺序化后不再与对应 request hash 做一致性校验
- **入口/函数**: `_validate_expected_child_request_evidence()` and `_validated_option_chain_scope_evidence()`
- **文件(行号)**: `src/application/opend_symbol_outputs.py:681-722`; `src/application/required_data_coverage.py:942-976`
- **输入场景**: 两个 child 都带正确且唯一的 `planned_request_sha256`，child 列表可任意换序，但把两个 child 的 `request_index` 值互换；两个 index 仍唯一且都在合法范围内。
- **实际分支**: 两个 validator 都用 hash 正确匹配 planned request，同时只检查 index 的类型、范围和全局唯一性，没有检查“这个 hash 对应的 child 是否保留该 planned request 的原 index”。
- **预期行为**: child 列表位置不应参与语义身份；但 `request_index` 作为保留的兼容证据，必须与 hash 所指向的 planned request 一致。列表换序应通过，hash/index 互相矛盾应作为 `internal_contract_error` 拒绝。
- **实际行为**: hash/index 冲突的 payload 被接受，结构化结果还报告 `internal_integrity=valid`；持久化审计证据内部自相矛盾。
- **直接证据**: output validator 的 `expected_by_hash` 只保存 planned request，不保存原 index；coverage validator 虽保存 `(request_index, request)`，但从 `observed_by_hash` 取 child 后未比较 child 自报 index。现有 reorder 测试仅反转 child list 并保留 index，不能覆盖交换 index 的反例。
- **影响**: 当前 row/scope 仍由 hash 正确匹配，因此不会直接串行；但系统会接纳并持久化无法可靠审计的 request identity，未来任何兼容消费者读取 `request_index` 都会得到错误关联。
- **建议改法和验证点**: `expected_by_hash` 同时保存原 planned index；hash 匹配后要求 child `request_index == expected_index`，但绝不要求 child 在 list 中的位置等于 index。新增测试：反转 child list 且保留 index 继续通过；仅交换两个 index 必须以 `internal_contract_error` 失败。structured evaluator 同步验证 aggregate `request_count` 与 children/plan 数量一致。
- **修复结果**: 两个 validator 均按 hash 找到 planned request 后独立核对原 index；structured evaluator 同时核对 request_count。列表反转继续通过，index 互换以 internal_contract_error 失败，相关 210 项通过。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
