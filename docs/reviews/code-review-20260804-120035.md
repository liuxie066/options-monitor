### DR-S1-01-未修复-高-Expected contract 的多份计划表示可以互相矛盾却仍获得 complete/ready

- **入口/函数**: `build_required_data_expected_fetch_contract()` ->
  `validate_required_data_expected_fetch_contract()` ->
  `publish_required_data_quote_snapshot()` -> `seal_required_data_snapshot()`
- **文件(行号)**: `src/application/required_data_plan_identity.py:53-83,86-193,206-305`;
  `src/application/required_data_coverage.py:113-190`;
  `src/application/opend_symbol_outputs.py:121-205,225-269,1132-1271`;
  `src/application/required_data_snapshot.py:95-122`
- **输入场景**: `merged_requests` 声明到期日 B，而 discovery、
  `projected_expirations`、top-level/nested `side_plans` 和实际 CSV 只覆盖到期日 A；
  或 multi-spec aggregate 删除/减少 `meta.requests` child evidence，只保留自报的
  aggregate 时间。
- **实际分支**: contract validator 分别校验各容器的形状和局部字段，却不证明
  `merged_requests`、nested/top-level side plans、projected/discovered expirations 是同一
  demand 的等价投影。Coverage 只从 `merged_requests` 读取 RV flag，其余覆盖完全取
  top-level `side_plans`。`_validate_timestamp_evidence()` 在 `meta.requests is None` 时
  直接跳过 child evidence。
- **预期行为**: 一个 contract 只能表达一份自洽、闭合的 exact demand；矛盾计划应在
  gateway/receipt/seal 前失败，多请求 authority 必须保留可与 exact request 数量/身份
  对账的 child evidence。
- **实际行为**: 定向复现中 request 到期日为 `2026-09-18`，payload/CSV/side plan 为
  `2026-08-28`，仍得到 `receipt_published=True`、manifest `complete`、symbol `ready`。
- **直接证据**: canonical SHA-256 只能证明矛盾内容没有变化，不能证明内容自洽；seal
  复用同一宽松 contract validator，因此无法在后续边界补救。
- **影响**: 回执和终态 manifest 可宣称覆盖从未验收的 exact request；双账户消费者会
  共享同一份错误完成 authority。
- **建议改法和验证点**: 在 contract owner 规范化并交叉校验 discovery、projection、
  request、nested/top-level side plan；`success_empty` 必须没有 request/side demand；
  multi-spec child evidence 数量和 request identity/hash 必须精确匹配。新增矛盾 expiry、
  option type、window、empty projection、缺 child/少 child/错 child 的零 receipt 测试，
  并验证 malformed global authority 不产生 terminal manifest。
- **修复风险**: 高
- **严重程度**: 高

### DR-S1-02-未修复-高-Coverage 把声明过但未验证的 DTE/position strike/非法数值降级成无约束

- **入口/函数**: `required_data_frame_covers_fetch_plan_debug()`、
  `_spot_reference_matches_frame()`、`_strikes_cover_bounds()`
- **文件(行号)**: `src/application/required_data_coverage.py:113-190,271-292,321-365`;
  `src/application/required_data_plan_identity.py:196-247`;
  `src/application/required_data_planning.py:583-631`
- **输入场景**: contract 要求 DTE 20-30，但 raw/CSV 都写 DTE 999；Close Advice
  position-only demand 要求 strike 100，而 cache 只有 strike 90；或 spot/strike bounds
  使用 bool、非法字符串、NaN/Infinity、倒置范围。
- **实际分支**: debug coverage 不检查 DTE；position plan 把 exact strike 放在
  `min_strike/max_strike`，coverage 却只读取为空的 `base_min_strike/base_max_strike`；
  宽松数值转换又把多种非法值变成 `None`，即“没有约束”，而 canonical JSON 允许
  NaN/Infinity。
- **预期行为**: 所有声明过的 exact constraints 必须是合法有限值并由最终 CSV 满足；
  非法声明不是可选约束，position-only exact strike 不能退化为任意 strike。
- **实际行为**: 三类反例均能通过 coverage，并可由 cached/fresh publisher 获得新回执。
- **直接证据**: `_strikes_cover_bounds()` 在两个 base bound 都为 `None` 时只要求存在
  一个 strike；`_safe_float()` 将无效值返回 `None`；spot 预期值无效/非正时直接返回
  match；RV 的 bool 可被 pandas 转成正数。
- **影响**: 系统可在实际缺少目标持仓合约或数据字段错误时宣告 required-data 完整，
  造成 Close Advice 不可评估、候选误筛选或错误风险容量。
- **建议改法和验证点**: contract 层拒绝 bool-as-number、非有限/非正 spot/strike、
  非法 DTE、倒置范围和非法 ISO 日期；coverage 对 active exact request 逐 side/expiry
  验证 DTE 与 discovery trading date，并在 base bounds 缺失时使用 effective
  `min_strike/max_strike`。新增 DTE 999、position strike 90/100、NaN/Inf/bool/reversed
  bounds 的零 receipt 测试。
- **修复风险**: 中
- **严重程度**: 高

### DR-S1-03-未修复-高-Raw JSON 与 consumer CSV 的决策字段可以漂移仍被签成权威回执

- **入口/函数**: `_validate_required_data_quote_candidate()` ->
  `publish_required_data_quote_snapshot()`
- **文件(行号)**: `src/application/opend_symbol_outputs.py:225-269,552-589,1089-1271`;
  `src/application/required_data_snapshot.py:542-596`
- **输入场景**: raw 保持 `mid=1.1,dte=25,RV=0.2`，CSV 在 receipt 前改成
  `mid=99,dte=999,RV=9.9`，identity 五字段不变。
- **实际分支**: validator 只比较 row count 和
  `(symbol, option_type, expiration, contract_symbol, strike)`，不比较 spot、bid/ask、
  last/mid、volume/OI、IV/RV、delta、currency 等下游字段。
- **预期行为**: receipt 前必须证明 CSV 是 raw provider evidence 的唯一允许 projection；
  multiplier enrichment 等本地转换必须是窄白名单且有可验证来源。
- **实际行为**: 定向复现输出 `accepted_value_drift=true` 并成功写 receipt；frozen
  consumer 随后直接使用 captured CSV bytes。
- **直接证据**: receipt 同时绑定两份 bytes，但没有证明两份 bytes 的业务对应关系。
- **影响**: 未由 provider evidence 支持的价格、波动率或风险字段可成为双账户共享的
  frozen decision authority。
- **建议改法和验证点**: 建立唯一 canonical row projection，按 contract code 一一对应，
  规范化 null/number/bool/string 后比较全部 consumer-visible columns；只允许已证明的
  multiplier enrichment。逐字段篡改 mid、bid/ask、spot、IV、RV、delta、DTE 时必须零
  receipt；合法 multiplier 补全仍通过。
- **修复风险**: 中
- **严重程度**: 高

### DR-S1-04-未修复-中-Set-based snapshot coverage 接受同一 contract 的重复行

- **入口/函数**: `fetch_symbol_request()` -> `_validate_snapshot_completeness()` ->
  `_row_identity_counter()`
- **文件(行号)**: `src/application/opend_symbol_fetching.py:518-636`;
  `src/application/opend_symbol_outputs.py:334-393,552-589`
- **输入场景**: requested code set 只有一个 contract，但 option chain/raw/CSV 各包含
  该 contract 两行（完全重复或价格冲突）。
- **实际分支**: requested/row codes 被压成 set；JSON/CSV Counter 只证明双方重复次数
  相同，并不要求每个 requested code 恰好一行。
- **预期行为**: exact snapshot authority 对每个 requested contract 必须是一对一；重复或
  冲突行应 fail closed，不能由 publisher 静默选取或传播。
- **实际行为**: 定向复现输出 `accepted_duplicate_contract=true`、raw rows 2、requested
  count 1，并成功写 receipt。
- **直接证据**: 下游 candidate scanner 逐行消费，没有统一 drop-duplicate boundary。
- **影响**: 同一合约可形成重复 candidate/trace/decision，或以冲突价格产生非确定结果。
- **建议改法和验证点**: 在 provider 产行和 finalizer 双边强制 contract code 唯一，
  `len(rows) == len(requested_codes)` 且每个 Counter value 为 1；覆盖完全重复与冲突重复
  两类 provider/direct-publisher 测试。
- **修复风险**: 低
- **严重程度**: 中

### DR-S1-05-未修复-高-同一 run 的 terminal snapshot manifest 可以被重复 seal 覆盖

- **入口/函数**: `seal_required_data_snapshot()` -> `atomic_write_json()`
- **文件(行号)**: `src/application/required_data_snapshot.py:66-183`;
  `src/infrastructure/io_utils.py:85-114`
- **输入场景**: 同一 run/plan/receipt 连续 seal 两次，或第二次 summary 与第一次冲突。
- **实际分支**: seal 不读取现有 target，每次重新采样 `sealed_at_utc` 并用
  `Path.replace()` 覆盖原文件。
- **预期行为**: terminal commit record 必须 write-once-or-verify；精确重入原字节复用，
  任意冲突保持旧 authority 不变并 typed fail。
- **实际行为**: 相同 summary 一秒后重复 seal，两次均 `complete`，但 bytes/hash 不同；
  complete/partial/failed 也可互相覆盖。
- **直接证据**: prefetch file lock 在 seal 前已经释放；Close Advice 会把 seal 期间 hash
  变化视为 integrity failure。
- **影响**: 不同账户可能绑定同一 run 的不同 manifest generation；无业务变化的重入也会
  中断正在消费的账户。
- **建议改法和验证点**: 先构造不含新时间噪声的 semantic candidate；若 target 存在，
  完整校验 run/root/plan/entries 后精确 adopt，否则冲突拒绝且保留旧 bytes。测试 identical
  reseal bytes/hash 不变、conflicting plan/status 保留原文件、terminal state absorbing。
- **修复风险**: 中
- **严重程度**: 高

### DR-S1-06-未修复-中-结构化 connection failure 被覆盖后 gateway pool 无法关闭坏连接

- **入口/函数**: `fetch_option_snapshots()` -> `fetch_symbol_request()` ->
  `_fetch_one_inprocess()` -> `ThreadLocalFutuGatewayPool.mark_failure()`
- **文件(行号)**: `src/application/opend_market_snapshot_fetching.py:224-294`;
  `src/application/opend_symbol_fetching.py:638-718`;
  `src/application/multi_tick/required_data_prefetch.py:698-709,782-799`;
  `src/infrastructure/futu_gateway_pool.py:7-13,35-50,95-106`
- **输入场景**: market snapshot 因 connection reset/timeout 返回缺失 code 的 typed error
  payload，连续两个 symbol 共用同一 worker gateway。
- **实际分支**: 顶层错误被换成 `SNAPSHOT_COVERAGE_INCOMPLETE` 的展示文案；caller 只把
  该文案包装成 RuntimeError；pool 依赖异常字符串分类，未命中 connection key 后把
  `failure_count` 清零。生产 gateway 没有 `is_connected()` 时会直接复用。
- **预期行为**: 完整性错误仍 fail closed，但底层 connection cause 必须作为结构化健康
  证据传到 pool；连续连接失败应关闭并重建当前 worker gateway。
- **实际行为**: receipt 不会发布，但坏连接恢复机制失效，后续 symbol/账户继续级联失败。
- **直接证据**: 现有 prefetch 测试 mock 掉 `mark_failure`，只验证调用次数，没有经过真实
  classifier。
- **影响**: 一个连接故障可扩大成同一双账户共享轮次的多 symbol 可用性故障。
- **建议改法和验证点**: pool 接收结构化 provider failure/cause，分类 nested
  errors/snapshot_errors/spot_errors，展示文案不参与健康真相。用真实 pool 连续制造两次
  snapshot connection failure，断言 close/rebuild；纯 coverage error 不应误关连接。
- **修复风险**: 中
- **严重程度**: 中

### DR-S1-07-未修复-高-Quote cache metadata 绑定旧 CSV 字节并刷新真实 observation 时间

- **入口/函数**: `save_outputs()` -> `publish_quote_cache_metadata()` ->
  `apply_multiplier_cache_to_required_data_csv()`
- **文件(行号)**: `src/application/opend_symbol_outputs.py:681-761,953-1031`;
  `src/application/multiplier_steps.py:17-50`;
  `src/application/close_advice_quote_cache.py:32-70,73-139`
- **输入场景**: raw observation 已有年龄且缺 multiplier；`save_outputs` 先生成 CSV/meta，
  finalizer 再从本地 cache 把 multiplier 补为 100。
- **实际分支**: metadata 在 normalization 前对旧 CSV hash 签名，并用
  `datetime.now()` 代替 raw `source_observed_at`；normalization 改写 CSV 后不刷新 metadata。
- **预期行为**: cache provenance 必须绑定 finalizer 最终 CSV bytes，freshness 必须沿用
  provider observation，不能因持久化或本地 enrich 获得新鲜度。
- **实际行为**: multiplier 补全后 metadata 返回 `quote_provenance_bytes_mismatch`；另一定向
  复现中 raw+32 分钟的 receipt 已过 30 分钟 TTL，但被刷新过时间的 15 分钟 quote cache
  仍报告 fresh。
- **直接证据**: 同一共享 CSV 在 receipt/seal 路径可 ready，在 cache validator 路径可能
  无效或比 provider evidence 更新，形成两套真相。
- **影响**: manual/Close Advice cache 可以拒绝一份已签 authority，或把 stale source 当成
  新观察继续使用。
- **建议改法和验证点**: metadata 只在全部 normalization 后发布，hash 绑定最终 bytes，
  `source_observed_at` 和 source run identity 从 raw evidence 继承；cached/subprocess/re-entry
  禁止合成新 observation。测试 multiplier 补全后 provenance hash 有效、raw 时间不刷新、
  raw TTL 到期后 cache 同样 stale。
- **修复风险**: 中
- **严重程度**: 高

  write-once/adopt semantics and conflict preservation at every terminal authority boundary.
- No live provider, production notification, broker/ledger, runtime configuration, release, deploy,
  merge, push, or external write was performed during review.
