## Findings

### DR-02-未修复-高-缓存 finalizer 已发布回执后的 debug 写失败会误触发重拉取
- **入口/函数**: `ensure_required_data()` cached planned-data path -> `finalize_required_data_quote_candidate()` -> `_write_fetch_plan_debug()`
- **文件(行号)**: `src/application/required_data_steps.py:141-181`; `src/application/opend_symbol_outputs.py:1696-1772`
- **输入场景**: 现有 raw/CSV/scope evidence 完整且缓存 finalizer 成功，但随后的 fetch-plan debug 文件因 report 目录权限、磁盘空间或临时 I/O 错误写入失败。
- **实际分支**: cached branch 先调用 finalizer；finalizer 会验证、更新 cache metadata、发布 quote receipt 并解析回执证据。返回后才调用 `_write_fetch_plan_debug()`。这两步位于同一个宽泛 `try/except Exception` 内，debug 写失败会设置 `should_refetch=True`并继续执行 provider fetch。
- **预期行为**: 缓存候选一旦通过权威验证并发布了当前 run 回执，非权威 debug artifact 失败不应把已成功的状态重新解释为需要 provider refetch。
- **实际行为**: 系统已有可见的 cache metadata/receipt 成功状态，但仍继续发起 OpenD 拉取和 fresh finalization；可造成多余 provider I/O、同 run 回执重新发布/冲突，以及对外“缓存成功但又重拉”的不一致。
- **直接证据**: `ensure_required_data()` 在 lines 145-153 先完成 cached finalizer，lines 154-160 后写 debug，lines 180-181 捕获任何异常后设置 refetch。finalizer 在 lines 1718-1724 更新 cache metadata，lines 1749-1761 发布 receipt，并在 lines 1762-1772 验证已发布证据；因此 debug 异常发生时权威副作用已完成。
- **影响**: 定时主链在非关键调试写故障时产生重复数据获取和回执状态风险，破坏已验证缓存复用的幂等语义。
- **建议改法和验证点**: 将 debug artifact 从“是否 refetch”的决策域移出。最小改法是 cached finalizer 成功后直接返回权威 evidence，debug 写单独 best-effort 且不改变 provider/cache 决策；或在 finalizer 之前写 debug，但不应让其绕过 raw/CSV/evidence 验证。新增回归：模拟 cached finalizer 成功并产生 evidence，随后 debug writer raise，断言 OpenD executor 未被调用、返回 evidence 保留，且不产生第二次 finalization。
