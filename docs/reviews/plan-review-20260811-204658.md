# Plan Review — Earnings Near-Expiry Window

- Review type: adversarial PlanReview
- Reviewed target: `docs/gateflow/earnings-near-expiry-window/plan.md`
- Binding goal: `docs/gateflow/earnings-near-expiry-window/goal-confirmation.md`
- Branch/base: `feat/earnings-near-expiry-window` / `origin/main@8902f9fd`
- Review scope: six-natural-day policy, OpenD evidence projection, contract outcome aggregation, frozen candidate
  completeness, AI Advice/Daily Brief disclosure, Combo Funding Put parity, compatibility, and tests
- Excluded scope: implementation/code review, RV/premium/multiplier/fee/capacity/ranking changes, release, deploy, and
  production operations
- Conclusion: `fail`

## Assumptions tested

1. Every contract carrying `risk_earnings_unavailable` makes the candidate universe outcome-indeterminate.
2. Intersecting recorded failed intervals with the hard window is sufficient proof that the rest of the hard window
   has authoritative OpenD coverage.
3. A second persisted candidate-universe summary can remain consistent with existing frozen `scope_results` and
   strategy results.
4. A positive blocking event can be treated as conclusive without weakening malformed-artifact fail-closed behavior.
5. Existing Sell Put underwriting is the single Combo Funding Put gate, so one domain policy can preserve parity.
6. One atomic slice is justified because policy, evidence semantics, strategy status, and consumer disclosure form one
   externally visible contract.

Assumptions 1–3 are not sufficiently specified by the current plan. Assumptions 4–6 are supportable if the findings
below are fixed.

## Findings

### PR-01-未修复-高-按“出现财报缺口”计 partial 会把已经确定拒绝的合约误判为候选全集不完整
- **位置**: `Candidate Engine and strategy aggregation`，尤其 plan 第 150–159 行的 unavailable 计数和状态表
- **问题类型**: 状态机漏洞 / 契约缺失 / 非最优方案
- **当前写法**: 只要一个决策包含 `risk_earnings_unavailable`，就把该合约计入 unavailable contract scope；
  accepted candidate 与任意 unavailable sibling 并存时统一输出 `partial_data`。
- **反例/失败场景**: 某合约的硬财报窗口恰好缺证据，但它同时确定违反 DTE、strike、收益率或容量门槛。
  即使 OpenD 后续证明没有财报，该合约仍不可能成为候选。当前计划仍会把它算作 outcome-unavailable；若全组都是
  这类合约，会把合法 `no_candidate` 变成 `partial_data`/`data_unavailable` 并继续阻断 AI Advice；若另有候选，
  会产生虚假的候选全集不完整提示。
- **为什么有问题**: 用户要隔离“受 OpenD 缺口实际影响的范围”，不是把任何伴随缺口都提升为结果不确定。
  Candidate Engine 会累积多个 reject，因此证据缺口和最终 eligibility 是否仍未决是两个不同事实。
- **直接证据**: `candidate_engine.evaluate_opening_candidate_policy()` 会在一个决策中累计所有门槛 reject；
  `candidate_scanning.py:297-332` 当前只要 reason 集合命中 unavailable 集合就优先计为 unavailable，不检查是否同时存在
  确定性 reject。plan 第 150–159 行沿用了同样的 presence-based 模型。
- **影响**: 规则改完后仍可能频繁出现零建议或不必要的 partial warning，直接违背本 work unit 要修复的用户可见结果；
  状态统计也无法解释“45 张分别被什么调节拦截”一类审计问题。
- **建议改法和验证点**: 把每个决策拆成两个正交事实：`evidence_gaps`（诊断）与
  `eligibility_outcome = accepted|definitive_reject|unresolved`。只有 reject 集合中不存在任何现有语义下的确定性
  policy/ineligibility reject、且至少有一个 unavailable reject 时，才计为 unresolved 并影响 partial/data-unavailable；
  同时存在确定性 reject 时保留 earnings gap 供提示/审计，但不降低候选全集的 eligibility completeness。明确列出
  unavailable reason 集合，避免把 `risk_earnings_event` 当缺口。新增回归：
  `earnings_unavailable only -> unresolved`、`earnings_unavailable + hard_dte -> definitive_reject`、
  `earnings_unavailable + return_floor -> definitive_reject`、accepted sibling 加两类 reject 时只有前者触发 partial。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR-02-未修复-高-硬窗口“无失败记录”不等于已证明连续覆盖，缺失或陈旧 projection 可被当作干净无事件
- **位置**: `Per-expiration OpenD coverage`、`Schema and compatibility boundary`、provider coverage 测试矩阵
- **问题类型**: 契约缺失 / 状态机漏洞 / 版本兼容 / 测试缺口
- **当前写法**: 计划把“记录在 artifact 中且状态失败的 interval”与 hard/soft window 求交，并笼统要求校验
  schema/hash；没有定义 interval 集合必须如何证明从 `coverage_start` 到 `coverage_end` 连续、唯一、无重叠，也没有
  规定保存的 `evidence_by_underlier` projection 必须与原始 events/intervals 精确一致。
- **反例/失败场景**: 新 v2 artifact 因生产者 bug、部分写入后被重新组装、或 projection 生成漂移而漏掉一个 hard-window
  interval；剩余 interval 全是 `ok`，artifact 自身 hash 也正确。消费者只寻找显式 failed interval，于是把缺失日期当作
  authoritative absence。类似地，顶层 events 含 day-1 财报，但保存的 projection 错误标为 non-blocking/无事件时，
  当前 loader 直接消费 projection。
- **为什么有问题**: `snapshot_hash` 只证明 payload 内部 bytes 没变，不能证明 coverage contract 完整或 derived
  projection 与 source facts 一致。新规则的安全性完全依赖 hard-window absence proof；这个 proof 不能由“没看见失败项”
  代替。
- **直接证据**: `earnings_calendar.py:240-248` 当前仅筛选显式失败 interval；`earnings_calendar.py:385-398` loader
  只校验 schema/source/market/整体 hash；`earnings_calendar.py:403-429` 随后直接读取保存的 projection，不重算或比较。
  Plan 第 90–119 行没有补上 exact partition/projection invariant。
- **影响**: OpenD 获取不到或 artifact 内部漂移可被误报为“硬窗口完整且无财报”，产生本应 fail closed 的候选；这是
  比过度过滤更危险的假阳性。
- **建议改法和验证点**: 在 plan 中定义 v2 canonical validator：intervals 必须按日期排序、首尾精确匹配
  `coverage_start/coverage_end`、连续、无空洞/重叠/重复、每段 1–7 个自然日、status/reason/result-hash 组合合法；
  `expirations_by_underlier` 与 projection key 集合精确一致。消费者从已验证的 events+intervals 重新投影，并与持久化
  projection 做 canonical equality（或干脆不把 derived projection 当独立 authority）；不一致一律
  `earnings_calendar_snapshot_invalid`。positive blocker 还必须位于一个已验证 `ok` interval。新增缺 interval、重叠 interval、
  重复 interval、错误 coverage_end、projection/event 不一致和 blocker 位于 failed interval 的 fail-closed 测试。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR-03-未修复-中-新增持久化 completeness summary 会复制现有 scope authority，计划未定义唯一真源和交叉不变量
- **位置**: `Frozen candidate-universe completeness` 与 `Schema and compatibility boundary`
- **问题类型**: 过度设计 / 过度耦合 / 契约缺失
- **当前写法**: 在 snapshot sealing 时从 `scope_results` 再生成一个 `complete|partial` summary，持久化、校验并哈希；
  同时允许 snapshot v1 additive 或整体 bump，两条实现路径尚未收敛。
- **反例/失败场景**: `scope_results` 中一个 strategy scope 为 `completed/partial_data`，但新 summary 因 reason 过滤或
  fixture 迁移错误写成 `complete`。两者都在同一个 content hash 内，所以 hash 校验仍通过；AI Advice 与 Daily Brief 若
  消费不同字段会给出相反披露。
- **为什么有问题**: 现有 snapshot 已把 `strategy_results`、`scope_results`、contract decisions 和 ranked candidates
  一并冻结。`opening_candidate_snapshot.py:155-176` 已对它们整体 content-hash；但 validator 在
  `opening_candidate_snapshot.py:400-407` 主要只校验集合类型，后续也没有完整验证 strategy scope reason 与
  strategy result 的对应关系。再增加一个可漂移的持久化派生状态不是最小设计。
- **直接证据**: Plan 第 128–130 行仍把 schema 选择留给 implementation agent；第 169–178 行要求第二份 persisted
  summary，却没有规定 exact recomputation equality 或消费者唯一读取面。
- **影响**: implementation agent 必须临场设计 schema 兼容和 source-of-truth，可能出现自洽 hash 下的语义矛盾，
  增加 AI/Brief 两条链路耦合及后续迁移成本。
- **建议改法和验证点**: 计划应先锁定最小方案：把现有 `scope_results` 作为唯一 frozen authority，补齐 strategy scope
  的 schema/枚举/对应关系验证；提供一个纯函数从已验证 scope rows 推导 universe summary，AI frozen input 和 Brief
  都调用同一函数。只有 AI frozen input 需要把派生 summary 纳入自身 hash，不必给 opening snapshot 新增第二份状态。
  如果确实选择持久化，则必须 bump schema 并规定 summary 等于从 scope rows canonical recomputation 的结果，任何不一致
  fail closed。新增互相矛盾 fixture 的拒绝测试。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

## Open Questions

- 无需用户新增策略选择。以上都是在已确认目标内收敛 correctness 和最小设计的问题。

## Residual Risks

- OpenD 可能在成功响应中漏报真实事件；本地只能证明 API 响应和区间契约完整，不能独立证明外部日历事实完备。
  建议作为 provider quality/observability 后续项，不在本 work unit 引入第二数据源。
- 同日整天 pending 会在事件已经实际发布后继续保守处理到市场本地午夜；这是用户确认的政策，不是实现缺陷。
- 财报门放行后 RV、收益、流动性、资金和覆盖容量仍可产生零候选；实现验证必须保留逐 contract reject provenance。
- 旧 v1 artifact 在升级后 canonical 消费应 fail closed；不做历史迁移。任何跨版本同-run恢复风险应在实现 artifact 中
  明确记录。

## Final conclusion

`fail`。六自然日方向、共享策略所有权和同日语义正确，但计划尚未区分“存在证据缺口”与“资格结果仍未决”，
也没有给 hard-window absence 建立连续覆盖和 derived projection 一致性证明；这两点都可能继续造成错误零建议或更危险的
假阳性。修复三个 finding 并通过 PlanReview re-review 后，才适合交给 implementation。
