## Goal and boundary understood

The plan must stop repeated option-close notifications without weakening the canonical
`trade_events -> position_lots` ledger. It must accept a broker deal once across Push, Poll and Inbox
replay; separate option-leg closure from cause resolution; reserve pending quantities without fabricating
a zero projection; and create durable notification intents that do not automatically resend after an
uncertain provider outcome.

Broker source ownership, per-lot terminal events, lifecycle allocations, business-state revision and
delivery attempts are intentionally different grains. The implementation must preserve those grains
instead of using a single id or mutable receipt flag for all of them.

## Re-review of the fifth-freeze changes

1. **Broker source ownership — closed**: the plan now adds an append-once ledger owner registry,
   requires transaction-local claims for option anchors and stock settlements, retains ownership after
   void, and prevents evidence-type or role changes from reusing the same source.
2. **Push/Poll payload drift — closed**: source payload hashes use allowlisted normalized economic
   fields and exclude transport/receipt provenance, so the same deal received through two transports
   remains idempotent while economic-field drift fails closed.
3. **Timing/pairing overcoupling — closed**: the immutable timing policy contains only market,
   contract and settlement-calendar facts. The 15-minute pairing window is derived from the first
   accepted option-close evidence and cannot be moved by replay.
4. **Business versus delivery revision — closed**: `resolution_revision` advances only with canonical
   business-state changes; manual resend retains that state and increments only `delivery_revision`.
5. **Duplicate public transitions — closed**: deterministic transition slots plus canonical
   state fingerprints prevent repeated due ticks or additional incomplete observations from creating
   another interim, initial-final, needs-review or conflict message.
6. **Historical replay notification leak — closed**: a live writer may create a pending ordinary-close
   intent only while first creating the complete split set. Existing historical events without a seeded
   Outbox row are audit-only; migration remains the sole historical suppression/final-intent owner.
7. **Implementation sequencing — closed**: ledger idempotency primitives and atomic writer behavior are
   isolated in Slice C1 before lifecycle adoption/overlay propagation in Slice C2 and before runtime
   dispatch.

## Assumptions tested

1. Canonical broker identity includes internal account, Futu account id and deal id.
2. Push and Poll may carry different provenance for the same economic event.
3. Existing evidence uniqueness by `(source_type, source_event_id, evidence_type)` alone cannot prevent
   reuse under another evidence type or an embedded stock-deal list.
4. A stock settlement deal must remain owned after its original terminal event is voided.
5. Stock-first arrival can remain an unclaimed candidate until a unique case is known.
6. A lifecycle timing policy may exist before option-close evidence is accepted.
7. Receipt time is suitable for notification coalescing but not for financial cause classification.
8. Pending zero-price evidence can make quantity non-actionable without changing the financial
   projection.
9. One broker deal may produce multiple deterministic per-lot events but only one aggregate
   ordinary-close notification.
10. A replay of an old broker deal may encounter canonical events without any new Outbox row.
11. Repeated reconciliation can observe new non-terminal evidence without deserving another public
    status message.
12. A manual resend is a delivery operation, not a new lifecycle resolution.
13. Unknown provider acceptance cannot safely return to automatic retry.
14. Void-aware effective allocation must be consistent across read, planning, writer, quality and
    migration paths.
15. Complete no-settlement evidence must be checked against frozen pre-terminal remaining and then
    revalidated inside the terminal writer transaction.
16. Missing Futu metadata or query-coverage proof must remain `needs_review`, not be guessed.
17. Migration suppression must complete before dispatcher activation.
18. Production service restoration remains a separate authorization boundary.

## Special review lenses

### Architecture boundary review

The revised plan keeps cause policy in a pure domain resolver, broker queries and observation assembly
in application/infrastructure, and economic writes/source ownership in the ledger transaction owner.
Pairing provenance is no longer stored as an instrument timing fact. Delivery attempts cannot advance
business resolution. No blocking dependency-direction or authority violation remains.

### Best-practice review

The plan now uses canonical identities, allowlisted hashes, append-only source ownership, immutable
evidence, transaction-local revalidation, deterministic state fingerprints, semantic transition slots,
bounded delivery retries, frozen unknown outcomes, migration dry-run/readback and crash-boundary fault
injection. Negative broker evidence remains complete-or-unavailable.

### Optimal-solution review

Reusing the existing lifecycle case/evidence/allocation and canonical projection remains the smallest
credible design. A narrow source-claim table is safer than scanning evidence JSON for global uniqueness.
Separating delivery revision is simpler and more accurate than manufacturing a new business resolution
for a resend. Historical notification seeding stays in migration rather than adding a broad automatic
backfill path to the live writer.

### Overengineering review

The additional source registry, timing binding, lifecycle overlay and Outbox are each tied to a
demonstrated failure mode. The plan avoids a second projection, provisional financial close event,
mutable allocation status, separate systemd service and automatic cash-settlement support. The
canonical fingerprint has a versioned allowlist and does not absorb arbitrary runtime metadata.

### Overcoupling review

The fifth freeze separates four concepts that were previously at risk of moving together: market
timing versus message arrival, source ownership versus evidence type, business revision versus delivery
attempt, and per-lot accounting versus broker-level notification. Slice C1 supplies storage/transaction
primitives before C2 propagates lifecycle actionability, so later runtime work no longer has to invent
future-slice schema.

## Open Questions

- Slice B must still establish with fixtures whether the installed Futu SDK and configured account can
  prove contract settlement style, last-trading cutoff, history-order completeness, pagination and
  cash-flow coverage. Any unprovable capability remains `needs_review`.
- Feishu webhook responses may not provide a queryable message identity. If provider reconciliation
  cannot prove acceptance, `unknown` remains operator-owned and cannot be automatically resent.

Neither question requires changing the plan's state machine or authority boundaries.

## Residual risks and suggested tracking

- **Current partial implementation drift**: the in-progress repository schema still contains
  `pairing_until_ms` in the timing table, has only one Outbox revision dimension, and has no source-owner
  registry. The runtime still constructs the synchronous receipt callback. Track these as Slice
  C1/E implementation obligations; do not treat the present worktree as satisfying the frozen plan.
- **Overlay consumer inventory**: Position Advice, Close Advice, auto-close, assignment scenarios,
  reports, agent queries, quality checks and migration all need the same fail-closed overlay. Maintain an
  explicit call-site checklist and integration tests.
- **Canonicalizer compatibility**: source/state fingerprint versions must be frozen with fixtures before
  any migration manifest is generated. A canonicalizer change requires a new schema version, not silent
  reinterpretation.
- **Legacy ambiguity**: historical records without account-bound broker keys or unique source ownership
  must remain review-only and must not receive automatically generated pending notifications.
- **Rollout handoff**: schema upgrade, migration apply, dispatcher enablement and trade-intake restore
  remain separate gates. The stopped production service is not authorized to restart by this review.

## Final conclusion

**pass-with-risks**

The fifth frozen plan is code-generation-ready. The new owner-claim, pairing derivation, dual-revision,
transition-slot and historical-replay contracts close the remaining idempotency ambiguities without
creating a second financial authority. Remaining risks are implementation conformance, broker capability
proof and rollout inventory, all covered by explicit fail-closed gates and tests.
