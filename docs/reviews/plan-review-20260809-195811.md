## Assumptions tested

1. A single shared observation snapshot can be safely published by market-scoped Tick runs.
2. A one-file PM prepared envelope has an unambiguous integrity/hash contract and recovery path.
3. The current append-only evidence log can reconstruct the latest semantic evidence snapshot without
   mixing historical successful runs.
4. PM preparation is executed or recovered exactly once across both branches of the existing
   `prefetch_done` state machine.
5. Removing a public `./om` dispatch while retaining a managed collector does not leak application
   orchestration into the public CLI layer.
6. Exact scopes, fact registry, account isolation and fail-closed source binding can be proven with
   deterministic tests.

## Findings

### 1-未修复-高-单一 observation_set 整份覆盖会让 US/HK Tick 互相删除观察标的
- **位置**: Plan 4.5、5.5、S5 和 S6 的 observation publisher
- **问题类型**: 并发恢复风险 / 状态机漏洞 / 契约缺失
- **当前写法**: Tick “原子发布共享 `observation_set.json`”，先在当前 Tick 内跨账户合并；
  S6 再由 `multi_account_tick.py` 发布四来源 union。
- **反例/失败场景**: US Tick 先把 US 配置、PM 持仓、期权和候选写入整份 snapshot；HK Tick
  随后只掌握当轮 HK account/run 数据并原子替换同一路径，US 的动态 PM/期权/候选标的消失。
  两个市场 Tick 并发时还会发生 read-modify-write lost update。
- **为什么有问题**: 原子 replace 只保证单次文件完整，不保证多 writer 合并正确。Collector
  因此可能在没有任何账户或策略变化时停止刷新另一市场的真实持仓标的，直接违背“四来源
  主动观察”和跨账户匿名复用目标。
- **直接证据**: Plan 119–123、184–188、491–494、543–551 只定义单路径/整份 snapshot，
  没有 market partition、writer lock、generation merge 或 stale-partition 规则；项目 Tick
  本身按 market/runtime config 独立运行。
- **影响**: 搜索覆盖静默缺失、Advice 长期 `no_evidence`，并发结果不可重复，测试无法证明
  多市场生产语义。
- **建议改法和验证点**: 保持一个匿名文件，但 schema 按 canonical market 分 partition；
  publisher 在 private lock 下读取、验证、只替换当前 market partition 后原子写回，Collector
  读取一致快照再 union。为每个 partition 保存 generation/hash/generated_at；配置标的由
  managed collector 每轮合并，不依赖动态 partition。新增 sequential US→HK、HK→US、并发
  publish、同 market replacement、损坏 snapshot fail-closed 测试。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### 2-未修复-高-evidence index 没有定义“本次成功快照成员”，会把历史事件永久混入当前建议
- **位置**: Plan 5.5、S5 evidence state；现有 `evidence_store.freeze_evidence_index()`
- **问题类型**: 状态机漏洞 / 数据一致性 / 不可直接实施
- **当前写法**: Plan 只要求 success/failure 分开、保留 last success、identity hash 过滤和
  URL/content 去重，没有说明当前 symbol success 应选择哪些 `symbol_evidence` 行。
- **反例/失败场景**: 第一次成功搜索记录事件 A；下一次成功搜索返回事件 B 或合法零证据。
  若实现沿用当前 store，把该 symbol 的全部历史 `symbol_evidence` 去重后返回，则 A 仍进入
  最新 frozen view；更糟的是本轮零证据会更新 `last_success_at`，把旧 A 重新标成“新鲜”。
- **为什么有问题**: freshness 属于成功搜索快照，不能给历史行续期。Append-only 真源必须
  能从 status 明确重建当次完整 semantic snapshot，不能用“该 symbol 所有历史行”猜成员。
- **直接证据**: 现有 `evidence_store.py:149-167,200-207` 收集全部 symbol evidence，并仅用
  最新 status 的时间判断 freshness；`collector.py:385-416` 的 status 只有 evidence_count，
  没有 snapshot member refs/hash。Plan 499–500 没有补这个关联。
- **影响**: 已过期、被撤回或已被新搜索取代的风险继续改变 `switch/defer`；零结果可能把旧
  事件错误续鲜，破坏可审计性和 Advice reuse hash。
- **建议改法和验证点**: 每次成功 symbol status 必须引用该次完整 semantic snapshot
  （例如 ordered `evidence_refs` + `semantic_snapshot_hash`，所有 evidence 行绑定同一
  `evidence_run_id/symbol/identity_hash`）。Freeze 只读取选定 last-success status 所列成员；
  合法零证据的成员为空。若业务要 carry forward，Collector 必须显式把仍有效证据纳入新
  snapshot，而不是 store 隐式保留。测试 A→B、A→empty、failed after A、identity change、
  tampered/missing member。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### 3-未修复-中-PM 单文件 envelope 的 payload_sha256 没有 hash domain，完整性合同不可实现
- **位置**: Plan 5.2、S2 artifact publication/loading
- **问题类型**: 契约缺失 / 不可直接实施
- **当前写法**: `prepared_portfolio_distribution.v1.json` 是包含 normalized rows 的单 envelope，
  同时要求 envelope 内含 `payload_sha256`，但没有定义它覆盖哪些字段。
- **反例/失败场景**: 若 hash 覆盖整个文件，会产生自引用；若实现者各自排除不同字段，S2
  writer 与 S6 loader 会得到不同 hash；若只 hash rows，freshness/trust/account 等权威字段
  可被改动却仍通过所谓 payload hash。
- **为什么有问题**: 该 hash 后续进入 Advice binding 和 tamper tests，是状态权威的一部分。
  hash domain 含糊会迫使 implementation 重新设计，违反 code-generation-ready 要求。
- **直接证据**: Plan 145–152 只列字段；S2 312–337 要求 write-once/hash tamper；没有 nested
  payload、canonicalization 或 envelope integrity hash 定义。
- **影响**: PM quality/account/valuation 绑定可能被篡改或误判；writer/reader 测试会根据实现
  偶然形状编写，不能证明设计合同。
- **建议改法和验证点**: 定义 envelope 为 `authority + payload + integrity`；
  `payload_sha256` 只覆盖 canonical JSON `payload`（normalized assets + derived totals），另设
  `envelope_sha256` 由外部 manifest/调用方对完整文件 bytes 计算并传递，或明确单文件 loader
  以 trusted path bytes hash 绑定而不在文件内自存完整 hash。测试分别篡改 authority、payload、
  hash、账户和 valuation currency。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 4-未修复-高-S2 未覆盖 prefetch_done 恢复分支，无法保证 PM once-per-run 与同一 authority
- **位置**: Plan S2、S6 Tick handoff；`run_tick_account_execution()` prefetch state machine
- **问题类型**: 状态机漏洞 / sequencing / 测试缺口
- **当前写法**: S2 要求“每个账户最多读取 PM 一次”并返回对象，但没有说明 initial prefetch
  和 `prefetch_done=True` recovery 两条路径如何发布/加载 PM artifact，S6 才笼统补 handoff。
- **反例/失败场景**: implementation 把 PM 调用放进现有 `if scanning_accounts and not
  request.prefetch_done` 块；re-entry 走 `prefetch_done=True` 时现有代码只恢复 required-data、
  operational portfolio 和 option manifests，PM envelope 不存在于 handoff。另一种实现是在
  recovery 重新调用 PM，则同 run 产生不同 observed facts，违反 once/same-run freeze。
- **为什么有问题**: prepared authority 的价值就在重入时复用同一 generation。PM 是 soft
  dependency，不能照搬 option manifest missing 时的 hard account error，也不能静默重取。
- **直接证据**: `tick_account_execution.py:375-390` 是 initial preparation；
  `:758-833` 的 recovery 只恢复 existing operational portfolio/option。Plan 304–337 没有
  recovery transition 或 manifest path/hash maps；S6 550 才写“只补 handoff”。
- **影响**: 同一个 run 在不同入口得到 PM available/unavailable 两种 Advice，或重复外部取数；
  re-entry tests 通过不了，生产重试不可审计。
- **建议改法和验证点**: S2 同时实现并测试两条状态：initial path 调 PM 并发布；recovery path
  只从 exact run/account state 加载、验证和传递 envelope bytes hash，缺失/损坏转 Advice
  unavailable 但不影响 account scan，不重取 PM。显式增加 outcome/request 中的
  `prepared_portfolio_distribution` authority/hash/status maps，S6 只消费。测试
  initial→recovery 零额外调用、missing/tampered recovery soft degradation、多账户隔离。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

## Architecture boundary review

总体方向正确：Candidate Engine 运营事实、PM 战略分布、SQLite option authority 和公开
evidence 分属清晰边界；PM 不做 hard barrier、Advice 不直接读取数据库也符合项目约束。
需要修正的是共享 snapshot 的多 writer ownership、prepared recovery 和 append-only
snapshot reconstruction，而不是新增通用框架。

Managed collector 的最终入口还略含糊：Plan 允许把
`src/interfaces/cli/ai_evidence_collector.py`“转为 managed-service wrapper”。修 plan 时应明确
业务 runner 归 application，service wrapper 只做 argv/env 适配，且不再由 `./om` parser
分发；这属于 finding 1–4 修复时可一起收紧的低风险边界，不单列 finding。

## Best-practice / optimal-solution / overengineering / overcoupling review

- 最优路径仍是复用现有 prepared writer/loader、PM client 和 JSONL，不需要数据库迁移或
  event bus。
- Observation set 按 market partition 加一把小范围文件锁，比新建每账户 watcher、数据库或
  Collector 直接遍历账户目录更简单且更安全。
- Evidence status 显式列 snapshot members 是 append-only log 的最小完备合同；不需要第二个
  latest store。
- 七个 slices 边界整体可 review；修复 S2 state machine 与 S5 snapshot semantics 后不需要
  重排或合并 slices。

## Conclusion

`fail`

Plan 的总体架构和范围合理，但 observation multi-writer、evidence snapshot membership、PM
integrity hash 和 prefetch recovery 四项会造成生产事实丢失或不可审计。必须先修 plan 并
re-review，之后才能进入 accepted plan commit。
