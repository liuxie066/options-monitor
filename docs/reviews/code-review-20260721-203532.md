## Findings

### AG-001-未修复-高-Daily Brief 关闭时 scheduled scan 不再提交 processed-target 水位

- **入口/函数**: `run_tick_notification_flow`
- **文件(行号)**: `src/application/tick_notification_flow.py:167-186`
- **输入场景**: canonical scheduled tick reaches a scan target while `notifications.daily_brief.enabled` is false.
- **实际分支**: account pipeline runs, but `daily_brief_prep` is `None`; the only `commit_scan_targets_fn` call is guarded by `daily_brief_prep is not None`, and Slice 4 removed the previous account-execution mark.
- **预期行为**: scheduler processed-target state is scan orchestration authority and must advance after a durable account outcome regardless of which notification projection is enabled.
- **实际行为**: neither `last_processed_scan_target_utc_by_account` nor `last_run_utc_by_account` advances. A later 10-minute wake-up within catch-up grace may rerun the same target, and every later target remains dependent on stale state.
- **直接证据**: `tick_account_execution.py` only returns target mappings; no writer remains there. The flow calls the writer only inside the Daily Brief-enabled branch.
- **影响**: duplicate broker/pipeline work and unstable notification timing under the existing disabled-Daily-Brief configuration; scheduler correctness is incorrectly coupled to a presentation feature flag.
- **建议改法和验证点**: commit exact scheduled targets after either notification preparation path succeeds and before any provider call; add a regression with Daily Brief disabled proving one exact commit and no duplicate coupling.
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### AG-002-未修复-高-manual/force 扫描会写普通候选 delivery state 并可能发送候选通知

- **入口/函数**: `_prepare_daily_brief_notification`
- **文件(行号)**: `src/application/tick_notification_flow.py:727-850`
- **输入场景**: `trigger_kind` is `manual` or `force`, pipeline succeeds, and the successful brief contains an unalerted candidate.
- **实际分支**: only `fixed_target` is suppressed for non-scheduled triggers. The flow still calls `record_daily_decision_brief_candidates`, chooses `candidate_alert`, prepares an envelope, reads it back and sends it. It can also select an already-pending scheduled envelope.
- **预期行为**: approved plan §6.4 requires non-scheduled scans to update successful current only; they must not create fixed/candidate delivery state, send ordinary candidate notifications, or advance alerted state.
- **实际行为**: a manual inspection/force scan has hidden delivery side effects and can notify users unexpectedly.
- **直接证据**: `trigger_kind` is checked only when deriving `fixed_target`; candidate recording, notification decision and retry selection are unconditional.
- **影响**: operator safety regression, unexpected real sends, and candidate delivery history contaminated by manual scans.
- **建议改法和验证点**: for `trigger_kind != scheduled`, persist successful current but skip candidate-state recording, delivery decision/preparation and retry selection; test both manual and force candidate scans leave delivery state absent and sender uncalled.
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### AG-003-未修复-中-多账户首次升级时 processed-target map 会让未迁移账户丢失 legacy seed

- **入口/函数**: `_last_processed_scan_target_for_account`
- **文件(行号)**: `src/application/scan_scheduler.py:467-474`
- **输入场景**: legacy state has `last_run_utc_by_account` for `lx` and `sy`; after `lx` first writes the new `last_processed_scan_target_utc_by_account` map, that map has no `sy` entry yet.
- **实际分支**: because the map exists, lookup for `sy` returns `None` instead of falling back to `sy`'s legacy `last_run`.
- **预期行为**: compatibility switches per account; each account uses legacy `last_run` until that account has its first explicit processed-target entry.
- **实际行为**: `sy` can treat an already-completed recent target as unprocessed and repeat it during rollout.
- **直接证据**: fallback to `_last_run_for_account` occurs only when the entire map is not a dict, not when the requested account is absent.
- **影响**: account-specific duplicate scan/send risk during gradual first-write migration.
- **建议改法和验证点**: fall back per account when its map value is absent; add a state with only `lx` in the new map and a valid legacy `sy` last-run.
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### AG-004-未修复-高-account scheduler fallback 可在缺少 exact target 的情况下准备并发送 scheduled 报告

- **入口/函数**: `run_scheduler_flow` -> `run_tick_account_execution` -> `run_tick_notification_flow`
- **文件(行号)**: `src/application/multi_tick_scheduler.py:239-244,299-317`; `src/application/tick_account_execution.py:181-186`; `src/application/tick_notification_flow.py:167-186,927-931`
- **输入场景**: global scheduler decision is due, but one account's in-process scheduler payload/normalization fails and falls back to the global should-run decision.
- **实际分支**: fallback has no `scheduler_decision`, so account execution emits no exact target mapping. Notification rendering falls back to the global scheduler decision, can prepare a fixed report, but the empty target map bypasses the commit block and provider send remains reachable.
- **预期行为**: scheduled delivery requires an exact account-to-target mapping; missing/malformed mappings fail closed before provider delivery and do not guess from global state.
- **实际行为**: message may be sent without committing the account's processed target, enabling duplicate rescans/retries and violating durable prepare -> target commit -> send.
- **直接证据**: the commit guard checks only whether the mapping is truthy; it never validates completeness against accounts that actually scanned.
- **影响**: duplicate user messages and inconsistent scheduler/delivery state under a real scheduler-degradation path.
- **建议改法和验证点**: validate every scheduled scanned account has a non-empty exact target before notification preparation/provider execution; audit and raise on mismatch; add a missing-target test proving sender and commit callback are both unreachable.
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高
