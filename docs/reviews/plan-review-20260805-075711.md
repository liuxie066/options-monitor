# Plan Review

## Reviewed target and scope

- **Target**: `docs/plans/trade-intake-settlement-collector-resilience-plan-20260805.md`
- **Review mode**: adversarial implementation-plan review after the 2026-08-05 07:24 review findings were repaired
- **Scope**: branch-local due routing, settlement capability/error taxonomy, source-local leases/backoff, semantic projection, canonical admission, legacy compatibility, concurrency/crash recovery, configuration, tests, and later production acceptance
- **Excluded**: code implementation, historical evidence cleanup, release/deployment, production service start, live provider calls, notifications, and business-data writes

## Goal and boundary understood

The plan is intended to stop a specific repeatable failure class: an optional lifecycle settlement collector is polled every minute despite a missing capability or unchanged result; volatile attempt fields make each result look new; canonical evidence and account-wide read cost then grow without bound.

The claimed generality is intentionally narrow. It covers every required source of `settlement_observation` through one typed contract, while cash-flow method absence is only the first fixture. It does not claim to repair unrelated periodic jobs or all high-CPU conditions.

## Assumptions tested

1. Provider gating can be applied only after a case is known to require settlement observation, without freezing local-only deadline reconciliation.
2. Static API absence, explicit account unsupported, transient failure, unknown failure, and structurally observed incomplete data can be distinguished without parsing error text.
3. A disposable source-local control row can bound calls without becoming business admission authority.
4. Backoff survives unrelated lifecycle evidence changes and resets only for a meaningful provider-input/capability/semantic change.
5. Semantic identity excludes attempt and mutable output fields while retaining every fact needed to distinguish new settlement coverage.
6. Unrelated account rows or SDK-added columns cannot create a new settlement semantic state.
7. Issue and terminal evidence use one transactional latest-state admission owner and remain safe across crashes, restarts, and two writers.
8. Legacy timestamp-derived evidence can seed the new semantic head without scanning or rewriting the full historical evidence set.
9. The plan remains a minimal settlement-specific work unit rather than a generic task framework.

## Special review lenses

### Architecture boundary review

The final plan has one-way ownership. The trade due runner owns classification and provider invocation; source-local SQLite owns only lease/backoff; an I/O-free lifecycle-settlement evidence contract owns normalization and semantic projection; the ledger writer owns generation CAS and canonical admission. The explicit prohibition on ledger-to-trades/provider imports avoids the earlier dependency inversion. The shared pure contract also lets the writer project legacy evidence inside the same transaction without calling infrastructure.

### Best-practice review

Unknown errors default to bounded retry rather than permanent park. Provider calls require atomic claims, but correctness does not depend on the claim store. The write order is claim, collect, canonical transaction, then control update; this gives defined behavior at both crash windows. Semantic equality is a versioned allowlist with source-specific row normalization, not a blacklist of volatile fields.

### Optimal-solution review

The additional control row and one-row canonical admission head are justified by separate responsibilities. A checkpoint-only design cannot close the write/crash window; a global semantic unique key would incorrectly suppress `A -> B -> A`; and comparing timestamp-ordered evidence without a head is ambiguous for same-millisecond writes and version skew. The chosen latest-state head is the smallest durable mechanism that handles all three cases.

### Overengineering review

The plan does not add a daemon, generic retry engine, public reset CLI, migration/cleanup workflow, task DSL, or service split. Capability keys and outcome shapes are reusable only within the settlement collector. Other collectors must opt in through a separately reviewed change.

### Overcoupling review

The collector kill switch cannot stop discovery, local due aging, listener ingestion, backfill, or holdings sync. Cache invalidation and retry eligibility are also separated: any case-scope change may force a no-provider replan, but an unchanged provider-input scope preserves backoff. Full provider result rows remain audit data; only case-relevant normalized rows participate in semantic equality.

The mixed-case regression requires the local case to advance while the blocked provider case makes zero calls/writes. Crash-before-write retries; crash-after-write is absorbed by latest-semantic admission; two writers serialize or fail generation CAS. The admission head also repairs a stale pointer after an old-version write.

## Findings

No material unresolved findings.

The adversarial pass specifically tested the previously missed self-invalidating and false-change cases: post-write case status/revision, post-write cache scope, same-millisecond evidence, `A -> B -> A`, unrelated lifecycle evidence, unrelated provider rows, legacy rows without semantic metadata, control loss, and old-version head drift. The revised plan gives an explicit owner and deterministic test for each.

## Open questions

- The production Futu adapter's explicit account-unsupported code allowlist still needs authoritative provider evidence during implementation. This is not blocking: the safe initial implementation can leave the allowlist empty and classify every unverified code as `unknown_error`.
- The claim lease should be calculated from the collector's total configured provider timeout/retry budget plus margin, not merely hardcoded to 120 seconds. The plan already binds the lease to that timeout; implementation review should verify the exact formula and a slow-call concurrency test.
- Confirm that deployed source mapping assigns one due owner per account/market/case. Cross-source overlap cannot duplicate canonical business state because the ledger writer is authoritative, but separate source inboxes would not share a provider-call lease.

## Residual risks and suggested tracking

- **Existing history size**: the roughly 30 MB historical evidence remains. Initial ambiguous-case classification may parse it once per account, and explicit full lifecycle reads may remain slow. Track bounded lifecycle readers or compaction as a separate work unit; do not fold destructive cleanup into this fix.
- **Shared process lock**: an eligible provider call still occupies the current trade-intake process topology. Bounded cadence removes the sustained loop, but service isolation remains a separate hardening issue.
- **Whole-inbox corruption**: because attempt state shares the source inbox database, whole-file corruption can stop the listener before local lifecycle routing. The plan accurately leaves that existing service-level failure outside this collector fix.
- **Malformed latest legacy evidence**: automatic admission fails closed and requires offline inspection. This is preferable to guessing semantic equivalence or scanning thousands of rows in the live path.
- **Mixed-version writers**: rollback artifacts are compatible, and stale heads are repaired, but concurrent old/new application writers remain forbidden by rollout sequencing.
- **Production verification**: CPU thresholds, zero-call/zero-write deltas, and local-case progression can be proven only after separately authorized release, deployment, and service start.

Suggested tracking destinations: implementation slices S1-S3 in this plan; bounded historical reader, service isolation, and whole-inbox recovery as separate future work units.

## Final conclusion

**pass-with-risks**

The plan is now code-generation-ready for the scoped settlement-collector resilience work. The four prior blockers are closed: the gate is branch-local, error classes are safe, attempt control is separated from canonical admission, and semantic equality is versioned down to relevant source-row fields. Remaining items are explicit rollout, topology, legacy-data, and service-isolation risks rather than missing implementation design.
