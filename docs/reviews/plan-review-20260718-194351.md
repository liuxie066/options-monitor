# Plan Review：升级/发布耗时优化计划

## Review 元数据

- **Review target**：当前讨论中的升级与发布耗时优化计划（P0/P1/P2 及长期 dependency lock 建议）
- **Review scope**：本地 release preflight、GitHub Actions release/guardrail/plugin workflows、生产 `service_upgrade` 的依赖安装、共享 venv 生命周期、超时/恢复语义、生产 `uv` rollout、Feishu 健康检查与 post-switch config rebuild
- **代码基线**：`origin/main` / `v1.2.412` 的干净工作树 `/private/tmp/options-monitor-release-1.2.412`
- **Review 方法**：architecture boundary、best-practice、optimal-solution、overengineering、overcoupling、timeout/recovery/concurrency、test-gap adversarial review
- **限制**：本 review 不实施修复，也不修改原计划

## 被 review 的计划摘要

### P0

1. 去掉两个测试中的真实 30 秒等待。
2. 捕获 subprocess timeout，并始终写结构化升级状态及执行清理。
3. server 模式只安装一次依赖，不先装 runtime 再装 server。

### P1

1. 在生产主机安装 `uv`，设置 `OM_UPGRADE_INSTALLER=uv`。
2. 共享 venv 直接在最终 hash 目录构建，避免 rename 后脚本 shebang 指向临时目录。
3. 内联 GitHub Actions `resolve-tag`。
4. 增加 pip cache、合并依赖安装。
5. 减少 Guardrails、Agent Plugin、Release CI 的重复工作。

### P2

1. 可选优化 Feishu WS SDK 冷启动 import。
2. 可选减少切换后的重复 config rebuild。

### 长期建议

生成 fully resolved dependency lock，使共享 venv hash 可复现，避免浮动 SDK 依赖被无声冻结。

## Goal、success signal 与边界审查

计划的真实目标应是：**在不削弱发布质量门、升级原子性、失败可恢复性和生产回滚能力的前提下，降低 release preflight、GitHub release 和生产依赖变更升级的端到端耗时。**

当前计划给出了优化方向和观测数据，但没有给出可直接交付 implementation agent 的完整 success contract。至少缺少：

- 每个 slice 的目标耗时和允许回退上限；
- 失败状态机、超时 payload、清理和重试契约；
- 共享 venv 的完整/不完整状态、并发 owner 和 crash recovery 契约；
- installer/lock/cache 三者一致的依赖语义；
- GitHub required checks、权限和分支保护不变式；
- 生产 `uv` rollout 的 preflight、canary、fallback 和 rollback 验收标准。

因此本 review 按“是否足够 code-generation-ready”而非“方向是否合理”进行判定。

## Assumptions tested

| Assumption | Adversarial result |
|---|---|
| 去掉两个真实 sleep 不会削弱 cooldown 行为覆盖 | **基本成立，但需限定改法。** 两个慢测试测的是错误聚合/保护逻辑；已有独立测试 monkeypatch `_sleep_after_rate_limit_wave` 并断言 30 秒 cooldown。必须让慢测试注入 clock/sleep，而不是删掉 cooldown assertion。 |
| 捕获 `TimeoutExpired` 就足以修复升级超时后的脏状态 | **不成立。** 还需要定义进程树终止、operation 记录、锁释放、临时目录处理、status durability 和 retry/re-entry。 |
| 直接在最终 hash 目录构建 venv 只会修复 shebang，不会损失安全性 | **不成立。** 现有 temp→rename 同时承担发布原子性；直接构建会让消费者看到半成品，除非补完整状态机。 |
| `uv` 可作为严格生产 installer 直接启用 | **证据不足且当前不可实施。** 生产主机目前没有 `uv`；计划没有版本、安装 owner、兼容性、fallback 或 rollback 契约。 |
| 依赖 lock 可以留到长期优化 | **不成立。** 当前 hash 只覆盖 requirement 文件内容，而 runtime 含浮动 lower bounds；缓存命中会长期复用旧解析结果，已经是 correctness/operability 语义冲突。 |
| 合并 CI 重复工作不会改变安全边界 | **不成立。** Release job 有 `contents: write`，Guardrails/Agent Plugin 只有 `contents: read`；合并 job/workflow 可能扩大权限并改变 required check 名称与 branch protection。 |
| server 单次安装天然等价于 runtime+server 两次安装 | **仅在 `requirements/server.txt` 始终 `-r runtime.txt` 时成立。** 计划没有把这个关系变成受测试的契约。 |
| Feishu `find_spec`/延迟 import 能等价替代真实 SDK import 检查 | **不成立。** `find_spec` 只证明模块可发现，不证明 SDK 及其 transitive imports 可加载。 |
| 将所有优化按 P0/P1/P2 一次推进便于交付 | **不成立。** 测试、CI 权限、依赖解析、主机 installer、venv 状态机和运行时 health check 属于不同 failure domains，统一推进扩大回归面并使收益归因困难。 |

## Special lens 结果

### Architecture boundary review

- `service_upgrade` 同时跨越主机工具可用性、依赖解析、缓存发布、release symlink 和结构化状态持久化；计划必须在该 owning boundary 内定义显式状态机，而不能只在 `_run_command()` 增加一个异常分支。
- CI validation 的只读权限边界与 release publish 的写权限边界当前是分离的。任何“合并重复工作”都不能默认跨越该边界。
- dependency policy 的真源分散在 requirements、constraints、hash 计算和 installer 行为之间；计划没有先统一契约。

### Best-practice review

- 长进程 timeout 处理应包括 child/process-group termination、bounded cleanup、durable failure record、idempotent retry，而不是只 catch exception。
- 缓存产物应有明确的 build/publish/valid 状态；半成品不能与可复用成品使用同一路径且仅靠文件存在判断。
- 生产工具 rollout 应有版本固定、readiness probe、canary、fallback 和 rollback。

### Optimal-solution review

- 在 dependency resolution 语义未收敛前先引入 `uv`，可能只是更快地生成不可复现缓存；先定义 lock/cache policy，再选择 installer，顺序更安全。
- 修复 venv shebang 的最优路径不是简单删除 temp→rename，而是保留“不可被消费者使用的构建态”，同时确保 venv 创建时使用最终绝对路径。
- 两个 30 秒测试应注入 sleep/clock seam；无需改变生产 cooldown 逻辑或新增通用调度抽象。

### Overengineering review

- P2 的 Feishu 冷 import 和二次 config rebuild 当前只占正常升级的一部分，且前者承担真实依赖可加载验证。若在 P0/P1 尚未收敛前引入新的 lazy-import/probe abstraction，ROI 低并增加 health semantics 分叉。
- 不需要为两个测试建立通用时间框架；局部 monkeypatch/injected sleeper 足够。

### Overcoupling review

- 原计划把本地测试、GitHub workflow、生产主机依赖工具、缓存目录状态机和运行时健康检查绑在同一个优化项目中，要求跨多个 owner 同步修改和验收。
- CI 去重若通过合并 job 实现，会把只读 validation 和写 release permission 耦合。
- installer、dependency hash 和 lock policy 必须作为一个明确契约共同设计；当前计划却把它们拆成“近期速度优化”和“长期复现性优化”，形成时间上的错误解耦。

## Material findings

### PR-001-未修复-严重-超时修复没有定义可恢复的升级状态机
- **位置**: P0「捕获 subprocess timeout，并始终写结构化升级状态/cleanup」
- **问题类型**: 状态机漏洞 / 并发恢复风险 / 契约缺失 / 不可直接实施
- **当前写法**: 计划把修复描述为捕获 timeout 并写状态、执行清理。
- **反例/失败场景**: `pip`/`uv` 超时时，顶层 Python 收到 `subprocess.TimeoutExpired`，但安装器派生的子进程仍存活或持有文件；升级锁被释放后重试，新进程与旧进程同时写同一个 venv/cache。又或者 cleanup 删除目录时旧进程仍在写，形成半成品、磁盘泄漏或后续误判。
- **为什么有问题**: catch exception 只改变控制流，不自动解决 process tree、durability、lock ownership、重试和部分写入。实现 Agent 必须自行设计这些关键语义，计划尚未 code-generation-ready。
- **直接证据**: `src/application/service_upgrade.py:156-193` 把 timeout 直接传给 `run_cmd`，没有捕获 `TimeoutExpired`；`src/application/service_upgrade.py:1510-1515` 只捕获 `RuntimeError`。生产已有约 39 分 38 秒、无 completion marker 的 stale build 目录，说明异常路径会留下实际运行时残留。
- **影响**: 状态不一致 / 不可恢复 / 升级并发写入 / 隐藏失败 / 后续返工
- **建议改法和验证点**:
  1. 在计划中先定义 command outcome schema：`ok`、`failed`、`timed_out`、`cancelled`，timeout 也必须追加 operation 并写最终 upgrade status。
  2. 明确 subprocess/process-group 启动和终止策略：TERM、grace period、KILL、等待回收；说明对 injected `run_cmd` 的测试接口。
  3. 规定 cleanup 只能在确认子进程退出后执行；无权/无法清理时记录 `cleanup_failed`，不得伪报完成。
  4. 明确升级锁在何时释放、重试如何识别前一次 owner、stale lock 与 stale build 如何关联。
  5. 添加 timeout、child ignores TERM、cleanup failure、重试成功、status write failure 的测试；验收必须证明无后台安装进程和无可复用半成品。
- **修复风险（高）**: 涉及 subprocess 生命周期和生产恢复行为。
- **严重程度（严重）**: 当前缺口已能产生长时间残留和不可预测重试。

### PR-002-未修复-严重-直接在最终 venv 路径构建会移除原子发布边界
- **位置**: P1「共享 venv 直接在最终 hash 路径构建，避免 rename」
- **问题类型**: 并发恢复风险 / 状态机漏洞 / 非最优方案 / 架构边界
- **当前写法**: 为修复 venv script shebang 指向 `.tmp.<pid>`，建议取消临时路径 rename，直接写最终 hash 目录。
- **反例/失败场景**: 构建在安装中途被 SIGKILL、主机重启、磁盘满或网络失败，最终 hash 目录已经存在。另一个升级进程或后续重试看到目录后，可能删除正在写的目录、误用仅有 Python 但缺包的环境，或与前一次残留争用。
- **为什么有问题**: 现有 temp→rename 虽造成绝对 shebang 错误，但同时提供“构建态不可见、完成后发布”的原子边界。直接构建只能解决路径问题，却把完整性和并发安全回退为目录存在判断。
- **直接证据**: `src/application/service_upgrade.py:1335-1345` 定义 temp build path 和 marker validity；`src/application/service_upgrade.py:1414-1418` 会删除 invalid final/build path；`src/application/service_upgrade.py:1482-1485` 在写 marker 后 rename 并 link。生产共享 venv 的 `bin/pip` shebang 实际指向旧 temp 目录，证明路径问题真实，但不证明可以安全移除发布状态。
- **影响**: 半成品被复用 / 并发破坏 / 不可恢复 / 生产升级失败
- **建议改法和验证点**:
  1. 计划应采用显式状态协议：在最终绝对路径创建 venv，但以 `.incomplete`/owner metadata 标识构建态，只有通过 import/sanity validation 后原子写 completion marker。
  2. release `.venv` symlink 和 cache lookup 只能接受 completion marker + executable Python + 必要 import validation 全部通过的目录。
  3. 定义同 hash 并发构建策略：现有全局 upgrade lock 是否足够；若不足，增加 per-hash owner lock，而不是猜测目录状态。
  4. 定义 stale owner 检测、SIGKILL 后清理、正在运行 owner 不被删除、旧完整 cache 不被覆盖。
  5. 添加 crash points：venv 创建后、runtime install 后、server install 后、marker 前、link 前；逐点验证重试和消费者不可见性。
- **修复风险（高）**: 需要重写共享 venv lifecycle，而不只是改一个路径。
- **严重程度（严重）**: 原建议直接实施会把已知 shebang bug换成更危险的半成品发布问题。

### PR-003-未修复-高-依赖 lock 被错误地后移为长期优化
- **位置**: 长期建议；P1 installer/cache 优化的前置条件
- **问题类型**: 动机不成立 / 契约缺失 / 非最优方案 / open question 未收敛
- **当前写法**: 先优化 `uv`、pip cache 和共享 venv，之后再考虑 fully resolved dependency lock。
- **反例/失败场景**: `futu-api` 或 `yfinance` 发布兼容性变化，但 requirements 文件未变。共享 venv hash 不变，因此正常升级继续复用数周前解析的 SDK；另一台主机或 cache miss 又解析出新版本。同一 release tag 在不同主机上运行不同依赖，且 cache hit 与项目注释所称“正常升级可拾取 SDK fixes”相冲突。
- **为什么有问题**: 这不是纯速度问题，而是 release identity、可重现性和 cache invalidation 契约。没有先决定“浮动跟随”还是“release 锁定”，就无法正确设计 hash key、cache reuse 或 installer rollout。
- **直接证据**: `requirements/runtime.txt:3-4` 使用 `futu-api>=10.6.6608`、`yfinance>=1.4.1`；`constraints/runtime.txt:1-4` 明确声称市场 SDK 通过正常升级拾取 fixes；`src/application/service_upgrade.py:1242-1269` 的 hash 只包含环境 context 和依赖文件内容，不包含实际解析版本。生产旧共享 venv 从 5 月持续复用到 7 月，证明浮动依赖不会在普通 cache hit 时更新。
- **影响**: 版本漂移 / 无法复现 / cache 语义错误 / 回滚不可信 / 风险后移
- **建议改法和验证点**:
  1. 在任何 installer/cache 改造前，由计划明确选择依赖政策：release-resolved lock（推荐）或带 TTL/registry fingerprint 的主动刷新；不要同时声称可复现和自动浮动。
  2. 若选择 lock，hash 必须覆盖 resolved artifact；release preflight/CI 校验 lock 与 source requirements 一致。
  3. 若选择浮动，status 必须记录 resolved versions，cache key/expiry 必须确保“正常升级拾取 fixes”的行为可验证，并接受同 tag 非确定性。
  4. 增加同一 tag 重建一致性、cache hit、cache miss、回滚到旧 release 的依赖版本测试。
- **修复风险（中）**: 设计决策影响 requirements/CI/cache，但边界清晰后实现可控。
- **严重程度（高）**: 当前 cache 已与声明语义冲突，继续优化会固化错误。

### PR-004-未修复-高-生产 uv strict rollout 缺少 readiness、fallback 和 rollback 契约
- **位置**: P1「主机安装 uv，设置 `OM_UPGRADE_INSTALLER=uv`」
- **问题类型**: 最佳实践偏离 / 契约缺失 / 切片过粗 / 不可直接实施
- **当前写法**: 把 `uv` 作为生产性能优化，并建议使用 strict `uv` 模式。
- **反例/失败场景**: 主机上的 `uv` 被升级、PATH 在 cron/service 环境中不同、目标 Python 不受支持、镜像/证书配置只对 pip 生效，或 `uv` 对 requirement/constraint 的解析结果不同。strict mode 会在 pip 可用时仍阻断升级；若同时切换 cache key，回退到 pip 还可能无法复用已有 venv。
- **为什么有问题**: 生产当前没有 `uv`，这是新增的 host-level dependency 和单点故障。计划没有规定谁安装/升级、允许版本、服务环境 PATH、proxy/index 继承、canary 或一键回退。
- **直接证据**: 生产 `command -v uv` 无输出；`src/application/service_upgrade.py:1467-1470` 在 mode=`uv` 且不可用时直接失败；`src/application/service_upgrade.py:1229-1238` 把 installer mode 放入 dependency context，因此切换模式也改变 cache identity。
- **影响**: 生产升级阻断 / 新单点故障 / 回滚复杂 / 运行环境漂移
- **建议改法和验证点**:
  1. 拆成独立 rollout slice：代码先支持并验证 `auto`，主机再安装固定版本 `uv`，最后才评估是否切 strict。
  2. 明确 readiness probe：service/cron 相同用户和环境下可发现 `uv`、版本范围、Python 版本、index/proxy/cache 路径、最小安装 smoke。
  3. 首次在 disposable hash/cache 上 canary，不覆盖现有完整 venv；记录 pip/uv resolved package diff 和耗时。
  4. 定义回退：取消环境变量即可回到 pip，并证明不需要手工清理/改 symlink；strict 模式启用需单独 CEO approval。
- **修复风险（中）**: 可通过独立、可回滚 rollout 降低。
- **严重程度（高）**: 原计划直接把性能工具变成生产升级硬依赖。

### PR-005-未修复-高-CI 去重没有保护 required checks 与最小权限边界
- **位置**: P1「减少 Guardrails/Agent Plugin/Release CI 重复工作」及「内联 resolve-tag」
- **问题类型**: 架构边界 / 过度耦合 / 契约缺失 / 测试缺口
- **当前写法**: 广义合并/复用依赖安装和重复检查，以降低多个 workflow 的总耗时。
- **反例/失败场景**: 把 Guardrails 或 Agent Plugin steps 合入 release job 后，它们在 `contents: write` 权限下运行；或者删除/改名独立 workflow/job 后，branch protection 继续等待旧 required check、或不再强制原检查。仅在 VERSION push 触发的 release 也不能替代 PR 上的 guardrail/plugin 验证。
- **为什么有问题**: 重复执行不等于重复责任。PR quality gate、main push validation 和 release publish 有不同 trigger、权限和审计语义。计划没有先列 required check/permission matrix，implementation agent 无法安全判断哪些工作可合并。
- **直接证据**: `.github/workflows/guardrails.yml:3-10` 与 `agent-plugin.yml:3-10` 在 push/PR 上运行且只有 `contents: read`；`release-from-version.yml:3-9` 只在 main 的 VERSION 变更触发；`release-from-version.yml:29-35` 和 `_release-reusable.yml:17-22` 为 publish 赋予 `contents: write`。三者都执行部分 smoke/plugin/依赖安装，但安全边界不同。
- **影响**: 权限扩大 / required checks 失效 / 未经验证发布 / review 不可验收
- **建议改法和验证点**:
  1. 计划先建立 trigger × check × permission × artifact matrix，标明 branch protection 依赖的稳定 check names。
  2. 只共享只读 composite action/cache/setup，不把 validation job 合并到写权限 publish job；publish job 应只下载/消费已验证 artifact，或保持最小 steps。
  3. `resolve-tag` 可单独内联到 release job，但必须保留 VERSION/tag/commit 一致性校验，不能只节省 job scheduling。
  4. 验收包括 PR、普通 main push、VERSION main push、workflow failure 四种场景，并检查实际 token permissions 和 required check 显示名称。
- **修复风险（中）**: workflow 改动小，但错误会直接削弱发布门。
- **严重程度（高）**: 当前计划没有区分速度重复与安全职责重复。

### PR-006-未修复-中-server 单次安装依赖于未固化的 include 契约
- **位置**: P0「server 模式安装一次依赖」
- **问题类型**: 契约缺失 / 测试缺口 / 过度耦合
- **当前写法**: 因 `requirements/server.txt` 当前包含 `-r runtime.txt`，建议只安装 server requirements，避免 runtime 二次解析/安装。
- **反例/失败场景**: 后续维护者将 server 文件改为只列 server-only 包，或改用 generated lock，但安装代码仍只执行 server 文件。升级可成功创建 venv，却在运行时缺 pandas/futu 等 runtime 包。
- **为什么有问题**: 优化正确性依赖一个文件包含关系，但计划没有把它提升为受验证的 public build contract。仅凭当前文件内容改执行顺序会制造隐式耦合。
- **直接证据**: `requirements/server.txt:1-2` 当前为 `-r runtime.txt` + `lark-oapi`；`src/application/service_upgrade.py:1121-1201` 的 pip path 先安装 root requirements，再在 include_server 时安装 server requirements，实际重复解析 runtime。
- **影响**: 未来依赖缺失 / 隐式耦合 / 回归难发现
- **建议改法和验证点**:
  1. 计划明确 server requirements 是“runtime superset”还是“server delta”。推荐定义唯一安装入口（resolved server lock/superset），不要依赖命令顺序叠加语义。
  2. release check 增加契约验证：server 环境必须能 import 全部 runtime smoke modules 和 `lark_oapi`。
  3. 测试同时覆盖 pip 与 uv 的 command plan，证明 runtime 不重复安装且 server 产物完整。
- **修复风险（低）**: 契约和测试明确后改动局部。
- **严重程度（中）**: 当前可优化，但没有测试会把风险推给未来维护。

### PR-007-未修复-高-计划切片过宽且缺少逐 slice 验收与回滚门
- **位置**: 整体 P0/P1/P2 sequencing
- **问题类型**: 切片过粗 / 过度耦合 / 不可直接实施 / review 不可验收
- **当前写法**: 先做 test+CI，再做 upgrade reliability，再做生产 uv，最后做 health/config 微优化，但每一层仍包含多个不同 failure domain，且没有独立 PR、acceptance budget、rollback gate。
- **反例/失败场景**: 一次 release 同时改变 test sleep、CI workflow、timeout cleanup、venv lifecycle、installer 和 cache key。生产升级变快或失败时，无法隔离是 installer、依赖版本、状态机还是 workflow artifact 造成；回滚代码也未必能回滚 host-level `uv` 或已生成 cache。
- **为什么有问题**: 项目是 operations-sensitive production tool。没有观测窗口和独立回滚单元的广泛性能优化，不符合最小改动最大收益与质量优先原则。
- **直接证据**: 观测表明本地 98.83 秒中约 60 秒来自两个测试；正常生产升级只有约 20.06 秒且共享 venv reuse 约 0.81 秒；真正高风险慢路径是 dependency-change install 和异常残留。不同瓶颈应由不同 success metric 验收，不能用单一“升级更快”证明。
- **影响**: 回归归因困难 / rollback 不完整 / implementation agent scope creep / review 不可验收
- **建议改法和验证点**:
  1. 重写为至少四个独立 slices：A 测试 sleep seam；B timeout/status/process cleanup；C dependency policy + venv lifecycle；D CI setup/cache 去重。生产 `uv` 是 C 完成后的独立 rollout，不与代码 PR 绑定。
  2. 每个 slice 给 baseline、目标、non-goal、文件边界、failure tests、rollback 方法和观测窗口。
  3. 顺序建议：A（低风险立即收益）→ B（可靠性）→ dependency policy decision → C（cache/venv）→ D（CI）→ uv canary → 可选 P2。
  4. 每个 slice 完成后保留一次未优化路径作为回归对照；未达到耗时目标或错误率上升即回滚，不继续下一 slice。
- **修复风险（低）**: 主要是重写计划和切分交付，不要求先改代码。
- **严重程度（高）**: 当前整体计划不能安全交给单个 implementation agent 自主执行。

## 可保留的方向

以下方向有充分证据，重写计划时可以保留，但不能绕过上面的契约：

1. **两个慢测试注入 sleeper/clock**：预计将 full pytest 从约 94 秒降到约 34 秒，是当前最高 ROI、最低风险改动。
2. **为 timeout 追加结构化 operation/status**：方向正确，但必须扩展为完整 process/recovery 状态机。
3. **消除 server runtime 重复解析**：方向正确，但先固化 server superset/lock 契约。
4. **修复共享 venv shebang**：是生产真实 bug，但不能简单删除构建态隔离。
5. **内联 `resolve-tag`**：可作为独立 workflow 小改，预计节省约 10–14 秒 scheduling，但必须保留 metadata validation。
6. **CI cache/setup 复用**：可共享只读 setup，不合并安全职责。

6. `uv` 由操作系统包、官方 installer、pipx 还是其他方式管理？谁负责升级和安全补丁？

## Final conclusion

**fail**

计划的性能诊断和优先级方向总体可信，尤其是两个 30 秒测试、重复 server install、stale venv shebang 和 timeout 残留都由直接证据支持；但当前计划尚未定义 production upgrade 的 timeout/process recovery 状态机、共享 venv 原子发布语义、dependency lock/cache correctness、CI 权限/required-check 不变式以及 `uv` rollout/rollback。它仍会迫使 implementation agent 在高风险边界上现场设计，因此不应直接进入 `/execute`。
