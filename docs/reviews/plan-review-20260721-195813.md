## 6. Architecture boundary review

- **Decision Brief ownership**：scheduled ordinary rendering 由 structured artifacts -> Daily Brief assembler/lifecycle -> existing delivery adapter 单向负责；Compact/Legacy Markdown 被 poison tests 隔离。
- **Trigger ownership**：trigger classification 留在 `multi_account_tick.py`/runtime trigger context；renderer 不推断 operator intent。
- **Config ownership**：validator 负责接受/拒绝与 warning；sender 不再读取 legacy switch；cache version 属于 config loader。
- **Read-model ownership**：runtime status/analysis 只描述 compatibility artifact，不把其 presence 当 delivery truth；actual delivery health 继续来自 notification diagnosis/send counters。
- **Shell ownership**：`notification_shells.py` 只负责 H1/fields/sections 排版；业务状态、dedupe、retry、rate limit、persistence 留在原 caller。
- **Transport ownership**：P0 provider payload、capacity preflight、retry、delivery confirmation 和 Post->text rollback 不下沉到 renderer/shell。

Conclusion: boundaries are implementation-ready.

## 7. Best-practice and optimal-solution review

- 两阶段 config migration + validator-versioned cache 能处理 new-code/old-config 与 strict cleanup，而不要求原子 code+config deploy。
- terminal failure 不再借用 success/skip，且定义 deterministic duplicate replay；符合 fail-closed/idempotent execution best practice。
- public contract 采用 canonical field + bounded compatibility alias + machine-readable replacement，不做无期限双真源。
- manual/force 与 scheduled 使用同一扫描链但不同 ordinary-delivery contract；避免复制 scanner 或引入第二 sender。
- no-candidate 作为 Daily Brief 状态，而不是保留独立 heartbeat renderer，减少重复 authority。

没有发现更简单且同样安全的替代路径。立即删除 Compact artifact 或旧 config key 会放大 version-skew/rollback 风险；保留 runtime renderer flag 则会恢复第二 authority。当前 staged path 是更实际的最小安全方案。

## 8. Overengineering review

通过：

- 不新增 renderer registry、template DSL、继承体系、通用 message DTO 或 provider-specific business renderer；
- finalization 复用现有函数并加 caller-provided reason，不新增第二 finalizer；
- idempotency 仅扩展现有 key/payload，不新建状态存储；
- read-model migration 复用现有 runtime status/analysis schema，未引入新服务或数据库；
- shared shells 只有两个 public functions，且明确禁止吸收业务 state machine。

## 9. Overcoupling review

- P1 与 broader `option-notification-experience` 都会修改 `tick_notification_flow.py`，但计划已固定实施顺序、要求后者 rebase/修订 rollback 并重新 PlanReview；不是静默覆盖。
- Legacy deletion、strict config rejection 和 legacy read alias removal 被绑定在同一 hard-pause cleanup，是合理的 compatibility exit bundle；任一证据不足即继续 Phase A/B，不会部分破坏旧 reader/config。
- System Notice 和 Receipt shell 分别独立切片，失败可单独回退，不要求 renderer cutover 同步成功。

没有未受控的跨层双向依赖。
