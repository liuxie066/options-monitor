## Reviewed scope

Reviewed the proposed checkpoint/tail projector, retained-lot representation,
public-record conversion, diagnostics, event and lot generations, invalidation,
diff publication, writer/preflight facades, migration/startup behavior,
activation binding, benchmark comparability, latency, allocation, WAL, and
steady-state storage bounds. The current Codex agent independently checked each
DeepSeek claim against source before assigning a finding.

## Material findings

### P3A-PR-01 — high — blocking — resumable state is neither lifetime-bounded nor sufficient as written

The plan says the checkpoint stores ordered "current lot state", but the
current projector retains fully closed `PositionLot` objects and their complete
`close_event_ids`. On the failing retained-closed fixture this makes checkpoint
state grow with lifetime history. At the same time, replacing the list with only
"current adjust fields" and a last close id does not yet prove that the exact
legacy public row remains reproducible.

Direct evidence:

- `PositionLot.apply_close()` appends every close id and the projector keeps
  closed lots in `lots_by_id`;
- `publisher._position_lot_to_legacy_record()` reconstructs fields from the open
  event, ordered effective adjust patches, current lot economics, and last close;
- the accepted performance failure is specifically the retained-closed-lot
  fixture.

Required correction: checkpoint only active/open resumable lots, carry the
exact current public fields plus the minimum economic continuation facts for
each active lot, emit and then evict a fully closed lot, and force full mode for
an event that targets an evicted closed lot. Prove full versus resumed equality
with deterministic and property-style transition tests. Unchanged closed rows
remain in authoritative `position_lots`; they are not copied into every
checkpoint.

### P3A-PR-02 — high — blocking — diagnostic parity is underspecified and can silently diverge

The plan proposes a count/hash/sample summary for prefix diagnostics. Current
projection, import, invariant, and event validators create error diagnostics;
successful publication rejects those errors and current successful publisher
fixtures have an empty diagnostic list. A general summary is therefore both
unnecessary today and insufficient if a future warning affects the exact public
result.

Required correction: freeze v1 fast checkpoints as `zero diagnostics only`.
A checkpoint may be seeded only from a full-oracle result with an exactly empty
effective diagnostic list; any tail diagnostic, including a future non-error
diagnostic, selects the full path. Historical APIs continue returning complete
diagnostics. The acceptance comparator still checks exact empty-list parity and
a fixed zero-summary sentinel, without retaining prefix diagnostic rows.

### P3A-PR-03 — high — blocking — hidden O(E) reads remain and the proposed comparison is not operation-equivalent

`persist_trade_event_object()` and
`persist_trade_event_objects_atomically()` load all events once to build an
`existing_by_id` map before loading all events again for projection. Preflight
also replays complete history. The current Phase 1 timing baseline invokes
`rebuild_position_lots_from_trade_events()` repeatedly; it proves the O(E)
problem, but it is not the same operation as an ordinary append.

Required correction:

- add primary-key lookup for the candidate event ids and a count primitive;
- resolve untargeted close candidates from the trusted active accumulator, with
  same-transaction revalidation, rather than scanning retained closed lots;
- inventory every full-history call on eligible paths with fail-on-call spies;
- compare old full-mode and new fast-mode executions of the same public facade,
  same candidate event, and independently reset identical database fixture;
- keep explicit rebuild measured and O(E), but do not present it as a fast
  append result.

### P3A-PR-04 — high — blocking — normal invalidation and corruption are conflated

The plan allows a legal void/repair/backdate/update/delete to invalidate all
checkpoints, then says the full fallback may leave mode disabled or untrusted.
That can make one lawful control operation permanently disable the fast path.

Required correction: normal semantic invalidation invalidates checkpoint rows
but does not change an enabled global mode. A successful full replay atomically
publishes lots/heads and seeds a new full checkpoint, so the next eligible
append can be fast. Only payload/hash/schema corruption or shadow semantic
mismatch sets global mode `untrusted` and requires explicit verify/reactivate.
Full-oracle publication after checkpoint corruption may leave current lots and
heads trusted while only the checkpoint path remains untrusted.

### P3A-PR-05 — high — blocking — trigger and cross-account freshness proof is incomplete

DeepSeek asserted that global source generation necessarily makes account B
stale after an account A append. That assertion is not true if every successful
transaction publishes all account heads with the same final global generation,
as the plan intends. The plan nevertheless lacks the explicit A-write/B-read
test and a closed classification for future columns. A future projection-bearing
column omitted from a trigger can create a falsely fresh head.

Required correction: retain the accepted global source generation, explicitly
update all existing heads on every successful event publication, and test A
append -> B trusted read. Add a versioned classification for every table column,
make an unclassified column fail migration/readiness tests, cover INSERT,
UPDATE, DELETE, and REPLACE semantics, and bind activation to the verified
SQLite schema cookie. Arbitrary out-of-authority schema tampering remains an
operational boundary, but a normal DDL change must disable the fast path.

### P3A-PR-06 — medium — blocking — rotation latency has no independent acceptance limit

The plan measures a rotation transaction and bounds its WAL, but the 500 ms
latency gate can be hidden by the 99 ordinary transactions between rotations.

Required correction: run a separate forced-rotation 5/30 distribution at both
the 100-event and 1-MiB boundaries. Its p95 wall and CPU must each be at most
500 ms, in addition to allocation/WAL/K limits. Report max and cycle p99 as
diagnostics; do not move checkpoint I/O outside the atomic transaction without
a new review.

### P3A-PR-07 — medium — blocking — startup index creation is O(history)

`CREATE INDEX` over populated `trade_events` or `position_lots` scans and sorts
existing rows. The statement that startup creates indexes while doing no
O(history) work is false.

Required correction: startup may create the new indexes only for an empty/new
store. On a populated store it adds metadata-only columns/tables/triggers,
reports the missing indexes as not ready, and leaves checkpoint mode disabled.
The explicit migration `apply` owns and separately measures backfill and index
construction.

### P3A-PR-08 — medium — blocking — prefix binding and backdated invalidation are not codegen-exact

The plan names a prefix chain but does not define byte framing, so two
implementations can disagree or concatenate ambiguously. It also describes
"intersected/later" invalidation without proving the <=50 ms lookup.

Required correction: freeze the chain seed, UTF-8 event bytes, eight-byte
big-endian length framing, and recurrence. Backdated/control selection compares
only the incoming sort key/target against the at-most-three checkpoint boundary
rows; v1 invalidates all for control/update/delete and never scans event history
to discover affected lots.

## DeepSeek claim dispositions

- Accumulator/public parity: agreed and strengthened as P3A-PR-01/02.
- Global generation makes unrelated accounts unavailable: disagreed as a
  necessary outcome; all-head publication closes it, but the missing proof is
  accepted in P3A-PR-05.
- Combo force-full fails the measured workload: partially agreed. The Phase 1
  fixture is synthetic open/close history, not Combo membership. Phase 3A must
  benchmark real eligible single/batch facades and report force-full facades
  separately; expanding Combo membership is not justified without measured
  evidence.
- Generic trigger on every UPDATE: disagreed because the accepted Phase 1
  contract explicitly excludes metadata-only changes. A closed column
  classification plus schema binding is safer and avoids needless invalidation.
- Normal invalidation can become permanently untrusted: agreed, P3A-PR-04.
- Rotation spike: agreed, P3A-PR-06.
- Startup index is O(history): agreed, P3A-PR-07.
- Per-transaction raw module-byte fingerprint: disagreed. Semantic
  `projector_schema`, acceptance source revision, release/deploy drift checks,
  and SQLite schema binding are the stable contracts. Raw source hashing is
  packaging-dependent and does not prove semantic equivalence.
- Backdated invalidation could scan O(E): agreed that the original text is
  ambiguous; fixed by the K<=3 boundary algorithm in P3A-PR-08.

## Assumptions requiring retest after correction

1. Fully closed lots never need to remain in the resumable active state for an
   append-safe future event; a target to an evicted lot must force full mode.
2. Every currently successful publish has exactly zero effective diagnostics.
3. All eligible writer/preflight paths can avoid full event-list reads.
4. Streaming a changed account's canonical stored-lot fingerprint, if still
   required, remains within the combined 500 ms gate without loading all rows
   as Python objects; failure returns this aspect to plan review rather than
   adding an unmeasured Merkle projection.
5. Updating all account heads stays inside the accepted account-fanout budget.

## Open questions

No user-choice question is required. All findings can be corrected inside the
accepted Phase 3A boundary. Combo broad-membership acceleration and raw
executable fingerprinting remain deliberately outside that boundary.

## Residual risks

- Force-full control, Combo, and explicit rebuild paths remain O(E); they must
  be measured and reported separately and cannot be called fast.
- Canonical account fingerprinting may still read retained public lot rows for
  a changed account. It must stream with bounded allocation and pass the
  end-to-end gate; no speculative Merkle table is approved in this plan.
- Source code that changes projection semantics without bumping the explicit
  projector schema remains a review/release process risk.

## Conclusion

`fail`

The core direction remains credible, but P3A-PR-01 through P3A-PR-08 must be
written into the plan and re-reviewed before the accepted-plan commit or any
source implementation.
