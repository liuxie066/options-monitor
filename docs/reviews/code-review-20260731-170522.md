### 1-未修复-高-迁移 bridge 未进入冻结 decision snapshot，Position Advice 与运行期得到不同生命周期事实

- **入口/函数**: `decision_state_snapshot()` -> `build_lifecycle_read_models_from_decision_snapshot()` -> Position Advice / positions context，对比运行期 `lifecycle_case_read_model()` -> `lifecycle_option_close_anchor_facts()`
- **文件(行号)**: `src/application/ledger/decision_snapshot.py:81-96`; `src/application/positions/context_builder.py:347-455`; `src/application/ledger/lifecycle_overlay.py:63-70`; `src/application/trades/lifecycle_reconciliation.py:83-111,156-196`; `src/application/ledger/queries.py:402-570`
- **输入场景**: canonical v2 case 只有一个合法的非 allocating `migration_bridge`；被 supersede 的 legacy case 持有唯一零价 option anchor 和 source claim；尚未写 terminal allocation。这正是本次新增 bridge 采用路径。
- **实际分支**: 运行期 read model 调用新 helper，解引用 legacy evidence/claim，临时加入 rebased zero-price anchor，因此产生完整 reservation 和 `cause_pending`。冻结 decision snapshot 只包含 cases/evidence/allocations，不包含 source claims；context builder 又只按当前 case id 分组 evidence。它看到的 v2 evidence 只有 bridge，而通用 overlay 直接跳过 `migration_bridge`，不会生成同一 rebased anchor 或 reservation。
- **预期行为**: 同一冻结 ledger generation 中，运行期调和、Position Advice 和 positions context 应消费同一个 ledger-owned lifecycle overlay；合法 bridge 的 reservation、closure fact、reason state 和冲突原因必须一致，并被 decision fingerprint 覆盖。
- **实际行为**: 运行期模型为 `closure_fact=option_leg_closed`、`reason_state=cause_pending`、reserved contracts 等于冻结目标；snapshot 模型为 reserved 0，deadline 前表现为 open/not-started 语义，deadline 后可变成 `needs_review`。同一个 case 因读取入口不同而得到不同事实，且 legacy source claim 的存在、缺失或冲突不进入 decision-state fingerprint。
- **直接证据**: `lifecycle_reconciliation.py:95-110` 仅在运行期把 helper 返回的 anchor 加入 evidence；`context_builder.py:377-397` 只使用 snapshot 中按 v2 case id 分组的原始 evidence；`lifecycle_overlay.py:66-68` 无条件跳过 bridge；`decision_snapshot.py:81-96` 的 fingerprint payload 没有 source claims 或 validated bridge facts。新增测试 `tests/test_lifecycle_redesign_contracts.py:748-766` 只断言运行期 read model，未经过 decision snapshot/context builder。
- **影响**: 本次修复不能真正闭环最初的 Position Advice 持仓事实问题；用户可能同时看到运行期正在等待/采集结算证据，而 Position Advice 报告 partial、not-started 或需要人工复核。当前路径仍偏向 fail-closed，但审计、解释和 fingerprint 一致性已破坏，后续 promotion 也无法证明使用的是同一事实。
- **建议改法和验证点**: 在 ledger 的 coherent read transaction 中输出经过验证、版本化的 bridge/anchor reservation facts，或把 source claims 纳入 snapshot 后由一个纯 contract resolver统一生成 overlay；将该结果纳入 decision fingerprint。新增同一 fixture 下 live read model 与 frozen snapshot model 的逐字段等价测试，并覆盖 claim 缺失、claim 冲突、数量不匹配和 deadline 前后。
- **修复风险（低/中/高）**: 高
- **严重程度（低/中/高/严重）**: 高

### 2-未修复-高-Combo identity 采纳未验证 group 的完整成员集合，可把额外持仓错误标记为 active combo

- **入口/函数**: `option-positions adopt-combo-identity` -> `adopt_existing_combo_identity_atomically()` -> Position Advice `_group_structure_states()` / `_apply_selected_proposal()`
- **文件(行号)**: `src/application/ledger/writer.py:291-340,354-375`; `src/application/position_advice_plan_builder.py:1388-1446,430-447,952-999`; `tests/test_position_advice_v2_ledger.py:346-419`
- **输入场景**: 三条 fully-open lot 共享同一个已有 `strategy_group_id`：用户精确选择一条 Funding Put 和一条 Participation Call，但还有一条额外 Short Put（或其它同 group leg）。选中的两腿在数量、角色、strike、expiry、broker/account/symbol 等字段上均合法。
- **实际分支**: adoption writer 虽然重放了全部 lots，却只按用户传入的两个 record id 调用 `_existing_combo_adoption_leg()`；没有扫描或拒绝其它同 `strategy_group_id` 的 projected lots。随后插入 immutable identity。Position Advice 按 group id 给所有同组 lots 复用该 identity 的 `active_combo` state，但 identity 内只绑定被选中的两腿。
- **预期行为**: 正式采纳前必须证明 group membership 唯一且完备：同 group 的有效 lot 集合恰好等于两个指定 record id，角色各一条，不能存在额外或重复腿。
- **实际行为**: 含额外腿的歧义 group 可被正式标为 active combo。对额外 Short Put 生成建议时，plan builder 会把该行当作 combo funding leg，同时在 group operation 中引用 identity 绑定的 Participation Call，形成“关闭额外 Put、持有另一组合 Call”的错误 group action scope。
- **直接证据**: `writer.py:310-340` 建立了全量 `records_by_id`，但校验只读取两个显式 id；插入前没有按 `strategy_group_id` 汇总成员。`position_advice_plan_builder.py:1404-1446` 以 group id 生成一个 state，`:430-447` 将该 state 应用于每个同 group position，`:952-999` 再从 identity 取得固定 call id。新增测试只构造两条 lot，没有额外成员或重复角色用例。
- **影响**: 一次 insert-only、需备份恢复的身份写入可把歧义历史元数据升级为正式组合事实，随后污染 Position Advice 的 group classification 和多腿操作计划。
- **建议改法和验证点**: 在同一 `BEGIN IMMEDIATE` transaction 内按 normalized group id 收集全部 projected lots，要求非终止 group 成员集合严格等于传入的两个 record id，并验证各角色唯一；存在额外、重复、残余或跨账户成员时 fail closed。新增 extra Put、extra Call、duplicate role、closed residual 和同 group 不同 symbol/account 测试，并断言零 identity 写入。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### 3-未修复-中-reconcile-due 只隔离 read-model 和 collector 异常，最终单案 reconciliation 仍可中断整批

- **入口/函数**: `reconcile_due_lifecycle_cases()` -> `reconcile_lifecycle_close_reason()`
- **文件(行号)**: `src/application/trades/close_reason_reconciliation.py:513-541,555-571,581-588`; `src/application/trades/close_reason_reconciliation.py:253-259`; `tests/test_settlement_observation.py:479-535`
- **输入场景**: 第一条 active v2 case 的 zero-price anchor 有合法 `received_at_ms`，因此 read model 能形成 `cause_pending`，但 `event_time_ms` 为非数字；当前时间已过 pairing window、尚未到 observation deadline。账户中还有其它合法 due cases。
- **实际分支**: 新增 try/except 能隔离 read-model conversion 和 collector 抛错，但 deadline 前不会调用 collector，随后直接在 try 之外调用 `reconcile_lifecycle_close_reason()`。该函数对 anchor execution time 执行 `int(...)` 并抛出 `ValueError`，整个 for-loop 退出，后续 case 不再处理。
- **预期行为**: 文档承诺 malformed active case 按 case 返回人工复核原因且不影响同批其它 case；所有单案数据校验阶段都应遵守这一边界。
- **实际行为**: 只有前两个阶段被隔离；最终 reconciliation 的可预期数据错误仍恢复为原来的 account-batch crash。
- **直接证据**: `close_reason_reconciliation.py:513-541` 和 `:555-571` 分别包住 read model 与 collector；`:581-588` 的最终调用没有异常边界；同文件 `:253-259` 存在直接整数转换。新增测试只覆盖 collector 主动抛 `RuntimeError`，没有“collector 返回后/无需 collector 时 reconciliation 抛错 + 后续 case 继续”的用例。
- **影响**: 一条历史 malformed anchor 仍可阻止同账户其它到期案件收敛，定时任务表现为整批失败；不会直接写错账，但会延迟结算确认并重复触发运维诊断。
- **建议改法和验证点**: 把单案 reconciliation 的 `TypeError`、`ValueError`、`OverflowError` 纳入 per-case fail-closed 结果，同时保留 SQLite/infrastructure/write-authority 异常为全局失败，避免掩盖系统故障。新增两 case 回归：第一条在最终 reconciliation 数据校验失败，第二条仍成功进入结果集。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
