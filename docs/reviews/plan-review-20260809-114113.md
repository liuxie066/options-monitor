# Plan Review — ai-decision-advice

- Reviewed target: `docs/gateflow/ai-decision-advice/plan-20260809.md`
- Scope: goal alignment, slice 划分、架构边界、合同完整性、执行语义、测试覆盖
- Method: adversarial plan review（planreview skill）

## Assumptions tested

1. 候选快照、portfolio context、ledger 投影可直接支撑四类冻结输入；
2. `service_deploy.py` timer 机制可承载 collector 调度；
3. diff/通知语义可扩展 AI 动作变化；
4. DeepSeek Responses adapter 可以独立窄实现；
5. slice 依赖顺序正确、各自可独立验收。

## Findings

### 1-未修复-高-“行业集中度”输入无数据源，plan 未说明
- **位置**: plan S4（contexts.py / projection.py）；设计文档 7.2、8、9.3
- **问题类型**: 契约缺失 / 不可直接实施
- **当前写法**: 设计文档要求向模型发送“标的、行业和币种权重”并投影“新增一张
  后的行业集中度变化”；plan 原样接受，未给数据来源。
- **反例/失败场景**: S4 实现时发现 `build_futu_portfolio_context` 只产出
  symbol/shares/currency/cost，完全没有 industry 字段；OpenD
  `get_stock_basicinfo` 返回列也不含行业（code/name/lot_size/exchange_type
  等，无 sector/industry）。实现者被迫三选一：省略行业（违反设计合同）、
  从 web 搜索推断行业（把非可信内容变成结构化输入，违反 11.3）、或引入新
  数据依赖（scope 扩张）。
- **直接证据**: `src/application/futu_portfolio_context.py:471-560` 的
  `stocks_by_symbol` 构造无 industry；futu SDK
  `.venv/.../open_quote_context.py:190-219` 的 basicinfo 列清单无行业；
  全仓 `rg "industry"` 在 src 下零命中。
- **影响**: S4 阻塞或静默降级设计合同；验收矩阵无法判定。
- **建议改法和验证点**: 在 plan 中显式裁决——v1 行业维度标注为
  `industry_unavailable`，输入只含 symbol/currency 权重与集中度；设计文档
  7.2/8/9.3 同步注明行业维度为后续扩展（如需行业，应另立数据真源 work
  unit，而非从搜索推断）。验证点：contexts 测试断言无 industry 键、
  projection 只输出 symbol/currency/expiry 集中度。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### 2-未修复-高-身份快照的持久化位置与生命周期未定义
- **位置**: plan S2（identity.py）；设计文档 5.1
- **问题类型**: 契约缺失 / 并发恢复风险
- **当前写法**: 设计文档要求“冻结 `symbol_identity_snapshot` 后再进入搜索
  批次”；plan 只说构建快照，未说写到哪里、谁读、跨批次是否复用。
- **反例/失败场景**: 快照若只存内存，collector 进程重启后重新逐标的调
  OpenD basicinfo，启动补刷场景放大 OpenD 调用；若存 JSONL，则需要与
  evidence 相同的追加/重建语义，plan 未给；若存 run 目录，则 collector 是
  跨 run 的常驻调度，归属矛盾。
- **直接证据**: `src/application/tick_run_workspace.py:266-336` 的
  no-follow 写入只覆盖 run/account 与 shared-required 目录；plan 未指定
  `output_shared/state/ai_decision_advice/` 下的身份快照文件名与 schema。
- **影响**: S2/S3 各自实现可能产生两份不一致的身份事实，违反设计文档
  “唯一真源”原则；S3 无法验证“先冻结身份再搜索”。
- **建议改法和验证点**: plan 明确 `symbol_identity_snapshot` 写入
  `output_shared/state/ai_decision_advice/symbol_identity_snapshot.json`
  （原子写、内容 hash），schema 含 code/market/exchange/name/aliases/
  observed_at；evidence 记录引用其 hash。验证点：identity 测试断言快照
  schema 与重写幂等；collector 测试断言证据记录携带身份 hash。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### 3-未修复-中-通知 diff 语义扩展点未定位到 domain 函数
- **位置**: plan S6（diff 语义扩展）
- **问题类型**: 不可直接实施
- **当前写法**: plan 说“diff 语义扩展（实质动作变化，含
  needs_review→keep）”，未指出改哪个函数、brief 结构中 AI 动作挂在哪。
- **反例/失败场景**: `diff_daily_decision_briefs` 位于
  `domain/domain/daily_decision_brief.py:566`，只比较 actionability 与
  actions 列表；AI 建议若不进入 brief 的规范化结构，diff 永远看不到变化，
  通知语义（设计文档 14）无法实现；实现者可能把 AI diff 塞进
  application 层平行实现，违反 domain 所有权。
- **直接证据**: `domain/domain/daily_decision_brief.py:566-616`；
  `daily_decision_brief_repository.py:1077` 的调用点。
- **影响**: 通知语义漏实现或错层实现。
- **建议改法和验证点**: plan 明确——brief 规范化结构新增
  `ai_decision_advice` 段（含每策略动作），`diff_daily_decision_briefs`
  增加动作变化比较（keep/switch/defer/needs_review 两两迁移均 material，
  unavailable 变化不 material）；domain 层改动 + domain 测试。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 4-未修复-中-collector 调度时区与“每 24 小时全量核对”基准未定义
- **位置**: plan S3；设计文档 6.1/6.2
- **问题类型**: 契约缺失
- **当前写法**: 设计文档写“每 4 小时刷新”“每 24 小时全量核对”，未说 UTC
  还是市场时区、从哪个时间点起算。
- **反例/失败场景**: 以本地时区实现则 US/HK 市场的“上次成功刷新”比较在
  夏令时切换时漂移；以进程启动时间起算则重启后全量核对节奏重置。
- **直接证据**: 仓库调度先例统一 UTC
  （`src/application/scan_scheduler.py:114,178` 全部 `timezone.utc`）。
- **影响**: 刷新节奏不可审计；验收矩阵“超过 8 小时”判断基准漂移。
- **建议改法和验证点**: plan 明确所有刷新/过期/全量核对时间一律 UTC，
  以证据记录中的 `last_success_at` 持久化字段为基准，与进程生命周期无关。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 5-未修复-中-候选提醒路径的 Advice 等待语义与 30s 预算关系未说明
- **位置**: plan S6；设计文档 13.1
- **问题类型**: 状态机漏洞
- **当前写法**: 设计文档说候选提醒“承载 unavailable”，plan 未说明候选提醒
  是否也等待 30s、还是直接读既有 Advice 产物。
- **反例/失败场景**: 候选提醒发生在非固定简报 tick；若每个候选提醒 tick 都
  触发一次 30s 模型调用，调用频率与预算语义失控；若不等待，则需要明确
  “只读最近一次固定简报生成的 Advice 还是当轮独立生成”。
- **直接证据**: `src/application/tick_notification_flow.py:900-990` 的
  candidate_alert 分支与 fixed_report 共用 brief 组装；设计文档 13.1 只说
  “模型仍基于完整候选判断”，未说等待。
- **影响**: S6 实现自由选择，可能导致模型调用频率超标或提醒永远缺 AI 段。
- **建议改法和验证点**: plan 明确——候选提醒路径同样运行 Advice（同一 30s
  账户预算），失败即 unavailable、提醒按原节奏发出；复用条件（13.2）在两
  条路径一致。验证点：编排测试覆盖 alert 路径的超时与复用分支。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 6-未修复-低-S7 渲染与 S6 编排的 brief view 契约未先行冻结
- **位置**: plan S6/S7
- **问题类型**: 切片耦合
- **当前写法**: S6 把 Advice 产物“挂进 brief view”，S7 消费该 view；view
  的字段契约没有在任何 slice 中先行定义。
- **反例/失败场景**: S6 定义的 view 字段与 S7 渲染需要的不一致（例如 CC
  聚合需要的 per-symbol 动作、引用候选、来源列表），S7 被迫回头改 S6。
- **建议改法和验证点**: plan 中先冻结 brief view 的
  `ai_decision_advice` 字段契约（schema、per-strategy 结构、unavailable
  表达），S6 生产、S7 消费都以该契约为准。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低
