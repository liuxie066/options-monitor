## Findings

### 1-未修复-高-snapshot 300 秒窗口在 fetch 时刻固化，候选决策时刻不重验

- **入口/函数**: `opend_symbol_fetching.fetch_symbol_request` -> `normalize_option_observation` -> `run_candidate_scan` 决策链
- **文件(行号)**: `src/application/opening_quote_evidence.py` (`normalize_option_observation` 的 `decision_at = _utc_now(now_utc)`、`snapshot_age_seconds` 计算); `src/application/opend_symbol_fetching.py:739-746`（调用点未传 `now_utc`）
- **输入场景**: OpenD snapshot 在 T 时刻取得并写入 required-data CSV；scan/候选决策在 T+Δ 时刻读取该 CSV 重算。生产 tick 中 fetch 与 scan 跨多个 symbol/策略，Δ 可能接近或超过 300 秒。
- **实际分支**: `normalize_option_observation` 在 fetch 时刻以 `decision_at = now()`（fetch 即时）计算 `snapshot_age_seconds ≈ 0`，`opening_contract_status` 因此固化为 `ready`；决策时刻（`run_candidate_scan`/`calculate_opening_candidate_metrics`）不再基于 `snapshot_received_at_utc` 与真实决策时间重算年龄，只读取已固化的 `ready` 状态。
- **预期行为**: 设计 §4.2 / §5 / 完成定义 #4 要求“超过 300 秒的是 OM 持有的 snapshot”，即 5 分钟窗口约束的是“取得 snapshot 到完成候选决策”的时间；当决策距 `snapshot_received_at_utc` 超过 300 秒时该合约应 `data_unavailable`。
- **实际行为**: `snapshot_age_seconds` 恒为 fetch 即时年龄（≈0），永远 `<= 300`，决策时刻的 300 秒窗口形同虚设；任何持有超过 300 秒的 snapshot 仍以 fetch 时刻的 `ready` 进入候选。仅有 payload 级 `SOURCE_MAX_AGE_SECONDS["quotes"]=1800`（30 分钟，`_validate_payload_freshness`）兜底，阈值与设计要求的 300 秒不一致，且不满足“OM 持有的 snapshot 超过 300 秒即不可用”的语义。
- **直接证据**: `opend_symbol_fetching.py:739-746` 调用 `normalize_option_observation(..., snapshot_received_at_utc=...)` 时**未传 `now_utc`**，故 `opening_quote_evidence.py` 中 `decision_at = _utc_now(None) = now()` 为 fetch 时刻；`snapshot_age_seconds = decision_at - snapshot_received ≈ 0`。`candidate_models.py`/`candidate_scanning.py` 在决策时刻只透传 `snapshot_received_at_utc`/`snapshot_age_seconds`，不重算年龄；`calculate_opening_candidate_metrics` 只检查 `opening_contract_status == "ready"`（fetch 时刻快照）。
- **影响**: 5 分钟取得新鲜度门槛在真实决策路径上失效，陈旧 snapshot（>300 秒）可被当作新鲜候选放行，直接削弱本次改动声称的核心安全保证；在慢 symbol/大批量 tick 下风险真实存在。
- **建议改法和验证点**: 将 300 秒校验绑定到真实决策时刻：在 `run_candidate_scan`/`calculate_opening_candidate_metrics` 决策入口以决策 `now_utc` 与 `snapshot_received_at_utc` 重算 `decision_age_seconds`，>300 秒即 `evidence_unavailable`（fail closed），不再只信任 fetch 时刻固化的 `opening_contract_status`；payload 层把 quotes 的可用窗口与 300 秒对齐或明确分工。验证点：构造 `snapshot_received_at_utc` 距决策时刻 >300 秒的 required-data，断言该合约在决策时被判 `evidence_unavailable` 而非 `ready`。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### 2-未修复-中-publish_strategy_scan_status 丢弃 completed 状态的 reason，partial_data/no_candidate 在持久化 status 中丢失

- **入口/函数**: `symbol_monitoring._publish_status` -> `publish_strategy_scan_status` -> `strategy_scan_status_index` -> Daily Brief `_append_strategy_status_gaps`
- **文件(行号)**: `src/application/strategy_scan_status.py:121-124`（`if status_norm == "completed": payload["candidate_count"]=... else: payload["reason"]=...`）
- **输入场景**: 某 scope 零候选且 `evidence_unavailable_count>0`，`symbol_monitoring` 以 `status="completed", reason="partial_data"`（或 `no_candidate`）调用 `_publish_status`。
- **实际分支**: `publish_strategy_scan_status` 对 `completed` 只写 `candidate_count`，`reason` 仅写入非 `completed` 分支；持久化 JSON 与 `strategy_scan_status_index` 中 `completed` 状态的 `partial_data`/`no_candidate` reason 被静默丢弃。
- **预期行为**: 设计 §7.2 要求 scope 状态可区分 `no_candidate`（合法不入选）与 `partial_data`（部分证据不可用）；该区分应能通过持久化 scan status 供 Daily Brief 等下游一致解释。
- **实际行为**: 内存路径（`_report_capture` -> opening snapshot `_strategy_results`）保留 reason 且能正确投影 `partial_data`；但持久化 `strategy_scan_status.v1` JSON 与索引丢失 `completed` 的 reason，使依赖该 JSON 的下游（Daily Brief `_append_strategy_status_gaps`、运维排查）只能看到 `completed`，无法区分合法空与部分证据缺失。Daily Brief 当前主要靠 opening snapshot 的 `strategy_status`（`partial_data` 已是独立 status）规避，但 scan-status JSON 这一事实源与新语义不一致。
- **直接证据**: `strategy_scan_status.py:121-124` 条件分支；`symbol_monitoring._completed_scan_status` 返回 `("completed", "partial_data"|"no_candidate")`；`_publish_status` 将该 reason 透传给 `publish_strategy_scan_status`，后者在 `completed` 分支丢弃。
- **影响**: 持久化 scan status 与 opening snapshot 两个事实源对同一 scope 的语义不一致；下游/排障无法从 scan-status JSON 判断零候选是“合法无候选”还是“证据不完整”，observability 缺口。
- **建议改法和验证点**: 在 `publish_strategy_scan_status` 允许 `completed` 状态持久化受限 reason 集合（`no_candidate`/`partial_data`/`market_closed`），并在 index/daily brief 读取处透传；保持 success_empty 校验不回归。验证点：对 `completed`+`partial_data` 的 scope 断言 scan-status JSON 含 `reason=partial_data`，且 Daily Brief 能据此区分。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
