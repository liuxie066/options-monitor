## Goal and boundary understood

The plan must stop duplicate expiry receipts while preserving broker and ledger correctness. A zero-price
option close proves the option leg has closed, but the final reason may remain pending until matching stock
settlement or a complete post-deadline no-settlement observation exists. Push and Poll must converge on one
broker identity; the canonical lifecycle/ledger remains the only financial-fact authority; notification
intents must be durable and transition-driven.

## Re-review of previous findings

1. **No-settlement evidence contract — addressed**: the plan now defines a frozen
   `broker_settlement_observation.v1`, required sources, account/time coverage, source receipts,
   completeness and fail-closed behavior.
2. **Timing policy — addressed**: the plan adds immutable timing bindings, exact two-business-day
   semantics, missing-policy review behavior and removes quality's independent deadline fallback.
3. **Parallel state authority — addressed**: closure fact and reason state are derived read-model fields;
   existing lifecycle case/evidence/allocation/ledger remains canonical.
4. **Outbox atomicity — addressed in principle**: the plan places notification intent in the ledger
   transaction and defines claim, send-started, unknown, suppression and manual reconciliation behavior.
5. **Migration safety — addressed**: the plan defines inventory, explicit manifests, one-to-one mapping,
   ambiguity isolation, suppression-before-dispatch, dry-run/apply/replay/audit and rollback boundaries.

## Assumptions tested

1. A pending zero-price option close can be represented without prematurely selecting a terminal reason.
2. The canonical projection can prove broker option absence before the terminal reason event is written.
3. Every consumer of open lots will honor the pending lifecycle reservation.
4. One canonical close event corresponds to one ordinary broker close and therefore one receipt.
5. A broker close split across multiple target lots retains one notification identity.
6. Void/repair of a terminal lifecycle event also removes its allocation from the effective read model.
7. Late corrective evidence can obtain remaining allocation quantity after the original event is voided.
8. Timing policy and settlement observation are immutable and account-bound.
9. Incomplete broker coverage cannot produce `expiration_no_settlement`.
10. Inbox can safely finish after evidence acceptance because all later progress is lifecycle-owned.
11. Outbox crash boundaries freeze uncertain delivery instead of resending.
12. Migration suppression is installed before any live dispatcher can observe pending intents.

## Special review lenses

### Architecture boundary review

The plan now places domain policy, evidence assembly, canonical ledger writes and delivery in appropriate
owners. The remaining architecture defect is inside the ledger boundary: the plan has not decided how
“option leg closed but reason pending” relates to canonical open-lot projection, and the correction path
does not connect voided terminal events to effective lifecycle allocations.

### Best-practice review

The evidence and Outbox contracts now follow fail-closed and transactional patterns. However, a state
machine is not implementation-ready when one transition requires a postcondition that can only be created
by that same transition. Aggregate operation identity must also be distinct from per-lot event identity.

### Optimal-solution review

The safest minimal path is to reuse the existing pending lifecycle reservation: keep target lots in the
canonical projection until the reason event closes them, expose them as non-actionable through one read
model, and require that every consumer respects that reservation. Adding a provisional economic close
event would introduce a new ledger event and later reversal problem. For corrections, reuse the existing
`void_event_ids` capability in allocation resolution rather than adding mutable allocation deletion.

### Overengineering review

The new observation and Outbox contracts are justified by the incident's failure modes. No material
overengineering finding remains. A provisional close event or second lot projection would be
overengineering and should not be introduced to repair Finding 1.

### Overcoupling review

The plan correctly keeps the resolver pure. The ordinary close notification identity still couples one
user-visible receipt to one per-lot ledger event, even though the existing close writer deliberately splits
one broker deal across several events. That coupling would recreate duplicate messages at a different key.

## Findings

### 1-未修复-严重-`option_leg_closed` 与 canonical projection 的前置条件互相矛盾，自动到期无交割无法合法落账

- **位置**: 第 6.1-6.4 节单一事实模型、第 9.3 节 `complete=true`、第 11.4 节原子写入
- **问题类型**: 状态机漏洞 / 架构边界 / 不可直接实施 / 契约缺失
- **当前写法**: 零价 option-close evidence 可以先让 `closure_fact=option_leg_closed`，原因仍为
  `cause_pending`；assignment、exercise 或 expire_close 的 terminal event 在原因收敛时才写。
  但 `expiration_no_settlement` 的完整 observation 又要求 broker position 和 canonical
  projection 在 terminal 写入前都已经显示 option quantity 为零。
- **反例/失败场景**: 到期零价 option deal 被 Inbox 接受，没有股票腿。Lifecycle case 与
  option-close evidence 已存在，但尚未生成 `expire_close`。Canonical `position_lots` 由
  `trade_events` 投影，因没有 close/assignment/exercise/expire_close event，target lot 仍有
  `contracts_open > 0`。第二营业日 observation 的 broker position 已消失，但 plan 的
  “canonical projection 为零”条件失败，因此 resolver 永远不能生成本应使 projection 归零的
  `expire_close`。
- **为什么有问题**: 这是循环前置条件。Implementation agent 只能在三种错误方向中自行选择：
  提前把零价成交写成 `expire_close`、新建一个 provisional close event，或忽略 plan 的
  projection-zero guard。第一种重新引入错误原因，第二种形成双重 close/修复复杂度，第三种违反
  plan 的完整性契约。
- **直接证据**:
  - 计划第 97-104 行允许 option-close evidence 在原因未定时形成 `option_leg_closed`。
  - 计划第 119-128 行规定只有最终 reason 才映射至 `close`、`assignment`、`exercise` 或
    `expire_close` ledger event。
  - 计划第 377-390 行要求 terminal 写入前 canonical projection 已为零；第 600-611 行又把
    terminal event 与 projection 更新放在最终原子事务。
  - `domain/domain/ledger/events.py:11-13` 只有 close/expire_close/assignment/exercise
    会关闭 lot。
  - `src/application/trades/lifecycle.py:186-199` 当前 pending zero-price 路径只存 case/evidence，
    不写 terminal event。
- **影响**: 自动 `expiration_no_settlement` 可能永远不发生；或实现者为满足条件而提前写错误的
  expire_close，导致 assignment/exercise 迟到时冲突、仓位双重关闭或收益事实错误。Pending lot
  若没有被所有消费面统一标为 non-actionable，还可能继续进入 Close Advice。
- **建议改法和验证点**:
  - 明确采用现有 pending lifecycle reservation：原因收敛前 canonical lot 保持原剩余数量，
    但 read model 将 target lot 标为 `option_leg_closed` 且 `actionable=false`。
  - 将 no-settlement 的 ledger 前置条件改为“projection remaining 与 case frozen target
    remaining 一致且未被其它 event 消费”，而不是 projection 已为零；terminal transaction
    写入 `expire_close` 后才验证 projection 为零。
  - 列出并修改所有 open-lot 消费者，至少包括 position context、Close Advice、报告与质量检查；
    它们必须使用同一 lifecycle reservation，不能直接把 pending target 当作可操作 open lot。
  - 测试从 zero-close evidence -> pending non-actionable -> complete observation ->
    expire_close -> projection zero 的完整顺序，并证明 pending 阶段没有交易建议。
- **修复风险（低/中/高）**: 高
- **严重程度（低/中/高/严重）**: 严重

### 2-未修复-高-普通平仓用 per-lot event id 作为 notification case，会把一笔 broker deal 再次拆成多条回执

- **位置**: 第 11.2 节普通主动平仓 notification case id、第 11.4 节普通 close 原子 Outbox
- **问题类型**: 幂等身份错误 / 过度耦合 / 用户可见重复 / 测试缺口
- **当前写法**: 普通主动平仓使用 `close:<canonical_close_event_id>` 作为 notification case id，
  并为普通 close 创建一条最终 Outbox。
- **反例/失败场景**: 一笔 Futu close deal 关闭同一合约的两个 FIFO target lots。现有 writer
  把源 deal 按 target lot 拆成两个 canonical close events，每个 event id 不同。若每个
  `canonical_close_event_id` 都生成 notification case，就会产生两条“主动平仓”回执，虽然
  Push/Poll broker deal identity 只有一个。
- **为什么有问题**: Ledger event grain 是 target lot，通知 grain 是 broker operation。
  把两者绑定为同一个 identity，正好绕过了 plan 已解决的 broker deal 去重，并重现本次事故的
  用户可见症状。
- **直接证据**:
  - 计划第 566-570 行将普通 notification case 定义为
    `close:<canonical_close_event_id>`。
  - `src/application/ledger/commands.py:386-449` 验证一个 source deal 的总数量后，按每个
    `match` 生成 split deal 和独立 event。
  - 同一代码第 426-432 行已经保存
    `source_deal_id/split_count/split_index`，证明一个 broker operation 可以对应多个 ledger
    events。
- **影响**: 一笔普通平仓跨多个 lot 时会重复发飞书；Outbox 唯一约束无法阻止，因为 case id
  本身不同。通知统计也会把一个操作错误计为多个案件。
- **建议改法和验证点**:
  - 普通平仓 notification subject 使用 account-scoped canonical broker deal key：
    `close:<futu:account:futu_account_id:deal_id>`，而不是 per-lot event id。
  - 一个 transaction 完成全部 split close events 和 projection 后，只创建一个 aggregate
    Outbox；payload 冻结 ordered event ids、target lots 和总 contracts。
  - 缺少 canonical broker key 时，账本可以按现有安全规则处理，但自动通知进入 review/suppressed，
    不退化为 raw deal id 或每事件通知。
  - 增加一笔 deal 关闭 2/3 个 lots、重放相同 deal、不同账户同 raw deal id 的测试，均应只有
    一个 final intent。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### 3-未修复-高-迟到证据的 void/repair 只描述操作口径，没有让旧 lifecycle allocation 退出有效解

- **位置**: 第 9.4 节迟到证据、第 12 节人工复核、`resolution_corrected`
- **问题类型**: 状态机漏洞 / 修复不可执行 / 数据一致性 / open question 未收敛
- **当前写法**: expire_close 后到达 assignment/exercise 时进入 conflict；operator 通过受控
  void/repair 和 projection replay 修正，然后用更高 revision 发送结果更正。人工 evidence
  append-only，不能删除旧 evidence。
- **反例/失败场景**: 一张 Short Put 已分配 `expire_close` allocation，之后迟到的股票交割证明
  assignment。Operator void 原 expire_close trade event，projection 恢复 lot；但原 allocation
  row 仍存在。Lifecycle read model 如果继续统计该 allocation，remaining quantity 仍为零；
  新 assignment evidence 无数量可分配，或与旧 terminal type 形成 mixed/conflict，无法达到
  corrected resolution。
- **为什么有问题**: Trade-event void 与 lifecycle-allocation effectiveness 是两个模型。
  Plan 没有规定 authoritative void event ids 如何进入每个 allocation resolver/read model/writer，
  也没有定义 correction transaction 的顺序和 postconditions。仅写“void/repair”会把核心设计留给
  implementation agent。
- **直接证据**:
  - 计划第 392-401 行只规定 operator 流程结果，没有 allocation invalidation contract。
  - 计划第 671-681 行要求 append-only manual evidence，但未说明旧 allocation 的 effective 状态。
  - `domain/domain/lifecycle_allocation.py:117-138` 已支持传入 `void_event_ids` 后忽略相应 allocation，
    这是可复用的最小机制。
  - `domain/domain/option_lifecycle.py:141-152` 和
    `src/application/trades/lifecycle_reconciliation.py:103-106` 当前调用
    `resolve_allocations()` 时没有提供 void event ids。
  - `src/application/ledger/repository.py:278-294` 的 allocation row 没有 mutable status 或
    supersession 字段。
- **影响**: 方案承诺的迟到证据纠正无法收敛，case 会长期 conflict；若实现者直接删除/改 allocation，
  又会破坏 append-only 审计和 migration replay。
- **建议改法和验证点**:
  - 复用现有 `void_event_ids` 参数：ledger facts query 从 canonical void events 计算 effective
    voided terminal event set，并传给所有 read model、allocation planning、writer preflight、
    context builder、quality 和 migration replay。
  - Correction transaction 先验证原 terminal event 已被合法 void，再基于排除旧 allocation 后的
    remaining quantity 写新 evidence、terminal event、allocation、projection、revision 和
    correction Outbox。
  - 原 allocation row 保留，不 UPDATE/DELETE；其无效性由 canonical void chain派生。
  - 测试 expire_close -> void -> assignment、assignment -> void -> expire_close、partial allocation
    correction、重复 correction 和 projection replay。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高
