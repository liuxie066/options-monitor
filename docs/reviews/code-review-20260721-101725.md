## Findings

### ADR-01 — Futu split pagination can overclaim complete coverage while unread pages remain

- **Severity**: P1
- **Location**: `src/application/events/source_futu.py:103-115,205-221`
- **Entry point**: `fetch_symbol_event_evidence_futu()` through run-level event prefetch.
- **Triggering input**: `get_corporate_actions_stock_splits()` returns a non-terminal `next_key` on the last allowed `split_pages` request.
- **Actual branch**: `_fetch_split_rows()` exits the bounded loop and returns collected rows even though another page is advertised; the caller then sets `coverage["split"].status = "complete"`.
- **Expected behavior**: Any unconsumed provider page must make split coverage partial/unknown so Daily Brief cannot confirm event absence from incomplete evidence.
- **Actual behavior**: The truncated result is persisted as successful complete split coverage. If the other event categories are also complete and no fetched event remains upcoming, `build_candidate_event_risk()` can produce `confirmed_none`.
- **Direct evidence**: The loop has no post-loop exhaustion check, while `build_candidate_event_risk()` treats all three `complete` statuses plus an empty event list as authoritative absence.
- **Impact**: A candidate may tell the user that no important event is confirmed even though an unread split page exists, violating the fail-closed product contract and the zero false confirmed-absence success metric.
- **Fix direction**: Detect loop exhaustion with a non-terminal `next_key` and raise into the existing per-category partial-coverage path; add a regression proving truncated pagination cannot be complete.
- **Fix risk**: Low. The change only downgrades evidence when the adapter can directly prove pagination is incomplete; fully exhausted pagination and the public list-returning compatibility API remain unchanged.
