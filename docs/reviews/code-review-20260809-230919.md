### DR-S5-01-未修复-高-刷新队列未消费历史尝试时间，大观察集中后置标的可永久饥饿
- **入口/函数**: `run_managed_collector()` -> `RefreshQueue.build()` -> `run_evidence_collector()`
- **文件(行号)**: `src/application/ai_decision_advice/managed_collector.py:140-148,167-207`; `src/application/ai_decision_advice/collector.py:434-442`
- **输入场景**: 同一 priority tier 的 symbol 数量超过一轮预算能处理的数量，前几个 batch 每轮都用完 5 分钟预算。
- **实际分支**: managed runner 在读取 evidence history 之前使用 `RefreshQueue.build(observed)`，没有传入 `last_attempt_by_symbol`；下一轮仍按 priority + symbol 固定顺序从头开始。
- **预期行为**: 同层内最久未成功/未尝试的 symbol 优先，未完成项在下轮重试，已完成的前置 symbol 不应每轮抢占相同预算。
- **实际行为**: 后置 symbol 没有 status 或 evidence snapshot，但排序也不会因此提前；前置 batch 可在每个 4 小时周期重复刷新。
- **直接证据**: `RefreshQueue.build()` 已有 `last_attempt_by_symbol` 语义，但唯一真实 service caller 在第 147 行未传入；evidence records 到第 167 行才读取；collector 在 deadline 后只将后续 batch 加入当轮 `unfinished_symbols`，没有跨轮队列真源。
- **影响**: 有开放期权或持仓的真实标的可长期处于 `no_evidence`，AI Advice 无法覆盖它们，而 timer 持续正常运行。
- **建议改法和验证点**: 先读取 evidence status，以最新 `last_checked_at`/`last_success_at` 构建 `last_attempt_by_symbol`后再建 queue；增加两轮回归，证明第一轮预算耗尽后第二轮会先处理尚未成功的同层 symbol。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### DR-S5-02-未修复-高-单个 DeepSeek batch 异常会中断整轮并跳过失败状态持久化
- **入口/函数**: `run_evidence_collector()` -> `_call_with_repair()` -> injected/DeepSeek `model_runner`
- **文件(行号)**: `src/application/ai_decision_advice/collector.py:486-530,543-586`; `src/interfaces/cli/ai_evidence_collector.py:30-46`
- **输入场景**: 第一个 batch 发生 network timeout、HTTP error 或 adapter exception，后面仍有可处理 batch，且该 symbol 有一份可保留的旧成功快照。
- **实际分支**: `_call_with_repair()` 在第 569 行直接调用 runner，没有把 provider exception 转成 batch failure；异常穿透到 service wrapper 才被统一捕获。
- **预期行为**: 当前 batch 记录失败、保留旧 success snapshot，然后在剩余预算内继续后续 batch。
- **实际行为**: 本轮已组装的 records 未 append，当前 symbol 没有新的 failed status，后续 batch 不执行，wrapper 只返回无 symbol 细节的 `collector_error`。
- **直接证据**: runner 调用不在 `try` 内；只有 JSON/shape error 被处理；`append_evidence_records()` 位于所有 batch 完成后；CLI 的外层 catch 不能恢复 symbol 状态机。
- **影响**: 一个短暂 provider 错误扩大为整轮失败，运行诊断无法区分哪些 symbol 失败，已有部分成功结果也可因未 append 而丢失。
- **建议改法和验证点**: 在 batch 边界捕获 provider exception，转成该 batch 的 failed symbols，不持久异常文本；继续后续 batch。测试第一 batch raise、第二 batch 成功，并验证失败 status 不遮蔽旧 success。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### DR-S5-03-未修复-高-OpenD 全市场失效会被报为 collector 成功
- **入口/函数**: systemd internal wrapper -> `run_managed_collector()` -> `_opend_market_snapshot_provider()` -> identity skip path
- **文件(行号)**: `src/application/ai_decision_advice/managed_collector.py:157-165,205-230,267-308`; `src/application/ai_decision_advice/collector.py:443-463`; `src/interfaces/cli/ai_evidence_collector.py:47-48`
- **输入场景**: `futu-api` 不可导入、OpenD 连接失败、snapshot 返回错误，或一次未分批的 market snapshot 请求失败。
- **实际分支**: provider 对所有异常和非 `RET_OK` 统一返回 `{}`；identity 将所有 symbol 标成 `identity_unavailable`；collector 又把这些 symbol 追加到 `completed_symbols`；managed runner 无条件返回 `status=completed`，wrapper exit 0。
- **预期行为**: identity unavailable 应与搜索 completed 分开计数；整个观察集都无法建立身份时，service 应显式报 failed/degraded，而不是绿色成功。
- **实际行为**: 可以长期一条证据都不更新，systemd 每 4 小时仍记录成功退出，summary 还会将全部失败身份计为 completed。
- **直接证据**: provider 的 import/call/return-shape 错误分支均 `return {}`；collector 第 462 行对 skip 执行 `summary.completed_symbols.append(symbol)`；managed 第 218 行不检查 summary；wrapper 把 `completed` 视为 exit 0。
- **影响**: 用户最担心的“持续无数据导致没有结果”会被运行状态掩盖，无法通过 service 健康及时发现。
- **建议改法和验证点**: 在 summary 中单独记录 `identity_unavailable_symbols`；仅完成可归因搜索才计 completed；全部不可用时返回非零状态，部分不可用时返回可审计 degraded/partial。OpenD 调用收敛到现有 infrastructure gateway 并按现有 200-code 上限分批，增加 import/network/RET error 和部分 batch 回归。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### DR-S5-04-未修复-中-Responses 顶层非 completed 状态未校验，可被提升为成功证据快照
- **入口/函数**: `build_deepseek_evidence_runner()` -> Responses extraction -> `_search_audit_complete()`
- **文件(行号)**: `src/application/ai_decision_advice/managed_collector.py:54-96`; `src/infrastructure/deepseek_responses.py:95-120,152-220`
- **输入场景**: DeepSeek 返回顶层 `status=incomplete` 或 `failed`，但 output 中恰好存在可解析的完整 JSON 片段和已 completed 的 search call。
- **实际分支**: adapter 不读取顶层 `status`，直接提取 output/usage/search/citation；collector 只检查结构与 search-call 计数。
- **预期行为**: 非 `completed` Responses 必须在 provider adapter 边界 fail closed，不得产生 successful symbol status。
- **实际行为**: 不完整 provider response 可通过所有当前 validator 并写入 `last_success_at`/active refs。
- **直接证据**: `create_deepseek_response()` 返回原 payload；runner 第 81-96 行未检查 `response.status`；search audit 只遍历 output items。DeepSeek 官方 Responses 合同明确存在 `completed`/`incomplete`/`failed` 终态。
- **影响**: cutoff 与证据完成审计不再能证明整个 provider 执行无错，与“证据覆盖完成”的确定性边界相冲突。
- **建议改法和验证点**: adapter 在提取内容前要求顶层 status 严格等于 `completed`；测试 `incomplete` + 形式完整 output 仍进入 batch failed，且不生成 success status。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
