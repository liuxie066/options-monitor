## Assumptions tested

1. **同一 run 的市场事实可以在账户 pipeline 前冻结一次**：成立。plan 把 planning、fetch、multiplier enrichment、receipt 和 terminal manifest 置于同一 producer boundary，并禁止 frozen consumer 再 discovery、fetch 或 write。
2. **direct Sell Call 的账户持仓需求不会被第一个账户的 plan 截断**：成立。base demand 与每个 ready prepared context 进入 order-independent union，且复用现有 side-plan merge 与 effective min-strike 规则。
3. **前置 portfolio context 不会无限阻塞整点 run**：成立。plan 将当前未实际生效的 `portfolio_timeout_sec` 明确定义为所有 scanning accounts 共享的 monotonic absolute deadline；对不可取消的 gateway I/O 使用可 terminate/kill 的 subprocess，并隔离 child 写入和迟到结果。
4. **partial failure 不会因其它成功策略恰好 0 candidates 被误判为 blocked**：成立。plan 新增完整 expected `strategy_scan_status_index.v1`，以 execution availability 而不是 candidate row count 聚合，并把 completed/0 明确定义为 available。
5. **数据缺口不会被持久化或渲染成 candidate invalidation**：成立。plan 在 repository lock 内用纯 domain reconciliation 保留同 action identity 的 evidence hold，并定义 active/unavailable/recovered/absent 的完整 diff 状态机。
6. **full manifest failure 即使不启动 account pipeline 仍能进入现有 fixed-failure path**：成立。plan 明确 synthetic per-account result、metrics、scheduled target、`ran_pipeline_accounts=[]` 和 `pipeline_succeeded=false`，没有复用 `ran_scan=true` 伪装实际执行。
7. **新增契约不会改变普通 manual/dev pipeline**：成立。frozen semantics 只由显式 manifest 参数启用，原 `--shared-required-data` 和 legacy fetch path 保持兼容。

## Special review lenses

- **Architecture boundary**: run barrier、required-data snapshot、symbol scan、Daily Brief service、repository/domain diff 的 ownership 分离清楚。application 层持有 manifest/process orchestration，domain 只持有纯 evidence reconciliation/diff，未形成 `domain -> src` 反向依赖。
- **Best-practice**: monotonic absolute deadline、killable worker、parent-only publish、payload/receipt/manifest commit marker、per-family output commit marker、expected index 和 typed terminal outcomes覆盖了 timeout、late write、partial commit、empty success 与 full failure。
- **Optimal solution**: 对当前无 application deadline 且不可可靠取消的 OpenD/Futu 查询，窄 subprocess 比遗留 background thread 或为每账户重置 timeout 更可控；复用现有 receipt、runtime config helper 和 repository lock，避免新数据库或第二套 candidate lifecycle。
- **Overengineering**: 新增两个窄 schema 和一个 context worker 模块都有直接 failure mode 支撑；plan 明确排除 option context/FX 冻结、通用 snapshot framework、新配置键和新 retry policy，范围仍受控。
- **Overcoupling**: frozen path 通过显式 manifest 连接 producer/consumer；strategy status index只表达 availability 和 artifact binding；evidence hold复用既有 action identity。legacy path、通知路由和 material threshold 不被强绑到新实现。

## Residual risks and suggested tracking

- **Concurrent broker sessions**: context preparation 会为每个 configured scanning account 同时启动 child。当前账户集合很小且这是避免顺序饥饿的必要代价；在 `tick_metrics` 跟踪 child count、duration、exit reason。如未来账户数显著增加，再基于观测单独设计有界批处理，不在本 work unit 预先泛化。
- **Process termination portability**: `terminate -> short grace -> kill` 的具体 grace 值属于实现常量，应由 deterministic fake-worker tests 覆盖 macOS/Linux 行为，并记录残留 PID 检查；不需要新增生产配置键。
- **Legacy-path guarantees**: 未传 frozen manifest 的 manual/dev pipeline仍允许补取，因此不具备同一 run 跨账户不可变保证。这是 plan 明确保留的兼容边界，应在 handoff 文档中持续说明。
- **Live provider behavior**: 本 review 只证明计划契约，不证明真实 OpenD 在 terminate 时的所有驱动行为。实施后先用 blocking fake 和 no-send run 验证，再将任何 live canary 作为单独授权的运维动作。
- **Receipt age**: 长耗时账户 pipeline 可能逼近 receipt freshness窗口。按 plan 记录 seal-to-consume latency，并在 focused test 中覆盖预期最大 pipeline duration；若实际超过窗口，再单独调整 freshness policy。

## Final conclusion

**pass-with-risks**

第二轮四项 finding 已被具体且可测试的契约关闭：context barrier 有共享绝对时限和迟到隔离，partial 聚合不再依赖 candidate row count，evidence-unavailable 有可持久化的身份状态机，full failure 有 notification flow 可直接消费的账户结果表。当前方案可以交给 implementation agent；剩余风险均可在实施测试和 no-send 验证中跟踪，不构成设计 blocker。
