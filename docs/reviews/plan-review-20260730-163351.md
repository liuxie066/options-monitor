# Plan Review

## Reviewed target and scope

- Target: `docs/plans/daily-brief-local-gap-degraded-delivery-plan-20260730.md`
- Review mode: adversarial implementation-plan review
- Scope:
  - typed option-chain outcome；
  - `success_empty` 零行 quote snapshot；
  - symbol-local provider error degradation；
  - candidate capture/source evidence chain；
  - Close Advice/open-position exclusion boundary；
  - Daily Brief reliability 和现有 notification flow；
  - implementation slices 与验收矩阵。
- Excluded:
  - 代码实现 review；
  - 生产运行验证；
  - 真实通知；
  - 对方案的修改。

## Goal, boundary, and assumptions tested

方案目标是只让 opening candidate scan 中有充分证据的局部期权链缺口进入正常或 degraded
Daily Brief，同时保持持仓、完整性和账户级可信度问题继续使用 `fixed_failure`。

本次尝试证伪以下关键 assumptions：

1. `success_empty` 可以沿用现有 quote receipt 并安全穿过候选扫描；
2. candidate capture v2 的 degraded 判定可以在 candidate source 继续保持 v1 时被下游可靠证明；
3. optional strategy status/prefetch read-model 足以承载 degraded authority；
4. 仅调用 `load_close_advice_required_data_plan()` 足以证明持仓 required-data exclusion；
5. Close Advice 禁用可以安全解释为无需 position overlap 检查；
6. 同 run、同 endpoint/market 的任意成功 response 足以证明另一个 provider error 是局部错误；
7. 现有 notification persistence 和 retry 不需要修改。

## Mandatory review lenses

### Architecture boundary review

`success_empty` 复用 fetch owner、quote snapshot 和既有 completed-zero strategy 路径，ownership
清楚。主要架构缺口在 degraded evidence：capture v2 是 Account Run 的可靠性裁决，但 candidate
source v1 发布后丢弃该裁决；Daily Brief 随后依赖 optional、未被 source manifest 采用的 read-model。
Close Advice exclusion 也指定了不具备 frozen-manifest binding 的 reader。

### Best-practice review

成功空结果使用正向 provider evidence，而不是从文件为空反推，符合 fail-closed 和可测试性要求。
但 provider-error 降级缺少 immutable adopted proof，并且 provider peer 没有时间方向，无法证明
错误发生时 provider health domain 仍然健康。

### Optimal-solution review

删除 eligibility catalog、consumer projection 和跨批次告警状态机是正确收缩。
`success_empty` 可以继续作为独立、低耦合 slice。对于 provider error，最小安全替代不是恢复之前
全部 coverage 模型，而是增加一个窄的 account-scoped degraded coverage proof，或将该 proof
纳入 candidate source v2；继续使用 candidate source v1 不是可审计的最小闭环。

### Overengineering review

未发现新的状态机、存储层、后台服务或无当前需求支撑的抽象。方案在这方面已经明显收敛。
剩余 findings 要求的是补齐现有安全声明所必需的证据，不是扩大产品范围。

### Overcoupling review

方案为了保持 candidate source v1，把可靠性裁决分散到 capture v2、strategy status index、
prefetch summary 和 Daily Brief assembler，导致一个降级决策必须依赖多个未统一采用的 artifact。
同时 source publisher 直接接收 Close Advice plan path，却没有使用已经存在的 manifest-bound
解析边界。这些耦合会让局部实现需要跨模块自行重建事实链。

## Findings

### 1-未修复-高-candidate source v1 丢弃 degraded coverage 证据，normal authority 无法证明被省略 scope 合法

- **位置**: 第 6.4 节 Candidate capture、第 6.5 节 Candidate source、第 6.6 节 Daily Brief
- **问题类型**: 架构边界 / 契约缺失 / 过度耦合 / 不可直接实施
- **当前写法**: capture v2 负责验证 expected scopes、局部 provider error 和
  `reliability=degraded`；随后仍发布 `position_advice_candidate_all_decisions.v1`，只保存可靠
  decision rows 和 quote dependencies。缺口事实改由 strategy status index 和 required-data
  summary 进入 Daily Brief。
- **反例/失败场景**: 账户有 A、B 两个 opening scopes。A 有可靠 quote，B provider error。
  capture v2 正确判定 degraded，但 candidate source v1 只发布 A 的 decisions/quote。之后
  `strategy_scan_status_index.v1.json` 缺失、损坏、被旧 writer 覆盖，或 summary 与 manifest
  不一致。source manifest 仍把 candidate source v1 验证为完整 quotes-derived source；
  Daily Brief 对 status index 和 prefetch summary 都按 optional artifact 读取，不能从 adopted
  source graph 证明 B 是 allowlisted unavailable，而不是 expected scope 静默丢失。
- **为什么有问题**: 方案的核心安全声明是“只有被验证的局部 gap 才能正常发送”，但负责该声明
  的 capture v2 没有被发布、采用或绑定到 candidate source receipt。下游得到的是与旧 complete
  run 无法区分的 v1 candidate source。optional read-model 只能用于展示，不能补充 notification
  authority。
- **直接证据**:
  - 计划第 247-259 行把 degraded 裁决放在 capture v2，却允许 publisher 继续输出 source v1；
    第 269-280 行明确不向 candidate source 增加 coverage dependency。
  - `position_advice_source_producers.py:123-192` 的 candidate source payload 只包含 decisions、
    count、risk policy hashes 和 quote snapshot ids，没有 expected/degraded scopes 或 capture
    digest。
  - `position_advice_source_receipts.py:38-41,273-287` 只要求 candidate source 依赖 quotes。
  - `daily_decision_brief_service.py:418-440` 把 prefetch summary 和 strategy status index 都作为
    `required=False` 读取；`:2316-2361` 只检查 index 的 schema/run/account/items，没有 adopted
    receipt 或 manifest dependency。
- **影响**: expected scope 丢失或 degraded evidence 漂移时仍可能形成正常 notification
  authority；implementation agent 必须自行发明跨 artifact join 或原地改变 v1 语义，造成
  fail-open、schema drift 或后续返工。
- **建议改法和验证点**:
  - 为 provider-error degraded 增加最小 account-scoped immutable proof，并让 candidate source
    receipt 精确依赖它；或升级为 candidate source v2，直接包含 expected scope set、
    reliability、degraded scope refs 和 sealed manifest digest。
  - Daily Brief 只能从已 adopted proof 投影 authority；strategy index/summary 保留为 read-model。
  - 测试删除、篡改、跨 run 替换 status index/summary 时，adopted proof 仍能决定 degraded；
    缺失或不匹配 proof 必须 fixed failure。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### 2-未修复-高-Close Advice exclusion 没有绑定 frozen manifest，且 disabled 分支不能证明没有 open-position requirement

- **位置**: 第 2.3 节安全边界、第 5.3 节局部 provider error、第 6.4 节 publisher 持仓边界
- **问题类型**: 架构边界 / 信任边界 / 最佳实践偏离 / fail-open
- **当前写法**: account_run 把 `close_advice_required_data_plan` path 传给 source publisher；
  publisher 调用 `load_close_advice_required_data_plan()` 检查 degraded symbol 是否与 position
  requirement 重叠。Close Advice 明确禁用时不要求计划。
- **反例/失败场景**:
  1. 同一 run id 下存在另一份 content-valid plan 文件，但它不是 required-data manifest 封存的
     relpath/hash；该文件省略某 open position。`load_*()` 会接受它，publisher 因而把相关
     symbol 的 provider error 误判为 opening-only。
  2. 账户实际有 open option，但配置临时关闭 Close Advice。plan builder 会产生
     `close_advice_enabled=false, requirements=[]`；方案据此跳过计划要求，provider error 可以
     degraded，尽管缺失行情同时影响现有仓位。
- **为什么有问题**: “不涉及持仓”必须由冻结、与本轮 required-data manifest 同一事实链的
  position evidence 正向证明。配置关闭一个 consumer 不等于 open positions 不存在，也不能
  成为放宽取数可靠性的证据。
- **直接证据**:
  - 计划第 57、161、261-265 行把安全边界建立在 plan overlap 上，但明确指定
    `load_close_advice_required_data_plan()`，并允许 disabled 时不要求 plan。
  - `required_data_snapshot.py:146-168` 已把 Close Advice plan relpath 和文件 sha256 封存在
    required-data manifest。
  - `close_advice_required_data.py:382-445` 的 `load_*()` 只验证 plan 自身 schema、run id 和
    content hash；`:450-494` 的 `resolve_bound_close_advice_required_data_plan()` 才验证
    manifest relpath、expected path 和文件 sha256。
  - `close_advice_required_data.py:51-88` 显示 Close Advice disabled 时直接生成空 requirements，
    不读取 open positions，因此不能证明不存在持仓需求。
- **影响**: open short option 的行情缺口可能被当成 opening-only warning，正常 Brief 继续发送
  而没有 position-scoped `not_evaluable` 或 fixed failure，违反方案自己的持仓安全不变量。
- **建议改法和验证点**:
  - 使用已经验证的 required-data manifest 调用
    `resolve_bound_close_advice_required_data_plan()`，不得只读取 request path。
  - Close Advice disabled 时，provider-error degraded 要么继续禁止；要么由 ledger owner 提供
    同 run、account-bound 的 open-option absence proof。不能从 disabled 或空 requirements 推断。
  - 测试同 run 替换 plan、manifest hash mismatch、account entry missing、Close Advice disabled
    但存在 open option，以及真正无 open option 的正常 degraded。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### 3-未修复-高-provider peer 只有同 run 身份约束，没有时间方向，可能把运行中形成的全局故障误判为局部

- **位置**: 第 3 节不变量 7、第 5.3 节局部 provider error、第 8.1/8.2 节验收矩阵
- **问题类型**: 失败语义 / 最佳实践偏离 / 测试缺口 / open question 未收敛
- **当前写法**: 只要当前 run 存在同 source、host、port、market domain 的一个
  `success_rows|success_empty`，且账户仍有一个可靠 opening scope，非 global retcode 的
  provider error 可以 degraded。
- **反例/失败场景**: 09:40:01 A 请求成功，09:40:20 provider 断连，随后 B、C 请求 timeout。
  A 是同 run、同 endpoint/market 的成功 peer，账户也仍有可靠 scope，因此当前规则把 B/C
  当成局部 gap；但 failure 发生时 provider health domain 已整体不可用。若 A 属于较早 wave，
  同 run 的跨度还可能接近整个 30 分钟 freshness window。
- **为什么有问题**: 历史上较早的成功 response 只能证明当时可用，不能证明失败发生时不是
  provider-wide transition。方案虽要求 observation/completion time，却没有在 peer predicate
  中使用它，也没有定义多失败聚合、先后顺序或最后状态。
- **直接证据**:
  - 计划第 77 行和第 157-163 行只约束同 run 与 provider identity；
  - 第 106、208 行要求记录时间，但第 5.3 节判定条件没有时间关系；
  - 第 380-395 行测试只区分相同/不同 endpoint，没有覆盖 success-before-failure、
    success-after-failure 或连续失败。
- **影响**: provider 在 tick 中途整体失效时，系统可能发送“局部问题、其他结果仍有效”的正常
  Brief，而不是全局可信度失败消息；这正是本方案必须避免的错误分类。
- **建议改法和验证点**:
  - 锁定一个保守的时间谓词：例如只接受在 failure completion 之后、同 health scope 的成功
    observation，或与 failure 调用时间窗口重叠的并发成功；较早成功不得证明后续失败局部化。
  - 对同 health scope 全部 terminal outcomes 按时间排序；最后已知状态为失败或连续失败达到
    未定义边界时 fail closed。
  - 若不愿在本 work unit 引入 health temporal semantics，先只交付 `success_empty`，继续让
    provider error fixed failure。
  - 增加 success-before-failure、failure-before-success、并发 overlap、多连续 timeout 和
    mixed global retcode 测试。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

## Open Questions

1. provider-error degraded 是否必须与 `success_empty` 同一 work unit 交付？若不是，先交付
   `success_empty` 可以形成更小且已闭合的第一 slice。
2. 对 Close Advice disabled 的账户，权威的“没有 open option”证明应来自现有 ledger decision
   snapshot，还是直接规定 provider error 不可 degraded？
3. provider peer 的最小安全时间谓词是什么：success-after-failure、调用窗口 overlap，还是更严格
   的最后状态规则？

## Residual risks

- 本计划明确延期 expiration/DTE/side 的部分覆盖；即使修复 findings，symbol-level terminal
  outcome 仍不能安全解释“有部分 rows 但不覆盖某账户策略需求”。建议在后续独立 coverage
  work unit 跟踪。
- `success_empty` 仍依赖 adapter 不吞转换异常。实现时应为 `save_outputs()` 当前宽泛 exception
  路径增加回归测试，确保 validation failure 不被写成成功空。
- 方案测试清单没有显式列出 `tests/test_required_data_prefetch_inprocess.py`、
  `tests/test_pipeline_watchlist_whitelist.py`、`tests/test_symbol_monitoring_fetch_spec_merge.py` 和
  `tests/test_position_advice_source_producers.py`；修订时应把这些 owning-boundary tests 纳入
  focused gate。

## Conclusion

**fail**

严格边界版已经消除了上一版最明显的过度设计，`success_empty` 的最小路径基本成立；但
provider-error degraded 仍缺少被 source graph 采用的不可变证据、持仓排除校验存在 frozen
binding/disabled 空洞，provider peer 也缺少时间语义。这三个问题都会让“只有局部问题才正常发送”
在真实故障中变成 fail-open，因此当前计划还不能直接交给 implementation agent。
