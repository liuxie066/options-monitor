## Findings

### PR-W1A-01-未修复-高-计划新造了第二套 projection content hash，与已确认的 Research artifact provenance 真源冲突

- **位置**: `plan.md` 的 Ranking projection top-level required fields、Validator invariants 和 Rerank invariants。
- **问题类型**: 架构边界 / 契约缺失 / 过度耦合。
- **当前写法**: projection 顶层新增 `content_sha256`，并计划使用 domain `canonical_sha256` 重算；rerank 结果也绑定该 hash。
- **反例/失败场景**: W4 按产品合同把 projection 写入 corpus 时必须附加 `research_artifact_provenance.v1`。W1A 的严格 top-level 白名单会拒绝 `artifact_provenance`；若 W4 改写或双写 hash，同一 artifact 就有两个 content hash 真源。
- **为什么有问题**: 产品合同已明确要求所有新 append-only artifact 复用现有 provenance/hash 合同，不新建 hash 框架。计划把纯投影边界和未来 corpus 持久化绑到了不同语义的 hash。
- **直接证据**: 产品合同 §5.3 固定 `artifact_provenance.content_sha256` 由 `artifact_content_sha256()` 对移除 provenance 后的 compact JSON 计算；§7.2 要求 projection 复用该 Research artifact provenance/write-once 合同。现有 owner 为 `src/application/shadow_replay/common.py:246-310`。
- **影响**: W1A 与 W4 无法共享一份可验证 projection bytes；删除 source run 后的重放证据可能因 hash 语义不一致失效，或迫使后续模块加转换 shim。
- **建议改法和验证点**: 删除顶层 `content_sha256`，把 `artifact_provenance` 纳入严格 schema；直接复用 `attach_artifact_provenance()` / `validate_artifact_provenance()` / `artifact_content_sha256()`，固定 artifact kind 和 opening-snapshot source generation 投影。rerank 只引用 `artifact_provenance.content_sha256`。增加 provenance 缺失、kind/hash/source-generation 冲突测试。
- **修复风险（低/中/高）**: 低。
- **严重程度（低/中/高/严重）**: 高。

### PR-W1A-02-未修复-中-point/snapshot provenance 由三个无关联标量传入，计划没有一条可执行的交叉绑定合同

- **位置**: `plan.md` 的 `build_ranking_projection(opening_snapshot, recommendation_point_id, opening_snapshot_ref, source_commit_sha)` 入参和 Builder invariants。
- **问题类型**: 契约缺失 / 不可直接实施 / seam 过度耦合。
- **当前写法**: 三个 point/provenance 值作为独立标量传入，计划只要求它们非空或符合 hash 外形，没有定义与 snapshot `market/account/run/content hash` 的交叉校验。
- **反例/失败场景**: 调用方把 point A 的 ID 和 ref 与 snapshot B 传入 builder。输出仍可通过自身 hash 校验，后续 corpus 只看 projection 时无法发现它不是同一个正式 point 的 T0 事实。
- **为什么有问题**: 产品合同§7.3 明确要求同时验证 point、projection、account、Sell Put scope、snapshot hash 和 accepted IDs。W1A 可以不拥有 W2 的发布行为，但必须冻结后续 W2 可直接产生的最小 binding 输入，不能把关联语义留给实现者猜。
- **直接证据**: opening snapshot 已封存 `run_id/account/market/content_sha256/account_config_sha256/strategy_policy_sha256`；产品合同§7.1 定义 point ID 为 64 位 SHA-256 且 point 绑定 snapshot path/hash。当前计划未列出这些 cross-field assertions。
- **影响**: 可生成内部一致但语义上错配的长期 corpus projection；后续模块要么信任错证，要么重新定义 v1 schema。
- **建议改法和验证点**: 把三个标量收敛为一个严格 `point_binding` 输入，至少含 64 位 point ID、market/account/run、safe relative snapshot ref、64 位 snapshot content hash、UTC decision time 和 40 位 source commit SHA；全部与 snapshot 交叉校验。W2 仍是 producer point 发布 owner，W1A 只定义/校验这个最小投影输入。增加 point/snapshot/account/run/hash 错配及 absolute/`..` ref 失败测试。
- **修复风险（低/中/高）**: 低。
- **严重程度（低/中/高/严重）**: 中。
