### 1-未修复-严重-股票交割匹配可跨 Futu 账户、价格与时间窗口误配并直接写错权威账本

- **入口/函数**: `resolve_trade_deal()` -> `_find_matching_option_case()` / `_find_matching_stock_evidences()` -> `_stock_matches_lifecycle_close()` -> `_write_v2_lifecycle_close_from_case()` -> `reconcile_lifecycle_evidence()`
- **文件(行号)**: `src/application/trades/lifecycle.py:499-668,829-886,1193-1253`; `src/application/trades/lifecycle_reconciliation.py:819-892`; `src/application/ledger/writer.py:744-798`
- **输入场景**: `lx` 的一个零价期权 close anchor 来自 Futu account `1001`；随后 `lx` 下另一 Futu account `1002` 出现相同标的、方向和数量的普通股票成交，成交价为 `100.09`、期权 strike 为 `100`，股票成交发生在 observation start 十天之后。
- **实际分支**: 候选查询只按 internal account 和 symbol 过滤；case 匹配返回首个命中项。自动匹配不比较 option anchor 与 stock deal 的 Futu account id，非严格价格分支允许 `max(0.01, strike * 0.001)` 浮点容差，且到期后只有时间下界、没有 settlement deadline 上界。writer 的二次校验只检查方向、数量、symbol 和时间下界，也不检查 Futu account id、Decimal 精确 strike 或 deadline。
- **预期行为**: 自动匹配必须同时满足 internal account 和 Futu account id 一致、成交价以 Decimal 精确等于 strike、成交时间位于 observation window，并且候选在所有 pending cases 中全局唯一；writer 必须在事务内重新验证这些条件，任一不满足即 fail closed。
- **实际行为**: 公开 intake 复现返回 `assignment_recorded`，写入一条 assignment terminal event，并将 `contracts_open` 从 `1` 归零；terminal evidence 中保留的股票事实却明确是 `futu_account_id=1002`、`price=100.09`。这把与 anchor 不同账户、不同价格且超出预期窗口的普通股票成交解释成了 assignment。
- **直接证据**: `_find_matching_option_case()` 在首个匹配 case 处直接返回；`_stock_matches_lifecycle_contract_terms()` 使用浮点容差；`_stock_matches_lifecycle_close()` 对任何到期日之后的时间直接接受；`_validate_evidence_for_case()` 没有 Futu account、strike 和 deadline 校验。冻结方案 `docs/plans/option-expiry-close-reason-receipt-redesign-plan-20260730.md:691-717` 明确要求上述全部条件及事务内重验。
- **影响**: 不相关的股票成交可以生成 assignment/exercise terminal event，永久改变 `trade_events -> position_lots` 权威投影，造成持仓数量和后续收益、风控、通知错误；现有 source claim 还会让错误解释获得唯一消费权。
- **建议改法和验证点**: 将 Futu account id 纳入 case/anchor 绑定；使用 Decimal 精确比较 strike；按冻结 timing 的 observation start 与 settlement deadline 双边校验；先收集全部候选并要求全局唯一；在 ledger transaction 中对 source claims、账户、价格、窗口、数量、reservation 和重投影结果全部重验。新增公开 intake 回归：跨 Futu account、`strike ± 0.01`、deadline 后、两个可匹配 cases 均必须进入 review 且无 terminal event；合法唯一匹配才允许写入并精确减少 projection。
- **修复风险（低/中/高）**: 高
- **严重程度（低/中/高/严重）**: 严重

### 2-未修复-严重-close-reason 可在没有 terminal allocation/event 时把案件标记为 ledger_written 并创建最终通知

- **入口/函数**: `reconcile_lifecycle_close_reason()` -> `resolve_close_reason()` -> `advance_lifecycle_case_state()` -> `advance_lifecycle_case_state_atomically()`
- **文件(行号)**: `domain/domain/option_close_reason.py:55-77,327-346`; `src/application/trades/close_reason_reconciliation.py:116-139,254-387`; `src/application/ledger/writer.py:1948-2163`; `tests/test_option_close_reason.py:120-143`
- **输入场景**: lifecycle case 的冻结目标仍有 `2` 张未结；没有 terminal allocations。observation 提供 `stock_match_status="full"`、`stock_contracts=1`，随后以 `apply_changes=True` 执行 close-reason reconciliation。
- **实际分支**: resolver 直接信任 observation 中的 `full` 标记，将状态判为 `resolved`，但 `contracts_resolved` 仍为 `1`，没有与 target/remaining quantity 比较。application 对非 expiration resolution 不走 terminal evidence writer，而是把 `resolved` 映射为 `ledger_written`，再由 state-advance writer创建 `resolution_confirmed` Outbox intent；该 writer 只读取既有 allocation，不写 terminal event，也不要求 remaining 为零。
- **预期行为**: `full` 必须由冻结目标和当前有效 allocation/stock evidence 数量推导，不得由输入自证；任何 resolved/ledger_written 状态、最终通知、terminal allocation/event 和 projection 变化必须在同一 ledger transaction 中完成并相互一致。
- **实际行为**: 可重复复现得到 `decision.status=resolved`、`contracts_resolved=1`、case `status=ledger_written`，但 `terminal_events=[]` 且目标 lot 的 `contracts_open=2`。系统能够对仍完全开放的仓位生成“最终原因已确认”的持久状态和通知意图。
- **直接证据**: `resolve_close_reason()` 对 `stock_match_status == "full"` 无数量一致性校验；`reconcile_lifecycle_close_reason()` 允许 observation 覆盖推导状态，并在普通 resolved 分支只调用 state advance；`advance_lifecycle_case_state_atomically()` 构造 Outbox，但没有 terminal write。现有参数化测试还固定了“目标 2 张、`full` + `stock_contracts=1` 仍 resolved”的错误契约。
- **影响**: case/read model/通知与权威账本发生永久分叉；后续流程可能把未平仓头寸当作已完成，而投影仍保留原数量。重复执行还会受到既有 transition key 和 state fingerprint 约束，增加受控修复难度。
- **建议改法和验证点**: 删除外部 `stock_match_status` 对 full/partial 的决定权；仅从有效 evidence、allocation 和 frozen remaining 推导；所有 assignment/exercise resolution 统一进入 terminal reconciliation writer；writer 在事务内断言 resolved quantity、allocation、terminal events、case status、projection 和 Outbox 一致。新增 0/partial/full/over-allocation 测试，其中 `full` 数量不足必须 fail closed，只有 terminal event 写入并重投影归零后才允许 `ledger_written` 和 `resolution_confirmed`。
- **修复风险（低/中/高）**: 高
- **严重程度（低/中/高/严重）**: 严重

### 3-未修复-高-lifecycle case 身份缺少 Futu account id，两个经纪账户的 option anchors 会合并到同一案件

- **入口/函数**: broker intake -> `accept_option_close_evidence()` -> `accept_option_close_evidence_atomically()` -> `build_lifecycle_case()` / `lifecycle_case_key()`
- **文件(行号)**: `domain/domain/option_lifecycle.py:67-132`; `src/application/ledger/writer.py:1132-1415`; `src/application/trades/lifecycle_runtime.py:155-177`
- **输入场景**: 同一个 internal account `lx` 映射了两个 Futu account；两边各有一笔同 contract 的零价 close evidence，且权威 lot 有足够数量容纳两笔 reservation。
- **实际分支**: 每个 evidence/source claim 会正确保留自己的 canonical Futu account id，但 case key 只包含 internal account、broker、contract、side、expiration 和 lot ids。接收下一笔 evidence 时，既有 case 也只按 internal account 与 `contract_key` 复用，不比较 Futu account id。
- **预期行为**: lifecycle case 必须绑定 internal account 与唯一 Futu account id；不同 Futu account 的 option anchor 不得共享 case、reservation、settlement observation 或最终原因。
- **实际行为**: 复现中来自 `1001` 和 `1002` 的两笔 anchors 返回相同 `case_id`，case 本身没有 `futu_account_id`，其 evidence/source claims 同时包含两个 Futu account id。到期轮询却从运行时 source 选择单一 Futu account 查询，因此一个混合 case 可能用错误账户的 observation 收敛。
- **直接证据**: `lifecycle_case_key()` 与 `build_lifecycle_case()` 没有 Futu account 参数或字段；`accept_option_close_evidence_atomically()` 虽验证 canonical source prefix，却在 `1257-1270` 仅按 account 与 contract 复用 case；`lifecycle_runtime.py:155-177` 要求 source 恰有一个 Futu account id，却无法从 case 校验该绑定。冻结方案在第 9 行和 canonical identity 不变量中明确要求双重账户身份。
- **影响**: 不同经纪账户的证据、reservation、settlement observation 和原因可能交叉污染；即使 stock matcher 单独补上账户判断，case 级身份缺失仍会使自动收敛和迁移无法可靠证明账户归属。
- **建议改法和验证点**: 将规范化 Futu account id 纳入 `lifecycle_case_key`、持久化 case 字段、既有 case 查找和所有 reconcile/observation 边界；为旧 case 提供 fail-closed 的受控迁移，无法唯一映射的进入 review。新增同 internal account/同 contract/不同 Futu account 的隔离测试，以及旧 case 单一映射、歧义映射和 repeat migration 测试。
- **修复风险（低/中/高）**: 高
- **严重程度（低/中/高/严重）**: 高
