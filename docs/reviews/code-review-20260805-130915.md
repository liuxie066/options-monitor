## Findings

### DR12-01-未修复-高-claim 缺少统一完成边界，非崩溃异常仍会遗留租约并绕过持久退避

- **入口/函数**: `reconcile_due_lifecycle_cases_for_source()` provider preclaim、collection/reconciliation、post-write candidate refresh
- **文件(行号)**: `src/application/trades/lifecycle_runtime.py:787-848, 935-1139, 1178-1257`; `src/application/trades/inbox.py:18`; `src/application/trades/settlement_attempts.py:510-580`
- **输入场景**: provider case 已经 eligible 并成功 claim，随后出现任一普通 Python 异常：共享 account read-model/validation 构建失败、collector contract 的自定义实现抛出异常、canonical reconciliation 抛出未列举的异常，或写后 compact candidate refresh 抛出异常。
- **实际分支**: 第一个 case 在共享 account materialization 之前预先 claim；每个 case 在 provider 调用前 claim。lease guard 的 `finally` 只停止续租线程，不调用 `complete_settlement_attempt()`。`complete_settlement_attempt()` 仅位于整段 happy-path 尾部，因此上述异常直接越过 outcome 更新和 claim 清理。
- **预期行为**: 除真实进程崩溃或 claim ownership 丢失外，每个已获取的 claim 都必须在单一收口点完成：已调用 provider 的未知处理异常持久化为 `unknown_error` 并进入 5 分钟起步的有界退避；provider 前的准备失败至少释放 claim并留下有界、可诊断的控制状态；控制库不可写则明确返回 `control_store_unavailable`。
- **实际行为**: control row 保留 `claim_id/claim_until_ms`，没有 `reason_code`、没有 outcome、没有指数退避。120 秒租约到期后同一 case 再次 eligibility，可能重新执行昂贵 account materialization 或 provider 调用；listener 只会记录外层通用异常。
- **直接证据**: `lifecycle_runtime.py:794-820` 在 `lifecycle_case_read_models_for_account()` 之前获取 preclaim，而 `827-848` 无异常清理；`990-1127` 只处理列举异常且会重抛其他 `ValueError`，collector 自身也不受 runtime fallback 约束；`1197-1210` 的 post-refresh `try/finally` 只停止 guard；唯一的 `complete_settlement_attempt()` 在 `1246-1256`。`inbox.py:18` 把最短租约定义为 120 秒，`settlement_attempt_updates_after_outcome()` 才是写入 backoff 并由 complete 清除 claim 的路径。
- **影响**: DR11 只修复已知 canonical 畸形字段仍不足以闭合故障类；任何未预见异常、版本偏差或临时读失败都可把“每次异常”退化为“每个 lease 再做一次昂贵工作”，重新形成 CPU/延迟尖峰，并丢失可观测的失败分类。
- **建议改法和验证点**: 抽出 claim completion/failure helper，把从首个 preclaim 开始的每条非崩溃退出路径纳入统一收口。provider 后未知异常应生成不含原始错误文本的 `unknown_error/settlement_attempt_processing_failed`，保留 exception class 作为受限诊断字段，写入 backoff 并清 claim；provider 前失败应释放或持久化准备阶段退避，且不能增加 provider-attempt count。对 pre-read、collector、reconciliation、post-refresh 四个注入点做 fake-clock 测试，分别证明 claim 清除、调用计数、下一次 eligibility 和 control-store failure 行为。
- **修复风险（低/中/高）**: 高
- **严重程度（低/中/高/严重）**: 高

## Residual Risk

- 真正的进程退出仍依赖 lease expiry，这是预期 crash-recovery 语义；不能在另一 worker 可能仍持有 ownership 时主动清理。

- 本 review 不把 settlement attempt contract 推广到其他 periodic jobs；其他 job 需要分别采用该 contract 才获得同等保护。
