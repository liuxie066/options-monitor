### MR109-INTEGRATION-03-未修复-中-delivery-only no-send 被记录为已发送
- **入口/函数**: `run_tick_notification_flow()` 的 persisted-envelope delivery-only retry
- **文件(行号)**: `src/application/tick_notification_flow.py:400-445`
- **输入场景**: scheduled no-scan wake-up 找到 retryable exact envelope，同时 operator 以 `--no-send` 运行验证。
- **实际分支**: delivery decision 返回 `should_send=false`；通用 no-send 分支把全部 message accounts 放入 `sent_accounts`，随后 delivery-only 分支以非空 `sent_accounts` 完成。
- **预期行为**: provider 未尝试时 delivery state 保持 pending，运行应明确记录 skipped/no-send，并与真实 provider-confirmed send 区分。
- **实际行为**: provider 和 confirmation 都未执行，但 idempotency completion message 记录为 `delivery_only_sent`，`run_end` 也按成功发送语义携带 `sent_accounts`。
- **直接证据**: `else: sent_accounts = list(account_messages.keys())` 后，delivery-only 使用 `"delivery_only_sent" if sent_accounts else "delivery_only_no_send"`；当前测试没有覆盖 delivery-only + no-send 组合。
- **影响**: 状态确认本身不会错误推进，但运行日志/idempotency 证据会声称已发送，导致 operator 误判重试结果和排障历史。
- **建议改法和验证点**: delivery-only + no-send 单独完成为 `skipped/delivery_only_no_send`，记录 `would_send_accounts` 而不是 `sent_accounts`；新增回归证明 provider 未调用、envelope 仍 pending、completion 未声称 sent。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
