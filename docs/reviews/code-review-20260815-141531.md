### 1-未修复-中-US 被 Corpus 公共契约接收，但必然在 HK-only feature owner 处失败
- **入口/函数**: `seal_day_expectation()` / `capture_recommendation_point()` -> `_identity()` -> `_feature_enabled()` -> `effective_feature_status()`
- **文件(行号)**: `src/application/strategy_lab/top1/corpus.py:95-102, 189-211, 459-468, 674-679`; `src/application/strategy_lab/top1/lifecycle.py:114-120`; `docs/plans/sell-put-top1-optimization-loop-mvp-20260814.md:68-69`; `docs/gateflow/sell-put-top1-w4/plan.md:105-110`
- **输入场景**: 调用方按 W4 artifact/API contract 传入 `market="US"`，并期望得到 feature/Corpus 命令结果。
- **实际分支**: Corpus `_identity()` 接受 `HK|US`，schema v2 也允许 US；随后 `_feature_enabled()` 调用仍由首发纵切拥有的 `effective_feature_status()`，后者只接受 HK 并抛 `experiment_invalid`，再被改写为 `CorpusError(corpus_input_invalid)`。
- **预期行为**: 首发范围应与已确认总设计一致，只公开 `HK/lx`；若未来扩 US，应由单独能力确认统一扩展 feature/lifecycle/Corpus，而不是让当前 API 半接受。
- **实际行为**: 公共边界和持久化 schema 表示 US 可用，但实际每条持久命令都无法通过 feature gate；这是可静态证明的死分支合同。
- **直接证据**: Corpus line 97 接受 `{"HK", "US"}`；lifecycle line 115 明确要求 `market == "HK"`；总设计 line 69 明确 US 需另行补能力和确认。
- **影响**: US 调用方得到与公开 contract 相反的输入错误；schema/artifact 面提前固化未获授权的市场范围，增加后续合同漂移。
- **建议改法和验证点**: 将 W4 plan、Corpus identity/artifact validator 和 v2 Corpus CHECK 一致收窄为 HK；补 US 明确 `corpus_input_invalid` 且零写入测试。未来 US 扩展单独改完整 owner 链。

- **严重程度（低/中/高/严重）**: 中

### 2-未修复-中-已进入 conflict 的 day 重试会返回一个从未发布的 artifact hash
- **入口/函数**: `seal_day_expectation()` existing conflict / indexed-artifact failure branches -> `_seal_result()`
- **文件(行号)**: `src/application/strategy_lab/top1/corpus.py:419-443, 510-523`
- **输入场景**: 第一次 seal 成功；第二次用不同 schedule/calendar 触发 day conflict；第三次再用任意新 denominator 重试，或原 indexed artifact 已缺失/篡改。
- **实际分支**: line 512 发现 DB 已是 conflict 后，直接把本次尚未 publish 的 `payload, content` 传给 `_seal_result()`；line 520 的 artifact-invalid 分支同样如此。`_seal_result()` 无条件填入构造路径及本次 bytes/content hashes。
- **预期行为**: conflict 结果只能引用 SQLite 保留的原始 immutable artifact，或者把 artifact 三字段置空；不能声明未落盘的 proposed bytes。
- **实际行为**: 返回 `status=conflict`，但 `artifact_sha256` / `artifact_content_sha256` 可能既不等于 DB 原事实，也没有对应文件。
- **直接证据**: publish 只发生在 line 526 之后；两个提前返回点位于 publish 之前，而 `_seal_result()` line 432-441 仍计算并返回 proposed content 的 ref/hash。
- **影响**: 调用方、回执或后续审计若保存该 conflict envelope，会得到无法读取且与 SQLite 不一致的证据引用，破坏 artifact-first 的一致性承诺。
- **建议改法和验证点**: 为 existing conflict 构建基于保留 row 的 conflict result（或统一 null artifact fields）；补“成功 -> drift conflict -> 再次不同 drift”及“indexed artifact 被篡改”回归，断言返回引用与持久事实一致。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 3-未修复-中-非法 timezone 绕过 CorpusError 的稳定错误合同
- **入口/函数**: `seal_day_expectation()` -> `scheduled_scan_targets_for_date()` -> `ZoneInfo()`
- **文件(行号)**: `src/application/strategy_lab/top1/corpus.py:478-482`; `src/application/scan_scheduler.py:417-453`
- **输入场景**: feature 已启用，schedule 含未知 timezone，例如 `{"timezone":"Not/A_Zone", ...}`。
- **实际分支**: `ZoneInfo()` 在 scheduler line 436 抛 `ZoneInfoNotFoundError`（`KeyError`）；Corpus 只捕获 `TypeError|ValueError`，所以异常原样逃逸。
- **预期行为**: W4 plan 已将 `CorpusError.reason_code` 限定为四种；非法 caller schedule 应稳定失败为 `corpus_input_invalid`，不泄漏平台异常。
- **实际行为**: 同类非法 schedule 有些映射为 `CorpusError`，timezone 这一支却以不同异常类型中断调用。
- **直接证据**: catch tuple 不包含 `KeyError` / `ZoneInfoNotFoundError`；scheduler helper 也未转换该异常。
- **影响**: W7 调用该 API 时无法只按 Corpus contract 处理输入失败，可能把可解释配置错误当未捕获任务崩溃。
- **建议改法和验证点**: 在 scheduler public wrapper 将非法 timezone 规范化为 `ValueError`，或在 Corpus 边界显式捕获 `ZoneInfoNotFoundError` 并映射 `corpus_input_invalid`；补零写入回归。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
