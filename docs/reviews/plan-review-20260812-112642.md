## Reviewed scope

The review challenged the proposed two-slice retirement of AI Decision Advice, with particular attention to the
independent validity of each slice, immutable Daily Brief digest compatibility, frozen-delivery retry semantics,
configuration error contracts, shared DeepSeek/Assistant ownership, and whether the plan stays inside the confirmed
product-removal goal.

## Assumptions tested

1. Slice 1 can be committed and tested independently while Slice 2 still owns removal of Tick handoff plumbing.
2. Starting the common Daily Brief normalizer from `dict(source)` is compatible with both “new normalized Briefs omit
   retired keys” and “public reads never expose retired fields.”
3. Notification flow can safely inspect a referenced immutable Brief revision without defining a repository-owned raw
   inspection contract.
4. Removing `ai_decision_advice` from YAML passthrough keys while adding only a runtime-validator tombstone gives an
   operator a targeted retirement error on every supported config entry path.
5. The proposed compatibility mechanisms are necessary safety work rather than a replacement feature or unrelated
   architecture expansion.

## Findings

### PR-01-未修复-高-Slice 1 会在 Slice 2 前移除被现有 Tick 调用仍传入的 Brief 参数
- **位置**: Slice 1 “Exact allowed changes” 第 1 项；Slice 2 “Exact allowed changes” 第 2 项
- **问题类型**: 切片过粗 / 不可直接实施 / 过度耦合
- **当前写法**: Slice 1 删除 Advice assembly parameters；Slice 2 才删除 `TickNotificationRequest` 字段和
  `_advice_handoff_for_account()`。
- **反例/失败场景**: Slice 1 提交后，`_prepare_daily_brief_notification()` 仍把 `_advice_handoff_for_account()` 返回的
  `prepared_portfolio_distribution`、`prepared_option_positions_context` 等关键字传给
  `assemble_daily_decision_briefs()`。如果 Slice 1 已删除这些参数，任何实际 scan 路径都会在 deterministic Brief 组装前
  抛出 unexpected-keyword `TypeError`。
- **为什么有问题**: Gateflow 要求每个 accepted slice 是可运行、可验证的行为增量；当前切分要求 Slice 1 暂时依赖 Slice 2
  才能恢复调用契约，因此不能形成安全 checkpoint。
- **直接证据**: 当前 `tick_notification_flow.py:736-750` 无条件计算并展开 Advice handoff；当前
  `daily_decision_brief_service.py:614-669` 接收并继续传递这些参数。Plan 将 handoff helper 删除明确放在 Slice 2。
- **影响**: Slice 1 commit 破坏 scheduled tick；focused unit tests 可能因没有覆盖真实 handoff 展开而漏报，后续 review
  无法把两 slice 的回归隔离。
- **建议改法和验证点**: Slice 1 只删除模型调用和输出字段，暂时保留并明确忽略旧的私有 handoff 参数；Slice 2 在同一
  change set 中删除 Tick request/handoff 字段、Brief 参数和 Advice-only preparation module，并把
  `daily_decision_brief_service.py` 加入 Slice 2 allowed files。增加一个 Slice 1 回归，向 assembler 传入旧 handoff 参数并
  断言无模型调用且输出无 retired fields；Slice 2 再断言调用签名/请求对象不再包含这些字段。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### PR-02-未修复-高-公共 normalizer 保留 retired keys，和新写入及公共读取契约冲突
- **位置**: “Passive historical compatibility” 第 1–3 项；Slice 1 “Exact allowed changes” 第 2 项
- **问题类型**: 契约缺失 / 架构边界 / 非最优方案
- **当前写法**: Plan 让 `normalize_daily_decision_brief()` 从 `dict(source)` 开始并保留旧字段，再依赖各产品投影执行
  copy-and-strip。
- **反例/失败场景**: 任何调用者把旧 Brief、测试 fixture 或带 retired keys 的对象传给
  `persist_daily_decision_brief_success()`，公共 normalizer 都会把字段继续带入新 revision。新增或遗漏一个读取投影时，也会
  再次暴露旧字段；兼容正确性依赖每个消费者都记得 strip。
- **为什么有问题**: `normalize_daily_decision_brief()` 是共享的写入和读取规范化边界。Goal 要求新 normalized/persisted
  Brief 及公共输出都不含 Advice；把删除责任分散到多个 view/renderer 会制造负向名单耦合。历史 digest 兼容需要保留的是
  磁盘原始字节和旧 digest 计算，不是让 retired fields 继续存在于当前 normalized contract。
- **直接证据**: 当前 `domain/domain/daily_decision_brief.py:214-258` 从源对象复制全部 key；当前 repository 在写入和读取
  校验中都调用该 normalizer。Plan 自身同时要求 “new normalized/persisted Briefs omit retired keys” 和 normalizer “may
  preserve legacy retired fields”。
- **影响**: retired fields 可被再次持久化或经遗漏的公共读路径泄漏，导致“彻底删除”只在已知 renderer 上成立；后续新增
  consumer 还会继承隐式兼容负担。
- **建议改法和验证点**: 当前 normalizer 必须无条件删除两个 retired keys。`daily_brief_compatible_digests()` 在收到原始
  persisted mapping 时，分别计算当前 stripped payload digest，以及仅将原始 retired key/value 重新附加到同一规范核心的
  legacy payload digest；不得解析、补默认值或接受任意 mismatch。repository 原始文件保持不写。测试应证明：normalizer
  对带旧字段输入也 strip；旧 fixture 的既有 digest 仍被接受；篡改核心字段或旧字段仍造成 digest mismatch；新 write
  不可能重新持久化旧字段。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR-03-未修复-中-冻结重试检查没有锁定 repository-owned 原始 revision 契约
- **位置**: “Frozen retry state”；Slice 1 “Exact allowed changes” 第 4 项
- **问题类型**: 架构边界 / 不可直接实施 / 状态机漏洞
- **当前写法**: Plan 只说 notification boundary 使用 private predicate 检查 referenced persisted revision，并用 Markdown
  markers 作为 defense-in-depth，没有指定读取、身份校验、digest 校验或 card payload 检查的 owning function。
- **反例/失败场景**: 实现者可能从 notification flow 自行拼 revision path/read JSON，绕开 repository 的 account/market/date/
  revision 和 digest 校验；也可能只扫 `rendered_message`，但旧 Feishu `rendered_transport` 中仍有退休文案。若 normalizer 按
  PR-02 正确 strip，notification flow 通过普通 Brief read 又无法看见原始 retired keys。
- **为什么有问题**: revision 路径、严格 JSON、identity 和 compatible digest 均由 repository 所有；跨层重读会产生第二套
  storage protocol。冻结 envelope 的可发送性判断必须与 repository 已验证的 source revision 绑定，且检查发生在任何
  text/card outbound map 写入之前。
- **直接证据**: 当前 `_normalize_delivery_envelope()` 会调用
  `daily_decision_brief_repository._validate_successful_revision_source()` 校验 revision，但该 helper 只返回 normalized Brief；
  notification flow 在 `tick_notification_flow.py:697` 和 `:941` 直接复制 frozen message/transport。
- **影响**: guard 可能被 path/version skew 绕过、误判合法 failure envelope，或只阻断 fallback 文本而让 card payload 泄漏；
  同时形成 repository ownership 穿透。
- **建议改法和验证点**: 在 repository 内定义唯一 read-only inspection contract，由已验证的 retry envelope 解析其 raw
  successful revision，复用 strict read/identity/compatible-digest 校验，并返回稳定分类
  `legacy_ai_payload_retired | clean`；message 及完整 normalized transport 的 marker scan 也由该 contract 或一个纯函数统一
  覆盖。notification flow 只消费分类并在两条 retry path 的 map 写入前阻断。测试覆盖 raw field、message-only marker、
  card-only marker、clean successful Brief、clean fixed failure、missing/corrupt source，以及 pending/ambiguous 状态不变。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 中

### PR-04-未修复-中-YAML 作者入口会先报 generic unknown key，达不到 targeted retired-key contract
- **位置**: “Configuration”；Slice 2 validation
- **问题类型**: 公共契约 / 测试缺口
- **当前写法**: Plan 从 `PASSTHROUGH_KEYS` 删除该 key，仅要求 runtime `validate_config()` 对 exact key 给 targeted error。
- **反例/失败场景**: 操作者把现有 `ai_decision_advice` 留在 `config.yaml` 根或 market override 时，
  `yaml_to_market_user_config()` 在调用 runtime validator 之前由 `_reject_unknown_keys()` 报通用“不支持”，并提示一长串 allowed
  keys；不会说明功能已退休。
- **为什么有问题**: `config.yaml` 是项目的 human authoring source。Goal 明确要求 authored/runtime config contract 都不再
  支持，并让 validation 描述 retirement；只修 runtime JSON 路径遗漏了主要 operator 入口。
- **直接证据**: 当前 `config_yaml.py:152-167` 对 allowed set 外的 key 直接给 generic error；`:614-631` 在 build early
  validation 中先调用它；当前 key 同时允许于 root 和 market passthrough。
- **影响**: 升级后的配置失败缺少可执行迁移信息，config validate/build 四条 gate command 无法证明 retirement UX。
- **建议改法和验证点**: 在 YAML unknown-key owner 处识别 exact retired key，并在 root 与 market 两个 path 发出同一 targeted
  “AI Decision Advice has been retired; remove this section” 错误；runtime JSON validator 保留对应 tombstone。新增 root YAML、
  market YAML、runtime JSON 三个 exact-message regression，并证明相近拼写仍走普通 unknown-key 错误。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

## Lens conclusions

- **Goal-bound minimal design**: legacy digest compatibility and retry blocking directly map to confirmed safety
  signals; no replacement AI or unrelated candidate change is required. Findings PR-02/03 narrow these mechanisms
  rather than expanding scope.
- **Architecture boundary**: Plan correctly preserves Candidate Engine, option-position, Close Advice, generic
  portfolio queries, and shared LLM providers. PR-03 is the remaining storage ownership violation risk.
- **Best practice / optimal solution**: stripping at the canonical normalizer plus reconstructing exact legacy digest
  candidates is simpler and safer than a strip list in every public projection.
- **Overengineering**: no schema v2, migration, service tombstone, or replacement abstraction is justified. A single
  repository inspection result and two exact retired config sentinels are the minimum compatibility surface.
- **Overcoupling**: PR-01 is a concrete transient coupling between two slices; the rest of the two-slice structure is
  credible after resequencing the private call contract.

## Open questions

None. All four findings can be resolved inside the confirmed goal and approved file ownership without user-visible
scope change.

## Residual risks and destination

- Existing installed collector services after source removal — `assigned to later work unit` requiring separately
  authorized production service reconciliation.
- Historical Advice/Evidence/Brief disk usage — `assigned to later work unit` requiring explicit destructive-data
  authorization.
- Unknown third-party consumers of internal Daily Brief Python functions — `fixed in current slice` through temporary
  Slice 1 compatibility parameters, then repository-wide call/import proof before Slice 2 removal.
- Provider-side delivery already accepted before retirement — `assigned to later work unit`; immutable provider history
  is outside this source work unit and no replay/retraction is authorized.

## Final conclusion

`fail`. The overall retirement direction and two-slice size are sound, but PR-01 and PR-02 make the current plan unsafe
to hand to implementation. Resolve all four findings, produce a re-review artifact, and only then create the accepted
plan commit.
