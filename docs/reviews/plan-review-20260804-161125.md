## Assumptions tested

- all configured expected Futu account IDs are alternatives, so matching any one is sufficient broker identity readiness;
- a per-account broker binding may be resolved independently in US and HK configs without an explicit cross-config equality/union rule;
- a quote-route conflict or outage can be introduced into the current auto-intake lifecycle path without changing broker capture/apply availability or ledger ordering;
- creating the quote gateway in a source loop does not imply eager quote readiness;
- the existing assigned-stock OpenD endpoint override can change from override to equality assertion without an explicit public contract migration;
- additive health capability fields can preserve compatibility without naming exact schema/tests;
- three matched windows and the frozen MAD threshold can distinguish a material resource change without claiming causality from source tests.

## Predecessor finding resolution

The repaired plan materially closes the five findings from `plan-review-20260804-151803.md`:

1. **Unproven performance/security claim — resolved.** The plan separates source correctness from incident closure, labels the two-process shape logical routing rather than privilege isolation, and adds baseline/post-change gates.
2. **Coupled quote/trade gateway — resolved.** It specifies independent lazy clients, typed builders/readiness, close behavior, caller spies, and a compatibility facade.

## Findings

### PR-01-未修复-高-Broker readiness 只要求命中任一 account ID，且没有跨 US/HK 的每账户绑定一致性契约

- **位置**: plan `§3 Broker-binding derivation and compatibility` / `Broker identity readiness` / `§6.2 Runtime route inventory` / gateway tests; lines 98-122, 184-194, 323-342.
- **问题类型**: 身份权威不完整 / 跨配置漂移 / 健康误绿
- **当前写法**: broker binding 按单个 runtime config 解析；readiness 在 `get_acc_list()` 中找到“at least one” configured expected account ID 即通过。P0 会列出每个 binding，但只明确规定 quote binding 不收敛时停止，没有规定同一 account 在 US/HK 的 broker endpoint、`trd_env` 和 ID 集如何合并或冲突。
- **反例/失败场景**: 一个逻辑账户通过 legacy trade mapping 映射到两个 Futu account IDs；OpenD 的 `get_acc_list()` 只返回其中一个，broker readiness 仍为 green，但 portfolio 代码随后会逐个查询全部 configured IDs。另一种场景是 `lx` 在 US config 解析到 `11111/REAL`、在 HK config 解析到 `11112/REAL`；两个 config 分别合法，P0 也能列出它们，但“每账户一个 broker plane”实际变成按 market 漂移的两个 endpoint。
- **预期行为**: readiness 必须验证本次 caller 真正需要的完整 ID 集，而不是任一候选；同一逻辑 account 在所有 selected runtime configs 上必须有明确的 endpoint/environment/identity 聚合规则。若 market-specific account IDs 合法，应保留 market provenance、形成显式 required union，并验证每一个；若不合法，应在 P0/validation fail closed。
- **实际行为**: implementation agent 可以按计划实现 `configured_ids ∩ observed_ids != ∅`，同时允许跨 config endpoint 漂移，导致 health 通过但部分账户事实查询失败或路由到不同 OpenD。
- **直接证据**: `src/application/account_config.py:355-366` 的 legacy mapping 会返回映射到同一 account 的全部 IDs；`:229-234` 将该列表作为 account IDs。`src/application/futu_portfolio_context.py:505-521` 取得整个 ID set 后对它查询 balance/positions。`src/application/account_config.py:257-279` 的 runtime plan 是按单个 config 构造，没有跨 config equality。Futu 官方也要求在其他交易调用前取得并确认正确的 trading account：<https://openapi.futunn.com/futu-api-doc/en/trade/get-acc-list.html>。
- **影响**: 账户现金/持仓/成交证据可能部分缺失，health 仍显示 broker ready；跨市场配置可把同一账户事实分流到不同进程，破坏本方案最核心的 per-account broker authority。
- **建议改法和验证点**: 定义一个带 config/market provenance 的 account binding set。对每个 account 明确要求 endpoint 和 `trd_env` 跨 selected configs 一致；account ID 选择“完全相等”或“显式 union”之一并写入计划。Readiness 要求 `required_ids` 是 observed eligible IDs 的子集，并对每个 required ID 校验环境；additional OpenD accounts 仍可忽略。新增 US/HK endpoint mismatch、environment mismatch、two-required-one-observed、market-specific union complete/incomplete 测试，并让 P0 和 Gate F 对任何冲突 fail closed。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### PR-02-未修复-高-Auto-intake 对 quote binding/readiness 失败的降级顺序不明确，可能把行情故障升级成交易接入停机或改写现有 ledger 顺序

- **位置**: plan decision 4 / authority table / `§8.4 Mixed lifecycle path` / caller tests; lines 18, 44, 65, 296-308, 350-351.
- **问题类型**: 状态机歧义 / 可用性耦合 / 写入顺序风险
- **当前写法**: 计划同时要求 quote failure 不阻塞 broker、auto-intake source loop 创建 quote gateway、quote-route conflict 在 apply 前阻断 lifecycle writes，并保持现有 `needs_review` 行为；没有规定 source-loop 使用 lazy 还是 ready quote builder，也没有区分静态 binding conflict、瞬时 quote outage 和 CLI due-reconcile 的处理顺序。
- **反例/失败场景**: sy broker push 健康但共享 quote endpoint 暂时 down。若 source loop 用 `build_ready_futu_quote_gateway()`，listener 在建立交易连接前就退出，造成成交接入/回补中断。若实现者为满足“conflict prevents lifecycle writes before apply”而把 calendar preflight 移到 `_process_payload()` 前，又改变当前 ledger/inbox transaction sequence。反过来，若保持当前顺序，trade payload 已应用后 calendar 才失败，测试中的“before apply”便不成立。
- **预期行为**: 必须按入口定义失败矩阵。建议 auto-intake 保持 broker transport/inbox/apply 独立，quote gateway lazy 使用；静态 conflict 或瞬时 quote failure只让 timing evidence 走既有 `lifecycle_timing_policy_unavailable -> needs_review`，不能阻断 push/backfill。只读/显式 `reconcile-due` CLI 可在自身 apply 前 fail closed。若要让配置冲突阻断整个 listener，则这是新的交易状态机/可用性策略，应从本 work unit 移出。
- **实际行为**: 当前计划支持两种相反实现；其中一种会漏掉/延迟交易接入，另一种会改变 ledger 写入顺序，且两者都可能声称满足部分 acceptance 文本。
- **直接证据**: `src/application/trades/auto_intake.py:1270-1303` 先执行 `_process_payload()`，之后才调用 lifecycle timing；异常只写入 result 的 `needs_review` 诊断。`src/application/trades/lifecycle_runtime.py:48-137` 在 calendar unavailable 时按现有流程将 case 转为 `needs_review`。这正是计划声称要保留的状态机，但计划没有把它与 source-loop gateway construction 和 CLI preflight 分开。
- **影响**: 行情单点故障可能连带停止 broker trade intake，或为消除歧义而意外改变安全关键的 ledger/inbox 状态顺序。
- **建议改法和验证点**: 增加入口 × 失败类型矩阵：listener startup、push apply、backfill、periodic due reconcile、CLI dry-run/write；分别覆盖 missing/conflicting binding、quote login down、broker login down。明确 auto-intake 的 quote gateway 为 lazy/non-blocking dependency并保持 `_process_payload -> timing` 顺序；明确 only CLI due-reconcile 的 config preflight 可以在其写入前退出。新增“quote down, broker push仍应用且 case needs_review”“quote conflict 不停止 listener”“broker down 仍按原 listener recovery”“CLI conflict zero write”测试。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

## Architecture boundary review

The revised plan now respects the main ownership boundaries: quote authority comes from effective fetch bindings, broker authority is account-scoped, direct listener state remains unchanged, and HOME/service/Incus work is deferred. The remaining architecture gap is not another layer; it is the exact cardinality of broker identity across configs and the degraded-dependency contract at the lifecycle composition root.

No capture/applier entity, provider registry, quote-owner config, or HOME migration is needed to close the new findings.

## Best-practice review

The lazy-client and typed-readiness design is testable and follows least-coupling principles. Broker readiness should use complete required identity, not existential identity. Safety-critical intake must also distinguish an auxiliary market-data dependency from its primary durable broker path so an outage cannot silently widen blast radius.

The measurement plan is appropriately separated from source correctness. Its relative-MAD threshold, zero-median handling, natural-window constraint, and separate absolute incident criteria avoid claiming a performance win from tests alone.

## Optimal-solution review

The narrow optimal correction remains the plan's chosen direction:

1. aggregate and validate one complete broker binding set per account across selected configs;
2. split SDK capability clients/readiness;
3. migrate pure callers;
4. split mixed callers while preserving auto-intake ordering and degraded behavior;
5. measure before any HOME, listener-process, or capacity redesign.

The plan does not need a broader topology or new state machine. It needs two missing contracts made explicit.

## Overengineering review

The new quote-route inventory is justified because several current callers choose endpoints differently. Keeping it pure and derived avoids a second authority. A generalized provider registry, fallback graph, third OpenD, per-account capture processes, and HOME migration remain correctly excluded.

The capability-aware watchdog/doctor is a wider slice, but it is necessary: otherwise health itself continues to activate quote work on broker-only endpoints and cannot verify the intended architecture.

## Overcoupling review

Most previous overcoupling is removed. The unresolved coupling is operational: source-loop construction can still couple shared quote readiness to account trade intake unless the plan explicitly makes quote a lazy degraded dependency. Public assigned-stock override semantics are also coupled to the route-authority change and need their own compatibility contract.

## Open Questions

1. For one logical OM account present in multiple runtime markets, must Futu account IDs be identical, or is the required identity the union of market-scoped IDs?
2. Must broker host/port and `trd_env` be identical across US/HK for the same account? If not, the target should be renamed from per-account to per-account-per-market broker planes.
3. On an auto-intake static quote-binding conflict, should broker push/backfill continue and lifecycle timing become `needs_review`, or should startup block? The latter expands the trade-state availability contract.
4. Is `option_positions_read` explicit OpenD endpoint selection intended as a supported diagnostic escape hatch? If yes, it needs a named mode and must be excluded from scheduled routing; if no, it needs a documented contract migration.
5. Which exact legacy health fields must remain byte/semantic compatible when typed capability results are added?

## Residual Risks and tracking

- Even after both blocking findings are fixed, OpenD may retain the same mmap working set with zero OM quote clients; track host closure in the Incus experiment artifact, not in source completion.
- One shared quote endpoint remains a generic market-data single point of failure and is exposed to quote-right kicking/quota constraints.
- The lx physical OpenD can still combine quote and lx broker capabilities; logical routing is not strong isolation.
- Capability-aware health probes themselves generate provider calls. Keep option-field probes quote-only, bounded, and outside high-frequency broker health loops.
- Multi-process listener isolation, HOME/device migration, service topology, and capacity changes remain separate future work units and must not be pulled into fixes for PR-01/PR-02.

Suggested tracking destinations:

- PR-01: revise the account broker-binding/readiness sections and P0/F tests in the reviewed plan;
- PR-02: add an auto-intake degraded-dependency matrix and deterministic state-order tests to the reviewed plan;
- PR-03: close in the same plan revision if assigned-stock route semantics remain in scope, otherwise preserve the existing override and defer its contract change;
- resource outcome: existing Incus remediation experiment artifact;
- listener/HOME/security isolation: separate plans only if independently justified.

## Final Plan Review Conclusion

`fail`

The repaired plan successfully closes all five predecessor findings and establishes the right architecture direction. It is not yet code-generation-ready because broker identity can pass on only a subset of required accounts and because the auto-intake quote-failure order permits two incompatible implementations, one of which can stop trade intake. The public tool/health contract gap is secondary but should be closed in the same revision.

Revise only these narrow contracts; do not reintroduce listener process splitting, HOME migration, a new quote-owner config, or unmeasured capacity changes. Re-run planreview after the broker binding set and auto-intake degradation matrix are explicit.
