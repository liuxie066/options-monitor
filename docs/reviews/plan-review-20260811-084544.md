## Findings

### 1-未修复-中-lifecycle 删除 staggered→diagonal 映射后，旧 `structure_mode=staggered_expiry_pair` 行会被误判为 same_expiry_mismatch 而非 unsupported

- **位置**: plan Slice 3「lifecycle: `_expiry_structure` 删 staggered 映射；inventory 只接受 `{same_expiry}`」
- **问题类型**: 状态机漏洞 / 契约缺失 / 不可直接实施
- **当前写法**: plan 只说删除 staggered→diagonal 映射并让旧 diagonal 落入 `unsupported_expiry_structure` → `review_required`；未规定 `_expiry_structure` 对 `structure_mode=staggered_expiry_pair`（无显式 `expiry_structure` 快照）的返回值。
- **反例/失败场景**: 现有/历史行带 `strategy_snapshot.structure_mode=staggered_expiry_pair` 但无 `expiry_structure` 字段。`_expiry_structure`（`domain/domain/combo_yield_lifecycle.py:27-38`）当前先读 `expiry_structure`，再读 `structure_mode`，其中 `staggered_expiry_pair→diagonal`；删除该映射后，此类行会落入函数末尾的默认 `return "same_expiry"`，随后在 `:164-165` 因 put/call 到期不同而报 `same_expiry_mismatch`，而不是 `unsupported_expiry_structure`。
- **为什么有问题**: 用户决策是「错期不支持，fail-closed 为 review_required」。`same_expiry_mismatch` 是误导性归因（把错期错标为同期错配），无法从 inventory issue 识别历史错期数据，与 R1 的历史兼容说明不一致。
- **直接证据**: `combo_yield_lifecycle.py:27-38` 默认分支返回 `"same_expiry"`；`:81` 只对 `not in {"same_expiry","diagonal"}` 报 `unsupported_expiry_structure`；`:162-165` 在非 diagonal 且到期不同时报 `same_expiry_mismatch`。plan R1 声称「存量/未来错期数据将落入 unsupported_expiry_structure」。
- **影响**: 旧错期行被错误分类、review 人员被误导；success signal 中「旧 diagonal/错期数据落入 fail-closed 路径」不成立。
- **建议改法和验证点**: plan 明确：`_expiry_structure` 保留对 `structure_mode=staggered_expiry_pair` 或显式 `expiry_structure=diagonal` 的识别，返回 `"diagonal"`；inventory 校验集改为只含 `{"same_expiry"}`，`diagonal` 落入 `unsupported_expiry_structure`。新增/改写测试：旧 staggered 行断言 `summary_classification=="review_required"` 且 `"unsupported_expiry_structure" in inventory_issues`，且不出现 `same_expiry_mismatch`。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 2-未修复-中-直接删除归因 diagonal 校验会让旧 diagonal 组静默流入绩效报告

- **位置**: 修改点 5 / Slice 3「归因: 删 diagonal 到期序校验」
- **问题类型**: 状态机漏洞 / 非最优方案 / 契约缺失
- **当前写法**: plan 将 `domain/domain/performance/strategy_attribution.py:145-148` 的 diagonal 到期序校验直接删除。
- **反例/失败场景**: 归因输入直接来自事件快照的 strategy 组（`engine.py:304 build_strategy_attribution(events, allocations, facts, ...)`），不经过 lifecycle inventory 的 `unsupported_expiry_structure` 过滤。测试 `test_performance_attribution.py:37-49` 与 `test_performance_strategy_attribution.py:59,336-341` 表明带 `expiry_structure=diagonal` 的事件会进入归因且当前被校验/接受。删除该校验后，旧 diagonal 组将作为普通 same-expiry 组参与绩效计算，不再被标记为 invalid。
- **为什么有问题**: 用户在生命周期面要求 fail-closed（review_required），绩效面却变成 silent-accept；两个消费端行为不一致。生产数据当前无 diagonal 存量（风险低），但 plan 的 R1 历史兼容承诺覆盖绩效面时失效。
- **直接证据**: `strategy_attribution.py:144-148` 当前对 diagonal 且 call<=put 报 `invalid_diagonal_expiry_order`；`engine.py:304` 归因不经 lifecycle classification；`attribution.py:12,62` 的 `expiry_structure` 直接来自事件拓扑。
- **影响**: 旧错期数据在绩效报告中静默按同期归因，产生错误 PnL/资本拆解，且无 review 信号。
- **建议改法和验证点**: 改为 fail-closed：删除 diagonal 到期序校验，但保留/新增「非 same_expiry 结构一律 `unsupported_expiry_structure`」校验，使 diagonal 组落入 `partial` + issue，而不是静默通过。改写两个 performance 测试：diagonal 组断言 `partial`/`strategy_group_invalid`，same-expiry 正常组保持通过。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
