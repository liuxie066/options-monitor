## Scope

- Goal / Non-goals / Success Signal / Goal Alignment / Design Alignment
- Implementation Decisions / Slices / Tests / Docs / Risks
- 重点压测：角色互换后的结构校验、配置契约、独立扫描依赖、snapshot 耦合、Daily Brief 边界

## Assumptions Tested

1. variant=cc_lp 能承载 CC+LP 且不破坏 sp_lc 现有行为；
2. 角色互换后 strike_order 语义正确（call > put）；
3. Sell Call 独立扫描复用 required-data，不新增网络取数；
4. cc_lp_candidate_snapshot.v1 独立文件不与现有 combo snapshot 冲突；
5. Daily Brief 消费 CC+LP 快照且不改通知格式；
6. 无持仓 → not_applicable。

## Findings

### 1-未修复-高-角色互换后 strike_order 语义可能被复用错误

- 位置: Plan §4、§9 Slice 1（validate_yield_enhancement_pair 复用）、确认文档 §3
- 问题类型: 契约缺失 / 状态机漏洞
- 当前写法: 新增 compute_cc_lp_metrics 薄封装（复用底层指标，换角色与保留率下限），且 §9 Slice 1 写复用 validate_yield_enhancement_pair
- 反例/失败场景: 现有 validate_yield_enhancement_pair 硬编码 put_leg.strike >= call_leg.strike → reject。若 CC+LP 直接复用而不换角色参数，会把 call_strike > put_strike 的正确组合全部拒绝（因为现有校验要求 put < call）；若简单反转参数，又会放行 call < put 的非法结构。确认文档 §3 明确 call_strike > put_strike 是必须，但 plan 未说明底层校验如何参数化角色。
- 为什么有问题: 复用是正确方向，但角色参数化缺失会导致实施 agent 要么写出行为相反的校验、要么 hack 反转参数顺序，破坏 SP+LC 现有行为或放行非法结构。
- 直接证据: yield_enhancement.py:150-151 硬编码 if put_leg.strike >= call_leg.strike: rejects.append(strike_order)；yield_enhancement.py:22-28 已定义 funding_put / participation_call 角色枚举。
- 影响: 实施 Agent 跑偏 / 生成错误代码 / SP+LC 回归 / 非法 CC+LP 结构放行。
- 建议改法和验证点: 在 domain 层把 strike_order 校验参数化为角色（funding_leg / reversal_leg），按角色决定比较方向；新增测试断言 CC+LP 下 call > put 通过、put > call 拒绝，且 SP+LC 现有测试保持全绿。
- 修复风险（低/中/高）: 中
- 严重程度（低/中/高/严重）: 高

### 2-未修复-中-objective 与 variant 双概念职责重叠，契约可能过度

- 位置: Plan §7（combo_yield.variant ∈ {sp_lc, cc_lp} + objective 增加 premium_funded_long_put）、Slice 2
- 问题类型: 过度设计 / 契约重复
- 当前写法: 同时新增 variant 枚举和扩展 objective（premium_funded_long_put）
- 反例/失败场景: 现有 objective 已唯一取值 premium_funded_long_call，且 derive_yield_enhancement_policy 强制 mode = YIELD_ENHANCEMENT_INCOME_UPSIDE_MODE。若同时改 objective 和 variant，配置面出现两个表达选哪个结构的字段，validator 需要校验两者一致性（如 variant=cc_lp 但 objective=premium_funded_long_call 冲突），增加实现与维护成本；若只用一个字段，则另一个是冗余。
- 为什么有问题: 违反 Goal-bound minimal design：确认文档没有要求 objective 扩展，只要求变体承载。双字段导致契约重复与一致性死锁。
- 直接证据: yield_enhancement_config.py:14 YIELD_ENHANCEMENT_OBJECTIVES = {premium_funded_long_call}；config_validator.py:640-643 对 objective 唯一枚举校验；yield_enhancement_config.py:206 mode 固定。
- 影响: 实施 Agent 过度设计 / 配置校验复杂化 / 后续维护双字段一致性问题。
- 建议改法和验证点: 只新增 variant（sp_lc/cc_lp），objective 保持 premium_funded_long_call（描述资金腿收权利金 + 反转腿表达的上层目标），variant 决定具体结构；或反之只用 objective 扩展。二选一，不要双概念。
- 修复风险（低/中/高）: 低
- 严重程度（低/中/高/严重）: 中

### 3-未修复-中-objective 单一枚举在 config_validator 的硬编码需要同步改

- 位置: Plan Slice 2（config validator）
- 问题类型: 契约缺失 / 实施缺口
- 当前写法: plan 只写 objective 增加 premium_funded_long_put，但若按 Finding 2 二选一保留 objective 扩展，validator 的 YIELD_ENHANCEMENT_OBJECTIVES 集合必须同步改，且 derive_yield_enhancement_policy 的 mode 推导逻辑也要支持新 objective。
- 反例/失败场景: 只改 config 默认值不改 validator 集合 → 配置校验拒绝新 objective；只改 validator 不改 policy 推导 → mode 仍强制 income_upside，角色语义错位。
- 为什么有问题: plan 对改哪里不够 code-generation-ready，实施 agent 可能漏改联动点。
- 直接证据: yield_enhancement_config.py:206 mode = YIELD_ENHANCEMENT_INCOME_UPSIDE_MODE 硬编码；config_validator.py:640-643 枚举校验硬编码。
- 影响: 配置校验拒绝 / 角色语义错位 / 实施返工。
- 建议改法和验证点: 若保留 objective 扩展，必须把 YIELD_ENHANCEMENT_OBJECTIVES、derive_yield_enhancement_policy 的 mode 推导、config_validator 枚举三处联动写进 plan 的 exact allowed changes，并加配置单测。
- 修复风险（低/中/高）: 低
- 严重程度（低/中/高/严重）: 中

### 4-未修复-低-Sell Call 独立扫描的 avg_cost / shares 依赖未在 plan 中显式列出

- 位置: Plan §8 Implementation Decision 2、Slice 2
- 问题类型: 契约缺失 / 实施缺口
- 当前写法: 复用 run_sell_call_scan 输出，再经 enrich_and_filter_covered_call_underwriting、无持仓 → not_applicable
- 反例/失败场景: run_sell_call_scan 的 CandidateScanConfig 要求 avg_cost（计算 effective_min_strike = avg_cost * 1.02）和 shares（容量）；CC+LP 独立扫描需要从持仓上下文注入这些值。plan 未说明 CC+LP 的 Sell Call 独立扫描如何获取 avg_cost/shares（同 run_sell_call_scan_and_summarize 的 stock 参数，还是别处）。
- 为什么有意义: 无持仓跳过已确认，但有持仓时独立扫描的输入来源是实现必需细节；不写清 agent 会猜或复用错误来源。
- 直接证据: scan_sell_call.py:320-343 effective_min_strike 依赖 avg_cost；sell_call_steps.py:113-118 无持仓上下文 → not_applicable。
- 影响: 实施 Agent 猜输入来源 / 复用错误 / 扫描结果错误。
- 建议改法和验证点: plan 显式写明 CC+LP 的 Sell Call 独立扫描从 portfolio_ctx 注入 stock（与 run_sell_call_scan_and_summarize 一致），无 stock → not_applicable。
- 修复风险（低/中/高）: 低
- 严重程度（低/中/高/严重）: 低

### 5-未修复-低-Daily Brief 展示边界未完全收紧

- 位置: Plan §8 Implementation Decision 6、Slice 3、§12 Risks
- 问题类型: 范围漂移风险
- 当前写法: Daily Brief 消费快照但不改通知格式，§12 写若需完整展示，作为后续 work unit
- 反例/失败场景: 若 Daily Brief 仅读取快照而不渲染，那它读的意义是什么？如果 Slice 3 顺手把 CC+LP 渲染进 Daily Brief（改 renderer），就超出不改通知格式的非目标。
- 为什么有问题: 非目标说不改通知格式，Slice 3 又说消费快照，两者边界模糊，实施 agent 可能顺手改渲染。
- 直接证据: daily_decision_brief_service.py:841-879 消费 combo snapshot 且写 _source_path；daily_decision_brief_renderer.py 是渲染所有权。
- 影响: 范围漂移 / 通知格式意外改变。
- 建议改法和验证点: 明确定义 Slice 3 的消费= 加载快照到决策数据源（供未来展示用），不改 renderer；展示改造独立为后续 work unit。
- 修复风险（低/中/高）: 低
- 严重程度（低/中/高/严重）: 低
