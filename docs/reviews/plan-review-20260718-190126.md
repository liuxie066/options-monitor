# Plan Review — Python 3.12 Runtime Contract

## Reviewed target and scope

- Target: `docs/gateflow/python312-runtime-contract-plan-20260718-185616.md`
- Branch/base: `codex/python312-runtime-contract` from `origin/main@e128b412`
- Review type: adversarial Gateflow plan review
- Scope: runtime selector semantics, launcher/install bootstrap boundaries, import guards, service-upgrade runtime/cache behavior, CI, generated commands, tests, and residual direct-shebang risk

## Assumptions tested

1. One candidate order can safely serve launchers, test tooling, release preflight, and venv-creation tooling.
2. `OM_PYTHON` precedence is compatible with the promise that an incompatible repo venv is never bypassed.
3. Import guards in `src` and `domain` fail before deeper unsupported syntax/type evaluation on Python 3.9.
4. A sourced shell helper can validate missing/broken candidates without `set -euo pipefail` terminating the caller unexpectedly.
5. Service upgrade can use `sys.executable` for venv creation while keeping dependency cache identity stable at implementation + major/minor + platform + dependency inputs.
6. Direct internal shebang execution is a classified residual risk rather than an accidentally supported public path.
7. Fake-interpreter tests can exercise selection, version rejection, argv forwarding, and remediation without depending on the host Python version.

## Findings

### PR-001-未修复-高-显式 override 与“不允许绕过坏 venv”契约互相矛盾
- **位置**: `Launcher selection contract` 第 84–90 行；runtime contract assertions 第 233–234 行
- **问题类型**: 契约缺失 / open question 未收敛
- **当前写法**: 候选顺序把 `OM_PYTHON` 放在 repo `.venv/bin/python` 之前，同时声明“现有不兼容 repo venv 是错误且不会被静默绕过”。
- **反例/失败场景**: `.venv/bin/python` 是 Python 3.11，同时操作员显式设置 `OM_PYTHON=/opt/python3.12`。按候选顺序会成功启动并绕过坏 venv；按第 90 行则必须失败。实现者可以合理地写出两种相反行为，测试也无法确定正确预期。
- **为什么有问题**: 这是 public launcher 的核心 precedence/state contract，不是实现细节。尤其 `OM_PYTHON` 最有价值的修复场景正是临时绕过错误或缺失的 repo venv；如果允许，应明确这是“显式绕过，不是静默绕过”；如果不允许，则 `.venv` 必须在 `OM_PYTHON` 前验证。
- **直接证据**: plan 第 84–90 行；成功信号要求 deterministic selection；S1 stop condition 明确把 precedence ambiguity 定义为停止条件。
- **影响**: 实施 Agent 跑偏 / 测试契约互斥 / 操作员修复路径不确定。
- **建议改法和验证点**: 明确采用一种语义。推荐：`OM_PYTHON` 是唯一允许显式绕过 repo venv 的 escape hatch；未设置 `OM_PYTHON` 时，存在的 repo venv 必须先验证且不兼容即失败，不能继续到 `PYTHON`/PATH。分别增加“显式 override 绕过坏 venv成功”和“无 override 时坏 venv阻断 fallback”测试。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### PR-002-未修复-高-venv bootstrap 脚本不能复用会优先选择目标 venv 的同一策略
- **位置**: `First-Principles Judgment` 第 61–67 行；`Affected Files` 第 100–105 行；`Shell selector` 第 140–147 行；S1
- **问题类型**: 架构边界 / 状态机漏洞 / 测试缺口
- **当前写法**: 一个 shared selector 按 repo `.venv` 优先的顺序服务所有 repository tooling，其中包含 `scripts/install_agent_plugin.sh`；该脚本随后执行所选 Python 的 `-m venv .venv`。
- **反例/失败场景**: repo 已有兼容 `.venv` 时，selector 返回 `.venv/bin/python`，然后脚本让该解释器创建/覆盖它自身所在的 `.venv`。这会把 bootstrap source 和 mutation target 绑定在一起，可能失败、产生部分重建，或让已有环境被意外修改。repo 已有不兼容 `.venv` 时，通用策略又会在安装脚本本应提供修复入口时直接阻断。
- **为什么有问题**: launcher/test execution 与 venv bootstrap 是不同 ownership/state transition。前者应优先使用已安装依赖的 repo venv；后者必须选择外部 bootstrap interpreter，并在任何 mutation 前验证 >=3.12。一个无 profile 的统一 candidate order 不能同时满足两者。
- **直接证据**: 当前 `scripts/install_agent_plugin.sh` 第 5、10 行使用外部 `${PYTHON:-python3}` 创建 `.venv`；plan 将其列入 shared selector consumers，但未定义 skip-repo-venv/bootstrap mode。
- **影响**: 安装路径不可恢复 / 环境部分覆盖 / 计划实施后 installer 行为退化。
- **建议改法和验证点**: 保留一个 helper，但明确两种窄入口或参数化 profile：`select_repo_python`（launch/test，考虑 `.venv`）与 `select_bootstrap_python`（创建 `.venv`，绝不选择目标 `.venv`，顺序为显式 override -> `python3.12` -> diagnostic `python3`）。`install_agent_plugin.sh` 必须先 dry validation 再执行 venv mutation；测试覆盖已有兼容/不兼容 `.venv` 时 bootstrap source 都不指向目标 `.venv`。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

## Open questions

- `OM_PYTHON` 是否被定义为可显式绕过不兼容 repo venv 的恢复入口？推荐是。
- `scripts/install_agent_plugin.sh` 对已存在 `.venv` 的既有重建/复用语义是否需要保持？至少必须保证 bootstrap interpreter 不来自目标 venv；具体 `venv --clear`/失败行为不应在本 work unit 擅自新增。

## Residual risks and tracking destination

- Arbitrary internal file executed directly via `#!/usr/bin/env python3` may still reach an old interpreter before package guards. Plan has明确 non-goal and residual-risk classification; track in docs/runtime contract rather than broad shebang churn in this work unit.
- `./.venv/bin/python` generated commands require a prepared dev environment. This is an intentional explicit dependency failure rather than interpreter ambiguity; retain as documented operational prerequisite.
- Patch-level 3.12 drift remains accepted by the minimum-minor contract; service-upgrade cache identity should continue to include implementation, major/minor, platform, and dependency inputs.

## Conclusion

**fail**

The scope and overall direction are sound, but the plan cannot enter implementation until override precedence and bootstrap-vs-repo selector semantics are made internally consistent and directly testable.
