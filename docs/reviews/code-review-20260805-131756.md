## Findings

### DR13-01-未修复-高-续租 guard 启动和 completion 计算仍在保护区外，资源耗尽时 claim 继续泄漏

- **入口/函数**: `_SettlementClaimLeaseGuard.start()`；`reconcile_due_lifecycle_cases_for_source()` provider processing/post-refresh；nested `complete_claim()`
- **文件(行号)**: `src/application/trades/lifecycle_runtime.py:144-148, 1078-1097, 1294-1324, 1376-1394, 568-603`
- **输入场景**: 已获取 claim 后，本机因线程/资源压力使 `threading.Thread.start()` 抛 `RuntimeError`；或 post-refresh 返回畸形 candidate，使 `case_scope_fingerprint()` 抛异常；或持久控制行中的计数异常使 `settlement_attempt_updates_after_outcome()` 在调用 control operation 前抛异常。
- **实际分支**: 两次 lease guard 都通过 `... ).start()` 在对应 `try` 之前启动；start exception 因而绕过 DR12 新增的 processing/refresh catch。post scope 和 completion updates 也在最后一次受保护的 refresh `try` 之后计算。nested `complete_claim()` 只包装 SQLite operation，不包装 updates 构造。所有这些路径都发生在 claim acquisition 之后且不会执行 claim completion。
- **预期行为**: claim 的结构性边界应覆盖从 ownership 获得到 `complete_settlement_attempt()` 提交的全部普通异常，包括 guard 建立、scope/update 计算；后台续租无法启动时不得调用 provider，并应在仍持有初始租约时持久化 preparation failure、清 claim 和设置 backoff。
- **实际行为**: 线程启动失败会直接向 listener 冒泡并保留 120 秒 claim；在高 CPU/线程压力的真实故障条件下，这条路径比普通业务异常更可能发生。scope/update 计算异常同样绕过 outcome 和 backoff，证明当前“统一 completion helper”仍是调用约定而非不可绕过的所有权保证。
- **直接证据**: `_SettlementClaimLeaseGuard.start()` 在 `thread.start()` 周围没有捕获；第一次 `.start()` 位于 `lifecycle_runtime.py:1080-1096`，其 processing `try` 从 `1097` 才开始；第二次 `.start()` 位于 `1307-1323`，refresh `try` 从 `1324` 才开始；`case_scope_fingerprint(post_candidate)` 位于 `1379`，`settlement_attempt_updates_after_outcome()` 位于 nested helper `579-587`，两者都没有 failure completion fallback。
- **影响**: 系统最需要退避保护的资源紧张状态仍可退化为 lease 周期重试，并且 provider 前的 guard-start failure 没有结构化诊断；这会破坏 DR12 宣称的“所有非崩溃路径完成 claim”不变量。
- **建议改法和验证点**: 让 guard start 把本地启动失败记录为 guard error而不是向外抛，且在任何 provider 调用前检查该 error并通过 owned completion 写 `unknown_error`；post guard 同理。把 post-scope 和 update 计算纳入同一 owned failure fallback，或将 complete helper 自身改为先安全构建 updates、构建失败时用最小合法 unknown-error updates 完成 claim。注入两个 guard-start failure 和一个 completion-preparation failure，证明 provider 不被调用、claim 清空、backoff 持久化；ownership-lost 行为保持不变。
- **修复风险（低/中/高）**: 高
- **严重程度（低/中/高/严重）**: 高

## Residual Risk

- 真正的进程崩溃仍只能等待 lease expiry；本 finding 只要求普通 Python exception 不模拟成 crash。
- 当 control DB 写失败或 ownership 已转移时，当前 worker不得强制清 claim；返回 `control_store_unavailable` / `claim_ownership_lost` 仍是正确行为。
- 多 case 的共享 preparation failure 目前每次只给已拥有的首个 case 设置退避；这是避免无 claim 覆盖并发 worker 状态的保守选择，不在本 finding 中扩大为 source-global breaker。
